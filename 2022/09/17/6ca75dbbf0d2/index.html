Linux基础命令——后端开发必备运维技能

发布于 2022-09-17 分类：技术, 2022, 工程化 👁

前言

实际项目部署在矿区机房，日常运维、日志排查、JVM 监控全靠 Linux 命令。我经历过”磁盘打满导致服务假死”、”CPU 飙高 100% 排查束手无策”的事故现场，慢慢总结出一条认知：后端开发不需要成为 Linux 专家，但必须有一套”事故现场肌肉记忆”——出了问题，手指知道往哪敲。

这篇文章不按命令字母排序，而是按排查场景组织，每个场景给出一条完整的命令链。

场景一：日志排查（80% 的日常）

核心命令链：tail + grep

grep 的参数优先记四个：-i（忽略大小写）、-n（行号）、-c（计数）、-A/-B（上下文）。时间跨度大时配合 less app.log 用 /关键词 搜索、G 跳末尾、gg 回开头。

统计分析：awk + sort + uniq 三件套

这三条管道是排障高频组合，理解一次终身受用：awk 取列 → sort 排序（uniq 只对相邻行去重，所以必须先排序）→ uniq -c 计数 → sort -rn 按次数倒序 → head 取前 N。

场景四：进程与端口

kill -9 的代价：Spring 的优雅停机、正在处理中的请求、消息消费位点保存全部被跳过。生产环境先 kill，等 30 秒无效再 -9——这个顺序错过的代价可能是一次数据不一致。

场景五：Java 进程运行时诊断

jstat 输出速读：关注 FGC（Full GC 次数）是否持续增长、FGCT（总耗时）占比——FGC 每小时好几次，堆要么太小要么有泄漏。

网络连通性排查

“服务连不上”三步定位：ping（网络层）→ telnet（传输层，不通基本是防火墙/安全组）→ curl（应用层，通了不通就是应用/路由问题）。每一层排除，二分钟收敛到根因。

安全红线

命令 风险 规矩
rm -rf <path> 不可逆删除 先 mv 后处理；删除前 ls 确认路径；绝不带变量通配符执行
kill -9 跳过优雅停机 先普通 kill 等 30 秒
chmod -R 777 全目录开放权限 用最小权限（644/755）
生产环境 yum install 引入不可控依赖 走审批与变更流程

总结

  1. 日志排查一条链：tail -F（注意轮转用大写 F）+ grep -A/-B/-n + sed -n '/开始/,/结束/p' 截时间段；
  2. 统计三件套 awk | sort | uniq -c | sort -rn | head 的管道逻辑要理解而非背——uniq 只去重相邻行，所以 sort 必须在它前面；
  3. 磁盘打满先 df -h 再逐层 du -sh | sort -rh，df/du 对不上查 lsof | grep deleted（句柄未释放）；
  4. CPU 飙高四板斧：top → top -Hp → printf "%x" → jstack | grep nid，5 分钟定位到代码行；
  5. kill -9 是最后手段，先给优雅停机 30 秒；rm -rf 先 mv 后删，永不直接删；
  6. 不需要成为 Linux 专家——把这几个事故场景的命令链练成肌肉记忆，就超过大多数开发者了。
