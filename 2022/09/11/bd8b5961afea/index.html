Git团队协作——从单兵作战到团队开发

发布于 2022-09-11 分类：技术, 2022, 工程化 👁

前言

最初用 Git 只会 commit 和 push，一个人开发倒也没问题。加入团队后，代码冲突、分支管理、合并回滚各种问题接踵而来。最惊险的一次：我在未 pull 的情况下直接 git push -f，把同事刚提交的代码整个覆盖掉了——那天下午我一边道歉一边系统学了一遍 Git 的分支模型和撤销体系。

这篇文章按”日常操作 → 分支模型 → 冲突处理 → 事故救援”组织，重点讲清楚每个操作背后的模型，因为 Git 的坑都源于”只背命令不懂模型”。

建立模型：三个区，一切命令都在它们之间搬运

理解了三个区域，所有 Git 命令突然变得好记：

flowchart LR
    A["工作区
（你正在编辑的文件）"] -->|git add| B["暂存区
（下次要提交的内容）"]
    B -->|git commit| C["版本库
（本地提交历史）"]
    C -->|git push| D["远程仓库
（团队共享）"]
    D -->|git fetch / pull| A
  • git diff 比较的是工作区 vs 暂存区；
  • git diff --cached 是暂存区 vs 最新提交；
  • 撤销操作的本质是”把文件从某个区拉回上一个区”，见下面的场景矩阵。

日常操作

查看信息

git blame 配合 git log -p <hash> 是”考古”标准链路：先找行归属，再看那次提交的完整上下文。

撤销操作：按所处阶段选择命令

这是新手最容易迷路的地方，做成矩阵就清楚了：

场景 命令 说明
改了还没 add git restore <file> 丢弃工作区修改（不可恢复，谨慎）
已 add 还没 commit git restore --staged <file> 撤回暂存，工作区保留
已 commit 还没 push git reset --soft HEAD~1 撤销提交，修改保留在暂存区
已 commit 还没 push git reset --hard HEAD~1 撤销提交并丢弃修改（高危）
想改上次提交信息/补文件 git commit --amend 只用于未 push 的提交

reset 三种模式一句话区分：--soft 只动 HEAD（修改保留在暂存区）、--mixed（默认）动 HEAD 和暂存区（修改保留在工作区）、--hard 三区全动（修改丢弃）。--hard 前先想三秒。

分支管理

命名与流程模型

日常功能开发的标准循环：

merge vs rebase：选哪个？黄金法则是什么？

维度 merge rebase
历史 真实但分叉 线性整洁
安全性 不改写历史 改写 commit hash
适用 合入主干 功能分支同步上游

黄金法则：rebase 只用于自己独占的分支（未 push 或只有你一个人在用）。 对共享分支 rebase 等于改写公共历史，其他人 pull 之后整个仓库错乱——这就是我当年覆盖同事代码的根因。共享分支一律 merge（团队建议 merge --no-ff，保留功能分支的边界）。

解决冲突

标准流程：打开冲突文件 → 逐个标记手动取舍（注意别把两个都保留造成重复代码）→ 删标记 → git add → git commit（merge 场景）或 git rebase --continue（rebase 场景）。随时可以 git merge --abort / git rebase --abort 整体撤回。

减少冲突的四个习惯：小步快跑（MR 粒度小，前面 review 文章提过 400 行红线）、频繁 rebase 同步 develop、团队按模块分工、公共文件改动提前在群里打招呼。

Commit 规范：写给三个月后的自己和全团队

规范 commit 不只是好看：CI 可以按 type 自动生成 CHANGELOG，git log --grep "^fix" 一键拉出某个版本的修复清单，回滚时也能快速圈定范围。

第一次知道 reflog 的时候我是震惊的：它让”手滑”从灾难变成了小插曲。reflog 是本地最后的安全网，但它救不了未提交的 --hard 工作区修改。

3. 开发到一半要切分支

4. fetch 和 pull 的区别（多人协作必懂）

git pull = fetch + merge，会把远程的合并直接灌进你的工作分支；建议日常用 git fetch 先看一眼 git log HEAD..origin/develop，再决定 merge 还是 rebase——对远程发生的变更保持知情权。

.gitignore：第一次提交前就该写好

两个坑：.gitignore 只对未跟踪文件生效，已经提交的文件要先 git rm --cached <file> 再 ignore；密码类配置一旦提交过，即使后续删除，历史里仍然存在——敏感信息泄露后要换密码，删文件没用。

总结

  1. 一切命令围绕三个区：工作区 → add → 暂存区 → commit → 版本库 → push → 远程；撤销操作就是反向搬运；
  2. 撤销矩阵记场景：未 add 用 restore，已 commit 未 push 用 reset --soft，--hard 永远想三秒；
  3. merge 与 rebase 的黄金法则：rebase 只碰自己独占的分支，共享分支一律 merge（建议 --no-ff）——这条法则背后就是我覆盖同事代码的事故；
  4. 冲突处理靠预防：小 MR、频繁 fetch 同步、按模块分工；
  5. git reflog 是本地最后的安全网，reset 错了 90 天内都能救回来；但未提交的工作区修改没有安全网；
  6. commit 规范写给三个月后的自己和 CHANGELOG 自动化；敏感配置一旦进过仓库历史，删除文件也无济于事，直接换密码。
