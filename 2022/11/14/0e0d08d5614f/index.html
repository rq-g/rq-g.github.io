跨域问题——从No Access-Control到CORS配置

发布于 2022-11-14 分类：技术, 2022, SpringBoot 👁

前言

前后端分离后，矿端前端调用后端接口经常报 “No ‘Access-Control-Allow-Origin’” 错误。在实际场景中，矿端前端部署在 mine.example.com，后端 API 部署在 api.mine.example.com，不同子域名导致跨域。最初我以为是后端接口有问题，后来才知道这是浏览器的同源策略导致的跨域问题。学会 CORS 配置后，跨域问题迎刃而解。

本文将从实际项目的真实场景出发，系统讲解跨域的原理、CORS 配置和各种解决方案。

什么是跨域？

同源策略

浏览器要求：协议、域名、端口三者完全相同，才是同源。

同源判断规则

  • URL1: http://mine.example.com:80/page
  • URL2: http://api.mine.example.com:8080/users
  • 协议：都是 http ✅
  • 域名：mine.example.com ≠ api.mine.example.com ❌
  • 端口：80 ≠ 8080 ❌
  • 结论：不同源 → 跨域！

跨域场景

跨域场景判断

  • URL1 URL2 是否跨域
  • http://localhost:8080 http://localhost:3000 跨域(端口)
  • http://mine.example.com http://api.mine.com 跨域(域名)
  • http://example.com https://example.com 跨域(协议)
  • http://example.com:80 http://example.com 同源(80默认)
  • http://example.com/a http://example.com/b 同源(路径)

非跨域场景

为什么要有同源策略？

同源策略的作用

  1. 恶意网站的JS可以读取银行网站的Cookie
  2. 恶意网站可以向银行网站发送请求（携带Cookie）
  3. 恶意网站可以读取银行网站的响应内容
  4. 恶意网站的JS可以发送请求，但浏览器会拦截
  5. 如果目标网站没有配置CORS，浏览器不会把响应交给JS
  6. 保护了用户的敏感数据

CORS

CORS（Cross-Origin Resource Sharing）是浏览器提供的一种机制，服务端通过设置响应头告诉浏览器允许跨域。

简单请求

简单请求

  • 条件：
    • 方法：GET / HEAD / POST
    • Content-Type：text/plain / multipart/form-data
  • application/x-www-form-urlencoded
    • 无自定义请求头
  • 流程：
  • 浏览器 GET → 服务器
  • 浏览器 ← 响应 服务器
  • |
  • | 检查响应头：Access-Control-Allow-Origin
  • | 包含当前源？→ 允许JS读取响应
  • | 不包含？→ 拦截响应，报跨域错误

预检请求

预检请求（Preflight）

  1. 浏览器先发 OPTIONS 请求（预检）
  2. 服务器返回允许的配置
  3. 预检通过，浏览器发送实际请求
  4. 服务器返回响应（带CORS头）

跨域携带 Cookie

allowCredentials 注意事项

  • allowCredentials = true 时：
  • ❌ allowedOrigin 不能用 *
  • 浏览器会拒绝：Credentials flag is ‘true’,
  • but the ‘Access-Control-Allow-Origin’ header is ‘*’.
  • ✅ 必须指定具体域名
  • config.addAllowedOriginPattern(“http://mine.example.com“);
  • 原因：如果允许任何源携带Cookie，
  • 恶意网站就能带着用户的Cookie访问你的API

跨域常见问题

1. 配置了 CORS 还是跨域

CORS 配置了还是跨域的常见原因

  • 原因1：Filter/Interceptor在CORS之前拦截了OPTIONS请求
  • 解决：确保CORS配置优先级最高，OPTIONS请求不被Auth拦截
  • 原因2：Nginx和SpringBoot都配了CORS
  • 症状：响应头有两个Access-Control-Allow-Origin
  • 解决：只在一处配置CORS
  • 原因3：allowCredentials=true但origin用了*
  • 症状：浏览器报错Credentials flag
  • 解决：指定具体域名
  • 原因4：自定义请求头未在allowedHeaders中声明
  • 症状：预检请求失败
  • 解决：addAllowedHeader(“Authorization”)
  • 原因5：自定义响应头未在exposedHeaders中声明
  • 症状：前端JS读取不到自定义响应头
  • 解决：addExposedHeader(“X-New-Token”)

生产环境跨域方案

生产环境跨域方案对比

  • 方案1：Nginx反向代理（推荐）
  • 前端和API都通过Nginx，同域不同路径
  • www.mine.example.com/ → 前端
  • www.mine.example.com/api/ → 后端
  • 优点：完全同源，无需CORS
  • 缺点：需要Nginx配置
  • 方案2：CORS配置
  • 后端配置CORS，允许前端域名
  • mine.example.com → api.mine.example.com
  • 优点：配置简单
  • 缺点：每次请求都要CORS头
  • 方案3：网关统一处理
  • Spring Cloud Gateway统一配置CORS
  • 优点：所有微服务统一配置
  • 缺点：需要网关基础设施
  • 推荐：方案1（Nginx反向代理）最简单可靠

总结

跨域是前后端分离的必经之路。在实际场景中，从”看到跨域报错就慌”到”理解原理 + 正确配置”，核心认知是：跨域是浏览器的安全策略，CORS 是服务端的授权机制。开发环境用代理、生产环境用 Nginx 反向代理，是最简单的解决方案。

关键收获：

  • 跨域是浏览器行为，服务端之间调用不受影响
  • CORS 是服务端授权，通过响应头告诉浏览器允许跨域
  • 预检请求 OPTIONS 必须放行，否则 PUT/DELETE 等请求会失败
  • allowCredentials=true 时不能用通配符，必须指定具体域名
  • CORS 只配一处，Nginx 和 SpringBoot 不要重复配置

跨域安全深度分析

CORS安全风险

CORS配置安全风险

  1. 生产环境指定具体域名，不用*
  2. 只允许必要的Method
  3. 只暴露必要的Header
  4. allowCredentials谨慎使用

CSRF vs CORS

CSRF（跨站请求伪造）

  • CSRF vs CORS
  • 攻击者诱导用户访问恶意页面
  • 恶意页面利用用户已登录的Cookie发起请求
  • 用户不知情的情况下执行了操作
  • CORS（跨源资源共享）
  • 浏览器安全机制，限制跨源请求
  • 服务端通过响应头授权跨源访问
  • 关系：
    • CORS配置不当会增加CSRF风险
    • allowCredentials=true + Origin:特定域名 是安全的基础
    • 推荐使用CSRF Token + CORS双重防护

跨域与微服务

微服务架构下的CORS

  • 方案1：网关统一处理（推荐）
  • 前端 -> Gateway(CORS) -> 微服务A/B/C
  • 微服务不需要单独配置CORS
  • 方案2：各服务单独处理
  • 前端 -> Gateway(透传) -> 微服务A(CORS)
  • -> 微服务B(CORS)
  • 配置分散，容易遗漏
  • 推荐方案1，在Gateway统一配置CORS
  • 微服务间调用不走网关，不存在跨域问题
