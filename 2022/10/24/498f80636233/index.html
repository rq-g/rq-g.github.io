DTO/VO分层——别让Entity到处跑

发布于 2022-10-24 分类：技术, 2022, SpringBoot 👁

前言

在实际场景中，系统涉及矿工管理、设备监控、安全预警、生产调度等多个模块。刚写接口时，我直接用Entity接收参数和返回结果，觉得简单省事。后来需求不断变化：矿工密码不能返回前端、设备创建和修改的字段不同、不同接口返回不同字段——直接用Entity根本搞不定。有一次前端联调时，矿工列表接口把密码和盐值全部返回了，差点酿成安全事故。从那以后，我在实际项目中严格做DTO/VO分层，再也没有出现过类似问题。

为什么不能直接用Entity？

问题1：敏感信息泄露

问题2：字段冗余

问题3：创建和修改字段不同

问题4：关联数据无法返回

分层设计

各层对象职责

DTO/VO 分层架构图

  • Entity → 数据库映射，与表结构严格对应
  • DTO → 接口入参，接收前端传入的数据
  • VO → 接口出参，返回给前端的数据
  • QueryDTO → 查询参数，封装查询条件
  • CreateDTO → 创建参数
  • UpdateDTO → 更新参数

对象流转

对象流转路径

  • 前端 → CreateDTO → Service → Entity → 数据库
  • 数据库 → Entity → Service → VO → 前端
  • 前端 → QueryDTO → Service → PageResult → 前端

分层原则

原则 说明 违反后果
Entity不出Controller 只在Service和Mapper层使用 敏感信息泄露、前后端耦合
DTO只做入参 不返回给前端 字段职责不清
VO只做出参 不接收前端参数 入参出参混淆
QueryDTO封装查询条件 不混用DTO 查询条件与业务参数混杂
创建和更新分开 CreateDTO和UpdateDTO 字段校验无法区分
