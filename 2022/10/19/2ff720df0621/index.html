统一返回结果封装——接口规范的第一步

发布于 2022-10-19 分类：技术, 2022, SpringBoot 👁

前言

刚写接口时，返回格式随心所欲：有的返回 Map、有的返回对象、有的直接返回字符串，矿端前端同事苦不堪言。在实际场景中，每种接口返回格式都不一样，前端每个接口都要特殊处理，尤其是错误处理逻辑到处重复。后来统一了返回格式，所有接口返回统一的 Result 对象，前后端协作效率大幅提升。

本文将从实际项目的真实场景出发，系统讲解统一返回结果封装的设计、实现和最佳实践。

没有统一返回的痛点

前端无法统一处理

没有统一返回的痛点

  1. 每个接口都要特殊处理
  2. 错误处理逻辑到处重复
  3. 新接口需要前后端反复确认格式
  4. 异常情况返回格式不可预测

状态码设计规范

  • HTTP标准码：

  • HTTP状态码通常统一返回200
  • 业务码通过Result.code区分

总结

统一返回结果是接口规范化的第一步。在实际场景中，从”返回格式随意”到”统一 Result 封装”，核心认知是：前后端协作的基础是接口规范，而接口规范的第一步是统一返回格式。Result + PageResult + 全局异常处理，三者组合构成了完整的接口返回体系。

关键收获：

  • Result 统一封装 是前后端协作的基础
  • PageResult 分页封装 是列表接口的标配
  • ResultCode 枚举 是状态码管理的最佳方式
  • 手动返回 Result 比自动包装更可控
  • Long 转 String + null 不返回 + 日期格式化 是 JSON 序列化的三大注意点

接口规范检查清单

接口规范检查清单

  • 返回格式：
  • 所有接口统一返回 Result
  • 分页接口使用 PageResult
  • 空数据返回空列表而非null
  • 状态码：
  • 200表示成功
  • 4xx表示客户端错误
  • 5xx表示服务端错误
  • 业务码按模块区分（1xxx/2xxx/…）
  • 数据格式：
  • Long类型转String
  • null字段不返回
  • 日期统一格式yyyy-MM-dd HH:mm:ss
  • 枚举返回友好描述
  • 敏感字段脱敏
  • 前后端协作：
  • 前端统一拦截器处理错误
  • 接口文档与实际返回一致
  • 错误码前后端同步
