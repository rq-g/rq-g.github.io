抽象类与接口——何时用谁，一次说清

发布于 2022-01-17 分类：技术, 2022, Java基础 👁

前言

“抽象类和接口有什么区别？”——这是面试必考题，但背过那套标准答案的人，到了真正写代码的时候依然纠结：这个场景到底该用哪个？我见过把 50 行业务逻辑塞进接口 default 方法的设计，也见过为了一个回调函数专门建抽象类的过度设计。

这篇文章不满足于”语法差异”，而是给出一套可以直接落地的判断标准，以及几个反模式案例。

核心区别一览

维度 抽象类 接口
关键字 abstract class interface
实例化 不能 不能
构造方法 ✅ 有（供子类初始化公共状态） ❌ 没有
成员变量 任意（可以有状态） 只能 public static final 常量
方法 抽象 + 具体任意混合 抽象 + default + static + private(JDK9+)
访问修饰符 任意 方法隐式 public
继承 单继承 多实现
设计语义 is-a（是什么） can-do（能做什么）

表格里最关键的一行是成员变量：抽象类可以有状态，接口不能。JDK 8 之后接口有了 default 方法，语法上越来越像抽象类，但”接口无状态、抽象类有状态”这条本质区别至今没变——这也是后面所有判断标准的根基。

JDK 8/9 接口演进：为什么会”越来越像抽象类”

default 方法诞生的动机值得记住：接口演化问题。Java 8 给 Collection 加 forEach/stream 时，如果只能加抽象方法，全世界所有实现类（包括用户自己写的）全会编译报错。default 方法让接口能在不破坏已有实现的前提下演进。

但要警惕：default 方法是接口演化的补丁，不是放业务逻辑的地方。它适合的场景是”基于接口其他方法推导出的通用行为”（如 Comparator.reversed()、Iterable.forEach()），而不是 50 行的业务代码。

默认方法冲突规则（面试深水区）

一个类实现的两个接口有同名 default 方法时，编译器强制处理：

冲突解决三原则：类（或父类）的实现永远优先于接口 default → 子接口覆盖父接口 → 仍然冲突则必须显式覆盖。这保证 Java 虽然多继承行为，但不会有菱形继承的歧义。

判断标准：三问法

第一问：有没有公共状态？

  • 有公共字段/状态需要子类共享 → 抽象类（接口唯一的字段是常量，放不了状态）
  • 只定义行为契约，无状态 → 接口

第二问：有没有模板流程？

  • 有公共流程骨架，子类填充细节 → 抽象类（模板方法模式是抽象类的”专属武器”）
  • 各实现完全独立，无公共流程 → 接口

final 修饰模板方法是关键细节：流程骨架不允许子类篡改，只开放扩展点——这就是”开闭原则”在继承体系里的具体形态。

第三问：需不需要多继承？

  • 一个类要同时具备多种能力 → 接口（Java 只能单继承）
  • 一种身份即可 → 都行，倾向接口

项目中的典型选择

场景 1：实体基类 → 抽象类

公共状态是硬理由，用接口连第一步都迈不过去。

场景 2：策略/处理器 → 接口

无公共状态、无公共流程、希望多实现注册进策略工厂——三问全是接口答案。

场景 3：契约 + 模板 → 接口和抽象类配合（最常用）

对外只暴露接口（调用方、Spring 注入、策略工厂都面向接口），继承体系内部用抽象类收拢公共逻辑：

这是 JDK 集合框架的标准套路：List 是接口，AbstractList 是骨架实现（ArrayList 继承它），对外你永远只见接口。

场景 4：能力标记 → 接口

标记接口配合 instanceof 检查使用（如 JDK 的 Serializable、Cloneable），但注意：现代 Java 更推荐注解（如 @RefreshScope）做标记，类型安全且支持元数据。

三个反模式

1. 常量接口反模式

java.io.ObjectStreamConstants 就是 JDK 承认的历史包袱。

2. 接口里写业务逻辑

判别标准：default 方法里是否需要访问字段？需要 → 它本该是抽象类方法。

3. “接口优先”教条化

Effective Java 说”优先用接口而不是类来引用”，很多文章歪解成”永远用接口”。当场景存在公共状态和模板流程时，强行接口化会导致 default 方法泛滥、逻辑无处安放。正确的顺序是：先接口定契约，出现公共状态/流程后再引入骨架抽象类——JDK 集合框架就是这么长出来的。

面试题的深层答法

被问”区别”时，按这个层次答，比背表格高一个段位：

  1. 语法层：状态（抽象类可有字段）、构造器、多继承能力的差异；
  2. 字节码层：接口方法调用走 invokeinterface（查接口方法表），抽象类实例方法走 invokevirtual（虚方法表），抽象类在此处略有性能优势但可忽略；
  3. 设计层：is-a vs can-do；抽象类表达”一族事物的共性骨架”，接口表达”能力契约”；
  4. 演化层：default 方法是为了解决接口演化问题，冲突规则（类优先、显式覆盖）保证多继承行为无歧义；
  5. 实战层：接口定契约 + 抽象类做骨架的组合，是 JDK 集合框架、Spring 大量基础设施采用的形态。

总结

  1. 一条本质区别贯穿始终：抽象类有状态，接口无状态——default 方法再像抽象类，接口也放不了字段；
  2. 三问法决策：有公共状态？有模板流程？需要多继承？前两问答”是”倾向抽象类（或组合方案），第三问答”是”必须接口；
  3. 最实用的形态是接口定契约 + 抽象类做骨架实现：调用方面向接口，继承体系内部收拢公共逻辑，final 锁死模板流程；
  4. 三个反模式记住：常量接口（用 final 类或枚举）、default 方法写业务、教条化”接口优先”；
  5. default 方法是接口演化的补丁，冲突规则是”类优先、冲突必须显式覆盖”，这是 Java 多继承行为不产生菱形歧义的原因；
  6. 不确定时的兜底策略：先用接口（成本低、灵活），当第二个实现出现重复代码时，再抽骨架抽象类——重构的成本远低于一开始就选错方向。
