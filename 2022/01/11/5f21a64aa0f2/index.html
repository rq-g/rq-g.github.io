面向对象之抽象——从具体到通用的思维跃迁

发布于 2022-01-11 分类：技术, 2022, Java基础 👁

前言

抽象是面向对象四大特性里最”玄”的一个：封装是藏细节，继承是复用代码，多态是灵活调用，抽象是什么？我的理解是从具体事物中提取共性、忽略非本质细节的能力。它不像其他三个特性那样有明确的语法载体，却直接决定了代码的可维护性和扩展性——两个程序员面对同一个需求，抽象能力的高低，写出来的代码三个月后的维护成本能差一个数量级。

这篇文章记录我对抽象的理解：从”是什么”，到项目里怎么落地，再到三个最容易掉进去的误区。

什么是抽象？

抽象有两种语法载体：

  1. 抽象类：abstract 修饰，可以包含抽象方法（只声明、不实现）和具体方法；
  2. 接口：interface 定义，JDK 8 之后可以有 default 和 static 方法。

注意这段代码里的一个核心动作：final 的 importData 是流程共性，两个 abstract 方法是差异点。抽象的本质工作就是把一个复杂问题切成”稳定的共性”和”变化的差异”两半，然后分别处理。

抽象类 vs 接口

维度 抽象类 接口
构造方法 可以有 不能有
成员变量 任意（可有状态） 只能常量（public static final）
方法 抽象 + 具体任意混合 抽象 + default + static（+ private，JDK9）
继承 单继承 多实现
设计语义 is-a（是什么），模板设计 can-do（能做什么），行为契约

选择原则三句话：有公共状态和模板逻辑 → 抽象类；只定义行为契约 → 接口；拿不准 → 先接口（加抽象类的成本低，改掉的成本高）。

抽象在项目中的三层实战

1. 模板方法模式（抽象类）：锁死流程，开放差异

Excel 报表、PDF 报表、CSV 报表各自一个子类，只写 fetchData/buildReport 十几行，流程骨架、数据清洗、导出日志全部复用。新增一种报表的成本从”复制 300 行”降到”写 20 行”，这就是抽象的直接收益。

2. 行为契约（接口）：转换器的泛型抽象

一个泛型接口统一了系统里所有的对象转换器，配合 Map<Class<?>, Convertible<?, ?>> 注册表，任何地方都能按类型找到转换器——抽象 + 泛型让”转换”这个动作有了统一入口。

3. SPI 扩展机制（接口 + 工厂）：为未来留门

这是”抽象为扩展服务”的典型：新增一种消息类型只需要加一个实现类，工厂、调用方、老实现全部零改动。新需求来临时的改动半径，是检验抽象质量的终极标准。

抽象的层次感：好代码是分层的

好的抽象不是”有没有”，而是”层次是否清晰”：

flowchart TD
    A["高层抽象：接口
定义能力契约"] --> B["中层抽象：抽象类
提供模板与公共逻辑"]
    B --> C["底层实现：具体类
完成业务细节"]
    C --> D["使用者永远面向高层抽象
（依赖倒置）"]

Spring 框架是这个结构的教科书式示范：

  • BeanFactory（接口）→ 定义”获取 Bean”的能力契约
  • AbstractBeanFactory（抽象类）→ 收拢 getBean 的模板流程（单例缓存、类型转换）
  • DefaultListableBeanFactory（具体类）→ 完整实现

日常业务代码同理：Controller 依赖 Service 接口而不是实现类，就是让自己永远站在高层抽象上——底层实现可以随时替换，调用方无感。

三个抽象误区（都是我踩过的）

误区 1：过度抽象

过度抽象的代价是类爆炸：为了改一行逻辑要跳五个文件。抽象是有成本的（理解成本、跳转成本），只在收益大于成本时使用。

误区 2：抽象层次不一致

判断方法：读接口方法的签名，如果出现 Connection、HttpServletRequest、File 这类底层类型，就是层次泄漏。

误区 3：接口污染（胖接口）

按能力拆成小接口（接口隔离原则 ISP）：

胖接口的真正危害在扩展时爆发：每加一个方法，所有实现类（包括别人的）都要跟着改——接口是承诺，每一条承诺都要兑现，所以别轻易承诺。

抽象判断标准：一张速查表

信号 是否抽象 原因
同一逻辑写了两遍 观察中，第三遍动手 DRY，但要等模式稳定
明确需要多种实现 是 开闭原则
需要运行时切换策略 是 策略模式
只有一个实现且短期无变化 否 过度设计
三字段的 DTO 否 抽象收益不抵成本
简单 CRUD 否 增加复杂度

注意第一条和我之前写的不一样：“写第二遍就抽象”其实是激进派，第二遍时你还不知道差异点在哪，抽象出来的接口大概率是错的。实践中”Rule of Three”（第三次重复时抽象）往往更稳。

总结

  1. 抽象的本质是切分共性与差异：稳定流程用 final 模板锁死，变化点用 abstract 方法/接口开放；
  2. 三个落地武器：模板方法（抽象类）、泛型行为契约（接口）、SPI 扩展工厂——分别解决”流程复用”、”动作统一”、”未来扩展”；
  3. 好抽象是有层次的：接口定契约 → 抽象类做骨架 → 具体类填细节，Spring 的 BeanFactory 三层结构是标准范本；
  4. 三个误区记住：过度抽象（类爆炸）、层次泄漏（底层类型出现在高层接口）、胖接口（承诺兑现不起）；
  5. 我的抽象观经历了三个阶段：一开始觉得抽象没用（直接写具体类不好吗？），后来觉得到处都该抽象（什么都要搞接口），最终找到平衡——在需要扩展的地方抽象，在稳定的地方具体；
  6. 一句话检验标准：看新需求来临时的改动半径——只加文件不改老代码的抽象是好抽象。
