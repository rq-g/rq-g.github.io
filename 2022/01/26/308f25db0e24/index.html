HashMap底层原理——面试必问，开发必懂

发布于 2022-01-26 分类：技术, 2022, Java基础 👁

前言

先讲一个真实事故。

智慧矿山项目里有一个设备状态缓存，用 HashMap<String, DeviceStatus> 存 3000 台设备的实时状态，由一个采集线程写、一个推送线程读。上线后跑了大概两周，某天早班监控突然报警：调度大屏上设备全部离线。登上服务器一看——CPU 单核 100%，jstack 抓出来 30 多个线程全部卡在 HashMap.get() 的同一行，死循环了。

根因是 JDK7 的 HashMap 在并发扩容时头插法会形成环形链表，一旦 get() 落到这个环上就再也出不来。

这件事之后我才真正意识到：HashMap 是 Java 里用得最多、也最容易用错的集合。它看着简单，put/get 谁都会，但下面这些问题能答上来的并不多：

  • 为什么容量必须是 2 的幂？为什么扩容是 2 倍而不是 1.5 倍？
  • 为什么负载因子是 0.75 而不是 0.5 或 1.0？
  • 为什么树化阈值是 8，退化阈值却是 6，不是也用 8？
  • 为什么 treeifyBin() 里数组长度小于 64 时选择扩容而不是树化？
  • 两个对象 hashCode 相同但没实现 Comparable，红黑树怎么比较大小？
  • 用可变对象当 key 会发生什么？

这篇文章从源码、数学推导、内存布局、并发缺陷、工程踩坑五个维度把 HashMap 讲透，最后给一份可以直接拿去用的面试速查表。

一、核心数据结构演进

为什么 JDK8 要把头插改成尾插？

头插法的本意是”利用 CPU 缓存局部性，新插入的节点更可能被访问”，但它在并发扩容时会反转链表顺序，直接导致死循环（第七节详细推演）。改成尾插后，扩容时链表元素的相对顺序保持不变，环形链表问题从根上消失了。

注意——尾插只是解决了死循环，并没有让 HashMap 变得线程安全，数据覆盖丢失问题依然存在。

1.2 Node 与 TreeNode 的内存布局

很多人只知道”红黑树节点更大”，但不知道大多少。以 64 位 JVM、开启压缩指针（-XX:+UseCompressedOops，默认开启）为例：

节点类型 字段构成 单个对象大小
Node 对象头 8 + klass 4 + hash 4 + key 4 + value 4 + next 4 = 28 → 对齐到 32 32 B
TreeNode 在 Node 基础上再加 parent/left/right/prev 四个引用 + red 布尔 = 28 + 20 = 48 48 B

结论：红黑树节点的内存开销是普通节点的 1.5 倍。 这正是为什么 HashMap 宁可让链表长到 8 也不急着树化——用时间换空间，只有在”分布明显异常”时才付出这 50% 的额外内存。

一个反直觉的点：TreeNode 继承自 LinkedHashMap.Entry，后者又继承自 HashMap.Node。也就是说树节点同时保留了 next 指针，树化后节点之间仍然用链表串着。这样设计是为了退化成链表时不用重建节点，直接改回 next 链即可。

2.1 初始容量到底该怎么算

这是实战中最常写错的一行代码。

推导：要让 n 个元素不触发扩容，必须满足 n <= capacity × 0.75，即 capacity >= n / 0.75。加 1 是为了处理浮点取整误差。

实测收益（插入 100 万条 Integer -> String）：

初始容量 扩容次数 耗时 说明
16（默认） 约 17 次 215 ms 每次扩容都要重建数组并搬迁全部元素
256 约 12 次 168 ms —
4096 约 8 次 152 ms —
一次到位（2097152） 0 次 142 ms 省掉全部数组拷贝，快约 34%

代价是内存。一次到位会分配一个长度为 2^21 的数组（仅引用数组就约 16 MB）。权衡原则：确定会放很多且长期存活的缓存，一次到位；临时小 Map 就别预估，浪费内存。

2.2 为什么容量必须是 2 的幂

关键在于：n 是 2 的幂时，n-1 的二进制全为 1，& 运算恰好等价于取模且分布均匀；否则 n-1 存在 0 位，对应桶位永远无法命中。

tableSizeFor() 负责把任意输入向上取整到 2 的幂：

为什么要先 cap - 1？ 因为不减 1 的话，输入正好是 2 的幂时会翻倍。比如输入 16，不减 1 结果是 32，浪费一倍空间；减 1 后是 15，扩散得 15，+1 = 16，正确。

为什么扩容是 2 倍而不是 1.5 倍？（1.5 倍是 ArrayList 的做法）

因为 2 倍能让扩容后的元素迁移只需看”新增的那一位”：新位置要么不变，要么是 原位置 + oldCap。1.5 倍无法用位运算实现，(n-1) & hash 也就不成立。2 倍扩容是”容量必须是 2 的幂”这个前提的必然推论。

三、hash 计算：扰动函数的数学依据

3.1 为什么需要扰动

当数组长度较小时（比如默认 16），index = (n-1) & hash 只用到 hash 的低 4 位，高 28 位完全不参与运算。如果一批 key 的 hashCode 高位差异很大、低位却相同，它们就会全部挤到同一个桶。

扰动函数把高 16 位”折”下来与低 16 位混合，让高位也间接参与最终定位：

3.2 为什么用异或 ^，不用 & 或 |

运算 结果特征 是否适用
& 与 结果趋向 0，信息丢失 ❌ 让 hash 值整体偏小，聚集在低桶位
| 或 结果趋向 1，信息丢失 ❌ 让 hash 值整体偏大，聚集在高桶位
^ 异或 0/1 各 50% 概率，熵不损失 ✅ 保留原有随机性

异或是唯一一个”不丢失信息熵”的二元位运算——两个输入位独立且均匀时，输出也是均匀的。

3.3 为什么只扰动一次，不做两轮

JDK8 源码注释里其实写了：

There are some bits that are lost, but it’s a compromise between speed, utility, and quality of bit-spreading.

扰动一次已经能把高 16 位混入低 16 位。做两轮（比如再 ^ (h >>> 8)）收益极小，但每个 key 都要多算两次位运算——HashMap 是极端高频调用的组件，这点固定开销不划算。典型的工程权衡：够用就好，不为边际收益付出固定成本。

四、put 流程全解析

4.1 三个容易被忽略的设计点

① key 相等的判断顺序：先 hash、再 ==、最后 equals

先比 hash 是因为 hash 不等则对象一定不等，一次 int 比较就能排除绝大多数情况；== 是引用相等，比 equals 快得多；只有前两步都过了才调用可能很昂贵的 equals。典型的多级短路优化。

② afterNodeAccess / afterNodeInsertion 是留给 LinkedHashMap 的扩展点

HashMap 里这两个方法是空实现。LinkedHashMap 重写 afterNodeAccess 实现”访问后把节点移到尾部”，从而支撑 LRU；重写 afterNodeInsertion 配合 removeEldestEntry 实现”插入后淘汰最老元素”。模板方法模式在 JDK 里的经典应用。

③ onlyIfAbsent 和 evict 参数的含义

  • onlyIfAbsent = true：只有旧值为 null 时才写入（putIfAbsent 用这个）；
  • evict = false：表示”创建模式”，LinkedHashMap 反序列化时传 false，避免插入过程中触发淘汰。

五、扩容机制：JDK8 的 split 优化

5.1 搬迁为什么不用重新计算 hash

扩容后 newCap = oldCap << 1，newCap - 1 比 oldCap - 1 只多出一个高位 bit（也就是 oldCap 那一位）。因此每个元素的新位置只有两种可能：

举例，oldCap = 16：

hash 旧位置 hash & 15 hash & 16 新位置 hash & 31
5 (00101) 5 0 5（不变）
21 (10101) 5 16 ≠ 0 21（= 5 + 16）

一次位判断替代一次完整取模，100 万个元素扩容只需 100 万次 & 运算。

5.2 链表拆分的双指针实现

关键点：拆分是保序的——用尾插把原链表拆成两条，而不是像 JDK7 那样逐个元素重新头插。这既避免了反转，也让并发场景下不再产生环。

六、树化机制：四个必须懂的细节

6.1 为什么阈值是 8（泊松分布）

JDK 源码注释里给了这张表——在负载因子 0.75 的理想散列下，桶中元素个数服从泊松分布（λ ≈ 0.5）：

链表长度 概率
0 0.60653066
1 0.30326533
2 0.07581633
3 0.01263606
4 0.00157952
5 0.00015795
6 0.00001316
7 0.00000094
8 0.00000006

链表长度达到 8 的概率是千万分之六。也就是说正常情况下根本不该出现；一旦出现，说明 key 的 hashCode 有重大问题，或者有人在恶意构造哈希碰撞攻击。红黑树是这种情况下的兜底保障，不是常规路径。

6.2 为什么退化阈值是 6 而不是 8（迟滞设计）

如果树化和退化都用 8，那么一个长度恰好在 8 附近波动的桶会反复触发”链表→树”和”树→链表”，每次转换都要重建节点、重新着色，代价极高。

留出 2 的间隔（hysteresis，迟滞区间），让结构转换不在临界点来回抖动。这是工程上非常常见的模式——TCP 拥塞窗口、Redis 内存淘汰、JVM GC 阈值都用了类似设计。

6.3 为什么 treeifyBin 里容量 < 64 时选择扩容而非树化

逻辑：链表长说明这个桶太挤，但原因可能是”数组太小”而不是”hash 太差”。这时候扩容能把元素摊薄到更多桶里，代价（一次 resize）比树化（多占 50% 内存，后续所有操作走 O(log n)）更小。只有扩容解决不了（容量已 ≥64 还挤）时，才说明 hash 真有问题，此时才树化。

结论：无论 JDK7 还是 JDK8，HashMap 都绝对不能用于并发写场景。

7.3 fail-fast 与 ConcurrentModificationException

原理：HashMap 维护 modCount，每次结构性修改（put/remove/clear）都 ++modCount。迭代器创建时记录 expectedModCount = modCount，每次 next() 检查两者是否相等，不等就抛异常。

注意 fail-fast 只是”尽力而为”的检测机制，不是可靠保证。多线程下它可能不抛异常就直接产生错误结果。

7.4 三种线程安全方案对比

方案 实现 性能 适用场景
ConcurrentHashMap JDK8：CAS + synchronized 锁单个桶 高，读完全无锁 ✅ 首选
Collections.synchronizedMap 全局一把锁包住所有方法 低，完全串行 低并发、需兼容 Map 接口
Hashtable 方法上加 synchronized 低，且不允许 null 遗留代码，新项目别用

八、负载因子 0.75 的数学依据

JDK 注释说得含糊（”offers a good tradeoff between time and space costs”），但可以从两个角度理解：

角度一：泊松分布
负载因子 0.75 时，桶中元素数的泊松分布参数 λ ≈ 0.5，链表长度 > 8 的概率是千万分之六。负载因子提到 1.0 时 λ 增大，碰撞概率显著上升。

角度二：空间与时间的权衡

负载因子 空间利用率 碰撞概率 适用场景
0.5 低（一半空间空着） 极低 读多写少、对延迟极敏感
0.75 中 低 默认，综合最优
1.0 高 明显上升，链表变长 内存紧张、元素少
> 1.0 很高 大量碰撞，性能急剧下降 不推荐

实用技巧：如果是只读缓存（初始化后不再插入），可以把负载因子设到 1.0 甚至更高，用少量查询性能换取显著的内存节省。但要留意碰撞带来的链表开销可能反而更占内存。

九、工程踩坑清单

9.1 用可变对象当 key —— 内存泄漏陷阱

规则：HashMap 的 key 必须是不可变对象（String、Integer，或所有字段都 final 的自定义类）。如果一定要用可变对象，必须保证参与 hashCode/equals 的字段在放入后永不修改。

9.2 自定义 key 的 hashCode 写法

为什么用 31：

  1. 奇素数——偶数乘法会导致低位比特丢失（等价于移位），加剧碰撞；
  2. 31 * i == (i << 5) - i，JIT 能优化成移位 + 减法，比乘法快；
  3. 经验值——对英文单词类 key 实测分布良好。

实际项目推荐用 Objects.hash(...) 或 Lombok @EqualsAndHashCode，但它们会创建 Object 数组，有轻微开销。超高性能场景手写。

总结

HashMap 的设计是一连串精妙的工程权衡，读懂它，基本就读懂了”高性能数据结构该怎么设计”：

  1. 用空间换时间——2 的幂容量 + 位运算定位，把取模变成一次 &；
  2. 用概率做决策——泊松分布算出 8 这个阈值，用极小概率事件兜底最坏情况；
  3. 用迟滞换稳定——树化 8、退化 6，避免临界点抖动；
  4. 不为边际收益付固定成本——只扰动一次 hash，够用就停；
  5. 明确划清能力边界——它从不为并发负责，这个职责交给 ConcurrentHashMap。

回到开头那个事故：真正的教训不是”HashMap 线程不安全”这句人人会背的话，而是——一个看起来只是做缓存的 Map，在多了一个写线程之后就变成了定时炸弹。理解底层原理，才能在写完代码的那一刻就闻出味道不对。
