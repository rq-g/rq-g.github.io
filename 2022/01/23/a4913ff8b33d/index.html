八大基本数据类型与包装类——那些年踩过的空指针坑

发布于 2022-01-23 分类：技术, 2022, Java基础 👁

前言

在实际场景中，NPE 的很大一部分跟基本类型和包装类的混用有关。数据库字段为 null，映射到包装类是 null，自动拆箱时直接 NPE——这个坑我至少踩了五次以上。更深一层的坑在于：拆箱 NPE 的触发条件非常隐蔽，代码 review 时扫一眼根本看不出来，只有跑到特定分支才炸。

这篇文章把八大基本类型、装箱拆箱机制、缓存池原理、以及我在项目里真实踩过的 5 个坑完整梳理一遍。

八大基本数据类型

类型 大小 范围 默认值 包装类
byte 1字节 -128~127 0 Byte
short 2字节 -32768~32767 0 Short
int 4字节 -2^31 ~ 2^31-1 0 Integer
long 8字节 -2^63 ~ 2^63-1 0L Long
float 4字节 IEEE 754 0.0f Float
double 8字节 IEEE 754 0.0d Double
char 2字节 0~65535 ‘\u0000’ Character
boolean JVM 未规定 true/false false Boolean

包装类是对象，内存开销远超基本类型。以 64 位 JVM（开启压缩指针）为例：

数据 内存占用 说明
一个 int 4 字节 栈上/数组内
一个 Integer 对象 16 字节 对象头 12 + int 4
List<Integer> 存 100 万个数 约 16MB+ 对象引用 4 + 每个对象 16
int[] 存 100 万个数 4MB 纯数据，无对象开销

所以对大批量数值计算，int[] 比 List<Integer> 省近 4 倍内存——这也是为什么 JDK 8 专门提供了 IntStream、OptionalInt 这类避免装箱的特化 API。

自动装箱与拆箱：编译器偷偷做了什么

用 javap -c 反编译可以看到，装箱拆箱就是两次方法调用，没有任何魔法。也因此，所有 NPE 本质上都一样：在 null 上调用了 xxxValue()。

最经典的拆箱 NPE

典型事故链路：数据库 remark_count 字段为 NULL → MyBatis 映射到实体类的 Integer remarkCount 是 null → 业务代码里 int total = baseCount + order.getRemarkCount(); → 拆箱 NPE。

顺带说一个反向的语义陷阱：如果实体类字段写成了基本类型 int，数据库 NULL 映射过来会静默变成 0——不报错，但 NULL（未知/未填写）和 0（真实值为零）的业务语义被混淆了，统计报表会悄无声息地出错。

缓存机制——面试必考，也是 == 陷阱的根源

Integer、Byte、Short、Long、Character、Boolean 的 valueOf() 都有缓存池：

类型 缓存范围 可配置
Byte -128~127（全量） 否
Short -128~127 否
Integer -128~127 是（-XX:AutoBoxCacheMax=N）
Long -128~127 否
Character 0~127 否
Boolean TRUE / FALSE（仅两个实例） 否

这个坑的阴险之处：测试环境用小数字造的数据（状态码 1、2）一切正常，生产环境换成大 ID 立刻行为不一致。

坑 2：数据库映射拆箱 NPE

配套原则：POJO 类属性、RPC 方法的参数与返回值必须用包装类；局部变量推荐基本类型（局部变量生命周期自己可控，且省去装箱开销）。

坑 3：方法参数的隐式拆箱

除非业务上明确”该参数不允许为空”，否则方法形参也用包装类，把”为空”变成一个可以显式处理的分支而不是异常。

一个实战变体：用 Long 做设备 ID，某处代码用 == 比较，压测环境 ID 都是 -128~127 范围内的小值，一切正常；上了生产，ID 是 19 位雪花数，== 永远 false，去重逻辑全部失效。这种”测试环境正常、生产环境翻车”的 bug，根因几乎都能追到缓存池。

    B -->|是| C[必须用包装类

总结

  1. 装箱拆箱的本质是 Integer.valueOf() / xxxValue() 两次方法调用——所有拆箱 NPE 都是”在 null 上调方法”；
  2. 缓存池让 -128~127 的包装类是同一对象，这是 == 陷阱的根源：包装类之间比较一律 equals（或 Objects.equals），不要用 ==；包装类与基本类型比较会拆箱比数值，但 null 会炸；
  3. 三目运算符是隐形杀手：只要一个分支是基本类型，表达式类型就提升为基本类型，null 分支被选中即 NPE——两个分支类型必须统一；
  4. 选型口诀：POJO 属性、RPC 参数返回值、集合元素用包装类；局部变量、内部计算、数值数组用基本类型；可能为 NULL 的数据库字段绝不能用基本类型映射（NULL 被静默当 0，语义错乱）；
  5. 性能意识：Integer 对象 16 字节 vs int 4 字节，大批量数值场景用基本类型数组或 IntStream 特化流，避免百万级装箱；
  6. 三条防坑习惯覆盖 90% 的场景：实体类全用包装类、拆箱/比较前先判空、三目分支类型统一。
