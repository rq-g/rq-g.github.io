ArrayList底层原理——动态数组的核心秘密

发布于 2022-01-29 分类：技术, 2022, Java基础 👁

前言

在智慧矿山项目里做过一次设备数据导出：从数据库查出 20 万条设备状态记录，循环 add 到一个 ArrayList 里，然后批量落库。功能没问题，但上线后监控显示这段导出耗时 3.2 秒，其中 GC 频繁。

用 JProfiler 一抓，发现 ArrayList.grow() 被调用了 24 次，最后一次要拷贝 71140 个引用，期间产生了 24 个废弃的 Object[] 数组——最大的那个 106710 长度，约 420KB。这些”临时尸体”全部进了老年代。

改成 new ArrayList<>(200000) 之后，扩容次数从 24 次降到 1 次，耗时降到 0.7 秒，GC 次数归零。

一行构造参数的差别，4.5 倍性能差。

这就是理解底层的价值。ArrayList 是 Java 里最常用的集合，但绝大多数人对它的认知停留在”数组实现的 List，会自动扩容”。这篇文章要把下面这些问题讲透：

  1. 为什么源码里有两个长得一模一样的空数组常量？
  2. 为什么扩容是 1.5 倍而不是 2 倍、3 倍？
  3. MAX_ARRAY_SIZE 为什么要 Integer.MAX_VALUE - 8？减的 8 是什么？
  4. 为什么 foreach 里 remove 会抛 ConcurrentModificationException，但删倒数第二个元素就不抛？
  5. elementData 为什么要加 transient，还非要自己写 writeObject？

1.2 为什么要有两个”一模一样”的空数组？

这是 ArrayList 源码里最容易被忽略、但设计得很精巧的一个细节。

两个都是空数组，内容完全相同。区别只在于：它们被用来区分”这个 ArrayList 是怎么创建出来的”，从而决定首次扩容扩到多大。

创建方式 使用的空数组 首次 add 后容量
new ArrayList<>() DEFAULTCAPACITY_EMPTY_ELEMENTDATA 10（用 DEFAULT_CAPACITY）
new ArrayList<>(0) EMPTY_ELEMENTDATA 1（按 1.5 倍规则：0 → 1）

源码里这个分支：

为什么这么设计？ 因为语义不同：

  • new ArrayList<>()：用户没表态，JDK 认为”你大概率要放不少东西”，给个合理的默认值 10，避免一开始就频繁扩容。
  • new ArrayList<>(0)：用户明确说”我要一个容量为 0 的列表”，JDK 应当尊重这个显式指定，不能自作主张扩到 10。

这是一个用”空数组的身份”来携带状态的小技巧——省掉了一个 boolean 字段。

提示：JDK 7 及之前没有这个区分，无参构造直接 this(10) 分配 10 个长度的数组。JDK 8 改成延迟初始化，配合这两个常量，让”创建了但从不使用”的 ArrayList 不占任何额外内存。如果你有上万个空 List 对象（比如 ORM 映射出来的空集合字段），这个优化能省下可观的内存。

2.2 grow() 逐行精读

四个分支逐个说：

① oldCapacity + (oldCapacity >> 1)

用移位而不是 / 2，一是性能（移位指令比整除快），二是 >> 对正整数就是整除 2。这里有个小细节：如果 oldCapacity 是 1，那么 1 + (1>>1) = 1 + 0 = 1，扩不动。所以从 0 或 1 开始时，靠分支 ② 兜底到 minCapacity。

② addAll 场景

如果只按 1.5 倍扩，得扩 30 多次。分支 ② 直接一步到位：newCapacity = minCapacity = 1000000。

③ MAX_ARRAY_SIZE

为什么减 8？ 源码注释写得很清楚：

Some VMs reserve some header words in an array. Attempts to allocate larger arrays may result in OutOfMemoryError: Requested array size exceeds VM limit.

部分 JVM 会在数组对象里保留一些 header words（对象头。HotSpot 里普通对象头是 8 字节（Mark Word）+ 4 字节（Klass Pointer，开启压缩指针时），还有 4 字节数组长度）。JDK 保守地预留 8 字节，避免分配到 VM 的实际限制边界导致 OOM。

④ Arrays.copyOf

System.arraycopy 是 JVM intrinsics（JIT 会直接替换成高效的内存操作，本质上是 memmove），比手写 for 循环快得多。但它依然是 O(n)，而且扩容时还要额外分配一个新数组——代价是双重的。

2.3 为什么是 1.5 倍，不是 2 倍？

这是最有意思的一个问题。答案不在 Java 里，在内存分配器里。

  • k = 2：2 > 1.618，新数组永远比所有旧块加起来还大 → 旧内存永远无法复用，只能不断向 OS 要新内存，产生大量内存碎片。
  • k = 1.5：1.5 < 1.618 → 新数组可以放进之前释放的内存里，内存友好。

同时 k 又不能太小：太小会导致扩容次数暴增（拷贝总代价上升）。1.5 正好卡在”扩容次数可接受”和”内存可复用”之间。

这也解释了为什么不同实现取值不同：MSVC 的 std::vector 用 1.5，GCC 用 2（它做了别的优化），Java 的 ArrayList 用 1.5。

2.4 扩容的真实代价

下面是我按源码逻辑实算的数据（不是估算）：

元素数 扩容次数 累计元素拷贝次数 最终 capacity 浪费空间
100 7 202 109 9
1,000 13 2,456 1,234 234
10,000 19 28,096 14,053 4,053
100,000 24 213,413 106,710 6,710
1,000,000 30 2,430,972 1,215,487 215,487

关键观察：

  1. 拷贝总量约 2~3 倍于元素数。这正是”均摊 O(1)”的含义——n 次 add 总拷贝 O(n) 次，均摊下来每次 add 是 O(1)。
  2. 最坏情况浪费接近 50%。100 万元素时最终容量 1,215,487，白白多占 215,487 × 4 字节 ≈ 843KB（64 位压缩指针下每个引用 4 字节）。
  3. 24 个废弃数组是 GC 压力的主要来源——它们大小不一，容易触发老年代 GC。

3.1 remove 源码：为什么最后要置 null

最后一行 elementData[--size] = null 看似多余，其实是必须的。

如果不置 null：size 减了 1，逻辑上元素已删除，但 elementData[size] 这个槽位仍然持有该对象的强引用。只要 ArrayList 本身还活着，这个对象就永远无法被 GC 回收 —— 这就是经典的内存泄漏（游离对象，loitering objects）。

对于存大对象的 List（比如缓存的图片、报表数据），漏掉这一行会让内存只增不减。Effective Java 里专门有一节讲这个问题。

4.5 fail-fast 的局限性

modCount 机制叫 fail-fast（快速失败），但它有个重要前提：

它只在单线程下可靠，不能作为并发安全的保证。

原因：modCount 是普通 int，没有 volatile，也没有任何同步。多线程下：

  • 线程 B 的修改，线程 A 可能根本看不到 modCount 变化 → 不抛异常，但数据已经错了；
  • 也可能在 next() 里读到过期值 → 数组越界 / 返回 null。

JDK 文档原话：

Note that the fail-fast behavior of an iterator cannot be guaranteed as it is, generally speaking, impossible to make any hard guarantees in the presence of unsynchronized concurrent modification. Fail-fast iterators throw ConcurrentModificationException on a best-effort basis.

“best-effort”（尽力而为）—— 所以别指望它帮你兜住并发 bug。并发场景请用第五节里的线程安全容器。

五、ArrayList vs LinkedList：为什么 LinkedList 几乎不该用

维度 ArrayList LinkedList
底层 动态数组 双向链表
get(i) O(1) O(n)（要遍历到 i）
add(e) 尾部 均摊 O(1) O(1)
add(0, e) 头部 O(n)（整体后移） O(1)
remove(i) O(n) 定位 O(n) + 删除 O(1)
内存占用（100 万元素） 约 4 MB（仅引用数组） 约 24 MB（每个节点带对象头和前后指针）
缓存友好度 高（内存连续，CPU 预取命中） 低（节点分散，cache miss 严重）
随机访问 支持（RandomAccess 标记） 不支持

5.1 LinkedList 的内存成本

每个 Node：

加上对象头 16 字节 → 每个节点 24 字节 + 4 字节对齐 = 24 字节（64 位 JVM 开启压缩指针）。

ArrayList 每个元素只占 4 字节（一个引用槽）。

100 万元素：

  • ArrayList：4 MB + 数组对象头
  • LinkedList：24 MB + 100 万个节点对象的 GC 压力

5~6 倍内存差距。

5.2 被忽略的关键：缓存局部性

这是比时间复杂度更重要的实战因素。

CPU 读取内存时会把**相邻的一整块（cache line，通常 64 字节）**加载进 L1/L2 缓存。ArrayList 的元素在内存里连续存放，遍历时一次 cache line 能拿到 16 个引用（64/4），后续 15 次访问全部命中缓存。

LinkedList 的节点分散在堆各处，几乎每次访问都是一次 cache miss（约 100 个 CPU 周期，比缓存命中慢 ~100 倍）。

实测结果：即使是在 LinkedList 理论占优的”头部插入”场景，当数据量超过几千时，ArrayList 的 add(0, e) 往往还是比 LinkedList 快——因为 arraycopy 是连续内存的高效 memmove，而 LinkedList 每次都要 new 一个节点对象（分配 + GC）并 cache miss。

5.3 什么时候该用 LinkedList

坦白说，很少：

  • ✅ 需要频繁在已知位置（通过迭代器持有）做插入/删除，且数据量不大
  • ✅ 需要当作 Deque / 队列用（此时用 ArrayDeque 通常更好）
  • ❌ 不要因为”要频繁增删”就选它——先测，大概率 ArrayList 更快
  • ❌ 不要用它做队列，用 ArrayDeque（无界）或 LinkedBlockingQueue（有界/并发）

ArrayDeque 是循环数组实现的双端队列，在绝大多数”栈/队列”场景下都比 LinkedList 快且省内存。

六、线程安全：三个方案怎么选

ArrayList 不是线程安全的。并发 add 可能：

  • 元素覆盖（elementData[size++] = e 不是原子操作，两个线程可能写到同一个位置）
  • size 计数错误
  • 扩容时数组引用错乱，甚至 ArrayIndexOutOfBoundsException

三个替代方案对比：

方案 原理 读性能 写性能 迭代时修改 适用场景
Vector 所有方法 synchronized 差 差 抛 CME ❌ 已过时，别用
Collections.synchronizedList 装饰器，方法级 synchronized 中 中 必须手动同步 低并发的兼容场景
CopyOnWriteArrayList 写时复制整个数组 极高（无锁） 极差（O(n) 且加锁） ✅ 安全（快照迭代） 读多写极少，如监听器列表、配置缓存

6.1 CopyOnWriteArrayList 深入

三个要点：

  1. 每次写都复制整个数组 —— 100 万元素的 List 做一次 add，要拷贝 4MB。绝对不能用来做高频写入。
  2. 读操作完全不加锁，读的是 volatile 数组引用，所以极快。
  3. 迭代器是快照：创建迭代器时持有当时的数组引用，之后原 List 怎么改都不影响迭代，永不抛 CME。代价是读不到最新数据（弱一致性）。

典型误用：用 CopyOnWriteArrayList 存设备实时上报数据（高频写）→ 每次写入 O(n) 拷贝 + 大量垃圾对象 → CPU 和 GC 双杀。这种场景应该用 ConcurrentLinkedQueue 或 LinkedBlockingQueue。

6.2 synchronizedList 的坑

JDK 文档明确要求：迭代 synchronizedList 时，必须手动在返回的 list 上同步。忘记这一步，迭代期间被其他线程修改，照样抛 CME。

十、JDK 版本演进

版本 变化
JDK 1.2 ArrayList 诞生，作为 Vector 的非同步替代
JDK 1.5 引入泛型，Object[] elementData 变为泛型容器
JDK 1.7 无参构造直接 new Object[10]（饿汉式）
JDK 1.8 改为延迟初始化 + 两个空数组常量区分；新增 removeIf、forEach、stream
JDK 9 新增 List.of() 不可变工厂方法；new ArrayList<>(0) 等场景复用共享空数组
JDK 11+ toArray(T[]::new) 等函数式写法

JDK 7 → JDK 8 的改动值得单独说：

对于一个有大量空 List 字段的系统（典型如 ORM 查询结果里的空集合、JSON 反序列化后的空数组），这个改动能显著降低内存占用——因为所有空 ArrayList 共享同一个静态空数组实例，而不是每个都持有一个 10 长度的数组。

十一、避坑清单

扩容与容量

  1. ✅ 已知元素数量时，构造时指定 initialCapacity（× 1.25 余量）
  2. ✅ 长期持有且不再修改的大 List，调用 trimToSize()
  3. ❌ 不要在循环里 new ArrayList<>() 再 addAll，直接复用或预分配
  4. ✅ addAll 大集合时无需担心，JDK 会一步扩到位

遍历与删除
5. ❌ 禁止在 foreach 里调用 list.remove()
6. ✅ 优先用 removeIf（O(n) 批量删除，且可读性最好）
7. ⚠️ 删除倒数第二个元素不抛 CME，但结果是错的——别靠”没报错”判断代码正确
8. ✅ 需要按索引删除时用倒序 for 循环

API 陷阱
9. ❌ Arrays.asList() 返回的不是 ArrayList，不能 add/remove；且 set 会改原数组
10. ❌ subList() 返回视图，不是副本；需要独立副本要 new ArrayList<>(subList(...))
11. ❌ clone() 是浅拷贝，元素对象仍共享
12. ✅ toArray() 必须传入类型数组：list.toArray(new String[0])

并发
13. ❌ ArrayList 不是线程安全的，并发 add 会丢数据甚至越界
14. ❌ fail-fast 是 best-effort，不能当并发安全保证
15. ✅ 读多写极少 → CopyOnWriteArrayList
16. ✅ 高频写并发 → ConcurrentLinkedQueue / LinkedBlockingQueue
17. ❌ 别用 Vector

选型
18. ✅ 默认选 ArrayList，绝大多数场景它比 LinkedList 快
19. ✅ 需要队列/栈时选 ArrayDeque 而不是 LinkedList
20. ✅ 元素数量巨大且内存敏感时，先算 ArrayList 与 LinkedList 的内存差（约 6 倍）

总结

回到开头那个 3.2 秒的导出——根因不是数据库慢，是 ArrayList 扩容了 24 次，每次都要分配新数组、拷贝全部元素，并丢弃一个越来越大的旧数组。改一个构造参数就解决了。

这篇文章的核心结论：

  1. size 和 capacity 是两回事，capacity - size 就是被浪费的内存，最多可达元素数的 50%。
  2. 两个空数组常量是为了区分创建方式：new ArrayList<>() 首次扩到 10，new ArrayList<>(0) 老实从 1 开始。这是用”对象身份”代替 boolean 字段的技巧。
  3. 扩容 1.5 倍不是拍脑袋：数学上增长因子必须 < 黄金分割比 φ ≈ 1.618，旧数组内存才有机会被复用；2 倍做不到。
  4. MAX_ARRAY_SIZE = Integer.MAX_VALUE - 8 减的 8 字节是给 JVM 数组对象头预留的。
  5. 均摊 O(1) ≠ 每次 O(1)：单次扩容仍是 O(n)，对延迟敏感的服务要预分配容量。
  6. foreach 删除抛 CME 的根因是 modCount != expectedModCount；但删倒数第二个元素时 hasNext() 提前返回 false，不抛异常——静默错误比崩溃更危险。
  7. LinkedList 几乎总是错的选择：内存占用 5~6 倍，且缓存局部性极差，实测常比 ArrayList 慢。
  8. elementData 用 transient + 自定义 writeObject，是为了只序列化 size 个有效元素，而不是整个 capacity。

一句话概括 ArrayList 的本质：它用”空间换时间”（预留容量）和”均摊”（1.5 倍增长）把动态数组做到接近静态数组的性能，代价是最多 50% 的内存浪费和偶发的 O(n) 扩容尖刺。理解这两笔账，就知道什么时候该预分配、什么时候该 trimToSize、什么时候该换个容器。
