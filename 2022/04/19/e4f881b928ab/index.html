全局异常处理——让接口错误不再裸奔

发布于 2022-04-19 分类：技术, 2022, SpringBoot 👁

前言

刚写接口的时候，异常处理就是在每个 Controller 方法里 try-catch，代码又丑又重复。在实际场景中，更糟糕的事情发生了——瓦斯报警接口忘了 try-catch，直接把 500 错误和完整堆栈信息返回给了矿端前端，堆栈里还包含了数据库连接信息，这可是严重的安全隐患。直到学会全局异常处理，才真正统一了错误返回格式。

本文将从实际项目的真实场景出发，系统讲解全局异常处理的设计、实现和最佳实践。

没有全局异常处理的痛点

痛点分析

没有全局异常处理的痛点

  1. 代码重复
  2. 容易遗漏
  3. 格式不统一
  4. 日志不统一

异常处理的原则

1. 不要吞掉异常

2. 不要把堆栈信息返回给前端

3. 异常粒度要合适

4. 日志级别要区分

异常日志级别选择

  • 参数校验异常 → log.warn
  • 理由：客户端问题，不是系统bug
  • 业务异常 → log.warn
  • 理由：预期的业务错误，不是系统bug
  • 系统异常 → log.error
  • 理由：非预期的系统bug，需要关注和修复
  • 数据库异常 → log.error
  • 理由：可能是数据问题或系统bug
  • 认证授权异常 → log.warn
  • 理由：可能是攻击行为，需要记录但不是bug

5. 异常处理器按粒度从细到粗排列

异常与 HTTP 状态码

异常与HTTP状态码映射

  • 2xx 成功
  • 200 OK → 正常业务响应
  • 201 Created → 资源创建成功
  • 4xx 客户端错误
  • 400 Bad Request → 参数校验失败
  • 401 Unauthorized → 未认证
  • 403 Forbidden → 无权限
  • 404 Not Found → 资源不存在
  • 405 Method Not Allowed → 请求方法不支持
  • 415 Unsupported Media Type → Content-Type不支持
  • 429 Too Many Requests → 请求过于频繁
  • 5xx 服务端错误
  • 500 Internal Server Error → 系统异常
  • 注意：前后端分离项目中，HTTP状态码通常都返回200
  • 通过业务状态码(Result.code)来区分成功/失败
  • 只有认证/授权类异常才使用401/403状态码

总结

全局异常处理是接口规范化的基础设施。在实际场景中，从每个方法 try-catch 到统一全局处理，核心收获是：异常处理是横切关注点，应该统一管理而非分散处理。好的异常处理体系让代码更简洁、错误更可追溯、用户体验更友好。

关键收获：

  • @RestControllerAdvice 是全局异常处理的核心注解
  • 异常分类体系 让错误码和消息更有语义
  • 业务异常 warn，系统异常 error 是日志级别的基本规则
  • 永远不要把堆栈返回给前端 是安全底线
  • 异常处理器粒度从细到粗 是匹配顺序的关键
  • 关键异常要告警 是运维的保障
