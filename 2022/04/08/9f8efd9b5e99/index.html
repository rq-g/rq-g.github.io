RESTful API设计——从随意命名到规范接口

发布于 2022-04-08 分类：技术, 2022, SpringBoot 👁

前言

刚写接口的时候，URL 命名随心所欲：/getUser、/deleteOrder、/queryList 各种风格混搭，甚至出现过 @GetMapping("/deleteUser") 这种用 GET 做删除的”作品”。直到和前端联调，命名不统一、状态码不一致、返回格式混乱，联调效率极低。后来团队统一了 RESTful 规范，协作顺畅了很多。

这篇文章把团队规范沉淀下来：核心思想、URL 设计、HTTP 方法语义、返回格式、以及几个实践中真正纠结过的决策。

什么是 RESTful？

REST 的核心思想一句话：用 URL 定位资源，用 HTTP 方法描述操作。

由此推出四条基本原则：

  1. URL 表示资源：名词（复数），不出现动词；
  2. HTTP 方法表示操作：GET 查、POST 增、PUT 改、DELETE 删；
  3. 状态码语义化：200/400/401/403/404/500 各司其职；
  4. 返回格式统一：全站一致的 JSON 结构。

反面教材 vs 正确姿势

用 GET 做删除不只是风格问题，是安全事故预备役：浏览器预加载、爬虫、URL 分享、CDN 缓存都可能”误触”你的删除接口。GET 必须无副作用，这是底线。

命名格式

  • 名词用复数（/users 不是 /user）；
  • 多级名词用中划线（/order-items，比驼峰或下划线对 URL 更自然）；
  • 过滤/排序/搜索用查询参数而不是新 URL：GET /users?status=1&sort=createdAt,desc&keyword=张。

HTTP 方法语义：重点是幂等性

方法 语义 幂等 安全
GET 查询 ✅ ✅（无副作用）
POST 新增 ❌ ❌
PUT 全量替换 ✅ ❌
PATCH 部分更新 ✅（规范上） ❌
DELETE 删除 ✅ ❌

幂等性 = 同一请求执行多次和一次的效果相同。这不是理论概念，它是重试机制的基石：网络超时后敢不敢自动重试，取决于方法是否幂等——GET/PUT/DELETE 可以放心重试，POST 绝对不能盲重试（重复下单就是这么来的，解决之道是幂等 token 或唯一业务键，见 MQ 幂等相关文章）。

PUT 和 PATCH 的区别也在这里：PUT 是”整个资源替换成我给你的”（幂等，缺的字段等于被置空）；PATCH 是”只改我给你的字段”。实践上很多团队只用 PUT + 全量对象，也能接受，但要全团队统一，两种语义混用最容易出 bug。

一个真实的团队争论：HTTP 状态码用不用？

两种流派：

方案 优点 缺点
严格 REST：HTTP 状态码表达一切 语义标准，网关/监控可直接按状态码统计错误率 前端要处处判状态码；部分代理/网关对 4xx/5xx 有拦截逻辑
永远 200 + 业务 code 前端处理统一；网关不误拦 监控系统无法靠状态码识别错误；语义浪费

我们的折中：HTTP 层面用状态码区分大类（200/401/403/500），业务错误统一 200 + body 里的 code。关键是在《接口规范》里写死，别让每个接口自己发挥。

Controller 层规范

三条纪律：Controller 只做参数转换和编排，不写业务；入参出参用 DTO/VO 而不是 Entity；创建接口返回新资源 ID（前端创建后跳详情页要用）。

API 版本管理

版本升级的纪律：v2 上线不等于 v1 删除——旧版本保留一个过渡期，配合调用方流量监控，归零后再下线。直接改老接口是联调事故的经典来源。

总结

  1. 核心一句话：URL 定位资源，HTTP 方法描述操作——四条原则（资源名词、方法语义、状态码、格式统一）覆盖 90% 场景；
  2. GET 必须无副作用，这是安全底线不是风格偏好；幂等性是重试机制的基石，POST 不能盲重试；
  3. 非 CRUD 动作名词化为子资源（POST /orders/{id}/cancel），一致性和可读性优先于教条；
  4. 状态码流派之争的答案是”团队写进规范统一执行”：HTTP 状态码分大类 + 业务 code 细分，是实践中的主流折中；
  5. 版本管理用 URL 路径（/v1/），升级不删旧版，流量归零再下线；
  6. 文档跟代码走（SpringDoc），Controller 只做编排、DTO/VO 隔离 Entity——接口层的规范最终都服务于一个目标：让前后端协作的沟通成本趋近于零。
