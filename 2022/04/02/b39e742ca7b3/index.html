SpringMVC请求流程——一个HTTP请求的旅程

发布于 2022-04-02 分类：技术, 2022, SpringBoot 👁

前言

写了一段时间的实际项目Controller，@RequestMapping、@RequestBody、@ResponseBody用得很溜，但一个HTTP请求从浏览器发出到Controller方法执行，中间经历了什么？这个问题困扰了我很久。尤其是瓦斯报警接口偶尔返回401，排查时不知道是Filter拦的还是Interceptor拦的，直到梳理了SpringMVC的完整请求流程，才能精准定位问题。

SpringMVC核心组件

组件 作用 矿山项目对应
DispatcherServlet 前端控制器，统一入口 所有请求的调度中心
HandlerMapping 处理器映射，找到对应Controller URL -> GasMonitorController.getById
HandlerAdapter 处理器适配器，调用Controller方法 参数绑定、返回值处理
HandlerInterceptor 拦截器，Controller前后执行 认证、日志、权限
Controller 处理器，业务逻辑 GasMonitorController
ViewResolver 视图解析器 前后端分离后基本不用
HttpMessageConverter 消息转换器 JSON <-> Java对象

完整请求流程

一个HTTP请求的完整旅程

  1. Servlet容器(Tomcat)接收请求
  2. Filter链执行（编码、跨域、XSS）
  3. DispatcherServlet接收请求
  4. HandlerMapping查找Handler
  5. 执行HandlerInterceptor.preHandle()
  6. HandlerAdapter调用Handler
  7. Controller处理业务
  8. 执行HandlerInterceptor.postHandle()
  9. 视图渲染 / 返回JSON（@ResponseBody）
  10. 执行HandlerInterceptor.afterCompletion()
  11. DispatcherServlet返回响应
  12. Filter链返回

总结

理解SpringMVC的请求流程，是从”会用”到”理解”的关键一步。在实际场景中，一个HTTP请求的旅程：Filter -> DispatcherServlet -> HandlerMapping -> Interceptor.preHandle -> HandlerAdapter -> Controller -> Interceptor.postHandle -> 响应。知道每一层在做什么，遇到问题就能精准定位。瓦斯报警接口返回401，是Filter没放行还是Interceptor拦截？理解了流程就能快速判断。
