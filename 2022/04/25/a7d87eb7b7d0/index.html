拦截器与过滤器——请求的前后置处理

发布于 2022-04-25 分类：技术, 2022, SpringBoot 👁

前言

做实际项目时，几乎每个接口都要验证用户是否登录，不同角色（矿长/调度员/安检员）权限不同。最初我在每个Controller方法里手动检查token，重复代码一大堆。更危险的是，有一次瓦斯报警接口忘了加权限检查，安检员直接触发了矿长才能执行的紧急断电操作。后来才知道，这种横切逻辑应该放在拦截器或过滤器中统一处理。

过滤器Filter

什么是过滤器？

过滤器是Servlet规范的一部分，在请求到达DispatcherServlet之前和之后执行。

Filter执行位置

  • 请求 -> Filter1 -> Filter2 -> DispatcherServlet -> Controller
  • 响应 <- Filter1 <- Filter2 <- DispatcherServlet <- Controller
  • Filter在Servlet容器层面，在SpringMVC之前

拦截器Interceptor

什么是拦截器？

拦截器是SpringMVC的一部分，在请求到达Controller之前和之后执行。

Interceptor执行位置

  • 请求 -> Filter -> DispatcherServlet
  • -> Interceptor1.preHandle
  • -> Interceptor2.preHandle
  • -> Controller
  • -> Interceptor2.postHandle
  • -> Interceptor1.postHandle
  • -> 视图渲染
  • -> Interceptor2.afterCompletion
  • -> Interceptor1.afterCompletion
  • -> DispatcherServlet -> Filter -> 响应

如何选择Filter还是Interceptor？

场景 推荐 原因
编码转换 Filter Servlet层面，最早处理
跨域处理 Filter 预检请求在DispatcherServlet之前
XSS过滤 Filter 需要包装Request
压缩/加密 Filter 通用HTTP处理
权限认证 Interceptor 需要注入UserService
日志记录 Interceptor 需要Handler信息
重复提交 Interceptor 需要用户上下文
上下文传递 Interceptor 需要Spring Bean

原则：和业务相关的用Interceptor，和HTTP协议相关的用Filter。

  • +– 需要Spring Bean？

  • +– 需要Handler信息？
  • | +– 是 –> Interceptor
  • | +– 否 –> 都可以
  • |
  • +– 需要处理非DispatcherServlet的请求？
  • +– 是 –> Filter

总结

拦截器和过滤器是Web开发中处理横切逻辑的利器。在实际场景中，最大的收获是理解了它们的区别和适用场景：Filter处理HTTP层面的通用逻辑，Interceptor处理业务层面的横切逻辑。用好它们，Controller就能专注于业务，不再被重复的认证、日志、限流代码污染。矿山安全场景下，权限拦截器的遗漏可能导致严重后果，必须统一管理。

Filter 和 Interceptor 的性能对比

Filter vs Interceptor 性能对比

  • Filter性能更高：
    • 在Servlet层执行，不经过Spring MVC解析
    • 适合高频、轻量的操作（如CORS、编码）
  • Interceptor功能更强：
    • 在Spring MVC层执行，可以获取Handler信息
    • 可以注入Spring Bean
    • 适合需要业务数据的操作（如认证、权限）
  • 建议：
    • 能用Filter解决的，优先用Filter
    • 需要Spring上下文的，用Interceptor
    • 不要在Filter/Interceptor中做耗时操作

拦截器链的执行流程详解

拦截器链执行流程（含异常场景）

  • 正常流程：
  • Interceptor1.pre → Interceptor2.pre → Controller
  • → Interceptor2.post → Interceptor1.post
  • → Interceptor2.after → Interceptor1.after
  • preHandle返回false：
  • Interceptor1.pre(false) → Interceptor1.after
  • （后续拦截器和Controller都不执行）
  • Controller抛异常：
  • Interceptor1.pre → Interceptor2.pre → Controller(异常)
  • → Interceptor2.after → Interceptor1.after
  • （postHandle不执行，afterCompletion一定执行）
  • 重要：afterCompletion无论是否异常都会执行
  • 所以资源清理必须放在afterCompletion中
