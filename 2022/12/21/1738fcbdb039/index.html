Nginx进阶——负载均衡与动静分离

发布于 2022-12-21 分类：技术, 2022, 工程化 👁

前言

在实际场景中，最初Nginx只用来做反向代理。后来项目流量增大，单实例扛不住了，开始用Nginx做负载均衡和动静分离，系统吞吐量提升了好几倍。同时，安全防护方面也用到了Nginx的限流和HTTPS配置。

本篇将结合实际项目的实战经验，从负载均衡、动静分离、HTTPS配置、限流防护到日志监控，全面解析Nginx进阶用法。

HTTPS握手流程

TLS 1.2 vs TLS 1.3 握手流程对比：

  • TLS 1.2 (2-RTT):
  • Client ── ClientHello ──────────────────→ Server
  • Client ←── ServerHello + Certificate ──── Server
  • Client ── Key Exchange + ChangeCipherSpec → Server
  • Client ←── ChangeCipherSpec + Finished ── Server
  • ══════════════ 加密通信开始 ══════════════
  • TLS 1.3 (1-RTT):
  • Client ── ClientHello + Key Share ──────→ Server
  • Client ←── ServerHello + Key Share + Finished ── Server
  • ══════════════ 加密通信开始 ══════════════
  • TLS 1.3优势：
    1. 握手从2-RTT减少到1-RTT
    1. 移除了不安全的加密算法
    1. 支持0-RTT恢复（已连接过的客户端）
    1. 智慧矿山场景：瓦斯告警推送延迟降低50ms

限流配置

限流区域定义

限流算法对比：

  • 算法 | 特点 | Nginx实现
  • 固定窗口 | 简单但有突刺 | limit_req
  • 滑动窗口 | 平滑无突刺 | 第三方模块
  • 令牌桶 | 允许突发流量 | limit_req+burst
  • 漏桶 | 恒定速率处理 | rate限速
  • limit_req参数说明：
  • rate=10r/s → 每秒10个请求
  • burst=20 → 允许20个请求排队等待
  • nodelay → 排队的请求立即处理，不延迟
  • burst+nodelay = 令牌桶效果

CORS预检请求流程

CORS预检请求处理流程：

  • 简单请求（GET/POST无自定义头）：
  • 浏览器 ── POST /api/device ──→ Nginx → 后端
  • 浏览器 ←── 200 + CORS头 ──── Nginx ← 后端
  • (一次请求完成)
  • 预检请求（PUT/DELETE/自定义头）：
  • Step1: 浏览器 ── OPTIONS /api/device ──→ Nginx
  • Nginx → 返回204 + CORS头（不转发后端）
  • Step2: 浏览器 ── PUT /api/device ──→ Nginx → 后端
  • Nginx ←── 200 + CORS头 ──── 后端
  • (两次请求完成)
  • 智慧矿山踩坑：
  • 问题：OPTIONS请求被转发到后端，后端返回401
  • 原因：OPTIONS请求不带Authorization头
  • 解决：Nginx层直接返回204，不转发OPTIONS到后端

Nginx进程模型：

  • Master进程（1个）：

└── 不处理业务请求：

  • Worker进程（多个，通常=CPU核心数）：

└── 单Worker可处理数万并发：

  • Cache Manager进程（1个）：
  • └── 管理缓存索引和过期清理
  • Cache Loader进程（1个）：
  • └── 启动时加载缓存索引到共享内存
  • 智慧矿山配置：
  • worker_processes auto; # 自动检测CPU核心数
  • worker_connections 10240; # 每个Worker最大连接数

  • 8核CPU：8 * 10240 = 81920个并发连接

Nginx平滑重启

平滑重启流程

Nginx平滑重启流程 (nginx -s reload)：

    1. Master进程收到reload信号
    1. 加载新的nginx.conf配置
    1. 启动新的Worker进程（使用新配置）
    1. 向旧Worker进程发送GRACEFUL_SHUTDOWN信号
    1. 旧Worker继续处理已建立的连接

└── 空闲连接 → 立即关闭：

    1. 旧Worker处理完所有请求后退出
    1. 只有新Worker在运行
  • 智慧矿山注意：
  • reload期间极短时间可能有502（新旧Worker交接间隙）
  • 解决：配置backup节点，reload时请求转到backup
  • 部署脚本：
  • #!/bin/bash
  • nginx -t && nginx -s reload && echo “reload success”

  • -t 先检查配置语法，再reload
