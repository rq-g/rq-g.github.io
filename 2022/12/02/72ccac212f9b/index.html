代码调试技巧——从println到专业调试

发布于 2022-12-02 分类：技术, 2022, 编码规范 👁

前言

刚写代码那会儿，调试全靠 System.out.println：到处加打印，跑一遍，删掉，再加，再删。最崩溃的一次是为了找一个偶现的空指针，前后加了 30 多行 println。后来系统学了 IDEA 的调试功能才发现：大多数人只用到了断点调试 10% 的能力——条件断点、日志断点、异常断点、表达式求值这几个功能，是质的飞跃。

这篇文章按”基础 → 进阶断点 → 运行时操控 → 特殊场景 → 方法论”的顺序，把我现在日常在用的调试技巧完整过一遍。

断点调试基础

核心快捷键（IDEA 默认，建议刻进肌肉记忆）

快捷键 功能 使用场景
Ctrl + F8 设置/取消断点 行号左侧点击等价
Shift + F9 Debug 模式启动 区别于普通运行
F8 Step Over 单步执行 不进入方法内部
F7 Step Into 进入方法 进入自己写的方法
Alt + Shift + F7 Force Step Into 强制进入 JDK/框架源码
Shift + F8 Step Out 跳出方法 当前方法剩余部分跑完
F9 Resume 到下一个断点 断点之间的快速移动
Alt + F8 Evaluate Expression 表达式求值，后面重点讲

一个新手常见误区：在框架代码入口点断点然后一路 F7 跟进去，结果陷进 Spring 源码出不来了。正确的姿势是 F8 大步走、只在自己写的代码上停下来；要进源码时用 Alt + Shift + F7 强制进入。

4. 字段断点：谁改了我的值？

在字段声明行打断点（默认是红色圆圈带标志），右键勾选：

  • Field access：字段被读取时暂停
  • Field modification：字段被修改时暂停

排查”某个状态字段莫名被改了”的神器——比全文搜索 setStatus 靠谱得多，因为它抓的是运行时的真实写入，连反射修改都逃不掉。

多线程调试

并发问题”单步复现不了、一打断点就消失”（海森堡 bug），需要专门的姿势：

  1. 切换线程视角：Debug 面板勾选 Show stack frames for all threads，能同时看到所有线程停在哪一行；
  2. 线程暂停策略：右键断点 → Make Default，可选 Suspend: All（所有线程都停）或 Thread（只停命中线程）——排查竞态时选 All，把现场完整冻结；
  3. 条件断点抓偶现：this.count != expectedCount 这类不变量断言，一旦被破坏立刻暂停。

单步调试会改变线程的时序，很多并发 bug 反而应该用 jstack 抓现场、用代码审查定位，而不是靠断点。这个分寸后面方法论部分细说。

每一步的输入输出都能展开看，处理”过滤条件写错导致结果不对”这类问题时一目了然。

远程调试：连上测试环境的 JVM

IDEA：Run → Edit Configurations → + → Remote JVM Debug，填主机和端口，Debug 连接即可，之后就像调试本地代码一样打断点。

三条铁律，违反过的人都付出了代价：

  1. 本地代码必须和远程部署的版本完全一致，否则断点行号错位，看到的”现场”是错乱的；
  2. 断点会挂起整个请求线程——线上环境绝对不要开（要用也是 Arthas，见下文）；
  3. 测试环境用完记得断开连接，忘掉的断点会在第二天早上把测试环境卡死，全组等你。

调试方法论：调试是推理，不是碰运气

工具只是手段，真正拉开效率差距的是方法论。

假设驱动的调试循环

flowchart LR
    A[观察现象
报错信息/日志/复现步骤] --> B[提出假设
最可能的原因是什么]
    B --> C[设计最小验证
一个断点/一行日志/一个实验]
    C --> D{假设成立?}
    D -->|是| E[修复并验证]
    D -->|否| F[排除该假设
修正认知回到 B]
    E --> G[总结: 为什么会写错
怎样从代码层面防住]

新手和熟手的差别就在这个循环的速度：新手”打断点 → 单步走 → 看看哪里怪怪的”，靠运气撞；熟手先读报错和日志形成假设，再用一次断点/求值去验证。每一次暂停都应该带着问题去。

三条实践原则

  1. 二分定位：执行链路长时，在中间打断点先分一半——问题在前面还是后面？log/日志断点铺在链路中段，两三次就能夹出问题行；
  2. 最小复现：剥离无关因素（关掉缓存、固定随机种子、造最小数据集），复现路径越短，定位越快，最后还能沉淀成回归测试；
  3. 分场合选武器：逻辑错误 → 断点调试；性能问题 → trace/火焰图而不是单步；并发问题 → jstack/代码审查优先；线上问题 → 日志 + Arthas。单步调试是逻辑 bug 的手术刀，不是万能钥匙。

一条容易被忽略的收尾动作

每个 bug 修完，花两分钟回答：这个 bug 为什么会发生？以后怎么在编码阶段防住（参数校验、Optional、超时设置、幂等）？很多”调试技巧”的终极形态，是让这一类 bug 从根上消失。

总结

  1. 告别 println 大法：日志断点 = 不改代码的 println，条件断点 = 精准命中目标数据，这两个功能组合能覆盖 80% 的调试场景；
  2. 异常断点抓 NPE 抛出瞬间，字段断点抓”谁改了我的值”，都比人肉搜索靠谱；
  3. 表达式求值（Alt + F8）让你暂停时执行任意代码验证猜想；Set Value / Drop Frame 能改现场，但记住外部副作用不会回滚；
  4. 远程调试三大铁律：版本一致、不上生产、用完断开；生产环境交给 Arthas 和 jstack/jmap；
  5. 方法论优先于工具：假设 → 最小验证 → 修正的循环 + 二分定位 + 最小复现，调试从碰运气变成推理过程；
  6. 最高级的调试技巧是修完后的两分钟复盘——把这一类 bug 从代码层面防住，才是真正减少了调试时间。
