日志收集入门——从散落日志到集中管理

发布于 2022-12-28 分类：技术, 2022, 工程化 👁

前言

在搭建日志系统之前，我们排查问题的姿势是这样的：用户报障 → 问网关在哪台机器 → ssh 登录 → grep 半天 → 发现要看的下游服务在另一台机器 → 再登录另一台。一次故障定位平均要登上四五台机器，而且日志滚动归档后，grep 历史文件慢得令人绝望。

压垮骆驼的最后一根稻草是一次跨 3 个服务的偶现超时：日志分散在 6 台机器上，时序对不上，我们花了两天才靠肉眼比对时间戳拼出完整链路。搭建 ELK 之后，同样的问题变成一条 Kibana 查询、30 秒出结果。这篇文章记录完整的搭建过程和后来踩过的坑。

架构：先看全景图

各组件的职责边界：

组件 职责 关键特性
Filebeat 在每台应用机器上采集日志文件 Go 编写，内存占用 ~10MB，断点续传（registry 记录 offset）
Logstash 解析、过滤、字段富化 JVM 进程，重度处理放这里，集群侧可水平扩展
Elasticsearch 存储 + 倒排索引检索 按天建索引，可配置生命周期策略
Kibana 查询界面、仪表盘、告警 DSL/KQL 查询

规模小可以砍掉 Logstash：Filebeat 直连 ES（output.elasticsearch），解析工作交给应用侧的 JSON 日志（见下文），链路越短越不容易出问题。

第一步：把日志写对——结构化是前提

日志系统的质量上限，由应用写日志的方式决定。采集和存储做得再好，日志本身是散乱文本，检索照样抓瞎。

级别使用规范

先统一级别语义，这是团队规范问题，比工具重要：

级别 语义 例子
ERROR 需要人工介入的异常 RPC 失败重试耗尽、数据不一致
WARN 可自动恢复的异常，需关注趋势 缓存 miss 降级、重试第 1 次
INFO 关键业务动作与状态变更 订单创建、任务下发、配置变更
DEBUG 详细过程信息，生产默认关闭 方法入参、中间计算

最常见的误用：把 ERROR 当 INFO 打（”开始处理”也打 ERROR），导致告警系统里 ERROR 日志泛滥，真故障被淹没——告警的价值与 ERROR 日志的信噪比成正比。

日志内容的三条红线

  1. 异常必须打完整堆栈：log.error("查询用户失败, userId={}", userId, e)——注意 e 作为最后一个参数，不要拼进字符串；
  2. 敏感信息脱敏：手机号、身份证、token 打进日志就是数据安全事故，用工具类统一脱敏；
  3. 禁止打印大对象：把整个 List 或请求体 toString 进日志，一次百万数据的批量任务能打出几个 G 的日志，把采集管道和 ES 磁盘打爆——真实发生过的事故，见文末”成本治理”。

第二步：MDC 链路追踪——让日志能”穿针引线”

集中收集解决了”日志在哪”，traceId 解决”日志是哪条链路的”。一次请求经过网关、服务 A、服务 B，把同一个 traceId 注入每一行日志，Kibana 里就能按 traceId 一把捞出完整链路。

第三步：采集与解析配置

Filebeat

multiline 是堆栈日志的关键：Java 异常堆栈有很多行，不加这个配置，堆栈会被拆成几十条独立日志，ES 里搜出来全是碎片。

Logstash

如果应用已经输出 JSON，filter 里一个 grok 都不用写——这就是”解析前移到应用侧”的收益：Logstash 只做转发，吞吐翻几倍。

ES 索引生命周期（ILM）

告警阈值要基于历史基线调：日常就有 2 条/5 分钟 ERROR 的服务，阈值设 10 会天天误报；误报三次，告警就没人看了——比没有告警更危险。

成本治理：日志系统的隐藏坑

日志量增长是指数级的，三个实战经验：

  1. 生产环境级别收口：root logger 设 INFO，DEBUG 只对个别包临时开启（动态调整，不重启）；
  2. 日志量监控：对”每日新增日志字节数”本身设告警，某天日志量突增 10 倍，大概率是某个分支在疯狂打日志（或打了大对象）；
  3. 索引分级别：ERROR 日志单独索引、保留 90 天，INFO 保留 30 天——排查用的核心数据保得更久，成本只有原来的一半。

总结

  1. 集中收集的价值不止是”不用逐台 ssh”，而是日志变成可检索的数据，跨服务的时序问题从两天变成 30 秒；
  2. 结构化是前提：应用侧直接输出 JSON 日志，Logstash 零解析，链路短、吞吐高、格式稳；
  3. traceId 让日志能”穿针引线”：MDC 注入 + afterCompletion 清理 + 异步线程用 TaskDecorator 传递 + 跨服务放进请求头，四步缺一不可；
  4. Filebeat 的 multiline 配置是堆栈日志不碎片的保命设置；ES 用 ILM 管生命周期，磁盘水位可控；
  5. 级别规范和信噪比决定告警价值：ERROR 滥发等于没有告警，阈值要基于历史基线调；
  6. 日志系统自己也需要被治理：级别收口、日志量监控、分级保留——别让排查工具本身变成需要排查的问题。
