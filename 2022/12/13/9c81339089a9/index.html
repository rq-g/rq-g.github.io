代码重构技巧——让代码越来越好看

发布于 2022-12-13 分类：技术, 2022, 编码规范 👁

前言

最初写代码只求功能跑通，三个月后回头看自己的代码，简直不忍直视：200 行的 processOrder、五层嵌套的 if-else、满屏魔法值。学会重构后我理解了一件事：代码不是写完就结束的资产，而是要被反复阅读和修改的负债——重构就是定期还债。

重构的定义（Martin Fowler）：在不改变软件可观察行为的前提下，调整其内部结构。抓住两个关键词：”不改变行为”（所以需要测试护住）和”内部结构”（所以与加功能分开）。

四条重构原则（先立规矩）

  1. 小步前进：每次只做一种手法，改完立刻验证——大爆炸式重构是事故之源；
  2. 测试先行：重构前先有测试网，没有测试就先补关键路径的测试；
  3. 持续进行：童子军军规——“让营地比你来时干净”。借改代码的机会顺手重构碰到的坏味道，别攒大扫除；
  4. 与功能分离：重构的 commit 和功能的 commit 严格分开，review 时才能区分”逻辑变化”和”结构变化”。

六个高频重构手法（附真实案例）

1. 提取方法：对付长方法的第一板斧

判断标准不是行数而是层次：方法体里的每一行应该处于同一个抽象层次（校验层/查询层/计算层），混层就是提取方法的信号。IDEA 的 Ctrl + Alt + M 选中即提取，改起来没有心理负担。

2. 以查询替代临时变量——但要警惕性能陷阱

注意：这个手法在循环里要谨慎——每次调用 getBasePrice() 都重算一遍，热路径上可能从 O(n) 变 O(n²)。提取时保留局部变量缓存结果，或者确认调用频率后再决定。

4. 以枚举替代魔法值

简单”状态 → 描述”的映射不用策略模式那么重，枚举就是最轻的正解。of() 方法在入口处把魔法值转成枚举，后续代码全部面向枚举，非法值第一时间被拦截。

5. 封装集合：守住不变量

unmodifiableList 防的是外部 getItems().add(...) 绕过校验直接改数据——这类 bug 排查起来极其隐蔽。

6. 以异常替代错误码

错误码的最大危害是可以被忽略——调用方不写 if (ret != 0) 编译器不吭声；异常则强制处理或显式声明。

代码坏味道识别清单

坏味道 阈值/信号 重构方向
长方法 滚动一屏看不完、注释分节 提取方法
过长参数列表 超过 3 个参数、有同源参数组 封装参数对象
重复代码 复制粘贴过一次 Rule of Three 后提取
分支泛滥 switch/if-else 链随业务增长 策略模式/枚举
魔法值 裸写的数字/字符串 常量/枚举
注释过多 注释在解释”为什么这么写” 让代码自解释，注释只留为什么
发散式变化 一个类因多种原因被修改 拆分职责
霰弹式修改 加一个小功能要改 5 个类 收拢内聚

其中发散式变化和霰弹式修改这对最值得体会：前者说明类职责太多，后者说明逻辑被切得太碎——两个方向的极端都是坏设计。

    B --> C[一次一个手法
小步修改]
    C --> D[跑测试验证]
    D --> E{通过?}
    E -->|否| F[回退本次小步] --> C
    E -->|是| G[提交 commit
重构与功能分离]
    G --> A

什么时候不要重构

重构不是美德绑架，以下情况忍住：

  1. 即将废弃的代码：下个版本就删的模块，重构投入打水漂；
  2. 没有测试覆盖的大面积遗留代码：先补关键路径测试，否则重构只是在”裸奔换轮胎”；
  3. 正在进行的功能分支：等功能合入后再重构，避免无意义的冲突。

借助 IDE 的重构快捷键

重构手法大多数有对应的自动化操作，永远用 IDE 重构而不是手改（语法树级别同步所有引用）：Shift + F6 重命名、Ctrl + Alt + M 提取方法、Ctrl + Alt + V 提取变量、Ctrl + Alt + C 提取常量、Ctrl + F6 改方法签名。

总结

  1. 重构的定义里藏着安全边界：不改变可观察行为——所以测试是前提，小步是纪律；
  2. 六个高频手法覆盖 80% 场景：提取方法（按层次拆）、查询替代临时变量（警惕循环重算）、策略替代条件、枚举替代魔法值、封装集合守不变量、异常替代错误码；
  3. 坏味道识别往两头看：发散式变化说明职责太重，霰弹式修改说明切分太碎，重构在两者之间找平衡；
  4. 三种情况不重构：即将废弃、无测试的大遗留、进行中的功能分支；
  5. 手法交给 IDE 快捷键，判断力留给自己——工具保证不手滑，人负责决定改哪里；
  6. 核心认知：重构不是推倒重来，而是小步改进——童子军军规：每次碰代码，让它比你发现时更干净一点。
