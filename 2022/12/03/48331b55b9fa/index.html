代码审查实践——从怕被review到主动review

发布于 2022-12-03 分类：技术, 2022, 编码规范 👁

前言

刚工作那会儿，每次提 MR（Merge Request）都手心冒汗——评论框里跳一条 “这里为什么要这么写”，第一反应不是思考问题本身，而是”他是不是针对我”。直到有一次，同事在我提的代码里指出了一个 @Transactional 方法内调用远程支付接口的问题，线上差点造成长事务拖垮连接池。那一刻我突然明白：review 不是审判，是免费的一对一技术辅导。

从那以后我开始主动发起 review、主动请求 review，两年下来最大的感受是：团队代码质量的下限，基本由 review 文化决定。这篇文章把我踩过的坑、总结的方法论整理出来。

为什么要做 Code Review：用数据说话

很多人觉得 review 是”流程负担”，我们看几组业界研究结论：

研究结论 数据来源 对我们的启示
代码审查能发现 60% 以上的缺陷，远高于测试单独的发现率 IBM / Cisco 多年实践统计 review 是性价比最高的质量手段
单次 review 超过 400 行，缺陷发现率断崖式下跌 Cisco 团队对 12 个月的 review 数据分析 MR 粒度必须小，一次 200~400 行最佳
review 前 60 分钟效率最高，之后急剧下降 Cisco 研究 单次 review 控制在 1 小时内，别攒着周末一起看
缺陷暴露越晚，修复成本越高：编码期 1 倍 → 测试期 10 倍 → 线上 100 倍 业界通行的缺陷成本曲线 review 拦在进主干之前，等于把钱省在刀刃上

一句话总结：review 的本质是把”线上事故”前置成”评论区讨论”。

Review 到底该查什么：优先级金字塔

新手审查者最常见的失败模式：盯着 for 循环里的空格、i++ 和 ++i，却放过了事务里包着 RPC 调用这种真炸弹。原因是没有优先级意识。

graph TB
    A["第 1 优先级：设计合理性
分层是否清晰？职责是否单一？
方案在高峰流量下能不能活？"] --> B["第 2 优先级：正确性
逻辑漏洞、边界条件、并发安全、事务边界"]
    B --> C["第 3 优先级：安全性
SQL注入、越权、敏感信息泄漏"]
    C --> D["第 4 优先级：可维护性
命名、重复代码、魔法值、可读性"]
    D --> E["第 5 优先级：风格问题
缩进、换行、import 顺序"]

关键结论：第 5 层根本不该由人来看。缩进、命名风格、未使用变量这些机械问题，交给工具：

问题类型 工具 接入方式
代码风格 CheckStyle / Spotless 构建期强制，不合规直接编译失败
潜在 Bug 模式 SpotBugs / ErrorProne 编译期扫描空指针、资源未关闭
代码坏味道 SonarQube CI 流水线门禁，低于阈值阻断合并
依赖漏洞 OWASP Dependency-Check 检查三方包 CVE

人的时间应该花在机器做不了的事情上：架构决策、业务正确性、边界思考。

六类高频问题：真实案例复盘

以下是我在 review 中实际拦截过的问题，按出现频率排序。

1. 事务边界问题（出现最多，杀伤力最大）

正确的拆法是把事务缩到只包数据库操作，远程调用和消息放在事务外：

review 时只要看到一个方法上有 @Transactional，就要条件反射地问三个问题：事务里有 RPC 吗？有发消息吗？事务范围是不是比实际需要的大？

2. N+1 查询

注意我用了 getOrDefault 而不是直接 .get(...).getName()——批量查询后内存组装这一步，还有一个 review 高频 bug：查询结果里缺了某条数据，直接 NPE。修了 N+1，引入了新 NPE，等于白修。

3. 并发问题：check-then-act

这类问题单线程测试永远测不出来，是 review 的独有价值——测试抓不住，只有人看代码才能发现：

review 中看到 get → if 判断 → set/写回 这个三段式，就要立刻警觉。

4. 异常吞噬与日志缺失

log.error("xx: " + e.getMessage()) 这个写法我在 review 里拦过不下二十次——它把堆栈全丢了，排查时只剩一句”连接超时”，不知道发生在哪一行。

5. 重复代码：该抽象时不抽象，不该抽象时硬抽象

但反过来也要警惕过度抽象：两个方法各 3 行、只是碰巧相似，强行抽成一个带 5 个布尔参数的”通用方法”，三个月后没人敢动。review 的经验法则是 Rule of Three：重复出现第三次之前，先忍着。

总结：从”怕”到”主动”的心智转变

  1. review 不是审判，是缺陷成本最低的拦截点——评论区一条意见，省掉的可能是一次线上复盘会；
  2. 人看机器看不出来的：架构、并发、事务、业务正确性；风格问题交给工具和 CI 门禁；
  3. 粒度决定质量：200~400 行的 MR 发现率最高，巨型 MR 等于没 review；
  4. 意见写法有公式：指出问题 + 解释原因 + 给出建议 + 分级标注；
  5. 提 MR 的人对质量负责一半：自我 review、小粒度、描述清晰，是审查者高效的前提；
  6. 最终的心智转变是：把”别人的代码”当成”团队的代码”——你要读它、维护它、在它出事的时候被凌晨叫醒，所以有责任在它进主干之前发表意见。
