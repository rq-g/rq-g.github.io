SQL优化实战——慢查询的排查与优化

发布于 2022-06-24 分类：技术, 2022, MySQL 👁

前言

实际场景中，矿工考勤报表接口越来越慢，从最初的200ms到后来的3秒，用户投诉不断。排查后发现是一条SQL全表扫描导致的——10万条考勤记录没有索引，每次查询都做全表扫描。从那以后，我学会了系统化的慢查询排查和优化方法。

本文将结合实际项目的实战经验，系统讲解慢查询定位、EXPLAIN分析、常见优化场景以及批量操作优化。

慢查询定位

开启慢查询日志

慢查询日志配置建议：

  • 参数 建议值 说明
  • slow_query_log ON 开启慢查询日志
  • long_query_time 1 超过1秒记录
  • log_queries_not_using_indexes ON 记录无索引查询
  • min_examined_row_limit 100 扫描行数<100不记录
  • log_output FILE 日志输出到文件
  • 实际项目配置：
  • long_query_time = 0.5 （核心接口要求500ms内返回）

EXPLAIN执行计划

EXPLAIN关键字段

EXPLAIN关键字段解读

  • type（访问类型）– 最重要！
  • ================================
  • system > const > eq_ref > ref > range > index > ALL
  • system → 系统表，只有一行
  • const → 主键/唯一索引等值查询，最快
  • eq_ref → 关联查询主键/唯一索引
  • ref → 普通索引等值查询
  • range → 索引范围扫描（BETWEEN, >, <, IN）
  • index → 全索引扫描
  • ALL → 全表扫描（必须优化！）
  • 目标：至少达到ref级别，避免ALL和index
  • key（使用的索引）
  • ==================
  • NULL → 没走索引，需要优化
  • 非NULL → 确认是否为期望的索引
  • key_len（索引使用长度）
  • ========================
  • 判断组合索引使用了几个字段
  • key_len = 字段定义长度之和
  • INT: 4字节, BIGINT: 8字节, VARCHAR(n): n*3+2字节(UTF8)
  • rows（预估扫描行数）
  • ======================
  • 越小越好
  • 不是精确值，是优化器的估算
  • Extra（额外信息）
  • ==================
  • Using index → 覆盖索引，好
  • Using where → Server层过滤
  • Using filesort → 额外排序，需优化！
  • Using temporary → 使用临时表，需优化！
  • Using index condition → 索引条件下推(ICP)，好

常见优化场景

1. 全表扫描 → 加索引

2. 文件排序 → 优化ORDER BY

ORDER BY优化原理：

  • 无索引排序：
  • 查询结果 → 在内存/磁盘中排序 → 返回
  • （Using filesort，额外开销）
  • 有索引排序：
  • 索引本身就是有序的 → 直接按索引顺序读取 → 无需额外排序
  • （Using index，高效）
  • 组合索引 idx(status, report_time)
  • 相同status下，report_time已排序
  • WHERE status = 0 ORDER BY report_time → 直接按索引读

3. 回表过多 → 覆盖索引

4. 深分页 → 延迟关联

深分页优化对比：

  • 方案1：普通LIMIT（慢）
  • LIMIT 100000, 10
  • → 扫描100010行，丢弃前100000行
  • → 返回10行
  • → 浪费了扫描100000行的时间
  • 方案2：延迟关联（快）
  • 子查询 SELECT id … LIMIT 100000, 10
  • → 走覆盖索引，只查ID
  • → 关联查询获取完整数据
  • → 快得多！
  • 方案3：游标分页（最快，推荐）
  • WHERE id > #{lastId} LIMIT 10
  • → 走主键索引，直接定位
  • → 无需扫描前面的行
  • → 缺点：不支持跳页

SQL优化的步骤

SQL优化流程

  • Step1：定位慢SQL
  • +– 慢查询日志
  • +– pt-query-digest分析
  • +– 应用APM监控
  • Step2：EXPLAIN分析

  • Step3：针对性优化
  • +– ALL → 加索引
  • +– Using filesort → 优化ORDER BY
  • +– Using temporary → 优化GROUP BY
  • +– 回表多 → 覆盖索引
  • +– 深分页 → 延迟关联
  • Step4：验证优化效果
  • +– 再次EXPLAIN确认
  • +– 对比优化前后查询时间
  • +– 压测验证

总结

SQL优化是后端开发的基本功。在实际场景中，我从”SQL慢就加索引”到”系统化排查优化”，核心方法是：慢查询日志定位 → EXPLAIN分析 → 针对性优化 → 验证效果。80%的SQL性能问题，通过加索引和避免索引失效就能解决。

经过深入学习，我还理解了：

  • 慢查询日志是定位问题SQL的第一步，pt-query-digest是分析利器
  • EXPLAIN的type和Extra是最重要的判断依据
  • 覆盖索引避免回表，延迟关联解决深分页
  • 批量操作要分批执行，避免长事务
  • SQL优化是一个持续的过程，需要监控和定期维护

索引优化策略对比

优化策略 适用场景 优化效果 代价 智慧矿山案例
添加单列索引 等值查询条件 高 写入变慢 考勤日期索引
组合索引 多条件查询 高 写入变慢 状态+时间索引
覆盖索引 查询列少 中 索引变大 设备ID+状态查询
前缀索引 长字符串 中 精度降低 设备名称前缀索引
函数索引 函数查询(MySQL 8.0+) 高 写入变慢 DATE函数索引
延迟关联 深分页 高 SQL复杂 隐患列表分页
FORCE INDEX 优化器选错索引 中 硬编码 物资统计查询

面试题精选

序号 面试题 关键答案
1 如何定位慢查询？ slow_query_log + pt-query-digest
2 EXPLAIN的type有哪些？ system/const/eq_ref/ref/range/index/ALL
3 Using filesort一定慢吗？ 不一定，数据量小时可接受
4 覆盖索引是什么？ 查询字段都在索引中，不需要回表
5 深分页怎么优化？ 延迟关联、游标分页
6 为什么索引列不能用函数？ 函数导致索引失效，改为范围查询
7 隐式转换是什么？ 字段和值类型不一致，导致索引失效
8 FORCE INDEX什么时候用？ 优化器选错索引时，但要慎用
9 批量插入怎么优化？ INSERT…VALUES批量、LOAD DATA
10 COUNT(*)和COUNT(1)区别？ InnoDB下无区别，都遍历
11 ORDER BY怎么优化？ 排序字段建索引、覆盖索引
12 GROUP BY怎么优化？ 分组字段建索引、WHERE先过滤
13 子查询和JOIN哪个快？ 通常JOIN更快，但看场景
14 索引越多越好吗？ 不是，影响写入性能和存储
15 如何监控SQL性能？ slow_query_log + performance_schema
