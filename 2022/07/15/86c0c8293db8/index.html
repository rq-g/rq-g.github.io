Java并发基础——线程创建与同步机制

发布于 2022-07-15 分类：技术, 2022, Java基础 👁

前言

在智慧矿山调度系统里踩过一个至今印象深刻的坑：80 台矿卡每秒上报一次 GPS，后台用一个 static int onlineTruckCount 统计在线车辆数。压测时 80 台车全在线，页面上却经常显示 78、79，偶尔跳回 76。

当时的第一反应是”丢包了”，抓包看数据一条不少。真正的原因很简单——count++ 不是原子操作。

这类问题的共性在于：代码语法完全正确、单线程跑百分百正确、一到并发就偶发。偶发意味着它会在测试环境消失、在生产高峰期出现。要根治它，靠死记”用 synchronized 包起来”是远远不够的，得知道底层到底发生了什么。

这篇文章不打算复读 API 文档。重点回答五个问题：

  1. 线程到底是怎么被创建和调度的，为什么生产环境禁止裸 new Thread()？
  2. 为什么 count++ 会丢数据？丢在哪一步？
  3. volatile 保证的”可见性”到底是什么，为什么它救不了 count++？
  4. synchronized 锁的到底是什么东西，JDK 1.6 之后它为什么不再慢？
  5. wait/notify 为什么要写在 while 里，写 if 会怎样？

一、线程的三种创建方式，以及为什么生产环境一个都不用

1.1 三种写法

三者的核心区别其实只有一条：能不能拿到返回值、能不能抛出受检异常。

方式 返回值 抛受检异常 能否继承其他类 任务与线程是否解耦
继承 Thread ❌ ❌ ❌（单继承） ❌ 绑死
实现 Runnable ❌ ❌ ✅ ✅
实现 Callable ✅ ✅ ✅ ✅

1.2 本质：Thread 和 Runnable 是什么关系

很多人以为这是”两种创建线程的方式”，其实不是——Java 只有一种创建线程的方式：new Thread().start()。

Thread 类本身就实现了 Runnable：

所以”实现 Runnable”只是把任务体交给 Thread 对象，线程永远是 Thread。这也解释了为什么推荐 Runnable：

  • Thread 类把”任务”和”执行任务的载体”耦合在一起，一个 Thread 实例只能跑一次（start() 第二次抛 IllegalThreadStateException），而 Runnable 可以被多个 Thread 复用，也可以交给线程池。
  • 继承 Thread 浪费掉了唯一的继承名额。

Callable 又多一层：FutureTask 同时实现了 Runnable 和 Future，所以能塞进 new Thread(futureTask) ——它本质上还是个 Runnable，只是额外提供了 get() 拿结果的能力。

1.3 start() 和 run() 到底差在哪

start() 内部调用的是 native 方法 start0()，由 JVM 走到 JVM_StartThread，最终调用操作系统的线程创建 API（Linux 下是 pthread_create）。线程是操作系统资源，不是 Java 对象——new Thread() 只是 new 了个 Java 对象，此时操作系统里还没有任何线程；只有 start() 之后才真正有。

这就是为什么 start() 不能调用两次：底层 pthread 已经创建过，Java 侧用 threadStatus 字段做校验，非零就抛异常。

1.4 为什么生产环境禁止裸 new Thread()

原始博客里的”多线程采集”示例就是典型反面教材——每来一个设备就 new Thread().start()。这在 4 台设备的 demo 里没问题，在 2000 台设备的生产环境里是灾难：

问题 具体后果
内存 每个线程默认栈大小 1MB（-Xss，64 位 Linux HotSpot 默认 1MB）。2000 个线程 ≈ 2GB 虚拟内存，直接 OutOfMemoryError: unable to create new native thread
创建成本 一次 pthread_create + 栈分配约几十微秒到毫秒级，高频创建销毁比执行任务本身还慢
调度开销 线程数远超 CPU 核数后，大量时间花在上下文切换（一次切换约 1~5μs，还要污染 L1/L2 缓存和 TLB）
不可治理 没有队列、没有拒绝策略、没有监控、无法限流，出问题只能等宕机
可观测性 jstack 里全是 Thread-1234 这种默认名，出事后根本定位不到是哪个业务

正确做法是交给线程池（本文不展开线程池，但请记住这条铁律）。裸 new Thread() 唯一合理的场景是：这个线程生命周期与进程等长，且只有一个，比如某些守护型后台轮询线程。

二、Java 线程状态：别再画 RUNNING 了

这是流传最广的一个错误。很多资料画的图里有 RUNNING（运行中）状态，但 Java 的 Thread.State 枚举里根本没有它。

2.1 六种状态

stateDiagram-v2
    [*] --> NEW : new Thread()
    NEW --> RUNNABLE : start()
    RUNNABLE --> BLOCKED : 竞争 synchronized 锁失败
    BLOCKED --> RUNNABLE : 拿到锁
    RUNNABLE --> WAITING : wait() / join() / LockSupport.park()
    WAITING --> RUNNABLE : notify() / notifyAll() / unpark()

    RUNNABLE --> TERMINATED : run() 结束
    TERMINATED --> [*]

2.2 三个高频误解

误解一：RUNNABLE 不等于”正在运行”。

Java 把操作系统层面的 ready（就绪，在等 CPU）和 running（正在占用 CPU）合并成了同一个 RUNNABLE。所以你在 jstack 里看到 RUNNABLE，只能说明”这个线程没被阻塞、没在等待”，不能说明它在跑。

误解二：阻塞在 IO 上的线程，状态是 RUNNABLE。

这条最坑。线程卡在 SocketInputStream.socketRead0()（比如调用一个没有超时时间的 HTTP 接口，对端不返回），jstack 看到的是：

状态是 RUNNABLE，但线程实际已经卡死几分钟了。因为 JVM 不知道操作系统层面的网络 IO 阻塞，它认为线程还在执行。这也是为什么”加超时时间”在并发编程里是硬性要求——RUNNABLE 会骗过所有基于线程状态的监控。

误解三：BLOCKED 专指 synchronized。

只有等待进入 synchronized 保护的监视器时才叫 BLOCKED。用 ReentrantLock.lock() 抢锁失败的线程，状态是 WAITING/TIMED_WAITING（因为它底层走 LockSupport.park()），不是 BLOCKED。

这个区别在排查时非常有用：jstack 里看到大量 BLOCKED，说明热点在 synchronized；看到大量 WAITING 且栈顶是 LockSupport.park，说明卡在 JUC 的锁或队列上。

三、为什么 count++ 会丢数据：从字节码到 JMM

3.1 拆开看：count++ 是四步

javap -c Counter.class 反编译后：

一条 count++ = 读 → 改 → 写 三步（加上操作数栈操作是四条指令）。三步之间随时可能被操作系统挂起。

3.2 复现丢失

线程 A 和 B 同时执行 increment()，count 初值 0：

时刻 线程 A 线程 B 主内存 count
t1 读取 count = 0 0
t2 读取 count = 0 0
t3 计算 0+1 = 1 0
t4 计算 0+1 = 1 0
t5 写回 count = 1 1
t6 写回 count = 1 1

两次自增，结果只加了 1。 这就是开头矿卡在线数显示 78 的原因——80 次自增，丢了几条。

3.3 但”读改写”还不是全部原因

很多人到这里就停了，认为”加锁让三步变原子就好了”。实际上还有第二个层次的坑：就算只有一条 count = 1，别的线程也可能读不到。

这涉及 Java 内存模型（JMM）。

3.4 JMM：工作内存与主内存

JMM 的核心抽象：所有共享变量存在主内存，每个线程有自己的工作内存（对应 CPU 缓存 + 寄存器 + 写缓冲区的抽象）。线程对变量的所有操作都在工作内存里做，不能直接读写主内存。

3.5 happens-before：JMM 给你的”承诺”

JMM 不要求你去背内存屏障，它定义了一套 happens-before 规则：如果操作 A happens-before 操作 B，那么 A 的结果对 B 可见，且 A 的执行顺序排在 B 之前。

这是面试必问、工程必懂的八条：

规则 内容
程序次序规则 单线程内，前面的操作 happens-before 后面的操作
管程锁定规则 对同一把锁的 unlock happens-before 后续的 lock
volatile 变量规则 对 volatile 变量的写 happens-before 后续对这个变量的读
线程启动规则 Thread.start() happens-before 该线程的任何操作
线程终止规则 线程内的所有操作 happens-before 其他线程通过 join() 成功返回 / isAlive() 返回 false
线程中断规则 调用 interrupt() happens-before 被中断线程检测到中断事件
对象终结规则 对象构造完成 happens-before 它的 finalize()
传递性 A hb B，B hb C ⇒ A hb C

记住这条推论就够了：要让一个写操作对另一个线程可见，你必须在二者之间建立 happens-before 关系。手段只有三种——synchronized（管程锁定规则）、volatile（volatile 规则）、以及 JUC 里的各种锁/并发容器（内部依赖前两者 + CAS）。

没有任何 happens-before 关系的两个线程之间，看到什么值都是合法的。 这不是”可能出错”，是”规范允许它出错”。

四、volatile：只解决一半问题

4.1 volatile 的两条语义

给变量加 volatile，等价于获得两个保证：

语义 内容 解决什么
可见性 对 volatile 变量的写，立即刷新到主内存；读，一定从主内存重新加载 可见性问题
禁止重排序 通过插入内存屏障，禁止特定顺序的重排 有序性问题

HotSpot 在实现 volatile 写时，会在写操作后插入一条 lock addl $0x0,(%rsp) 指令（一个空的带 lock 前缀的加法），它的作用是：

  1. 把当前处理器的写缓冲区全部刷回主内存（相当于 StoreLoad 屏障）；
  2. 使其他处理器里该变量的缓存行失效。

内存屏障插入策略：

操作 插入的屏障
volatile 写 之前 StoreStore（禁止上面的普通写被重排到 volatile 写之后）
volatile 写 之后 StoreLoad
volatile 读 之后 LoadLoad + LoadStore（禁止下面的读写被重排到 volatile 读之前）

4.2 为什么 volatile 救不了 count++

因为 volatile 只保证可见性和有序性，完全不保证原子性。

加了 volatile 之后，t1 时刻线程 A 读到 0，t2 时刻线程 B 读到 0 —— 读到的都是”最新”的值，这没错。但重点在于：A 做 0+1=1 和写回之间，B 也做了 0+1=1 并写回。可见性保证了”读到的值是最新的”，却保证不了”读和写之间没人插队”。

一句话区分：

  • volatile 解决的是 “一个线程写，其他线程读” 的场景；
  • 原子性需要解决的是 “多个线程都写” 的场景。

5.2 锁到底存在哪：对象头 Mark Word

Java 对象在堆里的布局分三块：对象头 + 实例数据 + 对齐填充。锁信息就在对象头的 Mark Word 里。

64 位 HotSpot 的 Mark Word（非压缩状态）布局：

锁状态 56 bit 1 bit (biased_lock) 4 bit (age) 2 bit (lock)
无锁 unused:25 + hashCode:31 0 分代年龄 01
偏向锁 threadID:54 + epoch:2 1 分代年龄 01
轻量级锁 指向栈中锁记录 Lock Record 的指针:62 — — 00
重量级锁 指向 Monitor（监视器）的指针:62 — — 10
GC 标记 空 — — 11

锁标志位（最后 2 bit）的含义：01 = 无锁或偏向锁（靠 biased_lock 位区分）、00 = 轻量级锁、10 = 重量级锁、11 = GC 标记。

5.4 锁升级：JDK 1.6 之后 synchronized 不再慢的原因

早期（JDK 1.5 及以前）synchronized 直接映射到操作系统的互斥量（mutex），每次加锁都要从用户态切到内核态，成本极高，所以大家一窝蜂改用 ReentrantLock。

JDK 1.6 引入了 锁升级（锁膨胀），让 synchronized 能根据竞争激烈程度自动切换实现：

锁 实现 适用场景 开销
偏向锁 在无锁竞争时，把线程 ID 用 CAS 写进 Mark Word，之后该线程进出同步块连 CAS 都不用做，只比对 threadID 只有一个线程反复进入同步块 极低
轻量级锁 在栈帧里建 Lock Record，用 CAS 把 Mark Word 换成指向 Lock Record 的指针 多个线程交替执行，几乎不同时竞争 低（CAS + 自适应自旋）
重量级锁 膨胀为 ObjectMonitor，抢不到锁的线程挂起，进入 _EntryList 真正的高并发竞争 高（用户态↔内核态切换）

几个关键细节：

  • 锁只能升级，不能降级（偏向锁可以被撤销回无锁，但重量级锁在 HotSpot 里不会自发降级；JDK 有”锁降级”的争议实现，一般理解为在特定 GC 安全点才有）。
  • 自旋不是无限自旋，HotSpot 用自适应自旋（Adaptive Spinning）：根据上一次在同一个锁上自旋是否成功、以及锁持有者的状态，动态决定自旋次数。
  • 偏向锁在 JDK 15 被废弃（JEP 374），默认关闭，后续版本被移除。原因是现代程序（尤其是用了大量并发库和线程池的代码）里，锁几乎总会被多线程访问，偏向锁的”撤销”操作需要进入全局安全点（STW），收益已经小于成本。所以如果你在 JDK 15+ 上测锁升级，看不到偏向锁这一级。

5.5 synchronized 是可重入的

上面不会死锁。实现原理：Monitor 里有一个计数器 _count 和持有线程 _owner。同一线程再次进入时，_count++；退出时 _count--，减到 0 才真正释放。ReentrantLock 同理（名字里的 Reentrant 就是这意思）。

synchronized (str) 锁字符串常量 字符串常量池导致不同地方的代码锁到了同一个对象，莫名其妙互斥。用 private final Object lock = new Object()
锁 Integer 等包装类 Integer 有缓存（-128~127），且 i++ 会生成新对象，锁会变。绝不能锁包装类
锁粒度过大 把不相关的操作也包进同步块，吞吐量骤降
在同步块里做 IO / 远程调用 持锁时间不可控，轻则吞吐下降，重则死锁
锁对象被重新赋值 lock = new Object() 后，之前抢旧锁的线程不再互斥

六、wait / notify：为什么必须写在 while 里

6.1 标准范式

6.2 原因一：虚假唤醒（Spurious Wakeup）

在 POSIX 的 pthread_cond_wait 规范里，线程可能在没有收到任何 signal 的情况下被唤醒，这叫虚假唤醒。JVM 的 Object.wait() 建立在这套机制之上，同样不能保证”醒来 = 有人通知了”。

规范原话大意是：即使没有线程调用 notify，wait 也可能返回，因此必须在循环中重新检查条件。

如果用 if：线程被虚假唤醒后不检查条件，直接往下执行 —— 在队列为空的情况下执行 queue.poll()，拿到 null，后面 null.doSomething() 就是 NPE。

6.3 原因二：notify 之后条件可能又变了

就算不是虚假唤醒，也存在这个场景：生产者 notify() 唤醒了消费者 A，但 A 还没抢到锁，另一个消费者 B 先抢到锁把唯一的元素消费掉了。A 拿到锁时队列又空了。只有 while 能让 A 再检查一次并继续等。

6.4 为什么必须在 synchronized 里调用 wait

因为要防止信号丢失（Lost Wakeup）。

看这个不用同步的错误写法：

时序问题：消费者判断 queue.isEmpty() 为 true，在它调用 wait() 之前，生产者已经放了一个元素并调用了 notify()。此时 notify 没有任何等待者，信号直接丢失；然后消费者才去 wait()，永远等不到通知。

而 wait() 的设计是：它必须在持有锁时调用，并且会原子地”释放锁 + 进入等待队列”。因为生产者的 notify() 也必须在同一个锁的同步块里执行，所以”检查条件”和”进入等待”之间不可能插入生产者的 notify —— 信号丢失被根本杜绝。

这也是为什么 wait() / notify() 定义在 Object 而不是 Thread 上：它们操作的是对象的等待集合（wait set），而不是线程本身。

6.5 notify 还是 notifyAll

notify() notifyAll()
唤醒数量 1 个（JVM 选择，不可控） 全部
风险 可能唤醒”不该被唤醒”的同类型线程，导致真正该醒的线程继续等，程序卡死 无此风险，但有”惊群”开销
适用条件 ① 所有等待线程的等待条件完全相同；② 单次通知最多只需要一个线程继续执行 除上述情况外的所有情况

结论：拿不准就用 notifyAll()。 用 notify() 换来的那点性能收益，远抵不上排查偶发卡死的成本。

经典反例：一个队列既有生产者等”非满”、又有消费者等”非空”，用 notify() 可能唤醒的是同类型线程（比如唤醒了另一个生产者），真正需要醒的消费者继续睡眠，整个系统假死。

6.6 完整的生产者—消费者实现

提示：生产环境直接用 BlockingQueue（ArrayBlockingQueue / LinkedBlockingQueue），上面的逻辑 JDK 已经实现好了，且经过充分验证。手写这段的价值在于理解 wait/notify 的正确范式。

6.7 四个”让线程停一下”的方法对比

方法 所属类 释放锁？ 响应中断？ 唤醒条件 状态
Thread.sleep(ms) Thread ❌ 不释放 ✅ 抛 InterruptedException 并清除中断标志 时间到 / 被中断 TIMED_WAITING
Object.wait() Object ✅ 释放 ✅ notify / notifyAll / 超时 / 被中断 WAITING / TIMED_WAITING
Thread.join() Thread ✅ 释放（内部用 wait 实现） ✅ 目标线程终止 / 超时 WAITING / TIMED_WAITING
LockSupport.park() LockSupport ❌ 不释放 ✅ 但不抛异常，直接返回且保留中断标志 unpark / 被中断 / 虚假唤醒 WAITING

两个高频考点：

  1. sleep 不释放锁，wait 释放锁。 所以 synchronized 块里 sleep(1000)，其他线程在这个 1 秒内完全进不来。
  2. join() 其实释放锁。 它的源码就是 synchronized(this) { while (isAlive()) wait(0); }，等待的是 Thread 对象上的锁。线程终止时 JVM 会自动 notifyAll() 这个 Thread 对象。很多资料里”join 不释放锁”的说法是错的。

七、线程中断：一个被大多数人用错的机制

7.1 interrupt 不是”杀死线程”

Thread.stop() 在 JDK 1.2 就被废弃了（强行终止会导致锁被瞬间释放、对象状态不一致）。取而代之的 interrupt() 是协作式的：

它只是把目标线程的中断标志位置为 true，具体要不要停、什么时候停，由目标线程自己决定。

7.2 三种情况

线程当前状态 调用 interrupt() 的结果
正常运行 仅设置中断标志位 = true，线程毫不知情，继续跑。需要线程自己用 isInterrupted() 检查
阻塞在 sleep/wait/join 立即抛 InterruptedException，并且清除中断标志位（置回 false）
已经终止 完全无效（不会抛异常，标志位也可能被忽略）

7.3 为什么要”清除中断标志”

sleep() 抛 InterruptedException 时会把中断标志清掉，这个设计常被吐槽，但它有道理：异常本身就是中断信号的载体。既然你已经通过捕获异常知道了”有人想中断我”，标志位就没有保留的必要了——保留反而会导致下游代码重复响应同一个中断。

代价是：如果你选择”吞掉异常”，就必须自己把标志位恢复，否则上层完全感知不到中断发生过。

7.4 错误写法 vs 正确写法

一条铁律：捕获了 InterruptedException 却既不恢复中断标志、也不重新抛出、也不退出循环——这是一个 bug。

7.5 中断不了的情况

场景 能否被中断 替代方案
sleep / wait / join ✅ 抛 InterruptedException —
ReentrantLock.lock() ❌ 会一直等到拿到锁 lockInterruptibly()
synchronized 等待监视器锁 ❌ 完全无法中断 只能改成 Lock，或靠超时/重启
阻塞 IO（InputStream.read()） ❌ 不响应中断 用 NIO 的 InterruptibleChannel，close() 通道
普通循环（不检查标志位） ❌ 因为没人看标志位 循环条件里加 isInterrupted()

synchronized 等待锁时无法中断是很多人不知道的坑。如果发生了死锁，interrupt() 救不了你，只能靠避免死锁（见下节）或者重启。这也是 ReentrantLock 存在的一个理由——它提供了 lockInterruptibly() 和 tryLock(timeout)。

八、死锁：四个条件与真实排查

8.1 死锁的四个必要条件

四个条件同时成立才会死锁，破掉任意一个即可：

条件 含义 破坏方式
互斥 资源同一时刻只能被一个线程持有 难破坏（锁的本质）
占有且等待 持有一把锁的同时去申请另一把 一次性申请所有资源
不可抢占 已获得的锁不能被强行剥夺 tryLock(timeout) 主动释放
循环等待 形成 A 等 B、B 等 A 的环 按固定顺序加锁

工程上最有效的是破坏循环等待：给所有锁编号，任何地方都按编号升序申请。

8.2 一个真实的矿山场景死锁

两个方法加锁顺序相反，并发量上来必死锁。而且它是偶发的——只有两个线程刚好分别卡在两把锁上时才触发，测试环境几乎不可能复现。

8.3 怎么定位：jstack 会自动告诉你

JVM 会自动检测死锁并在 jstack 输出开头打印 Found one Java-level deadlock。定位步骤：

8.4 解决方案

其他策略：

  • 减小锁粒度：能不用嵌套锁就不用，把业务拆成单锁操作。
  • 无锁化：用 CAS / 原子类 / 不可变对象，从根本上消除锁。
  • 监控告警：在应用里加一个定时线程，检测锁等待超时的线程并告警。

九、ThreadLocal：方便但最容易泄漏

ThreadLocal 给每个线程一份独立变量副本，常用于存用户信息、链路追踪 ID、数据库连接。

9.1 与同步机制的本质区别

方案 思路 适用场景
synchronized 时间换空间：多线程排队访问同一份数据 线程间需要共享、通信
ThreadLocal 空间换时间：每个线程一份副本，互不干扰 变量需要贯穿调用链，但不需要跨线程共享

9.2 泄漏原理

ThreadLocal 的存储结构：

flowchart LR
    T["Thread"] --> TM["ThreadLocalMap
(线程私有)"]
    TM --> E["Entry[] table"]
    E --> E1["Entry
key: WeakReference<ThreadLocal>
value: 强引用 → 用户对象"]

关键：Entry 的 key 是弱引用，value 是强引用。

如果 ThreadLocal 对象本身被回收（key 变 null），但线程还活着（尤其是在线程池里，线程永远不会销毁），那么这条引用链依然存在：

key 已经是 null 了，你再也没有任何途径访问这个 value，但它又无法被回收——这就是内存泄漏。线程池里线程复用，泄漏会不断累积，最终 OOM。

9.3 正确用法

规则：ThreadLocal.set() 之后，必须在 finally 里 remove()。在 Web 容器里用 ThreadLocal 而不清理，是一个几乎必然会踩的坑——因为 Tomcat 的线程是复用的，下一个请求会读到上一个请求遗留的用户 ID（串号，比内存泄漏更可怕，属于严重的越权安全问题）。

ThreadLocal 的 set/get/remove 方法内部会调用 expungeStaleEntry 清理部分脏 Entry，但这只是”顺手清理”，不能替代主动 remove()。

十一、并发编程避坑清单

创建与销毁

  1. ❌ 生产环境禁止裸 new Thread()，一律用线程池
  2. ❌ 禁止在循环里创建线程
  3. ✅ 线程名要有业务含义，方便 jstack 定位
  4. ✅ 线程池用有界队列 + 明确的拒绝策略（默认 AbortPolicy 会抛异常，别用无界队列）

同步与锁
5. ❌ 不要用 synchronized(String) / 锁 Integer 等包装类
6. ❌ 不要在同步块里做 IO、RPC、加锁范围外的耗时操作
7. ✅ 锁对象用 private final Object，且不可变
8. ✅ 需要中断/超时的场景用 ReentrantLock 而不是 synchronized
9. ✅ 嵌套加锁必须保证全局顺序一致

可见性与原子性
10. ❌ 别指望 volatile 能保证复合操作的原子性
11. ✅ 一写多读的状态标志用 volatile
12. ✅ 计数用 AtomicInteger / LongAdder（高并发计数用 LongAdder，性能高一个量级）
13. ✅ 多变量原子更新用 AtomicReference 或干脆加锁

等待与通知
14. ❌ wait() 必须写在 while 里，不能用 if
15. ❌ 拿不准就用 notifyAll()，别图性能用 notify()
16. ✅ wait/notify 必须在 synchronized 块内
17. ✅ 优先用 BlockingQueue / CountDownLatch 等 JUC 工具，不要手写 wait/notify

中断与 ThreadLocal
18. ❌ 不要吞掉 InterruptedException
19. ✅ 捕获后要么恢复中断标志，要么重新抛出，要么退出
20. ❌ ThreadLocal 用完必须 remove()，尤其在线程池/Web 容器里

监控
21. ✅ 所有阻塞调用必须设置超时时间（HTTP、DB、锁）
22. ✅ 监控线程数、线程池队列长度，而不是只看 CPU

总结

回到开头那个”80 台矿卡显示 78 台”的问题。它暴露的不是”忘了加锁”，而是对并发三个核心问题缺乏认知：原子性（读改写被打断）、可见性（缓存不一致）、有序性（指令重排）。

这篇文章的核心结论：

  1. 线程是操作系统资源，new Thread() 很贵（默认 1MB 栈），必须池化。
  2. Java 只有 6 种线程状态，没有 RUNNING。而且阻塞在网络 IO 上的线程状态是 RUNNABLE——这个会骗过所有基于状态的监控，所以超时时间是硬性要求。
  3. count++ 丢数据是因为它在字节码层面是”读-改-写”三步，加 volatile 只能保证读到最新值，保证不了这三步不被打断。要原子性，得用 CAS 或锁。
  4. volatile 的真正价值在于禁止重排序——DCL 单例少了它，就会返回半初始化的对象。
  5. synchronized 锁的是对象，信息存在对象头 Mark Word 里，JDK 1.6 之后有无锁→偏向→轻量→重量的升级路径，低竞争下已经很快了（JDK 15 起偏向锁已废弃）。
  6. wait() 必须配 while：一是防虚假唤醒，二是 notify 之后条件可能又变了；而且必须在同步块里调用，否则会出现信号丢失。
  7. interrupt() 是协作式的，它只置标志位；synchronized 等锁时无法被中断——这一点很多人不知道。
  8. ThreadLocal 的 Entry 是弱引用 key + 强引用 value，线程池下不 remove() 必然泄漏，更严重的是会造成请求串号（越权）。

并发编程真正难的地方，从来不是 API 怎么用，而是在没有 happens-before 保证的地方，任何事情都可能发生。写并发代码时，先问自己一句：我这两个操作之间，happens-before 关系建立在哪？
