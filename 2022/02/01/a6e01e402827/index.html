LinkedList底层原理——双向链表的真实面貌

发布于 2022-02-01 分类：技术, 2022, Java基础 👁

前言

在智慧矿山调度系统里做过一个”任务优先级队列”：紧急调度任务插队头，普通任务排队尾。当时随手写了一版 Deque<DeviceTask> queue = new LinkedList<>()，压测时发现两个问题：

  1. 消费线程和生产线程直接共享这个队列，偶发丢任务、偶发 ConcurrentModificationException——因为 LinkedList 根本不是线程安全的；
  2. 撤销功能用 history.get(currentIndex) 实现，历史记录超过一万条后，每次撤销都要从链表头遍历一万次，接口从 1ms 涨到 40ms。

这两个问题把我原来”链表插入删除快，所以用 LinkedList”的认知彻底打碎了。后来认真读了一遍 JDK 源码，才明白它的真实成本在哪里。

这篇文章回答六个问题：

  1. 每个节点到底占多少内存，100 万元素的 LinkedList 和 ArrayList 差多少？
  2. “链表插入 O(1)”这句话哪里是对的、哪里是骗人的？
  3. node(index) 为什么要从两头遍历，这个优化省了多少？
  4. Queue/Deque 的两套方法（add/offer、remove/poll）到底差在哪？
  5. 为什么 JDK 有 Stack 类却没人用？
  6. 什么场景真的该用 LinkedList？（答案：几乎没有）

一、底层数据结构：三个字段撑起一切

注意：LinkedList 没有”容量”的概念，没有任何数组，也没有 modCount 之外的预分配空间——这是它和 ArrayList 最本质的区别。

1.1 Node：真正干活的类

flowchart LR
    F["first"] --> A
    subgraph A["Node A"]
        A1["prev = null"] --- A2["item = 任务A"] --- A3["next = B"]
    end
    subgraph B["Node B"]
        B1["prev = A"] --- B2["item = 任务B"] --- B3["next = C"]
    end
    subgraph C["Node C"]
        C1["prev = B"] --- C2["item = 任务C"] --- C3["next = null"]
    end
    A3 -.-> B
    B3 -.-> C
    B1 -.-> A
    C1 -.-> B
    C3 --> L["last"]

结构要点：

  • 双向链表，每个节点两个方向的指针，所以任意节点都可以向前也可以向后遍历；
  • first.prev = null、last.next = null，链表两端是明确的边界；
  • 不是循环链表（不像 LinkedHashMap 的内部链表那样可选成环）。

1.2 一个节点到底占多少内存

64 位 JVM 开启压缩指针（-XX:+UseCompressedOops，JDK 8+ 默认开启）：

组成 字节
对象头（Mark Word 8 + Klass Pointer 4） 12
item 引用 4
next 引用 4
prev 引用 4
对齐填充（8 字节对齐） 8
合计 32 字节

对比 ArrayList：每个元素只占引用数组的一个槽位，4 字节。

100 万元素的内存对比：

ArrayList LinkedList
元素存储 4 MB 32 MB
节点对象个数 1 个数组 100 万个 Node 对象
GC 压力 低（一个连续大对象） 高（100 万个小对象）

8 倍的内存差距 + 100 万个额外对象。这就是”LinkedList 更省内存（因为不用预分配）”这个直觉错误的地方——它省下的扩容空间，远抵不上每个节点的对象头开销。

用 JOL 可以自己验证：ClassLayout.parseInstance(new LinkedList.Node<>(null, "x", null)).instanceSize()

二、”插入 O(1)”这句话，一半是真的

2.1 头部插入 addFirst

四步：建节点 → 改 first → 改原头的 prev → 计数。确实是 O(1)，没有任何遍历。

一个细节：源码用 final Node<E> f = first 把引用拷贝到局部变量。这不是多余——JIT 会把局部变量的读取优化成寄存器访问，重复读字段则可能被去优化打断。HotSpot 源码里大量使用这个模式。

2.2 尾部插入 addLast

和 linkFirst 完全对称。这就是 add(e) 的实际实现（add 直接调 linkLast），所以”尾部追加”也是 O(1)。

2.3 中间插入：O(n) 定位 + O(1) 指针

linkBefore 本身只改两个指针，是 O(1)。真正的开销全在 node(index)：

两个要点：

  1. 二分方向：index < size/2 就从头走，否则从尾走。最坏情况走 size/2 步——这个优化把常数项砍半，但改变不了 O(n) 的量级。
  2. 这就是”链表插入快”的真相：插入动作本身 O(1)，但为了找到插入位置，平均要走 n/4 步（随机位置）。所以 add(index, e) 整体是 O(n)。

唯一例外：手里已经拿着 Node 引用的时候。 迭代器内部就持有当前节点，所以 ListIterator.add() 是真 O(1)——前提是用迭代器顺序遍历，而不是每次都 list.add(i, e)。

2.4 删除：同样卡在定位上

unlink 才是真正的删除，注意它做了完整的 GC 清理：

三个 = null 一个都不能少。 被删节点虽然脱离了链表，但它自己的 item/next/prev 字段还持有引用。如果不置 null，只要这个 Node 对象还被别处引用（比如迭代器的 lastRet），它指向的元素就回收不掉——和 ArrayList 的 elementData[--size] = null 是同一个道理，都是清除游离引用（loitering objects）。

2.5 remove(Object o)：null 特判的原因

LinkedList 允许 null 元素，所以必须先特判 null，否则 o.equals(...) 直接 NPE。这个写法在 JDK 的集合源码里很常见（HashMap.get 也是同样套路）。

注意：删除的只是第一个匹配的元素。LinkedList 没有”删所有匹配”的原生方法（要批量删用 removeIf 或 Iterator.remove）。

三、双重身份：List + Deque

LinkedList 同时实现 List 和 Deque，是 JDK 里少有的”多面手”。但也因此有两套语义不同的方法。

3.1 Queue 的两套方法

这是面试必考、实战必混的地方：

操作 抛异常版 返回特殊值版 语义
入队（尾） add(e) offer(e) 队列满时：add 抛 IllegalStateException，offer 返回 false
出队（头） remove() poll() 队列空时：remove 抛 NoSuchElementException，poll 返回 null
查看队头 element() peek() 队列空时：element 抛异常，peek 返回 null

实战建议：除非你明确希望”空了就报错”，否则一律用 poll/peek/offer——用返回值判断比捕获异常优雅得多，也更不容易在循环里失控。

对应的 Deque 双端版本：

操作 头部 尾部
插入 addFirst / offerFirst addLast / offerLast
移除 removeFirst / pollFirst removeLast / pollLast
查看 getFirst / peekFirst getLast / peekLast

3.2 当栈用：push/pop

push/pop 只是 addFirst/removeFirst 的别名，栈顶在链表头部。

为什么不用 java.util.Stack？

三个致命问题：

  1. 继承 Vector——所有方法 synchronized，单线程场景白白付出锁开销；
  2. 暴露了 List 接口——你可以在”栈”上调用 get(1)、remove(0)、insertElementAt，栈的 LIFO 语义形同虚设，破坏封装；
  3. 基于数组（Vector），pop 还会 trimToSize-类的操作，实现晦涩。

JDK 文档自己都说：应该用 Deque 代替 Stack。而 Deque 的实现里，优先选 ArrayDeque。

3.3 fail-fast 与 ArrayList 一模一样

LinkedList 同样继承 AbstractList 的 modCount，迭代器同样在 next() 里做 checkForComodification()。上一节 ArrayList 的所有结论（foreach 删除抛 CME、删倒数第二个元素不抛但结果错、fail-fast 是 best-effort）原封不动适用于 LinkedList。

四、性能真相：基准测试要看怎么测

4.1 理论复杂度

操作 ArrayList LinkedList
get(i) O(1) O(n)（最多走 n/2 步）
add(e) 尾部 均摊 O(1) O(1)
add(0, e) 头部 O(n)（全量后移） O(1)
add(i, e) 中间 O(n)（移动后半段） O(n)（遍历定位）
remove(i) O(n) O(n)
contains / indexOf O(n) O(n)
迭代器插入/删除 O(n)（还是全量移动） O(1)

4.2 但复杂度相等 ≠ 性能相等

上面表格里”中间插入两者都是 O(n)”，实测 ArrayList 通常更快。原因有二：

第一，常数项差一个数量级。

  • ArrayList 的 O(n) 是 System.arraycopy——JVM intrinsic，编译成 memmove，CPU 上移动连续内存每元素约 1~2 ns；
  • LinkedList 的 O(n) 是 n/4 次指针跳转，每次都可能 cache miss（约 100 ns），还要解引用两次（Node → item）。

平均下来 LinkedList 的常数项比 ArrayList 大 50~100 倍。

第二，LinkedList 还有分配和 GC 成本。 每次 add 都要 new Node（TLAB 分配，快，但仍有时空开销），节点是 32 字节的小对象，堆里产生大量垃圾。

4.3 量级参考（10 万元素，JDK 17，参考值）

操作 ArrayList LinkedList 结论
顺序追加 10 万 ~3 ms ~6 ms 差距不大
随机 get 10 万次 ~1 ms ~数分钟级 完全不可用
头部插入 10 万 ~2000 ms ~5 ms LinkedList 赢
中间随机插入 10 万 ~50 ms ~数百 ms ArrayList 反而赢

结论很清晰：LinkedList 唯一明确赢的场景是头部（或迭代器位置）高频插入/删除。其余所有场景，包括理论打平的中间插入，实际都是 ArrayList 更快。

但”头部高频插入”这个场景，ArrayDeque 同样 O(1) 且更快（连续内存 + 无节点分配），所以 LinkedList 的生存空间被两头挤压。

五、两个真实代码的坑（原文示例的问题）

5.1 坑一：把 LinkedList 当并发任务队列

LinkedList 没有任何同步。生产/消费并发时会发生：

  • size 计数错乱（size++ 不是原子操作）；
  • first/last 指针竞争，出现节点”丢失”或链表断裂；
  • 生产线程扩容时消费线程遍历，抛 ConcurrentModificationException。

另外别忘了队列要有界——无界队列在消费端卡死时会内存无限增长，这是比丢任务更严重的事故。

5.2 坑二：用 history.get(currentIndex) 做撤销

LinkedList.get(i) 内部就是 node(i)，每次都是从头或尾遍历。一万条历史记录，撤销一次要走约 5000 次指针跳转。

两条教训：

  1. 在 LinkedList 上调用 get(i)，几乎总是设计错误的信号；
  2. 就算真的需要频繁头部/中部操作，也先想想 ArrayDeque 或 LinkedHashMap（LRU 场景）。

六、什么时候真的该用 LinkedList

过一遍真实的场景清单：

场景 该用什么 为什么不是 LinkedList
通用 List ArrayList 上面所有分析
队列 FIFO ArrayDeque O(1) 且更快、更省内存
双端队列 ArrayDeque 同上
栈 ArrayDeque 同上，且比 Stack 类安全
任务队列（生产者-消费者） LinkedBlockingQueue / ArrayBlockingQueue 线程安全 + 有界 + 阻塞语义
延迟/定时任务 DelayQueue / ScheduledThreadPoolExecutor 自带排序和阻塞
优先级调度 PriorityQueue O(log n) 插入，按优先级出队
LRU 缓存 LinkedHashMap（accessOrder=true） 哈希定位 O(1) + 内部链表维护访问序
需要维护插入顺序的 Map LinkedHashMap 内部就是双向链表，但配合哈希定位

真正非 LinkedList 不可的场景，我至今没在生产代码里遇到过。 它的价值更多在于：是理解双向链表、Deque 接口、fail-fast 机制的最佳教材。

唯一勉强说得过去的场景：迭代过程中大量随机位置的插入/删除（持有迭代器游标，O(1) 操作）。但这类需求通常也意味着数据结构选错了。

七、避坑清单

内存与性能

  1. ❌ 不要在 LinkedList 上调用 get(i) / remove(i)（每次 O(n) 定位）
  2. ✅ 需要顺序处理就用迭代器，操作当前节点是 O(1)
  3. ❌ 别用 java.util.Stack，用 ArrayDeque
  4. ✅ 队列/栈/双端队列，默认选 ArrayDeque
  5. ✅ 元素量大时先算内存账：LinkedList 每节点 32 字节，ArrayList 每元素 4 字节

并发
6. ❌ LinkedList 不是线程安全的，禁止多线程共享裸实例
7. ✅ 生产者-消费者用 LinkedBlockingDeque（有界！）
8. ✅ 高吞吐无阻塞用 ConcurrentLinkedDeque
9. ✅ fail-fast 只是 best-effort，不能当并发保护

API 语义
10. ✅ 队列操作用 offer/poll/peek（返回特殊值），别用 add/remove/element（抛异常）
11. ✅ push/pop 是 addFirst/removeFirst 的别名，栈顶在头部
12. ✅ remove(Object) 只删第一个匹配的，且 null 元素要特判（LinkedList 允许 null）

正确性
13. ✅ unlink 会把 item/next/prev 全部置 null 帮助 GC——手写链表时别忘了这步
14. ✅ modCount 机制与 ArrayList 一致，foreach 里删除同样会炸

总结

回到开头那个任务队列事故。根因不是”LinkedList 慢”，而是把它用在了它完全不能胜任的地方：多线程共享（非线程安全）+ 随机访问撤销（get 是 O(n)）。

这篇文章的核心结论：

  1. 每个节点 32 字节，比 ArrayList 的 4 字节引用贵 8 倍，而且 100 万元素 = 100 万个 Node 对象，GC 压力完全不在一个量级。
  2. “插入 O(1)”只在两种情况下成立：头/尾插入（有 first/last 指针直达），或手里已持有节点引用（迭代器）。add(index, e) 要先 node(index) 走 n/4 步，整体是 O(n)。
  3. node(index) 从两头遍历（index < size>>1 决定方向），把最坏步数从 n 砍到 n/2——这是 LinkedList 源码里最值得学习的优化思路，但它救不了 O(n) 的量级。
  4. unlink 里的三个 = null 不能省，这是清理游离引用的标准动作，和 ArrayList 的 elementData[--size] = null 一脉相承。
  5. Queue 的两套方法：add/remove/element 抛异常，offer/poll/peek 返回特殊值。实战默认用后者。
  6. Stack 类是反面教材（继承 Vector，暴露 List 接口破坏 LIFO 语义），栈请用 ArrayDeque。
  7. 中间插入实测 ArrayList 反而更快——arraycopy 是 memmove，LinkedList 的指针跳转 cache miss 严重。LinkedList 唯一明确赢的是头部高频插删，而那个场景 ArrayDeque 又碾压它。

一句话概括：LinkedList 是一个教科书级的双向链表实现，但在生产代码里，它的每一个典型用途都有更好的替代品——List 用 ArrayList，队列/栈用 ArrayDeque，并发队列用 Blocking 系，LRU 用 LinkedHashMap。理解它，然后不选它。
