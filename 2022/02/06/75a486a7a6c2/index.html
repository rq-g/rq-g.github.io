HashSet与LinkedHashSet——去重与顺序的抉择

发布于 2022-02-06 分类：技术, 2022, Java基础 👁

前言

做过一个设备告警去重的需求：80 台矿卡每 5 秒上报一次状态，后台要统计”今天出现过告警的设备清单”，要求按首次告警顺序展示。

第一版用 HashSet，去重没问题，但测试反馈”列表顺序每次刷新都不一样”。当时我第一反应是”Set 不就是无序的，有什么问题？”——直到运营拿着两个不同顺序的截图来对峙，我才意识到：对用户来说，”顺序不稳定”和”数据错了”是同一种体验。

改成 LinkedHashSet 一行解决。但真正让我重新审视 Set 的是后来三个更深的问题：

  1. 为什么 LinkedHashSet 构造器里那句 super(16, .75f, true) 的 true，网上一大半资料都说成 accessOrder = true？
  2. 为什么只用 BigDecimal 做去重，HashSet 和 TreeSet 会给出不同数量的结果？
  3. 百万级 ID 去重，HashSet 每个元素都存全量对象——有没有省内存的方案？

这篇文章把 Set 三兄弟（HashSet / LinkedHashSet / TreeSet）+ 两个被忽略的选手（EnumSet、布隆过滤器）一次讲清。

一、HashSet：HashMap 的一个”壳”

1.1 底层就是 HashMap 的 key

Set 的”元素”就是 Map 的 key，value 一律塞 PRESENT。

PRESENT 设计得很省：它是一个 static final 的共享对象，不管 Set 里有多少元素，value 永远只有这一个实例，只占 16 字节对象头。如果每次 add 都 new 一个 Object，100 万元素就多 16MB。

add 返回 boolean 的语义：map.put 在 key 已存在时返回旧 value（非 null），所以 == null 就能判断”是不是新元素”。

1.2 去重的真实流程

三个关键点：

① 扰动函数。HashMap.hash() 不是直接用 hashCode()：

高 16 位与低 16 位异或——因为定位桶位只用 (n-1) & hash，当 n 是 16 时只有低 4 位参与运算，高 16 位的信息全被丢掉了。异或一次让高位也影响低位，减少哈希碰撞。

② 判断”重复”的条件是 hash 相等 && equals 为 true。两者缺一不可，这就是为什么只重写 equals 不重写 hashCode 会去重失败（见第三节）。

③ 链表长度 ≥ 8 且表长 ≥ 64 时链表转红黑树，把最坏查找从 O(n) 拉回 O(log n)。阈值 8 来自泊松分布——默认扰动下单桶超过 8 个元素的概率约千万分之一，出现这个情况通常说明 hashCode 写得有问题。

1.3 遍历顺序为什么”不稳定”

HashSet 的迭代器是 map.keySet().iterator()，遍历的是 HashMap 的桶数组：

遍历顺序取决于 hashCode 分布 + 桶数组容量 + 扩容历史，与插入顺序完全无关。而且一旦扩容（rehash 重新分布），顺序还会变——这就是”每次刷新顺序不一样”的根源。

顺带一个高频面试点：HashSet 遍历顺序不是随机的，而是确定的——同一批元素、同一个 JVM 启动实例，顺序是一致的（String 的 hashCode 是稳定算法）。跨 JVM 可能不同（hashCode() 里用了 identity hash 的对象），但 String/Integer 这些是稳定的。

LinkedHashSet 保的是插入顺序，不是访问顺序。 访问顺序是 LinkedHashMap 在 accessOrder=true 时的行为（LRU 缓存的实现基础），Set 家族用不到。

顺带一提：Collections.newSetFromMap(new LinkedHashMap<>(16, .75f, true)) 才能造出一个”访问顺序的 Set”——但几乎没人需要。

  • 查找/去重走桶数组：O(1)，和 HashSet 一样；
  • 遍历走双向链表：从 head 到 tail，天然是插入顺序；
  • 代价：每个节点多 2 个引用（8 字节），且插入时多一次链表维护。

afterNodeInsertion/afterNodeAccess 这些回调是 LinkedHashMap 挂进 HashMap.putVal 流程的钩子，让 HashMap 的代码完全不用感知子类的存在——这是模板方法模式在 JDK 里的教科书案例。

2.3 性能账

操作 HashSet LinkedHashSet 实际差距
add / remove / contains O(1) O(1) 可忽略（多几次指针赋值）
遍历 桶数组（有空洞，跳过 null 槽） 链表（无空洞，连续跳转） LinkedHashSet 遍历反而常常更快
内存/元素 ~32 字节 ~40 字节 多 8 字节（before/after）
迭代器一致性 fail-fast fail-fast 相同

一个反直觉的事实：当 Set 很大而桶数组很稀疏时，LinkedHashSet 遍历更快。因为 HashMap 遍历要扫过整个桶数组（包括 null 槽），而链表遍历只走有效节点。数据量到百万级时这个差距可以测出来。

三、equals 与 hashCode：去重的一切前提

3.1 只重写 equals 的经典事故

为什么 equals 根本没被调用？ 两个 new Device("D001") 没重写 hashCode，用的是 Object.hashCode()（identity hash），两个对象返回值几乎必然不同 → 分到不同桶 → add 时的比对循环里 node.hash == hash 先失败，短路掉后面的 equals。

这就是 hashCode 契约的第一条为什么是”equals 相等则 hashCode 必须相等”——它保证”可能相等的对象一定落在同一个桶里”，equals 才有机会被调用。

3.2 完整契约与正确写法

三个工程细节：

  1. equals 和 hashCode 必须用同一批字段。用 deviceId 做.equals，就用 deviceId 做.hashCode。字段不一致 = 契约 1 被破坏。
  2. Objects.hash(...) 是可变参数版，内部会装箱，热点路径建议手写：result = 31 * result + (field == null ? 0 : field.hashCode())。
  3. ** hashCode 缓存**：大量做 Set key 的不可变对象，可以缓存 hash 值（String 就是这么做的，hash 字段懒计算）。

这是我真实踩过的坑。BigDecimal("1.0") 和 BigDecimal("1.00")：

  • compareTo 返回 0（数值相等）
  • equals 返回 false（equals 连 scale 一起比）

四、TreeSet：排序去重的代价与收益

4.1 底层就是 TreeMap

  • 按 key 排序（自然顺序或 Comparator），O(log n)；
  • 不允许 null（比较时 NPE）；
  • key 相等 → 覆盖，与 TreeMap 完全一致；
  • TreeSet<BigDecimal> 就是上面 BigDecimal 事故的另一半。

选择 TreeSet 的唯一理由是”需要有序遍历或范围查询”（first()/last()/headSet()/subSet()）。只要去重，不要排序，用它就是白白付出 O(log n) 和更多内存。

4.2 三兄弟总对比

维度 HashSet LinkedHashSet TreeSet
底层 HashMap LinkedHashMap TreeMap（红黑树）
顺序 无 插入序 key 排序
add/contains O(1) O(1) O(log n)
null 元素 ✅ 1 个 ✅ 1 个 ❌
内存/元素 最低 +8 字节 最高（6 字段节点）
范围查询 ❌ ❌ ✅

实测参考（10 万元素去重，JDK 17）：

操作 HashSet LinkedHashSet TreeSet
全部插入 ~15 ms ~18 ms ~60 ms
contains × 100 万 ~8 ms ~10 ms ~180 ms
遍历 ~2 ms ~1.5 ms ~4 ms

结论：HashSet 和 LinkedHashSet 差距可忽略，TreeSet 慢一个量级。默认选前两个，只在需要排序时选 TreeSet。

五、两个被严重低估的选择

5.1 EnumSet：枚举去重的性能之王

如果元素是枚举，别用 HashSet——用 EnumSet：

HashSet EnumSet
contains 哈希 + equals 一次位运算
内存 每元素 32 字节 8 字节装下 64 个枚举
迭代 遍历桶数组 位扫描，天然有序
创建 new HashSet<>() EnumSet.noneOf(...)

Redis 客户端配置、设备能力位标记、告警类型集合——凡是枚举集合，EnumSet 都是零成本。超过 64 个枚举值会自动切换成 JumboEnumSet（long 数组），依然碾压 HashSet。

同理，EnumMap 之于 HashMap 也是如此。

5.2 大数据量去重：布隆过滤器

HashSet 去重的本质是全量存储——100 万个 32 字符的设备 ID，光字符串就 64MB，加桶数组开销更多。当数据量上去且能接受极小概率误判时，用布隆过滤器：

数据量 HashSet 内存 布隆过滤器（1% 误判率）
100 万 ~100 MB ~1.2 MB
1 亿 ~10 GB ~120 MB

关键语义：mightContain == false 时 100% 没见过，== true 时有 1% 是误判。所以它适合”宁可放过不可错杀“的场景：

  • ✅ 缓存穿透防护（挡掉 99% 的无效 key 查询）
  • ✅ 爬虫 URL 去重
  • ✅ 消息去重的第一道快速筛（可疑的再查 DB/Redis 精确判重）
  • ❌ 不能用于”精确去重后决定业务结果”（误判会漏数据）

分布式场景用 Redisson 的 RBloomFilter，底层是 Redis 位图，多实例共享。

另一个思路：如果需要精确去重 + 超大集合 + 允许近似基数统计，HyperLogLog（Redis 的 PFADD/PFCOUNT）用 12KB 估算任意大的基数，误差 0.81%——统计”今天有多少独立设备上线”这种需求比 Set 合适得多。

八、避坑清单

equals / hashCode 契约

  1. ❌ 只重写 equals 不重写 hashCode → 去重失效，且不会报错，只会悄悄多数据
  2. ✅ 两者必须用同一批字段计算
  3. ✅ 优先用 record（自动实现 + 不可变），其次 Lombok @EqualsAndHashCode
  4. ⚠️ BigDecimal 做 key：compareTo 忽略 scale、equals 包含 scale，两种 Set 结果不同
  5. ✅ key 用不可变对象；放进 Set 后修改参与 hash 的字段 = 元素”丢失”（还在集合里，但 contains 找不到）

顺序与性能
6. ✅ HashSet 遍历顺序稳定但无意义（取决于 hash 分布 + 扩容历史），不要依赖它做展示
7. ✅ 需要插入顺序 → LinkedHashSet，遍历性能常常还更好
8. ✅ 已知数量时预分配：new HashSet<>((int)(n / 0.75f) + 1)
9. ❌ TreeSet 慢一个量级，仅在需要排序/范围查询时使用

正确性
10. ❌ Set.of(...) 不允许 null 元素、不允许重复（重复直接抛 IllegalArgumentException）
11. ✅ 并发场景用 ConcurrentHashMap.newKeySet()，别用 Collections.synchronizedSet（迭代要手动锁）
12. ✅ 布隆过滤器的 mightContain == true 不代表一定存在，业务判断前必须二次精确校验

总结

回到开头那个设备告警清单——顺序不稳定的根源是 HashSet 遍历走桶数组，顺序由 hash 分布和扩容历史决定，与插入顺序无关。换成 LinkedHashSet，一条双向链表把插入序固定下来，问题消失。

这篇文章的核心结论：

  1. HashSet 是 HashMap 的壳：元素做 key，value 全指向共享的 PRESENT 哑对象。去重的本质是 hash 扰动 → 桶定位 → equals 确认，三步缺一不可。
  2. super(16, .75f, true) 的 true 是哑参数，用来区分构造器重载，与 accessOrder 无关。LinkedHashSet 保的是插入顺序，靠 LinkedHashMap.Entry 的 before/after 双向链表实现。
  3. 只重写 equals 不重写 hashCode，equals 根本不会被调用——不同的 identity hash 把对象分进了不同桶，比对在 node.hash == hash 就短路了。用 record 一劳永逸。
  4. BigDecimal 是 compareTo/equals 不一致的活标本：HashSet 认为 1.0 和 1.00 是两个元素，TreeSet 认为是一个。金额、评分类 key 务必先归一化或转最小单位整数。
  5. EnumSet 用一个 long 装下 64 个枚举，contains 是一次位运算——枚举去重的性能天花板，绝大多数人没用过。
  6. 数据量上去后 Set 去重是内存黑洞：百万级 100MB，亿级 10GB。布隆过滤器用 1% 误判率换 99% 内存，HyperLogLog 用 0.81% 误差做基数统计——先问自己”需不需要精确”，再决定用不用 Set。
  7. 性能账：HashSet ≈ LinkedHashSet，TreeSet 慢一个量级。默认 HashSet + 预分配容量，需要排序才升 TreeSet。

一句话概括：Set 的选择不是”哪个能去重”（都能），而是”除去重外你还要什么”——要顺序选 LinkedHashSet，要排序选 TreeSet，要省内存选 EnumSet/布隆过滤器，要并发选 CHM.newKeySet()。而无论选哪个，equals 和 hashCode 的契约是地基，地基错了全盘皆输。
