TreeMap底层原理——红黑树在Java中的应用

发布于 2022-02-10 分类：技术, 2022, Java基础 👁

前言

第一次用 TreeMap 是做一个矿卡驾驶时长排行榜：key 是驾驶时长，value 是司机信息，遍历出来天然有序。上线第三天运营发现榜上少了两个人——两个司机驾驶时长完全相同（精确到分钟），后写入的把先写入的覆盖了。

当时的第一反应是”数据有问题”，排查半天才发现是 TreeMap.put 的语义：key 相等不是”追加”，是”替换 value”。这个问题用 HashMap 一样会踩，但 HashMap 没有”排序”这个直观预期，反而更容易被测试发现。

这件事让我意识到：排序容器不是”能自动排序的 HashMap”，它有一整套自己的语义——比较器怎么定相等、范围查询返回的是不是副本、为什么 key 不能是 null、为什么插入和删除的平衡策略不一样。这篇文章把这些问题讲透：

  1. 红黑树的五条规则是怎么”证明”树不会退化成链表的？
  2. 插入后怎么修复平衡？三种 case 分别做什么？
  3. 为什么 JDK 选红黑树而不是更严格的 AVL 树？
  4. floor/ceiling/lower/higher 四兄弟到底差在哪？
  5. subMap 返回的是副本还是视图？改了会发生什么？
  6. 为什么 ConcurrentSkipListMap 用跳表而不是红黑树？

一、TreeMap 是什么：一棵带排序约束的红黑树

核心特点：

特性 说明 原因
按 key 有序 自然顺序或 Comparator 底层是搜索树，中序遍历即有序
不允许 null key put(null, v) 抛 NPE 排序需要比较，null 无法比较
允许 null value ✅ value 不参与比较
O(log n) 增删查 红黑树保证平衡
线程不安全 并发修改会数据错乱 + fail-fast 无同步机制
key 相等 → 覆盖 value 不是追加 所有 Map 的通用语义

1.1 “key 相等”是谁决定的

这是排行榜事故的根因。TreeMap 判断 key 是否相等，只看比较器的返回值是否为 0，与 equals() 完全无关：

这意味着一个容易踩的坑：compareTo 返回 0 但 equals 返回 false 的两个对象，在 TreeMap 里被视为同一个 key，但在 HashSet/HashMap 里是两个不同元素。

compareTo 与 equals 必须保持一致（Effective Java 第 14 条），否则同一个对象在排序容器和无序容器里行为不一致，排查起来非常痛苦。

1.2 Entry：六个字段

color 用 boolean 而不是枚举——true 表示红色，false 表示黑色，一个字节解决。

对比 HashMap 的树化节点 TreeNode（继承 LinkedHashMap.Entry，还要维护 before/after 双向链表），TreeMap 的 Entry 精简得多。

二、红黑树：五条规则换来的保证

红黑树是一棵自平衡二叉搜索树，通过五条着色规则约束平衡：

  1. 每个节点非红即黑；
  2. 根节点是黑色；
  3. 叶子节点（NIL，空节点）视为黑色；
  4. 红色节点的子节点必须是黑色（不允许两个红节点相连）；
  5. 从任一节点到其所有后代叶节点的路径上，黑色节点数量相同（黑高一致）。

2.1 这五条规则证明了什么

设黑高为 bh。由规则 4，最短路径全黑，长度 = bh；由规则 4 + 规则 5，最长路径黑红相间，长度 ≤ 2 × bh。

所以：最长路径 ≤ 2 × 最短路径。树不可能退化成链表，高度被约束在 2·log₂(n+1) 以内——这就是 O(log n) 的来源。

对比一下就明白这个约束有多宽松又多有效：

普通 BST AVL 树 红黑树
平衡约束 无 严格：左右子树高度差 ≤ 1 宽松：最长 ≤ 2 × 最短
期望高度 O(log n)，最坏 O(n) ~1.44 log n ~2 log n
查找 最坏 O(n) 最快 略慢于 AVL
插入修复 无 最多 O(log n) 次旋转 最多 2 次旋转 + O(log n) 次变色
删除修复 无 最多 O(log n) 次旋转 最多 3 次旋转
适用 — 读多写少 写多读少（增删频繁）

JDK 选红黑树的核心理由：删除修复的旋转次数有上界（最多 3 次）。 AVL 删除可能引发 O(log n) 次旋转，每根到根的路径都要重新平衡。对于”增删频繁”的通用容器，红黑树的总代价更低。

（顺带一提：HashMap 的链表长度达到 8 才转红黑树，阈值 8 来自泊松分布——默认扰动下链表长度超过 8 的概率约千万分之一，这个设计在 HashMap 那篇里详细讲过。）

2.2 旋转：修复平衡的唯一手段

左旋（rotateLeft）：节点 p 的右孩子 r 顶替 p 的位置：

flowchart TB
    subgraph B["左旋前"]
        P1["P(黑)"] --> L1["L"]
        P1 --> R1["R(红)"]
        R1 --> RL1["RL"]
        R1 --> RR1["RR"]
    end
    subgraph A["左旋后"]
        R2["R(黑)"] --> P2["P(红)"]
        R2 --> RR2["RR"]
        P2 --> L2["L"]
        P2 --> RL2["RL"]
    end
    B ---|"rotateLeft(P)"| A

右旋对称。旋转的要点：

  • 只改 3~4 个指针，O(1)；
  • 旋转会改变颜色（源码里 setColor）；
  • 旋转不改变中序遍历结果（二叉搜索树的有序性），所以修复平衡是安全的。

三、put 源码精读：定位 → 插入 → 修复

3.1 完整流程

两个容易被忽略的细节：

  1. compare(key, key) 的作用：第一个元素插入时做”自比较”，如果 key 没实现 Comparable，在这里就抛 ClassCastException，而不是等到第二个元素才炸——把错误暴露得更早。
  2. 新节点默认是红色：

字段声明是 boolean color = BLACK，但构造器不设置 color，而 fixAfterInsertion 第一行是 x.color = RED。为什么新节点必须是红色？因为插入红色节点不会破坏规则 5（黑高不变），只需要处理”父节点也是红色”的情况；插黑色则必然破坏规则 5，修复代价更大。

3.2 fixAfterInsertion：三种 case

新节点 x 是红色，唯一会违反的规则是规则 4（父节点也是红色）。按”叔叔节点”的颜色分三种情况：

Case 条件 动作 后续
1 叔叔是红色 父、叔变黑，祖父变红 问题上移两层，可能继续循环
2 叔叔是黑色，x 是内侧孩子 对父节点左旋 转化为 Case 3
3 叔叔是黑色，x 是外侧孩子 父变黑、祖父变红，对祖父右旋 结束

关键结论：插入修复最多旋转 2 次（Case 2 → Case 3），变色次数最多 O(log n)（Case 1 连环上溯）。这就是红黑树插入性能好的原因。

最后一行 root.color = BLACK 也不是可有可无：如果 Case 1 一直上溯到根，根会被染红，必须拨回来。

3.3 删除修复（简述）

删除比插入麻烦得多——删除红色节点不破坏任何规则，删除黑色节点必然破坏规则 5（黑高）。所以 JDK 源码里 deleteEntry 有一个前提判断：只有删的是黑节点（或替代上来的节点是黑）才需要 fixAfterDeletion。

删除修复引入”双重黑”（double black）概念，分四种 case 处理，最多旋转 3 次。这块展开会非常长，工程上需要掌握的是：

  • TreeMap 的 remove 是 O(log n)，不是 O(1)；
  • 删除的旋转次数有上界（≤ 3），这是它胜过 AVL 的地方；
  • remove(key) 返回的是被删节点的 value，不是 boolean。

3.4 get：就是二叉搜索树查找

注意 get 里对 key 做了 (Comparable<? super K>) key 强转——如果 key 没实现 Comparable，get 会直接抛 ClassCastException。所以 TreeMap 的 key 类型约束是”硬”的，不像 HashMap 只依赖 hashCode/equals。

四、NavigableMap：TreeMap 真正的价值所在

如果只用 put/get，TreeMap 相比 HashMap 的唯一收益是”遍历有序”。但它的杀手锏是一整套范围/邻近查询 API——这是 HashMap 完全做不到的（HashMap 要范围查询只能全量遍历过滤，O(n)）。

4.1 四个”邻近查询”

方法 语义 例子（key: 80, 85, 90）
floorEntry(k) ≤ k 的最大 key floorEntry(87) → 85
ceilingEntry(k) ≥ k 的最小 key ceilingEntry(87) → 90
lowerEntry(k) < k 的最大 key（严格小于） lowerEntry(85) → 80
higherEntry(k) > k 的最小 key（严格大于） higherEntry(85) → 90

记忆技巧：floor/ceiling 是”闭区间”（含等于），lower/higher 是”开区间”（严格）。四个都返回 Map.Entry，且都只做一次 O(log n) 的树查找。

还有一个不对称的：firstEntry()/lastEntry() 取最小/最大，pollFirstEntry()/pollLastEntry() 取出并删除。

4.4 遍历：entrySet 是中序遍历

TreeMap 的 entrySet().iterator() 内部用 successor()（后继节点）逐个跳转——这就是中序遍历，所以结果天然按 key 升序。

整个遍历是 O(n)：第一个元素 O(log n)（找最左节点），之后每次 successor() 均摊 O(1)（树的总边数有限，均摊分析后整棵树走一遍是 O(n)）。

这也意味着：TreeMap 遍历 = 排序后遍历，不需要先 keySet().stream().sorted()。用 HashMap 做同样的事要多花一次 O(n log n) 排序。

五、三个真实场景的正确实现

5.1 排行榜：同分覆盖是必踩的坑

修复思路一：key 用复合键，保证唯一

修复思路二：value 挂 List，同分聚合

方案一更好：取 Top N 时方案一可以直接 limit(n)，方案二还得在 List 内部再处理边界。

生产环境的真实答案是 Redis ZSet（跳表实现）——排行榜天然需要”分数可变”（驾驶时长一直在涨），而 TreeMap 修改 key 的分数意味着”删了再插”，每次 O(log n) × 2，且单机内存受限。这个话题在分布式篇再展开。

5.2 定时/延时任务：TreeMap 不该出现在这里

时间戳做 key 几乎必然碰撞——同一毫秒内提交两个任务太正常了。而且这个场景 JDK 早有专门的容器：

ScheduledThreadPoolExecutor 内部就是一个基于堆的延迟队列（DelayedWorkQueue），不是 TreeMap，也不是红黑树——堆对”只取最小值”这个操作更友好（O(1) 取顶，O(log n) 插入，且无序遍历需求为零）。

选型经验：如果你的场景只需要 firstEntry() + pollFirstEntry()，用堆（PriorityQueue）；需要完整的范围查询/邻近查询，才用 TreeMap。

5.3 时间区间查询：TreeMap 的正确打开方式

设备状态快照查询——“查某设备在 14:30 时的状态”，这是 TreeMap 少数真正不可替代的场景：

这个场景 floorEntry/ceilingEntry 一次 O(log n) 定位，是 HashMap 做不到的（HashMap 要先全量遍历再过滤，O(n)）。

evictBefore 里 headMap(...).clear() 是个漂亮的惯用法：对视图 clear 会传导到原 map，一行完成批量删除。

6.1 为什么并发版用跳表，不用红黑树

这是个很好的架构问题。红黑树在并发下有两个致命伤：

  1. 旋转是全局操作。插入/删除可能引发从叶到根的连锁旋转，锁粒度无法缩小到单个节点——要么全局锁（性能差），要么复杂度爆炸。
  2. 读操作需要一致性。红黑树的遍历依赖 left/right/parent 指针的瞬时一致性，无锁读很容易读到”旋转到一半”的树。

跳表没有这些问题：

  • 插入/删除只影响局部（一层层向下索引），可以用 CAS 做细粒度无锁更新；
  • 读操作天然无锁——遍历链表即使读到并发修改，最坏是漏读或多读，不会崩；
  • 实现上不需要 parent 指针，内存也省。

代价是常数项略高（期望 O(log n)，但每层都是链表遍历）。“允许弱一致性读 + 高并发写”的场景，跳表完胜红黑树。

这也是为什么 Redis 的 ZSet、LevelDB/RocksDB 的 MemTable、Java 的 ConcurrentSkipListMap 全都用跳表——并发有序结构的事实标准就是跳表。

七、避坑清单

排序语义

  1. ❌ compareTo 返回 0 ≠ equals 返回 true → TreeMap 里同分数据会”消失”
  2. ✅ key 用不可变对象（record / final 字段），compareTo 与 equals 保持一致
  3. ❌ 不要用时间戳、分数这类”天然可能重复”的值单独做 key
  4. ✅ 需要复合排序时用 record 实现复合 compareTo，或者 value 挂集合

key 可变性
5. ❌ put 之后修改 key 参与比较的字段 → 排序失效，get 找不到（树的落点已错）
6. ✅ key 用 record、String、包装类型等不可变对象
7. ✅ 必须修改时：先 remove 旧 key，改完再 put 回去

API 使用
8. ✅ 邻近查询记牢：floor/ceiling 闭区间，lower/higher 开区间
9. ✅ subMap/headMap/tailMap 返回视图，改视图 = 改原 map；要副本就包一层构造器
10. ✅ 视图 clear() 会删除原 map 对应区间——这也是批量清理的惯用法
11. ✅ remove(key) 返回被删的 value（可能为 null），不是 boolean

选型
12. ✅ 只需要”取最小/最大”→ 堆（PriorityQueue），不是 TreeMap
13. ✅ 定时任务 → ScheduledThreadPoolExecutor，不要自己用 TreeMap 做
14. ✅ 排行榜/实时分数 → Redis ZSet（跳表）
15. ✅ 并发环境需要排序 → ConcurrentSkipListMap，不是给 TreeMap 加锁

总结

回到开头那个排行榜事故——两个司机同分，后写的把先写的覆盖了。根因是我把 TreeMap 当成”会排序的 HashMap”，忽略了它的排序语义：key 是否相等由 compareTo 决定，与 equals 无关。

这篇文章的核心结论：

  1. 红黑树的五条规则换来一个可证明的保证：最长路径 ≤ 2 × 最短路径，所以高度 ≤ 2log n，增删查稳定 O(log n)。
  2. 新节点默认染红，因为插红只可能违反规则 4（修复代价小），插黑必然违反规则 5（黑高，修复代价大）。
  3. 插入修复最多旋转 2 次，删除修复最多 3 次——这个上界是 JDK 选红黑树而不是 AVL 的根本原因（AVL 删除可能 O(log n) 次旋转）。
  4. TreeMap 的杀手锏是 NavigableMap：floor/ceiling/lower/higher 四个邻近查询 + subMap 区间视图，是 HashMap 完全做不到的能力。排行榜、状态时间线回查这类场景，它是 JDK 里的唯一选择。
  5. subMap 等返回的是视图，改视图就是改原 map；想要副本要包一层构造器。视图的 clear() 会删除原 map 区间数据——这既是坑也是惯用法。
  6. key 相等由比较器决定，且 key 必须不可变——可变 key put 之后再改，树就”找不到”它了。
  7. 并发有序选跳表不选红黑树：旋转是全局操作锁不住，跳表可以用 CAS 做局部无锁更新。这也是 Redis ZSet、RocksDB MemTable 的共同选择。

一句话概括：TreeMap 不是 HashMap 的替代品，而是”范围查询”这个专用问题的专用解。用对场景（排序、邻近查询、时间线）它是神器，用错场景（通用 KV、排行榜、定时任务）就是给自己埋雷。
