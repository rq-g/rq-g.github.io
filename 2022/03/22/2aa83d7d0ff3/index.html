Optional正确用法——告别空指针异常

发布于 2022-03-22 分类：技术, 2022, Java基础 👁

前言

NullPointerException是Java开发者最常遇到的异常，没有之一。在实际项目前半年，80%的运行时异常都是空指针——矿工查询为空、设备关联位置缺失、预警处理人未分配。直到学会Optional，配合合理的判空逻辑，空指针异常才真正从日常开发中消失。

场景1：矿工查询为null：

  • Miner miner = service.getById(id);
  • miner.getName() → NPE!
  • 场景2：设备关联位置为null
  • device.getLocation().getName() → NPE!
  • 场景3：预警处理人为null
  • alert.getHandler().getPhone() → NPE!
  • 场景4：Map取值为null
  • map.get(“key”).toString() → NPE!
  • 场景5：自动拆箱为null
  • int count = getCount(); → NPE!
  • 解决方案：Optional + 工具类判空
  • 让”可能为空”在类型系统中显式表达

六、最佳实践总结

原则 说明
方法返回值用Optional 明确告知可能为空
类字段不用Optional 不支持序列化
方法参数不用Optional 增加调用复杂度
优先orElseGet 避免不必要的计算
不要isPresent+get 退化成null判断
链式调用用map 优雅处理多层判空
ofNullable优于of 防止null值NPE
结合工具类判空 覆盖所有空值场景

总结

Optional是实际项目中告别空指针异常的关键武器。核心认知：Optional不是用来替代所有null判断的，而是用在方法返回值和链式调用场景，让”可能为空”这一语义在类型系统中显式表达。配合工具类的判空方法，空指针异常从”日常常客”变成了”稀客”。关键是理解Optional的设计意图——它是返回值的包装器，不是null的替代品。

十二、判空编码规范

12.1 实际项目判空规范

1. Service单条查询返回Optional：

  • Optional findById(Long id)
    1. Controller层用Optional链式处理
  • service.findById(id)
  • .map(this::toVO)
  • .orElseThrow(…)
    1. DTO字段不用Optional
  • private String name; // 不是Optional
    1. 方法参数不用Optional
  • void update(String name) // 不是Optional
    1. 集合返回空集合而非null
  • return CollUtil.newArrayList(); // 不是null
    1. 前置校验快速失败
  • Objects.requireNonNull(param, “参数不能为空”)
    1. 链式调用用Optional.map
  • 不写if嵌套判空
    1. 默认值用orElseGet而非orElse
  • .orElseGet(() -> createDefault())
