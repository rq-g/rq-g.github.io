2. CAP理论

特性 说明
Consistency 一致性：所有节点数据一致
Availability 可用性：每个请求都能得到响应
Partition tolerance 分区容错性：网络分区时系统仍能工作

3. BASE理论

特性 说明
Basically Available 基本可用：允许降级响应
Soft state 软状态：状态允许短暂不一致
Eventually consistent 最终一致性：最终数据会一致

4. 分布式事务方案对比（面试必备）

方案 原理 优点 缺点 适用场景
XA 两阶段提交 强一致性 性能差、阻塞 数据库层面事务

维度 AT模式 TCC模式 SAGA模式

二、分布式ID生成方案

1. 分布式ID要求（面试必备）

要求 说明
全局唯一 多个服务生成的ID不能重复
趋势递增 ID随时间递增，有利于索引
高可用 ID生成服务不能宕机
高性能 ID生成速度要快
可反解 可以从ID中获取时间、业务信息

2. 常见方案对比

方案 优点 缺点 适用场景
数据库自增ID 简单、有序、易理解 单点瓶颈、无法水平扩展、性能低 小规模系统
UUID 分布式、无中心、无需协调 无序导致索引性能差、长度长、无业务含义 对顺序无要求的场景（如TraceId）
雪花算法 有序、高性能、分布式、可反解 依赖时钟、时钟回拨问题、需分配机器ID 大规模分布式系统
Redis INCR 高性能、有序、简单 依赖Redis、持久化风险、需考虑主从同步延迟 需要有序短ID的场景
数据库号段模式 高可用、有序、降低DB压力 实现复杂、号段用完时依赖DB、ID不连续 大规模分布式系统

3. 雪花算法原理

雪花算法ID结构（64位）

字段 位数 说明
符号位 1位 0表示正数
时间戳 41位 可表示约69年
机器ID 10位 可支持1024台机器
序列号 12位 每毫秒可生成4096个ID

4. 雪花算法实现（项目实战）

5. 时钟回拨解决方案

方案 说明 优缺点
抛出异常 检测到回拨直接抛出 简单，但会导致服务不可用
等待同步 等待时钟追上上次时间 可能造成性能抖动
引入NTP同步 使用NTP服务同步时间 依赖外部服务，无法完全避免回拨
保留历史时间 记录历史最大时间戳，回拨时沿用 兼容性好，但ID可能重复

面试官追问：

问：雪花算法的时间戳部分为什么是41位？能表示多少年？

答：41位二进制可以表示的最大值是2^41 - 1，约等于2.199万亿毫秒。换算成年就是2.199万亿 / (1000×60×60×24×365) ≈ 69.7年。所以只要选择一个合适的起始时间戳（epoch），就能保证69年内不会出现ID重复。我们项目中选择2022年1月1日作为起始时间，预计可以用到2091年。

问：如果机器ID分配冲突了怎么办？

答：机器ID分配冲突会导致ID重复，这是严重问题。解决方法：

  1. 配置中心分配：使用Nacos等配置中心统一分配机器ID，避免手动配置错误
  2. 基于IP生成：根据服务器IP计算机器ID，如IP的后10位
  3. 数据库存储：在数据库中记录已分配的机器ID，启动时检查

我们项目中使用配置中心分配，每个服务启动时从配置中心获取唯一的机器ID。

问：雪花算法和数据库号段模式怎么选？

答：

维度 雪花算法 号段模式
依赖 无（只需要机器ID） 依赖数据库
性能 极高（内存操作） 高（减少DB访问）
ID连续性 不连续 连续
时钟依赖 依赖系统时钟 不依赖
实现复杂度 低 高

雪花算法适合对性能要求极高、不依赖外部组件的场景；号段模式适合需要连续ID、对时钟不敏感的场景。我们项目中使用雪花算法，因为它性能高且无外部依赖。

6. 雪花算法踩坑记录

问题 现象 解决方法
时钟回拨 服务器时间回拨，导致ID重复 等待时间追上、使用历史时间、拒绝服务
workerId分配 多个服务使用相同workerId 使用配置中心（Nacos/Apollo）统一分配

三、分布式锁

1. 分布式锁要求（面试必备）

要求 说明
互斥性 同一时刻只能有一个客户端持有锁
可重入 同一客户端可以多次获取锁
锁超时 锁要能自动过期，防止死锁
高可用 锁服务不能宕机
公平性 按请求顺序获取锁（可选）

2. 实现方案对比

方案 优点 缺点 适用场景
Redis分布式锁 高性能、易实现 可能出现死锁、锁过期、非重入 高并发场景

数据库分布式锁 简单、无需额外组件 性能低、单点风险、无过期机制 小规模系统

3. 面试高频追问

问题 答案
分布式事务和本地事务的区别？ 分布式事务涉及多个数据服务，需要协调器（TM/RM/TC），本地事务只涉及单个数据库
Seata AT和TCC的区别？ AT自动回滚（基于undo log），无侵入；TCC手动实现try/confirm/cancel，性能更高但实现复杂
雪花算法时钟回拨怎么处理？ 等待时间追上、使用历史时间、拒绝服务，推荐等待时间追上
Redis分布式锁为什么不安全？ SETNX和EXPIRE不是原子操作，需要用Lua脚本；锁过期后业务可能继续执行
Redisson是如何实现可重入锁的？ 使用Hash存储线程ID和重入次数，unlock时减少次数，次数为0时删除锁
