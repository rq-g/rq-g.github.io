一、下单流程设计

1. 下单流程架构

步骤 操作 说明
用户请求 POST /api/order/create 提交商品列表、收货地址、优惠券

启动超时任务 - 延迟队列/定时任务，15分钟后检查订单状态
返回订单信息 - 返回订单ID、订单状态、支付链接

二、防止超卖方案

1. 超卖原因分析

时间点 请求A 请求B 库存
T0 - - 100
T1 检查库存=100，准备扣减50 检查库存=100，准备扣减60 100
T2 扣减库存，100-50=50 - 50
T3 - 扣减库存，50-60=-10 → 超卖 -10

根本原因：检查和扣减不是原子操作，并发下读到脏数据。

2. 解决方案对比

方案 原理 优点 缺点 适用场景
Redis Lua原子扣减 Lua脚本中判断+扣减原子执行 高性能、无锁竞争 Redis宕机风险 秒杀/高并发
数据库乐观锁 UPDATE stock SET stock=stock-qty WHERE stock>=qty 强一致、实现简单 并发高时大量失败 普通商品
分布式锁 加锁后检查扣减 保证数据一致性 性能较差 低并发强一致
数据库悲观锁 SELECT … FOR UPDATE 强一致 并发度低 后台管理

三、支付回调幂等性

1. 支付回调流程

步骤 操作 说明
支付平台回调 POST /api/payment/callback 可能重复调用（网络问题、重试机制）
幂等性校验 - 使用支付流水号作为唯一键、已处理过则直接返回成功
更新订单状态 - 订单状态从 PENDING → PAID
通知下游服务 - 库存扣减确认、积分增加、消息推送

2. 幂等性实现

3. 支付场景中的真实问题

问题 现象 解决方案
重复回调 支付平台多次回调 幂等性校验（Redis setIfAbsent）
回调与取消并发 订单已超时取消，但用户支付成功 支付回调检查订单状态，已取消则自动退款
回调丢失 支付平台未回调 主动轮询支付状态（定时任务补偿）
金额不一致 回调金额与订单金额不符 校验金额，不一致则记录异常并人工处理

5. 分库分表真实问题

问题 现象 解决方案
跨库JOIN 订单表和用户表不在同一个库 代码层组装 / 冗余字段 / 宽表
跨库分页 每个库取前N条，合并后排序不准确 禁止深分页 / 使用游标分页 / ES索引
分布式事务 订单和库存不在同一个库 最终一致性（本地消息表 + MQ）
扩容迁移 分片数不够需要扩容 一致性哈希 / 双写迁移
非分片键查询 只按user_id分库，按order_no查需全表扫描 建立索引表（order_no → user_id 映射）
全局ID生成 自增ID会冲突 雪花算法 / 号段模式

总结

电商核心业务场景题是面试中的重中之重，核心要点：

  1. 下单流程：参数校验 → 库存锁定 → 创建订单 → 超时任务，注意重复下单、价格篡改等真实问题
  2. 防止超卖：Redis Lua原子扣减 + 数据库乐观锁兜底 + 多级库存保护 + Redis/DB一致性对账
  3. 支付幂等：Redis去重 + 数据库唯一索引兜底 + 支付回调与订单取消并发处理
  4. 分库分表查询：根据查询维度选择合适的路由策略，非分片键查询需要索引表，跨库分页用游标方案
