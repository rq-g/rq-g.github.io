Maven 依赖调解：version 冲突的完整裁决规则

Maven 面试的分水岭在”依赖怎么冲突的、怎么裁决的”，只答”就近优先”不及格。完整规则按优先级排序：第一，DependencyManagement 优先——父 POM 或 import 的 BOM 里声明的版本压倒一切传递依赖，这是企业级项目锁版本的正统方式。第二，路径最短优先——A→B→C(1.0) 与 A→D→C(2.0)，B 路径短则 C 用 1.0。第三，路径等长时先声明优先——同为两跳，POM 中依赖声明顺序在前的赢。第四，同一 GAV 在同一 POM 重复声明时后者覆盖前者。理解裁决规则后，排查依赖冲突的完整动作是：mvn dependency:tree -Dincludes=组:artifact 定位冲突来源 → 在结果里看每个版本的引入路径 → 用 <exclusion> 掐掉错误路径或在 dependencyManagement 强制统一。两个高频翻车点必须讲：同名不同 groupId 的类冲突（如 commons-beanutils 的新旧版本分属不同坐标，tree 看不出来，靠运行期 NoSuchMethodError 和 classpath 顺序定位）；传递依赖的 scope 隔离（test/provided 不参与传递），很多人以为 exclusion 了运行期就干净，其实编译期行为和运行期 classpath 是两回事。依赖冲突是”本地好好的、测试环境报错”的头号原因，能把这条讲完整，Maven 题就过关了。

四、面试高频问题

1. Maven依赖冲突如何解决？

答案：

  1. 使用 mvn dependency:tree 查看依赖树
  2. 找到冲突的依赖版本
  3. 在pom.xml中使用 <exclusions> 排除不需要的版本
  4. 或者直接声明需要的版本

2. Git如何回退到之前的版本？

答案：

  • git reset --soft <commit-id>：保留修改，回退commit
  • git reset --hard <commit-id>：丢弃所有修改，完全回退
  • git revert <commit-id>：创建新的commit撤销指定commit

3. 如何查看Linux系统中某个端口被哪个进程占用？

答案：

  • netstat -tlnp | grep <port>
  • ss -tlnp | grep <port>
  • lsof -i :<port>

Git 团队协作：分支模型与高危操作红线

Git 面试考到团队协作层面，重点变成”分支模型怎么选、什么操作会毁灭仓库”。分支模型按团队规模选：小团队（<5人）用 GitHub Flow（main + feature 分支，PR 即门禁）最轻量；发布节奏固定的团队用 GitFlow（develop/release/hotfix 分层）或简化版——注意 GitFlow 的完整版在现代 CI/CD 下维护成本很高，多数团队实际用的是”main 长期稳定 + feature 短分支 + release tag”的简化模型。代码合入必须过 PR + 保护分支：禁止直接 push main，PR 强制至少一人 review 加 CI 通过，这是任何模型下都不该省的门禁。高危操作红线清单：git push --force（覆盖远端历史，团队协作下等于删除别人的提交，只能 --force-with-lease 且限于自己的分支）；对已推送的公共提交做 rebase（改写公共历史，其他人 pull 后一片混乱——规则是私有分支随便 rebase，公共分支只 merge）；git reset --hard 后想找回的提交（用 git reflog 抢救，reflog 是本地操作的最后后悔药）。rebase 与 merge 的选择：个人 feature 分支同步主干用 rebase（历史线性干净），合入主干用 merge 或 squash（保留合并语义）。能把”历史是否被改写”作为所有判断的核心，说明 Git 心智模型是完整的。

Linux 排查三板斧：从 CPU 飙高到定位代码行

Linux 部分面试最高频的实战题是”线上 CPU 100% 怎么排查”，它把一批零散命令串成了固定流水线，背熟这条线基本能覆盖 80% 的运维面试题。第一步，定位进程：top 看 CPU 占比最高的 Java 进程，拿到 PID。第二步，定位线程：top -Hp <pid> 看该进程内 CPU 最高的线程号（tid）。第三步，转换为十六进制：printf '%x' <tid>，因为 jstack 输出里线程 nid 是十六进制。第四步，抓栈定位：jstack <pid> | grep -A 30 <nid_hex>，找到该线程正在执行的代码行——如果是业务线程，看代码；如果是 GC 线程（名如 GC task thread），CPU 高的根因是频繁 GC，转向 jstat -gcutil <pid> 1000 看 GC 频率和回收效果。第五步，按根因分叉处理：死循环/热点代码用 arthas 的 profiler 或 thread -n 3 精准定位；GC 问题按内存分析路径走（jmap + MAT 看大对象）。类似的流水线还有内存排查线（jmap -histo 快速看对象分布 → jmap -dump + MAT 看引用链）和磁盘排查线（df -h 看容量 → du -sh /* 逐层找大目录 → lsof | grep deleted 找已删但被进程占用的文件——日志文件删了空间不释放的经典坑）。三条流水线 + 事故现场冷静的顺序感，就是运维面试要的全部东西。
