分库分表与海量数据面试题——Sharding-JDBC、分布式事务

发布于 2026-03-21 分类：技术, 2026, 分库分表, 面试题 👁

前言

分库分表是处理海量数据的核心技术，当单表数据量达到千万级时，就需要考虑分库分表。这篇文章结合分库分表核心原理、实际项目实战经验，深入分析Sharding-JDBC、分布式事务等核心问题。

分库分表架构

一、分库分表基础

1. 何时需要分库分表

指标 阈值 说明
单表数据量 千万级（1000万） 查询变慢、索引维护开销大
单库数据量 几十GB到几百GB+ 备份恢复时间长、性能下降
QPS 万级别10000+ 单库无法支撑
连接数 持续高位 数据库连接池耗尽

为什么”千万级”是分水岭？ 这个数字不是拍脑袋，它来自 B+ 树的结构约束：InnoDB 一个 16KB 页约能放 1000 个索引键（以 BIGINT 主键估算），三层 B+ 树约能索引 10 亿行，理论上千万级远未触顶。真正的问题在于二级索引的回表 IO——数据量越大，索引选择性下降、Buffer Pool 缓存的页占比越低，回表命中率从接近 100% 一路下滑，行数增长到某个量级后查询延迟出现非线性劣化。同时，千万级也意味着：DDL 变更从分钟级涨到小时级、binlog 备份恢复从分钟级涨到小时级、单实例写 QPS 接近硬件上限。所以”千万级”是运维成本、性能劣化和硬件容量三条曲线交汇的工程经验值，而不是硬性技术红线——如果查询模式简单（纯点查、纯追加写），两三千万也能稳住；反之复杂聚合查询在两千万就要动手。

2. 分库分表的痛点

痛点 说明
分布式事务 跨库事务难以保证ACID
跨分片查询 JOIN操作复杂
排序分页 全局排序分页困难
ID唯一性 需要分布式ID生成方案
运维复杂度 多库多表管理难度增加

面试加分点：被问”分库分表有什么代价”时，只答上面五条是及格线。更好的回答是把代价按”能不能避免”分类：分布式事务、跨分片查询、排序分页是结构性代价（只要分了片就存在，只能用架构手段缓解）；ID 唯一性是一次性代价（选好分布式 ID 方案就一劳永逸）；运维复杂度是持续性代价（扩容迁移、监控告警、问题排查全都翻倍）。再补一句”所以我们团队的原则是能不分就不分，优先用归档、读写分离、缓存把单表容量问题往后推两年”，能明显体现工程判断力。

二、Sharding-JDBC 分片策略

1. 分片策略类型

策略 说明 适用场景
精确分片 按固定值路由 按用户ID、地区等
范围分片 按范围路由 按时间、ID范围
哈希分片 按哈希值路由 均匀分布数据
复合分片 多个字段组合分片 复杂查询场景
自定义分片 自定义分片逻辑 特殊业务需求

2. 精确分片配置

源码级理解：PreciseShardingAlgorithm 只在 SQL 中分片键出现等值条件时被调用（WHERE user_id = 123），ShardingSphere 把值传给算法、拿回目标库表名完成路由。这意味着它天然不支持 LIKE、IN 跨值等场景——IN 条件走的是 ListShardingAlgorithm（每个值算一次路由后归并）。理解这个调用时机，就明白为什么”分片键必须出现在 WHERE 里”：不出现时 ShardingSphere 不知道数据在哪，只能全路由（广播到所有分片），性能和全表扫描等价。

3. 范围分片配置

范围分片的双刃剑：范围分片（尤其按时间）最大的好处是老数据天然冷热分离——查询带时间条件时只路由到对应月份的表，且历史分片可以整体归档甚至下线。但它的致命弱点是写热点：所有新写入永远落在最新分片，单表写入压力不因分片而减少，只是把历史数据挪走了。所以”按时间范围分片解决写入压力”是常见误区——它解决的是存储和查询范围问题，写入热点要靠哈希分片或两者组合（先按月范围分库、库内按 user_id 哈希分表）。

2. 跨分片查询解决方式

方案1：避免跨分片JOIN

为什么”应用层聚合”反而更快？ 直觉上 JOIN 一次查询比两次快，但在分片环境下恰好相反：数据库 JOIN 需要把两个分片的数据拉到同一节点做归并，网络传输和中间结果集的临时存储成本远高于两次精确路由查询。改造的关键在第二步的批量 IN 查询——把 N+1 次（每个订单查一次用户）压成 1 次，前提是控制好单批大小（MySQL 的 IN 列表建议不超过 1000 个值，超了分批）。这是面试里”分库分表后怎么优化 JOIN”的标准满分答案：能路由的先路由、JOIN 拆成两次批量查询、内存里聚合。

方案2：使用广播表

广播表（Broadcast Table）的适用边界要讲清楚：它适合小而稳定、读多写少的表——字典、配置、地区码。每次写入会同步到所有分片节点，所以大表广播等于把写放大 N 倍；而且多分片间的一致性靠 ShardingSphere 的同步保障，极端情况下可能短暂不一致。地区表这种千万行的”看起来像字典”的表不要广播，那是典型的滥用。

方案3：子查询优化

注意：子查询改写只在 users 表未分片（或按 city 分片）时有效——ShardingSphere 能把子查询结果作为路由依据的前提是子查询本身可以定位。如果两张表都是哈希分片且分片键不同，子查询同样退化为全路由，此时唯一出路是数据冗余（订单表冗余 user_city 字段）或引入异构索引（把”城市 → 用户ID”的映射同步到 ES）。

四、分库分表后的问题

1. 分布式事务问题

面试深挖点：为什么不直接用 XA？ @GlobalTransactional（Seata AT 模式）底层替代了传统 XA 的两阶段提交，核心差异在锁的粒度和持锁时长：XA 在 prepare 阶段就持有数据库级行锁直到 commit，跨库调用时锁持有时间是”最慢参与者”的耗时，高并发下连接池和行锁双双枯竭；Seata AT 用本地事务先提交 + undo log 补偿的方式，一阶段就释放本地锁，全局锁只在 Seata 服务端维护，冲突概率和持锁时长都小得多。代价是 AT 模式存在中间态可见性——本地已提交、全局未提交的数据对其他事务可见，需要 @GlobalLock 或业务隔离设计兜底。能把这层对比讲清楚，比背”XA 性能差”高两个档次。

2. ID唯一性问题

雪花 ID 的时钟回拨问题是必考追问：workerId 相同的两个节点同时生成 ID，或系统时钟回拨（NTP 校准、虚拟机迁移），会导致 ID 重复。应对方案按优先级：记录上次生成时间戳，发现回拨小于阈值（如 5ms）时自旋等待；回拨较大时报错拒绝服务并告警；或者改用号段模式（Leaf-segment）——从数据库批量取号段缓存在内存里，彻底摆脱时钟依赖。雪花 ID 趋势递增的特性对 InnoDB 是友好的（近似顺序写入减少页分裂），这也是它比 UUID 更适合做主键的本质原因。

3. 排序分页问题

深分页是分片环境的一号性能杀手，把账算清楚：全局取第 10000 页（LIMIT 99990, 10），ShardingSphere 要让每个分片返回前 100000 条，2 个分片就是 20 万条数据流经归并引擎——内存和 GC 都扛不住。游标分页（WHERE created_at < 上次位置）把每页成本变成常数，代价是只能顺序翻页、不能跳页，且排序字段必须含唯一后缀（同毫秒多条记录会丢数据，需加 id 作为 tie-breaker）。产品侧的正确姿势是说服前端用”下一页/无限滚动”替代”跳转到第 N 页”——这也是所有大厂深分页方案的共同结论。

Sharding-JDBC 的归并引擎：理解它才算入门

多数人把 Sharding-JDBC 当”透明代理”用，但它的核心组件是归并引擎（Merge Engine），理解归并才能解释一半以上的生产问题。归并分五类，代价天差地别：遍历归并（各分片顺序流出、聚合返回，成本最低）；排序归并（各分片数据按排序键归并，流式处理内存友好，但要求 SQL 带排序条件）；分组归并（GROUP BY 需要先把分片数据拉全再分组，数据量大时内存压力大）；聚合归并（比较型的 MAX/MIN 可流式，SUM/COUNT 必须拉全量再算）；分页归并（前文说的深分页灾难）。由此能推出几条实战军规：聚合查询尽量带分片键把范围压到单分片；GROUP BY 的维度尽量包含分片键；SELECT COUNT(*) 全分片统计是慢查询重灾区，替代方案是维护计数字段或走数仓。面试被问”Sharding-JDBC 的局限”，能按归并引擎的五类代价展开，比背”跨分片 JOIN 不支持”深一个层次——局限不是功能列表，是归并引擎的工作方式决定的。

五、分库分表实战案例

1. 订单表分库分表设计

订单表分库分表设计

分片策略：按user_id分库，按order_id分表

数据库 表
ds0 orders_0, orders_1, orders_2, orders_3
ds1 orders_0, orders_1, orders_2, orders_3

分片规则：

  • user_id % 2 = 0 → ds0
  • user_id % 2 = 1 → ds1
  • order_id % 4 → orders_0~3

为什么库和表用不同的分片键？ 这是这个设计的精髓。库用 user_id 是因为用户的绝大多数查询都带 user_id（查我的订单），带分片键的查询直接路由到单库，性能最优。表用 order_id 则是为了让单表容量上限翻倍——如果库表都用 user_id，单用户订单全落在一张表里，重度用户（代购、企业账号）会成为单表热点。双键组合的代价是”按 order_id 查详情”无法路由库（不知道在哪个库），需要基因法补救：把 user_id 的哈希基因（如低 2 位）嵌入 order_id 的生成过程，使 order_id 本身携带路由信息——这是面试的高频进阶题，能主动提出来是明显的加分项。

2. 配置示例

INLINE 算法的局限：行内表达式（ds${user_id % 2}）开发调试方便，但它是 Groovy 脚本解析，每次路由都有解析开销，且逻辑无法做条件分支。生产环境当分片逻辑涉及任何判断（比如灰度期间新旧规则并存）时，要换成 CLASS_BASED 类型指向自定义算法类——配置里换算法名、代码里控逻辑，才能支撑平滑扩容。

读写分离与分库分表的组合拳

生产架构里两者几乎总是组合出现，但组合次序和坑位有讲究。标准分层是”读写分离打底、分库分表按需叠加”：先让写主从、读从库，解决读扩展；读扩展到顶（跨库聚合的从库查询过于复杂）或写成为瓶颈时，再在写侧引入分片。叠加后的路由顺序要清楚：ShardingSphere 先做分片路由（决定到哪个库），再做主从路由（该库内选主还是从）——这意味着写操作永远落主库、同一会话内的强一致读也应该强制走主库（HintManager 或 MASTER 路由注解），否则”刚写入就读不到”的经典问题在分片环境会更隐蔽。另一个高频坑是复制延迟放大：分片前的从库延迟是单库的，分片后写入被打散到多个主库，每个主库的从库都在延迟，应用侧任何一个”写后读”都可能在多个从库上撞到不同的旧数据版本。所以分片架构里”主从延迟监控”必须按分片粒度建，读多写少的分片和写密集分片要分别对待——读写分离和分库分表不是两个独立功能，而是一条数据通路上的两级路由，分开设计必踩坑。

六、分库分表最佳实践

1. 分片键选择原则

原则 说明
查询频率 选择高频查询字段作为分片键
数据均匀 分片键值分布要均匀
业务场景 结合业务查询模式选择
避免热点 避免某个分片数据过多

一条原则压倒其他所有原则：分片键一旦选定，运行期不可更换。改分片键等于全量数据重分布，等于停机迁移。所以选分片键的思考顺序是：先枚举系统未来三年可能的查询维度，确认”最重要的那个维度”不会变；再验证该字段的基数和分布（拿生产数据抽样统计，而不是拍脑袋）；最后用”基因法/冗余字段”覆盖次高频查询维度。把”分片键不可变”讲在前面，能直接体现候选人有分库分表的真实落地经验——这是吃过亏才知道的约束。

2. 扩容策略

表扩容到4分片

阶段 分片规则
原分片 user_id % 2 → ds0/ds1
新分片 user_id % 4 → ds0/ds1/ds2/ds3

数据迁移：

  1. ds0 → ds0（user_id % 4 = 0）
  2. ds1 → ds1（user_id % 4 = 1）
  3. ds0 → ds2（user_id % 4 = 2）
  4. ds1 → ds3（user_id % 4 = 3）

注意事项：

  • 选择低峰期迁移
  • 双写阶段（同时写入新旧分片）
  • 验证数据一致性

双写迁移的完整时序比”注意事项”四个字复杂得多，面试能展开讲就是实战派：第一阶段只读旧分片，部署新分片集群；第二阶段开双写（旧库为主、新库为辅，写失败只记日志不报错），同时用 binlog 同步工具把存量数据搬到新分片；第三阶段数据追平后做全量校验（行数 + 抽样字段比对 + 关键业务对账）；第四阶段灰度切读（先切内部账号、再切 1%、10%、50%、100%）；第五阶段确认无回滚需求后停旧写、下线旧库。每一步都有回退预案，整个周期通常按月计——“分库分表容易，扩容迁移难”就是这个意思，也是**建议初期分片数一步到位（如预留 4 倍容量）**的根本原因：能让未来的自己不做迁移，就是最大的架构收益。

总结

分库分表是处理海量数据的核心技术，掌握这些知识不仅能应对面试，还能设计出高性能的数据库架构。核心要点：

  1. 分片策略：精确分片、范围分片、哈希分片的选择——先想清楚查询维度再定分片键，它不可更换
  2. 跨分片查询：避免JOIN、使用广播表、子查询优化——本质都是”把广播变成路由”
  3. 分布式事务：使用Seata等框架保证一致性——理解AT模式与XA的锁粒度差异
  4. ID唯一性：使用雪花算法生成分布式ID——必须能答出时钟回拨的应对
  5. 排序分页：使用分片键限制范围、游标分页——深分页是分片环境的一号杀手

这些都是面试中高频问到的问题，一定要深入理解并能说出落地实现。最后送给读者一句话：分库分表不是性能优化的起点，而是其他手段（索引、缓存、归档、读写分离）穷尽之后的终点——面试官问”什么时候分库分表”，最想听到的答案是”能不分就不分”之后的”什么时候必须分”。
