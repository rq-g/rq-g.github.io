TCP与HTTPS网络深度解析——从三次握手到epoll与零拷贝

发布于 2026-03-10 分类：技术, 2026, 网络 👁

这是 Netty 系列的前置篇。要真正理解 Netty 的 Reactor 模型、零拷贝和长连接治理，必须先把 TCP 和操作系统的 IO 模型吃透。全文以矿卡调度系统的 WebSocket 长连接链路为案例贯穿。

一、TCP 连接的生老病死

1.1 三次握手：不只是”确认能收到”

教科书说三次握手是”确认双方收发能力”，这个答案面试只能拿 60 分。真正要回答的是为什么两次不行、四次没必要：

  • 两次不行：服务端收到 SYN 并回复 SYN+ACK 后就认为连接建立，但这个 ACK 如果在网络中丢失，服务端会一直维护一个”单方面认为存在”的连接，白白占用资源（历史 SYN 请求过期后到达，两次握手会创建大量无效连接）；
  • 三次本质：双方各自确认”我的发送和接收能力都正常，且对方的序列号我已同步”。第三次 ACK 携带客户端的初始序列号确认，缺了它服务端无法确认客户端收到了自己的序列号。

面试加分点——SYN Flood 攻击与半连接队列：三次握手中服务端收到 SYN 后分配半连接（SYN_RCVD 状态），攻击者伪造海量 SYN 不回 ACK，半连接队列被打满导致正常用户无法建连。Linux 的防御手段：tcp_syncookies=1（不存状态，用加密 Cookie 验证合法后再建连接）、减小 tcp_synack_retries、增大 backlog。

1.2 四次挥手与 TIME_WAIT

四次挥手比握手难记，关键是理解为什么比握手多一次：TCP 是全双工，两个方向的数据通道要各自独立关闭。被动关闭方收到 FIN 后可能还有数据没发完，所以 ACK 和它自己的 FIN 分开发（中间可能有数据传输），这就是多出来的一次。

真正在生产里反复折磨人的是 TIME_WAIT：主动关闭方在发出最后一个 ACK 后进入 TIME_WAIT，停留 2MSL（Linux 上 60 秒）。两个原因：确保最后的 ACK 若丢失，对方重发的 FIN 还能被响应；让本连接的旧报文在网络中自然消亡，避免污染复用的新连接。

问题场景：矿卡网关与数百台车载终端建长连接，每次重启网关（主动关闭方是网关）就会产生上万 TIME_WAIT，端口耗尽报 Cannot assign requested address。治理手段按优先级：

更根本的方案是应用层治理：长连接由客户端主动断开重连（把 TIME_WAIT 留在终端侧），或使用连接池复用。tcp_tw_recycle 这个参数网上老文章还在推荐，但它对 NAT 环境是灾难性的（丢弃时间戳回退的连接），4.12 内核已删除，新文章再推荐就是照抄不消化。

1.3 滑动窗口与拥塞控制：吞吐的两大开关

滑动窗口解决”流量控制“（别把接收方撑死），拥塞控制解决”网络过载“（别把网络挤死），两者机制独立、相互配合：

机制 目标 核心动作
滑动窗口 对端接收能力 接收方通过窗口字段通告可用缓冲，发送方未确认数据不超过窗口
慢启动 探测网络容量 cwnd 从小值指数增长，直到 ssthresh
拥塞避免 稳态线性增长 cwnd 超过 ssthresh 后每 RTT 加 1
快重传/快恢复 丢包后快速恢复 3 个重复 ACK 触发重传，cwnd 减半而非回到初始

对应用层的实际影响：带宽延迟积（BDP）决定吞吐上限。跨地域专线 RTT 40ms、带宽 1Gbps，理论最大在途数据约 5MB，但 Linux 默认 tcp_rmem/tcp_wmem 上限常常只有几百 KB——大文件传输慢，第一反应不该是加带宽，而是查窗口参数和 BBP 是否匹配。

长连接场景还有一条容易被忽略：Nagle 算法与延迟确认的叠加。Nagle 攒小包（等 ACK 或攒满 MSS 才发），接收端延迟确认（最多 40ms 才 ACK），两者叠加最高引入 40ms+ 的发送延迟。交互式协议（WebSocket 推送、游戏）要在 socket 上显式关闭 Nagle：TCP_NODELAY=true。Netty 里对应 .childOption(ChannelOption.TCP_NODELAY, true)——这行代码缺失是”消息推送莫名延迟 40ms”的最常见根因。

二、HTTPS：一次握手到底发生了什么

2.1 TLS 1.2 握手全流程

以 RSA 握手为例（注意这是 TLS 1.2 的方式）：

sequenceDiagram
    participant C as 客户端
    participant S as 服务端
    C->>S: 1. ClientHello（随机数C、支持的密码套件）
    S->>C: 2. ServerHello（随机数S、选定套件）+ 证书
    C->>C: 3. 验证证书链（签发者/有效期/域名/吊销状态）
    C->>S: 4. ClientKeyExchange（预主密钥，用服务器公钥加密）
    C->>S: 5. ChangeCipherSpec + Finished
    S->>C: 6. ChangeCipherSpec + Finished
    Note over C,S: 双方用 随机数C+随机数S+预主密钥 派生会话密钥
后续全部对称加密

两个必考的理解点：

  • 为什么非对称加密只用于握手：RSA/ECDHE 性能比 AES 差两个数量级，只用来交换”生成对称密钥的原料”，之后全走对称加密（AES-GCM/ChaCha20）；
  • 证书验证验证了什么：不是验证”加密”，而是验证”身份”——确认公钥真的属于对方域名，防中间人用自己的公钥替换。验证链逐级追溯到内置的根 CA，任何一环过期/域名不匹配/被吊销都握手失败。

2.2 TLS 1.3 的演进：一次往返完成握手

TLS 1.2 握手需要 2-RTT，TLS 1.3 砍到 1-RTT，核心变化是把密钥交换固定为 ECDHE（前向安全：私钥即使泄露，历史流量也无法解密），客户端在 ClientHello 里直接带上密钥分享参数，服务端一个往返就能确认会话密钥。外加 0-RTT 恢复：复用之前的会话时，客户端可以在第一个飞行包里就带上业务数据——代价是 0-RTT 数据没有防重放保护，只允许用于幂等请求。

对 Java 工程的实际意义：网关开启 TLS 1.3 后，移动端弱网下建连延迟可观测地下降（2-RTT→1-RTT 少一个往返，RTT 100ms 时省 100ms+）。JDK 8u261+ 才支持 TLS 1.3，升级 JDK 对安全性能也是直接收益。

2.3 会话复用：生产必须开启

每次完整 TLS 握手 = 1~2 RTT + 非对称运算（ECDHE 每次约几毫秒 CPU），QPS 上千时这是实打实的 CPU 大头。两种复用机制：

机制 原理 特点
Session ID 服务端缓存会话状态，客户端凭 ID 恢复 服务端有状态，集群需共享或会话粘滞
Session Ticket 服务端把加密的会话状态发给客户端保存 服务端无状态，多节点集群友好

结论：集群网关一律用 Session Ticket（配合 ticket 密钥轮换）。Nginx 对应 ssl_session_cache shared:SSL:50m; ssl_session_timeout 1d;。

三、IO 多路复用：从 BIO 到 epoll

3.1 三种模型的真实差异

这是理解 Netty 的地基，用”餐厅服务”类比一次讲透：

  • BIO（阻塞）：一个服务员盯一桌客人，客人不点菜服务员就干站着。1000 个连接要 1000 个线程，线程内存栈 + 上下文切换直接把系统拖垮。矿山项目早期 WebSocket 用 BIO，单机撑到 2000 连接 GC 就开始异常；
  • NIO（非阻塞 + 轮询）：服务员不干等，挨桌问”要点菜吗”（Selector.select() 轮询所有连接），一晚问一圈浪费在无效轮询上，连接数越大浪费越大；
  • epoll（事件驱动）：前台拿一个”呼叫器”（epoll 实例），任何一桌客人有动静，呼叫器响，服务员只去被叫到的桌。连接数大小不再影响服务能力，只与”活跃连接数”相关。

3.2 select/poll/epoll 对比

维度 select poll epoll
fd 数量上限 1024（fd_set 位图） 无硬限制 无硬限制
fd 传递 每次调用全量拷贝进内核 同左 注册一次（epoll_ctl），事件就绪回填
就绪检测 内核线性扫描全部 fd 同左 回调机制，只返回就绪 fd
复杂度 O(n) O(n) O(1)（活跃连接数相关）
触发模式 LT LT LT / ET

epoll 的三个系统调用各司其职：epoll_create 创建实例、epoll_ctl 注册/修改关注的事件、epoll_wait 等待事件（返回的就绪列表由内核回调填充）。ET（边缘触发）vs LT（水平触发） 是高级考点：LT 下只要缓冲区还有数据，epoll_wait 每次都返回（编程简单，可能重复唤醒）；ET 只在状态变化时报一次（必须一次把数据读到 EAGAIN，编程复杂但少唤醒）。Netty 默认 LT（EpollSocketChannel 封装了循环读），Java NIO 的 Selector 在 Linux 底层就是 epoll 的 LT 模式。

单 Reactor 多线程有个隐蔽的坑：业务线程池处理完要写回结果时，必须把写操作交还 IO 线程执行（或加锁），否则多个业务线程并发写同一个 Channel 就是数据错乱。Netty 的 channel.writeAndFlush 从任意线程调用都安全，本质是它内部把写任务投递回 EventLoop 队列——这个细节就是”主从 Reactor”设计的价值。

四、零拷贝：四个层次逐一拆解

“零拷贝”不是没有拷贝，而是消除 CPU 参与的多余拷贝。以”从磁盘读文件经网卡发出”为例，按层次演进：

Java 世界的对应物：

技术 底层 典型用途
FileChannel.transferTo() sendfile 文件服务器、日志传输
MappedByteBuffer（mmap） 内存映射 RocketMQ CommitLog、Kafka 索引
DirectByteBuffer 堆外内存 Netty 的 PooledDirectByteBuf
Kafka 的 FileRecords sendfile 消费者批量拉取消息

Netty 的”零拷贝”另有含义（面试常混淆）：Netty 层面的零拷贝主要是 JVM 堆内的操作优化——CompositeByteBuf 合并多个 Buffer 免内存拷贝、Unpooled.wrappedBuffer 包装已有数组、slice()/duplicate() 共享底层数据。它和 OS 层的 sendfile 零拷贝是两个层面，答案里要分清。

堆外内存的直接收益：socket 读写如果用堆内存，JVM 要先把堆数据拷贝到临时直接缓冲再交给内核（GC 可能移动堆对象，内核不能持有堆地址）；直接用堆外内存省掉这一拷贝，且不受 GC 停顿影响。代价是分配/释放更贵、需要小心内存泄漏——这就是 Netty 池化（PooledByteBufAllocator）存在的理由。

五、长连接治理：从 TCP 参数到应用层心跳

长连接链路（矿卡网关 ↔ 车载终端）生产问题清单，每一条都对应 TCP 或应用层的知识点：

1. 连接”假活”。网线拔了/设备进隧道信号丢失，TCP 层毫无感知（没有任何包交互，连接永远”正常”）。内核的 keepalive 默认 2 小时才探测，完全不可用。方案是应用层心跳：客户端 30s 一次 PING，服务端 90s 无任何包判定死亡并关闭。心跳间隔的权衡：太小浪费流量（车载 4G 流量是成本），太大故障感知慢，一般取”容忍断线时长 ÷ 2”。

2. 半打开连接（Half-Open）。一方崩溃重启后，对端还持有旧连接继续发数据，收到 RST 才知道。服务端必须有连接状态机：收到未知连接 ID 的包就下发”重连指令”，而不是默默丢弃。

3. 优雅关闭。close() 直接发 FIN（可能丢在途数据），shutdown(SHUT_WR) 先关写方向、读尽对端数据再关，才是完整关闭。Netty 对应 channel.close() 前先 flush 并等待 ChannelFuture 完成；停机时配合 shutdownGracefully() 排空 EventLoop 任务。

4. 惊群与连接风暴。网关集群重启瞬间，数千终端同时重连（比 NMS 波峰更猛）。服务端除了等待退避，还要在重连响应里下发随机退避窗口（如 0~30s 抖动），把重连洪峰摊平——这就是为什么标准的 MQTT 重连规范里带 jitter 的原因。

六、弱网与无线环境：矿区网络的特殊课题

矿卡调度的网络不是办公室光纤——露天矿区 4G/5G 专网覆盖不均、运输车辆在采坑背坡面频繁进出信号盲区、多普勒与穿透损耗叠加，丢包率日常 2%~5%（有线网 <0.1%）。这个环境下 TCP 的经典假设被打破，几个针对性课题：

1. 丢包混淆拥塞判断。传统 CUBIC 把无线丢包一律当拥塞处理，cwnd 减半导致吞吐断崖——实际链路根本没拥塞，只是信号波动。BBR（Google 拥塞控制算法）改用”测带宽 + 测 RTT”建模，不依赖丢包信号，矿区实测吞吐提升 2~3 倍。内核 4.9+ 开启：net.ipv4.tcp_congestion_control=bbr，配合 net.core.default_qdisc=fq。这是矿区项目里少见的”一个内核参数改变体验”的优化。

2. MTU 与隧道分片。矿区常用 VPN 隧道回传（GRE/IPSec 封装开销 20~80 字节），外层封装后实际可用 MTU 缩小到 1400 以下，但终端仍按 1500 发包，触发分片——分片丢失一片，整包重传，弱网下雪上加霜。治理：隧道接口统一 MTU 1400 + MSS 钳制（clamp-mss-to-pmtu），让 TCP 层主动缩小段长而不是 IP 层分片。

3. RST 与 FIN 的语义差异在排障中的价值。优雅关闭（FIN 四次挥手）和异常终止（RST 立即销毁）在抓包里一眼可辨。矿区排障规律：大量 RST 出现在终端侧，通常是终端进程被系统杀（车载 Linux 内存回收）；RST 出现在服务端，先查连接表是否被会话管理误清理。tcpdump 抓包时按 tcp.flags.resets 过滤，比看应用日志快得多。

4. 心跳与弱网的配合。信号盲区进出时心跳超时误判会引发”离线→上线”抖动，重连风暴随之而来。除了重连 jitter，服务端判死加一道二次确认：超时后下发一次应用层探测（而非直接关连接），探测也失败才判死——代价是最多 30s 的死亡感知延迟，换来误判率下降一个数量级，对”矿区车辆状态大屏”这种展示型场景是划算的权衡。

七、面试高频问题速答

Q1: 三次握手为什么是三次，两次为什么不行？
防止历史失效的 SYN 创建无效连接占资源，且第三次 ACK 确认双方序列号同步完成。两次握手下，服务端无法确认客户端收到了自己的初始序列号。

Q2: TIME_WAIT 为什么是 2MSL，过多怎么办？
保证最后的 ACK 丢失后有足够时间响应对方重传的 FIN，并让旧报文自然消亡。过多用 tcp_tw_reuse + 扩端口范围 + 应用层连接复用治理，绝不用已删除的 tcp_tw_recycle。

Q3: select 和 epoll 的本质区别？
select 每次调用全量拷贝 fd 并线性扫描，复杂度 O(n)；epoll 注册一次、内核回调维护就绪链表，epoll_wait 只返回就绪 fd，复杂度与活跃连接数相关，十万连接下差距是数量级的。

Q4: TLS 握手中非对称加密和对称加密各干什么？
非对称（ECDHE/RSA）只用于安全地协商出对称会话密钥；对称（AES-GCM）负责真正的数据加密，因为性能高两个数量级。TLS 1.3 固定 ECDHE 还带来了前向安全。

Q5: 什么是零拷贝？Kafka 为什么快？
消除 CPU 参与的冗余拷贝。Kafka 消费链路用 sendfile 直接把页缓存数据 DMA 到网卡，加上顺序写与批量压缩，把磁盘 IO 和内存拷贝都压到最低。

Q6: 长连接为什么需要应用层心跳？
TCP 在对端异常消失（断网/崩溃）时不产生任何报文，连接状态”假活”；内核 keepalive 默认 2 小时无法满足业务感知要求，应用层心跳把死亡检测压缩到秒级，并顺带承载业务级的存活语义。

八、总结

TCP 的握手挥手是”连接的仪式”，滑动窗口和拥塞控制是”传输的油门刹车”，epoll 是”事件驱动的神经”，零拷贝是”数据的直达通道”——这四层从下到上，正好是 Netty 所解决的问题域。下一篇进入 Netty 主体：EventLoop 如何组织 epoll、ByteBuf 如何实现池化与引用计数，以及矿卡 WebSocket 集群的完整落地。
