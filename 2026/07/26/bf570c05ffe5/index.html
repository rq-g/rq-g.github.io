露天矿山无人驾驶调度平台（六）：技术难点与重构路线图

发布于 2026-07-26 分类：技术, 2026, 智慧矿山, 架构设计 👁

这是系列最后一篇。前面五篇把系统拆开了，这篇把发现的问题收拢成一张可执行的清单，并给出分阶段的改造路线。

一、核心技术难点 TOP 10

按「影响面 × 紧急度」排序。

# 难点 现状 潜在影响 解决方案 优先级
1 JT808 关闭 CRC 校验 bCheckCRCCode=false，且用分隔符切帧 比特翻转无法发现，控制指令可能出错 对齐私有化改造后的校验口径并开启；MQTT 层用 QoS1 + 应用层 seq 连续性校验 P0

二、三个阶段的改造路线

阶段一：止血（2~4 周，不动架构）

这一阶段只做低风险、高收益的修补：

  1. 修 bug 级问题

    • TraceIdResponseFilter 的 mutate() 结果未回传
    • 地图融合的 tryLock/unlock 不匹配
    • CoordinateCalculateService 传 null LineString
    • DispatchLogQueue.push() 改 offer() 并加监控计数
    • GlobalExceptionHandler.handleAccessDeniedException 补 @ExceptionHandler

  2. 统一超时与熔断

    对 rcloud-equipment、rcloud-algorithm-platform 配置熔断规则。

  3. JNI 加固

    • 路径改配置 + 启动 fail-fast
    • 调用包一层超时线程池

  4. 清理明显的死代码

    • SyncFuture（零引用）
    • TCPServer / NettyServerBootstrapRunner（已注释）
    • MqttMsgDecoder 空实现、WorkStateChangeApplyHander 空壳
    • OauthCliendetails / GrantTypeConstant（OAuth2 残留）

阶段二：补基建（1~2 个月）

  1. 可观测性三件套

    • 链路追踪（SkyWalking Agent 无侵入接入，成本最低）
    • 指标（Micrometer + Prometheus + Grafana），重点埋点：调度周期耗时、MQ 消费延迟、JNI 调用耗时、Feign 错误率
    • 日志（ELK/Loki 收集 + traceId 串联）

  2. 安全加固

    • 服务间 HMAC 签名
    • 网关剥离/覆盖外部传入的身份 header
    • Knife4j 的 root/root 明文密码改配置 + 生产关闭

  3. 缓存一致性

    • Caffeine 失效广播（Redis Pub/Sub，约 50 行代码）
    • 收敛 service/processor 两份不一致的缓存配置

  4. JT808 校验开启

    • 对齐私有化改造后的校验口径，灰度开启

阶段三：架构治理（3~6 个月）

  1. 拆巨类

    • TemporaryDispatchService（2138 行）→ 按 TaskNodeEnum 拆成策略类 + 一个编排器
    • DispatchControlService（2015 行）、MapMonitorService（1910 行）同理
    • DispatchGroupVO（991 行的 VO）拆分成多个场景 VO

  2. 消除复制式复用

    • 把 7 份 LoginUserInfoFeignInterceptor、MyMetaObjectHandler、Lock4jConfig、DistanceUtils、RegionUtil 收到 rcloud-common starter
    • 统一 MyMetaObjectHandler，逻辑删除 2=未删除 的反直觉约定加注释或改掉

  3. 解循环依赖

    • equipment ↔ dispatch 的共享读模型改为 MQ 事件同步的本地只读缓存
    • 逐步关闭 allow-circular-references

  4. superPOM 版本对齐

    • 4.8 线与 5.0 线合并，用 versions-maven-plugin 批量升级并回归

三、专题：2138 行的 TemporaryDispatchService 怎么拆

这是个典型症状，值得单独给方案。

症状：类里按 TaskNodeEnum + DestinationTypeEnum 组合出约 30 个 private 分支方法，每个方法几十行，方法之间靠成员变量传递状态。

拆分方案：策略模式 + 编排器

关键改动：把所有”隐式成员变量传参”改成显式 TaskContext 对象。这一步做完，拆类就只是搬代码。

收益：

  • 新增一个作业节点类型，只需加一个实现类，不改编排器；
  • 单个策略类可以独立写单测（现在 2138 行的类几乎无法测试）；
  • 方法调用栈变浅，StopWatch 埋点可以精确定位到哪个节点慢。

风险与规避：拆分必然引入改动风险，建议先用「分支-by-分支」的方式：每次只搬一个分支方法，跑通回归再搬下一个。

四、从这套系统里能带走的 7 条经验

抛开具体问题，这套代码里有些东西是通用的：

  1. 高频链路不要用分布式锁，用 Redis 原子操作做幂等。 1 秒周期的派车场景，SADD 返回值判定比加锁轻量得多。

  2. 集群定时任务可以很轻。 AbstractClusterJobThread 用 setNX + 归属判定 + 续期 + 下一跳，200 行就实现了故障转移，不是所有场景都需要 XXL-JOB。

  3. 协议网关要配置化。 base_agreement_info 表驱动协议→topic 映射，新增设备不改代码。对接多类型设备时这是刚需。

  4. 计算密集的部分外置。 几何融合、路径规划都交给 C++ .so，Java 做编排。边界划清楚了，性能问题才好定位。

  5. 健康检查要探”能用”而非”能连”。 MySQL 真的 insert 一次、RocketMQ 检查 topic 是否创建——比 SELECT 1 有意义得多。

  6. 主链路不要写数据库。 DispatchLogQueue 的思路是对的：日志用内存队列异步落库，主链路零 DB 写。（只是实现上批量逻辑被注释了。）

  7. 半成品比缺失更危险。 SyncFuture、TCPServer、空的 MqttMsgDecoder——它们看起来”已经做了”，review 会跳过，直到生产出事。定期做死代码清理是必要的。

五、系列总结

篇 主题 一句话结论
01 架构全景 18 个服务、事件驱动、计算与管控分离
02 框架与工程结构 自研 starter 有亮点，但版本漂移、异常无码
03 服务治理 自研健康巡检是亮点，Feign 零治理是短板
04 调度核心 集群任务框架和幂等设计值得学，主链路细节有坑
05 通信·地图·算法 工业级难点集中区，JNI 和地图融合风险最高
06 难点与路线图 先止血、再补基建、最后治架构

整体评价：这是一套业务复杂度远超技术复杂度的系统。它的难点不在于用了多新的框架，而在于要在「地图每天都在变、网络时断时续、设备十几种协议」的现实约束下，把调度这件事做对、做稳。从这个角度看，代码里那些”土办法”（异步轮询重发、本地缓存 TTL 自愈、复制式复用）恰恰是工程团队在交付压力下的合理选择——只是现在到了还债的时候。

本系列基于对 rcloud-* 系列仓库的静态代码分析写成，所有结论均标注了具体类与文件路径。文中涉及的内部地址、账号等敏感信息已做脱敏处理。
