露天矿山无人驾驶调度平台（六）：技术难点与重构路线图

发布于 2026-07-26 分类：技术, 2026, 智慧矿山, 架构设计 👁

这是架构篇的收尾。前面五篇把系统拆开了，这篇把发现的问题收拢成一张可执行的清单，并给出分阶段的改造路线。

性能与容量不在本篇——「能撑多少台车、QPS 多少、100 台能不能上」是另一个维度的问题，单独放在第七篇与第八篇。本篇只处理正确性、可维护性与架构健康度。

一、核心技术难点 TOP 13

按「影响面 × 紧急度」排序。

# 难点 现状 潜在影响 解决方案 优先级
1 JT808 关闭 CRC 校验 bCheckCRCCode=false（JT808MessageDecoder / SimulationJT808MessageDecoder 两处）；DTU 通道甚至没有帧解码器 比特翻转/截断报文无保护，控制指令可能出错 补齐字段数校验；对齐私有化改造后的校验口径并开启；MQTT 层 QoS1 + 应用层 seq 连续性校验 P0

9 用户上下文非 TTL；操作人恒为 "auto" 裸 ThreadLocal，无 TransmittableThreadLocal；MyMetaObjectHandler 把 createBy 写死为 "auto" 异步场景用户信息静默丢失；审计字段无法追溯真实操作人 换 TTL + 线程池装饰器；MyMetaObjectHandler 接回 LoginUserUtils 并保留匿名兜底 P1
10 同机多实例会把编组线程停死 checkRegThreadId() 只在 IP 相同时返回 threadId，同机新旧实例互判 → toStop() 永久停 “建了就停”循环，线程反复起停；单机 HA/测试环境必现 toStop() 不应对”同 IP 不同 threadId”生效，改为跳过等人接管 P1
11 集群锁只锁”干活”、没锁”起线程” DispatchGroupManageThread 里的 clusterJobSyncService 被注释，每实例为所有编组起线程 线程数 = 实例数 × 编组数，多数空转并持续打 Redis 管理线程纳入集群注册，或按编组做一致性哈希分片 P2
12 巨类与复制式复用 全系超 2000 行的类 7 个：EquipEquipmentService 4028、DispatchGroupService 3707（61 个 public 方法）、DispatchRegionService 2706、TruckProtocolService 2215（18 个注入依赖）、TemporaryDispatchService 2138、DispatchControlService 2015、MapMonitorService 1910；另有 DispatchGroupVO 991 行；Interceptor/Config 复制 7 份；MapFeignService 4 份且 TTL 差 20 倍；HealthController 9 份且端点各异 不可维护；副本参数持续漂移；巡检覆盖度取决于抄得最少的那个 按 TaskNodeEnum 拆策略类；横切关注点收进 common starter P2
13 异常无错误码 RockaiException 只有 message 前端无法按错误类型分支；i18n 做不了 引入 ErrorCode 枚举，响应体统一 {code,message,data,traceId} P2

补充说明第 8 项的确切位置：缺陷在 OSMMapService（MapFusionService:531 调用它），而不是 MapFusionService 自身；该方法 javadoc 还写着”这里不进行锁定控制”，与实现相反。

二、三个阶段的改造路线

阶段一：止血（2~4 周，不动架构）

这一阶段只做低风险、高收益的修补：

  1. 修 bug 级问题

    • TraceIdResponseFilter 的 exchange.getRequest().mutate() 结果被丢弃（TraceIdResponseFilter:33）
    • OSMMapService.batchUpdateBoundaryLineByPOIId 的 tryLock/unlock 不匹配（同模式共 8 处）
    • CoordinateCalculateService 拼好了 linePointCoordinateArray 却传 null lineString
    • DispatchLogQueue.push() 改 offer() 并加监控计数
    • GlobalExceptionHandler.handleAccessDeniedException 补 @ExceptionHandler 并加回异常入参
    • DispatchGroupService 第 130 行 TimeUnit.SECONDS 改回 MINUTES
    • AbstractClusterJobThread 里”同 IP 不同 threadId 就 toStop()“改为跳过（同机多实例）

  2. 统一超时与熔断

    对 rcloud-equipment、rcloud-algorithm-platform 配置熔断规则。

  3. JNI 加固

    • 路径改配置 + 启动 fail-fast
    • 调用包一层超时线程池

  4. 清理明显的死代码

    • SyncFuture（零引用）
    • TCPServer / NettyServerBootstrapRunner（已注释）、以及挂在它上面的 ServerChannelInitializer / DispatchMsgHandler / EscapeUtils
    • MqttMsgDecoder.decoder() 空实现、WorkStateChangeApplyHander（拼了一堆 mqttDataMap 却没有任何发送调用，只打了一行”发送 mqtt topic 成功”）
    • OauthCliendetails / GrantTypeConstant（OAuth2 残留，在 rcloud-common-core）

阶段二：补基建（1~2 个月）

  1. 可观测性三件套

    • 链路追踪（SkyWalking Agent 无侵入接入，成本最低）
    • 指标（Micrometer + Prometheus + Grafana），重点埋点：调度周期耗时、MQ 消费延迟、JNI 调用耗时、Feign 错误率
    • 日志（ELK/Loki 收集 + traceId 串联）

  2. 安全加固

    • 服务间 HMAC 签名
    • 网关剥离/覆盖外部传入的身份 header
    • Knife4j 的 root/root 明文密码改配置 + 生产关闭（现状是 knife4j.basic.enable=true, username=root, password=root，且 production: false，10+ 服务的 bootstrap.yml 里都是这一份）

  3. 缓存一致性

    • Caffeine 失效广播（Redis Pub/Sub，约 50 行代码）
    • 收敛 service/processor 两份不一致的缓存配置（MapFeignService 4 份、DispatchGroupCaffineCacheConstant 2 份）

  4. JT808 校验开启

    • 对齐私有化改造后的校验口径，灰度开启

阶段三：架构治理（3~6 个月）

  1. 拆巨类

    • TemporaryDispatchService（2137 行）→ 按 TaskNodeEnum 拆成策略类 + 一个编排器
    • DispatchControlService（2015 行）、MapMonitorService（1910 行）同理
    • DispatchGroupVO（991 行的 VO）拆分成多个场景 VO

  2. 消除复制式复用

    • 把 7 份 LoginUserInfoFeignInterceptor（system-service / dispatch-service / dispatch-processor / equipment-service / eam-service / largescreen-service / keda-service）、MyMetaObjectHandler、Lock4jConfig、DistanceUtils、RegionUtil、CoordinateUtil 收到 rcloud-common starter
    • 把 9 份 HealthController 收成按 classpath 自动装配的 starter（有 Redis 才暴露 redis 探测）——顺便解决”巡检覆盖度取决于抄得最全/最少的那一份”
    • 统一 MyMetaObjectHandler：当前 4 份写 isDelete = "0"（字符串）、rcloud-system-service 写 isDelete = 2（整数），而 YesOrNoEnum 是 1=是 / 2=否——同一个”未删除”在全项目有两种取值，必须定一个并加注释

  3. 解循环依赖

    • equipment ↔ dispatch 的共享读模型改为 MQ 事件同步的本地只读缓存（当前是 8 ↔ 9 的密集双向 Feign）
    • 逐步关闭 allow-circular-references（现散落在 17 份 bootstrap.yml）

  4. superPOM 版本对齐

    • 实际是三条线：4.7.0（algorithm / eam / web-interface）、4.8.0（dispatch / equipment / exchange / largescreen / map / system）、5.0.0（仅 common）
    • 先吃 4.7 → 4.8（同大版本、风险低），再整体评估 4.8 → 5.0；用 versions-maven-plugin 批量升级并回归

三、专题：2138 行的 TemporaryDispatchService 怎么拆

这是个典型症状，值得单独给方案。

症状：类里按 TaskNodeEnum + DestinationTypeEnum 组合出约 30 个 private 分支方法，每个方法几十行，方法之间靠成员变量传递状态。

拆分方案：策略模式 + 编排器

关键改动：把所有”隐式成员变量传参”改成显式 TaskContext 对象。这一步做完，拆类就只是搬代码。

收益：

  • 新增一个作业节点类型，只需加一个实现类，不改编排器；
  • 单个策略类可以独立写单测（现在 2138 行的类几乎无法测试）；
  • 方法调用栈变浅，StopWatch 埋点可以精确定位到哪个节点慢。

风险与规避：拆分必然引入改动风险，建议先用「分支-by-分支」的方式：每次只搬一个分支方法，跑通回归再搬下一个。

四、从这套系统里能带走的 7 条经验

抛开具体问题，这套代码里有些东西是通用的：

  1. 高频链路不要用分布式锁，用 Redis 原子操作做幂等。 1 秒周期的派车场景，SADD 返回值判定比加锁轻量得多。

  2. 集群定时任务可以很轻。 AbstractClusterJobThread 用 setNX + 归属判定 + 续期 + 下一跳，200 行就实现了故障转移，不是所有场景都需要 XXL-JOB。（但要注意两个边界：它没有解决”每台机器都为同一个任务起线程”的空转问题，而且”同 IP 不同 threadId 就自杀”的判定在同机多实例下会打死自己的线程——轻量框架要配轻量的边界检查。）

  3. 协议网关要配置化。 base_agreement_info 表驱动协议→topic 映射，新增设备不改代码。对接多类型设备时这是刚需。

  4. 计算密集的部分外置。 几何融合、路径规划都交给 C++ .so，Java 做编排。边界划清楚了，性能问题才好定位。

  5. 健康检查要探”能用”而非”能连”。 MySQL 真的 insert 一次、RocketMQ 检查 topic 是否创建——比 SELECT 1 有意义得多。

  6. 主链路不要写数据库。 DispatchLogQueue 的思路是对的：日志用内存队列异步落库，主链路零 DB 写。（只是实现上批量逻辑被注释了。）

  7. 半成品比缺失更危险。 SyncFuture、TCPServer、空的 MqttMsgDecoder——它们看起来”已经做了”，review 会跳过，直到生产出事。定期做死代码清理是必要的。

五、系列总结

篇 主题 一句话结论
01 架构全景 17 个服务、事件驱动、决策与管控分离；派车是 MQ 驱动，不是定时扫描
02 框架与工程结构 自研 starter 有亮点，但 superPOM 三条线、异常无码

05 通信·地图·算法 工业级难点集中区，JNI 和地图融合风险最高
06 难点与路线图 先止血、再补基建、最后治架构
07 性能瓶颈与容量 瓶颈是 20 倍调用放大，不是数据量；100 台不建议直接上
08 优化与升级路线 去放大、去同步、去无效；30~50 台 → 500 台

5.2 整体评价

整体评价：这是一套业务复杂度远超技术复杂度的系统。它的难点不在于用了多新的框架，而在于要在「地图每天都在变、网络时断时续、设备十几种协议」的现实约束下，把调度这件事做对、做稳。从这个角度看，代码里那些”土办法”（异步轮询重发、本地缓存 TTL 自愈、复制式复用）恰恰是工程团队在交付压力下的合理选择——只是现在到了还债的时候。

最后补一条横向观察：这套系统里几乎所有的坑都不是”写错了”，而是”写了两遍、改了一遍”——注释说着一件事、代码做另一件事（DispatchGroupMainThread 的 9 项职责、OSMMapService 的”这里不锁定”）；两份副本参数不一致（MapFeignService 10 分钟 vs 30 秒）；新旧实现并存（DumpLineService / NewDumpLineService 共用一把锁）；"0" 与 2 两种”未删除”。它的债务形态高度一致：不是能力不足，而是缺一个”唯一的说法”。 这也是后面三个阶段里，最值得先做的一件事——先把”同一个概念只能有一种写法”变成硬约束（starter 收敛 + CI 规则），剩下的重构才有意义。

六、本系列的覆盖边界

为免读者以为漏了，明确一下本系列没有覆盖的部分：

  • TDengine 的写入模型与降采样策略（只在技术栈里出现，没有展开）
  • MinIO 的地图文件版本管理与清理（只提到”结果 JSON 存 MinIO”）
  • OTA 升级链路（只提到 rcloud-equipment 负责 OTA，未展开协议与灰度）
  • 前端与生产大屏（largescreen 只作为数据消费方出现）
  • 现场部署拓扑与硬件（车载域控、DTU、红绿灯的选型与组网）

这几块若要补齐，各自都够写一篇。

另外，本篇的改造路线只覆盖正确性 / 可维护性 / 架构健康度三个维度；容量与性能（能撑多少台车、QPS、100 台可行性、三阶段性能优化清单）已单列为第七篇与第八篇。两者有交集的部分（如”消费异常被吞””Feign 零熔断”）在性能篇里被赋予了量化后果，可对照阅读。

本系列基于对 rcloud-* 系列仓库（12 个工程 / 20 个应用 / 34.8 万行代码）的静态代码分析写成，所有结论均标注了具体类与文件路径。文中涉及的账号、密钥、连接串已做脱敏；内网地址（如 Nacos 的 172.28.1.*:8848）与命名空间名按原值保留，以便对照代码定位，请勿在公网环境复用。公网 IP、生产域名等已隐去。
