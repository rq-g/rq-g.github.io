1.1 版本漂移：一个正在发生的问题

rcloud-common 的父 POM 版本是 superPOM:5.0.0-SNAPSHOT，而多数业务仓库还停在 4.x 线。把 10 个仓库逐个列出来，问题比”两条线”更细碎——实际是三条线：

superPOM 版本 仓库
5.0.0-SNAPSHOT rcloud-common（仅此一个）
4.8.0-SNAPSHOT rcloud-dispatch、rcloud-equipment、rcloud-exchange、rcloud-largescreen、rcloud-map、rcloud-system
4.7.0-SNAPSHOT rcloud-algorithm、rcloud-eam、rcloud-web-interface

二方库已经升到 5.0 线，业务线还散落在 4.7 和 4.8 两条线上（3 : 6 : 1 的分布）。这种”基础设施先行、业务跟进滞后”的状态在中台化改造中很常见，但风险在于：当 superPOM 5.0 升级了某个公共依赖的大版本（比如 Jackson、Netty），业务线编译时用的是 4.x 锁定的版本，运行期可能出现 NoSuchMethodError。

更麻烦的是 4.7 与 4.8 并存：rcloud-algorithm、rcloud-eam、rcloud-web-interface 这三个连 4.8 都没跟上，跨仓库传递依赖时实际生效的版本取决于 Maven 的最近优先/第一声明规则，同一份代码在不同聚合下编译出的依赖树可能不同。

建议：把 superPOM 版本做成 ${revision} 占位统一在原 pom 里声明，或者用 versions-maven-plugin（项目里其实已经配了这个插件）做批量对齐。优先级建议先吃掉 4.7 → 4.8（同一大版本、风险低），再整体评估 4.8 → 5.0。

缺点：环境是编译期决定的，运维无法在不重新打包的情况下切换环境；且 dev/test 共用同一个 Nacos 实例，只靠 namespace 隔离，没有灰度能力。

二、三个自研 Starter

rcloud-common 下有 4 个模块，其中 3 个是标准的 Spring Boot Starter（有 META-INF/spring.factories）。

2.1 rocketmq-starter：注解驱动的消费者自动注册

这是三个 starter 里设计得最好的一个。核心思路：用注解声明 topic，启动期扫描所有 IMessageHandler 实现并自动 subscribe()，业务代码零配置。

装配逻辑在 RockaiRocketmqAutoConfigure：

两个值得学习的设计点：

(1) 环境前缀自动加 env_。RockaiDynamicProducer 重写了 send()：

收发双方都统一加前缀，于是多套环境可以共用同一个 RocketMQ 集群而 topic 不打架。这个技巧在”测试环境不想单独部署 MQ”的场景下非常实用——比每个环境建一套集群成本低得多。

(2) 订阅关系集中在一个 Consumer Group。所有 topic 订阅到同一个 DefaultMQPushConsumer，好处是连接数少、运维简单；风险是任意一个 handler 抛异常或阻塞，会影响同组其他 topic 的消费（RocketMQ 的消费线程池是共享的）。项目里 consumeThreadMin/Max 都做了可配置，但没看到不同重要级 topic 的隔离。

这个风险有多大，可以把 Nacos 里的实际值代进去算一下：

rcloud-dispatch-processor 一个服务就订阅了 10 个 topic（6 个任务 topic + monitor + 挖机/装载机/矿卡实时信息），全部共用这 20~60 个线程：

  • 派车决策的单条处理耗时在 300400ms 量级（其中 68 次串行 Feign，见第七篇）；
  • 按 60 线程、350ms/条估算，理论约 171 msg/s，再扣掉日志开销与线程池争抢，实际不足 100 msg/s；
  • 而 defaultTopicQueueNums=2 意味着这个数字没法靠加实例提上去——超过 2 个实例也分不到队列。

也就是说：这不是”理论上的设计风险”，而是一个已经被配置值锁死的天花板。

改进建议：按”重要级”拆 23 个 Consumer Group（如 P0-控制指令、P1-状态上报、P2-日志），避免慢消费拖垮指令通道；同时把 consumeThreadMax 提到 128256、defaultTopicQueueNums 提到 8~16，先解除并发与扩展两道封印。

这两个 starter 存在明显的历史包袱：

问题 证据
配置类被注释 RedisConfig 整个类挂在 //@Configuration 下，不生效
两套 AutoConfigure 并存 RockaiRedisAutoConfigure（Lettuce）与 RockaiRedissonAutoConfigure 都声明了 redisService Bean，且后者 90% 代码是注释
序列化器不一致 redis-starter 用 Jackson2JsonRedisSerializer + activateDefaultTyping；RedisConfig（已停用）用 GenericJackson2JsonRedisSerializer

序列化这块值得单独说。Starter 里的写法：

activateDefaultTyping 会在 JSON 里写入 @class 类型信息，好处是反序列化能还原多态类型，坏处是：

  1. 存储的 JSON 里带全限定类名，一旦类改包名/重命名，老数据全部反序列化失败；
  2. 这是一个已知的反序列化安全敏感点（PolymorphicTypeValidator 需要严格配置白名单，这里用的是默认校验器）。

建议：业务对象序列化统一用 StringRedisSerializer + 显式 JSON.parseObject(json, Xxx.class)，把类型控制权交回业务代码。

键过期监听的设计倒是简洁：

rcloud-dispatch 启动时注册了一个 handler：RedisKeyExpirationListener.addHandler(new RedisKeyExpirationHandler(...))。

但这里有个坑：Redis 的键过期事件是发布即忘的，消费者掉线期间的事件永久丢失；且过期事件的触发有延迟（Redis 用惰性删除 + 定期删除，不保证准时）。所以它只能用于”补偿型”逻辑，绝不能用于”超时必须执行”的核心链路。dispatch 里的实现方法体恰好是空的，某种程度上也说明这条路走不通。

2.3 common-core：统一响应与异常

响应体有三套并存：

类 结构 状态
ResponseMsg<T> success(boolean) / errorCode / errorMsg / data 注释写着”由于前端修改工作量大，暂时不启用”
RockaiResponse extends HashMap status=200/500 / message / data 已 @Deprecated
PageBean<T> current / size / total / list 在用

工厂类是 ResponseMsgFactory，全部方法 synchronized static（这里其实没必要加锁，无状态静态方法加锁是纯粹的性能损耗）。

全局异常处理器只有一个，在 common-core 里：

覆盖了 Exception、RockaiException、BindException、MethodArgumentNotValidException 等。有一处 bug：

@ResponseStatus 只在”方法被 Spring 调用后”才决定响应码，而缺少 @ExceptionHandler 意味着 Spring 的异常解析器永远不会路由到这里——这个方法是一段死代码，403 会以 handleException(Exception) 兜底的形式返回 500。顺带说，它是无参的，即使补上 @ExceptionHandler 也拿不到 AccessDeniedException 实例，无法带出”缺哪个权限”的信息。

最大的问题是异常没有错误码：

于是各服务的 XxxBizException 抛出的都是中文字符串。前端想根据错误类型做分支处理（比如”该车正在作业中”弹提示 vs “系统异常”重试）只能靠字符串匹配，i18n 也做不了。

改进建议：引入 ErrorCode 枚举（code + defaultMessage + httpStatus），RockaiException 持有 ErrorCode，响应体统一为 {code, message, data, traceId}。迁移期可保留 message 字段做兼容。

三、Nacos 配置体系

3.1 shared-configs：公共配置抽离

各服务通过 shared-configs 共享配置，避免每个服务重复配 MySQL/Redis：

data-id 引入方
rcloud-common.yaml 全部服务
rcloud-common-mysql.yaml system、web-interface
rcloud-common-mysqltdengine.yaml equipment、exchange
rcloud-common-redis.yaml system、equipment、web-interface
rcloud-common-rocketmq.yaml equipment、system-health

refresh: false 是全局默认 —— 也就是说配置变更必须重启才生效。对调度类系统来说这未必是坏事（避免运行期配置漂移），但意味着改个超时时间要滚动重启全部实例，应急时很被动。

3.2 环境隔离：namespace 而非灰度

这是”硬隔离”，没有 Nacos 的 metadata / version 灰度路由能力。prod 用独立域名 rcloud.nacosserver:8848，dev/test 共用 172.28.1.81:8848。

风险点：dev 和 test 共用 Nacos 实例但 namespace 不同，理论上安全；但如果有人误把 discovery.namespace 配错，dev 环境的服务会注册到 test，造成跨环境污染。项目里 config.namespace 和 discovery.namespace 是两个独立变量，正是这种误配的高发区。

四、Spring Boot 3 迁移的中间态

从代码可以确证已经是 Boot 3.x：

  • jakarta.servlet.http.HttpServletRequest、jakarta.validation.ConstraintViolation、jakarta.annotation.Resource
  • 使用了 spring-cloud-starter-bootstrap（Boot 2.4+ 之后需要显式引入才能用 bootstrap.yml）

但仍有残留：

  • 部分类还在用 javax.annotation.Resource
  • MyBatis-Plus 的 PaginationInnerInterceptor(DbType.MYSQL) 写法是老版本 API
  • MyMetaObjectHandler 用 new Date() 而非 LocalDateTime

这说明迁移是”能跑就行”式推进的，没有做彻底清理。对这类系统，建议建一条 CI 规则：禁止新增 javax.* 依赖，逐步收敛。

五、值得抄走的三个设计

  1. RocketMQ 环境前缀自动加 env_ —— 多环境共享 MQ 集群的最低成本方案，生产/测试 topic 天然隔离。
  2. 注解驱动的消费者注册 —— @MessageHandlerType + 启动期扫描，新增消费者零配置，且 starter 里做了”配置订阅”与”注解订阅”的合并去重。
  3. Maven profile 驱动 Nacos 地址 —— 一份代码打多环境包，配置中心地址不进代码库。

六、需要立刻修的三个问题

  1. superPOM 版本漂移（4.8 vs 5.0），尽快对齐；
  2. RockaiException 无错误码，这是前端联调和可观测性的最大障碍；
  3. RedisConfig 注释残留 + 两套 AutoConfigure，会让新人误判哪个生效。
