露天矿山无人驾驶调度平台（一）：架构全景

发布于 2026-07-15 分类：技术, 2026, 智慧矿山, 架构设计 👁

关键词：Spring Cloud / Nacos / RocketMQ / Netty / JT808 / 高精地图 / 无人驾驶调度

这是一套真实在生产矿山跑的无人驾驶调度系统。本文是系列第一篇，先把「它到底是什么、由哪些服务组成、一次调度怎么流转」讲清楚，后面的文章再逐层拆开。

一、先说业务：这套系统到底在调度什么

露天矿的运输作业本质上是一个闭环的物料搬运循环，参与者是四类设备：

角色 干什么 系统中的关键约束
挖掘机 / 装载机 在装载区把矿石/剥离物装到矿卡上 装点有泊位，一次只能服务一辆车，需要排队
无人驾驶矿卡 重车去排土场/破碎站卸载，空车回装载区 全程自动驾驶，路线由云端规划下发
排土场（排土线） 卸载剥离物，边界每天在变化 边界靠车端采集回传，云端融合后更新地图
破碎站 / 地磅 卸载矿石、称重 有停车位分配与互斥放行

云端要解决的问题可以概括成一句话：在动态变化的矿区地图上，把 N 台车实时分配给 M 个装载点和 K 条排土线，并保证它们不撞车、不死锁、效率最高。

这决定了系统的三个硬性特征：

  1. 强实时 —— 调度线程 1 秒一轮，车端状态上报是秒级的；
  2. 状态密集 —— 每辆车的位置、载重、作业阶段、自动驾驶模式、故障位都是状态机，调度决策依赖全量状态；
  3. 地图是活的 —— 排土线边界每天随作业推进而移动，地图要能增量更新并同步到车端。

只看服务清单，20 个应用是一张平铺的网；按职责与依赖方向切开，它其实是一个非常标准的六层结构，外加一条纵向贯穿的能力带。

2.2 支撑这个分层的三条硬约束

约束一：时间尺度决定层次。 这是整套架构最本质的分层依据——

层 时间尺度 典型动作
L2 长连接 毫秒级处理，秒级心跳 报文解码、会话维持
L4 processor 报文到达即算（车端秒级上报） 派车决策，事件驱动
L4 service 编组线程 1 秒一轮 编组配置缓存同步（不派车）
L3 算法 毫秒～百毫秒 一次路径规划
L5 展现 分钟级 大屏刷新

把不同时间尺度的逻辑塞进同一个进程，快的必然被慢的拖住。rcloud-dispatch 拆成 service（连库、低频管控）+ processor（不连库、纯消费 MQ 做计算）就是这条约束的直接产物。

一个容易搞错的地方：很多人（包括我一开始）以为”1 秒一轮的调度线程”就是派车决策本身。实际拆开看是两件事——

  • DispatchGroupMainThread（在 service，每编组一个、周期 1000ms）干的是编组配置缓存的心跳：比对编组版本号，变了就异步刷新编组/工作面/卸载区配置并给 Redis 续期；
  • 真正的派车决策 LoadTaskService.doLoadTaskSendScaner(TruckTaskRealInfoDTO) 在 processor，由 LoadTaskTruckInfoHandler 消费车端实时状态报文触发——是事件驱动，不是定时扫描。

换句话说，”1 秒”的节奏感来自车端上报频率，不是调度线程的周期。第四篇会把这个区别展开。

约束二：车端是不可信边界。 L1 永远只能通过 L2 进入系统。L2 必须完成鉴权（JT808 的 0x0100 注册 / 0x0102 鉴权）、会话绑定、解码、异常报文丢弃。业务层拿到的永远是结构化 DTO，不是字节流。

约束三：指令下行必须异步。 L4 → L2 不允许 Feign 直达，代码里也确实如此——dispatch → equipment → RocketMQ → exchange。原因很直接：派车决策要等车端应答（SyncFuture 那套有超时），而它是在 MQ 消费线程里跑的，同步等一个往返会把消费线程整条堵住。

2.3 现实里的三处跨层违规（附证据）

架构图画得再干净，代码里总会有妥协。这三处是真正在生产代码里存在的：

# 违规 代码证据 真实风险
1 L2 反向依赖 L4 rcloud-exchange 中的 CommonProtocolFeign（@FeignClient("rcloud-equipment")）、EquipmentFeignAPIClient、SystemFeignAPIClient 接入层被业务层拖累：equipment 一慢，报文处理线程就阻塞，心跳超时面扩大。且完全没有熔断
2 L4 内部双向 Feign 环 dispatch → equipment：truckProtocolFeignService.sendLoadTask()；equipment → dispatch：9 个 @FeignClient(FeignServiceConstant.DISPATCH)——CheckLoadPointFeignClient、DebugPanelFeignClient、DepartureAndParkFeignClient、DispatchGroupBusinessFeignClient、DispatchGroupFeignClient、DispatchLogFeignClient、DispatchMaintenanceRecordFeignClient、DispatchRegionFeignClient、LoadBufferPointFeignClient 任一服务重启或变慢，另一侧请求直接失败；无熔断时形成雪崩。更麻烦的是它让”调度状态归谁所有”变得模糊
3 L3 越过 L4 直接读写数据 algorithm 侧直接持有 Redis 对象：PointRedis、TruckInfoRedis、ParkPointRedis、DetectionSecurityControlRedis 算法层与业务层共享同一份缓存的读写权，缓存模型一改，两个服务必须同步改

对应的收敛方向：

  1. L2 → L4：exchange 对 equipment/system 的调用只在低频路径保留（启动预热、异常上报），热路径改为本地缓存 + MQ 推送设备快照；
  2. dispatch ↔ equipment：把 equipment 通知 dispatch 的事件全部搬到 RocketMQ（基础设施现成），反向 Feign 只保留强一致查询；
  3. L3 入参自足：调用方把点位、车辆信息随请求传入，算法侧只保留无状态计算 + 本地 Caffeine，不再持有业务 Redis。

2.4 数据所有权：写权限只归一个域

域 拥有的数据 谁可以读
调度域 编组、任务、调度日志、运行时状态（Redis） equipment / largescreen 经 Feign
地图域 OSM 文件（MinIO）、装载区/排土区、地图版本 dispatch / algorithm 经 Feign
设备域 设备台账、协议、故障、OTA exchange / dispatch 经 Feign
平台域 用户/角色/权限/参数/附件 全平台
接入域 TDengine 报文日志、会话（内存 + Redis） 仅自身

一句话概括规则：写权限只归一个域，跨域读取走 Feign 或 MQ。目前唯一的破坏者是 L3 算法层对 Redis 的读写。

4.1 实测运行时基线（这几个值直接决定容量上限）

技术栈只说明”用了什么”，而下面这些来自 Nacos 的实际配置值，才决定”能撑多少”：

三个最值得注意的点：

  1. defaultTopicQueueNums=2 —— 单 topic 最多 2 个队列并行消费，实例数超过 2 个时多余实例分不到消息，水平扩展被封住；
  2. Redis 与 EMQX 都是单点 —— 这两个是真正的 SPOF，Redis 一挂，编组选主、实时状态、分布式锁全停；
  3. qos=2 —— 每条遥测数据要 4 次握手（PUBLISH→PUBREC→PUBREL→PUBCOMP），对 1Hz 的高频遥测来说代价偏高，控制指令才真正需要它。

这些数字会在第七篇里被用来推导容量。

几个值得注意的设计决策：

  • 决策在 processor、管控在 service，分界线是”有没有被 MQ 触发”。rcloud-dispatch-service 连库、提供 HTTP 配置与查询接口，并跑 1 秒一轮的编组配置缓存同步线程；rcloud-dispatch-processor 不连库，MQ 一到就做决策，结果通过 Feign 回写。这个拆分让”高频计算”和”低频管控”可以独立伸缩。
  • 派车是事件驱动、不是定时轮询。这一点特别容易看错：DispatchGroupMainThread 的 javadoc 里还列着”下发装载任务””下发卸载任务””装载等待区扫描”等 9 项职责，但实现里只剩第 1 项（刷新配置缓存），其余 8 项早已迁到 processor 由 MQ 触发。注释与实现分叉了，读代码时必须以 doBusiness() 的实际方法体为准。
  • 指令不走 Feign 直达车端。dispatch → equipment → RocketMQ → exchange → 车端，中间用消息队列解耦，避免消费线程被网络 I/O 拖住。
  • 协议是配置化的。base_agreement_info 表定义了每种协议报文对应的 topic，exchange 按表分派，新增协议不用改网关代码——这是典型的”配置化协议网关”。

六、读这套代码时的四个”反直觉”之处

  1. dispatch 里没有 MQ 生产者。所有 topic 都在 DispatchMQTopicConstant 定义（11 个），但 11 个消费者全在 processor（consumer 目录下正好 11 个 Handler），service 一个生产者都没有——它只被别人调用。
  2. “1 秒一轮”的不是派车，是配置缓存。DispatchGroupMainThread 每编组一个线程、周期 1000ms，但 doBusiness() 只做编组配置同步；派车由 processor 消费 MQ 触发。它的 javadoc 里还留着 8 项早已迁走的职责。
  3. exchange 的 JT808 TCP 通道实际没启用。RCloudExchangeApplication 里 tcpServer.start() 两行被注释，NettyServerBootstrapRunner 整个类是注释状态，真正在跑的是 WithOutTCPServer（withOut.tcp.port = 20001，逗号分隔文本）+ MQTT。
  4. map 服务的 lanelet2_* 七张表没有对应的 Entity/Mapper。库表是遗留的（外部工具写入），Java 侧真值在 MinIO 的 OSM 文件 + 内存 OSMMapContainerDTO。

第 4 条再补一层：本系统的”服务清单”和”仓库清单”并不相等。FeignServiceConstant 里定义了 13 个服务名，其中 4 个在本仓库群里找不到任何启动类——rcloud-report、rcloud-pre-algorithm、rcloud-safety-guarantee、rcloud-exchange-qingyan。而它们不是摆设：processor 有 4 个 Client 在调 REPORT，equipment 有 2 个 Client 在调 SAFETY_GUARANTEE。所以”这套系统有几个服务”这个问题，取决于你问的是代码边界还是部署边界——前者 17 个（本仓库群里的启动类），后者更大。

这些”看起来矛盾”的地方，往往藏着系统的演进史，后面几篇会逐个展开。

架构风格 微服务 + 事件驱动，决策与管控分离；派车是 MQ 事件驱动，不是定时扫描
最核心的链路 状态上报 → MQ → processor 决策 → 算法算路 → Feign 回写 → MQ → 网关下发
最值得学的 自研集群任务调度框架、配置化协议网关、地图增量融合闭环
