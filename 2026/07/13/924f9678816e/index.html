场景50：秒杀系统设计

考察点：流量削峰、库存扣减、防超卖、异步下单

核心概念：

  • 流量削峰：通过多级缓存和限流，减少后端压力
  • 库存扣减：Redis原子扣减 + DB兜底
  • 防超卖：多级校验，确保库存不超卖
  • 异步下单：快速返回，异步处理订单

真人回答示例：

面试官：”请你设计一个秒杀系统，如何保证高并发下不超卖？”

我：”秒杀系统的核心挑战是高并发和防超卖。我设计的秒杀系统主要有几个层次：

首先是流量入口削峰。通过CDN静态化和Nginx限流，拦截90%以上的无效流量，这是第一道防线。CDN可以缓存秒杀页面，Nginx可以设置请求频率限制，比如每秒每个IP最多10个请求。

其次是用户资格校验。在API网关层校验用户是否在白名单中、是否已达到限购数量等，快速拒绝无效请求。

然后是Redis库存扣减。这是最关键的一步，必须保证原子性。我们用Lua脚本实现判断和扣减的一体化操作，先检查库存是否充足，再扣减库存，同时记录用户已下单（防止重复下单）。Lua脚本在Redis中是原子执行的，可以保证并发安全。

接下来是异步下单。Redis扣减成功后，不直接写DB，而是发送MQ消息，快速返回’排队中’给用户。消费者从MQ中获取消息，异步处理订单。

最后是DB兜底。消费者处理订单时，会再次检查DB中的库存，用UPDATE WHERE stock > 0的方式扣减库存，如果affectedRows为0，说明库存不足，回滚Redis中的库存。

在智慧矿山项目中，我们用类似的方案处理矿山设备的抢购。比如新到一批矿用传感器，需要在短时间内分配给各个矿区。我们用Redis扣减设备库存，MQ异步分配，DB兜底，保证了高并发下的设备分配安全。”

追问应对：

面试官：”如何处理库存超卖的情况？”

我：”库存超卖主要有两种原因：一是Redis和DB的数据不一致，二是并发请求导致的竞态条件。处理方法有几种：第一是多级校验，Redis扣减时校验一次，DB落库时再校验一次；第二是使用唯一索引，在订单表上建立用户ID+商品ID的唯一索引，即使前面的校验都通过了，重复下单也会被唯一索引拦截；第三是库存回滚，如果DB扣减失败，需要回滚Redis中的库存，保证数据一致性。”

面试官：”如何处理消息积压？”

我：”消息积压主要是因为消费者处理速度跟不上生产者发送速度。处理方法有几种：第一是增加消费者数量，水平扩展消费能力；第二是优化消费者的处理逻辑，减少处理时间；第三是设置消息过期时间，如果消息超时未处理，直接丢弃或转到死信队列；第四是使用消息优先级，重要的消息优先处理。”

场景52：动态规划——最长递增子序列

考察点：动态规划、状态转移方程、时间优化

核心概念：

  • 状态定义：dp[i]表示以第i个元素结尾的最长递增子序列长度
  • 状态转移：dp[i] = max(dp[j]) + 1，其中j < i且nums[j] < nums[i]
  • 时间优化：使用二分查找优化到O(n log n)

真人回答示例：

面试官：”请你实现最长递增子序列的算法。”

我：”好的，最长递增子序列是经典的动态规划问题。

动态规划的思路是：定义dp[i]表示以第i个元素结尾的最长递增子序列长度。对于每个i，遍历前面所有的j，如果nums[j] < nums[i]，那么dp[i] = max(dp[i], dp[j] + 1)。时间复杂度是O(n²)，空间复杂度是O(n)。

还可以用二分查找来优化，时间复杂度可以降到O(n log n)。维护一个tails数组，tails[i]表示长度为i+1的递增子序列的最小末尾元素。遍历每个num，用二分查找找到它在tails中的位置，如果找到，就更新tails[position]为num；如果没找到，就把num添加到tails末尾。tails的长度就是最长递增子序列的长度。

在智慧矿山项目中，我们用类似的思路来优化车辆调度路径。比如在选择最优路径时，需要找到一条递增的路径序列，使得总效率最高。动态规划可以很好地解决这类问题。”

场景53：动态规划——最长公共子序列

考察点：动态规划、二维状态、空间优化

核心概念：

  • 状态定义：dp[i][j]表示text1前i个字符和text2前j个字符的最长公共子序列长度
  • 状态转移：text1[i] == text2[j]时，dp[i][j] = dp[i-1][j-1] + 1；否则，dp[i][j] = max(dp[i-1][j], dp[i][j-1])
  • 空间优化：使用滚动数组，将空间复杂度从O(n*m)降到O(min(n,m))

真人回答示例：

面试官：”请你实现最长公共子序列的算法。”

我：”好的，最长公共子序列也是经典的动态规划问题。

动态规划的思路是：定义dp[i][j]表示text1前i个字符和text2前j个字符的最长公共子序列长度。如果text1[i] == text2[j]，那么dp[i][j] = dp[i-1][j-1] + 1；否则，dp[i][j] = max(dp[i-1][j], dp[i][j-1])。时间复杂度是O(nm)，空间复杂度是O(nm)。

还可以用滚动数组来优化空间复杂度。只需要一个一维数组，每次更新时保存上一行的值即可。空间复杂度可以降到O(min(n,m))。

在智慧矿山项目中，我们用最长公共子序列来比较不同矿区的设备配置，找出最相似的配置方案，方便进行标准化管理。”

真人回答示例：

面试官：”请你实现01背包和完全背包问题。”

我：”好的，背包问题是动态规划的经典应用。

01背包的思路是：每个物品只能选一次。定义dp[j]表示容量为j的背包能装的最大价值。遍历每个物品，然后从容量倒序遍历，这样每个物品只会被选一次。状态转移方程是dp[j] = max(dp[j], dp[j - weights[i]] + values[i])。

完全背包的思路是：每个物品可以选无限次。和01背包类似，但是遍历容量时是正序遍历，这样每个物品可以被选多次。

在智慧矿山项目中，我们用背包问题来优化车辆的装载方案。比如一辆矿用车可以装载不同种类的矿石，每种矿石有不同的重量和价值，我们需要找到最优的装载方案，使得总价值最大。”

场景55：一致性哈希算法

考察点：哈希环、虚拟节点、数据分布

核心概念：

  • 哈希环：将节点和数据映射到0-2^32的环形空间上
  • 虚拟节点：为每个物理节点创建多个虚拟节点，均匀分布
  • 数据分布：数据映射到最近的节点

一致性哈希实现：

真人回答示例：

面试官：”请你实现一致性哈希算法。”

我：”好的，一致性哈希是分布式系统中常用的负载均衡算法。

一致性哈希的核心思想是：首先，构建一个哈希环，将节点和数据映射到0-2^32的环形空间上。然后，数据会被映射到最近的节点上。当节点加入或移除时，只有一部分数据需要重新分配，而不是所有数据。

为了解决数据分布不均匀的问题，引入了虚拟节点。为每个物理节点创建多个虚拟节点，均匀分布在哈希环上。这样数据分布会更加均匀。

在智慧矿山项目中，我们用一致性哈希来分配车辆调度任务。将调度任务哈希到不同的调度节点上，当调度节点扩容或缩容时，只有少量任务需要重新分配，保证了系统的稳定性。”

  • UUID：随机生成，全球唯一
  • 数据库自增：依赖数据库
  • Leaf：美团开源的分布式ID生成系统

Snowflake实现：

真人回答示例：

面试官：”请你实现Snowflake算法。”

我：”好的，Snowflake是Twitter开源的分布式ID生成算法。

Snowflake的ID由三部分组成：第一部分是41位的时间戳，可以使用约69年；第二部分是10位的机器ID，可以支持1024台机器；第三部分是12位的序列号，每毫秒可以生成4096个ID。

实现时需要注意几个问题：首先是机器ID的分配，需要保证每个机器的ID唯一；其次是时钟回退的处理，如果系统时钟回退，需要等待时钟恢复；最后是序列号的循环，当序列号达到最大值时，需要等待下一个毫秒。

在智慧矿山项目中，我们用Snowflake生成车辆任务ID、设备ID等，保证了ID的唯一性和有序性，方便进行数据排序和查询。”
