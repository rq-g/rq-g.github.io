场景27：GC调优实战

考察点：GC算法、内存分配、性能优化

核心概念：

  • 年轻代：存放新生对象，GC频率高，速度快
  • 老年代：存放存活时间长的对象，GC频率低，速度慢
  • GC算法：Serial、Parallel、CMS、G1、ZGC

关键配置：

调优流程：

  1. 监控GC状态：用jstat、jvisualvm、GCEasy
  2. 分析GC日志：查看GC频率、停顿时间、内存使用
  3. 调整参数：根据分析结果调整堆大小、GC算法、新生代比例
  4. 验证效果：观察GC是否改善

真人回答示例：

面试官：”如何进行GC调优？”

我：”GC调优是Java性能优化中的重要环节，我一般按这个流程来做。

第一步，监控GC状态。用jstat -gcutil 1000来实时查看GC情况，包括YGC次数、FGC次数、YGC时间、FGC时间、堆内存使用情况等。也可以用GCEasy来分析GC日志，它会给出详细的分析报告和优化建议。

第二步，分析GC日志。查看GC的频率和停顿时间，如果YGC太频繁或者停顿时间太长，就需要优化。比如智慧矿山无人驾驶调度系统的车辆调度核心服务，YGC每5秒一次，每次停顿300ms，这就需要优化。

第三步，调整参数。根据分析结果来调整参数。如果YGC太频繁，可能是新生代太小，可以增大新生代的大小，比如把-XX:NewRatio从2改成1，让新生代占堆的50%。如果FGC太频繁，可能是老年代太小，或者有内存泄漏，可以增大老年代或者排查内存泄漏。

第四步，验证效果。调整参数后，观察GC是否改善，比如YGC次数减少，停顿时间变短。

在智慧矿山项目中，我们的无人驾驶调度系统一开始用的是Parallel GC，后来发现FGC停顿时间长达2秒，严重影响了车辆调度的实时性——井下无人车的调度指令需要在50ms内下发，GC停顿导致指令延迟，存在安全隐患。后来改成了G1 GC，设置了-XX:MaxGCPauseMillis=100，把最大停顿时间限制在100ms以内。同时增大了新生代的比例，YGC的频率从每5秒一次降到了每20秒一次，停顿时间从300ms降到了50ms以内。调度指令下发延迟从平均150ms降到了30ms，满足了井下安全运行的要求。

总结一下，GC调优的流程是：监控 → 分析 → 调整 → 验证。”

追问应对：

面试官：”如何选择合适的GC算法？”

我：”选择合适的GC算法需要考虑几个因素：首先，应用的响应时间要求，如果是低延迟应用，比如智慧矿山的无人驾驶调度系统，要求调度指令延迟在50ms以内，应该选择G1或者ZGC；如果是批处理应用，对延迟要求不高，可以选择Parallel GC。其次，堆内存的大小，如果堆内存很大，比如32G以上，应该选择G1或者ZGC，它们对大堆的处理更好。最后，Java版本，ZGC只有Java 11+才支持。在我们项目中，考虑到需要支持大堆（16G）和低延迟要求，最终选择了G1 GC，Java版本是17。”

面试官：”如何判断是否有内存泄漏？”

我：”判断是否有内存泄漏可以从几个方面入手：首先，观察堆内存的使用情况，如果堆内存一直在增长，没有下降的趋势，就可能有内存泄漏。其次，观察FGC的情况，如果FGC越来越频繁，而且每次FGC后释放的内存很少，也可能有内存泄漏。最后，用jmap导出堆快照，用MAT分析，看看哪些对象占用了大量内存，是否有内存泄漏的嫌疑。”

场景28：类加载机制

考察点：类加载器、双亲委派模型、自定义类加载器

核心概念：

  • 类加载器：Bootstrap、Extension、Application、Custom
  • 双亲委派模型：子类加载器先委托父类加载器加载
  • 类加载过程：加载 → 链接 → 初始化

自定义类加载器：

真人回答示例：

面试官：”什么是双亲委派模型？为什么要使用它？”

我：”双亲委派模型是Java类加载器的核心机制。

首先，类加载器有几种：Bootstrap类加载器，负责加载JDK核心类，比如java.lang包下的类；Extension类加载器，负责加载JRE扩展目录下的类；Application类加载器，负责加载应用程序的类；还有自定义类加载器，负责加载我们自己定义的类。

双亲委派模型的工作原理是：当一个类加载器需要加载一个类时，它首先委托给它的父类加载器去加载，父类加载器再委托给它的父类加载器，直到最顶层的Bootstrap类加载器。如果父类加载器找不到这个类，子类加载器才会自己去加载。

使用双亲委派模型有几个好处：首先，保证了Java核心类的唯一性，比如java.lang.Object类，不管哪个类加载器加载，最终都是由Bootstrap类加载器加载的，这样就保证了Object类在整个JVM中只有一个版本。其次，防止了恶意代码替换Java核心类，比如有人写了一个自己的java.lang.Object类，如果没有双亲委派模型，这个类就可能被加载，从而破坏Java的安全机制。

在智慧矿山项目中，我们的无人驾驶调度系统用到了自定义类加载器。因为井下设备协议多样，不同厂家的无人车有不同的通信协议，我们需要动态加载不同的协议解析类。自定义类加载器从指定目录加载协议解析类，实现了协议的热插拔——不需要重启服务就能切换协议。同时，我们也遇到过类加载问题，比如不同版本的协议类冲突，这时候就需要检查类加载器的委托关系和类的路径。”

追问应对：

面试官：”如何打破双亲委派模型？”

我：”打破双亲委派模型可以通过重写ClassLoader的loadClass方法来实现。默认的loadClass方法会先委托父类加载器，如果父类加载器找不到才自己加载。如果我们重写这个方法，直接调用findClass方法，就可以打破双亲委派模型。但是一般不建议这样做，因为会破坏Java的类加载机制，可能导致类重复加载等问题。”

面试官：”什么是类的初始化？什么时候会触发？”

我：”类的初始化是类加载过程的最后一步，主要是执行静态变量的赋值和静态代码块。触发类初始化的情况有几种：首先，创建类的实例；其次，调用类的静态方法；再次，访问类的静态变量；最后，使用反射调用类。需要注意的是，访问类的静态常量不会触发初始化，因为静态常量在编译时就已经确定了。”

场景29：Java内存模型

考察点：内存可见性、原子性、有序性、volatile

核心概念：

  • 主内存：所有线程共享的内存区域
  • 工作内存：每个线程独有的内存区域
  • volatile：保证可见性和有序性，不保证原子性

volatile原理：

真人回答示例：

面试官：”什么是Java内存模型？volatile关键字有什么作用？”

我：”Java内存模型是Java并发编程的基础，定义了线程之间如何共享数据。

Java内存模型把内存分为主内存和工作内存。主内存是所有线程共享的内存区域，存放着对象的实际数据。工作内存是每个线程独有的内存区域，存放着主内存中数据的副本。线程之间不能直接访问对方的工作内存，必须通过主内存来通信。

当一个线程修改了共享变量时，它会先修改工作内存中的副本，然后再刷新到主内存。当另一个线程读取这个变量时，它会从主内存中读取最新的值，然后复制到自己的工作内存中。

volatile关键字有两个作用：首先，保证可见性，当一个线程修改了volatile变量时，会立即刷新到主内存，其他线程读取时会立即从主内存读取最新的值。其次，保证有序性，禁止指令重排序，确保volatile变量的读写操作按照代码的顺序执行。但是volatile不保证原子性，比如i++这种复合操作，即使i是volatile的，也不是原子的。

在智慧矿山项目中，我们用volatile来保证无人驾驶车辆状态标志的可见性，比如车辆的紧急停车标志。当井下发生安全隐患时，调度中心设置一个volatile的emergencyStop标志为true，所有负责车辆控制的线程都能立即看到这个变化并执行停车指令。这个场景对可见性要求极高，任何延迟都可能导致安全事故，所以volatile是必不可少的。”

追问应对：

面试官：”volatile和synchronized有什么区别？”

我：”volatile和synchronized都可以保证线程安全，但有几个区别：首先，volatile只保证可见性和有序性，不保证原子性；synchronized既保证可见性，又保证原子性。其次，volatile是轻量级的，性能更好；synchronized是重量级的，性能较差。最后，volatile只能修饰变量；synchronized可以修饰方法和代码块。”

面试官：”什么是指令重排序？为什么会发生？”

我：”指令重排序是编译器和CPU为了优化性能而对指令的执行顺序进行调整。比如一段代码，先赋值a=1，再赋值b=2，编译器可能会先执行b=2，再执行a=1，因为这两个操作没有依赖关系。指令重排序可以提高执行效率，但在多线程环境下可能会导致问题，比如一个线程看到了重排序后的结果，而另一个线程没有。volatile可以禁止指令重排序，确保指令按照代码的顺序执行。”

场景30：线程池参数设定

考察点：线程池参数、线程池类型、拒绝策略

核心参数：

参数 作用 建议值
corePoolSize 核心线程数 CPU密集型：N+1；IO密集型：2N
maximumPoolSize 最大线程数 根据业务需求设定
keepAliveTime 空闲线程存活时间 60秒
workQueue 任务队列 ArrayBlockingQueue / LinkedBlockingQueue
handler 拒绝策略 CallerRunsPolicy / AbortPolicy

线程池配置：

真人回答示例：

面试官：”如何设定线程池的参数？”

我：”设定线程池的参数需要考虑几个因素，主要是核心线程数、最大线程数、任务队列和拒绝策略。

首先是核心线程数。核心线程数是线程池长期保持的线程数，即使线程空闲也不会回收。设定核心线程数需要考虑任务的类型：如果是CPU密集型任务，比如智慧矿山无人驾驶调度系统的路径规划计算，核心线程数可以设为CPU核心数；如果是IO密集型任务，比如车辆通信、传感器数据采集，核心线程数可以设为CPU核心数*2。

其次是最大线程数。最大线程数是线程池允许的最大线程数，当任务队列满了之后，线程池会创建新的线程，直到达到最大线程数。最大线程数一般设为核心线程数的2-4倍。

然后是任务队列。任务队列用于存放等待执行的任务，有几种选择：ArrayBlockingQueue是有界队列，适合任务量可控的场景；LinkedBlockingQueue是无界队列，适合任务量不确定的场景。一般建议使用有界队列，避免任务无限堆积。

最后是拒绝策略。当任务队列满了，而且线程数已经达到最大线程数时，就需要拒绝新的任务。有几种拒绝策略：AbortPolicy直接抛出异常；CallerRunsPolicy让调用者自己执行；DiscardPolicy丢弃任务；DiscardOldestPolicy丢弃最老的任务。一般建议使用CallerRunsPolicy，让调用者自己执行，这样可以减缓任务的提交速度。

在智慧矿山项目中，我们为无人驾驶调度系统配置了多个线程池。路径规划线程池是CPU密集型，核心线程数设为16（CPU核心数是32，考虑到其他服务占用，设为16），最大线程数设为24，任务队列用ArrayBlockingQueue，容量是500。车辆通信线程池是IO密集型，核心线程数设为32，最大线程数设为64，任务队列容量是2000。拒绝策略都用CallerRunsPolicy，确保调度任务不会丢失。这样既保证了路径规划的计算效率，又满足了大量车辆通信的需求。”

追问应对：

面试官：”如何监控线程池的状态？”

我：”监控线程池的状态可以从几个方面入手：首先，ThreadPoolExecutor提供了一些方法来获取线程池的状态，比如getPoolSize()获取当前线程数，getActiveCount()获取活跃线程数，getQueue().size()获取任务队列的大小。其次，可以用Spring的Actuator来暴露线程池的指标，比如线程数、任务数、拒绝数等。最后，可以用Prometheus + Grafana来监控线程池的状态，设置告警规则，当线程池的活跃线程数超过阈值时及时告警。”

面试官：”线程池中的线程是如何创建和销毁的？”

我：”线程池中的线程创建和销毁遵循一定的规则：首先，当有任务提交时，如果当前线程数小于核心线程数，就创建新的线程；其次，如果当前线程数等于核心线程数，就把任务放到任务队列中；再次，如果任务队列满了，而且当前线程数小于最大线程数，就创建新的线程；最后，如果线程空闲时间超过了keepAliveTime，而且当前线程数大于核心线程数，就回收空闲线程。这样既保证了并发处理能力，又避免了资源浪费。”

场景31：并发编程实战

考察点：synchronized、Lock、原子类、并发容器

核心工具：

工具 作用 适用场景
synchronized 互斥锁 简单场景
ReentrantLock 可重入锁 需要公平锁或条件变量
AtomicInteger 原子操作 计数器、ID生成
ConcurrentHashMap 并发Map 高并发读写
CountDownLatch 线程同步 等待多个线程完成

并发编程示例：

真人回答示例：

面试官：”如何实现线程安全的计数器？”

我：”实现线程安全的计数器有几种方式，各有优缺点。

第一种是用synchronized关键字。在计数器的increment方法上加synchronized，这样每次只有一个线程能执行这个方法，保证了线程安全。但是synchronized是重量级的，性能较差，不适合高并发场景。

第二种是用ReentrantLock。创建一个ReentrantLock对象，在increment方法中先获取锁，执行完后再释放锁。ReentrantLock比synchronized灵活，可以实现公平锁，还可以设置锁的超时时间。

第三种是用原子类，比如AtomicInteger。AtomicInteger提供了原子操作，比如incrementAndGet()，可以保证原子性，而且性能很好，适合高并发场景。

在智慧矿山项目中，我们用AtomicInteger来实现无人驾驶车辆的任务计数器，每辆车完成一个运输任务就递增计数。因为井下有上百辆无人车同时运行，并发量很高，AtomicInteger的性能更好。同时，我们用ConcurrentHashMap来缓存车辆的实时状态信息，包括位置、速度、电量等，ConcurrentHashMap支持高并发读写，不需要额外的同步，而且读操作是无锁的，性能非常好。

需要注意的是，原子类只保证单个操作的原子性，如果是复合操作，比如先检查再更新，就需要用锁来保证原子性。比如我们在更新车辆状态时，需要先检查车辆是否处于可调度状态，然后再更新，这就需要用锁来保证原子性。”

追问应对：

面试官：”ConcurrentHashMap是如何实现线程安全的？”

我：”ConcurrentHashMap是通过分段锁来实现线程安全的。在Java 7中，ConcurrentHashMap把数据分成多个段，每个段有一个锁，不同段的操作可以并发执行，这样提高了并发性能。在Java 8中，ConcurrentHashMap改用了CAS和synchronized来实现，当操作的桶为空时，用CAS来插入；当桶不为空时，用synchronized来锁住桶的头节点。这样既保证了线程安全，又提高了并发性能。”

面试官：”什么是CAS？有什么问题？”

我：”CAS是Compare-And-Swap的缩写，是一种乐观锁。CAS操作包含三个参数：内存位置、期望值、新值。CAS操作会比较内存位置的值和期望值，如果相等就把内存位置的值更新为新值，返回成功；否则返回失败。CAS的优点是不需要加锁，性能更好。但是CAS有几个问题：首先是ABA问题，一个值从A变成B再变成A，CAS会认为没有变化；其次是自旋问题，如果CAS一直失败，会导致线程一直自旋，消耗CPU资源；最后是只能保证单个变量的原子性，不能保证多个变量的原子性。”

场景32（新增）：设计模式应用

策略模式示例：

真人回答示例：

面试官：”你在项目中用过哪些设计模式？”

我：”在智慧矿山项目中，我用过几种设计模式。

首先是单例模式。我们的调度中心核心服务用了单例模式，确保整个系统只有一个调度实例，避免多调度中心导致车辆冲突。

其次是工厂模式。我们的车辆通信模块用了工厂模式，不同厂家的无人车（比如小松、卡特彼勒）有不同的通信协议，通过工厂模式来创建对应的协议解析对象，这样可以方便地接入新的车辆类型。

然后是策略模式。我们的路径规划模块用了策略模式，支持多种路径规划算法（A*、Dijkstra、RRT），根据不同的场景（避障、最短路径、最快路径）选择不同的策略，这样可以方便地扩展新的路径规划算法。

还有观察者模式。我们的安全监控模块用了观察者模式，当井下发生异常（瓦斯超标、人员闯入禁入区）时，会通知所有的告警处理器，比如发送紧急停车指令给车辆、推送告警信息给调度人员、记录安全日志等，这样可以方便地扩展新的告警方式。

设计模式的核心思想是’开闭原则’，对扩展开放，对修改关闭。使用设计模式可以提高代码的可维护性和可扩展性。”

追问应对：

面试官：”单例模式有几种实现方式？各有什么优缺点？”

我：”单例模式有几种实现方式：第一种是饿汉式，在类加载时就创建实例，优点是线程安全，缺点是如果实例用不到，会浪费资源。第二种是懒汉式，在第一次使用时创建实例，优点是节省资源，缺点是线程不安全，需要加锁。第三种是双重检查锁，在懒汉式的基础上优化，只在第一次创建时加锁，优点是线程安全且性能好。第四种是静态内部类，利用类加载机制保证线程安全，优点是线程安全且延迟加载。第五种是枚举，用枚举来实现单例，优点是线程安全且可以防止反序列化。一般推荐使用静态内部类或枚举方式。”
