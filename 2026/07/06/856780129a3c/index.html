MQ消息丢失全场景复盘——生产者、Broker、消费者三层排查与Java实战

发布于 2026-07-06 分类：技术, 2026, 消息队列, 高并发 👁

前言

先讲两个真实事故。

事故一（智慧矿山无人驾驶调度）：调度中心给 12 台矿卡下发了”装载区变更”任务，调度大屏上 12 台全部显示”下发成功”。但现场有 3 台矿卡一直按旧路线空跑到排土场，直到班组长在电台里喊才发现。事后复盘——消息压根没进 Broker。生产者用的是异步发送，回调里只写了一句 log.info，异常被吞了，send() 本身永不抛错。

事故二（支付回调）：支付网关回调订单服务，订单状态改成”已支付”，然后发消息通知积分服务加积分。线上跑了一个月，月底财务对账发现 4000 多笔订单积分没到账。根因是发送 MQ 时 Broker 正在做主从切换，几十毫秒的抖动导致发送失败，代码里 send() 之后没校验 SendResult，异常被 catch 住打印了一行日志就结束了。

很多人以为”用了 MQ，消息就一定能到”。实际上 MQ 只保证它自己那一段，从业务代码到 Broker、从 Broker 到业务代码这两段，全靠你自己兜。 消息从产生到消费完，中间至少经过 7 个环节，任何一个环节掉链子，消息就静悄悄地消失了。

这篇文章把消息丢失拆成 生产者、Broker、消费者 三层，逐层讲清楚：为什么会丢、怎么复现、Java 代码怎么写、出事了怎么查。

一、先建立全局视角：一条消息的 7 次渡劫

排查消息丢失，最忌讳的就是”凭感觉改配置”。先把链路画出来，你才知道该去哪个环节找证据。

flowchart LR
    A["① 业务线程调用 send()"] --> B["② Producer 客户端缓冲/序列化"]
    B --> C["③ 网络传输到 Broker"]
    C --> D["④ Broker 写入 PageCache"]
    D --> E["⑤ 刷盘 / 副本同步"]
    E --> F["⑥ Consumer 拉取到内存"]
    F --> G["⑦ 业务处理完成"]
    G --> H["⑧ 提交 ACK / Offset"]

对应每个环节的风险点和”丢失时谁背锅”：

环节 丢失原因 责任方 典型症状
① 业务调用 send 没调用 / 异常被吞 业务代码 业务库有数据，MQ 完全没这条消息
② 客户端缓冲 进程被 kill，缓冲区未 flush 业务代码 重启瞬间丢一批
③ 网络传输 网络抖动、Broker 主从切换 中间件 发送超时 / Broker 侧无记录
④ PageCache 机器断电、OS crash 中间件 Broker 返回成功，重启后消息没了
⑤ 副本同步 单副本宕机、异步复制未完成 运维/架构 磁盘损坏后数据不可恢复
⑥ 消费者内存 拉到了但进程崩了 业务代码 Offset 已提交但业务逻辑没执行
⑦ 业务处理 抛异常但已 ACK 业务代码 日志有异常，消息不会重投
⑧ ACK 自动提交早于业务完成 业务代码 最难查，现象=随机丢消息

一句话排查口诀：先看生产者有没有发出来，再看 Broker 有没有存下来，最后看消费者有没有真正处理完。顺序不能反，90% 的”MQ 丢消息”最后是第 ⑦⑧ 步的锅。

二、生产者端：最常见的 4 种丢法

2.1 同步发送不校验返回结果

这是排名第一的坑。RocketMQ 的 send() 只有在网络异常、超时、Broker 明确拒绝时才抛异常；返回 SendResult 但状态是 FLUSH_DISK_TIMEOUT、SLAVE_NOT_AVAILABLE 时，方法本身是正常返回的。

注意 FLUSH_DISK_TIMEOUT 这类”半成功”状态：很多同学看到返回了 SendResult 就认为万事大吉。异步刷盘下，Broker 写 PageCache 成功就会返回 SEND_OK，此时机器掉电，消息照样丢。核心业务要么开同步刷盘，要么靠本地消息表兜底。

2.2 异步发送回调吞异常

异步发送性能好，但回调是在独立的 IO 线程里执行的，异常不会抛到业务线程，最容易被忽略。

2.3 无脑使用 sendOneway

sendOneway 只负责把消息写进 Socket 缓冲区，不等任何响应，完全没有可靠性保证。它只适合日志采集、埋点上报这类”丢一条无所谓”的场景。

发送方式 吞吐量 可靠性 适用场景
sendOneway 最高 无保证 日志、埋点、监控数据
异步 send + callback 高 回调可感知 设备高频上报、通知类
同步 send 中 可感知返回状态 订单、支付、任务下发
事务消息 低 最高（与本地事务原子） 强一致业务

2.4 事务消息用错：本地事务提交了，半消息没确认

RocketMQ 事务消息的正确流程是：发送 Half 消息 → 执行本地事务 → 根据本地事务结果 Commit/Rollback → 事务回查兜底。

最容易写错的地方：executeLocalTransaction 里返回 UNKNOW 又没有有效的回查逻辑，或者本地事务抛了异常导致连 execute 都没进。

踩坑提醒：事务回查默认回查 15 次（transactionCheckMax），间隔可配置。如果你的 checkLocalTransaction 里查的是从库，主从延迟会导致”本地事务已提交但回查查不到”，从而误回滚。回查必须查主库或强一致存储。

2.5 Kafka / RabbitMQ 生产端的对应配置

Kafka —— 关键是 acks + 幂等 + 重试：

acks=all 有个经典误区：它只在 min.insync.replicas >= 2 时才有意义。如果 min.insync.replicas=1，ISR 里只剩 Leader 一个，acks=all 等价于 acks=1，Leader 宕机照样丢。生产环境必须 replication.factor=3 + min.insync.replicas=2 + acks=all 三件套一起配。

RabbitMQ —— 关键是 publisher confirm + mandatory + 交换机/队列持久化：

中间件 生产者可靠性三要素
RocketMQ 校验 SendStatus + 事务消息/本地消息表 + 同步刷盘（核心业务）
Kafka acks=all + enable.idempotence=true + min.insync.replicas≥2
RabbitMQ publisher confirm + mandatory/returns + 交换机/队列/消息三重持久化

三、Broker 端：写入了内存不等于落了地

3.1 刷盘策略的取舍

中间件 配置项 可靠 性能
RocketMQ flushDiskType=SYNC_FLUSH 高（写入即落盘） 低，TPS 下降约 30%~50%
RocketMQ flushDiskType=ASYNC_FLUSH 掉电丢 PageCache 内数据 高
Kafka 依赖 OS PageCache + 副本 靠副本数保证，不建议 log.flush.interval.messages=1 高
RabbitMQ Quorum Queue（Raft） 高，多数派确认 中

实践建议：

  • Kafka 的设计哲学就是”不靠刷盘靠副本”，所以 Kafka 生产环境不要去改刷盘参数，把 replication.factor=3 + min.insync.replicas=2 配好即可；
  • RocketMQ 核心业务（订单、任务下发）建议 SYNC_FLUSH + 同步复制（brokerRole=SYNC_MASTER），日志类 Topic 用 ASYNC_FLUSH；
  • RabbitMQ 3.8+ 优先用 Quorum Queue 替代镜像队列，避免经典的”镜像队列网络分区后丢消息”问题。

3.2 单副本 = 定时炸弹

硬性要求：生产环境任何业务 Topic，副本数 ≥ 2（推荐 3）。只有一个副本的 Topic 应该被 JMX/巡检脚本自动告警出来。

四、消费者端：90% 的”丢消息”都发生在这里

4.1 头号杀手：自动 ACK

自动 ACK 的语义是”消息投递到消费者就算成功“，而不是”业务处理完才算成功”。

basicNack(tag, false, true) 的 requeue=true 会把消息放回队头，如果这条消息永远处理失败，它会无限循环霸占消费线程，把整个队列拖死。生产上要么限制重试次数（用 Redis 计数 + 超过阈值丢死信），要么直接 requeue=false 走死信。

4.2 被忽略的盲区：死信队列没人管

消息进入死信队列，如果没人处理、没有告警，效果等同于消息丢失，而且是”看起来一切正常”的丢失。

死信处理的三条铁律：

  1. 死信必须有告警，堆积数量超过阈值立刻通知到人；
  2. 死信必须可追溯：原始 topic、body、失败原因、重试次数全部落库；
  3. 死信必须可重投：提供一个管理后台”一键重发”按钮，别让人去写 SQL 补数。

五、兜底方案：本地消息表（最朴素也最可靠）

事务消息虽好，但依赖中间件支持、有回查开销。本地消息表是通用性最强、最好落地的方案——用数据库事务保证”业务数据”和”待发消息”原子写入，再由定时任务保证最终投递。

重试一定要有退避。我见过最惨的一次：某服务因为 DB 连接池打满导致发送失败，定时任务每 5 秒全量扫描重试，结果把 MQ 和 DB 一起打挂了。退避间隔建议 min(2^n * 60s, 2h)，最大重试次数 8~10 次，超过就告警让人介入。

六、排查手册：消息丢了怎么快速定位

flowchart TD
    A["用户投诉：消息没生效"] --> B{"生产者日志有 send 记录？"}
    B -- 无 --> C["业务代码没发 / 事务回滚了
查业务库 & 本地消息表"]
    B -- 有 --> D{"SendResult 是 SEND_OK？"}
    D -- 否 --> E["生产者发送失败
查网络/超时/Broker 状态"]
    D -- 是 --> F{"Broker 按 bizKey 查询能查到？"}
    F -- 查不到 --> G["Broker 侧丢失
查刷盘策略/副本数/磁盘故障"]
    F -- 能查到 --> H{"消费者日志有这条消息的入参？"}
    H -- 无 --> I["消费位点/分组问题
查 consumer group、tag 过滤、订阅关系"]
    H -- 有 --> J{"消费日志里有异常？"}
    J -- 无异常但没生效 --> K["检查是否 catch 后返回 SUCCESS
检查幂等是否误判为已处理"]
    J -- 有异常 --> L["查是否进死信队列
查重试次数是否耗尽"]

常用排查命令：

场景 命令
RocketMQ 查消息 mqadmin queryMsgByKey -n nsaddr:9876 -t TOPIC -k bizKey
RocketMQ 查堆积 mqadmin consumerProgress -n nsaddr:9876 -g consumerGroup
RocketMQ 查死信 mqadmin queryMsgByTopic -n nsaddr:9876 -t %DLQ%consumerGroup
Kafka 查消费位点 kafka-consumer-groups.sh --bootstrap-server x:9092 --describe --group g
Kafka 查最早消息 kafka-console-consumer.sh --topic t --from-beginning --max-messages 1
RabbitMQ 查队列 rabbitmqctl list_queues name messages messages_ready messages_unacknowledged
RabbitMQ 查未确认 rabbitmqctl list_consumers

RabbitMQ 里 messages_unacknowledged 长期不降，几乎等价于”消费者卡住或者手动 ACK 漏了”，是排查消费者问题最直接的指标。

复盘方法论：为什么”三层排查”比”逐个试”快十倍

消息丢失排查最容易犯的错是从生产者开始逐层打日志重放，一小时过去可能还卡在第一层。三层框架的价值在于每层有独立的”丢失判定信号”，可以先定位层再定位点：生产者层，看发送结果确认状态（ACK/重试日志）——发送方拿到 ACK 了，消息就肯定到了 Broker，排查直接跳到 Broker 层，这一步就能砍掉一半时间；Broker 层，看消息是否落盘（RocketMQ 查 ConsumeQueue 索引、Kafka 查 log segment 的 offset 区间），落盘了就是”在”，查清理策略（retention）和刷盘配置；消费者层，看 offset 提交记录与业务处理日志的时间差——offset 提交了但业务日志没有，几乎必然是消费者先提交后处理的反模式或处理异常被吞。再补一个实战利器：消息轨迹（message trace），RocketMQ Admin 工具和自建的发送-存储-消费三张流水表，能把”哪一层丢的”从推理变成查询。我们团队最终固化了一条规矩：消息量大的核心链路必须建消息轨迹表，一个月一次的排查收益就超过它的存储成本。

七、防丢清单（建议贴到团队 Wiki）

层 检查项 是否必须
生产者 同步发送校验 SendStatus，不只看是否抛异常 ✅
生产者 异步发送回调处理 onException + 半成功状态 ✅
生产者 核心业务使用事务消息或本地消息表 ✅
生产者 重试带指数退避 + 最大次数，禁止无限重试 ✅
生产者 禁止核心业务使用 sendOneway ✅
Broker 副本数 ≥ 3（至少 2） ✅
Broker 核心 Topic 同步刷盘 + 同步复制 推荐
Broker Kafka min.insync.replicas ≥ 2 配合 acks=all ✅
Broker 磁盘使用率告警（>75% 预警，>85% 严重） ✅
消费者 关闭自动 ACK / 自动提交 offset ✅
消费者 业务成功后才确认，异常返回重投 ✅
消费者 禁止 catch 异常后返回消费成功 ✅
消费者 死信队列有消费者 + 落库 + 告警 + 可重投 ✅
全局 消费逻辑幂等（重试必然带来重复） ✅
全局 消息轨迹/链路追踪打通（bizKey 贯穿全链路） 推荐

“丢了”还是”慢了”：一个被严重低估的区分

复盘消息丢失时最危险的认知偏差是把”消费延迟”当成”消息丢失”。真实案例：业务方报障”订单消息丢了”，排查一小时后发现消费堆积了 40 万条，那条消息排在第 39 万位——消息没丢，是迟到 2 小时。区分两者的判据很明确：拿消息的 msgId 查 Broker 轨迹，存在且 offset 已被消费组提交过 → 走”慢了”的堆积排查；Broker 里没有且发送方有 ACK → 才是真的丢了。这个区分直接决定处置动作：丢了要启动补偿和防丢加固，慢了要扩容消费者或降级非核心消费。对业务方的话术也要变：”丢消息”会触发全链路恐慌，”消费积压、预计 X 分钟内追平”是可接受的服务波动——工程师对故障的命名方式，直接影响组织的响应方式。经验法则：收到”消息丢失”报障，第一动作永远是查堆积曲线，这个顺序能省掉大部分无效排查。

八、总结与思考

消息丢失这件事，从来不是”配一个参数”能解决的，它是生产者、Broker、消费者、业务存储、监控告警这一整条链路的工程问题。我的经验排序：

  1. 先把消费者自动 ACK 关掉——这是投入产出比最高的一步，一个改动能消掉一大半”幽灵丢消息”；
  2. 再给核心业务上本地消息表——把”消息”当成业务数据的一部分来管理，用数据库事务兜底；
  3. 最后补死信告警和幂等——保证出问题能发现、能补偿、重复消费不出错。

最后留个思考题：你的项目里，MQ 消息丢失是通过什么手段发现的？ 如果是靠用户投诉或者对账才发现，说明监控和可观测性还缺一块——真正可靠的系统，消息异常应该是告警先响，而不是业务先炸。
