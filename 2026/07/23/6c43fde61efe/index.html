露天矿山无人驾驶调度平台（五）：车云通信与高精地图——JT808、lanelet2 与 JNI 算法

发布于 2026-07-23 分类：技术, 2026, 智慧矿山, 架构设计 👁

关键词：Netty / JT808 / MQTT / OSM / lanelet2 / JNI / Reeds-Shepp / JTS

前两篇讲的还是”互联网味”的东西。这一篇进入真正的工业现场：车载终端协议、每天都在变的矿区地图、C++ 算法库。这三块的难点和 Web 开发完全不是一个体系。

“MQTT 承载业务、JT808 只作为应用层报文格式” —— 这是个很务实的取舍。JT808 是部标道路运输车辆协议（北斗/GPS 定位），天然适合车载终端，但它的 TCP 长连接在移动网络下维护成本高（矿区信号也不稳）。用 MQTT 做传输层，保留了 JT808 的报文语义，又拿到了 MQTT 的断线重连、QoS、海量连接能力。

1.1.1 MQTT 通道的实测配置（三个值得注意的值）

值 问题
qos: 2 QoS2 每条消息要 4 次握手（PUBLISH→PUBREC→PUBREL→PUBCOMP）。它保证”恰好一次”，适合控制指令；但矿卡实时状态是 1Hz 的高频遥测，丢了下一秒还会再来——用 QoS2 是把最贵的等级用在了最不值钱的数据上，代价是双倍网络往返与 broker 状态维护
单 EMQX 与 Redis 一样是单点。它挂掉 = 全车队失联，且重连风暴会瞬间打满鉴权与缓存
cleanSession: true 重连不恢复会话，离线期间的 QoS1/2 消息全部丢弃；配合 3s 心跳，网络抖动时会话重建频繁

建议拆分通道：控制指令（急停、任务下发）走 QoS2 + 独立 topic + 独立消费线程池；遥测状态走 QoS1。这不只是省带宽——更重要的是让”安全指令”不会被 1Hz 的遥测洪水挤在后面，这一点在第七篇里会展开（MQ 反压与指令延迟的耦合）。

1.3 JT808 私有化改造与它的三个坑

标准 JT808 的帧结构是 0x7E | 消息头 | 消息体 | 校验码 | 0x7E，消息头里有终端手机号 BCD[6] 和消息体长度字段。这个项目做的是：

改动 后果
删掉了终端手机号 BCD[6]，改用 IMEI 字符串 不再兼容标准 JT808，属于私有裁剪协议
停用了 JT808 TCP 通道，改由 MQTT 承载报文体 下文坑 ①② 因此在生产链路上不成立
bCheckCRCCode = false 见下方坑 ③，这一条在生产链路上依然成立

坑 ③（这条真的在跑）：校验码关了。

MQTT 通道收到 hex 报文后仍复用 JT808MessageDecoder 解码（MqttConsumerHandler），所以这条”关校验”的影响是真实的：网络传输中任何一个比特翻转都不会被发现，而这条链路上跑的是”派车指令””紧急停车”这类控制指令。

关的原因不难猜——协议被私有化改造后，某些字段的 CRC 计算口径没对齐，开着会大量丢包。但正确做法是把口径对齐然后打开，而不是关掉。

而真正需要补的是另一件事：在跑的 DTU 通道（WithOutServerChannelInitializer）连帧解码器都没有，报文由 WithOutServerHandler 直接 split(",") 解析。也就是说这条链路既没有长度字段、也没有分隔符分隔、也没有校验码——一个截断或错位的报文会安静地变成一条字段数目不对的记录。这是比”关 CRC”更靠前的风险：

建议（按性价比排序）：

  1. WithOutServerHandler 里补一条”字段数不符即丢弃并计数”的硬校验（改动最小）；
  2. bCheckCRCCode 对齐口径后灰度打开；MQTT 层统一 QoS 1 + 应用层 seq 连续性校验；
  3. 若 JT808/TCP 通道确定不再启用，把 ServerChannelInitializer / DispatchMsgHandler / EscapeUtils 一并清理，避免下一个人误判为现役链路。

二、rcloud-map：每天都在变的地图

2.1 数据模型：lanelet2

高精地图用的是自动驾驶领域标准的 lanelet2 模型。落到库里是 lanelet2_ 前缀的 7 张表（不是 6 张）：

层级 表 / 字段 含义
点 lanelet2_point lat / lon / ele（高程）
线 lanelet2_line 点数组，车道边界线
车道 lanelet2_lane left_line / center_line / right_line，含空载/满载限速、转向，以及 right_of_ways（路权ID数组）、regulatory_elements（锁定车道ID数组）两个字段
车道锁 lanelet2_lane_lock 类似的锁定关系（lane_relation_id + regulatory_elements 数组）
区域 lanelet2_area outer_line / inner_line / parking_spots / waiting_area
拓扑 lanelet2_lane_relation next_lane_ids —— 下一条车道
OSM 文件 lanelet2_osm_map 版本 + MinIO 上的 osm 路径 + 文件大小

两个容易写错的地方：

  1. regulatory_elements 不是一张表，它是 lanelet2_lane / lanelet2_lane_lock 上的 varchar 字段。路权同理，落在 lanelet2_lane.right_of_ways 字段上，Java 侧由 OSMRightOfWay 对象承载——“路权/锁定”是车道上的两个 ID 数组，不是独立的表。
  2. 说”四层”也不准：这 7 张表加 2 个字段一起构成 lanelet2 的要素图，真正驱动路径规划的是有向图那一层（lane_relation 的 next_lane_ids），而不是层级。

同库还有一批非 lanelet2 前缀的地图表：lane_details、lane_track、tif_map、three_dimension_map、electronic_fence（电子围栏）、poi_access、poi_connection、father_child_poi。

但它也是最容易出问题的地方，代码里有两个明显缺陷：

两个问题叠在一起：注释说”这里不锁定”，代码却自己 tryLock；而 tryLock 返回 false 时 finally 仍然会 unlock()——没持有锁的线程调用 unlock() 必然抛 IllegalMonitorStateException。OSMMapService 里这套 tryLock + 无条件 unlock 的模式一共出现 8 处（4 处 readLock + 4 处 writeLock），是模式化的写法问题，不是偶发。

三、rcloud-algorithm：JNI 调 C++

3.1 JNI 接入方式

用的是原生 JNI（不是 JNA），所以 JNI 模块里另建了一套 JNI* 镜像 DTO（JNIPointJNI、JNILoadPointJNIDTO…），字段顺序与 C++ 结构体强耦合。

三个风险：

  1. 路径硬编码 /home/rockai/lk/app/jni/libmodule.so，换机器必炸；
  2. catch (UnsatisfiedLinkError) 只打印不抛 —— 启动成功但真正调用时才 UnsatisfiedLinkError，问题被推迟到运行期；
  3. 无超时、无熔断 —— C++ 里一个死循环就能挂死整个 JNI 服务。

3.2 Reeds-Shepp 曲线用在哪

传入参数里有两个关键阈值：

Hybrid A* + Reeds-Shepp 是自动驾驶局部路径规划的经典组合：

  • Hybrid A*：考虑车辆运动学约束（最小转弯半径）的搜索算法；
  • Reeds-Shepp 曲线：允许前进+倒车切换的最短路径曲线，专门解决”如何把车倒进车位”；
  • Dubins 曲线：只允许前进的版本。

在这个系统里，它解决的是装载区/排土线内的精确对位——矿卡要倒到挖机铲斗下方、要倒到排土线边缘，误差要求厘米级。全局路径（哪条车道）由 A* 在 lanelet2 图上算，局部路径（怎么倒进去）交给 C++ 的 Hybrid A*。

“Java 做业务编排，C++ 做计算密集” —— 这个分工是对的。

3.3 性能设计：Redis 队列 + 串行消费

每秒只处理一个规划请求。这个吞吐对”每台车每次作业规划一次”的场景勉强够用，但如果几十台车同时进入装载区，队列会积压。

而且这里有个链式风险：JNI 无超时 → 每秒消费一个 → 一个请求 hang 住 → 整条队列永久阻塞。唯一的兜底是那个 31 秒过期的互斥位。

改进方案：

  1. JNI 调用放到独立线程池 + Future.get(timeout)，超时即放弃并标记失败；
  2. 消费端改成多线程（按 areaPoi 分片保证同区域串行）；
  3. System.load 改成从环境变量/配置读路径，且 UnsatisfiedLinkError 必须让启动失败（fail-fast）。

3.4 安全互斥：观察区 + 停止线

3.5 一个性能债：朴素 Dijkstra

矿区地图的车道数量级在几千到几万，O(V²) 是 10^8 级别。虽然结果缓存了（ROUTE_PLANNING 4h），但首次规划会很慢。换成优先队列（堆优化）能把 O(V²) 降到 O(E log V)，改动量不到 20 行。

四、三条线的共同特征

回头看这三块，能发现一些共性：

特征 表现
计算密集的都外置 几何融合 → C++ .so；局部路径 → C++ .so；Java 只做编排
状态都在内存 OSM 地图常驻 OSMMapContainerDTO；会话在 SessionManager；算法中间态在 Redis
协议/映射都配置化 base_agreement_info 表驱动协议分派；lanelet2 的 regulatory_element 驱动路权
容错靠重试而非事务 指令重发 30s×5；地图融合断点续传；JNI 靠 31s 互斥位兜底
半成品多 SyncFuture 死代码、TCPServer 注释、MqttMsgDecoder 空实现、WorkStateChangeApplyHander 只打日志不发送

最后一条值得警惕：这些半成品比缺失的功能更危险，因为它们看起来”已经实现了”，review 时容易被跳过，直到某个深夜出问题。
