露天矿山无人驾驶调度平台（四）：调度核心——1 秒一轮的派车循环是怎么跑起来的

发布于 2026-07-21 分类：技术, 2026, 智慧矿山, 架构设计 👁

关键词：集群任务调度 / Redis setNX / 幂等设计 / 二级缓存 / 生产者-消费者 / 状态机

这是全套系统最硬的一块。矿卡的状态报文秒级到达，每次到达都要在毫秒级内完成派车决策；同时还要保证多实例部署时同一个编组只被一个节点算一次。这篇先把这两条线拆清楚，再看它的实现细节。

一、三层看门狗线程模型

先明确一个容易搞混的前提：dispatch 里有两条互不相干的”周期性/触发式”链路。

链路 位置 触发方式 干什么
编组配置心跳 rcloud-dispatch-service（本节的看门狗线程） 1 秒一轮，每编组一个线程 同步编组 / 工作面 / 卸载区配置缓存
派车决策 rcloud-dispatch-processor MQ 报文到达即触发 校验 → 选点 → 调算法 → 下发（第二节）

前者不派车，后者不定时。之所以很多描述（包括这个类自己的 javadoc）会把两者混起来，是因为历史上它们确实在同一个线程里——DispatchGroupMainThread 的类注释至今还列着 9 项职责（刷新编组数据、更新矿卡/挖机/装载机实时状态、装载等待区扫描、排土等待区扫描、下发装载任务、下发卸载任务、下发驶入驶出进度），但方法体里只剩第 1 项：

flowchart TD

每个调度编组一个独立线程，这是个关键设计决策。好处：

  1. 故障隔离 —— 编组 A 的卡死不影响编组 B；
  2. 可独立调参 —— 大编组（车多）和小编组的扫描周期可以不一样；
  3. 可观测 —— 线程名带编组 ID（DispatchGroupThread-id-{groupId}），jstack 出来一眼看出哪个编组在卡。

代价是编组数量就是线程数，几十个编组还能接受，上百个就要重新设计了（下一节还有一处更隐蔽的代价）。

1.3 这套框架的两个代价

上面是它的好。但把 DispatchGroupManageThread 和 checkRegThreadId() 一起读，会发现两处没被注意的成本。

代价一：锁只锁住了”干活”，没锁住”起线程”。

DispatchGroupManageThread 里那行 clusterJobSyncService 是注释掉的（// ClusterJobSyncService clusterJobSyncService = ...），所以编组管理线程本身不参与集群注册——每个实例都会为所有编组各起一个 DispatchGroupMainThread：

真正拦重复的是 AbstractClusterJobThread 里的 setNX：抢不到的线程每秒 setIfAbsent + get 一次、continue，然后继续睡继续转。于是：

峰值线程数 = 实例数 × 编组数，而真正干活的只有”编组数”个。

3 个实例 × 40 个编组 = 120 个线程，其中 80 个纯空转、每个每秒两次 Redis 往返。编组规模上去以后这笔开销并不小。

代价二：同一台机器上部署多实例，会把编组线程”停死”。

checkRegThreadId() 只在注册 IP 与本机 IP 相同时才返回 threadId：

于是同机双实例（很常见的 HA 部署方式）会这样：

  1. 实例 A 的线程抢到注册，写入 IP, threadIdA；
  2. 实例 B 的线程 setRegIfAbsent 失败 → checkRegThreadId() 发现 IP 相同但 threadId 是 A → 走 toStop() → B 的线程永久停止（scheduleThreadToStop = true，不再复位）；
  3. Monitor → DispatchGroupManageThread 每 10 秒发现该线程 TERMINATED 就又 new 一个重建；
  4. 新线程 1 秒后再次判定”IP 同、不是我的 id” → 再次 toStop()。

结果就是”建了就停“的无尽循环。跨机部署不会触发（IP 不同走 continue，线程只空转不自杀），所以这个问题在单机多实例的测试环境或小规模现场最容易踩到，而且症状很隐蔽——jstack 里只会看到编组线程反复出现又消失。

修法很直接：toStop() 只应在”明确确认自己不该存在”时调用；对”IP 相同但 threadId 不同”这种同机新旧实例交替的场景，正确的动作是本轮跳过 + 不自杀，交给 TTL 自然过期。

以装载任务为例（LoadTaskService.doLoadTaskSendScaner()）：

第 ① 步的”地图版本一致”校验值得单独说。矿卡本地存了一份地图，云端也有一份。如果云端更新了地图而车端没更新，规划出来的路径车端可能执行不了（车道 ID 对不上）。所以在派车前强制校验版本，不一致就丢弃这辆车——这是无人驾驶系统特有的、传统调度系统不会有的校验。

2.1 换个视角看这 8 步：它们是 6~8 次串行同步 HTTP

上面这 8 步在工程语义上是”校验 → 选点 → 算路 → 下发”，但在性能语义上是另一回事——除第 ③ 步读 Redis 外，其余全是跨服务同步调用：

步 调用 类型
① mapFeignService.getMapMainVersion() 等 HTTP
② dispatchRegionFeignService.getRegionDetailByRegionPOICode() HTTP（内含 DB/Redis）
③ redisRuntimeTruckService.getLoadTaskTruckIdList() Redis
④ loadJobTaskFeignService.getDispatchExcavatorInfoByTruckId() HTTP（查库，较重）
⑤ algorithmFeignService.getDispatchByLoad() HTTP（算法 + 可能触发 JNI 算路，最重）
⑥ mapFeignService.getWaitingPointByPOICode() HTTP
⑦ truckProtocolFeignService.sendLoadTask() HTTP 下发
⑧ redisRuntimeTruckService.addTruckIdToLoadTaskList() Redis

8 步串行、无并行、无缓存、无熔断，单条端到端 300400ms。再乘以消息扇出系数（一条车端数据会被复制到 34 个 topic），这就是第七篇里”约 20 倍调用放大”的来源——派车主链路的性能问题，根源在这 8 步的形态，而不在某个具体服务慢。

换个写法能省多少：第 ①②④⑥ 步读的都是低频变更的配置类数据（区域、地图 POI、编组、可调度挖机），完全可以进本地 Caffeine + 变更广播失效，把 8 次 HTTP 压到 1~2 次（只剩 ⑤ 算路与 ⑦ 下发）。具体方案见第八篇第 3.3 节。

三、幂等：为什么不用分布式锁

直觉上，”防止同一辆车被重复派单”应该用分布式锁。但这个项目主要靠 Redis 集合：

对比一下两种方案：

方案 优点 缺点
分布式锁（lock4j） 语义严格，临界区绝对互斥 1 秒一轮的场景下，加锁/释放是纯开销；锁超时可能误放行
Redis 集合幂等 无锁、无阻塞、天然幂等；集合本身就是”已下发清单”，可观测 存在极小概率的 check-then-act 竞态

项目里 @Lock4j 在 dispatch 只用了 4 处（DepartureAndParkService:152 发车请求、DispatchGroupBackgroundService:113、以及两个排土线明细 DumpLineService:631 与 NewDumpLineService:640），核心派车链路一个锁都没用。

顺便一提，后两处是”新旧两份实现”（DumpLineService / NewDumpLineService），用的锁 key 完全相同（DUMPLINE_REALTIME_DETAIL_KEY_PREFIX + dumpLinePOICode）——同一条排土线的实时明细被新旧两套代码共享一个锁命名空间，这本身就是债务。（全项目 @Lock4j 共 17 处，equipment 一个服务就占了 9 处。）

这个选择是对的：1 秒周期 × 数百辆车，如果每辆车每个周期都抢锁，Redis 的 QPS 会翻好几倍，而且锁的开销比业务逻辑本身还大。

但 check-then-act 的竞态确实存在：两个线程同时 contains 都返回 false，会重复下发。缓解手段是让第 ⑦⑧ 步尽量靠近，或者用 SADD 的返回值做判断（Redis 单线程，SADD 返回 1 表示新增成功）：

这是典型的用 Redis 原子操作替代分布式锁的技巧，值得记住。

四、二级缓存：Caffeine + Redis

4.1 Caffeine 本地缓存

DispatchGroupService 里定义了 9 个缓存，覆盖编组相关的各种映射：

缓存 内容
装载机 ↔ 卸载区 某装载机可以去哪些卸载区
排土线 POI ↔ 卸载区 排土点归属
装载点 POI ↔ 挖机 装载点归属
挖机 ↔ 装载区 / 引导点 POI 反向映射
编组 ID ↔ 编组名称 名称冗余
设备 + 类型 ↔ 编组 ID 设备归属

配置风格基本统一（8 个是这样，第 9 个有单位 bug，见 4.4）：

没有失效广播，完全靠 TTL 自愈。这意味着多实例之间最长有 1 分钟的数据不一致窗口——运维在后台改了编组配置，某些实例可能要 1 分钟后才生效。

对调度系统来说，1 分钟的不一致可以接受吗？取决于改的是什么：

  • 改编组名称 → 无所谓
  • 改”某挖机归属哪个装载点” → 1 分钟内可能把车派到错误的装载点

建议：关键配置变更时，通过 Redis Pub/Sub 广播一个”缓存失效”事件，各实例收到后 cache.invalidateAll()。成本很低（几十行），但能把这个窗口从 1 分钟压到毫秒级。

4.2 Redis 缓存

Redis 这边的 key 设计规范得多，采用 dispatchgroup:{域}:{子域}:{id} 的分层命名：

类别 Key 模式 过期
车辆/设备实时状态 REALTIME_* 10s（REALTIME_EXPIRE_SECOND = 10）
急停按钮状态 EMERGENCY_STOP_BUTTON_STATUS_* 2s
编组配置 Hash dispatchgroup:config: + field(WORKINGFACE/DUMPREGION/TRUCK/…) 1h（DISPATCH_GROUP_INFO_EXPIRE_SECOND = 3600）
区域配置 dispatchgroup:config:region:{id} —
已下发队列（幂等） dispatchgroup:runtime:sendloadtruck / senddumptruck / sendparktruck / … 24h
装载点/车辆状态 LOADPOINT_REALTIME_* / DISPATCH_TRUCK_STATUS_* 24h
排土线实时明细 dispatchgroup:realtime:detail:dumpline:{id} 7d
收车/发车请求 dispatchgroup:runtime:park:inprogress: / dispatchgroup:departure:request: —
分布式锁 LOAD_TASK_SEND: / DUMP_TASK_SEND: / EXCAVATOR_WAITING_TRUCKS: —

2s / 10s / 1h / 24h / 7d 五档 —— 按数据变化频率设 TTL，而且把”急停按钮状态”这种安全相关数据压到 2 秒，这点做得专业。（一个自然的对照：本地 Caffeine 那一层却是”一刀切 1 分钟”，两层的粒度意识并不一致，见 4.4。）

4.3 一个隐蔽的坑：同一个类有 4 份，参数还不一样

MapFeignService 这个名字，在整个仓库群里出现了 4 次——rcloud-algorithm-service、rcloud-dispatch-processor、rcloud-dispatch-service、rcloud-equipment-service 各一份。其中 dispatch 内部那两份的缓存配置不一致：

10 分钟 vs 30 秒，差 20 倍。也就是说同一个”POI 编码 → 名称”的映射，processor 侧可能拿着 10 分钟前的值算派车，service 侧 30 秒就刷新了——而这两侧读的其实是同一份地图数据。（顺带一提，service/equipment 那两份的常量名拼成了 MAP_CHACHE_PERIOD_SECONDS，CHACHE——拼写漂移也是复制式复用的典型痕迹。）

同一份逻辑的两个副本，参数不同。这类问题在”复制式复用”下必然出现，且极难发现。

4.4 一个真实的单位 bug：10 分钟变成了 10 秒

DispatchGroupService 里 9 个 Caffeine 缓存都用同一个常量类 DispatchGroupCaffineCacheConstant。8 个是这样的：

但第 130 行那个单位写成了秒：

常量名是 ..._TIMEOUT_MINUTE、值 10，按名字应当是 10 分钟，实际生效 10 秒——“挖机 ↔ 引导点 POI”这个映射的缓存存活时间比其余缓存短 60 倍。表现就是这一项恒定高频回查（命中率极低），而因为是 Caffeine 自动过期，不会有任何日志或异常，只会体现为”这块查询 QPS 莫名偏高”。只靠读常量类看不出来，必须把 expireAfterWrite 的第二个参数一起看。

六、小结：这套调度代码的功力如何

做得好的地方：

项 评价
AbstractClusterJobThread 用 setNX + 归属判定 + 续期 + 下一跳，自己实现了集群任务调度，比无脑上分布式锁高明
三层看门狗 线程挂了自动复活，编组增删动态生效，运维不用重启
幂等用 Redis 集合 高频链路避开了锁开销，选择正确
日志异步落库 主链路零 DB 写，方向正确
地图版本校验 无人驾驶场景特有的必要校验，考虑到了
决策与配置分离 派车走 MQ 事件驱动、配置走 1 秒心跳，两条链路互不阻塞，这个边界划得对

需要改的地方：

项 风险 改法
doWork() 异常仍推进 nextTriggerTime 静默跳过一轮 try-catch 后决定是否回退
同机双实例会把自己的编组线程停死 “建了就停”循环，jstack 看不出 toStop() 不应对”同 IP 不同 threadId”生效，改为跳过等人接管
锁只锁干活、没锁起线程 线程数 = 实例数 × 编组数，多数空转 编组管理线程也纳入集群注册，或按编组做一致性哈希分片
push() 用 add() 队列满时主链路抛异常 改 offer() + 监控计数
批量落库被注释 DB 写放大 恢复攒批逻辑
Caffeine 无失效广播 分钟级不一致 Redis Pub/Sub 广播失效
TimeUnit.SECONDS 配 ..._TIMEOUT_MINUTE 常量 该缓存 10 秒即失效，QPS 异常 改回 TimeUnit.MINUTES
MapFeignService 4 份、TTL 10min vs 30s 两侧读同一份地图数据却不同步 收敛到 common，统一 TTL
幂等 check-then-act 竞态 极小概率重复下发 用 SADD 返回值判定
巨类 TemporaryDispatchService 2137 行 不可维护 按 TaskNodeEnum 拆成策略类
