露天矿山无人驾驶调度平台（三）：服务治理——网关鉴权、Feign 拓扑与自研健康巡检

发布于 2026-07-18 分类：技术, 2026, 智慧矿山, 服务治理 👁

关键词：Spring Cloud Gateway / JWT / RBAC / Feign / Nacos / 健康检查 / 可观测性

服务治理是这套系统里最有”人味”的部分：有设计得很讲究的自研健康巡检平台，也有裸奔的内网调用。这篇把好的和糟的一起摊开讲。

一、网关：一个 Filter 干完所有鉴权

rcloud-web-interface 是标准的 Spring Cloud Gateway，核心逻辑集中在 SecurityAccessControlGatewayFilterFactory。

1.1 鉴权流程

flowchart TD
    IN["请求进入"] --> W{"1. 白名单匹配"}
    W -->|是| PASS["放行"]
    W -->|否| JWT{"2. JWT 校验・java-jwt"}
    JWT -->|无效| R401["401"]
    JWT -->|临期| REN["自动续期・新 token 写回响应头"]
    JWT -->|有效| LIST["3. 拉取该用户可访问的 url + method 列表"]
    REN --> LIST
    LIST --> CHK{"4. 当前请求的 url + method 在列表内"}
    CHK -->|否| R403["403"]
    CHK -->|是| HDR["5. 用户信息写入 Request Header・userId / userName"]

JWT 会话存在 Redis：JwtUtils.getRedisKey(userId, ipAddress) —— key 里带 IP，意味着同一用户换网络就要重新登录。这个设计在矿山现场（车端/驾驶舱 IP 相对固定）可以接受，但对 Web 管理端不太友好。

Token 自动续期是个贴心设计：把新 token 回写到响应头，前端无感知刷新。但要注意，如果前端没处理响应头里的新 token，续期就白做了——这里需要和前端约定好 header 名。

SysPermission 表里有个很有意思的字段：

这种设计的好处是：同一套 RBAC 能同时服务 Web 管理端、车端 HMI、驾驶舱、监控大屏 7 类终端，每类终端看到的权限集不同。相比常见的”只做菜单权限”，这套做到了接口级，安全性高一档。

二、用户上下文：裸 ThreadLocal 的隐患

2.1 传递链路

flowchart TD
    GW["网关・解析 JWT"] -->|"写 header：userId / userName"| INT["下游服务・LoginUserInfoInterceptor"]
    INT --> A["从 header 取值 → LoginUserUtils.set 存入 ThreadLocal"]
    INT --> B["Feign 出向・LoginUserInfoFeignInterceptor"]
    B --> C["从 ThreadLocal 取 → 写入 Feign 请求头 → 下一跳服务"]
    C --> RM["请求结束 afterCompletion → LoginUserUtils.remove 防内存泄漏"]

2.2 三个问题

问题一：没有 TTL，异步场景静默丢失。

全库搜 TransmittableThreadLocal / TtlMDC 零命中。而 rcloud-system-health-service 里大量使用 CompletableFuture 并行探测，rcloud-dispatch 里有 Executors.newFixedThreadPool(5) 和多个自建 Thread——这些线程里 LoginUserUtils.get() 一律返回 null。

这里要补一句容易想当然的话：null 并不会体现为”操作人字段是空”。因为 MyMetaObjectHandler 压根没读 LoginUserUtils，它把 createBy/updateBy 写死成了字符串：

（rcloud-system-service 那份更省事，createBy 都不填。）所以真实症状不是”异步时丢成 null”，而是所有自动填充的记录里操作人恒为 "auto"，谁也追溯不到——埋点在主线程也没用，因为它根本没接。裸 ThreadLocal 的问题依然存在（任何自己取用户上下文的代码在异步线程里都会拿到 null），但别把它和 createBy 混为一谈。

顺带一提：MyMetaObjectHandler 在 5 个服务里各有一份副本，而且并不一致——dispatch / eam / equipment / exchange 写 isDelete = "0"（字符串），rcloud-system-service 写 isDelete = 2（整数）。配合 YesOrNoEnum（1=是 / 2=否）和 DispatchGroupMainThread 里用 YesOrNoEnum.YES 判”已删除”，等于全项目对”未删除”存在 0 和 2 两种取值。这是”复制式复用”最典型的下场。

问题二：服务间调用无签名，内网裸奔可提权。

网关验了 JWT，但服务之间的 Feign 调用只传了两个明文 header。只要能访问内网，任何人都可以构造：

直接以管理员身份调用任意内部接口。这在矿山现场（可能与办公网/运营商网络打通）是有实际风险的。

改进方案（三选一，推荐 1+3 组合）：

  1. 服务间调用加内部签名：Feign 拦截器用共享密钥对 timestamp + appName 做 HMAC，服务端 Filter 校验；
  2. 网络隔离：服务间通信走独立网段，不对外暴露；
  3. 网关剥离外部 header：网关注入 X-Internal-User，并强制覆盖客户端传入的 userId/userName，外部无法伪造。

问题三：同一个拦截器被复制了 7 份。

LoginUserInfoFeignInterceptor 在 system-service / dispatch-service / dispatch-processor / equipment-service / eam-service / largescreen-service / keda-service 各有一份，代码完全相同（注意没有一个叫 dispatch 的模块，也没有 web-interface 那份）。同理 LoginUserInfoConfig、MyMetaObjectHandler、Lock4jConfig、DistanceUtils、RegionUtil 也都是复制品；CoordinateUtil 在 dispatch-service / map-service / keda-service 还各有一份。

这类”复制式复用”是微服务拆分时最常见的债务——本该把这些横切关注点收进 rcloud-common 的 starter 里。而且副本一旦分散就会各自漂移：MyMetaObjectHandler 的 isDelete 取值分裂（"0" vs 2）、MapFeignService 的缓存 TTL 从 30 秒变成 10 分钟，都是这么来的。

循环依赖是被”放行”而不是被治理掉的。 这个开关是 Spring Boot 2.6 之后才需要显式打开的（默认禁止循环引用），打开它意味着：Bean 初始化顺序变得不确定，某些场景下会拿到未初始化完成的对象。

解法：把双方共享的”读模型”下沉。比如 equipment 需要的调度区域信息，通过 MQ 事件同步一份本地只读缓存，而不是实时 Feign 回查 dispatch。

3.4 Feign 治理缺失清单

治理项 现状
超时 只有 dispatch 显式设了值：Request.Options(1, MINUTES, 1, MINUTES, true)；web-interface 虽也定义了 FeignConfig，但用的是 new Request.Options() 默认（10s 连接 / 60s 读），等于没配；其余服务全默认。1 分钟读超时对 MQ 消费线程过长
重试 无（依赖 Ribbon/Spring Cloud LoadBalancer 默认）
熔断降级 零。全库搜 Sentinel 无命中，无一个 FallbackFactory
日志级别 未配置，排查问题时看不到请求/响应
负载均衡 spring-cloud-loadbalancer，默认轮询

没有熔断是最大的风险：dispatch → equipment → RocketMQ → exchange 这条链路上，只要 equipment 慢了，做派车决策的 MQ 消费线程就会被拖住（注意不是”1 秒调度线程”——那条只刷缓存，这个区别见第一篇），进而所有车的派车延迟。

这个”拖住”是可以量化的。派车决策在 processor 里串行走 68 次 Feign（区域、地图、点检、可调度挖机、算法、等待点、下发），单条约 300400ms；而消费线程池只有 20~60 个线程、且被 10 个 topic 共享。于是：

  • 任一下游从 50ms 变慢到 500ms，单条决策耗时翻到 ~3s，线程池瞬间打满；
  • 消费能力从 ~100 msg/s 掉到十几 msg/s，MQ 开始积压；
  • 积压超过 5 秒后，isRealTimeData() 把这些数据判为过期直接丢弃——不是”慢一点”，而是”任务漏下发”。

完整的推导过程和 100 台矿卡的可行性判定见第七篇；熔断的具体配置建议见第八篇。

建议最小改动方案：

  1. 统一 Feign 超时（连接 2s / 读 5s），通过 spring.cloud.openfeign.client.config.default 配置；
  2. 引入 Sentinel 或 Resilience4j，对 rcloud-equipment 这类关键下游配置熔断 + 快速失败；
  3. 关键写操作（如 sendLoadTask）配置 fallback 落”待补偿”记录，由定时任务重投。

四、自研健康巡检平台：全项目最有特色的基建

这是我认为整个系统里最值得写进简历的部分。

4.1 架构：一个”本该是 SDK”的设计

先纠正一个容易产生的误解。看模块名 rcloud-system-health-client 会以为它是”埋进各业务服务的客户端 SDK”，但它并没有被任何模块依赖（全仓按 artifactId 搜索只命中它自己的 pom）。真实形态是——

这个”复制 + 各自裁剪”的形态带来两个直接后果：

  1. 巡检覆盖度取决于别人抄得全不全。equipment-ext-trafficlight 只抄了 /health/heartbeat，等于它上面的 RocketMQ / Redis / DB 一律不在巡检范围内；而 dispatch-service 抄了 mysql+redis 却没抄 minio，尽管它也读地图文件。巡检结论”全部正常”的可信区间，等于所有服务里抄得最少的那一份。
  2. rcloud-system-health-client 成了一个死模块——它和 health-service 的 spring.application.name 都叫 rcloud-system-health（见 4.3），而它自己只有 heartbeat。它更像是”当初想做成 starter、最后没做”的残留。

顺带一提，文中若看到 /health/mqtt，那是笔误：全仓只有 /health/mqttclient。

改进方向：把 HealthController + 各组件探测逻辑收进 health-client 做成真正的 starter（按 classpath 自动装配：有 Redis 才暴露 redis 探测、有 MinIO 才暴露 minio 探测），各服务一行依赖接入。这一步同时解决了”覆盖不均”和”复制漂移”两个问题。

4.2 设计亮点

(1) 两级并行。服务间用线程池并行，服务内用 CompletableFuture 并行——十几个服务 × 若干类组件的巡检能在秒级完成。

(2) 防重入。AtomicBoolean isChecking 保证上一轮没跑完不会启动下一轮，避免巡检本身把系统压垮。

(3) 探测的是”能用”而不是”能连”。比如 MySQL 不是 SELECT 1，而是真的做一次 insert/delete 探测（MYSQL_INSERT_ERROR 这个枚举就是证据）；RocketMQ 检查的是 topic 是否真的创建（ROCKETMQ_TOPIC_UNCREATED）。

这一点比 Spring Boot Actuator 的 HealthIndicator 做得更实——Actuator 的 DataSource 健康检查默认就是 SELECT 1，能连上但磁盘满了、只读了、权限被回收了都发现不了。

(4) 覆盖了矿山场景特有的组件。TDengine（时序库）、MinIO（地图文件）、EMQX（MQTT Broker）——这些都不是标准 Actuator 会管的。

4.3 一个待确认的问题

health-client 和 health-service 的 spring.application.name 都叫 rcloud-system-health：

而且 health-client 的 pom 没有被任何业务服务显式依赖（这也是 4.1 里”各服务手抄 HealthController”的佐证）。如果不处理，client 和 service 会注册成同一个服务的两个实例，Nacos 上会出现同名实例互相干扰——巡检服务端自己也会被自己当成被巡检对象。

五、可观测性：目前是空白

能力 现状
链路追踪 自研 X-Trace-Id，有 bug 未生效；无 SkyWalking / Zipkin
指标监控 无 Micrometer / Prometheus
日志 各服务独立，无集中收集（未见 ELK/Loki 配置）
熔断限流 无 Sentinel
定时任务 xxl-job-core 只引在 rcloud-dispatch-service（XxlJobConfig 也在这个模块），而 rcloud-equipment-ext-transportationsales 的 bootstrap.yml 里有一段被注释掉的 xxl.job 配置；全项目无一个 @XxlJob 处理器 —— 两处半成品，分散在两个仓库

对于一个有 20 个服务、决策链路横跨 4~5 跳的系统，没有链路追踪是排查问题的最大障碍。
