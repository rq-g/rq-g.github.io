MQ消息堆积排查与治理——从定位到根治的高并发实战

发布于 2026-07-08 分类：技术, 2026, 消息队列, 高并发 👁

前言

先说一次印象深刻的线上事故。

智慧矿山无人驾驶项目，露天矿区部署了 80 多台矿卡和辅助设备，每台设备每秒上报一次 GPS + 状态数据。某个周一早班，所有设备同时上电开机，再叠加网络恢复后设备本地缓存的离线数据批量补传，瞬时 TPS 从常态的 800 直接干到 26000。

两分钟后，监控开始报警：vehicle-gps Topic 堆积量突破 300 万，Kafka 磁盘水位 20 分钟内从 42% 冲到 88%，消费端 CPU 打到 95%，业务侧的表现是——调度大屏上的矿卡位置全部停在 10 分钟前。

那一刻值班群里最常说的一句话是：”赶紧加消费者！” 但我们加了 3 个实例后，堆积曲线基本没动。为什么？因为 Topic 只有 8 个分区，消费者组里有 8 个以上实例时，多出来的实例是空转的，一个分区只能被组内的一个消费者消费。

消息堆积这事，怕的不是堆积本身，而是只会”加机器”这一招。这篇文章从定位、根因、应急、根治四个层次，把堆积问题讲透。

一、本质：一句话 + 一张水位表

消息堆积的本质就是一句话：消费速度 < 生产速度。

但同样是堆积，严重程度和处置方式天差地别，先建立水位分级：

分级 堆积量 / 延迟 业务影响 处置策略
L0 正常 堆积 < 1 万，延迟 < 1s 无感知 无需处理，观察即可
L1 轻微 堆积 1 万 ~ 50 万，延迟 < 1min 部分异步通知延迟 排查慢点，工作日修复
L2 严重 堆积 50 万 ~ 500 万，延迟 1~30min 业务数据可见延迟，对账差异 立即扩容 + 降级，当天根治
L3 故障 堆积 > 500 万 或 磁盘 > 85% 磁盘写满导致集群只读、全线故障 紧急止损，可牺牲非核心消息

关键认知：MQ 不是无限大的蓄水池。RocketMQ 默认消息保留 72h，Kafka 默认 7 天，堆积量一旦突破磁盘容量，Broker 会变只读甚至宕机，这时候丢的就不只是消息，是整个集群。

二、第一步：5 分钟快速定位堆积类型

不要上来就扩容，先用 4 个指标判断”慢在哪里”：

指标 怎么看 说明
生产 TPS 监控面板 / kafka-producer-perf / RocketMQ Console 判断是”生产突增”还是”消费变慢”
消费 TPS 消费端埋点 / consumerProgress 与生产 TPS 对比，差值就是堆积增长率
消费者在线数 consumerProgress 的 clientIP 数量 有没有实例掉线/GC 卡死
单条耗时 P99 消费端 APM（SkyWalking / Arthas trace） 判断是”每条都慢”还是”个别卡死”

判断树：

最有效的一招：直接上 Arthas 看消费线程在干什么。

如果是”全部变慢”，大概率是慢 SQL 或外部 RPC；如果是”个别分区不动”，大概率是单条消息把线程卡死了。

三、四种典型堆积场景与根治方案

场景一：消费逻辑太重，同步调用拖垮吞吐

现象：单条消息处理耗时 200ms+，消费 TPS 上不去。

根治方案：消费逻辑”瘦身”——只做必须同步做的事，其余异步化/批量化。

批量写库要配 MySQL 参数，否则 foreach 批量插入只是”看起来批了”：

优化手段 吞吐提升 复杂度 备注
消费线程池加大 2~3 倍 低 受 CPU/DB 连接限制
批量消费 + 批量落库 5~15 倍 中 效果最显著，优先做
非核心逻辑异步化 2~5 倍 中 需单独线程池 + 监控
多级拆解（Topic 分级） 取决于拆分 高 核心/非核心分 Topic 隔离

场景二：失败消息无限重试，一条脏数据堵死整个队列

现象：消费 TPS 看起来不低，但堆积持续上涨，日志里刷同一条消息的异常。

根因：某条消息因为字段格式错误、反序列化失败、依赖数据缺失，永远处理不成功，被无限重投。RocketMQ 默认重试 16 次（间隔 10s → 2h，总计约 4.5 小时），Kafka 若手动 seek 回退则会立刻重试。

经验值：业务类错误（参数非法、数据不存在）1~3 次即可转死信；依赖类错误（DB 抖动、RPC 超时）可以多给几次，因为重试大概率能自愈。

场景三：流量突增，消费并行度不足

这是最容易踩的坑——并行度由 Topic 的物理结构决定，不是由消费者实例数决定。

中间件 并行度上限 扩容无效的原因
Kafka Partition 数 一个 Partition 只能被组内一个 Consumer 消费，多余实例 idle
RocketMQ Topic 的 Queue 数（ReadQueueNums） 同理，Consumer 数 > Queue 数时空转
RabbitMQ 受 concurrency 和队列数限制 单队列可多线程，但顺序性会丢失

根治方案：

  1. 提前规划分区数：按 分区数 = 峰值TPS / 单分区消费能力 估算，再乘 1.5 倍冗余。Kafka 分区数只能增不能减，宁可多留；
  2. 紧急扩容分区：kafka-topics.sh --alter --partitions 64，注意这会导致 Key 路由变化（影响顺序性），且需要重启消费者触发 Rebalance；
  3. RocketMQ：调大 writeQueueNums/readQueueNums，或新建高分区 Topic 做迁移；
  4. 临时分流：把堆积消息转储到临时高分区 Topic，用独立的消费者组快速消费（见”应急”一节）。

场景四：消费线程阻塞 / 打满 —— 最隐蔽的一类

现象：消费者进程活着、连接正常，但就是不拉消息。

阻塞原因 线程状态 排查手段
慢 SQL / 锁等待 RUNNABLE（socket read） jstack 看 SocketInputStream.read
synchronized / 分布式锁竞争 BLOCKED thread --state BLOCKED
wait() / CountDownLatch 无超时 WAITING thread --state WAITING
HTTP 调用无超时 RUNNABLE 抓栈看 HttpClient
消费线程池队列无界 + 打满 线程池拒绝/OOM 看线程池活跃数和队列大小
Kafka 频繁 Rebalance 消费暂停 看 rebalance 日志、session.timeout.ms

补充场景：Kafka 反复 Rebalance

根因与参数：

参数 默认值 说明
max.poll.interval.ms 5min 两次 poll 间隔超时则踢出组，消费慢时误伤
session.timeout.ms 45s（新版 10s） 心跳超时

处理：批量处理耗时接近 max.poll.interval.ms 时，调大 max.poll.interval.ms 或减小 max.poll.records，二选一。我更推荐减小 max.poll.records——保持消费者”活着”比一次多拉点更重要。

四、应急止血：堆积已经爆了怎么办

核心原则：先止血恢复业务，再根治问题。止血手段可以有损，但必须可控、可追溯。

手段 适用场景 风险 操作要点
扩容消费者 并行度未满 低 先确认分区/队列数是否还有余量，否则无效
临时扩分区/队列 Kafka 分区不足 中 影响 Key 顺序性，业务低峰操作
调大批量拉取 单条开销小 低 max.poll.records / pullBatchSize 调大
消费逻辑降级 消费逻辑重 中 临时关闭非核心分支（推送、统计）
堆积消息转储 堆积巨大且需快速恢复 中 见下方”临时队列方案”
跳过脏消息 脏数据阻塞 高 必须先备份，再跳过
清空队列 磁盘告急 极高 最后手段，需业务方书面确认

临时队列转储方案（推荐）

⚠️ 绝对禁止的操作：直接在控制台点”清空队列”或删除队列。我见过有人清空后才发现里面是未对账的支付消息，最后靠数据库 binlog 一点点补回来的，代价惨重。任何删除动作前，先把消息 dump 到文件或备份 Topic。

五、架构层面：让堆积不再发生

5.1 监控告警（没有监控 = 裸奔）

告警项 阈值建议 级别
消息堆积量 > 10 万 持续 5min 警告
消息堆积量 > 100 万 或持续增长 30min 严重
消费延迟（消息产生到消费的时间差） > 60s 警告
Broker 磁盘使用率 > 75% 警告
Broker 磁盘使用率 > 85% 严重
死信队列数量 > 0 警告
消费失败率 > 1% 持续 2min 严重
消费者组在线实例数 少于期望值 严重

“堆积量”不如”消费延迟”直观。100 万堆积对一个日处理 10 亿条的日志 Topic 来说是常态，但对一个订单 Topic 就是 P0 故障。建议用**消息年龄（message age）**做主指标，堆积量做辅助。

5.2 Topic 分级隔离

核心原则：不要让日志流量冲垮业务消息。 三类消息分 Topic 甚至分集群，日志 Topic 堆积 1000 万也不影响调度指令。

5.3 消费端硬性规范（写进团队 Code Review 清单）

  1. 所有外部调用（HTTP / RPC / DB）必须设置超时，且超时总和 < 消费超时时间；
  2. 禁止在消费方法里 wait()、sleep()、使用无超时的 CountDownLatch；
  3. 消费线程池必须有界队列 + 拒绝策略 + 监控打点；
  4. 单条消息处理耗时 P99 目标 < 50ms（业务类）/ < 10ms（日志类）；
  5. 消费逻辑必须幂等（扩容、重试、Rebalance 都会导致重复消费）；
  6. 大对象（> 100KB）禁止直接放 MQ，走对象存储 + 消息传引用。

5.4 容量规划与压测

上线前必须做压测：用影子 Topic 模拟 3 倍峰值流量，验证消费能力和磁盘水位。压测不做的后果就是”上线即堆积”。

堆积应急的标准动作：先止血，再找根因

堆积告警拉响后的第一个小时决定损失大小，应急必须按”止血优先”的顺序执行，顺序错了会火上浇油。第一步，判断堆积趋势而不是绝对量：堆积 50 万且每分钟消 5000 条是在消化，堆积 10 万且每分钟涨 2 万是灾难进行时——趋势决定要不要立刻升级响应。第二步，扩容消费能力：加消费者实例（注意 Kafka 的消费者数超过分区数后无效，先扩分区）或临时跳过非核心处理逻辑（只解析消息头，业务校验后置）。第三步，识别并摘除毒消息：如果堆积是某条反复失败的消息卡住消费线程（无重试上限的消费者），定位后把它扔进死信队列让主流恢复——这是”一条消息拖垮整条管道”的典型场景，消费逻辑必须设重试上限的原因就在这。第四步，降级保护下游：堆积消化时消费速率翻倍，下游数据库可能被冲垮，先给下游加限流或开启消费端的速率限制（ Consumer 流控），别让止血动作本身变成新的故障。第五步，复盘时再根治：根因（慢 SQL、第三方超时、分区倾斜）留在事后分析，应急阶段的一切动作只围绕”恢复流动”四个字。把这套顺序写进值班手册并演练过，堆积事故的恢复时间能从小时级压到分钟级。

六、常见误区（这些坑我都踩过）

误区 真相
❌ 堆积了就加消费者实例 Kafka 分区数是硬上限，超出实例 100% 空转
❌ 分区数越多越好 分区过多导致文件句柄暴涨、Rebalance 变慢、ZK/KRaft 元数据膨胀。单个 Broker 建议分区数 < 4000
❌ 消费做批量就行，不用幂等 扩容、Rebalance、手动重投都会导致重复，幂等是必选项
❌ 只要消费成功就行，不监控死信 死信里往往藏着最真实的业务 bug，不监控等于把 bug 埋起来
❌ 堆积了就删消息 删除前必须确认业务影响 + 备份，否则数据不可逆丢失
❌ 消费端无限重试保证不丢 无限重试会把正常消息一起堵死，必须有重试上限 + 死信
❌ 消费慢就加大线程池 瓶颈常在 DB 连接池或下游接口，加大线程只会把下游打挂

堆积根因的四象限定位法

实战中堆积的根因千变万化，但用”生产侧/消费侧 × 突发/渐进”四象限能快速收敛。象限一：生产突发（生产速率骤增）——上游大促、批量任务误触发、消息风暴（某个事件被循环放大）。判据：生产速率曲线突刺。治理：生产端限流、修正上游任务。象限二：消费渐进变慢（消费能力缓慢劣化）——最隐蔽也最常见：数据库慢查询逐渐变多、下游接口悄悄变慢、消费者实例因发布引入了性能回退。判据：单条消息处理耗时曲线缓升。治理：沿消费链路做耗时分析，找到变慢的那一环。象限三：消费骤停（消费能力瞬间归零）——消费者全部宕机、频繁再均衡（Rebalance 风暴）、认证过期。判据：消费速率曲线断崖。治理：恢复实例、修 Rebalance 配置（max.poll.interval.ms 太小导致长处理任务被误判死亡是经典根因）。象限四：结构性倾斜（部分分区堆积）——分区数不够或消息键分布不均，个别分区成为热点。判据：按分区看堆积量，离散度极大。治理：改分区数（注意 Key 路由变化）或改消息键设计。四象限的第一步永远是画两条曲线：生产速率和消费速率——它们的相对关系直接告诉你根因在哪个象限，比逐个组件猜快得多。

七、总结

处理消息堆积，思路可以浓缩成三句话：

  1. 定位看对比——生产 TPS vs 消费 TPS，全部变慢 vs 部分卡住，一眼分出大方向；
  2. 止血要果断——扩容无效就转储，转储不行就降级，优先恢复实时链路，历史数据离线补；
  3. 根治靠结构——批量化提吞吐、异步化削逻辑、拆分 Topic 做隔离、超时+幂等做兜底、监控告警早发现。

最后，“加机器”永远是最容易想到、也最容易失效的办法。真正有效的是提前算清楚并行度上限、提前压测、提前分级隔离——把功夫花在没出事的时候。
