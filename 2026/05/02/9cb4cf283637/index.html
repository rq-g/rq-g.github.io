场景33：MySQL索引原理

考察点：B+树索引、索引类型、索引优化

核心概念：

  • B+树：平衡树，叶子节点存储数据，非叶子节点存储索引
  • 聚簇索引：主键索引，叶子节点存储整行数据
  • 非聚簇索引：二级索引，叶子节点存储主键值
  • 覆盖索引：索引包含查询所需的所有列

B+树结构：

索引优化策略：

  1. 最左前缀原则：索引按最左列开始匹配
  2. 避免索引失效：不要在索引列上做函数运算
  3. 选择合适的索引类型：主键用聚簇索引，频繁查询的列用非聚簇索引
  4. 覆盖索引：尽量让查询只使用索引，不需要回表

答：

面试官：”MySQL的索引是怎么实现的？为什么用B+树？”

我：”MySQL的索引主要是用B+树来实现的，特别是InnoDB引擎。

B+树是一种平衡树，它的特点是：首先，所有的数据都存储在叶子节点上，非叶子节点只存储索引，这样可以存储更多的索引，减少树的高度，提高查询效率。其次，叶子节点之间是双向链表，这样可以方便地进行范围查询，比如查询id在10到20之间的数据，可以直接遍历叶子节点的链表。

为什么不用B树或者红黑树呢？B树的数据分布在所有节点上，查询时可能需要访问多个节点，效率较低。红黑树的高度较高，对于大数据量来说，查询效率不如B+树。所以B+树是最适合作为数据库索引的数据结构。

在智慧矿山项目中，我们的无人驾驶车辆位置表有5000万行数据，每天新增约200万条位置记录。我们在车辆ID和时间戳上建了复合索引，查询某辆车在特定时间段的位置轨迹时，只需要遍历3-4层B+树就能找到数据，查询时间在10ms以内。如果没有索引，就需要全表扫描，查询时间会超过10秒，这在实时调度场景中是不可接受的。”

追问应对：

面试官：”什么是聚簇索引和非聚簇索引？有什么区别？”

我：”聚簇索引是主键索引，它的叶子节点存储的是整行数据。非聚簇索引是二级索引，它的叶子节点存储的是主键值。区别在于：首先，聚簇索引的数据和索引是在一起的，查询时不需要回表；非聚簇索引需要先查索引找到主键值，再用主键值查聚簇索引，这就是回表。其次，一张表只能有一个聚簇索引，但可以有多个非聚簇索引。”

面试官：”如何判断索引是否被使用？”

我：”判断索引是否被使用可以用EXPLAIN命令。EXPLAIN会显示查询的执行计划，包括是否使用了索引、使用了哪个索引、扫描了多少行等。如果type列是ALL，说明是全表扫描，没有使用索引；如果type列是ref或range，说明使用了索引。key列会显示使用的索引名称。rows列会显示扫描的行数，如果行数很多，说明索引可能没有被有效使用。”

场景34：MVCC机制

考察点：多版本并发控制、事务隔离级别、一致性视图

核心概念：

  • MVCC：多版本并发控制，通过保存数据的多个版本来实现并发访问
  • Undo日志：保存数据的旧版本，用于回滚和一致性视图
  • Read View：一致性视图，决定事务能看到哪些版本的数据
  • 事务隔离级别：READ UNCOMMITTED、READ COMMITTED、REPEATABLE READ、SERIALIZABLE

MVCC工作原理：

  1. 每个事务都有一个唯一的事务ID
  2. 每条记录都有多个版本，每个版本有一个创建事务ID和删除事务ID
  3. 事务在开始时创建一个Read View，包含活跃事务的ID列表
  4. 查询时，根据Read View来判断哪些版本的数据对当前事务可见

事务隔离级别：

隔离级别 脏读 不可重复读 幻读
READ UNCOMMITTED 可能 可能 可能
READ COMMITTED 不可能 可能 可能
REPEATABLE READ 不可能 不可能 可能
SERIALIZABLE 不可能 不可能 不可能

答：

面试官：”什么是MVCC？它是如何实现的？”

我：”MVCC是多版本并发控制，是InnoDB实现并发访问的核心机制。

MVCC的工作原理是这样的：首先，每个事务都有一个唯一的事务ID，是递增的。其次，每条记录都有多个版本，每个版本有一个创建事务ID（trx_id）和删除事务ID（roll_pointer）。当一个事务修改一条记录时，不会直接修改原来的数据，而是创建一个新的版本，把原来的数据作为旧版本保存到Undo日志中。

然后，事务在开始时会创建一个Read View，包含当前活跃事务的ID列表。当事务查询数据时，会根据Read View来判断哪些版本的数据对当前事务可见。判断规则是：如果记录的创建事务ID小于Read View中的最小事务ID，说明这条记录是在当前事务开始之前创建的，对当前事务可见；如果记录的创建事务ID在Read View的活跃事务ID列表中，说明这条记录是当前事务创建的，对当前事务可见；否则，这条记录不可见。

MVCC的优点是不需要加锁就能实现并发访问，提高了并发性能。在智慧矿山项目中，我们的无人驾驶车辆状态表有大量并发读写——调度中心实时更新车辆状态，同时多个监控终端查询车辆信息。MVCC保证了每个事务都能看到一致的数据，同时不会阻塞其他事务的读写操作。比如调度中心更新车辆位置时，监控终端查询到的是更新前的一致快照，不会看到部分更新的数据。”

追问应对：

面试官：”MVCC如何解决幻读问题？”

我：”MVCC在REPEATABLE READ隔离级别下可以解决幻读问题。因为在REPEATABLE READ隔离级别下，事务在开始时创建一个Read View，整个事务期间都使用同一个Read View。这样，即使其他事务插入了新的数据，当前事务也看不到这些新数据，因为新数据的创建事务ID大于Read View中的最大事务ID。但是，如果当前事务执行INSERT或UPDATE操作，可能会看到其他事务插入的数据，这时候InnoDB会用Next-Key Lock来防止幻读。”

面试官：”Undo日志是如何回收的？”

我：”Undo日志是通过purge线程来回收的。purge线程会定期扫描Undo日志，删除那些不再被任何事务引用的旧版本数据。判断一个旧版本数据是否可以被删除的标准是：如果这个旧版本数据的创建事务ID小于当前所有活跃事务的最小事务ID，说明没有任何事务需要访问这个旧版本数据了，可以被删除。purge线程的执行频率可以通过参数来调整。”

场景35：事务隔离级别

考察点：ACID、事务隔离级别、锁机制

核心概念：

  • ACID：原子性、一致性、隔离性、持久性
  • 脏读：读到未提交的数据
  • 不可重复读：同一事务中多次读取同一数据，结果不同
  • 幻读：同一事务中多次执行同一查询，返回的行数不同

事务隔离级别实现：

答：

面试官：”MySQL有哪些事务隔离级别？各有什么特点？”

我：”MySQL有四个事务隔离级别，从低到高分别是READ UNCOMMITTED、READ COMMITTED、REPEATABLE READ和SERIALIZABLE。

READ UNCOMMITTED是最低的隔离级别，一个事务可以读取另一个事务未提交的数据，可能会出现脏读、不可重复读和幻读。一般不建议使用这个级别。

READ COMMITTED是大多数数据库的默认隔离级别，一个事务只能读取另一个事务已提交的数据，可以避免脏读，但可能会出现不可重复读和幻读。

REPEATABLE READ是MySQL InnoDB的默认隔离级别，一个事务在整个期间内多次读取同一数据，结果都是一致的，可以避免脏读和不可重复读，但可能会出现幻读。不过InnoDB通过MVCC和Next-Key Lock解决了幻读问题。

SERIALIZABLE是最高的隔离级别，事务之间完全串行执行，可以避免所有并发问题，但性能最差，一般只在特殊情况下使用。

在智慧矿山项目中，我们使用的是REPEATABLE READ隔离级别。因为无人驾驶调度系统中，一个调度事务可能需要多次读取车辆状态来计算最优路径，如果使用READ COMMITTED，可能会出现不可重复读，导致路径计算错误。REPEATABLE READ既能保证数据的一致性，又有较好的并发性能。对于一些特殊场景，比如车辆任务分配，我们会使用更高级别的锁来保证数据的一致性。”

追问应对：

面试官：”如何解决不可重复读和幻读？”

我：”解决不可重复读可以用REPEATABLE READ隔离级别，因为在这个级别下，事务在开始时创建一个Read View，整个事务期间都使用同一个Read View，所以多次读取同一数据的结果是一致的。解决幻读可以用Next-Key Lock，它不仅锁住索引记录，还锁住索引记录之间的间隙，防止其他事务在间隙中插入数据。”

面试官：”什么是Next-Key Lock？”

我：”Next-Key Lock是InnoDB的一种锁机制，它是记录锁和间隙锁的组合。记录锁锁住索引记录，间隙锁锁住索引记录之间的间隙。当事务执行范围查询时，InnoDB会对查询范围内的所有索引记录和间隙加Next-Key Lock，这样可以防止其他事务在间隙中插入数据，从而避免幻读。”

场景36：分库分表实战

考察点：分库分表策略、数据路由、数据迁移、分布式事务

分库分表策略：

策略 优点 缺点 适用场景
按范围分 便于扩容 热点数据集中 时间序列数据
按哈希分 数据均匀 扩容复杂 通用场景
按业务分 业务清晰 某些库可能过大 业务独立的场景

数据路由：

答：

面试官：”如何实现分库分表？”

我：”分库分表是处理大数据量的常用手段，主要有几种策略。

首先是分库分表策略的选择。按范围分，比如按时间分，2024年的数据放在一个库，2025年的数据放在另一个库，优点是便于扩容，缺点是热点数据可能集中在某个库。按哈希分，比如按用户ID哈希，优点是数据分布均匀，缺点是扩容时需要重新分配数据。按业务分，比如门禁数据放在一个库，停车数据放在另一个库，优点是业务清晰，缺点是某些库可能过大。

然后是数据路由。需要一个路由规则，根据业务数据（比如用户ID、订单ID）来决定数据应该放在哪个库哪个表。比如按用户ID哈希，用户ID % 4决定库，用户ID % 16决定表。

接下来是数据迁移。如果是从单库单表迁移到分库分表，需要考虑数据的一致性和业务的连续性。可以用双写的方式，同时写入旧库和新库，然后逐步切换到新库。

最后是分布式事务。分库分表后，一个事务可能涉及多个库，需要用分布式事务来保证数据一致性，比如TCC、本地消息表等。

在智慧矿山项目中，我们的无人驾驶车辆位置表有5000万行数据，每天新增200万条记录。我们按车辆ID哈希分库分表，分成8个库64个表，每个表大约80万行数据。同时，我们按时间范围做了冷热分离，最近3个月的数据放在SSD上，3个月之前的数据迁移到HDFS上做离线分析。分库分表后，单表查询性能提升了6倍，数据写入吞吐量提升了8倍，满足了实时调度系统的要求。”

追问应对：

面试官：”如何处理分库分表后的跨库查询？”

我：”处理跨库查询有几种方式：首先，尽量避免跨库查询，通过合理的分库分表策略把相关的数据放在同一个库中。其次，如果必须跨库查询，可以用中间件来实现，比如ShardingSphere，它可以自动路由查询到多个库，然后合并结果。最后，可以用数据同步工具把需要联合查询的数据同步到一个汇总库中，比如用Canal把数据同步到Elasticsearch中进行联合查询。”

面试官：”分库分表后如何扩容？”

我：”分库分表后的扩容比较复杂，特别是按哈希分的情况。可以用几种方式：首先，提前规划好分库分表的数量，预留足够的空间。其次，如果需要扩容，可以用双倍扩容的方式，比如从4个库扩容到8个库，每个旧库的数据迁移到两个新库中。最后，可以用中间件来自动处理数据迁移，比如ShardingSphere的弹性伸缩功能。”

场景37：高频算法题——LRU实现

考察点：数据结构、哈希表、链表

核心思路：

  • 哈希表 + 双向链表：哈希表快速查找，双向链表维护访问顺序
  • 最近访问的放在链表头部：访问或插入时移到头部
  • 链表尾部是最久未访问的：容量满时删除尾部节点

代码实现：

答：

面试官：”请实现一个LRU缓存。”

我：”好的，LRU是最近最少使用的缓存策略，我用哈希表加双向链表来实现。

首先，哈希表用于快速查找，时间复杂度O(1)。双向链表用于维护访问顺序，最近访问的节点放在链表头部，最久未访问的节点放在链表尾部。

具体实现：首先，定义一个Node类，包含key、value、prev和next指针。然后，定义一个LRUCache类，包含capacity、cache（哈希表）、head和tail节点。head和tail是哨兵节点，方便操作。

get方法：如果key存在，就把对应的节点移到链表头部，返回value；如果key不存在，返回-1。

put方法：如果key存在，就更新value，然后把节点移到链表头部；如果key不存在，就创建一个新节点，放到链表头部，同时加入哈希表。如果缓存容量超过了限制，就删除链表尾部的节点，同时从哈希表中移除对应的key。

这样，get和put操作的时间复杂度都是O(1)，空间复杂度是O(capacity)。”

追问应对：

面试官：”如果要实现线程安全的LRU缓存怎么办？”

我：”要实现线程安全的LRU缓存，可以在get和put方法上加synchronized关键字，或者用ReentrantLock来保证线程安全。但是这样会降低并发性能，因为每次只有一个线程能访问缓存。另一种方式是用ConcurrentHashMap配合读写锁，读操作加读锁，写操作加写锁，这样可以提高并发性能。在智慧矿山项目中，我们用LRU缓存来缓存车辆的实时状态信息，因为车辆状态的查询频率很高，而且状态更新相对较少，LRU缓存命中率可以达到90%以上。”

面试官：”如何实现LFU缓存？”

我：”LFU是最不经常使用的缓存策略，实现比LRU复杂一些。可以用哈希表加最小堆来实现，哈希表用于快速查找，最小堆用于维护使用频率。每次访问时，增加节点的使用频率，然后调整堆。当容量满时，删除堆顶的节点（使用频率最低的节点）。但是堆的调整时间复杂度是O(log n)，性能不如LRU。在智慧矿山项目中，我们没有使用LFU，因为车辆状态的访问模式更适合LRU——最近访问的车辆状态更可能被再次访问。”

场景38：高频算法题——链表反转

考察点：链表操作、递归、迭代

迭代实现：

递归实现：

答：

面试官：”请反转一个链表。”

我：”好的，链表反转有两种实现方式：迭代和递归。

迭代方式：首先，定义两个指针prev和curr，prev初始为null，curr初始为head。然后，遍历链表，每次把curr的next指向prev，然后prev和curr都向前移动一步。当curr为null时，prev就是反转后的链表头。

递归方式：首先，递归反转head.next，得到反转后的链表头newHead。然后，把head.next的next指向head，把head的next指向null。最后返回newHead。递归的终止条件是head为null或者head.next为null，此时直接返回head。

迭代方式的时间复杂度是O(n)，空间复杂度是O(1)。递归方式的时间复杂度也是O(n)，但空间复杂度是O(n)，因为递归调用栈的深度是n。”

追问应对：

面试官：”如何反转链表的一部分？”

我：”反转链表的一部分需要找到要反转的部分的前驱节点和后继节点。首先，遍历链表找到要反转的起始节点的前驱节点。然后，反转起始节点到结束节点之间的部分。最后，把前驱节点的next指向反转后的起始节点，把反转后的结束节点的next指向后继节点。”

面试官：”如何判断链表是否有环？”

我：”判断链表是否有环可以用快慢指针的方法。定义两个指针slow和fast，slow每次走一步，fast每次走两步。如果链表有环，fast会追上slow；如果链表没有环，fast会到达链表的末尾。时间复杂度是O(n)，空间复杂度是O(1)。”

考察点：二叉树、递归、迭代

答：

面试官：”请实现二叉树的前序、中序、后序和层序遍历。”

我：”好的，二叉树的遍历有四种方式，每种方式都有递归和迭代两种实现。

前序遍历是先访问根节点，再访问左子树，最后访问右子树。递归实现很简单，先打印根节点，然后递归左子树，再递归右子树。迭代实现需要用栈，先把根节点压入栈，然后弹出节点，打印值，再把右子树压入栈，最后把左子树压入栈。

中序遍历是先访问左子树，再访问根节点，最后访问右子树。迭代实现需要用栈，先把所有左子节点压入栈，然后弹出节点，打印值，再处理右子树。

后序遍历是先访问左子树，再访问右子树，最后访问根节点。迭代实现比较复杂，需要记录上一个访问的节点，判断当前节点的右子树是否已经访问过。

层序遍历是按层次访问节点，需要用队列，先把根节点加入队列，然后每次处理一层的所有节点，把它们的子节点加入队列。

递归实现的时间复杂度都是O(n)，空间复杂度是O(h)，h是树的高度。迭代实现的时间复杂度也是O(n)，空间复杂度是O(n)，因为栈或队列最多存储n个节点。”

追问应对：

面试官：”如何在O(1)空间复杂度下实现二叉树的遍历？”

我：”在O(1)空间复杂度下实现二叉树的遍历可以用Morris遍历算法。Morris遍历的核心思想是利用二叉树的空指针来存储遍历的路径，从而避免使用栈或递归调用栈。具体来说，对于前序遍历，当当前节点的左子树为空时，访问当前节点，然后移动到右子树；当当前节点的左子树不为空时，找到左子树的最右节点，把它的右指针指向当前节点，然后移动到左子树。这样可以在O(n)时间复杂度和O(1)空间复杂度下实现遍历。”

考察点：排序算法、时间复杂度、空间复杂度

快速排序：

归并排序：

答：

面试官：”请实现快速排序和归并排序。”

我：”好的，快速排序和归并排序都是常用的排序算法，各有优缺点。

快速排序的核心思想是分治，选择一个基准元素，把数组分成两部分，左边的元素都小于基准，右边的元素都大于基准，然后递归排序左右两部分。快速排序的时间复杂度平均是O(n log n)，最坏是O(n²)，空间复杂度是O(log n)，因为递归调用栈的深度是log n。快速排序是不稳定的排序算法。

归并排序的核心思想也是分治，把数组分成两半，分别排序，然后合并。归并排序的时间复杂度是O(n log n)，不管最好还是最坏情况。空间复杂度是O(n)，因为需要额外的空间来存储临时数组。归并排序是稳定的排序算法。

快速排序的优点是不需要额外空间，平均情况下性能更好；缺点是最坏情况下性能较差，而且是不稳定的。归并排序的优点是性能稳定，是稳定的排序算法；缺点是需要额外空间。”

追问应对：

面试官：”快速排序的最坏情况是什么？如何避免？”

我：”快速排序的最坏情况是每次选择的基准元素都是最小或最大的元素，这样每次只能把数组分成一个元素和n-1个元素，递归深度是n，时间复杂度是O(n²)。避免的方法是选择合适的基准元素，比如选择中间元素、随机元素或者三数取中（选择第一个、中间和最后一个元素的中位数）。这样可以大大降低最坏情况的概率。在智慧矿山项目中，我们用快速排序来对车辆任务进行优先级排序，任务数量可达上万条，快速排序的平均O(n log n)性能满足需求。”

面试官：”什么是稳定排序？为什么需要稳定排序？”

我：”稳定排序是指相等的元素在排序前后的相对顺序保持不变。比如两个元素的值都是5，排序前第一个5在第二个5的前面，排序后第一个5仍然在第二个5的前面。需要稳定排序的场景有很多，比如多关键字排序，先按第一个关键字排序，再按第二个关键字排序，如果第二个关键字的排序是稳定的，就可以保证第一个关键字相同的元素仍然按第一个关键字排序的结果排列。在智慧矿山项目中，我们对车辆进行排序时，先按优先级排序，再按等待时间排序，等待时间排序需要是稳定的，这样优先级相同的车辆仍然按照等待时间排序。”
