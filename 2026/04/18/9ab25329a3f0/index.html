二、微服务拆分原则

1. 拆分原则

原则 说明
单一职责 一个服务只做一件事
高内聚低耦合 服务内部紧密，服务间松散
业务边界 按业务领域拆。
独立部署 服务可独立发布部。
可测试 服务可独立测。

2. 避免拆分过细或不足

判断条件 是 否
代码耦合度高？ 继续拆分 检查其他因素
团队规模足够？ 可以拆分 保持单体架构
未来有扩展需求？ 预留扩展点 保持现状

3. 拆分示例

拆分粒度的实战判断：三个信号与一条红线

“微服务拆多细”没有标准答案，但有过真实拆分经验的人会讲出判断信号而不是背原则。信号一：部署耦合导致的发布排队——多个团队改同一个服务，发布要互相等待、互相回归测试，一周排不了一次版，这是拆分的头号信号（拆的是组织不只是代码，康威定律在先）。信号二：资源需求冲突——同一个服务里，A 模块要大量 CPU（报表计算）、B 模块要大内存（缓存），无法独立伸缩，只能整体扩容，资源浪费一半以上。信号三：故障半径过大——任何模块的内存泄漏都拖垮整个服务，核心交易和非核心日志互相影响可用性。一条红线：分布式事务的数量——每拆出一个服务，跨服务操作就多一批，如果拆分方案导致核心链路（下单、支付）大面积依赖分布式事务，说明拆过头了，拆分方向应该是让高频核心路径保持在单个服务内。这条红线解释了为什么”按业务域拆”优于”按技术层拆”：业务域内的操作天然内聚，跨域调用才是少数。面试中被追问”会不会拆太细”，把这条红线讲出来，比”适度、合理”这类空词有说服力得多。

公共基础平台的三难选择：统一、灵活与进度

公共平台（统一认证、统一网关、统一日志、统一消息）的设计难点从来不在技术，在与业务团队的协作模式。三个张力点要有预案。统一 vs 灵活：平台提供标准组件，业务团队总有”我的场景不一样”的诉求——放开定制则平台碎片化失去意义，完全不放开则业务被迫绕路、自建影子系统。可行解是平台定义扩展点：统一认证留自定义登录方式接口、统一网关留插件机制，核心链路锁死、边缘能力开放。先行 vs 垫后：平台先行会做出没人用的功能（脱离真实需求），完全垫后则各业务先造轮子再统一，重构成本翻倍。经验值是跟随第一个真实业务半步——和首个业务共同建设，从第二业务开始收敛为标准。质量责任归属：平台组件故障算谁的？必须在组织层面约定 SLA 和责任边界（平台侧承诺可用性与版本兼容，业务侧遵守接入规范），否则出故障时相互扯皮比故障本身更消耗组织。面试聊公共平台，能把这三个协作问题讲透，比罗列”统一网关统一认证”的功能清单高一个层级——平台建设的成败，八成取决于治理设计，两成才是技术实现。

四、中后台系统设计

1. 设计原则

原则 说明
高可靠 多活部署、故障自动切。
可扩 模块化设计、插件化架构
可迭 清晰的代码结构、完善的测试
安全链 权限控制、数据加。
易用 良好的UI/UX设计

2. 架构设计

层级 组件 说明

业务层 核心业务模块 用户管理、角色管理、权限管理、数据统计、报表分析、系统配置、日志管理
业务服务层 事务管理、业务逻辑
数据层 MySQL + Redis + Elasticsearch 关系型存储、缓存、全文搜索
基础设施层 RabbitMQ/RocketMQ + Redis/Redisson + Nacos 消息队列、分布式锁、配置中心

总结

系统架构设计是架构师必备的核心能力，掌握这些知识不仅能应对面试，还能设计出高质量的系统。核心要点：

  1. 架构设计：理解复杂系统的设计思路和优化点
  2. 微服务拆：遵循单一职责、高内聚低耦合原则
  3. 公共平台：统一权限、日志、异常、返回体的设备
  4. 中后台系统：高可用、可扩展、可迭代的设计原理
    这些都是面试中高频问到的问题，一定要深入理解并能说出落地实现
