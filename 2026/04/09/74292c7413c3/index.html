登录认证与多端会话场景题——JWT、SSO、踢人下线、记住我

发布于 2026-04-09 分类：技术, 2026, 登录认证, 面试题 👁

前言

登录认证是所有业务系统的入口，也是面试场景题的常客——“怎么设计单点登录””多端登录互踢怎么实现””Token 泄露了怎么办”，这些问题看似简单，实际上每一问都在考察会话管理的完整心智模型。这篇文章结合认证体系的核心原理与真实项目经验，把登录场景题一次讲透。

认证体系核心框架

认证与授权的边界

概念 回答的问题 典型实现
认证（Authentication） 你是谁 账号密码、短信验证码、扫码、生物识别
授权（Authorization） 你能干什么 RBAC 角色权限、ACL、ABAC 属性权限
会话（Session） 你还是刚才那个你吗 服务端 Session、客户端 Token、OIDC

面试加分点：很多候选人把三者混着说。清晰的表达是——认证解决”建立身份”，授权解决”约束行为”，会话解决”身份的持续性”。登录流程的本质是：认证一次成功后，用会话机制把这次认证的结果低成本地延续到后续所有请求，免去每次请求都重新认证。后面所有场景题的设计分歧，本质都是”会话状态放哪里、怎么验证、怎么失效”这三件事的取舍。

两种会话模型的本质差异

这个表格是所有后续场景题的判断原点：Session 模式”可随时失效、可查可踢”，代价是每次验证都要查存储；Token 模式”验证零成本、天然适合分布式”，代价是签发后无法主动作废（除非引入黑名单，那又回到了有状态）。面试中被问”Session 和 JWT 怎么选”，能先讲清”失效能力”这个核心矛盾再给结论的，明显比直接背对比表高一个层次。

场景一：多端登录与互踢下线

用户在 Web、APP、小程序同时登录，产品要求：同端互踢（新登录挤掉旧登录）、跨端共存（Web 和 APP 可同时在线）、且被踢端下次请求能收到明确的”已被踢下线”提示。

方案设计

设计的精髓在”现任制”而不是”黑名单制”：如果给每个 token 单独存一条记录、被踢时加黑名单，键数量随登录次数无限增长；而”每用户每端只存一条现任记录”，登录覆盖即踢人，Redis 键数恒定为”用户数 × 端类型数”。被踢提示靠 login:kicked:{token} 的短 TTL 标记，旧端请求时发现 token 非现任，查一下被踢原因返回 401 + SAME_TYPE_RELOGIN，前端据此跳登录页并提示”您的账号在其他设备登录”。

面试追问：为什么不用 JWT 直接实现互踢？

JWT 天生无状态，签发后服务端无法判断它是否”过期于人心”——这正是互踢场景的死角。工程上的补救有两种：短有效期 + RefreshToken（access token 只给 15 分钟，互踢靠 refresh token 的现任制实现，最多容忍 15 分钟的”已踢未踢”窗口）；或 JWT + Redis 现任校验（JWT 里的 jti 与 Redis 现任记录比对，等于 JWT 退化成带签名的 SessionID）。能主动指出”JWT 一旦引入现任校验就不再是无状态方案”，是这道题的分水岭——很多候选人一边强调 JWT 无状态优点，一边设计出”每次请求查 Redis 验证 token”的方案而不自知。

场景二：单点登录（SSO）与跨域会话

公司有多个子系统（门户、调度平台、报表中心），要求登录一次全系统通行，且各子系统域名不同。

方案设计：统一认证中心 + 授权码换票据

这个流程的精髓是”两级会话”：认证中心的全局会话（TGC，Cookie 存在认证中心域下）+ 各子系统的本地会话（Token）。第 5 步的”免登录”之所以成立，是因为跳转到认证中心时浏览器自动带上了认证中心域的 Cookie——这就是 SSO 跨域问题的全部秘密：各子系统无法共享 Cookie，但它们共享认证中心域的这一个 Cookie。讲 SSO 讲不清 TGC 与本地会话的两级结构，后续的”统一登出怎么做”（需认证中心广播登出事件给各子系统销毁本地会话）就一定讲不清。

面试追问：授权码模式为什么不直接发 Token？

三个理由层层递进：安全——code 经过浏览器前端（URL 可见），直接发 Token 等于凭证暴露在前端历史记录里；code 是一次性短时凭证，换 Token 的动作在子系统服务端与认证中心之间完成（走 client_secret 鉴权），凭证不经过前端。授权确认——code 流程天然支持”用户在认证中心确认授权”的插入点，第三方接入时这是必要环节。适配服务端渲染与前后端分离两种形态——前后端分离时子系统拿 code 换 Token 后通过自己域的 Cookie 下发，认证中心域的凭据始终不暴露给子系统前端。能把这三个理由讲完整，说明 OAuth2 不是背的流程图，而是理解了每一步的安全动机。

场景三：”记住我”与免登录的安全设计

用户勾选”记住我”后关闭浏览器，两周内再访问不用重新登录。但要保证：换设备不生效、凭证泄露可检测、用户改密码后所有免登录凭证失效。

方案设计：系列令牌（Sequential Token）模式

系列令牌模式的核心是”每次使用即轮换”：Cookie 里的令牌用一次就换新的，Redis 只认最新那个。于是出现一个精妙的检测机制——如果有人偷了 Cookie，合法用户下次访问时用的是”已轮换的旧令牌”，必然验证失败，系统立刻知道”这份凭证被盗了”，删除整个系列强制重新登录并安全告警。比”记住我 = 长有效期 JWT”的朴素方案强在两点：可检测盗用、改密码时按用户维度批量删除系列即可全局失效。这道题在面试里出现率极高，能答出”轮换 + 盗用检测”的直接进入下一轮。

场景四：Token 泄露的应急与预防

风险分级与响应矩阵

泄露场景 检测难度 响应措施
单个用户 token 泄露 难（正常使用无法区分） 用户主动改密码 / 管理员强制下线
批量 token 泄露（拖库） 中（异常 IP/UA 聚类可发现） 全量会话作废 + 强制改密
签名密钥泄露 低（伪造 token 可通过验签） 换密钥 + 全量用户重新登录，最严重
传输层泄露（无 HTTPS） 低（中间人可截获） 强制 HTTPS + HSTS，属架构级事故

面试必答的预防清单：Token 走 Authorization 头而不是 URL 参数（URL 会进访问日志、浏览器历史、Referer）；Cookie 加 HttpOnly（防 XSS 窃取）+ Secure（仅 HTTPS 传输）+ SameSite（防 CSRF）；签名密钥进密钥管理服务并支持轮换；核心操作（改密码、支付）二次认证——即使 token 被盗，资金操作还需要密码或验证码，把泄露的爆炸半径限制在”信息可见”而不是”资金可动”。这层”爆炸半径”思维是把安全题从背诵拉到工程层面的关键。

会话续期与并发控制：两个被低估的细节

续期策略决定用户体验和安全性的平衡点。固定过期（token 7 天后必须重登）实现最简单，但活跃用户会被莫名登出，投诉率高；滑动续期（每次请求顺延）体验最好，但 token 实际上永不过期——一旦泄露就是永久凭证。生产方案是双上限：滑动续期到最长绝对有效期（如 30 天）后强制重登，同时敏感操作（改绑手机、支付）要求近期活跃凭证（30 分钟内）或二次验证。并发控制的坑在续期竞态：同一用户的多个请求同时触发续期，EXPIRE 命令本身是原子的所以无数据问题，但”登录态迁移”场景（用户在 A 端续期、B 端被判过期）会产生闪断——续期判断和过期判断要基于同一个服务端时间戳，而不是各请求本地时钟。这两个细节在面试里属于”没踩过坑就想不到”的区域，主动讲出来价值很高。

场景五：扫码登录的完整时序

扫码登录是登录场景题的进阶变体，考察的是状态机 + 长轮询/WebSocket 的组合设计。完整时序：第一步，PC 端请求”生成二维码”，服务端创建 qrcodeId，状态置为 WAITING，Redis TTL 120 秒，返回二维码图（内容是认证中心的短链 + qrcodeId）；第二步，手机 APP 扫码（APP 已登录），把 qrcodeId + 用户凭证提交到”确认扫码”接口，qrcodeId 状态置为 SCANNED（PC 端此时轮询到状态变化，页面显示”已在手机上确认，请在手机上点击授权”）；第三步，用户在手机上点击”确认登录”，状态置为 CONFIRMED 并把生成的 token 挂到 qrcodeId 上；第四步，PC 端轮询拿到 token，建立自己的会话。设计要点有三个：qrcodeId 必须是一次性且短时效的（120 秒未确认作废，防二维码被截屏重放）；PC 端轮询用长轮询（服务端 hold 住 25 秒，状态变化才返回）而不是 1 秒一次的短轮询，QPS 差 25 倍；SCANNED 与 CONFIRMED 两态分离是产品体验的关键——让用户知道”扫上了”和”确认了”是两个动作，也给了手机端反悔的机会。把二维码登录讲清楚，等于同时演示了状态机设计、轮询优化和跨端信任传递三个能力，这也是它在面试里出场率居高不下的原因。

认证体系的监控与审计：出事时你能查清吗

认证系统的监控要覆盖三个层面。可用性层：登录接口成功率、验证码服务耗时、认证中心 RT——登录失败率突增往往是依赖服务（短信通道、LDAP）故障的先兆，比业务监控更早报警。安全层：同一账号的失败尝试次数（撞库信号）、同一 IP 的登录账号数（薅号信号）、异地登录占比（盗号信号）、被踢事件量（互踢异常说明可能存在共享账号）。审计层：登录成功/失败、踢人、改密码、token 作废全部落审计表，保留 180 天——安全事件的复盘完全依赖这条时间线，”查不清”比”防不住”在合规上更致命。再配一条告警策略：单账号 10 分钟内失败 5 次触发账号级限频，单 IP 1 小时内失败 100 次触发 IP 级封禁，全局登录失败率超 30% 触发 P1 响应——阈值要在演练中校准，而不是拍脑袋定。

面试高频问题速答

1. Session 和 JWT 到底怎么选？

按”是否需要主动失效能力”定：管理后台、支付等需要随时踢人的场景用 Session（Redis 集中存储）；纯只读、高并发的开放接口用短有效期 JWT。两者混合（JWT 做短期凭证 + Redis 做现任校验）是生产最常见形态，但要清楚此时已不是无状态方案。

2. 分布式环境下 Session 共享怎么做？

Session 外置到 Redis（Spring Session 一行配置切换），所有实例读写同一个 Redis。关键细节是序列化兼容（发版期间新旧实例反序列化 Session 对象要兼容）和 Redis 的高可用（Session 存储挂了等于全站下线，按核心基础设施对待）。

3. 验证码防刷怎么设计？

分层：前端行为验证（滑块）挡机器流量、后端按”IP + 设备指纹 + 手机号”多维度限频、验证码一次性使用且 60 秒过期、短信验证码加发送量日限额告警。核心思想是把刷的成本抬高到超过收益，而不是追求绝对防住。

4. 改密码后怎么让所有会话失效？

Session 模式按 userId 删除所有会话键；JWT 模式维护”用户密码版本号”，JWT 载荷携带版本号，验签后再比对版本——密码改一次版本号 +1，旧 token 全部失效。这个”版本号”技巧同样适用于踢人下线（版本号按端维护）。

总结

登录认证场景题的答题主线只有一条：会话状态放在哪里、验证成本是多少、失效能力有多强——三者构成不可能三角，所有方案（Session、JWT、混合、系列令牌）都是在三角上的不同落点。最后送三条实战经验：其一，先问清产品需求的失效粒度（能不能被踢、几端在线），再选方案，顺序反了全是返工；其二，认证中心的可用性等级要按”全站登录的咽喉”对待，它挂了比任何业务服务挂了都严重；其三，安全设计的功夫在爆炸半径——假定凭证一定会泄露，然后让泄露的代价可控，这比”相信这套系统不会泄露”成熟得多。
