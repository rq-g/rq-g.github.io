二、Redis过期策略与内存淘汰

1. 过期策略（面试必备）

策略 说明 优点 缺点
定时删除 设置过期时间时创建定时器 及时释放内存 消耗CPU，大量定时器
惰性删除 查询Key时检查是否过期 节省CPU 过期Key长期占用内存
定期删除 每隔一段时间随机抽查并删除过期键 平衡CPU和内存 可能遗漏部分过期键

Redis采用：惰性删除 + 定期删除

2. 内存淘汰策略（面试必备）

策略 说明 适用场景
noeviction 不淘汰，写入返回错误 数据不能丢失
allkeys-lru 所有Key中淘汰最久未使用的 ★ 通用缓存场景
volatile-lru 过期Key中淘汰最久未使用的 有过期时间的数据
allkeys-random 所有Key中随机淘汰 无访问热点
volatile-random 过期Key中随机淘汰 -
allkeys-lfu 所有Key中淘汰使用频率最低的 ★ Redis 4.0+推荐
volatile-lfu 过期Key中淘汰使用频率最低的 -
volatile-ttl 过期Key中淘汰TTL最短的 有明确TTL需求

三、缓存三大问题（项目实战重点）

1. 缓存穿透（实际项目实战）

项目背景：

  • 500+车辆，但有些车辆ID不存在或已报废
  • 查询不存在的车辆时，直接穿透到MySQL
  • 高峰期大量无效查询，导致MySQL压力过大

项目数据：

  • 穿透请求占比：5%
  • MySQL压力增加30%
  • 解决方案：缓存空值 + 布隆过滤器

三种方案对比：

方案 优点 缺点 适用场景
缓存空值 实现简单 浪费内存、空值过多 少量无效请求
布隆过滤器 空间效率高 有误判率、需预加载 数据相对固定
接口限流 防恶意攻击 治标不治本 攻击场景

2. 缓存击穿（实际项目实战）

项目背景：

  • 热点车辆数据（如调度中车辆）过期
  • 大量请求同时查询，直接打到MySQL
  • MySQL瞬间压力暴增

项目数据：

  • 热点车辆数量：50+
  • 查询QPS：2000+/秒（高峰期）
  • 解决方案：互斥锁 + 逻辑过期

三种方案对比：

方案 优点 缺点 适用场景
互斥锁 保证强一致性 有等待时间、可能死锁 强一致性要求
逻辑过期 无等待、高可用 短暂数据不一致 高可用优先
永不过期+定时刷新 简单 数据有延迟 热点数据

3. 缓存雪崩（实际项目实战）

项目背景：

  • 凌晨0点，大量车辆数据同时过期
  • 500+车辆同时上线，缓存批量失效
  • MySQL瞬间压力暴增，系统崩溃

项目数据：

  • 同时过期Key数量：500+
  • MySQL QPS：10万（正常5000）
  • 解决方案：随机过期时间 + 多级缓存 + 熔断降级

缓存雪崩 vs 缓存击穿：

维度 缓存雪崩 缓存击穿
本质 大量Key同时过期 热点Key过期
影响范围 大面积不可用 单个热点不可用
解决方法 随机过期+多级缓存+熔断 互斥锁+逻辑过期
比喻 所有窗口同时下班 一个热门窗口下班

八、面试高频追问

Q1：Redis为什么这么快？

A：单线程 + IO多路复用 + 内存存储 + 高效数据结构。Redis 6.0多线程仅用于网络IO，命令执行仍是单线程。

Q2：Redis和Memcached有什么区别？

维度 Redis Memcached
数据结构 5种+高级结构 简单KV
持久化 RDB+AOF 不支持
集群 原生Cluster 客户端分片
内存管理 淘汰策略 LRU
线程模型 单线程(6.0+IO多线程) 多线程

Q3：Redis如何做高可用？

A：主从复制 + Sentinel哨兵 + Cluster集群。主从保证数据备份，Sentinel自动故障转移，Cluster水平扩展。

Q4：Redis Cluster如何处理数据分片？

A：16384个Hash Slot，Key通过CRC16(key) % 16384计算所属Slot，每个Master负责一部分Slot。

Q5：Redis Cluster如何处理节点故障？

A：主从自动切换 + 故障转移 + 集群自愈。从节点发起选举成为新Master，其他节点更新Slot映射。
