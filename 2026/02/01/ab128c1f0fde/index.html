一、InnoDB B+树索引原理

1. B+树结构

层级 内容 说明
根节点 100, 200, 300, 400 索引键，指向子节点
非叶子节点 只存储键值+子节点指针 不存储数据，一个节点可存更多键
叶子节点1 1~100 + 数据行 存储完整数据，指向下一节点
叶子节点2 101~200 + 数据行 存储完整数据，指向下一节点
双向链表 ←→ 叶子节点之间双向连接，支持范围查询

B+树高度计算：

2. B+树 vs B树

维度 B树 B+树
数据存储 叶子节点和非叶子节点都存储数据 仅叶子节点存储数据
索引大小 大（非叶子节点存数据） 小（非叶子节点只存键值）
范围查询 需要回溯 叶子节点链表直接遍历
磁盘IO 多（树高更高） 少（树高更低）
查询稳定性 不稳定（数据可能在非叶子节点） 稳定（必须到叶子节点）
适用场景 随机查询为主 ★ 范围查询为主（数据库索引）

3. B+树 vs 二叉树

维度 二叉树 B+树
树高 O(n)（最坏退化为链表） O(logN)，3层可存千万行
磁盘IO 多（树高太高） 少（树高可控）
查询效率 不稳定 稳定
适用场景 内存数据 磁盘数据

为什么不用红黑树？ 红黑树也是二叉树，树高约log₂N，千万数据树高约24，需24次磁盘IO，远不如B+树的3次。

1. 核心区别

维度 聚簇索引 非聚簇索引

索引结构 数据即索引 索引和数据分离
查询效率 最高（无需回表） 次高（需要回表）

3. 索引失效场景汇总

场景 示例 原因
跳过最左前缀 WHERE b = 2（索引a,b,c） 不符合最左前缀原则

四、MySQL锁机制

1. 锁的分类

维度 类型 说明
粒度 表锁 锁住整张表，MyISAM默认
粒度 行锁 锁住单行记录，InnoDB默认
粒度 间隙锁 锁住索引间隙，防止幻读
性质 共享锁（S锁） 读锁，多个事务可共享
性质 排他锁（X锁） 写锁，独占
模式 意向锁 表级锁，表示事务打算加行锁
算法 记录锁（Record Lock） 锁住索引记录
算法 间隙锁（Gap Lock） 锁住索引间隙
算法 临键锁（Next-Key Lock） 记录锁 + 间隙锁

2. 行锁 vs 表锁

维度 行锁 表锁
粒度 细（行级别） 粗（表级别）
并发性 高 低
开销 大（需要索引） 小
死锁 可能发生 不可能
适用场景 高并发读写 批量操作、MyISAM

3. InnoDB行锁的三种算法

临键锁退化规则：

条件 退化结果 说明
等值查询，记录存在 退化为记录锁 只锁住匹配的记录
等值查询，记录不存在 退化为间隙锁 锁住目标位置所在的间隙
范围查询 不退化，仍为临键锁 锁住范围内所有间隙和记录

5. 死锁

死锁预防策略：

策略 说明

6. 乐观锁实现

乐观锁 vs 悲观锁：

维度 乐观锁 悲观锁
原理 CAS + version SELECT … FOR UPDATE

适用场景 读多写少 写多冲突多

1. 使用EXPLAIN分析SQL

EXPLAIN输出字段：

字段 说明 重点关注
id 查询序号 子查询时id会递增
select_type 查询类型 SIMPLE/PRIMARY/SUBQUERY
table 表名 -
type 访问类型 ★ 最重要，从好到差排序
possible_keys 可能使用的索引 -
key 实际使用的索引 ★ NULL表示未用索引
key_len 索引长度 判断使用了联合索引的几个列
rows 预计扫描行数 越小越好
Extra 额外信息 ★ Using index/filesort/temporary

type值从好到差排序：

type 说明 出现条件
system 系统表，只有一行 MyISAM/Memory引擎
const 常量，最多匹配一行 主键/唯一索引等值查询
eq_ref 唯一索引扫描 JOIN时主键/唯一索引
ref 非唯一索引扫描 普通索引等值查询
range 索引范围扫描 BETWEEN、>、<
index 全索引扫描 索引列扫描
ALL 全表扫描 ★ 需优化

Extra常见值：

Extra 说明 优化建议
Using index 覆盖索引，无需回表 好
Using where 服务层过滤 正常
Using index condition 索引条件下推 好

十、MySQL配置优化

十一、真实项目中的常见问题

问题 原因 解决方法
慢查询突增 新上线SQL缺少索引或数据量增长 EXPLAIN分析+添加索引
索引失效 隐式类型转换/函数/左模糊 避免运算、统一类型
死锁频发 事务获取锁顺序不一致 按固定顺序操作、缩短事务
主从延迟 从库SQL线程单线程重放慢 并行复制、分库降低单库压力
行锁升级为表锁 未走索引导致锁住全表 确保UPDATE/DELETE走索引
Deep Page慢查询 LIMIT 1000000,10扫描太多行 延迟关联/游标分页
Using filesort ORDER BY字段无索引 WHERE+ORDER BY建联合索引
Using temporary GROUP BY和ORDER BY字段不同 统一字段或冗余列
连接数耗尽 未关闭连接/慢查询占用 排查慢查询、配置wait_timeout
Buffer Pool污染 全表扫描将热数据挤出 调大innodb_old_blocks_time
批量插入太慢 逐条INSERT + autocommit 批量INSERT + rewriteBatchedStatements
自增ID不连续 事务回滚或MySQL重启 正常现象，不影响使用
唯一索引死锁 两个事务交替插入相同唯一键 业务层保证唯一、先查再插
大事务阻塞 事务中包含RPC调用 事务中只做DB操作，RPC放事务外
分库分表后JOIN 跨库无法JOIN 代码层组装/冗余字段/宽表

总结

MySQL优化是高级Java开发的必备技能，核心要点：

  1. B+树原理：3层可存千万行，范围查询优势，比B树和二叉树更适合磁盘索引
  2. 聚簇索引vs非聚簇索引：聚簇索引存数据无需回表，非聚簇索引需回表
  3. 联合索引：最左前缀原则、区分度高的字段在前、覆盖索引减少回表
  4. 索引失效：10种场景，重点是运算/函数/左模糊/类型不匹配
  5. 锁机制：记录锁/间隙锁/临键锁、MVCC原理、RC vs RR区别
  6. SQL优化：EXPLAIN分析（type/Extra最关键）、Deep Page三种方案
  7. Buffer Pool：改良LRU算法、WAL机制、Redo Log
  8. 批量插入：rewriteBatchedStatements + 分批插入
  9. 主从复制：三线程模型、读写分离AOP实现
