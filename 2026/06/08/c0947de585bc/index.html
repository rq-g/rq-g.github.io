测试体系从0到1——JUnit5、Mockito与Testcontainers的工程化落地

发布于 2026-06-08 分类：技术, 2026, 工程化 👁

这是博客里唯一空白的工程域。单测写不写、怎么写、写多少，争议永远存在；本篇不给”覆盖率多少才算好”的空话，只回答三个实操问题：什么值得测、怎么写得快、怎么让测试在 CI 里活下来。案例来自矿卡调度系统的真实补测过程。

一、测试金字塔与投入策略

经典金字塔：大量单元测试 → 适量集成测试 → 少量端到端测试。落地的第一原则是按 ROI 分配：

层级 测什么 成本 矿卡系统的实际配比
单元测试 领域逻辑：调度算法、告警规则、费用计算 低（毫秒级、无依赖） 70%，核心服务覆盖率 80%+
集成测试 Repository、缓存、MQ 收发、配置装配 中（秒级，要真依赖） 25%，关键链路全覆盖
端到端 完整业务流（下单→调度→回执） 高（环境+数据准备） 5%，冒烟级别

判断”什么值得测”的一条实用标准：一个 if 语句承载的业务规则、一次历史事故、一段没人敢改的代码——这三类必须测；DTO 的 getter、纯 CRUD 的透传方法不值得。另一个反面信号：断言在复述实现（verify(repo).findById(any()) 这类没有业务断言的测试）写再多覆盖率也是假的安全感。

二、JUnit5：结构化测试的组织能力

2.1 相比 JUnit4 的关键升级

四个值得用的能力：@DisplayName 让测试报告可读（中文描述业务规则）；@ParameterizedTest 把”同一逻辑多组输入”压成一个测试（规则类代码的覆盖率利器）；@Nested 分组组织场景；assertAll 批量断言（一次失败全部报告，不用改一轮跑一轮）。

2.2 生命周期与执行控制

@BeforeAll/@AfterAll 默认静态（每类一次），@TestInstance(PER_CLASS) 可改为实例级——配置重的集成测试用它省初始化。执行控制用 @Tag("slow") 标注慢测试，CI 里 -Dgroups='!slow' 分层执行：PR 门禁跑快测试（<2min），夜间全量。

三、Mockito：把依赖”换掉”的艺术

3.1 三种替身的语义区别

类型 行为 用途
Mock 全部方法返回默认值，可验证交互 验证”调没调、调了几次”
Stub 指定方法返回指定值 提供”预设返回”
Spy 包装真实对象，部分方法可覆盖 测真实对象的部分行为

选型纪律：优先 Stub（Given 数据），少用交互验证（Then Verify）。verify(repo, times(1)).save(any()) 这类验证把测试锁死在实现上——重构换实现就红。交互验证只留给真正的事件边界：发消息、发邮件、调外部 API。

3.4 集成测试的替身策略

集成测试里”哪些依赖用真的、哪些用假的”是核心决策：

依赖 建议 理由
内存数据库 H2 替代 MySQL 不推荐 方言差异（函数/锁行为/执行计划）让测试通过但生产报错
Testcontainers 起真 MySQL 推荐 真实行为，一次性成本
内嵌 Redis（embedded） 不推荐 社区维护停更、行为差异；用 Testcontainers
WireMock 模拟外部 HTTP 推荐 第三方接口不可控，必须替身
本地事务/业务逻辑 全真 这是集成测试要验证的核心

五、让测试在 CI 里活下来

测试写出来只是开始，活过半年才是资产。四条工程纪律：

1. 分层执行。PR 门禁只跑单元测试（快、稳），集成测试夜间全量 + 发布前跑。用 Maven Surefire/Failsafe 分离（*Test 单测、*IT 集成），互不拖累。

2. 确定性是生命线。不稳定测试（flaky test）比没有测试更糟——团队会条件性忽略红色 CI。三个常见 flaky 源与解法：时间依赖（注入 Clock）、并发时序（awaitility 显式等待替代 Thread.sleep）、共享状态（测试间数据隔离，@Transactional 回滚或 TRUNCATE）。

3. 覆盖率当仪表盘不当 KPI。JaCoCo 接入 CI 报告，但只对核心模块设底线（调度引擎 80%），工具类/DTO 不设。全员凑数字的结果是大量无断言测试。

4. 测试也是代码。测试代码同样要 review：断言是否表达业务语义、替身是否过度、命名是否描述场景。一个不能回答”它在保护什么”的测试应该被删掉。

六、测试数据管理：被低估的工程问题

集成测试最容易烂掉的不是框架，是数据：测试 A 依赖测试 B 插的数据、并发执行时唯一键冲突、字典数据改动全量飘红。数据管理分层治理：

1. 静态基础数据（字典、配置、权限模板）：Flyway/Liquibase 迁移脚本统一管理，测试环境与生产同源——基础数据的”测试版”与”生产版”分叉是环境问题的头号来源。

2. 业务测试数据：每个测试自建自清，禁止跨测试依赖。@Sql 注解或 Builder 模式（OrderTestDataBuilder.aOrder().withAmount(100).build()）让”这个测试需要什么数据”显式化。Builder 模式在领域对象字段多时是刚需——测试可读性的一半来自数据构造的可读性。

3. 清理策略选型：@Transactional 自动回滚最快，但测不到真提交语义（自增 ID 跨测试跳号、事务内才有的行为差异），且与异步代码冲突（异步线程看不到未提交事务）。生产经验：单测层用回滚，集成层用 TRUNCATE 显式清理（注意外键顺序）或每测试独立 schema。唯一键 + 随机后缀（"ORD-" + UUID.randomUUID()）是并发执行的保命符。

4. 时间与随机数： Clock 注入已在前文强调，随机数据用固定 seed 的 Random（失败可复现），”随机测试数据”与”可复现失败”不矛盾——seed 打进日志即可。

七、契约测试：微服务接口的防退化网

微服务多了以后，单服务测试全绿、联调照样炸——因为接口契约变了（字段删除/语义变化），消费方的测试根本感知不到。契约测试（Consumer-Driven Contract Testing）把”接口约定”本身变成被测对象：

与集成测试的分工：集成测试验证”我调真实依赖能不能跑通”（对自己的责任），契约测试验证”我承诺的接口没变”（对他人的责任）。服务数量超过 5 个、跨团队调用频繁时，契约测试的投入产出开始明显为正；小团队先用”OpenAPI 契约评审 + 版本化变更日志”顶住即可（见对外 API 设计篇的契约先行）。

八、遗留代码的补测策略

存量项目没测试又不敢动，是绝大多数团队的真实处境。矿卡系统补测的顺序经验：

  1. 从”要改的代码”开始——只给即将修改的模块补测试（Michael Feathers 的”接缝”思路），不做全量补测的宏大计划；
  2. 先给”安全网”再重构——改造前为行为补”特征测试”（Characterization Test）：不评判对错，先固化当前行为，重构后行为不变即通过；
  3. 依赖解耦是前置工程——无法 mock 静态调用/单例，说明代码不可测，先做最小重构（依赖注入、Clock 注入），可测性与设计质量是同一件事；
  4. 集成测试先行——单元测试插不进去的遗留代码，先用 Testcontainers 集成测试从入口包住，性价比更高。

九、面试高频问题速答

Q1: 单元测试和集成测试怎么划分？
单测隔离外部依赖（毫秒级、测业务规则），集成测试用真实依赖（Testcontainers、秒级、测装配与协议边界）。按 ROI 配比约 7:2:1（单测/集成/E2E）。

Q2: Mockito 的 verify 什么时候该用？
只验证”事件边界”：发消息、调外部 API、写审计。数据操作类依赖优先用状态断言（Given 数据 → When → Then 结果），交互验证会锁死实现细节。

Q3: 为什么不用 H2 替代 MySQL 做集成测试？
方言差异（JSON 函数、锁行为、执行计划、默认值语义）导致测试通过而生产失败，是假信心。Testcontainers 起真 MySQL 的一次性成本远低于此。

Q4: 如何治理 flaky test？
定位三类根因：时间依赖（注入 Clock）、并发时序（awaitility 替代 sleep）、测试间共享状态（数据隔离）。CI 中统计失败率，连续不稳的测试隔离修复而不是留着污染门禁。

Q5: 遗留代码没有测试，如何安全重构？
先补特征测试固化当前行为（Testcontainers 集成测试从入口包住），再做最小解耦（依赖注入），然后重构，全程行为不变。只给”即将修改”的模块补测，不做全量宏大计划。

十、总结

测试体系的价值不在覆盖率数字，而在**”改动代码时的心理安全感”**：单测保护业务规则、集成测试保护技术边界、CI 纪律保护测试本身的有效性。三件套各司其职——JUnit5 组织结构，Mockito 隔离依赖，Testcontainers 提供真实环境——剩下的是把”测试也是代码”的纪律立起来。从下一个要修改的模块开始补，比任何宏大计划都有效。
