场景18：CPU 100%如何定位？

排查流程：

  1. top：查看CPU占用最高的进程
  2. top -Hp <pid>：查看进程内CPU占用最高的线程
  3. jstack <pid>：导出线程栈
  4. 分析线程栈：查找RUNNABLE状态的线程，定位问题代码

关键命令：

常见原因：

  • 死循环
  • 正则表达式回溯
  • 大量对象创建导致频繁GC
  • 线程池满，大量线程阻塞

回答要点：

  • 展示系统性的排查流程
  • 熟悉常用的排查工具
  • 能够分析线程栈和GC日志

答：

面试官：”线上CPU 100%，你怎么定位问题？”

我：”CPU 100%是线上常见问题，我一般按这个流程排查。

第一步，用top命令查看哪个进程占用CPU最高。找到进程ID后，用top -Hp 查看进程内哪个线程占用CPU最高，记下线程ID。

第二步，把线程ID转换成十六进制，因为jstack输出的线程ID是十六进制的。用printf “%x\n” 转换。

第三步，用jstack > thread_dump.txt导出线程栈，然后搜索转换后的十六进制线程ID，找到对应的线程。

第四步，分析线程栈。如果线程状态是RUNNABLE，而且堆栈显示在某个循环里，那很可能是死循环或者正则表达式回溯。如果线程状态是WAITING或BLOCKED，可能是线程池满了，大量线程在等待。

我之前遇到过一个案例，智慧矿山的调度系统CPU突然100%，排查发现是一个路径规划算法的死循环导致的。当时有个矿车的位置数据异常，导致路径规划算法进入了无限循环，CPU直接打满。后来在算法里加了最大迭代次数限制，问题就解决了。

还有一种情况是频繁GC导致CPU高，可以用jstat -gcutil 1000查看GC情况，如果YGC次数很多，FGC也频繁，就说明有内存问题。在智慧矿山项目中，我们对GC的要求很高，因为调度系统需要实时响应，GC停顿时间过长会影响矿车的安全行驶。

总结一下，CPU 100%的排查流程是：top找进程 → top -Hp找线程 → jstack导出线程栈 → 分析线程栈定位问题代码。”

追问应对：

面试官：”如果jstack导出失败怎么办？”

我：”如果jstack导出失败，可能是进程没有响应或者权限不足。可以尝试用jstack -F 强制导出，或者用jmap -dump导出堆快照，然后用MAT分析。另外，也可以用arthas来分析，它功能更强大，可以实时查看线程状态、方法执行时间等。”

面试官：”如何预防CPU 100%的问题？”

我：”预防CPU 100%的问题可以从几个方面入手：首先，代码review时要注意死循环和复杂算法的写法；其次，做好性能测试，模拟高并发场景；最后，设置监控告警，当CPU使用率超过阈值时及时告警。在智慧矿山项目中，我们设置了CPU使用率超过80%就告警，确保及时发现问题。”

面试官：”在矿山场景中，CPU 100%会有什么安全风险？”

我：”在矿山场景中，CPU 100%会导致调度系统响应延迟，进而影响矿车的安全行驶。比如调度指令无法及时下发，矿车无法及时调整速度或方向，可能会导致碰撞等安全事故。所以我们对CPU的监控要求很高，一旦CPU使用率超过阈值，会立即触发告警，通知运维人员处理。”

场景19：内存泄漏如何排查？

排查流程：

  1. jmap -heap <pid>：查看堆内存使用情况
  2. jmap -dump:format=b,file=heap.hprof <pid>：导出堆快照
  3. MAT/VisualVM分析堆快照：
    • 查找大对象
    • 查找内存泄漏的对象
    • 分析引用链

常见原因：

  • 静态集合持有对象引用
  • ThreadLocal未清理
  • 连接池/线程池泄漏
  • 监听器未注销

回答要点：

  • 熟悉堆内存分析工具
  • 能够识别常见的内存泄漏模式
  • 能够分析引用链，定位泄漏点

答：

面试官：”如何排查内存泄漏？”

我：”内存泄漏是指对象不再被使用，但仍然被引用，导致GC无法回收。我一般按这个流程排查。

第一步，用jmap -heap 查看堆内存使用情况，看看堆内存是不是一直在增长，有没有接近最大值。

第二步，用jmap -dump:format=b,file=heap.hprof 导出堆快照。注意如果堆内存很大，导出可能会比较慢，而且会暂停应用。可以用jmap -dump:live,format=b,file=heap.hprof 只导出存活对象，这样文件会小一些。

第三步，用MAT（Memory Analyzer Tool）或者VisualVM分析堆快照。MAT功能更强大，可以做泄漏检测。

在MAT里，我会看几个关键指标：一是直方图，看哪些类的实例数最多；二是支配树，看哪些对象占用了最多的内存；三是泄漏嫌疑报告，MAT会自动分析可能的泄漏点。

常见的内存泄漏原因有几种：一是静态集合持有对象引用，比如一个静态的List一直在add对象，从来没有remove，导致这些对象永远不会被回收。二是ThreadLocal未清理，如果ThreadLocal使用后没有调用remove()，线程池里的线程会一直持有这些对象。三是连接池泄漏，比如数据库连接、Redis连接没有正确释放。四是监听器未注销，注册了监听器但没有注销，导致被监听的对象永远不会被回收。

我之前遇到过一个ThreadLocal泄漏的案例。智慧矿山项目里用ThreadLocal存储矿车上下文，但在filter里没有调用remove()，导致线程池里的线程一直持有这些矿车对象，内存越来越大。后来在finally块里加了ThreadLocal.remove()，问题就解决了。

总结一下，内存泄漏的排查流程是：jmap -heap看堆使用 → jmap -dump导出快照 → MAT分析快照 → 定位泄漏点。”

追问应对：

面试官：”如何区分内存泄漏和内存溢出？”

我：”内存泄漏是指对象不再被使用，但仍然被引用，导致GC无法回收，最终导致内存溢出。内存溢出是指JVM堆内存不足，无法分配新的对象。内存泄漏是内存溢出的原因之一，但不是唯一原因。比如，如果程序一次性创建了大量的对象，超过了堆内存的限制，也会导致内存溢出。”

面试官：”如何预防内存泄漏？”

我：”预防内存泄漏可以从几个方面入手：首先，避免使用静态集合存储大量对象；其次，使用ThreadLocal时要在finally块里调用remove()；再次，使用连接池时要确保连接正确释放；最后，注册监听器时要记得注销。另外，可以用工具来检测内存泄漏，比如MAT的泄漏检测功能。”

面试官：”在矿山场景中，内存溢出会有什么安全风险？”

我：”在矿山场景中，内存溢出会导致调度系统崩溃，进而影响矿车的安全行驶。比如调度中心的JVM崩溃了，矿车无法接收调度指令，可能会导致矿车失控。所以我们对内存的监控要求很高，设置了堆内存使用率超过80%就告警，确保及时发现问题。”

答：

面试官：”Kafka消费积压1000万条，怎么处理？”

我：”消费积压是线上常见问题，需要组合多种手段来处理。

首先，临时扩容消费组。如果topic有多个分区，可以启动多个同group.id的消费者实例，让它们并行消费。比如原来只有2个消费者，现在扩容到10个，消费速度就能提升5倍。

其次，如果是非核心数据，可以考虑跳过部分偏移量。比如直接把offset往后移500万，先处理最新的数据，保证核心业务不受影响。

第三，暂停部分非核心业务。比如数据分析、日志统计这些可以暂停，把资源集中在核心业务上。

第四，事后补数据。等消费赶上后，用binlog回放或者数据修复工具把跳过的数据补回来。比如用Canal监听MySQL的binlog，把遗漏的数据重新写入Kafka，或者直接从数据库导出数据，批量导入。

第五，优化消费逻辑。比如把单条处理改成批量处理，减少数据库连接次数；把同步处理改成异步处理，提高吞吐量。

我之前遇到过一次消费积压，智慧矿山的矿车位置数据消费积压了800万条。当时我们先扩容了消费者实例，从3个扩到了15个，消费速度提升了5倍。同时跳过了300万条非核心数据，优先处理最新的矿车位置数据。等消费赶上后，用binlog回放把跳过的数据补回来了。

最重要的是建立监控和告警机制。比如监控Kafka的lag，如果lag超过10万就告警，及时发现问题，避免积压过多。

总结一下，处理消费积压的核心是：临时扩容 + 跳过非核心数据 + 事后补数据 + 优化消费逻辑，同时建立监控告警。”

追问应对：

面试官：”如果跳过的数据补不回来怎么办？”

我：”如果跳过的数据补不回来，就会导致数据丢失。这时候需要评估数据的重要性，如果是核心数据，就不能跳过，必须慢慢消费；如果是非核心数据，可以接受丢失，或者用其他方式补充，比如从其他系统同步。另外，在跳过数据之前，要做好备份，防止补不回来。”

面试官：”如何防止消费积压再次发生？”

我：”防止消费积压再次发生可以从几个方面入手：首先，做好容量规划，根据业务增长提前扩容；其次，优化消费逻辑，提高消费速度；最后，建立监控告警，及时发现积压问题。另外，可以设置消费组的最大延迟时间，当延迟超过阈值时自动扩容。”

面试官：”在矿山场景中，消费积压会有什么安全风险？”

我：”在矿山场景中，消费积压会导致矿车位置数据延迟，进而影响调度决策的准确性。比如矿车已经移动到了新位置，但调度中心还在使用旧位置数据做出调度决策，可能会导致矿车碰撞。所以我们对Kafka的lag监控要求很高，一旦lag超过阈值，会立即触发告警。”

场景21（新增）：线上接口响应慢如何排查？

考察点：全链路追踪、性能分析、瓶颈定位

  1. 监控告警：查看接口的响应时间、错误率、QPS
  2. 链路追踪：用SkyWalking/Jaeger查看请求的完整链路
  3. 数据库分析：用Explain分析慢SQL
  4. 代码分析：用Arthas查看方法执行时间

常见原因：

  • 慢SQL
  • 网络延迟
  • 第三方服务响应慢
  • 代码逻辑问题

答：

面试官：”线上接口响应慢，怎么排查？”

我：”接口响应慢是线上常见问题，我一般按这个流程排查。

第一步，查看监控告警。用Prometheus + Grafana查看接口的响应时间、错误率和QPS，看看是所有请求都慢还是部分请求慢。

第二步，用链路追踪工具，比如SkyWalking，查看请求的完整链路。看看请求在哪个环节耗时最长，是数据库查询慢，还是调用第三方服务慢，还是代码逻辑问题。

第三步，如果是数据库查询慢，就用Explain分析慢SQL，看看有没有走索引，有没有全表扫描。如果是调用第三方服务慢，就检查第三方服务的状态，看看是不是网络问题或者第三方服务本身慢。

第四步，如果是代码逻辑问题，就用Arthas来分析，查看方法的执行时间，定位耗时最长的方法。

我之前遇到过一个案例，智慧矿山的调度查询接口响应慢，排查发现是一个SQL没有走索引，全表扫描了一张500万行的矿车任务表，导致查询时间超过10秒。后来加了索引，查询时间降到了100毫秒以内。

还有一种情况是调用第三方服务慢，比如调用定位服务获取矿车位置数据，有时候网络延迟会导致接口响应慢。这时候可以加超时设置和熔断机制，避免第三方服务影响主业务。

在智慧矿山项目中，我们对接口响应时间的要求很高，调度接口的响应时间要控制在100ms以内，否则会影响矿车的实时调度。所以我们设置了响应时间超过200ms就告警，确保及时发现问题。

总结一下，接口响应慢的排查流程是：监控告警 → 链路追踪 → 数据库分析 → 代码分析。”

追问应对：

面试官：”如果所有环节都正常，但接口还是慢怎么办？”

我：”如果所有环节都正常，但接口还是慢，可能是一些隐性问题。比如，线程池满了，大量请求在排队等待；或者是GC频繁，导致停顿时间长；或者是网络带宽不够，导致数据传输慢。可以用jstack查看线程状态，用jstat查看GC情况，用iftop查看网络带宽。”

面试官：”在矿山场景中，接口响应慢会有什么安全风险？”

我：”在矿山场景中，接口响应慢会导致调度指令延迟，进而影响矿车的安全行驶。比如调度中心下发的避障指令延迟了，矿车无法及时刹车，可能会导致碰撞。所以我们对接口响应时间的要求很高，设置了严格的监控和告警机制。”

场景22（新增）：数据库死锁如何排查？

考察点：事务管理、锁机制、并发控制

排查流程：

  1. 查看死锁日志：SHOW ENGINE INNODB STATUS
  2. 分析死锁信息：找到死锁的事务和SQL
  3. 定位问题代码：找到导致死锁的业务逻辑
  4. 优化代码：避免死锁的发生

关键命令：

常见原因：

  • 事务顺序不一致
  • 锁粒度太大
  • 事务执行时间太长
  • 热点数据竞争

答：

面试官：”数据库死锁怎么排查？”

我：”数据库死锁是并发场景中常见的问题，我一般按这个流程排查。

第一步，查看死锁日志。用SHOW ENGINE INNODB STATUS命令查看InnoDB的状态，里面会有死锁的详细信息，包括死锁的事务ID、SQL语句、锁类型等。

第二步，分析死锁信息。找到死锁的两个事务，看看它们分别执行了什么SQL，加了什么锁。一般来说，死锁是因为两个事务互相持有对方需要的锁。

第三步，定位问题代码。根据死锁日志中的SQL语句，找到对应的业务逻辑，看看为什么会产生死锁。

第四步，优化代码。避免死锁的方法有几种：一是保证事务的顺序一致，比如所有事务都按相同的顺序访问表；二是减小锁粒度，比如用行锁代替表锁；三是缩短事务执行时间，避免长时间持有锁；四是避免热点数据的竞争。

我之前遇到过一个死锁案例，智慧矿山的调度系统中，两个事务同时更新矿车状态和任务状态，因为更新顺序不一致，导致死锁。后来我们统一了更新顺序，先更新任务状态，再更新矿车状态，问题就解决了。

在智慧矿山项目中，我们对数据库的并发控制要求很高，因为调度系统有大量的并发请求，需要保证数据的一致性。所以我们设置了死锁监控，一旦发生死锁，会立即触发告警。”

追问应对：

面试官：”如何避免数据库死锁？”

我：”避免数据库死锁可以从几个方面入手：首先，保证事务的顺序一致，所有事务都按相同的顺序访问表；其次，减小锁粒度，用行锁代替表锁；再次，缩短事务执行时间，避免长时间持有锁；最后，避免热点数据的竞争。另外，可以设置事务的超时时间，当事务执行时间超过阈值时自动回滚。”

面试官：”在矿山场景中，数据库死锁会有什么安全风险？”

我：”在矿山场景中，数据库死锁会导致调度事务无法提交，进而影响矿车的调度。比如两个事务互相等待对方的锁，导致调度指令无法下发，矿车无法正常行驶。所以我们对数据库的死锁监控要求很高，一旦发生死锁，会立即触发告警，通知运维人员处理。”

场景23（新增）：熔断与降级如何实现？

考察点：容错机制、服务降级、故障隔离

核心组件：

组件 作用 实现方式
熔断器 当服务故障时，快速失败，避免级联故障 Resilience4j/Hystrix
降级 当服务故障时，返回备用响应 缓存数据/默认值
限流 限制请求频率，防止服务被打垮 Sentinel/Redis

Resilience4j实现：

答：

面试官：”如何实现熔断与降级？”

我：”熔断与降级是分布式系统中的容错机制，用于防止级联故障。

首先是熔断器，当服务的故障比例超过阈值时，熔断器会打开，后续请求会快速失败，不再调用故障服务。经过一段时间后，熔断器会进入半开状态，允许少量请求尝试调用故障服务，如果成功就关闭熔断器，如果失败就继续打开。

然后是降级，当服务故障时，返回备用响应，而不是报错。备用响应可以是缓存的数据，也可以是默认值。比如调用定位服务失败了，可以返回上一次缓存的矿车位置数据。

在智慧矿山项目中，我们用Resilience4j来实现熔断与降级。比如调度服务调用定位服务，如果定位服务的故障比例超过50%，熔断器会打开，后续请求会直接返回降级响应。降级响应是上一次缓存的矿车位置数据，这样即使定位服务故障，调度服务也能正常运行。

还有限流，限制每个服务的请求频率，防止服务被打垮。我们用Sentinel来实现限流，比如每个矿车每秒最多处理10个调度请求。

在矿山场景中，熔断与降级特别重要，因为调度系统需要高可用，即使某个依赖服务故障，也不能影响调度功能。比如定位服务故障了，调度系统可以用缓存的位置数据继续调度，确保矿车的安全行驶。”

追问应对：

面试官：”熔断器的三个状态是什么？”

我：”熔断器有三个状态：关闭状态、打开状态和半开状态。关闭状态是正常状态，所有请求都会调用服务；打开状态是故障状态，所有请求都会快速失败；半开状态是恢复状态，允许少量请求尝试调用服务，如果成功就切换到关闭状态，如果失败就切换到打开状态。”

面试官：”如何设计降级策略？”

我：”设计降级策略要考虑几个因素：首先，降级响应的质量，要保证降级响应能满足业务需求；其次，降级的触发条件，要设置合理的阈值；最后，降级的恢复策略，要设置合理的恢复时间。在智慧矿山项目中，我们的降级策略是返回上一次缓存的数据，这样既能保证调度功能正常，又能保证数据的时效性。”

场景24（新增）：系统可观测性建设

考察点：日志、监控、链路追踪、告警

核心组件：

组件 作用 实现方式
日志 记录系统运行状态 ELK/Grafana Loki
监控 收集系统指标 Prometheus + Grafana
链路追踪 追踪请求的完整链路 SkyWalking/Jaeger
告警 及时通知异常情况 Alertmanager + 钉钉/短信

Prometheus指标收集：

答：

面试官：”如何建设系统的可观测性？”

我：”系统的可观测性是指能够理解系统内部状态的能力，主要包括日志、监控、链路追踪和告警四个方面。

首先是日志，要收集系统的运行日志，包括业务日志和技术日志。用ELK或者Grafana Loki来收集和存储日志，方便查询和分析。日志要包含请求ID、时间戳、日志级别、业务信息等，方便问题排查。

其次是监控，要收集系统的指标，包括CPU使用率、内存使用率、接口响应时间、错误率、QPS等。用Prometheus来收集指标，用Grafana来展示指标。监控要设置合理的阈值，当指标超过阈值时触发告警。

然后是链路追踪，要追踪请求的完整链路，查看请求在各个服务之间的流转情况，定位耗时最长的环节。用SkyWalking或者Jaeger来实现，在每个服务中注入追踪信息，比如Trace ID和Span ID。

最后是告警，要设置合理的告警规则，当系统出现异常时及时通知相关人员。告警渠道可以有邮件、钉钉、短信等，根据告警的严重程度选择不同的渠道。

在智慧矿山项目中，我们建设了完整的可观测性体系：用ELK收集日志，用Prometheus + Grafana监控指标，用SkyWalking做链路追踪，用钉钉和短信做告警通知。这样当系统出现问题时，我们能快速定位和解决。”

追问应对：

面试官：”如何设计告警规则？”

我：”设计告警规则要遵循几个原则：首先，告警要准确，避免误报和漏报；其次，告警要分级，根据严重程度分为P0、P1、P2等；再次，告警要有明确的处理流程，知道谁来处理、怎么处理；最后，告警要收敛，避免同一问题产生大量告警。具体的告警阈值要根据业务情况来设置，比如CPU使用率超过80%告警，响应时间超过500毫秒告警等。”

面试官：”在矿山场景中，可观测性有什么特殊要求？”

我：”在矿山场景中，可观测性的特殊要求是实时性和安全性。实时性方面，监控数据要实时更新，告警要实时通知，因为调度系统需要实时响应。安全性方面，监控数据和日志要加密存储，防止敏感信息泄露。同时，要设置安全审计，记录所有的操作日志，方便安全检查和事故追溯。”
