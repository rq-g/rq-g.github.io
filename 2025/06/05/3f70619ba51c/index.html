MySQL高可用方案对比——MHA、Orchestrator与MySQL InnoDB Cluster

发布于 2025-06-05 分类：技术, 2025, 高可用 👁

前言

在实际场景中，MySQL 作为核心关系型数据库承载了设备监控数据、告警记录、人员定位、生产调度等关键业务。矿山场景对数据层高可用提出了极高要求——井下网络抖动频繁、边缘节点与中心机房之间链路不稳定，任何一次主库不可用都可能导致告警延迟或数据丢失，直接影响安全生产。

MySQL 高可用是数据层高可用的基石。MHA、Orchestrator、MySQL InnoDB Cluster 是三种主流方案，各有优劣。选型不当可能导致主从切换失败或数据丢失。本文将从 MySQL 复制原理出发，深入剖析三种方案的架构细节、切换流程、数据一致性保证机制，并结合实际项目的实际运维经验，给出选型建议和常见问题解决方案。

MySQL 复制原理基础

在深入讨论高可用方案之前，必须理解 MySQL 复制的底层机制，因为所有高可用方案都建立在复制之上。

Binlog（二进制日志）

Binlog 是 MySQL Server 层记录所有数据变更操作的日志，是复制的基石。

  • Statement 格式：记录 SQL 语句本身，日志量小但主从不一致风险高（如 NOW()、UUID() 函数）
  • Row 格式：记录行变更前后的值，日志量较大但数据一致性有保证，是生产环境推荐格式
  • Mixed 格式：默认 Statement，遇到不确定函数自动切换 Row，是前两者的折中

GTID（全局事务标识符）

GTID 是 MySQL 5.6 引入的事务唯一标识，格式为 server_uuid:transaction_id（如 3e11fa47-71ca-11e1-9e33-c80aa9429562:1-5）。GTID 的核心价值在于简化主从切换和故障恢复——不再需要手动查找 binlog 位点。

GTID 在高可用中的关键作用：

  1. 主从切换时无需定位 binlog 位点，新主库的 Executed_Gtid_Set 即为数据同步位点
  2. CHANGE MASTER TO 自动对齐，避免人为位点计算错误
  3. 校验主从数据一致性：对比主从的 Executed_Gtid_Set 是否一致

Relay Log（中继日志）

Relay Log 是从库上保存从主库拉取的 binlog 副本，从库的 IO 线程将主库 binlog 写入 Relay Log，SQL 线程从中读取并执行。

Relay Log 在 MHA 中的特殊意义：当主库宕机时，主库上已执行但未发送给从库的 binlog 可能丢失。MHA 的核心思路就是通过比较各从库 Relay Log 的差异，尽可能恢复这些”未传 binlog”。

复制线程模型

半同步复制：主库执行事务后，至少等待一个从库确认收到 binlog 才返回客户端成功。相比异步复制，半同步大幅降低了数据丢失风险。

实际项目建议所有方案均开启半同步复制，rpl_semi_sync_master_timeout 设置为 3000ms（3秒），在网络抖动频繁的井下环境中避免频繁降级。

MHA 方案

MHA 架构

MHA（Master High Availability）由日本 DeNA 公司 Youshimatsu 开发，是 MySQL 高可用领域最早被广泛使用的开源方案之一。

组件 部署位置 职责
MHA Manager 独立管理服务器 监控主库状态；主库故障时选择最新从库；协调差异 Relay Log 应用；触发 VIP 切换脚本
MHA Node 每个 MySQL 实例 保存 Binlog（save_binary_logs）；应用 Relay Log（apply_diff_relay_logs）；清理 Relay Log

MHA 详细切换流程

MHA 的切换流程是其核心价值所在，理解每一步的细节对于排查切换失败至关重要。

步骤 操作 详细说明
1 Manager 检测主库不可用 通过 ping 连接检测，默认每 ping_interval（默认3秒）检测一次，连续 ping_type 次失败后判定主库宕机
2 尝试 SSH 到主库 尝试通过 SSH 连接主库，如果能连通则执行 save_binary_logs 保存主库上未发送的 binlog
3 选择最新从库 对比所有从库的 Exec_Master_Log_Pos / Executed_Gtid_Set，选择数据最接近主库的从库作为”候选主库”
4 识别差异 Relay Log 比较最新从库与其他从库的 Relay Log 差异，生成差异补丁文件
5 应用差异 Relay Log 将差异 Relay Log 应用到其他从库，使所有从库数据对齐到最新从库
6 提升最新从库为主库 执行 RESET SLAVE ALL; 断开复制关系，新主库开始独立写入
7 应用主库未传 Binlog 如果步骤2成功保存了主库未传 binlog，则应用到新主库，最大限度减少数据丢失
8 VIP 漂移到新主库 执行 master_ip_failover 脚本，将 VIP 从旧主库迁移到新主库
9 其他从库指向新主库 对其他从库执行 CHANGE MASTER TO 指向新主库，启动复制
10 完成 Manager 退出，等待人工介入或配置自动重启 Manager

Orchestrator 方案

Orchestrator 架构

Orchestrator 由 GitHub 工程师 Shlomi Noach 开发，用 Go 语言编写，是一个 MySQL 高可用和复制拓扑管理工具。与 MHA 的”脚本式”切换不同，Orchestrator 是一个持续运行的服务，提供可视化拓扑管理和自动化故障恢复。

拓扑发现与管理

Orchestrator 的核心能力之一是自动发现和持续追踪 MySQL 复制拓扑。

发现机制：

  1. 连接到已知的 MySQL 实例，查询 SHOW SLAVE STATUS 获取其上游主库和下游从库
  2. 递归遍历整个复制链，自动构建完整拓扑图
  3. 周期性刷新拓扑状态，检测拓扑变化

拓扑管理操作：

操作 命令/API 说明
发现实例 discover 将新实例加入拓扑
忘记实例 forget 从拓扑中移除实例
开始维护 begin-maintenance 标记实例维护中，不参与故障检测
优雅主库切换 graceful-master-takeover 计划内切换，先停止写入再切换
强制主库切换 force-master-failover 主库不可用时的强制切换
移动从库 repoint 将从库指向不同的上游
重构拓扑 regroup-replicas 重新组织从库层级

自动故障检测与切换

Orchestrator 的故障检测采用多级确认机制，避免网络抖动导致的误切换。

候选主库选择规则：

  1. 优先选择数据最新的从库（Exec_Master_Log_Pos 最大 / GTID 集合最全）
  2. 优先选择 read_only=0 的实例
  3. 优先选择已配置为候选的实例（candidate 标记）
  4. 优先选择版本与原主库一致的实例
  5. 优先选择延迟最小的实例

优雅切换（计划内维护）

与 MHA 不同，Orchestrator 原生支持优雅的主库切换，适用于计划内维护（如主库系统升级、硬件更换）。

Orchestrator 优劣分析

优势 劣势

Web UI 可视化拓扑管理 切换过程中无法恢复主库未传 binlog

MySQL InnoDB Cluster 方案

InnoDB Cluster 整体架构

MySQL InnoDB Cluster 是 MySQL 官方提供的高可用方案，由三个核心组件协同工作：

Group Replication 详解

Group Replication 是 InnoDB Cluster 的核心复制引擎，基于 Paxos 分布式共识协议实现，与传统的异步/半同步复制有本质区别。

单主模式 vs 多主模式：

模式 写入点 冲突处理 适用场景
单主模式（推荐） 仅 PRIMARY 节点可写 无冲突 大多数业务场景
多主模式 所有节点可写 基于认证的冲突检测（先提交者胜） 多活写入、异地多活

MySQL Router 详解

MySQL Router 是 InnoDB Cluster 的流量入口，负责将客户端请求路由到正确的后端实例。

路由策略：

端口 路由策略 说明
6446 读写（read-write） 始终路由到 PRIMARY 节点
6447 只读（read-only） 轮询路由到 SECONDARY 节点
64460 管理（x协议） MySQL Shell 管理连接
64470 管理API Router 自身监控端口

Router 自动感知：Router 持续从 Group Replication 的元数据获取集群状态，PRIMARY 切换后 Router 自动将读写流量路由到新 PRIMARY，客户端无需感知后端变化。

MySQL Shell 详解

MySQL Shell 是 InnoDB Cluster 的管理工具，提供统一的集群创建、扩展、维护接口。

监控与告警配置

无论采用哪种高可用方案，完善的监控和告警体系都是不可或缺的。以下是实际项目中使用的监控指标和告警规则。

核心监控指标

指标 采集方式 告警阈值 说明
复制延迟（Seconds_Behind_Master） SHOW SLAVE STATUS > 30s Warning，> 120s Critical 从库落后主库的秒数
GTID 集合差异 Executed_Gtid_Set 对比 主从不一致 检测数据不一致
Binlog 累积大小 SHOW BINARY LOGS > 10GB 未清理的 binlog 过大

常见项目问题与解决方案

以下是在实际项目及多个企业级项目中遇到的 MySQL 高可用问题及解决方案，按故障场景分类整理。

序号 问题 故障场景 根因分析 解决方案
1 MHA 切换失败，报”Failed to save binary log” 主库宕机，SSH 无法连接 主库磁盘满或 SSH 密钥失效，导致无法保存未传 binlog 1. 提前配置 secondary_check_script 二次确认 2. 定期检查 SSH 互信和磁盘空间 3. 配置磁盘使用率告警（>85%）
2 MHA 切换后从库数据不一致 主库宕机切换后，应用报数据缺失 使用异步复制，主库未传 binlog 丢失 1. 开启半同步复制 2. 配置 rpl_semi_sync_master_timeout 为较大值（如5000ms）3. 切换后通过 pt-table-checksum 校验数据
3 MHA Manager 单点故障 Manager 所在服务器宕机，集群无自动切换能力 MHA Manager 本身无高可用 1. 部署双 Manager + Keepalived VIP 2. 或使用 systemd 自动重启 Manager 3. 配置 Manager 进程监控
4 Orchestrator 误切换 网络抖动导致主库短暂不可达 故障检测过于敏感，未做二次确认 1. 增大 InstancePollSeconds（如5→10）2. 配置 RecoveryPeriodBlockSeconds 防止连续切换 3. 部署多 Orchestrator 实例做交叉检测
5 Orchestrator 切换后应用连不上新主库 VIP 切换脚本执行失败 arping 未发送免费 ARP，交换机 ARP 缓存未刷新 1. VIP 切换脚本中添加 arping -c 3 -A 2. 检查网卡名称是否正确 3. 测试环境中先验证 VIP 漂移
6 InnoDB Cluster 整体不可用 2 个 SECONDARY 同时宕机 3 节点集群丢失 2 节点，无法形成多数派 1. 部署 5 节点（容忍 2 节点故障）2. 或使用仲裁节点（MySQL 8.0.14+）3. 准备 forceQuorumUsingPartitionOf 应急脚本
7 InnoDB Cluster 新 PRIMARY 选举慢 PRIMARY 宕机后 30+ 秒才完成选举 Group Replication 的 member_expel_timeout 设置过大 1. 调整 group_replication_member_expel_timeout=5 2. 优化网络延迟（同机房部署）3. 确保节点间通信端口 33061 畅通
8 Group Replication 节点被驱逐后无法自动重连 网络闪断导致节点被驱逐 autoRejoinTries 未配置或次数耗尽 1. 设置 group_replication_autorejoin_tries=3 2. 监控被驱逐事件并告警 3. 预案中包含 cluster.rejoinInstance() 手动重连步骤
9 MySQL Router 无法感知 PRIMARY 切换 PRIMARY 切换后，Router 仍将请求路由到旧 PRIMARY Router 元数据缓存刷新间隔过长 1. 调整 Router 的 ttl 参数（如 0.5 秒）2. 确认 Router 与集群元数据表连通 3. 部署多 Router 实例 + 负载均衡
10 大事务导致 Group Replication 超时 批量 DELETE 百万行数据，Group Replication 广播超时 事务过大导致消息超出 communication_max_message_size 或认证超时 1. 大事务拆分为小批次（每批 1000~5000 行）2. 增大 group_replication_communication_max_message_size 3. 使用 group_replication_transaction_size_limit 限制事务大小
11 半同步复制频繁降级为异步 网络抖动导致从库 ACK 超时 rpl_semi_sync_master_timeout 设置过小 1. 增大超时到 3000~5000ms 2. 监控半同步状态变化 3. 评估网络质量，必要时优化从库地理位置
12 从库复制延迟持续增大 从库 SQL 线程单线程回放，无法追上主库写入速度 主库写入压力大，单线程回放成为瓶颈 1. MySQL 5.7+ 开启多线程复制：slave_parallel_type=LOGICAL_CLOCK; slave_parallel_workers=8 2. MySQL 8.0+ 使用 slave_parallel_type=DATABASE 3. 从库使用更高配置的磁盘（NVMe SSD）
13 复制中断 1062 Duplicate Entry 主从切换后，新主库写入与旧数据冲突 切换过程中旧主库未完全停止写入（脑裂） 1. 配置 read_only=1 + super_read_only=1 防止旧主库写入 2. MHA 切换脚本中添加 SET GLOBAL read_only=1 3. 使用 sql_slave_skip_counter 或 pt-slave-restart 跳过错误（需评估）
14 GTID 复制报错 1236 从库连接主库时 binlog 已被清理 主库 expire_logs_days 设置过小，从库延迟过大 1. 增大 expire_logs_days=7 2. 从库开启 relay_log_recovery=ON 3. 使用 clone 插件或 xtrabackup 重建从库
15 Binlog 磁盘空间耗尽 主库 binlog 大量堆积未清理 sync_binlog=1 + 高 TPS 导致 binlog 刷写频繁，expire_logs_days 未及时清理 1. 合理设置 expire_logs_days（7~14天）2. 配置磁盘空间告警 3. 手动 PURGE BINARY LOGS 清理 4. 评估是否需要 binlog_format=ROW 改为 MIXED 减少日志量

总结

MySQL 高可用方案选型要看业务阶段和需求：新项目直接上 InnoDB Cluster，老项目用 Orchestrator。MHA 虽然经典但已停更，不推荐新项目使用。

无论哪种方案，都要注意以下核心原则：

  1. 开启半同步复制（MHA/Orchestrator）或使用 Group Replication（InnoDB Cluster），减少数据丢失风险
  2. 定期演练主从切换，确保切换脚本和流程可用——实际项目每季度进行一次切换演练
  3. 完善监控告警，对复制延迟、半同步状态、节点健康度进行实时监控
  4. 准备应急预案，包括手动切换步骤、数据校验脚本、从库重建流程
  5. 评估网络环境，井下网络环境特殊，需合理设置超时参数和故障检测阈值
  6. 数据备份不可替代，高可用不等于备份，必须配合定期全量 + 增量备份
