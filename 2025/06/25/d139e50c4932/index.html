Java内存模型JMM——从happens-before到内存屏障

发布于 2025-06-25 分类：技术, 2025, 并发编程 👁

前言

volatile为什么能保证可见性？双重检查锁为什么必须加volatile？synchronized和volatile的区别？这些问题都指向同一个核心——Java内存模型（JMM）。理解JMM是深入理解并发编程的基础。这篇文章从JMM核心模型到happens-before规则，从volatile内存屏障到synchronized锁升级，结合实际项目实战经验，全面深入分析JMM核心原理。

JMM核心模型

Java内存模型抽象结构

Java内存模型（Java Memory Model，JMM）定义了Java虚拟机如何与内存交互的规范。JMM是Java语言规范的一部分（JSR-133），它描述的是一种抽象概念，而非真实物理内存布局。

内存区域 说明 类比
主内存 存储共享变量，所有线程共享 数据库
工作内存 每个线程的私有内存，存储共享变量的副本 本地缓存

核心问题：线程读取的是工作内存的副本，不是主内存

  • 线程A修改了共享变量，线程B可能看不到 → 可见性问题
  • 编译器/CPU可能对指令重排序 → 有序性问题
  • 复合操作（如i++）非原子 → 原子性问题

在实际场景中，车辆GPS数据并发处理时，多个工作线程从Kafka消费GPS消息，各自工作内存中缓存了设备状态副本。如果状态更新未正确同步到主内存，监控大屏就会显示过期的设备位置，这在矿山安全监控中是不可接受的。

JMM三大特性

特性 含义 保证手段
原子性 操作不可分割，要么全部执行要么不执行 synchronized、Lock、Atomic类
可见性 一个线程的修改对其他线程立即可见 volatile、synchronized、final
有序性 程序执行的顺序符合预期，禁止不合理的重排序 volatile、happens-before、synchronized

操作规则要点：

  1. read和load必须按顺序配对出现，但不要求连续执行
  2. store和write必须按顺序配对出现，但不要求连续执行
  3. 不允许一个线程丢弃最近的assign操作（变量在工作内存改变后必须同步回主内存）
  4. 不允许一个线程无原因地（无assign操作）将数据从工作内存同步回主内存
  5. 一个新变量只能在主内存中诞生，不允许在工作内存中直接使用未被初始化的变量
  6. 一个变量同一时刻只允许一条线程对其进行lock操作，但可以被同一线程多次lock
  7. 对变量执行unlock前，必须将其同步回主内存
  8. 不允许对未被lock的变量执行unlock，也不允许unlock其他线程lock的变量

智慧矿山场景：当设备状态监控线程（线程A）将”矿车-001”的状态从”运行”改为”故障”时，经历assign→store→write三步将新值写入主内存；调度线程（线程B）要看到最新状态，需要read→load→use三步从主内存读取。如果中间缺少同步机制，线程B可能始终读到旧值。

happens-before规则

happens-before是JMM的核心概念，它定义了操作之间的可见性保证：如果操作A happens-before 操作B，则A的结果对B可见。happens-before并不是说”A必须在B之前执行”，而是说”如果A在B之前执行，那么A的结果对B可见”。

8大happens-before规则

# 规则 含义 实际场景
1 程序顺序规则 同一线程中，前面的操作happens-before后面的操作 单线程代码按顺序执行（但不禁止重排序，只要重排序不影响单线程语义）
2 volatile变量规则 volatile写happens-before后续的volatile读 状态标志位更新后其他线程立即可见
3 锁规则 unlock happens-before后续对同一把锁的lock 线程退出synchronized块后的修改对下一个进入的线程可见
4 传递性 A hb B, B hb C → A hb C 链式推导可见性
5 线程启动规则 Thread.start() happens-before线程内的操作 主线程设置参数后启动子线程，子线程一定能看到参数
6 线程终止规则 线程内的操作happens-before Thread.join()返回 子线程的计算结果在join后对主线程可见
7 中断规则 interrupt() happens-before检测到中断 调用interrupt后，被中断线程的isInterrupted()返回true
8 对象终结规则 构造方法happens-before finalize() 对象在finalize中一定能看到构造方法中初始化的值

volatile原理

内存屏障类型详解

内存屏障（Memory Barrier / Memory Fence）是CPU和编译器提供的同步指令，用于禁止特定类型的指令重排序并保证内存可见性。JMM将内存屏障分为4类：

屏障类型 指令示例 说明 作用
LoadLoad Load1; LoadLoad; Load2 在Load2及后续读操作前，保证Load1要读的数据被读取完毕 禁止Load1和Load2之间的读重排序
StoreStore Store1; StoreStore; Store2 在Store2及后续写操作前，保证Store1的写操作对其他处理器可见 禁止Store1和Store2之间的写重排序
LoadStore Load1; LoadStore; Store2 在Store2及后续写操作前，保证Load1要读的数据被读取完毕 禁止Load1和Store2之间的读-写重排序
StoreLoad Store1; StoreLoad; Load2 在Load2及后续读操作前，保证Store1的写操作对所有处理器可见 禁止Store1和Load2之间的写-读重排序，开销最大

各处理器架构的内存屏障支持：

处理器 LoadLoad StoreStore LoadStore StoreLoad
x86 自动保证 自动保证 自动保证 mfence / lock前缀指令
ARM dmb dmb dmb dmb
SPARC membar #LoadLoad membar #StoreStore membar #LoadStore membar #StoreLoad
POWER lwsync lwsync lwsync sync

x86是强内存模型（TSO），只允许Store-Load重排序，因此只需要StoreLoad屏障。而ARM是弱内存模型，几乎所有重排序都可能发生，需要完整的屏障支持。

CAS与ABA问题

CAS原理

CAS（Compare-And-Swap）是一条CPU级别的原子指令，包含三个操作数：内存位置V、预期旧值A、新值B。只有当V的值等于A时，才将V的值更新为B，否则不做任何操作。

Java 9+ VarHandle内存访问模式

VarHandle简介

Java 9引入了java.lang.invoke.VarHandle，提供了比Atomic类更细粒度的内存访问控制。VarHandle统一了字段访问、数组访问和内存屏障操作。

plain get/set 普通读写，无特殊保证 无

核心区别：

  • volatile保证可见性和有序性，不保证原子性
  • synchronized保证原子性、可见性、有序性
  • volatile适合：一个线程写、多个线程读
  • synchronized适合：多线程读写复合操作

常见项目问题与解决方案

以下是实际项目中遇到的真实并发问题及解决方案：

# 问题 现象 原因 解决方案
1 DCL未加volatile导致NPE 单例对象字段为null或默认值 new操作重排序为”分配→赋值→初始化”，其他线程看到非null引用但对象未初始化 单例引用加volatile，禁止指令重排序
2 volatile误用保证复合原子性 计数器值丢失（少于实际操作数） volatile仅保证单次读/写原子性，i++是read-modify-write复合操作 使用AtomicInteger或synchronized
3 synchronized锁粒度过粗 GPS数据处理吞吐量低，监控大屏刷新延迟 整个processData方法加synchronized，导致数据处理和状态更新互斥 缩小锁范围，只锁必要的临界区；使用读写锁分离读写
4 偏向锁撤销引发STW 系统偶尔出现几十毫秒停顿，GPS数据积压 多个线程首次同时访问同一锁对象，批量偏向锁撤销需全局安全点 关闭偏向锁(-XX:-UseBiasedLocking)或预热锁对象
5 虚假共享导致性能下降 LongAdder计数器性能远低于预期 多个Cell对象在同一缓存行，MESI协议导致缓存频繁失效 使用@Contended注解或手动缓存行填充
6 LongAdder在设备计数场景优化不当 GPS数据处理计数sum()值不稳定 LongAdder.sum()遍历Cell时可能有并发修改，非精确快照 理解sum()语义，业务允许弱一致性用LongAdder，需精确值用AtomicLong
7 线程间共享状态未正确同步 监控大屏显示设备状态与实际不一致 工作线程修改设备状态后未刷新到主内存，大屏线程读到旧值 共享状态使用volatile或通过synchronized保护
8 CAS自旋导致CPU飙升 CPU使用率持续90%+，但TPS没有提升 大量线程竞争同一AtomicLong，CAS失败后自旋浪费CPU 使用LongAdder分散热点，或使用分段锁
9 锁粗化与锁消除未生效 性能分析发现synchronized开销仍很大 逃逸分析被关闭(-XX:-DoEscapeAnalysis)或锁对象逃逸出方法 开启逃逸分析，确保锁对象不逃逸；考虑使用非同步替代方案
10 MonitorEnter/MonitorExit不匹配 线程死锁，系统假死 字节码层面monitorenter和monitorexit不配对，锁未释放 确保同步代码块在异常路径也能释放锁；不要手动操作Monitor
11 wait/notify使用错误 线程永久等待，不唤醒 wait()在synchronized外调用或notify()唤醒了错误线程 wait/notify必须在synchronized内使用；使用Condition替代
12 StampedLock饥饿问题 读线程持续获取锁，写线程长时间等待 StampedLock非公平，大量读请求可能使写请求饥饿 使用StampedLock的乐观读模式；控制读写比例
13 ConcurrentHashMap组合操作非原子 设备状态检查+更新出现竞态 containsKey+put是两个独立操作，中间可能被其他线程插入 使用putIfAbsent/computeIfAbsent等原子方法
14 ThreadLocal内存泄漏 服务运行几天后Old Gen持续增长 线程池中线程复用，ThreadLocal值不断积累且未remove 使用后及时调用remove()；或使用InheritableThreadLocal替代方案
15 FutureTask get()阻塞 主界面卡死，无法操作 future.get()在主线程调用，任务长时间未完成 使用带超时的get(timeout)；或使用CompletableFuture异步回调

总结

JMM是Java并发编程的理论基础，贯穿了从底层硬件到上层应用的所有并发机制：

核心模型：JMM通过主内存-工作内存的抽象模型，定义了线程间如何通过8种原子操作交互。理解这个模型是理解可见性、原子性、有序性三大问题的前提。

happens-before：定义了操作的可见性保证规则，是判断并发代码正确性的理论工具。通过链式推导可以在不加锁的情况下保证非volatile变量的可见性。

volatile：通过内存屏障保证可见性和有序性，但不保证原子性。在x86架构上，volatile写通过lock前缀指令实现StoreLoad屏障，volatile读无需额外指令。

synchronized：通过Monitor实现原子性，同时隐含保证可见性和有序性。JDK 6+的锁升级机制（无锁→偏向锁→轻量级锁→重量级锁）大幅提升了无竞争和低竞争场景的性能。

final：保证构造方法中初始化的final域在对象发布后的可见性，是安全发布的基础。

CAS与LongAdder：CAS是原子类的基础，但存在ABA问题和自旋开销；LongAdder通过分段CAS解决了高并发写场景的热点问题。

VarHandle：Java 9+提供了比volatile更细粒度的内存访问控制，支持9种访问模式按需选择屏障强度。

实战要点：

  1. 理解8种内存交互操作是分析可见性问题的基础
  2. happens-before链式推导是验证并发代码正确性的利器
  3. volatile不保证原子性，复合操作必须用synchronized或Atomic类
  4. LongAdder是高并发写场景的最优计数方案
  5. 警惕虚假共享、ThreadLocal泄漏、ConcurrentHashMap组合操作等常见陷阱

在实际场景中，车辆GPS数据的高并发处理和设备状态实时监控对JMM理解有很高要求。只有深入理解JMM原理，才能正确使用volatile、synchronized、Atomic等并发工具，避免隐蔽的并发bug。
