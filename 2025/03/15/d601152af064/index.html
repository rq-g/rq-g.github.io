领域建模实战——电商订单系统的领域模型设计

发布于 2025-03-15 分类：技术, 2025, 架构 👁

前言

在实际项目的建设过程中，我们面对的不仅仅是设备监控和数据分析，更核心的挑战是如何将复杂的矿山业务——从采购订单、物资调拨、设备维修工单到安全巡检——抽象为清晰的领域模型。智慧矿山系统涵盖供应链管理、仓储物流、设备全生命周期管理等多个业务域，其复杂度远超传统 CRUD 系统。正是在这个项目中，我们深刻体会到：DDD 最难的不是写代码，而是建模。

实际项目的订单域与电商订单系统有着极高的结构相似性：采购申请对应购物车，采购订单对应交易订单，物资出库对应发货，验收确认对应收货。因此，本文以电商订单系统为案例，系统性地展示从业务分析到领域模型设计的全过程，并结合实际项目的实战经验，深入探讨 DDD 战略设计与战术设计的落地实践。

一、DDD 总览：战略设计与战术设计

DDD 分为战略设计（Strategic Design）和战术设计（Tactical Design）两个层面，二者缺一不可。

1.1 战略设计：限界上下文与上下文映射

战略设计解决的是”如何拆分系统”的问题。核心概念包括：

  • 限界上下文（Bounded Context）：一个明确的语义边界，在其中每个模型都有确切的含义。同一个”订单”在订单上下文和物流上下文中含义不同——前者关注交易语义，后者关注配送语义。
  • 上下文映射（Context Map）：描述不同限界上下文之间的关系和集成方式。

上下文映射关系分类

映射关系 含义 典型场景 集成方式
合作关系（Partnership） 两个团队协同开发，接口变更需协商 订单上下文与支付上下文 同步调用 + 版本协商
客户-供应商（Customer-Supplier） 下游依赖上游，上游需考虑下游需求 订单上下文（供应商）→ 库存上下文（客户） 事件驱动 + 接口契约
遵奉者（Conformist） 下游完全遵循上游模型 物流上下文遵奉第三方物流接口 适配器模式
防腐层（ACL） 下游通过翻译层隔离上游模型 订单上下文通过 ACL 对接 legacy 系统 适配器 + 翻译器
开放主机服务（OHS） 上游提供标准协议 支付上下文提供标准支付 API REST/gRPC 标准接口
发布语言（PL） 使用通用交换格式 上下文间通过 JSON Schema 通信 事件/DTO
分道扬镳（Separate Ways） 不做集成，各自独立 报表上下文独立读取数据 数据库视图/数据湖
大泥球（Big Ball of Mud） 遗留系统，边界模糊 旧 ERP 系统的订单模块 防腐层隔离

在实际场景中，我们曾遇到一个典型问题：采购域和库存域最初被设计为合作关系，但团队排期总是冲突。后来调整为客户-供应商模式——采购域作为上游定义事件契约，库存域作为下游消费事件，迭代效率显著提升。

1.2 战术设计：构建块全景

战术设计解决的是”在限界上下文内部如何建模”的问题。以下是 DDD 战术构建块的完整对照：

构建块 定义 特征 典型示例 生命周期
实体（Entity） 有唯一标识的领域对象 有 ID，可变，通过 ID 判等 Order、OrderItem 长生命周期，需跟踪状态变化
值对象（Value Object） 无唯一标识的领域对象 无 ID，不可变，通过属性判等 Money、ShippingAddress 短生命周期，随实体消亡
聚合（Aggregate） 一致性边界内的一组对象 有聚合根，外部只通过根访问 Order（根）+ OrderItem 保证事务一致性
聚合根（Aggregate Root） 聚合的入口和协调者 全局唯一标识，负责不变量 Order 控制聚合内所有变更
领域事件（Domain Event） 领域中已发生的事情 不可变，过去时态命名 OrderCreatedEvent 触发跨聚合/跨上下文流程
领域服务（Domain Service） 不属于任何实体/值对象的业务逻辑 无状态，纯业务操作 OrderDomainService 协调多个聚合的业务操作
应用服务（Application Service） 用例编排，不包含业务规则 薼薄，只做编排 OrderApplicationService 事务边界、安全、日志
仓储（Repository） 聚合的持久化抽象 模拟集合接口 OrderRepository 隔离领域模型与基础设施
工厂（Factory） 复杂对象的创建逻辑 封装创建规则 OrderFactory 保证创建时的不变量

五、聚合设计

5.1 聚合设计原则

聚合是 DDD 中最关键也最容易被误用的概念。以下是聚合设计的核心原则：

原则 描述 反模式
一致性边界 聚合内的数据必须保证强一致性 把弱一致数据放进同一聚合
小聚合优先 聚合应尽量小，理想情况下只包含聚合根 一个 Order 包含所有历史操作记录
通过 ID 引用 聚合间通过 ID 引用而非直接持有对象引用 Order 直接持有 Payment 对象
单次事务只修改一个聚合 一个事务只修改一个聚合实例 一个事务同时修改 Order 和 Payment
最终一致性跨聚合 跨聚合的一致性通过领域事件实现 用分布式事务（2PC/Saga）强一致跨聚合
聚合根是唯一入口 外部只能通过聚合根修改聚合内对象 直接修改 OrderItem 而绕过 Order

六、值对象设计

6.1 值对象 vs 实体：核心区别

十一、常见项目问题与解决方案

以下是结合实际项目和电商订单系统实战中遇到的典型问题汇总：

# 问题 现象 原因 解决方案
1 贫血模型泛滥 Entity 只有 getter/setter，业务逻辑全在 Service 层，Service 代码膨胀到数千行 未理解 DDD 的”充血模型”理念，按事务脚本模式开发 将业务逻辑迁移到聚合根和实体中，Service 只做编排；采用测试驱动保证重构安全
2 聚合边界过大 Order 聚合包含收货记录、评价、发票等所有关联数据，加载一次耗时数秒，内存占用高 把弱一致性数据放进聚合，混淆了”关联”与”一致性” 聚合只包含强一致数据；评价、发票等独立为聚合，通过 orderId 引用关联
3 跨聚合强一致性 使用 @Transactional 同时修改 Order 和 Stock，分布式环境下事务经常超时 一个事务跨多个聚合，锁竞争严重 一个事务只修改一个聚合，跨聚合通过领域事件 + 最终一致性
4 值对象使用 String/BigDecimal 金额用 BigDecimal，地址用 String，没有封装业务规则，金额为负数、地址不完整等问题到处出现 原始类型偏执（Primitive Obsession），用基本类型替代领域概念 定义 Money、Address 等值对象，在构造器中封装校验规则
5 聚合间直接引用对象 Order 直接持有 Payment 对象引用，加载 Order 时必须级联查询支付信息 违反”通过 ID 引用”原则，导致聚合边界模糊 Order 只持有 paymentId: Long，需要支付信息时通过 PaymentRepository 单独加载
6 领域事件丢失 订单支付成功但库存未扣减，或事件重复消费导致库存多次扣减 事件发布与业务事务不在同一个事务中，或消费端未做幂等 采用事务性发件箱模式（Transactional Outbox）；消费端做幂等校验
7 N+1 查询问题 订单列表页查询 50 条订单，产生 51 条 SQL（1 查订单 + 50 查明细） JPA 懒加载 OrderItem，遍历时逐条查询 使用 JOIN FETCH 或 EntityGraph 一次性加载；列表查询走 CQRS 读模型
8 状态机实现混乱 if-else 链判断订单状态，漏掉某些转换路径，出现已取消订单被发货的 Bug 状态转换规则散落在多个方法中，没有统一的状态机 使用状态模式或状态枚举（如本文 OrderStatus），显式定义合法转换
9 领域模型与数据库模型耦合 领域对象直接加 @Entity 注解，加新字段要改数据库，改数据库影响领域逻辑 共享模型策略，领域层直接依赖持久化框架 采用双模型转换，领域模型和数据模型分离，通过 Converter 互转
10 库存预占与释放不一致 用户下单预占库存，但支付超时取消后库存未释放 超时取消事件未被库存上下文消费 确保事件订阅的完整性；添加库存预占超时自动释放机制
11 并发修改冲突 两个运营人员同时修改同一订单，后提交的覆盖前提交 乐观锁未配置，或聚合更新未检查版本号 使用 @Version 乐观锁；聚合根增加 version 字段，更新时检查
12 仓储接口泄露查询需求 OrderRepository 中出现 findByNameLike、findByStatusAndCreateTimeBetween 等大量查询方法 混淆了仓储（命令）和查询的职责 仓储只保留按 ID 查询和保存；复杂查询走 CQRS 查询端
13 应用服务包含业务逻辑 支付金额校验、折扣计算写在了 ApplicationService 中，导致无法复用 没有区分领域服务和应用服务的职责边界 业务逻辑下沉到领域服务或聚合根中，应用服务只做编排
14 值对象不可变性被破坏 Money 类提供了 setAmount 方法，外部直接修改金额绕过校验 值对象设计为可变，违反值对象不可变原则 移除 setter，所有修改方法返回新实例；字段加 final 修饰
15 读模型与写模型不分 订单列表查询需要关联用户表、商品表，直接加载 Order 聚合做关联查询，SQL 极慢 用领域模型（写模型）做查询，聚合加载了不必要的关联数据 引入 CQRS，读模型使用视图或 ES，按展示需求反范式化数据

总结

领域建模是 DDD 的核心难点，也是其最大价值所在。本文从实际项目的实战出发，以电商订单系统为案例，系统性地覆盖了 DDD 落地的关键环节：

  1. 战略设计：通过限界上下文划分系统边界，通过上下文映射确定团队间协作模式，这是系统拆分的第一步。
  2. 事件风暴：从业务事件出发，识别命令、聚合和读模型，让建模从业务出发而非从数据库出发。
  3. 聚合设计：小聚合优先，通过 ID 引用关联，领域事件保证最终一致性，避免分布式事务。
  4. 值对象：替代原始类型，封装业务规则，不可变设计保证安全性。
  5. 领域服务 vs 应用服务：领域服务承载业务规则，应用服务负责用例编排，职责分明。
  6. 仓储模式：隔离领域模型与基础设施，双模型转换是最务实的方案。
  7. CQRS：命令与查询分离，写模型保证业务一致性，读模型优化查询性能。
  8. 持久化实践：JPA 和 MyBatis-Plus 各有优劣，根据项目特点选择；值对象持久化要选对方案。

建模的关键是从业务出发，而不是从数据库表出发。简单业务不要过度建模，复杂业务才值得投入 DDD。实际项目的经验告诉我们：DDD 不是银弹，但对复杂业务系统而言，它是目前最有效的应对复杂度的方法论。
