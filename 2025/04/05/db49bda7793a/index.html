Spring Security OAuth2实战——微服务的统一认证授权

发布于 2025-04-05 分类：技术, 2025, 微服务 👁

前言

在实际场景中，我们面对的是一个典型的微服务架构体系：设备监控服务、安全预警服务、人员定位服务、生产调度服务等十余个微服务模块，前端同时存在管理后台（SSR）、移动端APP和矿区大屏展示三种客户端。这种架构下，每个服务各自实现认证授权显然不可行——用户不可能每访问一个服务就登录一次，权限数据也不可能分散在每个服务中维护。

我们最终选择了 OAuth2 + JWT + Spring Security 作为统一认证授权方案：认证中心统一颁发Token，Gateway统一验证Token，各微服务从请求头获取用户身份信息。本文将系统性地梳理这套方案的理论基础、实现细节以及在实际项目中踩过的坑。

一、OAuth2 四大授权流程详解

OAuth2 定义了四种标准授权模式，不同场景使用不同模式，理解每种模式的流程是设计认证架构的前提。

1.1 Authorization Code（授权码模式）

最安全、最完整的模式，适用于有后端的Web应用。实际项目的管理后台就使用此模式。

关键点：

  • 授权码 code 只能使用一次，且有效期极短（通常10分钟）
  • Token 通过后端直接交换，不经过浏览器，避免Token泄露
  • 可配合 state 参数防止 CSRF 攻击

1.2 Client Credentials（客户端凭证模式）

适用于服务间调用，没有用户参与。智慧矿山中，安全预警服务调用设备监控服务的内部接口就使用此模式。

关键点：

  • 只有 access_token，没有 refresh_token（因为没有用户，过期了重新申请即可）
  • Token 的 scope 限制客户端能访问的资源范围
  • client_secret 必须安全存储，不能暴露给前端

1.3 Password（密码模式）

适用于高度信任的客户端，如自有移动端APP。智慧矿山的矿工APP使用此模式。

关键点：

  • 用户密码直接传递给认证中心，客户端必须是可信的
  • 适合自有APP，绝对不适合第三方应用
  • Spring Security OAuth2 新版本中已标记为 Deprecated，建议迁移到 Authorization Code + PKCE

1.4 Refresh Token（刷新令牌流程）

所有涉及用户的模式都会返回 refresh_token，用于在 access_token 过期后无感刷新。

关键点：

  • Refresh Token 有效期长（7天~30天），Access Token 有效期短（2小时）
  • Refresh Token 只能使用一次（Rotation策略），用过后旧Token失效
  • 如果 Refresh Token 也过期，用户必须重新登录
  • 实际场景中，矿工在井下作业时网络不稳定，Refresh Token 保证了不会频繁掉线

6.2 智慧矿山的混合策略

我们采用了 JWT + Redis 的混合方案：

  • 正常验证：资源服务本地验证 JWT 签名和有效期，零网络开销
  • 撤销检查：如果 Token 被主动撤销（用户登出/密码修改/权限变更），将 jti 加入 Redis 黑名单
  • 黑名单 TTL：等于 Access Token 的剩余有效期，Token 自然过期后黑名单自动清除

七、PKCE 扩展——保护 SPA 与移动端

7.1 为什么需要 PKCE

PKCE（Proof Key for Code Exchange）是为了解决授权码模式在公开客户端（SPA、移动APP）上的安全缺陷：

  • 公开客户端无法安全存储 client_secret
  • 恶意应用可能截获授权码 code
  • 即使截获 code，没有 code_verifier 也无法换取 Token

总结

OAuth2 + JWT + Spring Security 是微服务统一认证授权的成熟方案，在实际项目中的实践证明了其有效性。核心架构可以概括为三句话：

认证中心统一颁发——所有登录请求汇聚到认证中心，认证通过后颁发 JWT Token（含用户身份、角色、权限等声明）。

Gateway 统一验证——所有 API 请求经过 Gateway，由全局过滤器验证 Token 签名、有效期、黑名单，并将用户信息注入请求头透传到下游。

资源服务本地鉴权——各微服务从请求头提取用户身份，结合 RBAC（角色权限）+ ABAC（属性权限）进行细粒度授权控制，无需远程调用认证中心。

关键技术选型总结：

技术点 选择 理由
签名算法 RS256 公钥可公开分发，私钥只在认证中心，安全性优于 HS256
Token 格式 JWT（自包含） 无状态验证，性能最优，配合黑名单解决撤销问题
Token 撤销 JWT + Redis 黑名单 + 版本号 兼顾性能与即时生效需求
客户端认证 PKCE 保护公开客户端（SPA），无需 client_secret
权限模型 RBAC + ABAC RBAC 管功能权限，ABAC 管数据权限
服务间调用 透传请求头 + Client Credentials 有用户上下文透传头部，无用户上下文用客户端凭证
SSO Auth Code + Session 认证中心维护 Session，已登录用户直接授权

在实际项目中，认证授权从来不是纯技术问题——它需要与业务架构（矿区组织模型）、运维架构（密钥管理、监控告警）、安全合规（审计日志、等保要求）紧密结合。希望本文的实践能为类似项目提供参考。
