Redisson源码分析——看门狗与红锁的实现原理

发布于 2025-05-15 分类：技术, 2025, 源码分析 👁

前言

在实际场景中，我们大量使用了Redisson分布式锁来保障多节点部署下的数据一致性——从矿车调度互斥、设备状态变更，到告警事件去重、井下人员定位数据写入，分布式锁几乎无处不在。2024年初步引入时只停留在API层面，2025年决定深入源码，系统理解其实现原理：看门狗如何自动续期、可重入锁如何用Hash结构实现、红锁如何解决主从切换丢锁问题、公平锁如何排队、读写锁如何并发控制……只有真正读懂源码，才能在生产中正确使用和高效排错。

Redisson 架构总览

Redisson 是一个基于 Redis 的 Java 驻内存数据网格（In-Memory Data Grid），其核心设计理念是将 Redis 的数据结构映射为 Java 的并发数据结构，让使用者以熟悉的 JUC（java.util.concurrent）接口来操作分布式对象。

关键设计决策

设计决策 说明
Lua 脚本保证原子性 所有复合操作（加锁+设置过期、解锁+通知）都通过 Lua 脚本在 Redis 服务端原子执行，避免竞态条件

Timeout + TimerTask 续期 基于 Netty 的 HashedWheelTimer 实现看门狗定时续期，避免业务未完成锁过期

看门狗续期机制源码分析

看门狗（Watchdog）是 Redisson 最精妙的设计之一。它解决了一个经典矛盾：锁的过期时间太短，业务还没执行完锁就过期了；过期时间太长，持锁客户端宕机后其他客户端要等很久才能获取锁。

看门狗触发条件

核心规则：调用 lock() 或 tryLock() 不传 leaseTime 参数时，看门狗生效；显式传入 leaseTime 时，看门狗不生效，锁在指定时间后自动过期。

看门狗的 Timeout 与 TimerTask 机制

Redisson 的看门狗基于 Netty 的 HashedWheelTimer 实现，而非 JDK 的 Timer 或 ScheduledThreadPoolExecutor。这是因为：

特性 HashedWheelTimer ScheduledThreadPoolExecutor JDK Timer
时间精度 约1毫秒（tickDuration可配） 毫秒级 毫秒级
任务数量支持 百万级（时间轮算法） 千级（堆排序） 千级（堆排序）
取消效率 O(1) O(log n) O(log n)
适用场景 大量延迟任务、超时检测 少量定时任务 已过时
线程模型 单Worker线程 多线程池 单线程

HashedWheelTimer 的工作原理是时间轮算法：将一个轮盘分为若干个格子（默认512个），每个格子代表一个 tick（默认100ms）。任务根据延迟时间放入对应格子，Worker 线程每 tick 检查一次格子中的任务并执行到期任务。这比堆排序的调度器在大规模延迟任务场景下性能更优。

看门狗停止条件

看门狗在以下情况会自动停止：

  1. 业务执行完毕，调用 unlock()：unlock() 方法中会调用 cancelExpirationRenewal() 取消续期任务
  2. 客户端宕机：进程崩溃后没有线程再调度续期任务，锁在 30 秒后自动过期
  3. 续期失败：锁已被删除或不再属于当前线程（如被强制释放），Lua 脚本返回 0，递归调用不再执行
  4. 显式取消：调用 RedissonLock.cancelExpirationRenewal() 方法

可重入锁实现

可重入锁是 Redisson 分布式锁的基础实现。所谓”可重入”，是指同一个线程可以多次获取同一把锁而不会死锁，每次加锁计数器 +1，每次解锁计数器 -1，计数器归零才真正释放锁。

Hash 结构与线程标识

线程标识的格式为 clientId:threadId：

  • clientId：Redisson 客户端连接的唯一标识，由 ConnectionManager 生成，格式为 UUID（如 9e87f3c1-2b5d-4a1e-b8f6-3c2d1e0f9a87）
  • threadId：Java 线程ID（如 101）

组合后形如 9e87f3c1-2b5d-4a1e-b8f6-3c2d1e0f9a87:101，这个标识确保了：

  • 不同 JVM 进程的线程不会冲突（clientId 不同）
  • 同一 JVM 中不同线程不会冲突（threadId 不同）

红锁（RedLock）详细分析

主从切换丢锁问题

在 Redis 主从架构下，分布式锁存在一个严重隐患：

具体步骤：

  1. 客户端 A 在主节点加锁成功
  2. 主节点宕机，锁数据尚未同步到从节点
  3. 从节点被哨兵提升为新主节点
  4. 客户端 B 向新主节点请求加锁，成功
  5. 此时客户端 A 和 B 同时认为自己持有锁

RedLock 算法详解

RedLock 由 Redis 作者 antirez 提出，核心思想是：向 N 个独立 Redis 实例加锁，超过半数成功才算获取锁。

RedLock 源码分析

RedLock 算法的五个步骤

  1. 获取当前时间：记录开始加锁的时间戳
  2. 依次向 N 个实例加锁：使用相同的 key 和随机值，设置较短的超时时间
  3. 计算成功数：只有超过 N/2 + 1 个实例加锁成功才继续
  4. 验证有效时间：总耗时必须远小于锁的有效时间，否则加锁无效
  5. 失败回滚：如果加锁失败，向所有已加锁成功的实例发送解锁请求

RedLock 的争议

RedLock 自提出以来就饱受争议，最著名的反对者是分布式系统专家 Martin Kleppmann。

Martin Kleppmann 的反对意见：

  1. 时钟漂移问题：RedLock 依赖系统时钟来判断锁的有效性，而分布式系统中各节点时钟可能不同步。如果某个 Redis 实例的时钟向前跳跃，可能导致锁提前过期
  2. 进程暂停（GC）问题：持有锁的客户端可能因为 GC 暂停（尤其是 Full GC），导致锁过期后被其他客户端获取
  3. 网络分区问题：在复杂的网络分区场景下，RedLock 仍然可能违反互斥性
  4. 不必要的复杂性：Martin 认为 fencing token（递增令牌）方案更简单可靠

antirez 的反驳：

  1. Redis 实例通常运行在专用机器上，时钟漂移可控
  2. GC 暂停可以通过合理配置 JVM 来避免
  3. RedLock 的多次加锁大大降低了同时违反互斥的概率
  4. fencing token 方案需要修改所有资源端的代码

实际建议：

场景 推荐方案
大多数业务场景 单节点 Redis + 看门狗，配合业务层幂等
对互斥性要求极高 RedLock 或 ZooKeeper 分布式锁
已有 ZooKeeper 基础设施 Curator InterProcessMutex
可以接受偶发不一致 单节点 Redis + 补偿机制

公平锁实现（RedissonFairLock）

为什么需要公平锁

默认的 RedissonLock 是非公平锁——当锁释放时，所有等待的线程会被同时唤醒，通过竞争来获取锁。这可能导致某些线程长期”饥饿”——始终获取不到锁。

公平锁保证先到先得：按照请求锁的顺序依次获取，先等待的线程先获取锁。

读写锁实现（RedissonReadWriteLock）

读写锁的语义

读写锁允许多个读线程同时持有锁，但写线程必须独占。适用于读多写少的场景，能显著提高并发度。

锁降级与锁升级

锁降级（写锁→读锁）：持有写锁的线程可以再获取读锁，然后释放写锁，实现从写锁到读锁的平滑过渡。这是合法的，因为持有写锁说明独占了资源，自然可以读。

锁升级（读锁→写锁）：持有读锁的线程不能直接升级为写锁，因为其他读线程可能也在持有读锁。必须先释放读锁，再获取写锁。

总结

Redisson 分布式锁的源码揭示了以下核心设计思想：

  1. 看门狗机制：通过 Netty 的 HashedWheelTimer + 递归 Timeout 任务实现每 10 秒续期一次（internalLockLeaseTime / 3），解决业务未完成锁过期的问题。客户端宕机后看门狗自动停止，锁 30 秒后自动释放
  2. Hash 结构实现可重入：用 Hash 的 field 存储 clientId:threadId，value 存储重入次数，加锁时计数器 +1，解锁时 -1，归零才真正释放
  3. Lua 脚本保证原子性：所有复合操作（加锁+设过期、解锁+通知）通过 Lua 脚本在 Redis 服务端原子执行
  4. Pub/Sub 通知避免轮询：获取锁失败的线程通过订阅 Redis 频道等待锁释放通知，用 Semaphore 控制唤醒，避免惊群
  5. RedLock 解决主从切换丢锁：向 N 个独立 Redis 实例加锁，超过半数成功才算获取，但存在时钟漂移等争议
  6. 公平锁通过 List + ZSet 排队：List 维护 FIFO 等待队列，ZSet 管理等待超时
  7. 读写锁通过双 Hash 实现并发读：读锁和写锁分别用不同的 Hash Key，读锁允许多线程共存，写锁独占

理解这些源码层面的实现，才能在生产中正确使用、高效排错、合理选型。在实际场景中，我们正是基于这些理解，针对不同场景选择了不同类型的锁，并规避了大量潜在问题。
