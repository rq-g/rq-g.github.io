电商订单系统架构设计——从下单到支付的完整链路（下）

发布于 2025-11-22 分类：技术, 2025, 架构设计 👁

前言

在实际项目的电商模块建设中，我们面临了从零搭建订单系统的挑战。矿山物资采购场景下，订单链路涉及多种支付渠道、大额交易、复杂的售后退货流程，以及秒杀抢购时的高并发冲击。承接上篇内容，本文将继续深入讲解支付集成架构、支付回调处理、支付对账、订单超时取消、退款流程设计、订单查询优化、订单导出优化、订单统计设计、售后系统、订单状态通知、高并发订单设计等核心模块，并总结项目实战中遇到的常见问题与解决方案。

九、支付对账

9.1 对账的必要性

支付对账是保证系统资金安全的关键环节。在实际场景中，大额订单频繁出现，任何资金差错都可能造成严重损失。对账的主要目的包括：

  • 确保本地支付记录与支付渠道的账单一致
  • 发现并处理长款（用户已付款但本地未记录）和短款（本地已记录但用户未付款）
  • 作为财务核算的数据基础
  • 满足审计合规要求

十、订单超时取消

10.1 超时取消方案对比

方案 优点 缺点 适用场景
数据库定时扫描 实现简单 延迟大、数据库压力大 订单量小的系统
Redis Key过期 延迟低 可靠性差，不保证通知 辅助方案
RocketMQ延迟消息 延迟低、可靠性高 延迟级别固定 中等规模系统
时间轮(Netty) 延迟极低、精度高 单机方案，需配合持久化 高性能场景
Redis + MQ组合 延迟低、可靠、灵活 实现复杂 大规模生产系统

在实际场景中，我们采用 RocketMQ延迟消息 + 定时任务兜底 的双保险方案。

十二、订单查询优化

12.1 查询性能问题分析

在实际场景中，订单表数据量增长很快。上线半年后订单表超过500万行，多维条件组合查询性能急剧下降。典型的慢查询场景包括：

  • 用户端：按时间范围 + 订单状态查询个人订单
  • 运营端：按时间范围 + 订单状态 + 商品分类 + 支付渠道等多维条件查询
  • 财务端：按时间范围 + 支付状态 + 退款状态查询

12.2 CQRS架构

采用 CQRS（Command Query Responsibility Segregation） 模式，将写操作和读操作分离。写操作走MySQL主库，读操作走Elasticsearch。

13.1 传统导出的问题

在实际场景中，运营和财务人员经常需要导出订单数据。最初采用同步导出方式，数据量大时经常超时失败。主要问题包括：

二十、总结（下）

本文从实际项目实战出发，系统讲解了订单系统下半部分的核心架构设计，涵盖以下关键模块：

  1. 支付集成架构：策略模式实现多渠道统一抽象，支付宝/微信支付完整接入，防重复支付与分布式锁保障
  2. 支付回调处理：统一回调入口、签名验证、幂等性校验、金额校验、回调补偿机制
  3. 支付对账：日终自动对账、差异分类处理、长款/短款/金额不一致的告警与处理
  4. 订单超时取消：RocketMQ延迟消息 + 定时任务兜底双保险，取消订单的完整资源回滚
  5. 退款流程设计：多种退款场景、退款状态机、渠道退款接口对接、退款回调处理
  6. 订单查询优化：CQRS读写分离、ES索引设计、Canal数据同步、多条件组合查询
  7. 订单导出优化：异步导出、SXSSFWorkbook流式写入、MinIO文件存储、分页ES查询
  8. 订单统计设计：Redis实时统计、ES聚合分析、转化漏斗、商品排行
  9. 售后系统：多种售后类型、售后状态机、退货退款流程、售后与退款联动
  10. 订单状态通知：MQ事件驱动、多渠道通知（短信/WebSocket/站内信/微信模板/邮件）
  11. 高并发订单设计：Redis预扣库存、MQ异步落库、雪花算法ID生成、Sentinel限流降级、读写分离

一个健壮的订单系统需要考虑方方面面。从业务逻辑到技术实现，从正常流程到异常处理，从单机到分布式，从同步到异步，每一个环节都需要精心设计与反复验证。在实际项目的实践中，我们深刻体会到：架构没有银弹，只有适合业务场景的最佳实践。
