电商订单系统架构设计——从下单到支付的完整链路（上）

发布于 2025-11-08 分类：技术, 2025, 架构设计 👁

前言

在实际场景中，我们为矿区物资采购和设备供应链搭建了完整的电商订单系统。矿区的业务场景有其特殊性：一是采购物资涉及大宗工业品和精密设备，单笔订单金额大、流程长；二是矿区的网络环境不稳定，对离线容错和最终一致性要求极高；三是矿区多部门协同采购，对审批流和权限管控有严格需求。这些场景倒逼我们在订单系统架构上做了大量深度设计。

订单系统是电商平台的核心枢纽，涉及高并发、数据一致性、幂等性、分布式事务等复杂工程问题。本文将从订单系统整体架构出发，深入讲解从下单到支付的完整链路，涵盖领域模型设计、状态机实现、库存扣减策略、定价引擎、优惠券体系、购物车设计、分布式事务方案、订单表设计以及幂等性保障等核心主题。

四、库存扣减策略

库存是电商系统中最容易出问题的环节，扣减策略直接决定了超卖风险和用户体验。

4.1 三种库存扣减策略对比

策略 描述 优点 缺点 适用场景
预扣库存 下单时扣减，支付超时后回补 防止超卖、用户体验好 库存利用率低、恶意占库存 限量秒杀、稀缺商品
实扣库存 支付成功后扣减 库存利用率高 可能超卖 普通商品、库存充足
超卖策略 允许少量超卖，后续补货或取消 最大化销售 需要补单流程 大宗商品、库存可补充

实际项目的选择：矿区物资采购采用 预扣库存 + 实扣确认 的两阶段策略。下单时预扣库存锁定资源，支付成功后转为实扣；支付超时则释放预扣库存，回补可用库存。

十、订单表设计

10.1 垂直拆分

订单数据量增长极快，单表无法支撑。采用垂直拆分策略将订单相关表按职责分离：

10.4 分库分表策略

分片键选择说明：

  • 选择 user_id 作为分片键，因为大部分查询都是按用户维度
  • 绑定表保证 t_order 和 t_order_item 在同一分片，避免跨库 JOIN
  • 订单号中编码了 user_id 后缀信息，通过订单号也能定位到分片

10.5 非分片键查询方案

查询维度 方案 说明

运营后台查询 ES 索引 订单数据同步到 ES，支持全维度查询

十六、总结（上）

本文从实际项目的实际业务场景出发，系统性地讲解了电商订单系统的架构设计，核心要点如下：

  1. 领域模型设计：采用DDD方法建模，Order聚合根封装核心业务规则，领域事件驱动状态变更
  2. 状态机实现：显式状态转换表 + 策略模式，支持前置/后置动作，DB乐观锁保证并发安全
  3. 库存扣减策略：预扣/实扣/超卖三种策略对比，Redis + DB双重保障，Lua脚本保证原子性
  4. 定价引擎：SPI扩展点设计，链式计算会员价 → 优惠 → 优惠券 → 运费，支持灵活扩展
  5. 优惠券系统：完整的锁定 → 核销 → 退回流程，并发安全靠Redis锁 + DB乐观锁
  6. 购物车设计：支持离线购物车，登录后按合并策略合并，过滤失效商品
  7. 订单创建流程：库存锁定 → 定价 → 优惠券锁定 → 创建订单 → 事件发送 → 延时取消
  8. 分布式事务：Seata AT（强一致）、本地消息表（最终一致）、TCC（退款）按场景选择
  9. 订单表设计：垂直拆分 + 分库分表 + ES双写，绑定表避免跨库JOIN
  10. 幂等性设计：Redis + DB去重表 + 状态机三层保障，覆盖下单/支付/退款/消息消费全链路
