全链路压测实战——从压测到容量规划的闭环

发布于 2025-08-05 分类：技术, 2025, 性能调优 👁

前言

在实际场景中，我们面临着一个典型的高并发挑战：数十个矿区同时上报采掘数据、设备GPS位置、安全监测指标、告警推送等业务，高峰期流量可达日常的 5-8 倍。之前我们针对单个服务做了性能调优——JVM 调优、SQL 优化、缓存策略、连接池调参，但优化完单个节点后，如何确保从网关到数据库的整条链路能扛住大促级别的流量？单点优化不等于链路无忧，局部正常不代表整体不崩。全链路压测就是回答这个问题的核心手段。

全链路压测和单接口压测有着本质区别：单接口压测只关注一个接口的吞吐量，而全链路压测要模拟真实用户行为，流量经过网关、多个微服务、中间件（Redis、MQ、ES）、最终落库，任何一个环节都可能成为瓶颈。在智慧矿山的设备GPS数据采集场景中，一次完整链路涉及设备上报 -> 网关鉴权 -> 设备服务处理 -> 告警规则引擎 -> 告警推送，链路中任何一个服务慢了，整条链路都会被拖垮。

这篇文章记录了我们在实际场景中，从压测架构设计、影子库/影子表隔离、数据准备、流量录制回放、全链路标记透传、JMeter 分布式压测执行、压测监控体系、性能瓶颈分析到容量规划模型的完整闭环实践。

全链路压测概述

什么是全链路压测

全链路压测是指在真实的生产环境（或与生产环境高度一致的环境）中，通过模拟真实用户的完整业务链路流量，对系统从入口到数据存储的全链路进行压力测试，验证系统在目标并发下的性能表现和稳定性。

维度 单接口压测 全链路压测
测试范围 单个 API 接口 完整业务链路（网关→服务→DB）
流量模型 均匀并发请求 模拟真实用户行为（登录→操作）
数据隔离 通常使用测试环境 生产环境 + 影子库/影子表
发现问题类型 单点性能瓶颈 链路级瓶颈、资源竞争、级联故障
实施复杂度 低 高（数据隔离、标记透传等）
环境要求 测试环境即可 生产环境或1:1仿真环境
结果可信度 中（脱离真实流量模型） 高（贴近真实流量模式）
容量规划价值 有限（单点容量） 高（全链路容量模型）

数据隔离方案

影子库

在实际场景中，我们采用 独立影子库 的方案，而非在同一个库中用字段标记区分。原因有三：

  1. 数据量隔离：压测产生的大量数据不会影响生产库的统计查询和索引效率
  2. 安全级别最高：即使代码有 bug，也不会误写生产表
  3. 清理便捷：压测结束后直接 drop 影子库，比逐行删除快得多

影子表方案

在某些场景下，独立影子库成本过高（如使用云数据库按实例收费），可以采用影子表方案：

容量规划

容量评估模型

容量规划的目标是根据压测数据，建立 QPS 到服务器资源的映射关系，从而回答”需要多少台机器才能扛住目标流量”这个问题。

1. 单实例容量基线（来自压测）：

  • QPS_single = 压测单实例稳定QPS
  • RT_single = 压测单实例P99 RT
  • CPU_single = 压测单实例稳态CPU使用率
  • MEM_single = 压测单实例稳态内存使用
    1. 目标容量计算
  • QPS_target = 峰值QPS × 安全系数 × 毛刺系数
  • 其中：
  • 安全系数 = 1.3 ~ 1.5（留出安全水位）
  • 毛刺系数 = 1.1 ~ 1.3（应对突发流量）
    1. 实例数计算
  • N = ceil(QPS_target / QPS_single)
  • 同时验证：
  • N × CPU_single < 总CPU × 0.7
  • N × MEM_single < 总内存 × 0.8
    1. 完整资源评估
  • 应用实例 = N 台 × 规格
  • DB 主库 = QPS_db / 单库QPS上限
  • DB 从库 = 读QPS / 单库读QPS上限
  • Redis = 内存容量 × 2（含碎片+预留）
  • MQ = 消息积压容量 / 单Broker吞吐量
  • 网络带宽 = 峰值请求大小 × QPS × 2（双向）

常见问题与解决方案

在实际项目的全链路压测实战中，我们遇到了大量问题。以下是15个最具代表性的问题及其解决方案：

序号 问题 现象 原因 解决方案
1 影子库切换失败导致压测数据写入生产库 压测结束后生产表出现大量测试数据，设备状态表中有以 DEV-P- 开头的设备记录 AOP 切面仅拦截了 MyBatis Mapper 层，遗漏了 JdbcTemplate 直接执行的 SQL；Spring 事务管理器在切面之前执行导致数据源已绑定 统一使用 DynamicDataSource 切面，同时拦截 MyBatis 和 JdbcTemplate；增加数据写入审计日志，双重校验写入目标库；在事务开始前就完成数据源切换
2 ThreadLocal 在线程池场景丢失压测标记 异步告警处理任务中 PressureTestContext.isPressureTest() 返回 false，导致告警走入生产逻辑 普通 ThreadLocal 无法传递到线程池中的子线程，线程池中的线程是复用的，不会继承父线程的 ThreadLocal 值 替换为 TransmittableThreadLocal + TtlRunnable/TtlCallable 包装；线程池使用 TtlExecutors.getTtlExecutor() 包装；全局搜索 new Thread 确保全部使用 TTL 包装
3 压测流量触发限流被拒 压测接口大量返回 429 Too Many Requests，实际 QPS 远低于目标 压测流量走了正常的 Sentinel 限流规则，网关层没有对压测流量做限流豁免；Sentinel 的流控规则未区分压测流量 网关层识别压测标记后 skipRateLimit；在 Sentinel 规则中对压测流量白名单放行；自定义 SlotChain 对压测流量跳过限流检查
4 Feign 调用未透传压测 Header 下游服务没有走影子库，压测数据写入生产库 未配置 Feign RequestInterceptor；Spring Cloud 默认不会透传自定义 Header 添加 PressureTestFeignInterceptor，在 apply 方法中透传 X-Pressure-Test Header；对所有 FeignClient 全局注册该拦截器
5 MQ 消费者消费了影子消息 压测消息被生产消费者消费，导致告警通知发送给了真实用户 影子 Topic 与生产 Topic 相同，消费者未区分；消息的 routing key 未做区分 影子消息发到 shadow. 前缀的 Topic；消费者根据 ThreadLocal 标记选择 Topic；MQ 消费者增加压测标记校验，无标记则拒绝消费
6 Redis 影子 Key 未清理导致内存暴涨 压测后 Redis 内存使用率持续增长，从 40% 涨到 85% 压测产生的 pressure:* Key 未设置过期时间；清理脚本只在人工触发时执行 所有影子 Key 设置 TTL（默认 1 小时）；压测结束后执行 SCAN + DEL pressure:* 批量清理；增加 Redis 内存水位告警，自动触发清理
7 JMeter 分布式压测 Slave 失联 Master 日志显示 RMI 连接超时，部分 Slave 节点掉线 Slave 机器 firewall 未开放 1099/50000 端口；java.rmi.server.hostname 配置为 localhost 导致 Master 无法回调 关闭防火墙或开放端口；确保 java.rmi.server.hostname 配置为 Slave 的真实 IP；使用 RMI SSL 时确保证书配置正确
8 JMeter 压测结果不准确（QPS 偏低） 单机 JMeter 产生的 QPS 远低于预期，自身 CPU 100% JMeter 自身成为瓶颈：使用了 GUI 模式、启用了大量 Listener、JVM 堆内存不足 使用分布式压测；JMeter 使用非 GUI 模式（-n 参数）；禁用所有 Listener；增加 JMeter JVM 堆内存到 2G 以上；使用 BackendListener 写入 InfluxDB
9 压测期间数据库连接池耗尽 应用日志报 Could not get JDBC Connection，HikariPool-1 - Connection is not available 压测并发远超连接池大小；影子库和生产库共享连接池配置；长事务占用连接不释放 调大 HikariCP 的 maximumPoolSize；确保影子库有独立的连接池配置；长事务拆分为短事务；增加连接池监控指标
10 压测期间 Full GC 频繁 应用日志每分钟出现多次 Full GC，RT 飙升到秒级 压测产生大量临时对象撑爆 Old 区；G1 的 IHOP 阈值设置过高，并发标记来不及回收 增大堆内存到 4G；优化对象创建（对象池/复用/减少包装类）；调整 G1 的 IHOP 为 45%；使用 -XX:+UseStringDeduplication 减少重复字符串
11 压测期间 Redis 大 Key 导致慢查询 SLOWLOG 出现 HGETALL 耗时 > 100ms，P99 RT 异常 设备状态聚合缓存包含上千个字段，一个 Hash Key 存了整台设备的全部历史状态 拆分大 Key 为多个小 Key（按时间窗口）；使用 HMGET 按需获取字段替代 HGETALL；本地缓存热点数据减少 Redis 访问
12 压测时数据库死锁 Innodb Lock Wait Timeout 报错，事务回滚率飙升 多个事务以不同顺序更新同一组行；批量更新时锁范围过大；RR 隔离级别下 GAP 锁冲突 统一 SQL 更新顺序（按主键排序）；减小事务范围，避免长事务；降低并发度或使用乐观锁；将隔离级别调整为 RC 减少 GAP 锁
13 压测后 Grafana 看板数据缺失 压测期间的监控数据部分丢失，无法回溯分析 InfluxDB 写入速率超过其处理能力；JMeter BackendListener 批量发送间隔太短 InfluxDB 调大 cache-max-memory-size 和 cache-max-memory-sizePercentage；使用批量写入减少写入频率；Prometheus 作为替代方案存储指标数据
14 压测流量被 WAF/安全组拦截 压测请求大量返回 403 Forbidden，WAF 日志显示触发防爬规则 安全设备识别到异常流量模式（高并发来自少量 IP）；压测 IP 未加入白名单；User-Agent 触发规则 压测前将压测机器 IP 加入 WAF 白名单；与安全团队提前沟通压测时间和流量特征；压测请求使用合规的 User-Agent
15 Dubbo 调用未透传压测标记 RPC 调用后下游服务走入生产数据源，告警推送发送给了真实值班人员 Dubbo 走自定义协议，Feign 拦截器不生效；Dubbo Filter 链中未添加压测标记透传的 Filter；RpcContext Attachment 未透传 实现 Dubbo Filter，通过 RpcContext.getAttachment() 透传压测标记；在 META-INF/dubbo/org.apache.dubbo.rpc.Filter 中注册 Filter；全链路压测前验证 Filter 顺序正确
