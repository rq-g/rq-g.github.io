Spring循环依赖终极解析——三级缓存的来龙去脉

发布于 2023-01-22 分类：技术, 2023, Spring源码 👁

前言

循环依赖是Spring面试的高频题，但很多人只背了”三级缓存”四个字，说不清为什么需要三级而不是两级。2023年深入源码后，终于理解了每一级缓存的设计意图。

在实际场景中，在设备监控和安全预警模块之间出现了循环依赖：DeviceService依赖AlertService发送预警，AlertService依赖DeviceService查询设备信息。深入理解三级缓存后，不仅解决了循环依赖问题，还理解了AOP代理与循环依赖的交互机制。

实际项目技术栈：SpringBoot 2.7 + SpringCloud + Nacos + MyBatis-Plus + Redis + MQTT。项目中有多个Service之间存在双向依赖，理解三级缓存对排查循环依赖问题至关重要。

三级缓存定义

三级缓存各司其职

  • 存放完全初始化好的Bean（成品）
  • 所有属性已注入，AOP代理已创建
  • 可以直接使用
  • 线程安全的ConcurrentHashMap
  • 存放早期暴露的Bean引用（半成品）
  • 已实例化但未填充属性
  • 用于解决循环依赖时提前暴露
  • 避免重复调用ObjectFactory
  • 存放ObjectFactory（Bean工厂）
  • 调用getObject()时才决定返回原始对象还是代理对象
  • 延迟代理创建的决策
  • 保证代理单例性

为什么需要三级缓存而不是两级

两级缓存 vs 三级缓存：

问题场景：DeviceService需要AOP代理，与AlertService循环依赖：

  • 两级缓存方案:
    1. 实例化DeviceService → 直接创建代理 → 放入二级缓存
    1. AlertService从二级缓存获取DeviceService代理
    1. DeviceService初始化时又要创建代理 → 两个代理对象！
  • → 违反单例原则
  • 三级缓存方案:
    1. 实例化DeviceService → 将ObjectFactory放入三级缓存
    1. AlertService需要DeviceService → 调用ObjectFactory
  • → 第一次调用时创建代理（只创建一次）
  • → 放入二级缓存
  • → 记录earlyProxyReferences
    1. DeviceService初始化 → postProcessAfterInitialization
  • → 检查earlyProxyReferences → 已创建过代理 → 跳过
  • → 代理对象只创建一次，保证单例
  • 核心区别:
  • 两级缓存：提前暴露时就创建代理 → 所有Bean都提前创建代理
  • 三级缓存：延迟决策 → 只有循环依赖时才提前创建代理
  • 三级缓存的好处:
    1. 延迟代理创建：只在需要时才提前创建
    1. 保证代理单例：通过earlyProxyReferences避免重复创建
    1. 正常Bean不受影响：没有循环依赖的Bean走正常流程

循环依赖解决方案

四种主流方案的取舍逻辑值得展开：@Lazy 是”推迟”——注入一个代理占位，首次使用才真正解析，代价是错误被推迟到运行时（启动期查不出来，调用时才抛 NPE 或找不到 Bean）；Setter注入是”挪时间”——把依赖注入从构造期挪到属性填充期，恰好落在三级缓存能处理的窗口内，代价是对象存在”半初始化可用”的窗口；事件解耦是”断关系”——把双向调用改成事件广播，依赖关系在代码层面消失，这是唯一能提升架构质量的方案；ObjectProvider 是”手动延迟”——getIfAvailable 时才解析，语义比 @Lazy 更显式。工程上的优先级：能事件解耦就解耦（治本），否则 @Lazy 快速止血（治标），Setter 注解注入维持现状即可，禁止用三级缓存机制”故意设计”循环依赖——它能兜住不代表该用，循环依赖本质是设计信号，说明两个类的职责边界切错了。

SpringBoot 2.6+循环依赖配置

为什么官方从”默默支持”转向”默认禁止”

这个转向值得展开，因为它代表了 Spring 团队对循环依赖的态度演变。早期版本默默用三级缓存兜底，带来的隐性成本是：循环依赖掩盖了设计问题。两个 Bean 互相依赖，往往说明职责切分有问题——A 需要 B、B 又需要 A，通常意味着有第三种职责（比如事件、回调或公共服务）没被识别出来。三级缓存让这些”本该重构”的代码继续活着，直到某天引入了构造器注入、@Async 代理或 Boot 2.6 的新默认值才集体爆雷。

默认禁止的另一个技术动机是启动顺序的可预测性。允许循环依赖时，Bean 的创建顺序会影响代理创建时机和 AOP 行为，排查问题时”同一个代码不同环境行为不一致”的诡异现象有相当一部分源于此。禁止之后，容器启动失败并直接打印循环链路（BeanCurrentlyInCreationException + 完整依赖环），问题在启动期暴露而不是运行期。团队落地建议：不要一开了之——开启 allow-circular-references 前先跑一次启动，把打印出的每个循环环记录下来逐个重构（拆职责、@Lazy、事件驱动三选一），改完一个关一个开关位，最终回到默认禁止状态。把循环依赖当作”技术债仪表盘”来运营，比当作”配置开关”来对待更有长期价值。

面试高频问题

1. 三级缓存的作用分别是什么？

一级缓存singletonObjects存放完全初始化好的Bean，提供快速查找。二级缓存earlySingletonObjects存放早期暴露的Bean引用，避免重复调用ObjectFactory。三级缓存singletonFactories存放ObjectFactory，延迟代理创建的决策，保证代理单例性。

2. 为什么不能只使用两级缓存？

两级缓存无法保证代理单例。如果提前暴露时就创建代理，AOP代理可能在两处创建（提前暴露时和正常初始化后），导致两个不同的代理对象，违反单例原则。三级缓存通过ObjectFactory延迟决策，保证代理只创建一次。

3. 构造器注入为什么无法解决循环依赖？

构造器注入在实例化时就需要依赖，而三级缓存在实例化后才暴露半成品引用。实例化阶段还未到”放入三级缓存”的步骤，所以无法解决。

三级缓存小结：延迟代理创建的决策

三级缓存的核心价值是延迟代理创建的决策：通过ObjectFactory，Spring只在发生循环依赖时才提前创建代理，避免了所有Bean都提前创建代理的性能开销。理解了这一点，就不再只是背”三级缓存”四个字，而是真正理解了Spring的设计智慧。

在实际场景中，通过理解三级缓存，我们成功解决了DeviceService和AlertService的循环依赖问题，并通过事件驱动机制进一步解耦了服务间的直接依赖。循环依赖应该从设计上尽量避免，三级缓存是优雅的兜底方案，但不应该成为设计上的依赖。

三级缓存的并发安全分析

很多人疑惑：三级缓存里 singletonFactories、earlySingletonObjects 都是普通 HashMap（并非线程安全的 ConcurrentHashMap），为什么不会并发出问题？答案是所有写操作都被 synchronized (this.singletonObjects) 保护，且读多写少。

注意 singletonObjects 是 ConcurrentHashMap，但 singletonFactories 和 earlySingletonObjects 只是普通 HashMap——它们只在持锁块内被访问，因此无需并发容器。这也解释了为什么 Spring 在搬移缓存时要用”双重检查”：同一个 Bean 可能被多个依赖同时触发，第一个线程把半成品从三级搬到二级后，第二个线程再查就直接命中二级，避免重复执行 getObject() 导致代理对象被创建两次。

getSingleton 的并发时序

sequenceDiagram

    A->>R: 继续完成 deviceService 初始化

实战：循环依赖的排查与定位

当循环依赖未被三级缓存解决时，Spring 会抛出 BeanCurrentlyInCreationException，日志特征非常明显：

排查步骤（实战经验）：

  1. 先看异常栈顶部的 Bean 名，确定是哪两个 Bean 互相依赖；
  2. 确认注入方式：如果是构造器注入，三级缓存无能为力，必须改 @Lazy 或字段注入；
  3. 确认是否主动关闭了循环依赖：SpringBoot 2.6+ 默认 allow-circular-references=false，此时即使字段注入也会直接报错；
  4. 长期应消除循环依赖：提取公共逻辑到第三方 Service，或用事件机制解耦（前文已示例）。

原理深挖：三级缓存到底解决了什么问题

一个常见误解是”三级缓存是为了性能”。实际上，三级缓存的核心目的是：在”允许循环依赖”和”保证代理对象唯一”之间取得平衡。

  • 如果是普通对象（无 AOP）：三级缓存的 ObjectFactory 直接返回原始 Bean，从未真正创建代理，earlyProxyReferences 为空；
  • 如果是需要 AOP 代理的对象：第一次被循环依赖方获取时，getEarlyBeanReference() 调用 wrapIfNecessary 生成代理并记到 earlyProxyReferences；等到该 Bean 自己走完 initializeBean 的 postProcessAfterInitialization 时，发现 earlyProxyReferences 里已有记录，直接返回原对象而不再包装，从而保证”外部拿到的早期引用”和”最终成品”是同一个代理对象。

如果去掉三级缓存、只在实例化后立刻创建代理放进二级缓存（两级方案），那么所有 Bean 无论是否参与循环依赖都被提前代理，既浪费性能，又会让 earlyProxyReferences 的”是否已代理”判断失去意义。三级缓存用 ObjectFactory 把”是否提前代理”的决策延迟到真正被依赖的那一刻，这是它比两级缓存优雅的根本原因。

三级缓存与 @Lazy 的协作关系

@Lazy 是另一种打破循环依赖的思路，优先级高于三级缓存。它的实现不依赖缓存，而是直接注入一个延迟加载的代理：

@Lazy 与三级缓存的区别：

维度 三级缓存 @Lazy
适用注入方式 字段/setter 构造器/字段均可
是否创建代理 仅在需要代理时 总是创建延迟代理
解决了什么 实例化的半成品引用 构造器阶段的死锁
侵入性 零侵入（自动） 需改代码
推荐度 Spring 默认兜底 构造器依赖首选

实际项目中，我们优先用三级缓存（零侵入）兜底，仅当遇到构造器注入的循环依赖时，才用 @Lazy 在入口处打破死锁。

生产环境排查循环依赖的实战路径

循环依赖的报错 The dependencies of some of the beans in the application context form a cycle 只是起点，真正的排查要回答三个问题。**第一，环在哪里？**看报错堆栈里的 Bean 创建链（a → b → c → a），但注意 Spring Boot 2.6+ 默认禁止循环依赖，报错更早、链路更清晰，老项目升级时集中暴露的循环依赖大多是历史遗留。**第二，为什么以前能启动现在不能？**典型触发因素：有人把字段注入改成了构造器注入（构造器注入天然进不了三级缓存的提前暴露流程）、新加了 @Async 或 AOP 切面改变了代理时机、allow-circular-references 被关闭。第三，怎么修才是对的？spring.main.allow-circular-references=true 只是让问题延后到运行期 NPE，正确姿势是重构依赖方向——把环上被双向依赖的逻辑下沉为第三个 Service，或者用事件解耦（发布方不再持有监听方引用）。我们治理过的一个服务有 7 处循环依赖，其中 5 处都是”两个 Service 互调”这种设计味道，下沉公共逻辑后环自然消失，模块边界反而清晰了。

总结

方案 原理 适用场景 推荐度
三级缓存 提前暴露早期引用 setter/字段注入的循环依赖 Spring默认
@Lazy 生成代理对象延迟解析 构造器注入的循环依赖 临时方案
重构设计 提取公共逻辑消除依赖 所有场景 最佳方案
setter替代构造器 改变注入方式 简单场景 折中方案

实际项目在早期开发中产生了DeviceAlertService与GasMonitorService之间的循环依赖，最终通过提取AlertDispatcher中间层彻底解决。Spring的三级缓存是优雅的工程实现，但不应成为设计缺陷的遮羞布——消除循环依赖才是正道。SpringBoot 3.x默认禁止循环依赖，倒逼开发者写出更好的代码。
