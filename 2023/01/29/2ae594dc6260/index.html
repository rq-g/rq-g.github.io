Spring依赖注入原理——@Autowired与@Resource的底层差异

发布于 2023-01-29 分类：技术, 2023, Spring源码 👁

前言

日常开发中，@Autowired和@Resource用得最多，但一直没搞清楚它们的区别。直到一次线上问题：同一个接口两个实现类，@Autowired报错但@Resource正常。这次排查让我深入研究了两种注入方式的底层实现。

在实际场景中，项目中存在多个传感器数据处理策略实现（瓦斯传感器策略、温湿度传感器策略、压力传感器策略），使用@Autowired注入时频繁遇到NoUniqueBeanDefinitionException。深入理解@Autowired和@Resource的底层差异后，彻底掌握了多实现类的注入策略。

实际项目技术栈：SpringBoot 2.7 + MyBatis-Plus + Redis + MQTT。项目中有大量接口多实现场景，理解依赖注入原理对正确使用Spring至关重要。

@Resource注入原理

两种注入的源码级差异（为什么行为不同）

上面两段源码揭示了本质区别，但”先类型还是先名称”只是表象，真正的差异在解析入口与候选筛选机制：

1. 处理器与触发点不同。

  • @Autowired 由 AutowiredAnnotationBeanPostProcessor（AABBPP）处理，它在 postProcessMergedBeanDefinition 阶段扫描注解构建 InjectionMetadata，在 postProcessProperties 阶段执行 metadata.inject()；
  • @Resource 由 CommonAnnotationBeanPostProcessor（CABBPP，同时管 @PostConstruct/@PreDestroy）处理，它扫描 @Resource 后构建 ResourceElement，同样在 postProcessProperties 阶段通过 autowireResource() 注入。

两者都在”属性填充（populateBean）”阶段、都在 Bean 实例化之后，时机一致。

2. 解析入口的天壤之别（核心差异）。

  • @Autowired 走 DefaultListableBeanFactory.resolveDependency() → doResolveDependency()：先 findAutowireCandidates(type) 收集所有同类型候选 Bean 组成集合，再 determineAutowireCandidate() 按 @Primary → @Priority → 字段名/参数名 逐级筛选。也就是说，它是一条”先聚拢、后裁决”的路径。
  • @Resource 走 BeanFactory.getBean()：先 getBean(name) 按名字直接定位单例（没有”候选集合”概念），名字找不到才退化成 getBean(type) 做类型查找。它是一条”先精确定位、失败再退路”的路径。
flowchart TD
    A["@Autowired 注入"] --> B["resolveDependency(type)"]
    B --> C["findAutowireCandidates 收集所有同类型Bean"]
    C --> D["determineAutowireCandidate: @Primary→@Priority→名称"]
    D --> E["唯一候选 or 抛NoUniqueBeanDefinition"]
    F["@Resource 注入"] --> G["name非空?"]
    G -- 是 --> H["getBean(name) 精确命中"]
    G -- 否/名字失败 --> I["getBean(type) 类型查找"]
    I --> J["唯一 or 抛NoUniqueBeanDefinition"]

3. 异常语义不同，这是排查的关键。 当存在多个同类型 Bean 且无法消歧时：

  • @Autowired 抛 NoUniqueBeanDefinitionException——因为它”聚拢了多个候选，却裁决不出唯一”；
  • @Resource 若指定了 name：name 对应的 Bean 不存在则抛 NoSuchBeanDefinitionException（它压根没打算去比类型）；若未指定 name：先按字段名 getBean 失败，再 getBean(type)，同样可能因多个候选而失败。

4. required 语义差异。 @Autowired(required=false) 允许最终注入为 null（Spring 不强制）；@Resource 没有 required 属性，找不到就直接抛异常——这也是为什么可选依赖更推荐 @Autowired(required=false) 或 ObjectProvider。

实战结论： 如果你想要”类型安全 + 多实现自动裁决 + 可选依赖”，用 @Autowired 体系；如果你明确”就注入这个名字的 Bean”，用 @Resource(name=...) 更直白、且不受 @Primary 干扰（@Resource 名字优先，根本不会去读 @Primary）。这也解释了开篇那次线上事故：同一接口两个实现，@Autowired 因”两个候选+无@Qualifier+字段名不匹配”直接 NoUnique，而 @Resource(name="xxx") 因为按名字精确命中，轻松绕过歧义。

面试高频问题

1. @Autowired和@Resource的区别？

@Autowired是Spring注解，先按类型再按名称；@Resource是Java标准注解，先按名称再按类型。推荐使用构造器注入。

2. @Autowired如何处理多个实现类？

@Qualifier指定名称、@Primary标记默认、字段名匹配、Map/List集合注入。推荐使用策略模式+Map注入。

3. 为什么推荐构造器注入？

不可变性（final字段）、完整性（构造时全部注入）、显式依赖（参数列表一目了然）、便于测试（不需要反射）、避免循环依赖。

总结

依赖注入是Spring的核心机制。深入源码后，核心认知是：@Autowired按类型优先，@Resource按名称优先，构造器注入是最安全的方式。

在实际场景中，我们统一使用构造器注入（@RequiredArgsConstructor），多实现场景使用策略模式+Map注入。理解了注入原理和时机后，不再遇到”注入为null”的诡异问题，也彻底掌握了多实现类的注入策略。

注入方式速查表与选型原则

注入方式 注解 匹配逻辑 适用场景 智慧矿山应用
构造器注入 @Autowired (可省略) 先类型后名称 必须依赖 DeviceRepository、AlertService
Setter注入 @Autowired 先类型后名称 可选依赖 可选的MQTT客户端
字段注入 @Autowired 先类型后名称 简单场景 不推荐使用
@Resource @Resource 先名称后类型 需按名称注入 多数据源场景
@Value @Value SpEL表达式 配置值注入 矿区配置参数
ObjectProvider 构造器参数 类型+可选 可选依赖 可选的RedisTemplate
Map/List注入 构造器参数 类型+集合 策略模式 SensorDataStrategy

实际项目的依赖注入原则：1) 必须依赖用构造器注入+final；2) 可选依赖用ObjectProvider；3) 多实现用Map注入实现策略模式；4) 避免字段注入和@Autowired(required=false)；5) @Resource只在需要按名称注入时使用。良好的依赖注入设计让代码可测试、可维护、可扩展。
