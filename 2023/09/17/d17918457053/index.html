Nacos集群部署与数据持久化——生产环境高可用

发布于 2023-09-17 分类：技术, 2023, 微服务 👁

前言

开发环境一个单机 Nacos 就够了，但生产环境单机部署等于把注册中心和配置中心这两个”命根子”放在单点上——Nacos 一挂，所有服务的发现和配置拉取全部失效，整个智慧矿山平台直接瘫痪。

2023 年我们把 Nacos 从单机迁移到 3 节点集群，踩的坑比预想多：gRPC 端口遗漏导致客户端连不上、cluster.conf 写了 localhost 导致节点互相不认识、MySQL 连接池打满导致注册超时、Raft 频繁重选举引发服务列表抖动。本文系统梳理集群部署 + 数据持久化的完整方案，每个坑都给出根因和验证方法。

Nacos集群架构

为什么是 3 个节点，不是 2 个或 4 个

Nacos 集群对于持久化实例和配置写入走 Raft 多数派协议，写操作需要 (N/2)+1 个节点确认。节点数与容灾能力的关系：

节点数 多数派 可容忍故障 说明
2 2 0 任何一台挂了都无法形成多数派，不如单机
3 2 1 生产最低配置
4 3 1 比 3 节点多花钱，容灾能力却一样
5 3 2 核心系统推荐；机房级容灾

结论：偶数节点是纯浪费——4 节点容忍 1 台故障，和 3 节点一样，但机器、运维成本翻倍。这就是”节点数为奇数”这个面试题的数学本质。

端口规划（2.x 最大的部署坑）

端口 协议 用途 说明
8848 HTTP Web 控制台 + REST API Nacos 主端口
9848 gRPC 客户端连接 8848+1000，2.x 新增
9849 gRPC 服务端内部通信 8848+1001，2.x 新增
7848 HTTP 旧版 Raft 选举通信 1.x 遗留，2.x 部分场景仍用

真实踩坑：我们第一次部署 2.x 集群时，防火墙只开了 8848，控制台能访问、注册也”看起来正常”，但客户端日志疯狂刷 Client not connected, current status: STARTING。根因就是 9848/9849 没开——Nacos 2.x 客户端（gRPC 长连接）和 1.x 客户端（HTTP 短连接）行为完全不同，1.x 老客户端只走 8848 所以察觉不到。

防火墙规则一定要按”主端口 +1000/+1001”成组放行，另外注意：客户端连接的 9848 是客户端自己计算的（server-addr 端口 +1000），Nginx 转发 gRPC 时必须监听 9848 而不是 8848。

单机 vs 集群的本质差异

维度 单机模式 集群模式
存储 内嵌 Derby（不可多节点共享） 外置 MySQL
选举 无（自己就是 Leader） Raft 多数派选举
临时实例同步 不涉及 Distro 协议分片复制
故障影响 节点挂 = 全部不可用 挂 1 台不影响读写
配置成本 零配置 cluster.conf + MySQL + VIP
适用场景 开发/调试 生产必选

关键理解：集群模式改变了写路径。单机下配置写入直接落 Derby；集群下配置写入要经过 Raft 复制到多数派才返回成功，所以集群的写延迟天然高于单机，这是用可用性换来的代价，不是性能退化。

生产部署六步法

Step 1：准备 MySQL

然后导入 Nacos 发行包 conf/mysql-schema.sql（2.x 的表结构文件名，1.x 叫 nacos-mysql.sql）。核心表：

表 作用
config_info 配置主表（配置内容正文）
his_config_info 配置历史（控制台”历史版本”回滚的数据来源）
tenant_info 命名空间
users/roles/permissions 控制台鉴权

his_config_info 会持续增长，生产上要定期归档（保留 90 天足够回滚用），否则一年后这张表能涨到千万级，拖慢配置写入。

Step 2：application.properties

鉴权链路值得讲清楚，因为出过真实事故（Nacos 未开鉴权被扫描工具批量添加配置）：

  1. 用户名密码登录 → 返回 accessToken（JWT，用 token.secret.key 签名）；
  2. 后续请求携带 accessToken，Server 端拦截器校验签名与过期时间；
  3. Server 节点之间的内部通信用 serverIdentity 请求头互相认证——这就是为什么 key/value 必须改默认值，不然攻击者可以伪造节点身份绕过鉴权。

Step 3：cluster.conf

三条铁律：

  1. 不能用 127.0.0.1 或 localhost——其他节点会把这个地址解析到自己，导致”所有节点都认为自己和集群成员通信正常，实际是自己在和自己聊”，选举永远不结束；
  2. 必须用实际网卡 IP（hostname -i 确认），Docker 部署时尤其注意容器内 IP 与宿主机映射；
  3. 三个节点的文件内容逐字节一致，成员列表不一致会出现部分节点自成一派的假集群。

加载原理：启动时解析 cluster.conf 为 Member 列表 → 建立 gRPC 连接 → 通过 /v1/core/cluster/report 上报成员状态；文件为空则自动降级单机模式（这也是”改了配置没生效，一查原来读的是另一个目录”的常见根因——nacos.home 指向哪，conf 就从哪读）。

Step 4：JVM 参数

按注册实例规模选堆大小：

规模 实例数 堆大小 依据
小型 < 100 1G 注册表 + 配置缓存占用小
中型 100~500 2G 我们的实际配置
大型 > 500 4G 服务订阅推送（UDP/gRPC 回调）内存开销大

-Xms = -Xmx 是刻意的：避免运行期堆扩容触发 Full GC，注册中心这种”抖一下全网感知”的组件，内存要提前给足。

Step 5：Nginx 负载均衡（VIP）

两个注意点：HTTP 转发用 proxy_pass，gRPC 转发需要在 stream {} 块里配 proxy_pass（TCP 四层转发），用错层级 gRPC 握手直接失败。另外 VIP 方案和客户端直连多节点方案二选一即可，混用反而增加排查难度。

Step 6：客户端配置

方式二的原理：客户端拿到列表后随机挑一个建立 gRPC 长连接，断线自动换下一个。不走 Nginx 少一跳，但节点扩缩容要改所有应用的配置；走 VIP 则把复杂度收敛到接入层。我们选 VIP，因为 200+ 实例改配置的成本远高于维护 Nginx。

集群选举与数据同步

Raft 选举流程

sequenceDiagram
    participant F1 as nacos-2 (Follower)
    participant F2 as nacos-3 (Follower)
    participant L as nacos-1 (Leader)

    Note over L,F2: 稳态：Leader 每 5s 内多次发送心跳
    L->>F1: 心跳（携带 term、logIndex）
    L--x F1: Leader 宕机 ✕
    Note over F1: 选举超时（随机 150~300ms 基数）触发
    F1->>F1: term+1，转为 Candidate
    F1->>F2: RequestVote(term, lastLogIndex)
    F1->>F1: 自投一票
    F2-->>F1: Granted（term 更大即同意）
    Note over F1: 票数 >= 2 (多数派) → 成为 Leader
    F1->>F2: 心跳确认权威，恢复写入

两套数据同步协议并存（面试高频）

Nacos 集群里临时实例和持久实例走完全不同的协议，这是很多人搞混的地方：

维度 临时实例（Distro 协议） 持久实例（Raft 协议）
一致性模型 AP，最终一致 CP，强一致
复制方式 异步复制，不阻塞写 同步复制，多数派确认
数据归属 按 hash 分片，每个节点负责一部分 全量数据在 Leader
节点宕机 数据自动重平衡 重新选举
典型场景 微服务实例注册（我们的 200+ 实例） 数据库实例、DNS 类持久服务
宕机恢复 从其他节点 + 磁盘快照恢复 从 Leader 补日志

而配置数据根本不在节点间同步——三个节点直接共享 MySQL，写入走 Raft 只是为了保证”同一时刻只有一个节点处理写请求”的顺序性。理解这一点就明白为什么 Nacos 集群的 MySQL 是单点瓶颈（用主从保可用），而不是像 Kafka 那样数据分散在多副本。

这套语义对服务注册与配置中心的实际影响

把协议语义翻译成故障现象，集群运维时才不会慌。注册场景（AP）的宕机表现：某台 Nacos 节点挂掉，Distro 分片数据会自动重平衡，客户端长轮询换到存活节点后列表照常返回——但注意弱一致的代价：宕机瞬间未同步完的注册变更会短暂”回退”，表现为个别服务实例列表抖动，几秒内自愈。这正是注册中心选 AP 的原因：服务列表短暂不精确（多一个死实例、少一个新实例）可以靠客户端负载均衡和重试兜底，但”整个列表拿不到”就是雪崩。配置场景（CP）的宕机表现：Raft Leader 挂掉后有秒级不可写窗口（选举期间配置推送暂停），但已推送的配置不受影响；如果你在选举窗口内改配置，客户端会收到写入失败，必须重试。所以配置变更操作要避开集群波动期，发布系统里对 Nacos 写入加幂等重试是标配。

还有一个容易被忽略的推论：Distro 分片意味着每个节点只负责一部分实例数据，客户端连到哪个节点、查询的服务是否属于该节点分片，响应路径完全不同——非分片数据需要节点间转发。这就是为什么集群规模上来后（超过 10 节点），官方建议客户端直连 VIP 均匀打散，而不是全部指向固定两台节点：连接分布不均会让某几台节点的转发压力远高于其他节点，容量规划全部失真。

数据持久化

内嵌 Derby vs 外置 MySQL

维度 内嵌 Derby 外置 MySQL
数据位置 每个 Nacos 节点各自持有 全集群共享一份
多节点数据一致 不可能（数据不共享） 天然一致
备份恢复 无成熟方案 mysqldump + binlog 完备
性能 低（内嵌、无连接池） 高（HikariCP + 独立服务器）
适用 本地开发、演示 生产必选

一句话记忆：Derby 的数据在 Nacos 进程里，MySQL 的数据在 Nacos 进程外。前者注定了集群模式必须换 MySQL——三个节点各自一份 Derby，配置改了只落在一个节点上，其他节点查不到，这直接违反配置中心的基本契约。

读写优先级：读走 内存 > 磁盘 > 数据库；写按 内存 → 磁盘 → 数据库 顺序落。这个分层解释了一个经典现象：MySQL 里的配置明明改了，客户端没收到推送——因为推送的依据是内存 ConfigCache 的 MD5 对比，如果写路径在 MySQL 成功但内存缓存更新失败（极少见但存在），就会出现”库对缓存不对”的诡异状态，重启节点即恢复。

MySQL 高可用

我们采用一主一从 + 半同步复制：

  • Master：8C16G，SSD 500G（配置写入 + 控制台读）
  • Slave：4C8G，SSD 200G（只读备份，SHOW SLAVE STATUS 监控延迟 < 1s）
  • 复制模式：半同步（至少一个从库确认收到 binlog 才返回成功）——配置中心数据量小但绝不能丢，异步复制在主机宕机时可能丢最后几百毫秒的配置变更

Nacos 侧支持多数据源地址（db.url.0/db.url.1），主库故障时改配置重启即可切换；更省事的方案是前面挂 VIP/ProxySQL 统一入口，切换时只动数据库层。

连接池配置（实测参数）

参数推导逻辑：max_connections 必须大于所有 Nacos 节点连接总和 + 业务连接 + 管理连接，我们设的 500。connection-timeout=3000 是刻意的短——注册中心连不上数据库就应该快速失败，而不是让注册请求排队等 30 秒超时，把雪崩传播给上游。

备份与恢复

三个恢复场景的 RTO 实测目标：

场景 恢复手段 RTO
MySQL 主库故障 提升从库为主，改数据源重启 < 5 分钟
配置误删 his_config_info 表回插 / 控制台历史版本回滚 < 1 分钟
全量数据丢失 恢复全量备份 + 重放 binlog 到时间点 < 30 分钟

全量恢复后记得清空 Nacos 各节点的磁盘快照目录（data/naming、data/config）再启动——否则节点会用旧快照顶上来，出现”恢复成功但客户端拿到旧配置”的灵异现象。

Leader 选举频率是最容易被忽视的黄金指标：选举期间 Distro 分片重新分配、客户端连接抖动，业务表现就是”偶发的服务调用失败，过几秒自己好”。我们曾因为交换机端口协商问题导致每小时选举 2~3 次，监控加了这个指标才定位到。

滚动升级

核心纪律：一次只动一个节点，每步验证。

  1. 备份 MySQL + 配置文件；
  2. 停 nacos-1 → 替换包 → 启动 → 验证健康 + 服务列表完整；
  3. 依次处理 nacos-2、nacos-3；
  4. 全部完成后观察 30 分钟 Leader 稳定性。

1.x → 2.x 升级要额外走双写流程：先升级客户端到 2.x（仍走 8848 兼容），再升级 Server 并开启双写过渡期，验证数据一致后关双写。顺序反了（先升 Server）会让 gRPC 客户端连不上未开 9848 的旧集群。

常见问题排查手册

客户端连接不上集群

排查顺序（从最常见到最罕见）：

集群脑裂

现象：多个节点都认为自己是 Leader，同一服务在不同节点查询结果不同。处理三板斧：

  1. 确认网络分区点（ping/traceroute/交换机日志）；
  2. 保留多数派一侧，重启少数派节点——Raft 的 term 大者胜，少数派重新加入后会自动同步数据；
  3. 治本：节点数保持奇数 + 选举超时调大 + 跨交换机部署时评估单链路风险。

“配置改了但没生效”

分层排查：MySQL 里值对不对 → 控制台看到的是否新值 → 客户端是否收到推送（看客户端日志 refresh event received）→ 客户端 Bean 是否支持 @RefreshScope。最常见的根因是最后一条——配置推送成功但 Bean 没有 RefreshScope，热刷新天然不生效，和 Nacos 无关。

一次真实的集群故障复盘：从”服务批量下线”到根因

有一次凌晨收到批量告警：网关日志里大量 server list empty，随后几十个微服务触发降级。复盘时的排查路径值得记录。第一步看 Nacos 节点状态——三台里两台还在，但都报 unhealthy，集群处于”没有可用 Leader”的假死状态。第二步查机器指标：三台的磁盘 IO 打满，MySQL 主库 innodb_buffer_pool 命中率跌到 60%，慢查询堆积。第三步对时间线：那天 DBA 在凌晨做磁盘扩容迁移，MySQL 主从切换期间 Nacos 的配置写入全部超时，Raft 写请求堆积触发节点间心跳超时，进而连锁引发 Distro 分片重平衡风暴。

这次故障沉淀了三条硬经验。其一，注册中心的可用性受制于它依赖的最弱组件——Nacos 集群本身三个节点高可用，但共享 MySQL 一抖动整个集群跟着抖动，MySQL 主从切换前必须知会所有依赖方做”写暂停”预案。其二，客户端要有退化能力：这次降级没雪崩，靠的是客户端本地快照（Nacos client 会把最后一次服务列表缓存到磁盘），网络层故障时业务仍按旧列表运行，这就是”容灾最后一公里”。其三，变更窗口是最大的故障源：凌晨变更前先看 Nacos 集群和 MySQL 的健康基线，变更后半小时内盯着 nacos_monitor 的 longConnection 数和配置推送成功率，异常波动立刻回滚变更而不是继续排查。

容量规划：从连接数风暴说起

Nacos 集群的容量瓶颈往往不在内存和 CPU，而在长连接与推送能力。每个服务实例持有一条到 Nacos 的长连接，订阅方每订阅一个服务就注册一个 gRPC/HTTP 监听——300 个服务、平均 20 实例、每实例订阅 15 个服务，单是连接与监听句柄就是数万级。我们经历过一次”连接数风暴”：一个写错重试逻辑的新服务在启动失败后无限重连，瞬时 8000 条新连接把 Nacos 的 worker 线程池占满，其他所有服务的注册推送全部延迟，一个服务的 bug 变成了整个注册中心的故障。容量规划要算清四笔账：连接数（实例数 + 预留 30% 重连峰值，单节点 gRPC 模式实测可承载 10 万连接，但推荐值应保守）、配置监听数（每个客户端的配置监听上限 configListenCapacity，默认 3000，超过就设计问题）、推送 QPS（服务状态变更频率 × 订阅方数量，3000 实例的注册中心一次批量上下线就是一次推送风暴）、磁盘 IO（Derby/MySQL 的写入延迟决定配置变更的响应）。更重要的工程原则是隔离：生产注册与配置分集群部署，非核心环境（测试/预发）共享一套低配集群，任何环境的问题都不要波及生产注册中心——它是所有微服务的”神经中枢”，值得用最高的隔离级别对待。

面试高频问题

1. Nacos 集群如何保证高可用？
三层回答：接入层 VIP/Nginx 多后端；集群层 Raft 多数派（3 节点容忍 1 故障）+ Distro 分片互备；存储层 MySQL 主从半同步。再加运维层监控告警与滚动升级预案。

2. Nacos 2.x 为什么需要额外端口？
1.x 客户端轮询 HTTP（8848）；2.x 换成 gRPC 长连接，连接复用 + 服务端主动推送，时延和资源开销大幅下降。gRPC 通信端口按主端口 +1000（客户端）/ +1001（节点间）偏移，是刻意的约定便于防火墙成组放行。

3. Nacos 数据如何持久化？
分三类：配置数据存 MySQL（集群共享）；临时实例在内存 + Distro 异步同步 + 磁盘快照兜底；持久实例走 Raft 日志 + 快照。没有单一存储，是按数据可靠性要求分级的存储设计。

4. 集群节点数为什么是奇数？
Raft 多数派 (N/2)+1 下，奇偶节点的容灾能力相同（3 和 4 都容忍 1 台），偶数多花的钱买不到可用性，反而增加选举通信开销。

5. 如何处理脑裂？
Raft 天然以多数派为准；恢复时保留多数派、重启少数派，其数据会被新 Leader 覆盖同步。预防靠奇数节点、网络冗余、选举超时调优。

6. 1.x 升级 2.x 要注意什么？
客户端先行 → Server 双写过渡 → 验证一致后关双写；防火墙补 9848/9849；长连接推送生效后评估 UDP 相关参数是否清理。

命名空间与分组：治理先行，别等乱了再拆

Nacos 的命名空间（namespace）和分组（group）是免费的治理资源，但多数团队上线时只有一个 public 空间一个 DEFAULT_GROUP，等服务上百个再想拆分就痛苦了——所有客户端配置要改 namespace ID、配置要迁移、订阅关系要重建。治理设计应该在第一个服务上线前完成。我们的分层方案：命名空间按”环境 + 隔离等级”划分（dev、staging、prod、prod-secure 四个空间，涉及资金或设备安全控制的服务单独进 secure 空间，用独立的鉴权凭据访问）；分组按”业务域”划分（DISPATCH_GROUP、MONITOR_GROUP、INFRA_GROUP），服务发现和配置检索时用 group 收敛订阅范围，避免一个业务域的发布事件全网广播。两个容易忽略的细节：一是namespace 是隔离的硬边界——跨 namespace 的服务互相不可见，有人拿它当”灰度开关”用，结果灰度实例注册进去后生产实例找不到它，调用路由完全断掉，灰度隔离应该用元数据 + 路由规则实现，而不是 namespace；二是配置的 group 与服务的 group 语义无关，配置迁移时最容易混。命名空间规划本质上是一次廉价的架构决策，上线后重构它的成本，十倍于上线前想清楚的成本。

总结

Nacos 生产化的核心心智模型：

层 关键动作 一句话
接入层 VIP + Nginx，HTTP 与 gRPC 分开转发 客户端无感知 Failover
集群层 3 起步、奇数、真实 IP 的 cluster.conf 多数派决定生死
存储层 外置 MySQL + 半同步主从 + 每日备份 配置不能丢是底线
协议层 临时走 Distro（AP）、持久走 Raft（CP） 别把两种实例的语义搞混
运维层 Leader 选举频率 + gRPC 连接数监控 网络问题最先在这暴露

最后一个忠告：注册中心的高可用不只是 Nacos 自己的事——客户端要开启本地缓存快照（failover 目录），即使整个 Nacos 集群瞬间全灭，已启动的服务也能靠本地快照维持服务发现，这才是”面向失败的架构设计”。
