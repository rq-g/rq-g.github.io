SpringCloud整合Nacos——从零搭建微服务

发布于 2023-11-12 分类：技术, 2023, 微服务 👁

前言

2023年从单体架构转向微服务，第一步就是搭建微服务基础框架。SpringCloud + Nacos + OpenFeign + Gateway，这是最主流的微服务技术栈。

参与实际项目，这是一个大型工业物联网平台，需要将单体应用拆分为设备监控、安全预警、人员定位、生产调度等多个微服务。Nacos同时承担注册中心和配置中心的职责，Gateway做统一入口，OpenFeign做服务间调用。

实际项目微服务架构：5个核心服务 + 1个网关 + 1个公共模块，Nacos作为注册中心和配置中心，实现服务发现、配置管理、动态路由等能力。

面试高频问题

1. SpringCloud微服务架构包含哪些组件？

注册中心(Nacos)、配置中心(Nacos)、网关(Gateway)、服务调用(OpenFeign)、负载均衡(LoadBalancer)、熔断降级(Sentinel)。

2. Gateway的作用？

统一入口、路由转发、身份认证、限流熔断、日志监控。所有外部请求先经过Gateway再路由到具体服务。

3. 微服务之间如何通信？

同步调用：OpenFeign（推荐）。异步通信：MQ。选择：需要实时响应用Feign，不需要实时用MQ。

总结

SpringCloud + Nacos是Java微服务的主流方案。从零搭建后，核心认知是：Nacos同时做注册中心和配置中心，Gateway做统一入口，OpenFeign做服务调用，Sentinel做熔断降级。微服务不是拆分越细越好，而是按业务域合理拆分。

在实际场景中，我们将系统拆分为5个核心微服务，通过Nacos实现服务发现和配置管理，通过Gateway实现统一入口和认证，通过OpenFeign实现服务间调用。理解了微服务架构的每个组件，排查服务注册、配置加载、服务调用等问题时效率大幅提升。

原理深挖：Nacos 注册中心的 CP/AP 与心跳机制

Nacos 在 1.x 默认是 AP（可用性优先） 模式，基于自研的 Distro 协议做数据分片与最终一致；从 2.x 起引入了 Raft（CP 模式） 用于强一致场景。注册中心的 namespace 隔离、group 分组、cluster 集群三层模型，让同一套 Nacos 集群可以同时服务多套环境。

服务注册本质是向 Nacos Server 发送 REST 请求：

心跳与临时实例：默认实例是”临时实例”，靠心跳保活；超过 15s 未收到心跳标记为不健康，超过 30s 直接剔除。这解释了为什么服务宕机后，Nacos 控制台要等约 30s 才会把它移除——这也是 Feign 调用偶发失败的原因之一（调用到了已下线却还未剔除的实例）。生产环境应配合 Feign 的重试 + 熔断来兜住这 30s 的窗口期。

原理深挖：@RefreshScope 动态刷新的底层

@Value("${mine.threshold.gas}") 标注的字段默认在 Bean 创建时一次性注入，改了 Nacos 配置不会变。加上 @RefreshScope 后，配置变更时 Spring Cloud 会销毁并重建该 Bean，下次注入拿到新值。

坑：@RefreshScope 作用在 Bean 级别，被它代理的 Bean 每次刷新都会重建，有状态 Bean（如持有连接、缓存）会丢失现场。因此只给”纯配置消费”的 Bean 加 @RefreshScope，连接类资源用独立 Bean 管理。

生产踩坑：Nacos 配置不生效的 5 个原因

  1. bootstrap.yaml 未加载：Spring Cloud 2020+ 默认不再启用 bootstrap，需引入 spring-cloud-starter-bootstrap 或用 spring.config.import=nacos:...；
  2. data-id / file-extension 不匹配：file-extension: yaml 要求 Nacos 上的 data-id 形如 mine-device.yaml；
  3. namespace 写错：本地用 dev、Nacos 配了 prod，服务会注册到错误环境，互相看不见；
  4. shared-configs 顺序覆盖：多个共享配置存在同名 key 时，后加载的覆盖先加载的，顺序反了就拿到旧值；
  5. @Value 没加 @RefreshScope：配置变了但 Bean 没重建，字段仍是旧值。

服务调用容错：Feign + Sentinel 全链路

微服务下”一个服务慢拖垮整条链路”是常态，本项目用 Feign 降级 + Sentinel 流控 双重防护：

完整容错链路：网关限流（挡住洪峰）→ Feign 超时（快速失败）→ Sentinel 熔断（避免雪崩）→ Fallback（返回降级结果）。四层防护保证单点故障不扩散成系统级雪崩。

微服务拆分的边界原则

从单体拆到 5 个微服务，最大的教训是不要为拆而拆。我们的边界原则：

  • 按业务域（DDD 限界上下文）拆分：设备、预警、定位、调度各自独立，数据 Owner 清晰；
  • 数据库随服务拆分：每个服务独占数据库，禁止跨库 JOIN，需要时走 API 或 CDC 同步；
  • 共享逻辑下沉到 common 模块：统一返回、异常、工具类放 mine-common，但 common 不持有业务状态；
  • 强一致用本地事务，跨服务用最终一致：同服务内 @Transactional，跨服务告警通知用事件/MQ 兜底。

服务优雅下线时的 Nacos 注销

前文已说明 server.shutdown: graceful 实现优雅停机。在停机过程中，Spring Cloud 会自动向 Nacos 发送注销（deregister） 请求，摘除该实例，避免网关继续把流量打到一个正在关闭的实例上。但要注意：注销发生的前提是进程收到 SIGTERM 且 graceful 超时内完成。若用 kill -9 强杀，Nacos 只能等 30s 心跳超时被动剔除，期间会有请求失败。因此生产环境务必用 kill -15（SIGTERM）配合合理的 timeout-per-shutdown-phase。

Nacos 配置里常含数据库密码、MQTT 密钥等敏感信息，明文存储有泄露风险。生产环境应加密后再下发，应用启动时解密：

要点：密钥绝不能硬编码在代码或 Nacos 明文配置里，应通过 KMS（密钥管理服务）或环境变量注入；生产环境还需给 Nacos 控制台开启访问鉴权（nacos.core.auth.enabled=true），避免匿名访问拖库。

此外，配置变更本身也要走审批流与版本回滚：Nacos 自带配置的历史版本和一键回滚，发布阈值类配置（如瓦斯报警阈值、限流 QPS）前务必先在测试环境用 @RefreshScope 验证刷新链路通畅，确认业务能正确读到新值，再推到生产。一条错误的阈值配置，可能让全矿的预警系统集体失效或误报，安全生产场景下配置的”正确性”与”代码”同等重要。
