JVM内存模型——从运行时数据区到实战调优

发布于 2023-05-14 分类：技术, 2023, JVM 👁

前言

线上一次OOM事故让我开始认真学习JVM。实际项目上线三个月后，设备数据采集服务内存持续增长，最终OOM崩溃。当时只会重启解决，完全不知道怎么分析。2023年系统学习JVM后，终于能独立排查内存问题了。这篇文章从JVM运行时数据区出发，深入GC算法与收集器，结合实际项目实战经验，全面剖析JVM内存模型与调优方法论。

4.2 新生代收集器对比

收集器 线程数 STW 算法 特点 适用场景
Serial 单线程 是 标记-复制 简单高效，客户端模式默认 单CPU、小内存
ParNew 多线程 是 标记-复制 Serial的多线程版本 配合CMS使用
Parallel Scavenge 多线程 是 标记-复制 吞吐量优先，自适应调节 JDK8默认

4.3 老年代收集器对比

收集器 线程数 STW 算法 特点 适用场景
Serial Old 单线程 是 标记-整理 Serial的老年代版本 Client模式
Parallel Old 多线程 是 标记-整理 Parallel Scavenge的老年代版本 JDK8注重吞吐量
CMS 并发 部分 标记-清除 低延迟，并发标记/清除 重视响应时间

4.4 CMS收集器详解

  • STW 并发 STW 并发
  • 极短 耗时长 较短 耗时长

4.7 收集器选择建议

场景 JDK版本 推荐收集器 理由
后台计算，吞吐量优先 JDK8 Parallel Scavenge + Parallel Old 最大化吞吐量
交互式应用，延迟优先 JDK8 ParNew + CMS 低停顿
通用应用，平衡型 JDK9+ G1 平衡吞吐量和延迟
大内存(>16G)，低延迟 JDK11+ ZGC 超低停顿，不受堆大小影响
实际项目 JDK17 G1（4G堆）/ ZGC（16G+堆） 设备实时数据要求低延迟

9.2 调优前后对比（实际项目设备数据采集服务）

指标 调优前 调优后 提升
Young GC停顿 50~100ms 10~20ms 5倍
Mixed GC停顿 100~300ms 20~50ms 5倍
Full GC频率 1次/天 0次 消除
P99延迟 500ms 50ms 10倍
堆内存使用率 80% 60% -20%

调优关键操作：

  1. Region从2M增大到4M，大对象不再直接进老年代
  2. 更早触发Mixed GC（InitiatingHeapOccupancyPercent=45），老年代不再堆积
  3. 代码层面减少大对象（设备图片改为OSS存储，数据库只存URL）
  4. 修复内存泄漏（DeviceAlertCache使用Caffeine替代HashMap）
  5. Metaspace预分配256m，避免运行时扩容触发Full GC

9.3 常见场景推荐配置

场景 堆大小 推荐收集器 关键参数
小型应用 <2G G1 -XX:MaxGCPauseMillis=200
中型应用 2-8G G1 -XX:G1HeapRegionSize=4m
大型应用 8-16G G1 -XX:G1HeapRegionSize=8m
超大应用 >16G ZGC -XX:+UseZGC
实时性要求极高 任意 ZGC JDK17+

十、面试高频问题

10.1 JVM内存结构？

线程私有：程序计数器、虚拟机栈、本地方法栈。线程共享：堆、方法区。堆是GC的主要区域，分为新生代（Eden + S0 + S1）和老年代。方法区在JDK8后变为Metaspace，使用本地内存。

10.2 什么时候对象会进入老年代？

三种条件：年龄达到阈值（-XX:MaxTenuringThreshold，默认15，CMS为6）、大对象直接进入（-XX:PretenureSizeThreshold）、Survivor空间不足触发动态年龄判断（相同年龄对象超过Survivor空间一半）。

10.3 CMS和G1的区别？

CMS是老年代收集器，基于标记-清除，有内存碎片问题，并发标记/清除减少停顿。G1是分Region收集，新生代+老年代统一管理，基于标记-复制/整理，无碎片，可预测停顿时间（MaxGCPauseMillis），优先回收垃圾最多的Region（Garbage First）。

10.4 什么情况会触发Full GC？

  1. 老年代空间不足（大对象晋升、内存泄漏）
  2. Metaspace不足（动态类加载过多）
  3. 显式调用System.gc()（可用-XX:+DisableExplicitGC禁用）
  4. CMS的Concurrent Mode Failure（老年代预留空间不足，退化Serial Old）
  5. G1的Evacuation Failure（Mixed GC时没有足够空闲Region存放晋升对象）

10.5 如何排查OOM？

  1. 开启HeapDumpOnOutOfMemoryError，OOM时自动dump
  2. 使用jmap或Arthas heapdump手动导出堆转储
  3. MAT分析dump文件，查看Leak Suspects和Dominator Tree
  4. 通过GC Root引用链定位泄漏来源
  5. 对比jmap -histo:live两次结果，找出持续增长的对象

十一、实际项目问题汇总

以下问题均来源于实际项目实际生产环境，涵盖JVM内存模型相关各类典型问题：

# 问题 现象 原因 解决方案
1 内存泄漏导致OOM java.lang.OutOfMemoryError: Java heap space，服务每隔3-5天重启一次 DeviceAlertCache中的HashMap只增不减，每个设备的告警历史永远不清理，20万+设备导致内存持续增长 使用Caffeine缓存替代HashMap，设置maximumSize=50000和expireAfterWrite=30min，OOM问题彻底消失
2 GC频繁导致STW 接口偶发性超时，监控显示Young GC频率达每秒5次，STW累计占比12% 新生代设置过小（256MB），大量短生命周期设备数据对象在Eden区快速填满触发频繁YGC 增大新生代至1GB，调整-XX:SurvivorRatio=8，YGC频率降至每分钟2-3次，STW占比降至1%
3 线程死锁 矿井安全告警推送线程全部阻塞，告警无法发出，Arthas thread -b检测到死锁 AlertPushService中两个同步方法以不同顺序获取两把锁（lockA->lockB vs lockB->lockA），导致循环等待 统一锁获取顺序，改用ReentrantLock的tryLock(timeout)避免无限等待，并增加死锁检测告警
4 Full GC频繁 每分钟触发3-5次Full GC，每次耗时2-3秒，接口严重卡顿 大量设备图片数据（平均200KB）存入老年代，触发G1并发标记后频繁Mixed GC升级为Full GC 1.设备图片改为OSS存储，数据库只存URL；2.增大-XX:InitiatingHeapOccupancyPercent=55；3.增大堆内存至8GB
5 Metaspace OOM java.lang.OutOfMemoryError: Metaspace，Metaspace使用量持续增长至256MB上限 动态代码生成框架（CGLIB代理）不断创建新类且不释放，AOP切面范围过大导致代理类膨胀 增大MaxMetaspaceSize至512MB；排查自定义ClassLoader泄漏；优化AOP切面范围，避免对大量类创建代理
6 StackOverflowError 设备告警规则递归评估触发StackOverflowError，线程栈默认1MB溢出 告警规则嵌套引用形成循环（规则A引用规则B，规则B引用规则A），递归调用无法终止 1.修复规则循环引用，增加递归深度检测（最大10层）；2.改递归为迭代实现；3.增大-Xss至2MB作为兜底
7 CPU飙高 井下设备监控接口响应时间从50ms飙升至5s，top显示Java进程CPU达380% 设备告警规则引擎中正则表达式存在回溯陷阱，特定设备ID格式触发灾难性回溯 修复正则表达式，使用占有量词替代贪婪量词；增加正则预编译和匹配超时机制
8 大对象直接进老年代 G1收集器频繁Mixed GC，设备导出功能的List数据超过Region一半被视为Humongous对象 设备数据批量导出一次性加载10万条DeviceSensorData到List，超过2MB直接进老年代 改为分批加载流式处理，每批1000条；增大-XX:G1HeapRegionSize=4M减少Humongous对象
9 Survivor区溢出 Young GC后存活对象超过Survivor区容量，直接晋升老年代，老年代增长快 -XX:SurvivorRatio=8导致每个Survivor区仅占新生代1/10，高峰期存活对象太多 1.调整-XX:SurvivorRatio=6增大Survivor区；2.降低-XX:MaxTenuringThreshold=6减少晋升压力
10 浮动垃圾导致Concurrent Mode Failure CMS收集器老年代预留空间不足，退化为Serial Old，Full GC停顿5秒 CMS并发标记阶段产生的新垃圾（浮动垃圾）未及时回收，老年代使用率超过68%触发 1.降低-XX:CMSInitiatingOccupancyFraction=68更早触发CMS；2.增大老年代空间；3.考虑升级到G1
11 ThreadLocal内存泄漏 线程池中ThreadLocal的Entry引用无法回收，堆中UserContext对象持续增长 线程池复用线程，ThreadLocal使用后未调用remove()，Entry的key是弱引用但value是强引用 在拦截器afterCompletion中添加CONTEXT.remove()；或使用Try-with-resources模式自动清理
12 直接内存溢出 java.lang.OutOfMemoryError: Direct buffer memory，NIO堆外内存泄漏 Netty通信层分配的DirectByteBuffer未正确释放，设备数据上报使用NIO导致堆外内存持续增长 1.检查ByteBuf是否在finally中release；2.设置-XX:MaxDirectMemorySize=512m限制堆外内存；3.使用Netty的内存泄漏检测
13 类加载器泄漏 应用重启后Metaspace不降反升，自定义ClassLoader创建的类无法卸载 热部署框架创建的ClassLoader持有大量类引用，重启后旧ClassLoader未被GC Roots释放 1.排查ClassLoader引用链，找到持有旧Loader的GC Root；2.优化热部署逻辑确保旧Loader可被回收
14 频繁System.gc 每隔10分钟触发一次Full GC，排查发现是某个框架显式调用System.gc() 数据导出框架在导出完成后调用System.gc()期望释放内存，但导致Full GC停顿 添加-XX:+DisableExplicitGC禁止显式GC调用；修改框架代码去掉System.gc()调用
15 堆外线程栈占用过大 物理内存持续增长但堆内存使用正常，容器OOM Killed 每个线程栈1MB（-Xss1m），500个线程占用500MB栈空间，加上Metaspace和直接内存，总内存超限 1.减小-Xss至512k；2.减少线程池最大线程数；3.使用虚拟线程（JDK21+）替代平台线程

十三、总结

JVM是Java开发者的内功。核心认知是：理解内存模型才能排查OOM，理解GC算法才能选择合适的收集器，掌握排查工具才能快速定位线上问题。在实际项目中，从OOM到GC调优，从内存泄漏到CPU飙升，每一个问题都加深了对JVM的理解。遇到内存问题不再只会重启，而是能从dump文件和GC日志中找到根因，从GC算法和收集器原理出发进行针对性调优。
