CountDownLatch与CyclicBarrier——多线程协作利器

发布于 2023-05-05 分类：技术, 2023, 并发编程 👁

前言

实际项目中有大量多线程协作场景：矿井安全监控模块并行初始化后统一启动、多数据源并行查询汇总看板、多矿区分批数据处理、并发压测验证系统承载力。项目初期只会用Thread.join()，代码又丑又难维护——100台矿卡的调度系统启动时，主线程依次等待5个子模块初始化，总耗时达到45秒，其中大部分时间都在阻塞等待。2023年深入学习CountDownLatch和CyclicBarrier后，将系统启动时间从45秒优化到8秒，多线程协作变得优雅而可靠。

本文结合实际项目的真实实践，从核心原理到源码剖析，从实战场景到踩坑记录，全面讲解CountDownLatch与CyclicBarrier，并扩展Semaphore限流和Exchanger数据交换，覆盖多线程协作的典型需求。

一、CountDownLatch——等待N个线程完成

1.1 核心概念

CountDownLatch是JDK 5引入的同步辅助类，字面意思是”计数器门闩”——初始化时设置一个计数器，每次调用countDown()使计数器减1，调用await()的线程将阻塞直到计数器归零。它是一次性使用的，不可重置。

1.2 AQS源码剖析

CountDownLatch的底层实现依赖AbstractQueuedSynchronizer（AQS）的共享模式。理解AQS实现，才能真正掌握CountDownLatch的行为特征。

二、CyclicBarrier——N个线程互相等待

2.1 核心概念

CyclicBarrier是JDK 5引入的另一种同步辅助类，字面意思是”循环栅栏”——N个线程到达栅栏后互相等待，全部到齐后一起继续执行。与CountDownLatch不同，CyclicBarrier可循环使用（通过reset重置），且支持到达栅栏时执行一个回调动作（barrierAction）。

2.2 源码剖析

CyclicBarrier的内部实现基于ReentrantLock的Condition，核心是Generation机制实现循环重置。

实际项目需要按矿区对设备巡检数据分批处理，每个矿区的处理线程在完成本批次后需要等待其他矿区，全部完成后统一汇总上报。

2.4 实战2：传感器数据多轮校验

智慧矿山的传感器数据需要经过3轮校验：原始数据采集→异常值过滤→统计聚合。每轮校验由多个工作线程并行处理，一轮全部完成后才能进入下一轮。

2.5 CyclicBarrier的异常处理——BrokenBarrierException

CyclicBarrier的一个关键行为是：如果任何一个等待线程被中断或超时，栅栏会被破坏（broken），所有其他等待线程会收到BrokenBarrierException。这是与CountDownLatch的重大区别。

3.1 核心差异对照

四、Semaphore——限流控制

4.1 核心概念

Semaphore（信号量）用于控制同时访问某个资源的线程数量，本质是一个计数器。acquire()获取许可（计数减1），release()释放许可（计数加1）。当计数为0时，acquire()会阻塞。

4.2 实战：设备控制指令限流

实际场景中，设备控制指令（启停、调速、路径变更）不能无限下发，需要限制并发数，防止设备控制通道过载。

五、Exchanger——线程间交换数据

5.1 核心概念

Exchanger用于两个线程之间交换数据。当两个线程都调用exchange()方法时，它们互换各自持有的数据，然后继续执行。适合用于遗传算法、管道设计等场景。

5.2 实战：设备数据校验交换

实际场景中，传感器数据的”采集-校验”流水线使用Exchanger实现：采集线程将数据交给校验线程，同时取回校验结果。

对比维度 CountDownLatch CyclicBarrier

8.2 CountDownLatch的AQS原理？

CountDownLatch基于AQS共享模式实现：

  1. 构造函数将AQS的state设置为计数器初始值
  2. countDown()调用releaseShared(1)→tryReleaseShared(1)：CAS将state减1，减到0时调用doReleaseShared()唤醒AQS等待队列中的所有线程
  3. await()调用acquireSharedInterruptibly(1)→tryAcquireShared(1)：如果state!=0返回-1，线程进入AQS等待队列阻塞；如果state==0返回1，线程直接通过

关键点：tryReleaseShared使用CAS保证原子性，多个线程同时countDown不会丢失计数。

8.3 CyclicBarrier如何实现循环？

CyclicBarrier通过内部Generation类实现轮次管理：

  1. 每个Generation实例代表一轮等待
  2. 当最后一个线程到达（count==0）时，执行barrierAction，然后调用nextGeneration()
  3. nextGeneration()做三件事：signalAll()唤醒所有等待线程、重置count=parties、创建新的Generation
  4. 如果某个线程异常或被中断，调用breakBarrier()将当前Generation标记为broken，唤醒所有线程抛出BrokenBarrierException
  5. 调用reset()可以强制进入下一轮（新建Generation，重置count）

8.4 Semaphore的公平与非公平？

  • 非公平模式（默认）：线程获取许可时不检查AQS等待队列，直接CAS尝试获取。吞吐量高，但可能导致等待线程饥饿。
  • 公平模式：线程获取许可前先检查AQS等待队列是否有先到的线程，如果有则排队等待。保证FIFO顺序，但吞吐量降低约30%。

实际项目使用非公平模式，因为设备控制指令无优先级差异，吞吐量优先。

8.5 为什么countDown必须放finally？

如果countDown不在finally中，子线程抛异常后countDown不会执行，计数器永远无法归零，主线程的await将永久阻塞。这是实际项目中最常犯的错误（15个问题中的第1个），通过代码评审强制规范后消除。

十、总结

CountDownLatch和CyclicBarrier是Java并发编程中多线程协作的两大核心利器。在实际项目的实战中，核心认知如下：

  1. CountDownLatch适合”主等子”的一次性场景：并行初始化将启动时间从45秒优化到8秒，并行查询将看板响应从3秒优化到400毫秒。关键是countDown放finally、await设超时。

  2. CyclicBarrier适合”互相等”的循环场景：多矿区分批处理、传感器数据多轮校验，CyclicBarrier的循环重用和barrierAction特性让代码更简洁。关键是处理BrokenBarrierException、barrierAction轻量化。

  3. Semaphore是并发限流的首选：设备控制指令限流、数据库连接池限制，Semaphore的许可机制简洁有效。关键是tryAcquire代替acquire、release放finally。

  4. 线程池隔离比同步工具更重要：再好的同步工具，配上一个共享的无界线程池，也会互相影响。按模块隔离线程池是实际项目最有效的稳定性保障之一。

  5. 监控是闭环的最后一环：CountDownLatch的getCount()、CyclicBarrier的getNumberWaiting()、Semaphore的availablePermits()——这些指标让多线程协作从黑盒变成白盒。

技术工具的选择没有银弹，只有适合场景的才是最好的。2023年掌握这些多线程协作利器后，实际项目的并发编程从”能跑就行”进化到了”稳而优雅”。
