CAS与原子操作——无锁并发的基石

发布于 2023-05-07 分类：技术, 2023, 并发编程 👁

前言

从synchronized到volatile，再到CAS——这是理解Java并发编程的进阶之路。CAS（Compare And Swap）是JUC包中大部分并发工具的底层实现，理解CAS是理解无锁编程的关键。这篇文章从CAS核心原理到Unsafe底层实现，从Atomic类源码分析到LongAdder分段CAS，从ABA问题到实战限流器与自旋锁，结合实际项目实战经验，全面深入分析CAS与原子操作。

CAS核心原理

CAS是什么

CAS（Compare-And-Swap），即比较并交换，是乐观锁的核心思想：先比较再交换，只有一个线程能成功。CAS是CPU提供的一条原子指令，不是操作系统层面的机制，因此避免了用户态到内核态的切换开销。

Java 9+ VarHandle与原子操作

VarHandle简介

Java 9引入了java.lang.invoke.VarHandle，提供了比Unsafe更标准化的原子操作API。VarHandle统一了字段访问、数组访问和内存屏障操作。

VarHandle的9种访问模式

访问模式 方法后缀 语义 对应屏障
plain get/set 普通读写，无特殊保证 无
opaque getOpaque/setOpaque 保证原子性，但不保证顺序 编译器屏障
acquire getAcquire 保证后续读写不会重排到此读之前 LoadLoad + LoadStore
release setRelease 保证前面的读写不会重排到此写之后 StoreStore + LoadStore
volatile getVolatile/setVolatile 与volatile字段语义一致 完整的内存屏障
compareAndSet compareAndSet CAS操作，volatile语义 完整的内存屏障
compareAndExchange compareAndExchange CAS返回旧值，volatile语义 完整的内存屏障
getAndSet getAndSet 原子交换，volatile语义 完整的内存屏障
getAndAdd getAndAdd 原子加，volatile语义 完整的内存屏障

常见项目问题与解决方案

以下是实际项目中遇到的CAS与原子操作相关真实问题及解决方案：

# 问题 现象 原因 解决方案
1 ABA导致矿车状态丢失维修记录 矿车从”运行→维修→运行”后，安全检查遗漏维修环节 AtomicReference只比较值不比较版本，A→B→A的CAS会成功 使用AtomicStampedReference加版本号，每次修改版本+1
2 CAS自旋导致CPU飙升 GPS数据高并发写入时CPU使用率持续90%+，但TPS不提升 大量线程CAS竞争同一AtomicLong，失败后自旋空耗CPU 改用LongAdder分段CAS，不同线程CAS不同Cell
3 LongAdder sum()值不稳定 GPS数据处理计数sum()与实际有偏差 sum()遍历Cell时可能有并发修改，非精确快照 业务允许弱一致性用LongAdder，需精确值用AtomicLong
4 AtomicInteger误用于复合操作 设备注册check-then-act出现重复注册 containsKey+put非原子，两个线程同时通过检查 改用ConcurrentHashMap.putIfAbsent或Atomic类CAS
5 AtomicBoolean实现自旋锁不公平 某些线程长时间获取不到锁 非公平CAS，后到的线程可能先成功 改用TicketLock（排队锁）或ReentrantLock(fair=true)
6 DCL单例未加volatile 偶发NPE，单例对象字段为null new操作重排序为”分配→赋值→初始化”，其他线程看到未初始化对象 单例引用加volatile，禁止指令重排序
7 volatile误用保证复合原子性 GPS计数器值少于实际操作数 volatile仅保证单次读/写原子性，i++是read-modify-write三步操作 使用AtomicInteger或synchronized
8 AtomicIntegerFieldUpdater字段非volatile 运行时抛出IllegalArgumentException 字段更新器要求字段必须是volatile 确保被更新字段声明为volatile
9 虚假共享导致Cell性能下降 LongAdder在高并发下性能远低于预期 多个Cell在同一缓存行，MESI协议导致缓存频繁失效 使用@Contended注解或手动缓存行填充
10 AtomicReference包装多字段一致性丢失 设备状态更新后，部分字段是旧值部分是新值 AtomicReference只能保证引用的原子性，多字段需整体替换 将多字段封装为不可变对象，CAS替换整个引用
11 自旋锁长时间持有导致活锁 持有锁的线程被OS调度挂起，其他线程持续自旋 自旋锁不适合长临界区，持有锁期间线程被调度切换 临界区极短用自旋锁，否则用互斥锁
12 CAS操作缺少重试上限 极端情况下无限自旋导致线程假死 没有设置最大重试次数，异常场景下CAS永远失败 设置最大重试次数，超过后降级为锁或抛异常
13 LongAccumulator初始化值错误 矿车速度统计最大值始终为0 LongAccumulator(Long::max, 0)的identity=0，第一次比较max(0,100)=100正确，但统计最小值Long::min用Long.MAX_VALUE初始化 理解LongAccumulator的identity语义，max用0，min用Long.MAX_VALUE
14 AtomicStampedReference比较逻辑错误 状态更新偶尔失败 compareAndSet同时比较引用和版本号，引用相等但版本号不匹配 确保同时传入正确的期望值和期望版本号
15 高并发下AtomicLong成为瓶颈 设备在线数统计接口RT从10ms飙升到500ms 大量线程CAS竞争同一AtomicLong，自旋严重 低竞争场景用AtomicLong，高竞争场景用LongAdder；读多写少场景考虑StampedLock乐观读

总结

CAS是无锁并发的基石，JUC包中ReentrantLock、Atomic类、并发容器等都依赖CAS。深入理解CAS后，核心认知是：

CAS原理：CPU级别的原子指令（x86的lock cmpxchg），通过Unsafe类暴露给Java层。核心语义是”比较并交换”，只有当内存值等于期望值时才更新。

Atomic类体系：从基本类型（AtomicInteger/Long/Boolean/Reference）到数组类型、字段更新器、高性能累加器（LongAdder/LongAccumulator），构成了完整的原子操作工具集。

ABA问题：CAS的经典陷阱，值从A变B又变回A会导致误判。AtomicStampedReference通过版本号解决，AtomicMarkableReference通过布尔标记解决。

LongAdder：通过base+Cell[]的分段CAS机制，将单一热点分散到多个Cell，解决了高并发下AtomicLong的自旋问题。代价是sum()非精确快照，且空间开销更大。

实战要点：

  1. CAS适合低冲突场景，高冲突场景用LongAdder分段CAS或直接用锁
  2. 多字段原子更新必须用不可变对象+AtomicReference，不能用多个Atomic变量
  3. 自旋锁适合极短临界区，长临界区必须用互斥锁
  4. 理解CAS的底层实现有助于分析并发性能问题
  5. Java 9+的VarHandle提供了比Unsafe更标准化的原子操作API

在实际场景中，车辆GPS数据的高并发计数使用LongAdder，设备状态的原子更新使用AtomicStampedReference避免ABA，自旋锁用于极短临界区的设备标志更新。只有深入理解CAS原理和原子类的适用场景，才能在项目中做出正确的技术选型。
