ReentrantLock源码分析——从AQS到公平与非公平锁

发布于 2023-05-07 分类：技术, 2023, 并发编程 👁

前言

在实际场景中，Synchronized用久了，总觉得Lock只是Synchronized的替代品。直到矿车调度系统需要实现”可中断的锁”、”超时获取锁”等特性，才发现ReentrantLock远比想象中强大。深入源码后，更是理解了AQS的精妙设计——原来JUC包下那么多并发工具，底层都是同一套框架。

AQS设计哲学：为什么 ReentrantLock 这样实现

理解 ReentrantLock，关键是理解 AQS 的四处设计取舍：

1. 为什么用 volatile int state 而不是 synchronized 的 monitor？
state 是锁的”状态位”，volatile 保证多线程间的可见性（释放锁的写 happens-before 后续获取锁的读）。AQS 把”是否上锁、重入几次”抽象成一个整数，子类只关心 state 的语义，其余排队、阻塞、唤醒全部由 AQS 统一实现。这正是模板方法模式：AQS 固定 acquire/release 骨架，子类只实现 tryAcquire/tryRelease。

2. 为什么用 CLH 变体双向队列而不是简单的等待列表？
CLH 是 Craig-Landin-Hagersten 队列锁的变体，每个等待线程是一个 Node，通过 prev/next 指针串联。它把”自旋还是阻塞”的决策下放给每个 Node 自己（看前驱的 waitStatus），避免了全局锁竞争；入队/出队只需 CAS 修改 tail，扩展性远好于 synchronized 的单向等待队列。

3. 为什么释放锁（tryRelease）不需要 CAS？
因为只有持有锁的线程才能调用 unlock()，不存在并发写 state 的竞争；而加锁（tryAcquire）是多线程竞争，必须用 CAS 保证原子性。这一”不对称”设计正是性能与正确性的平衡点。

4. 为什么需要 CANCELLED/SIGNAL/CONDITION/PROPAGATE 四种状态？
它们是 AQS 在”阻塞—唤醒”过程中节点生命周期的精确刻画：SIGNAL 表示”我后面那位需要被唤醒”，CANCELLED 表示等待超时/中断而放弃，CONDITION 表示在条件队列中，PROPAGATE 用于共享模式（如 Semaphore）的唤醒传播。状态机让 AQS 能在无锁前提下正确协调大量线程。

内存语义：加锁不只是”独占”

很多同学以为 lock() 只是把锁占住，其实它建立了 happens-before 关系：线程 A 在 lock() 与 unlock() 之间写入的变量，对线程 B 在随后获得同一把锁后的读可见。原因是 state 是 volatile，AQS 的 release 写 state 与 acquire 读 state 形成 volatile 的可见性规则。换言之，ReentrantLock 既是互斥工具，也是线程间通信的”内存屏障”，可替代 synchronized 实现安全的共享变量访问。

生产实战与踩坑经验

lock() 必须放在 try-finally 中

最常见的错误是把 lock() 写在 try 外面却忘记 unlock()，一旦业务代码抛异常，锁永远不释放，后续线程全部阻塞（死锁）。正确模板：

用 tryLock(timeout) 避免无限等待

矿车调度中”库存调拨”场景不能无限等待锁，否则会导致调度线程池耗尽。用 tryLock 带超时获取，超时即返回 false 走降级或重试：

Condition 必须在持有锁时 await

调用 condition.await() 前必须已 lock()，否则直接抛 IllegalMonitorStateException。另外 await() 被唤醒后仍需重新竞争锁，存在”虚假唤醒”风险，返回值后必须用 while 而非 if 重新检查条件，否则可能拿到错误状态继续往下走。

不要把 synchronized 和 ReentrantLock 混用同一资源

两者互不感知，混用同一共享资源等于没有加锁。统一用一把锁保护同一临界区。

公平锁的隐藏成本

公平锁每次 tryAcquire 都要 hasQueuedPredecessors() 扫描队列，且禁止插队，高并发下吞吐量明显低于非公平锁。矿车调度只有在”必须严格 FIFO、且出现过线程饥饿”时才开启 new ReentrantLock(true)，绝大多数场景用默认非公平锁。

ReentrantLock 构造与 Condition 创建

从 AQS 视角看锁的全家福：ReentrantLock / CountDownLatch / Semaphore 的同源性

理解 AQS 最大的收益，是发现 JUC 里一大半工具其实是”同一个引擎的不同配置”。三者共享 AQS 的队列管理、挂起唤醒、状态语义，差异只在state 的含义和获取逻辑：ReentrantLock 把 state 解释为”重入次数”，获取逻辑是 state==0 才 CAS；CountDownLatch 把 state 解释为”剩余计数”，获取条件是 state==0、释放是 state–，所以它是一次性的（state 不可回升）；Semaphore 把 state 解释为”剩余许可”，获取条件是 state>0、可增可减，所以可复用。甚至 ReadWriteLock 也只是把一个 32 位 state 拆成高低位复用。面试答”AQS是什么”时，答出”状态语义 + 队列调度”这个抽象层次，比背 lock/acquire 流程更能体现理解深度。实际工作中这套同源性也很有用：遇到需要自定义同步器的场景（比如”最多 N 个设备同时下发指令”的自定义限流器），直接继承 AQS 改写 tryAcquire/tryRelease 十几行代码，比手写队列和挂起唤醒逻辑可靠得多。

读写锁升级为 StampedLock 的信号

工程上还有一个前置判断值得写进选型清单：什么时候该从 ReentrantLock 系列迁移到 StampedLock？信号有三个：一是监控显示读锁等待时间占比持续超过 30%（读读互斥的代价开始显现）；二是临界区读的耗时在微秒级（乐观读收益区间）；三是业务能接受弱一致读（validate 失败可重试）。三个条件同时满足再迁移，且迁移时必须回归测试可重入路径——StampedLock 不可重入，任何隐藏的重入调用都会变成死锁。反过来，只要临界区里有 IO 或需要 Condition，就直接放弃 StampedLock，ReentrantLock 的多 Condition 仍是最优解。

面试高频问题

1. ReentrantLock和Synchronized的区别？

Synchronized是JVM内置锁，自动获取释放；ReentrantLock是API层面锁，需手动获取释放。ReentrantLock支持可中断、超时、公平锁、多Condition。JDK6之后Synchronized经过锁升级优化（偏向锁→轻量级锁→重量级锁），两者性能差距不大。

2. AQS是什么？

AbstractQueuedSynchronizer，JUC锁的底层框架。核心是state变量+CLH双向队列。ReentrantLock、Semaphore、CountDownLatch都基于AQS实现。AQS采用模板方法模式，子类只需实现tryAcquire/tryRelease等方法。

3. 公平锁和非公平锁的区别？

公平锁先检查CLH队列是否有等待线程（hasQueuedPredecessors），严格先到先得；非公平锁新线程可以先CAS抢锁，允许插队。非公平吞吐量高但可能饥饿。ReentrantLock默认非公平，因为非公平锁减少线程上下文切换。

4. AQS的state变量有什么用？

不同工具赋予不同语义。ReentrantLock中state=0未锁定，>0锁定次数（可重入）；Semaphore中state=剩余许可数；CountDownLatch中state=剩余计数；ReentrantReadWriteLock中state高16位=读锁持有数，低16位=写锁重入数。

5. 为什么unparkSuccessor从tail向前遍历？

因为addWaiter()中，prev指针在CAS之前设置，next指针在CAS之后设置。如果中间有节点取消，next指针可能断裂。从tail沿prev链遍历是安全的，因为prev链始终完整。

6. ReentrantLock的可重入是如何实现的？

tryAcquire()中检查当前线程是否为锁持有线程（current == getExclusiveOwnerThread()），如果是则state+1。tryRelease()中state-1，只有state减到0才完全释放锁。state使用int类型，溢出时会抛出Error。

7. lockInterruptibly和lock的区别？

lock()中acquireQueued()被中断后只记录标志（interrupted=true），获取锁后通过selfInterrupt()补上中断。lockInterruptibly()中doAcquireInterruptibly()被中断后直接抛出InterruptedException，并调用cancelAcquire清理队列节点。

8. Condition的await和signal流程？

await()：将当前线程包装为Node加入条件队列 → fullyRelease释放锁 → park等待 → 被signal唤醒后转移到CLH队列 → 重新获取锁。signal()：将条件队列首节点转移到CLH同步队列，设置前驱SIGNAL等待被unpark。

9. 为什么非公平锁吞吐量更高？

锁释放后唤醒等待线程需要时间（线程从park到running涉及系统调用），非公平锁允许新线程在此期间插队获取锁，避免了线程上下文切换的开销。刚释放锁的线程大概率还在CPU时间片内，CAS成功率很高。

10. 如何选择Synchronized和ReentrantLock？

简单同步用Synchronized（自动释放、JVM优化），需要可中断/超时/公平/多Condition时用ReentrantLock。永远不要混用同一资源的两种锁，因为Synchronized和ReentrantLock互不排斥。

为什么读源码时总觉得”非公平”很难理解

很多同学读非公平锁的 lock() 源码时困惑：上来就 CAS(0, acquires) 抢锁，那队列里的线程算什么？换个角度就通了——非公平锁的”插队”只发生在两个瞬间：锁刚释放的一刹那（释放线程唤醒后继者之前，新线程抢先进 CAS）和锁空闲的初始状态。一旦竞争激烈、CAS 失败，新线程照样老老实实入队，并不会无限插队把老线程饿死。理解这一点，再看”公平锁为什么慢”也就清楚了：公平锁每次加锁前都要 hasQueuedPredecessors() 检查队列，这个检查本身就是一次对队列头节点的 volatile 读加判断，高并发下所有线程都挤在这个检查点上，缓存行竞争让它比非公平锁慢一截——JDK 作者在注释里写”fair locks have much lower overall throughput”就是这个原因。实际选型经验：吞吐敏感的短临界区（缓存更新、计数）用默认非公平锁；对延迟公平性有硬需求的场景（如按请求顺序处理配额）才用公平锁，并接受性能代价。

总结

ReentrantLock的核心是AQS：state表示锁状态，CLH队列管理等待线程。非公平锁在加锁时先CAS抢锁，抢不到再排队；公平锁则严格按队列顺序获取。在实际场景中，理解了AQS的tryAcquire/tryRelease + CLH队列机制，就理解了ReentrantLock的一切——可重入、可中断、超时获取、条件变量，都是在这个框架上扩展的。正是基于对ReentrantLock的深入理解，我们才能在矿车调度、库存调拨、任务队列等场景中选对锁、用对锁。
