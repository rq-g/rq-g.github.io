ConcurrentHashMap源码分析——JDK7与JDK8的演进

发布于 2023-05-01 分类：技术, 2023, 并发编程 👁

前言

在实际场景中，ConcurrentHashMap 是使用频率最高的并发容器——从矿车调度状态缓存、设备实时监控数据聚合，到告警事件去重索引、井下人员定位数据分组统计，几乎每一个高并发模块都离不开它。2023年之前只停留在”分段锁”和”CAS+synchronized”的面试八股层面，直到一次生产环境因 ConcurrentHashMap 使用不当引发的性能抖动，才下定决心深入源码，系统梳理 JDK7 到 JDK8 的演进逻辑：Segment 分段锁如何退场、CAS + synchronized 如何接力、volatile 如何保证 get 无锁可见、多线程如何并发扩容、CounterCell 如何分散计数……只有真正读懂每一行源码的取舍，才能在智慧矿山这样的高并发工业系统中正确选型、高效排错。

为什么不用 HashMap 和 Hashtable

在实际项目的选型阶段，曾短暂使用 HashMap 做设备状态缓存，上线后遭遇并发死循环；Hashtable 则因全表锁导致矿车调度接口 RT 飙升。最终选择了 ConcurrentHashMap。

面试高频问题

1. JDK8 为什么用 synchronized 替代 ReentrantLock？

synchronized 在 JDK6 后有锁升级优化（偏向锁 → 轻量级锁 → 重量级锁），低竞争场景下性能更好；ConcurrentHashMap 的锁粒度是单个桶，低竞争是常态；synchronized 不需要手动释放锁，减少忘记 unlock 的风险；synchronized 不依赖 AQS 的 CLH 队列，内存占用更少；ReentrantLock 的 Condition、公平锁等特性在 ConcurrentHashMap 场景中不需要。

2. ConcurrentHashMap 的 get 为什么不需要加锁？

Node 的 val 和 next 都是 volatile 的，保证可见性；get 操作只读不写，通过 volatile 语义保证读到最新值；写操作对链表的修改是追加式的（尾插新节点或更新 val），不会破坏正在遍历的链表结构；如果正在扩容，ForwardingNode 的 find 方法会转发到 nextTable 查找。

3. ConcurrentHashMap 如何保证并发扩容安全？

通过 ForwardingNode（hash=MOVED）标记正在迁移的桶；其他线程 put 时看到 ForwardingNode，会调用 helpTransfer 协助扩容；每个线程通过 transferIndex 领取一段桶（默认16个）独立迁移；迁移完成的桶放置 ForwardingNode，防止重复迁移；最后一个完成迁移的线程负责切换 table 引用和更新 sizeCtl。

4. ConcurrentHashMap 的 key/value 为什么不允许为 null？

并发场景下 null 有歧义：get(key) 返回 null 时，无法区分是 key 不存在还是 value 为 null；虽然可以用 containsKey 判断，但 containsKey 和 get 之间可能被其他线程修改，结果不一致；HashMap 可以容忍 null 因为它是单线程的，containsKey + get 不会被干扰。

5. 链表长度达到 8 一定会转红黑树吗？

不一定。treeifyBin 方法中会先检查数组长度是否 >= MIN_TREEIFY_CAPACITY(64)；如果数组长度 < 64，优先扩容而非树化；因为扩容能将元素分散到更多桶中，减少链表长度；且小数组时红黑树的内存开销（TreeNode 比 Node 多 4 个引用 + 1 个布尔）不划算。

总结

ConcurrentHashMap 是 Java 并发编程的巅峰之作，从 JDK7 到 JDK8 的演进体现了对高并发场景的持续优化。在实际项目的实践中，深入源码后的核心认知是：

  1. JDK8 用 CAS + synchronized 替代分段锁：锁粒度从 Segment 级别细化到桶级别，并发度从固定 16 提升到数组长度；synchronized 的锁升级优化在低竞争场景下优于 ReentrantLock
  2. get 无锁通过 volatile 保证可见性：Node 的 val 和 next 都是 volatile 的，读操作完全无锁，这是 ConcurrentHashMap 高并发读取的根基
  3. 多线程并发扩容提升效率：通过 ForwardingNode 标记 + transferIndex 任务分配，多个线程可同时迁移不同桶，是 JDK7 完全不具备的能力
  4. 红黑树优化最坏查询复杂度：链表长度 >= 8 且数组 >= 64 时转红黑树，查询从 O(n) 优化到 O(logN)，智慧矿山设备监控场景实测提升 10 倍
  5. CounterCell 分散计数：借鉴 LongAdder 思想，无竞争更新 baseCount，有竞争分散到 CounterCell[]，高并发计数不再成为瓶颈
  6. 原子方法是正确使用的前提：putIfAbsent、computeIfAbsent、compute、merge 等原子方法避免了复合操作的竞态条件，是日常开发的第一选择
