并发容器对比——CopyOnWriteArrayList与ConcurrentHashMap

发布于 2023-05-20 分类：技术, 2023, 并发编程 👁

前言

在实际场景中，多线程环境下使用ArrayList和HashMap导致数据不一致——设备状态列表并发修改报ConcurrentModificationException，传感器配置Map在并发读写时数据丢失。换成ConcurrentHashMap后问题解决，但CopyOnWriteArrayList在设备列表遍历时又出现性能问题。2023年系统学习并发容器后，终于能根据矿山业务场景选择合适的容器。

线程安全容器演进

线程安全容器的演进，本质是锁粒度不断变小、最终走向无锁的过程：

世代 代表容器 并发策略 问题
第一代 Vector / Hashtable 每个方法 synchronized 全表锁 单容器吞吐被锁死
第二代 Collections.synchronizedXxx 包装类，仍是全表锁 换汤不换药，迭代还需手动加锁
第三代 ConcurrentHashMap / CopyOnWriteArrayList 分段锁→CAS+synchronized；写时复制 锁粒度降到桶级/读完全无锁
第四代 BlockingQueue / ConcurrentSkipListMap / LongAdder 阻塞语义、跳表、分散计数 面向特定场景的专业化

多线程协助扩容是 ConcurrentHashMap 的精髓：扩容不再是”STW式的全表搬运”，而是每个读/写线程顺手帮着搬16个桶——把一次大停顿摊薄到每一次并发操作里。

红黑树转换阈值

阈值 值 含义
TREEIFY_THRESHOLD 8 链表长度≥8时尝试树化
UNTREEIFY_THRESHOLD 6 树节点≤6时反树化为链表
MIN_TREEIFY_CAPACITY 64 数组长度<64时优先扩容而非树化

为什么是8？ 负载因子0.75下，链表长度服从泊松分布，长度达到8的概率约千万分之一。如果真的到了8，说明hash冲突严重，树化让查找从O(n)降到O(log n)。8和6之间留2的缓冲，避免在临界值附近反复树化/反树化抖动。

实际项目经验：设备ID的hash分布均匀时几乎不会触发树化；如果监控发现频繁 treeifyBin，第一件事是检查key的hashCode()实现——典型事故是自定义key只重写equals不重写hashCode，所有元素挤进同一个桶。

三个关键设计：array 用 volatile 修饰（写线程替换引用后，读线程立即可见）；写操作锁的是同一把 lock 对象（JDK8起是 synchronized，此前是 ReentrantLock）；迭代器持有创建时的数组快照，遍历期间容器怎么改都影响不到它——这就是”弱一致性”。

源码分析

COW的适用边界：一套量化判断标准

COW 最容易被误用的地方是”无脑当线程安全 ArrayList 用”。判断能不能用 COW，本质是算三笔账。第一笔是写放大账：每次写都复制整个数组，10 万元素的列表单次 add 就是 10 万次引用拷贝（约 400KB 内存分配 + 拷贝），批量导入 1 万条数据就是 1 万次数组复制——O(n²) 的总代价。经验阈值：元素规模上千、每秒写入超过个位数，就不该用 COW。

第二笔是内存账：写期间新旧两份数组同时存活，峰值内存翻倍；且旧数组要等所有持有它的迭代器用完才能回收，”长迭代 + 高频写”会造成老年代快速膨胀。设备类型列表、白名单配置这类”启动加载、偶尔整表刷新”的场景完全无压力；但实时追加的监控数据流用 COW 就是内存事故。

第三笔是一致性账：COW 迭代器是快照语义，遍历开始后容器怎么改都看不到——这有时是特性（遍历期间不怕被并发修改抛 CME），有时是 bug（遍历中检查”元素是否存在”再操作，用的却是旧数据）。JDK 后来的 CopyOnWriteArrayList.forEach 也好、ConcurrentHashMap 的弱一致迭代也好，JUC 的迭代器几乎全是弱一致的，这是整个包的设计基调：并发容器优先保证”不崩、不锁死”，把”读到最新”的责任交给调用方评估。

为什么 JUC 里没有”完美的线程安全 List”

把 JUC 翻一遍会发现一个有趣的空白：有并发 Map（ConcurrentHashMap）、并发 Queue（十几种）、并发 Set（包装 COW），唯独”并发 List”只有 CopyOnWriteArrayList 这一个在特定场景下可用的实现。原因值得深想：List 的核心操作（按下标随机访问、中间插入删除）与高并发天然冲突——随机访问意味着无法分段（不像 Map 能按 hash 拆桶），中间插入意味着写写互斥无法避免。所以 JUC 的设计者给出的答案是”绕开”：要 FIFO 语义用 Queue 族（CAS 或双锁入队出队分离），要键值语义用 Map，只有”整体替换式的小列表”才留给 COW。理解了这个设计取舍，”为什么没有并发 ArrayList”这类面试题就有了源码层面的答案，选型时也不会再对着 COW 的性能曲线困惑。

ConcurrentLinkedQueue

CAS无锁实现原理

  • 无锁，纯CAS操作，不会阻塞
  • size()需要遍历整个链表，O(n)
  • 不允许null元素
  • 迭代器弱一致性

AtomicLong 是”所有人挤一个窗口”；LongAdder 是”先一个人值班，人多了临时开窗口分流”。代价是 sum() 读的时候要遍历 Cell 数组，读到的不是瞬时精确值——写多读少的监控计数场景可以接受，账务场景不行。

选型背后的统一逻辑：锁粒度与一致性级别的权衡

把整个 JUC 的演进串起来看，所有容器都在回答同一对矛盾：并发度（多少操作能同时进行）与一致性强度（读到多新的数据）。Vector/Hashtable 用方法级 synchronized，并发度 1，一致性最强（读永远看到最新）；ConcurrentHashMap 把锁拆到桶级，并发度等于数组长度，但换来的是弱一致迭代（size() 与 containsValue() 都是近似统计）；ConcurrentLinkedQueue 干脆去掉锁，用 CAS 自旋，吞吐最高，但 size() 退化成 O(n) 遍历——因为无锁结构下”精确计数”本身就需要加锁才能保证原子性；LongAdder 更进一步，连”分散热点的计数”都放弃了瞬时精确，明确告诉调用方 sum() 只是估计值。

这条线索对实际工作的指导意义在于：选并发容器时先问自己”这个数据读出来的精度要求是什么”。监控计数、在线人数、限流预判这类统计值，弱一致完全够用，换来的是数量级的吞吐提升；但库存扣减、配额控制这类”结果必须精确”的场景，弱一致统计就是资损事故，必须回到原子复合操作（compute/merge/Lua）或数据库层保证。很多线上问题追到底，根因都是”用了弱一致工具却按强一致语义在用”。

生产环境的三个真实教训

三个发生在我们项目里的教训，比任何理论都有说服力。教训一：COW 上的”先读后写”不是原子的。设备白名单功能，A 线程 contains() 判断通过后，B 线程 remove() 并提交，A 再执行基于白名单的操作——读和写之间没有任何同步保障，contains 和后续动作必须整体加锁，COW 只保证单次调用安全，不保证组合操作原子。教训二：CHM 的 size() 是”近似值”。JDK8 的 size() 汇总 baseCount + CounterCell 数组，多线程并发写时返回值是某一瞬间的估计值，用它做”达到阈值就触发熔断”的判断会漏判——高精度计数要么用 LongAdder 自己维护，要么接受近似语义并设计成幂等。教训三：迭代器弱一致性被当成强一致性使用。用 COW 的迭代器做”快照比对”是安全的（它就是快照），但有人把 CHM 的 keySet().iterator() 当成一致性快照来对账，遍历期间新写入的数据部分可见部分不可见，对账结果永远对不上——需要对账就用 keySet() 先拷贝成新集合，明确快照语义。三条教训的共同点：容器的线程安全是”单方法级别”的承诺，不是”业务操作级别”的承诺，把组合逻辑的原子性交给容器是设计者的错觉。

COW 与 ConcurrentHashMap 的设计哲学分野

把两类容器放在一起看，能看出并发设计中两种截然不同的取舍哲学。CopyOnWriteArrayList 选择了”写时复制、读永远无锁”：它的正确性建立在”读操作看到的永远是某个完整时点的快照”之上，代价是每次写都复制整个底层数组。这种设计只有在”读占 99% 以上、列表规模可控、写后不需要立刻读到最新值”时才是赚的——设备白名单、配置列表、监听器列表是它的典型舞台；而一个 10 万元素的实时更新的订单列表用 COW，每次 add 复制 10 万引用（约 400KB 内存分配），GC 压力会让系统看起来”没有 CPU 占用却频繁卡顿”。ConcurrentHashMap 则选择了”细粒度锁 + 无锁读的混合”：读基本无锁（依靠 volatile 的 Node.val 和 tab 数组），写只锁单个 bin，容量几乎不受限。理解这个分野的关键是问自己一个问题：这个容器需要的是”最终一致的快照”还是”实时的并发视图”？需要快照（遍历期间不怕数据旧，就怕遍历中抛 ConcurrentModificationException）选 COW；需要实时（统计计数、任务队列）选 CHM 家族。很多性能问题的根源，是用错了哲学而不是写错了代码。

面试高频问题

1. ConcurrentHashMap和Hashtable的区别？

ConcurrentHashMap用CAS+synchronized锁单个桶，并发度高；Hashtable用synchronized锁整个对象，并发度低。

2. ConcurrentHashMap JDK7和JDK8的区别？

JDK7用Segment分段锁，并发度固定为16；JDK8用CAS+synchronized锁单个桶，并发度等于数组长度，且引入红黑树优化长链表查询。

3. CopyOnWriteArrayList的原理？

写操作加锁复制整个数组，读操作无锁。适合读多写少场景，写操作O(n)性能差。

4. BlockingQueue的阻塞方法？

put/take：阻塞等待；offer/poll：非阻塞或带超时。

5. 为什么ConcurrentHashMap不允许null key/value？

因为get()返回null时无法区分是key不存在还是value为null。多线程场景下如果允许null，containsKey()+get()复合操作会有歧义。

6. ConcurrentHashMap的扩容机制？

多线程协助扩容，每个线程负责16个桶的迁移。迁移中的桶放ForwardingNode(hash=MOVED)，其他线程put时发现MOVED会帮忙迁移。扩容时2倍增长，链表长度>=8但数组<64时优先扩容而非树化。

7. CopyOnWriteArrayList的迭代器有什么特点？

弱一致性迭代器，创建时保存数组快照，后续修改不影响迭代。不支持remove/set/add操作（抛UnsupportedOperationException）。适合遍历远多于修改的场景。

8. LongAdder和AtomicLong的区别？

AtomicLong所有线程CAS竞争单个value，高并发下性能差。LongAdder通过Cell数组分散热点，不同线程CAS不同Cell，高并发下性能好。但LongAdder的sum()不是原子操作。

9. ConcurrentSkipListMap的特点？

基于跳表实现的有序并发Map，查找/插入/删除都是O(log n)。支持范围查询(subMap/headMap/tailMap)，CAS无锁实现，不允许null key/value。适用于需要排序和范围查询的并发场景。

10. ConcurrentHashMap中链表转红黑树的阈值为什么是8？

泊松分布在负载因子0.75时，链表长度达到8的概率约为千万分之一。如果真的到了8说明hash冲突严重，应该树化优化。而6是反树化阈值，8和6之间留2的缓冲避免频繁转换。

LongAdder 为什么快：把竞争摊开

LongAdder 一节容易只记住结论不懂原理，展开说透。AtomicLong 的问题在于所有线程挤在同一个 volatile 变量上做 CAS，失败线程不断自旋重试，高并发下 CPU 大量消耗在无效重试上，缓存行在核间来回弹跳（伪共享的典型场景）。LongAdder 的解法是**”分而治之 + 最后汇总”**：写时先尝试 CAS base 值，失败说明有竞争，就把增量落到自己对应的 CounterCell 上——Cell 数组初始为空，竞争越激烈按需扩容（上限为 CPU 核数），不同线程几乎落在不同的 Cell 上，把单点竞争摊成了多点并行。代价是读语义变了：sum() 要遍历 base 和所有 Cell 求和，返回的是没有一致性保证的近似值。这个取舍和 ConcurrentHashMap.size() 一脉相承：写吞吐优先，读精度让路。选型判断很清晰：监控指标、计数统计这类”最终对就行”的场景，LongAdder 完胜；需要精确值做条件判断（如”计数达到 N 就拒绝”）的场景，近似值不可接受，要么在低竞争下继续用 AtomicLong，要么自己加锁保护判断逻辑。JDK 设计者的倾向也很明确——LongAdder 的注释里直接写着”在多数统计场景下，它比 AtomicLong 更可取”，这是有数据支撑的官方推荐。

总结

并发容器是JUC包的核心组件，也是实际项目中多线程编程的基础。核心认知是：ConcurrentHashMap是高并发Map的首选，CopyOnWriteArrayList只适合读多写少，BlockingQueue是生产者-消费者的最佳实现。选对容器，多线程编程事半功倍。在实际场景中，正是基于对并发容器的深入理解，我们才能在设备状态缓存、任务队列、告警处理等场景中选对容器、避坑排雷。
