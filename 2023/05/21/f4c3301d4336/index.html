JVM垃圾收集器详解——从Serial到ZGC的演进

发布于 2023-05-21 分类：技术, 2023, JVM 👁

前言

实际项目的设备采集服务（device-service）上线三个月后，每到夜班巡检高峰期就会出现3~5秒的服务卡顿。运维同事反馈日志中出现了大量 Full GC 记录，单次停顿高达 4.2 秒。当时团队对 JVM 垃圾收集器的认知仅停留在”默认配置能跑就行”，完全不清楚 Serial、Parallel、CMS、G1、ZGC 之间的差异，更不知道如何根据业务场景选择和调优。2023 年系统学习 JVM 垃圾收集器后，终于能根据实际项目各服务的业务特征（实时性、吞吐量、内存规模）选择合适的 GC 策略并精确调优，最终将设备采集服务的 GC 停顿从 350ms 降至 20ms 以内，Full GC 频率从每日 3 次降至连续 60 天 0 次。

本文以实际项目为实战背景，从垃圾收集器的基础理论出发，逐一剖析 Serial、ParNew、Parallel Scavenge、CMS、G1、ZGC 六大收集器的原理、参数、调优实战，最后结合项目中的 15 个真实问题，给出完整的选型与调优方案。

1.4 垃圾收集算法

算法 原理 优点 缺点 适用区域
标记-清除 标记存活对象，清除未标记对象 实现简单，不需要移动对象 内存碎片，分配效率低 CMS
标记-复制 将存活对象复制到另一半空间 无碎片，分配快（指针碰撞） 空间利用率仅 50% 新生代（Serial/ParNew/Parallel）
标记-整理 标记后将存活对象向一端移动 无碎片，空间利用率高 移动对象开销大 老年代（Serial Old/Parallel Old）

三、Serial 收集器

3.1 工作原理

Serial 是最基础的垃圾收集器，使用单线程完成垃圾收集工作。在收集期间，必须暂停所有用户线程（STW）。

Serial 收集器工作流程：

  1. 单线程收集，无多线程同步开销
  2. STW 期间所有用户线程暂停
  3. 实现简单，内存占用最少
  4. 适合客户端模式、小堆内存场景

四、ParNew 收集器

4.1 工作原理

ParNew 是 Serial 的多线程版本，使用多个 GC 线程并行完成新生代收集。它存在的唯一意义就是配合 CMS 使用——CMS 只能搭配 ParNew 或 Serial 作为新生代收集器。

五、Parallel Scavenge 收集器

Parallel Scavenge 与 ParNew 类似，也是新生代多线程收集器，但它的设计目标是”吞吐量优先”。它自带自适应调节策略（Ergonomics），能根据目标吞吐量和停顿时间自动调整新生代大小、Eden 与 Survivor 比例、晋升年龄等参数。

六、CMS 收集器

6.1 工作原理

CMS（Concurrent Mark Sweep）是第一个实现并发收集的垃圾收集器，以获取最小停顿时间为目标。它采用标记-清除算法，在并发阶段与用户线程同时运行，大幅缩短 STW 时间。

6.2 CMS 四阶段深度分析

| | Update)减少停顿 |

  • 阶段 | 是否STW | 工作内容 | 实际项目影响
  • 初始标记 | STW | 标记GC Roots直接关联的对象 | safety-service 约 5ms
  • | | 速度极快 | 几乎无影响
  • 并发标记 | 并发 | 从GC Roots遍历整个对象图 | 与告警推送并发运行
  • | | 耗时最长，但用户线程不暂停 | CPU占用增加，不影响延迟
  • 重新标记 | STW | 修正并发标记期间的引用变更 | safety-service 约 20ms

  • 并发清除 | 并发 | 清除死亡对象 | 与告警推送并发运行

6.3 CMS 的四大问题

问题1：内存碎片

  • CMS 使用标记-清除算法，不做内存压缩
  • 长期运行后老年代内存碎片严重：
  • 老年代内存布局：
  • [O][ ][O][ ][O][ ][O][ ][O][ ][O][ ][O][ ]
  • O=存活对象 空格=碎片
  • 后果：大对象（如设备历史数据数组）无法分配，触发 Full GC
  • 解决：
  • -XX:+UseCMSCompactAtFullCollection # Full GC时压缩
  • -XX:CMSFullGCsBeforeCompaction=5 # 每5次Full GC后压缩一次
  • 注意：压缩本身需要STW，是权衡之举
  • 问题2：浮动垃圾
  • 并发清除阶段，用户线程仍在运行，可能产生新的垃圾
  • 这些垃圾本次CMS无法收集，称为”浮动垃圾”
  • 并发标记阶段：标记了对象A为存活
  • 并发清除阶段：用户线程将对象A置为不可达
  • 结果：对象A成为浮动垃圾，本次不收集，留待下次
  • 后果：需要预留空间给浮动垃圾
  • -XX:CMSInitiatingOccupancyFraction=70 # 老年代70%就触发CMS
  • 默认值：JDK5=68%, JDK6+=92%
  • 问题3：Concurrent Mode Failure
  • CMS 在并发清除阶段，如果老年代预留空间不够容纳新生代晋升的对象
  • 或者浮动垃圾占满了预留空间
  • CMS 退化为 Serial Old（单线程标记-整理），全堆扫描
  • 触发条件：老年代使用率 > CMSInitiatingOccupancyFraction
  • 且预留空间仍不足以容纳晋升对象
  • 实际项目中的一次 Concurrent Mode Failure：
  • 2023-04-15 03:22:15 CMS并发清除中
  • 2023-04-15 03:22:16 新生代晋升对象达 450MB
  • 2023-04-15 03:22:16 老年代剩余空间仅 380MB
  • 2023-04-15 03:22:16 Concurrent Mode Failure!
  • 2023-04-15 03:22:16 退化为 Serial Old，STW 4.2秒
  • 2023-04-15 03:22:20 服务恢复，但安全告警已超时
  • 解决：调低 CMSInitiatingOccupancyFraction（70→60）
  • 但过低会导致CMS频繁触发，增加CPU开销
  • 问题4：CPU敏感
  • 并发阶段GC线程与用户线程争抢CPU时间
  • 默认启动 (CPU核数+3)/4 个GC线程
  • 8核服务器：GC线程 = (8+3)/4 = 2 个
  • 4核服务器：GC线程 = (4+3)/4 = 1 个
  • 智慧矿山 safety-service 运行在8核容器中
  • CMS并发阶段占用 2 个CPU核心，对吞吐量影响约 25%
  • 解决：
  • -XX:ConcGCThreads=4 # 增加并发线程数（需权衡CPU占用）
  • 或升级为G1/ZGC # 根本解决方案

七、G1 收集器

7.1 工作原理

G1（Garbage First）是 JDK9 及以后的默认收集器，采用分 Region 的内存布局，打破了传统的新生代/老年代物理隔离，将堆划分为大小相等的 Region，每个 Region 可以动态地扮演 Eden、Survivor、Old 或 Humongous 角色。

G1 Region 内存布局：

  1. Region 动态角色：Eden 可变为 Old，Old 可回收后变为 Free
  2. 优先回收价值高的 Region（垃圾占比高的先回收 → “Garbage First”）
  3. 可预测停顿：根据 MaxGCPauseMillis 选择本次回收哪些 Region

7.2 G1 的三种收集模式

G1 的三种收集模式

  1. Young GC（纯新生代收集）
  2. Mixed GC（混合收集）
  3. Full GC（全堆收集）

7.3 G1 并发标记流程

G1 并发标记的四个子阶段：

  • 阶段1：初始标记（STW，借 Young GC 完成）
  • 标记 GC Roots 直接关联的对象
  • 借助 Young GC 的 STW 完成，无额外停顿
  • safety-service 约 2ms
  • |
  • v
  • 阶段2：并发标记（与用户线程并发）
  • 从 GC Roots 遍历整个对象图
  • 使用 SATB（Snapshot At The Beginning）算法
  • 在标记开始时拍摄对象图快照，保证标记完整性
  • 耗时最长，但不暂停用户线程
  • |
  • v
  • 阶段3：最终标记（STW）
  • 处理 SATB 缓冲区中残留的引用变更
  • 修正并发标记期间对象引用的变化
  • safety-service 约 10ms
  • |
  • v
  • 阶段4：筛选回收（STW）
  • 根据每个 Region 的回收价值（垃圾占比）排序
  • 在 MaxGCPauseMillis 目标内，选择回收价值最高的 Region
  • 将存活对象复制到新 Region，回收旧 Region
  • safety-service 约 20ms
  • 时间线：

八、ZGC 收集器

8.1 工作原理

ZGC（Z Garbage Collector）是 JDK15+ 生产可用的超低延迟垃圾收集器，停顿时间不超过 1ms（JDK16+ 不超过 0.1ms），且停顿时间不随堆大小增加而增长，支持最大 16TB 的堆内存。

ZGC 核心技术架构：

  1. 选择需要整理的 Page
  2. 分配新的 Page（目标位置）
  3. 并发将存活对象复制到新 Page
  4. 复制完成后，旧 Page 释放
  5. 应用线程访问旧地址时，读屏障自动修正到新地址

14.2 GC 调优原则

GC 调优七原则

  1. 先保证代码正确，再调优 GC
  2. 开启 GC 日志是调优的前提
  3. 优先调整堆大小，再切换收集器

十五、总结

实际项目的 GC 调优历程，是从”能跑就行”到”精准调优”的完整蜕变。回顾全文的核心要点：

1. 收集器各有千秋，没有银弹

2. 选型依据业务特征

  • 延迟敏感（safety-service）→ G1，MaxGCPauseMillis=20
  • 吞吐优先（report-service）→ Parallel，GCTimeRatio=99
  • 平衡场景（device-service）→ G1，MaxGCPauseMillis=50
  • 极低延迟（order-service试点）→ ZGC

3. 调优的本质是减少 Full GC

从 device-service 的实战来看，将 Full GC 从每日 3 次降至 60 天 0 次，靠的不是某个”神奇参数”，而是：扩堆 + 切换G1 + 优化Region大小 + 代码层面减少大对象分配。

4. GC 问题往往是代码问题的放大器

内存泄漏、ThreadLocal未清理、大对象全量缓存——这些代码问题才是GC频繁的根源。调优JVM参数只能治标，修复代码才能治本。

5. 数据驱动，持续监控

没有GC日志的调优是盲目的。实际项目已建立GC监控体系：GCEasy定期分析 + jstat实时监控 + Prometheus+Grafana大盘展示，确保GC问题第一时间发现和解决。

系统学习JVM垃圾收集器后，核心认知是：垃圾收集器的选择和调优不是黑魔法，而是基于数据和分析的科学决策。理解每种收集器的设计目标和权衡，结合业务特征做出选择，就是最好的调优。
