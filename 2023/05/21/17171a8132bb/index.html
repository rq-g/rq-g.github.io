JVM命令行工具实战——jps、jstack、jmap、jstat排查指南

发布于 2023-05-21 分类：技术, 2023, JVM 👁

前言

线上CPU飙高、内存溢出、线程死锁，这些问题每个Java开发者都会遇到。但很多人只会重启服务，不知道怎么排查根因。2023年在实际场景中，我系统学习了JVM命令行工具，从”重启大法”进化到”精准定位”，再也不怕线上问题了。这篇文章结合实际项目的真实生产场景，全面深入讲解jps、jstack、jmap、jstat四大核心工具的实战用法。

一、排查思路总览

1.1 排查通用流程

线上问题排查遵循”定位进程→分析线程→分析内存→监控GC→综合定因”五步法：

① 定位 ────▶ ② 分析 ────▶ ③ 分析 ────▶ ④ 监控 ────▶ ⑤ 综合：

  • 进程 线程 内存 GC 定因
  • jps jstack jmap jstat 修复

GC健康度判断矩阵：

指标 正常范围 异常（需排查）：

Young GC频率 几秒~几十秒一次 < 1秒一次：

  • Young GC单次耗时 < 100ms > 500ms
  • Full GC频率 几小时~几天一次 < 1分钟一次
  • Full GC单次耗时 < 1s > 5s
  • 老年代使用率 < 70% > 80%且持续增长
  • Metaspace使用率 < 80%且稳定 > 90%且持续增长
  • FGCT/GCT占比 < 20% > 50%
  • GC总耗时占比 < 2%应用运行时间 > 5%应用运行时间

五、jmap——内存分析

5.1 jmap命令详解

jmap（JVM Memory Map Tool）用于查看堆内存信息和导出堆转储文件，是OOM和内存泄漏排查的核心工具。

-heap -histo -dump

5.2 jmap参数详解

参数 作用 是否触发GC 使用场景
-heap 查看堆内存配置和使用 否 快速查看堆内存概况
-histo 查看对象统计（含垃圾对象） 否 查看对象分布概况
-histo:live 查看存活对象统计 是（Full GC） 排查内存泄漏，对比存活对象
-dump:format=b,file=xx 导出堆转储 否 OOM时导出快照
-dump:live,format=b,file=xx 只导出存活对象 是（Full GC） 减小dump文件大小
-finalizerinfo 查看等待finalize的对象 否 排查finalize队列问题
-F 强制执行（配合-dump/-histo） 否 jmap无响应时

5.3 对象统计（-histo）深度解读

jmap -histo输出按占用空间从大到小排列，重点关注以下几类异常：

异常模式 特征 可能原因 排查方法
某类实例数异常多 #instances远超预期 集合类未清理、对象未释放 对比两次-histo，找增长最快的类
某类占用空间异常大 #bytes远超预期 大对象、大数组 jmap -dump + MAT分析
byte[]/char[]排第一 [B或[C实例数巨大 String或JSON数据过多 查看引用这些数组的对象
自定义Entity类排前列 业务对象数量异常 业务缓存未清理 检查缓存策略和过期机制

十三、总结

JVM命令行工具是线上问题排查的利器，掌握它们是从”重启大法”进化到”精准定位”的关键：

  1. jps定位进程：排查第一步，确认目标Java进程PID
  2. jstat监控GC：实时观察GC频率、内存趋势，判断GC是否异常
  3. jstack分析线程：CPU飙高四步法、死锁自动检测、线程状态统计
  4. jmap分析内存：堆概况、对象统计、堆转储导出，配合MAT深度分析
  5. jinfo调整参数：动态修改JVM参数，无需重启进程
  6. 工具组合使用：一个线上问题往往需要多个工具配合排查，不要孤立使用

在实际项目的实战中，我深刻体会到：排查问题不是靠运气，而是靠系统化的方法论和熟练的工具操作。CPU飙高有四步法，内存泄漏有对比法，GC异常有决策树，线程死锁有自动检测。按照流程走，问题一定能定位到根因。

最后，记住一条原则：排查问题的第一步永远是收集信息，而不是猜测原因。
