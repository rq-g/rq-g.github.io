MySQL Online DDL——大表加字段的正确姿势

发布于 2023-10-08 分类：技术, 2023, MySQL深度 👁

前言

实际场景中，生产环境设备报警表已有5000万行数据，某次需求要给报警表加一个”处理优先级”字段。运维同事直接执行ALTER TABLE，导致整张表被锁2小时，期间所有报警写入全部超时，监控大屏数据中断，安监部门紧急通报。2023年学会Online DDL和pt-online-schema-change后，大表变更不再影响业务。本文结合实际项目的真实场景，系统讲解MySQL大表加字段的正确姿势。

DDL的执行方式

三种算法概览

三种算法对比：

INPLACE 短锁 快 大部分操作

INSTANT算法（MySQL 8.0.12+）

INSTANT算法原理

INSTANT实现原理：

关键点：

  • 只修改.frm/.sdi元数据文件
  • 不修改.ibd数据文件
  • 已有数据行不会物理更新
  • 查询时动态填充默认值

为什么 INSTANT 能做到不加锁？ 传统加列之所以慢，是因为 InnoDB 需要为每一行物理地写出新列的值。MySQL 8.0 引入的 INSTANT 算法改变了这一思路：它在表的元数据中记录”新增列”的信息（列定义、默认值、以及该列是在第几个 INSTANT 版本之后加入的标记位）。已有老行的数据页完全不动，当查询需要读取这些行时，InnoDB 通过隐藏的 row version 标记判断”该行不包含新列”，于是直接把表级默认值（如 0）动态补上返回给 Server 层。只有新写入的行才会真正携带这一列的物理数据。这种设计把”N 行重写”的时间复杂度降到了 O(1) 的元数据修改，因此无论表多大都是秒级完成。需要注意的是，INSTANT 加列次数并非无限，每张表有 INSTANT_COLS 上限（默认 64 次，由 innodb_max_instant_columns 限制余量），耗尽后仍需退回 INPLACE。

INPLACE算法

INPLACE算法执行流程

INPLACE执行流程（以添加索引为例）：

关键：Row Log记录执行期间的DML变更，保证数据一致。

INPLACE 为什么只需要”短暂锁表”？ INPLACE 的核心思路是”原地构建”——它不会像 COPY 那样新建一张全量表再重命名，而是在原表空间内直接构建新的索引 B+ 树。整个过程被切成三个阶段：准备阶段只持有极短的 MDL 写锁用于创建临时 frm / 分配增量日志结构；执行阶段才是重头戏，InnoDB 扫描聚簇索引、排序、构建二级索引，期间对原表的读写完全不阻塞；提交阶段再次短暂加锁，把执行阶段积累的最后一点增量（Row Log）追平，然后原子地替换数据字典。之所以敢在执行阶段放行业务 DML，正是因为 Row Log 把这段时间的写操作全部记录下来，留到后面回放，从而保证了”边改边读”的一致性。

COPY算法

COPY算法执行流程

COPY算法执行流程：

风险：

  • 全程锁表，DML全部阻塞
  • 拷贝过程耗时与数据量成正比
  • 需要额外磁盘空间（2倍表大小）
  • 拷贝过程中主从延迟增大

什么情况下逼不得已才用 COPY？ COPY 是唯一不依赖”原地”技巧的算法，代价也最大：它把原表数据逐行 INSERT ... SELECT 到新表，期间 MDL 写锁全程持有，意味着业务写入完全停摆。因此只有在无法用 INPLACE/INSTANT 实现的操作上才会退回 COPY，典型如：修改列的数据类型（如 INT→BIGINT、VARCHAR 扩长在某些版本仍走 COPY）、修改字符集、删除主键、把列改到非末尾位置（8.0.29 之前）。实际项目中，如果某次变更 Explain 出来是 COPY 又必须在大表上做，不要直接 ALTER，改用 pt-osc 或 gh-ost 这类”影子表 + 触发器/Binlog”方案，把锁表时间压缩到重命名的一瞬间。

三条实战经验：

  1. 优先 gh-ost 的场景：原表已有触发器、写入 QPS 很高、变更失败代价大（如核心报警表）。gh-ost 基于 Binlog 的方案对线上几乎零侵入，且 rename 前任何时刻都能安全终止——这对”不敢动生产库”的心态是巨大安慰。
  2. 仍可用 pt-osc 的场景：一次性历史表归档、测试环境、或团队更熟悉 Percona 工具链。它的触发器方案虽然笨重，但逻辑直观、出问题容易排查。
  3. 通用铁律：无论哪个工具，执行前先 --dry-run 校验；始终带 --max-load / --critical-load 上限；大表务必选业务低峰；执行期间盯住主从延迟与磁盘剩余（需 2 倍表空间）。二者都只改结构不改数据语义，但 gh-ost 在”可控、可回滚、低侵入”上更胜一筹，是实际项目大表变更的首选。

读懂这张速查表背后的判断逻辑

速查表是结论，背后的判断逻辑才可迁移。第一层看数据是否需要重排：加列/删列/改默认值只动元数据或只需惰性处理，所以能 INSTANT；改列类型、改字符集意味着每一行的二进制表示都要变，数据必须重写，只能 COPY——这一层判断不依赖版本，遇到没见过的 DDL 先问”每行的存储要不要变”。第二层看索引结构是否受影响：加索引要重建索引树但不动聚簇索引，所以能 INPLACE 并发 DML；而”指定位置加列”在 8.0.29 之前要重写整行（行内列有顺序），8.0.29 之后通过 instant column 机制解决了。第三层看风险兜底：INSTANT 失败会自动降级 INPLACE 再降级 COPY（ALGORITHM=INPLACE 显式指定则失败即终止，不静默降级）——生产变更建议显式指定算法，宁可失败也不要在深夜静默跑一个 COPY。

另一个从表里读不出来的实战规律：pt-osc/gh-ost 的价值不只在于”不锁表”，更在于可控和可回退。触发器/(binlog) 拷贝速率可调、可以暂停、可以随时终止并删掉影子表全身而退；原生 INSTANT 虽然秒级，但一旦跑了一个 COPY 级别的大 DDL，中途只能等或杀进程（回滚可能比执行更久）。所以大表变更的选型本质是”秒级完成风险自负”与”分钟级完成全程可控”之间的取舍，两个方案都有存在价值。

Online DDL的Row Log机制

INPLACE算法的Row Log机制：

Row Log大小限制：

  • innodb_sort_buffer_size：排序缓冲区大小（默认1MB）
  • innodb_online_alter_log_max_size：在线变更日志最大大小
  • 默认128MB，超过后DDL失败

Row Log 到底是什么、为什么不会丢数据？ 这是 Online DDL 最精妙的部分。INPLACE 在执行阶段允许业务继续写表，那么这些”边改边写”的增量如何并入正在构建的新结构（如新索引）？答案就是 Row Log——它不是 Binlog，而是 InnoDB 在执行 DDL 时临时在内存（row_log_buffer）和磁盘临时文件（#sql-*.ibd 旁的 rowlog）中维护的一份增量日志。每当有 DML 命中正在变更的原表，InnoDB 除了正常写原表，还会把这次变更（按”旧值 / 新值”形式）追加进 Row Log。

构建新结构的过程分两遍：第一遍扫描原表已有的全量数据，排序后写入新索引；第二遍把 Row Log 里累积的增量按顺序回放（replay）到新索引上。如果增量太多、内存放不下，就刷到磁盘临时文件，最后再一次性追平。这样不论 DDL 跑多久，期间发生的写操作都不会丢失。

两个必踩的坑：

  1. Row Log 撑爆 → DDL 直接失败。 innodb_online_alter_log_max_size 默认只有 128MB。如果变更期间写入量极大（比如大表上做热点更新），Row Log 超过这个上限，DDL 会报 DB_ONLINE_LOG_TOO_BIG 并回滚——但此时业务写入一直是正常的，只是变更没成功。生产环境对写入量大的表做 DDL，建议先把该参数调大到 1GB~4GB 再执行。

  2. Row Log 回放拖慢收尾。 第二遍回放阶段仍需短暂持有 MDL 写锁，写入越久、增量越大，收尾锁表时间越长。这也是为什么大表 DDL 最好选业务低峰、并配合 pt-osc/gh-ost 把压力摊平的原因。

大表变更的容量规划

一次真实的 Online DDL 事故复盘

把理论落到事故现场，理解会更深。某次凌晨给 8000 万行的设备遥测表加字段，DBA 用的是 ALGORITHM=INPLACE, LOCK=NONE，预演时一切正常，生产执行 40 分钟后突然所有写入报 Lock wait timeout。事后复盘根因有三层。第一层，长事务挡住了 DDL 的收尾锁：DDL 的 metadata 两阶段锁定允许中途并发 DML，但 commit 阶段需要拿到 MDL 排他锁，而一个跑了两小时的报表事务一直持有该表 MDL 共享锁，DDL 排在它后面，它后面又排了上千个新请求——整条 MDL 队列被一个事务焊死。第二层，监控缺位：我们有 DDL 超时告警，却没有”MDL 队列长度”监控，performance_schema.metadata_locks 表里能提前 20 分钟看到堵塞趋势却没人看。第三层，预案只有 A 没有 B：预案写了”用 pt-osc 重试”，但没写”在线 DDL 卡住时应该先 KILL DDL 还是先 KILL 长事务”——两个选项当时现场争论了十分钟，KILL 错了顺序导致 DDL 白跑 40 分钟重来。这次事故之后我们固化了三条纪律：DDL 前先查长事务（information_schema.innodb_trx 超过 1 分钟的一律先处理）、执行中每 5 分钟检查一次 MDL 等待队列、预案必须写清楚”出现 X 现象执行 Y 动作”的对应关系。工具的进步（INSTANT 算法、gh-ost）降低了 DDL 的技术门槛，但变更风险管理的门槛一分都没降。
