MyBatis批量操作深度优化——从逐条到批量

发布于 2023-10-22 分类：技术, 2023, MyBatis源码 👁

前言

实际项目有个传感器数据导入功能，运维人员每月需要将采集设备导出的Excel数据（约2万条）导入系统。最初用逐条insert实现，2万条数据耗时5分钟，期间数据库连接池被打满，其他接口全部超时。后来逐步优化：拼接VALUES 8秒、BatchExecutor 6秒、BatchExecutor+rewriteBatchedStatements 3秒。最终实现了500条/批+分批提交+失败重试的完整方案，导入2万条数据稳定在3秒以内。

这次优化让我深入理解了MyBatis批量操作的底层原理：逐条操作的网络往返和事务开销是性能杀手，拼接VALUES减少了网络往返，BatchExecutor利用JDBC的addBatch/executeBatch只编译一次SQL，rewriteBatchedStatements让MySQL驱动自动将多条INSERT重写为多值INSERT，性能最优。

追根溯源：为什么”逐条”这么慢

要理解批量为什么快，得先看清一次 insert 背后到底发生了什么。一条 SQL 从应用发到 MySQL 并落库，至少要经过四层开销：

  1. 网络往返（RTT）：应用与数据库通常不在同一进程，每次 executeUpdate() 都是一次”请求—响应”。即使内网，单次 RTT 也有 0.2~0.5ms。2 万条逐条插入 = 2 万次 RTT，仅网络就吃掉近 10 秒。
  2. SQL 解析与执行计划编译：MySQL 接到 SQL 后要先做词法/语法解析、权限校验、生成执行计划。相同 SQL 反复解析是纯浪费——这正是 prepareStatement + 参数绑定的价值所在。
  3. 事务提交开销：每条独立 insert 若各自提交，要刷 redo log、binlog，fsync 落盘本身是毫秒级磁盘 IO。2 万次提交就是 2 万次 fsync。
  4. 连接获取与释放：每条都从连接池借还连接，连接池竞争会把其他业务请求也拖垮（我们当时就是连接池被打满导致接口全超时）。

核心认知：批量优化的本质，就是用”更少的网络往返 + 更少的 SQL 编译 + 更少的事务提交”去换同样的写入量。下面三套方案，本质上是在这三个维度上逐步做减法。

对比逐条：8s vs 300s，提升37.5倍。大头是”实际执行”——即使批量，MySQL写入磁盘的开销省不掉，批量省的是往返、编译和事务这层”手续”。

三个注意事项：

  1. max_allowed_packet 限制（默认4MB）：单条SQL超限直接报 SQLSyntaxErrorException，提前调大：
  1. 分批大小建议500~1000条：SQL文本过长反而降低解析效率，还会放大第1条的风险。
  2. 拼接VALUES与Batch Executor的取舍：拼接VALUES一条SQL解决、速度快，但SQL长度不可控；Batch Executor稳妥、可控，但依赖JDBC批次机制（建议同时开 rewriteBatchedStatements=true，否则MySQL驱动仍是逐条发送）。

优化方案2：Batch Executor

BatchExecutor源码分析

BatchExecutor执行原理图

BatchExecutor 执行原理（同一 SQL 复用同一个 PreparedStatement，参数只 addBatch 不立即发送）：

优点：只编译一次 SQL，多次设置参数，一次网络发送。
缺点：不支持 SELECT；insert 的返回值是 BATCH_UPDATE_RETURN_VALUE，而非受影响行数。

优化方案3：rewriteBatchedStatements

rewriteBatchedStatements原理

开启 rewriteBatchedStatements=true 后，MySQL JDBC 驱动（com.mysql.cj.jdbc.ClientPreparedStatement）会在 executeBatch() 时做一层”重写”：

  • addBatch() 不再立即发送给数据库，而是缓存在 JDBC 驱动内存中；
  • 累积到一定数量、或调用 executeBatch() 时，驱动检查这批 SQL 是否是多值 INSERT；
  • 若是，则把多条 INSERT ... VALUES(?,?,?) 重写合并成一条 INSERT ... VALUES(?,?,?),(?,?,?),(?,?,?) 再发送；
  • 这样数据库只接收一条 SQL、只编译一次执行计划，网络往返也从 40 次降到 1 次。

注意：rewriteBatchedStatements 只对 INSERT 生效，对 UPDATE/DELETE 不生效（UPDATE/DELETE 仍逐条发送，无法重写）。并且必须配合 useServerPrepStmts=false——因为服务端预编译（server-side prepared statement）不支持重写，只能用客户端预编译。

性能提升来源小结：

  1. 网络往返：40 次 → 1 次；
  2. SQL编译：40 次 → 1 次；
  3. 事务提交：1 次。

实战踩坑：批量导入的三类线上事故

理论清楚了，但真正上线批量导入时，踩过的坑比方案本身还多。这里记录三类最典型的事故，都是血泪教训。

坑一：max_allowed_packet 超限导致整批失败

拼接 VALUES 方案下，一条 SQL 把所有行塞进去，SQL 包体积随行数线性增长。一旦超过 MySQL 的 max_allowed_packet（默认仅 4MB），会直接抛 PacketTooBigException，整批插入全部失败。

我们的经验：单批控制在 500~1000 条，基本不会撞包上限；如果单行字段特别宽（比如带长文本），要进一步调小批次。

坑二：并发批量写入引发的死锁

多个线程同时对不同分表做批量 insert，如果各线程插入的主键顺序不一致，InnoDB 加行锁的顺序就会交错，极易触发 Deadlock found。前文实战里我们按 (device_id, collect_time) 排序后再分批，就是为了让所有线程按同一顺序加锁，从根上规避死锁。

坑三：大事务造成主从延迟与锁等待

一次性 insert 2 万条再 commit，这个事务会长时间持有自增锁和插入意向锁，undo log 也会暴涨；从库回放这条超大 binlog 时会严重滞后，造成主从延迟，读从库的业务短暂读到旧数据。

解决思路就是前文强调的分批小事务：每 500 条一个独立事务，锁持有时间短、binlog 分散、某批失败只影响当前批。这也是”分批事务 vs 大事务”那张图想表达的核心。

面试高频问题

1. MyBatis批量插入怎么优化？

三个层次：拼接VALUES（简单，减少网络往返）、BatchExecutor（通用，JDBC addBatch/executeBatch）、rewriteBatchedStatements（MySQL最优，驱动层自动重写为多值INSERT）。建议500条/批，分批提交，失败逐条重试。

2. BatchExecutor的原理？

使用JDBC的addBatch+executeBatch。SQL只编译一次创建PreparedStatement，每次调用addBatch()将参数添加到批处理队列，调用executeBatch()一次性将所有参数发送到数据库执行。同一条SQL复用同一个Statement对象。

3. rewriteBatchedStatements是什么？

MySQL JDBC驱动的URL参数，开启后驱动在executeBatch()时自动将多条INSERT重写为多值INSERT（INSERT INTO t VALUES(…),(…),(…)），配合BatchExecutor性能最优。注意需要useServerPrepStmts=false才能生效。

总结

批量操作是数据库性能优化的基本功。实际项目的传感器数据导入从5分钟优化到3秒，核心认知是：逐条操作的事务开销和网络往返是性能杀手，拼接VALUES简单有效减少网络往返，BatchExecutor利用JDBC批处理只编译一次SQL，rewriteBatchedStatements让MySQL驱动自动重写为多值INSERT。500条/批+分批提交+失败重试+导入结果记录，这是批量操作的黄金法则。理解了BatchExecutor的源码——addBatch缓存参数、executeBatch一次性发送——就能避免返回值不正确、自增ID不回填等常见陷阱。
