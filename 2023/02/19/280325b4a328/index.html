MyBatis缓存机制——一级缓存与二级缓存深度剖析

发布于 2023-02-19 分类：技术, 2023, MyBatis源码 👁

前言

实际项目上线后遇到一个诡异问题：设备状态查询接口，第一次调用返回”在线”，第二次调用却返回”离线”。排查了两个小时，最终发现是MyBatis一级缓存在作怪——同一个SqlSession中，第一次查询缓存了设备状态，中间另一条线程修改了数据库状态，第二次查询命中了缓存返回旧数据。这次事故让我深入研究了MyBatis的缓存机制，理清了一级缓存和二级缓存的边界和陷阱。

实际项目有大量实时性要求高的场景：传感器数据秒级刷新、设备状态实时变更、告警信息即时推送。这些场景对数据一致性要求极高，而MyBatis的缓存机制在提升查询性能的同时，也带来了数据不一致的隐患。深入理解缓存源码后，我制定了实际项目的缓存策略：关闭二级缓存，一级缓存scope设为statement，用Redis实现业务级缓存。

生产实战：缓存引发的数据不一致与规避

把源码讲透后，最该记住的是”缓存什么时候会害你”。下面两个场景都来自实际项目。

事故1：一级缓存导致设备状态”假在线”。 前文提到：同一个 SqlSession 内先查 status=ONLINE，中间另一线程把库里改成 OFFLINE，第二次查命中一级缓存仍返回 ONLINE。在智慧矿山场景里，这意味着瓦斯超限报警被旧状态掩盖、人员定位显示错误位置，安全风险极高。根因是 BaseExecutor.query() 命中 localCache 直接返回旧对象引用（selectById 两次返回的是同一个对象，device1 == device2 为 true）。规避手段优先级：① 设 local-cache-scope: statement（每次查完即清，等于关掉一级缓存副作用）；② 必须同一事务复用时，在写操作后显式 sqlSession.clearCache()；③ 实时性要求高的查询，直接走 SqlSessionTemplate 每次新建会话（Spring 默认行为）。

事故2：二级缓存跨表脏读。 设备表缓存了”设备+区域名”的联合结果，区域表改名后只清了区域 namespace 的缓存，设备 namespace 里旧的 areaName 仍在，前端长期显示旧区域名。根因是二级缓存按 namespace 隔离，关联表的变更无法联动失效。规避手段：核心业务表直接关闭二级缓存，用 Redis 手动管理并主动失效（见下文策略表）。

一次查询的完整缓存命中链路：

flowchart TD
    Q[业务查询] --> L1{一级缓存 localCache 命中?}
    L1 -- 命中 --> R1[返回缓存对象]
    L1 -- 未命中 --> L2{二级缓存 命中?}
    L2 -- 命中 --> R2[返回二级缓存 提交后可见]
    L2 -- 未命中 --> DB[(查询数据库)]
    DB --> W1[写入一级缓存]
    DB --> W2[写入二级缓存待提交区]
    W2 --> C[SqlSession commit 后正式可见]

三条落地经验：

  1. 实时数据（设备状态、传感器、告警）绝不依赖 MyBatis 缓存，查库或查 Redis（短 TTL）；
  2. 只读配置/字典表可谨慎开二级缓存（readOnly=true + 定时 flushInterval），但仍不如 Redis 可控；
  3. 不论用哪层缓存，失效策略比缓存本身更重要——写入成功的同时必须主动清除对应缓存键，否则脏数据会持续被命中。

面试高频问题

1. 一级缓存和二级缓存的区别？

一级缓存SqlSession级别，默认开启不可关闭；二级缓存namespace级别，默认关闭需手动开启。一级缓存在BaseExecutor中用HashMap实现，查询后立即写入；二级缓存在CachingExecutor中用TransactionalCache装饰器管理，SqlSession提交后才真正写入。Spring整合后，每次查询新建SqlSession，一级缓存基本不命中。

2. 为什么生产环境不建议使用二级缓存？

三个硬伤：1.多表关联查询时namespace隔离导致缓存不一致；2.分布式环境下各节点缓存独立无法同步；3.序列化问题增加复杂度。用Redis替代更可靠，可控性更强。

3. Spring整合MyBatis后一级缓存还有效吗？

有效，但Spring通过SqlSessionTemplate管理SqlSession，默认每次查询使用新的SqlSession，一级缓存基本不会命中。如果需要在同一事务中复用SqlSession（@Transactional），一级缓存才会生效。设置localCacheScope=STATEMENT可以完全消除一级缓存的影响。

4. CacheKey是如何生成的？

由五部分组成：MappedStatement ID + RowBounds(offset,limit) + SQL语句 + 参数值 + Environment ID。任一部分不同则CacheKey不同。参数值的获取和DefaultParameterHandler相同，通过MetaObject反射取值。

缓存与事务的交互

事务提交对缓存的影响

事务提交对一级/二级缓存的影响：

  • 操作 一级缓存 二级缓存
  • SELECT 写入 写入待提交区
  • INSERT/UPDATE 清空 清空(同namespace)
  • DELETE 清空 清空(同namespace)
  • commit() 清空 待提交区→正式写入
  • rollback() 清空 待提交区→丢弃
  • close() 释放 不影响
  • 关键时序：
    1. 查询A → 一级缓存有 → 二级缓存待提交区有
    1. 另一个SqlSession查询A → 二级缓存没有（还未commit）
    1. 第一个SqlSession.commit() → 待提交区数据写入二级缓存
    1. 另一个SqlSession查询A → 二级缓存命中
  • 这就是为什么二级缓存需要TransactionalCache：
  • 防止未提交事务的脏数据被其他SqlSession读到

总结

MyBatis缓存机制看似简单，实则暗藏玄机。实际项目对数据实时性要求极高，任何缓存导致的数据延迟都可能造成安全风险。核心认知是：一级缓存是SqlSession级别的默认行为，Spring整合后基本无感；二级缓存是namespace级别的全局缓存，TransactionalCache管理事务性写入，生产环境慎用。真正可靠的缓存方案是Redis + 主动失效，而不是依赖MyBatis内置缓存。设置localCacheScope=STATEMENT关闭一级缓存影响，用Redis按数据特性制定不同的缓存策略，这是实际项目的最终选择。
