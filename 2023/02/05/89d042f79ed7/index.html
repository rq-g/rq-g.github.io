Spring事务底层实现——从@Transactional到数据库提交

发布于 2023-02-05 分类：技术, 2023, Spring源码 👁

前言

用了两年@Transactional，只知道加在方法上就能回滚，直到线上出现数据不一致——明明加了事务注解，部分数据却没回滚。排查后发现是事务失效导致的。这次事故让我下定决心搞透Spring事务的底层实现。

在实际场景中，在安全预警模块中，瓦斯浓度超标时需要同时写入预警记录和联动排风指令。一次事务失效导致预警记录写入但排风指令未执行，造成严重安全隐患。这次事故让我深入研究了Spring事务的完整底层链路。

实际项目技术栈：SpringBoot 2.7 + MyBatis-Plus + MySQL + Redis + MQTT。事务管理是安全生产的核心保障，理解事务底层实现至关重要。

事务失效的所有场景

1. 同类方法调用（最常见）

2. 非public方法

3. 异常类型不匹配

4. 异常被catch吞掉

5. 数据库引擎不支持

6. 多线程事务失效

事务失效场景总结表

序号 失效场景 失效原因 解决方案
1 同类方法调用 this是目标对象非代理 注入自身代理
2 非public方法 代理只拦截public方法 改为public
3 异常类型不匹配 默认只回滚RuntimeException rollbackFor=Exception.class
4 异常被catch吞掉 异常未传播到代理层 重新抛出/手动回滚
5 数据库引擎不支持 MyISAM不支持事务 使用InnoDB
6 传播行为设置错误 NOT_SUPPORTED/NEVER 选择正确的传播行为
7 未被Spring管理 不经过BeanPostProcessor 加@Component
8 多线程调用 ThreadLocal隔离 主线程控制事务

把8种失效场景收敛成一条根因

这8种场景死记硬背容易漏，其实可以收敛为一句话：@Transactional 生效的唯一前提是”调用穿过代理对象”。场景1（this调用）、场景7（不经容器）、场景2（代理不拦截非public）都是”没穿代理”；场景3、4、6是”穿过了代理，但代理判定不回滚”；场景5、8则更底层——事务边界根本不成立（引擎不支持、线程切换后 ThreadLocal 里没有同一个 Connection）。排查事务失效时的决策树因此非常简单：先确认 Bean 是代理对象（打日志看 AopUtils.isAopProxy(this)），再确认调用方是不是拿着代理引用调用，最后确认回滚判定条件与异常路径。团队里新人背不下8种场景没关系，把”事务是代理行为，不是方法行为”这一句话讲透，失效场景都能现场推出来。

面试高频问题

1. Spring事务的本质？

connection.setAutoCommit(false) + ThreadLocal绑定Connection到当前线程。展开说：Spring 的事务能力是三件事的组合——PlatformTransactionManager 抽象出”开事务、提交、回滚”的操作接口，TransactionInterceptor 通过 AOP 在方法边界插入这些操作，DataSourceTransactionManager 用 ThreadLocal 把连接和当前线程绑定，让同一个事务内多次拿到的是同一个 Connection。理解了”事务状态存在 ThreadLocal 里”，多线程事务失效、REQUIRES_NEW 的挂起恢复（suspend 时保存旧连接、resume 时放回）这些行为都能自然推出来。

2. REQUIRED和REQUIRES_NEW的区别？

REQUIRED加入当前事务，一荣俱荣一损俱损；REQUIRES_NEW新建独立事务，互不影响。源码层面的区别在 handleExistingTransaction：REQUIRED 直接参与（校验隔离级别/只读声明是否兼容）；REQUIRES_NEW 先 suspend() 挂起当前事务（保存连接和状态），开全新连接执行，返回时 resume() 恢复。由此推出两个实用结论：其一，REQUIRES_NEW 的内层事务提交不受外层回滚影响，代价是占用了两个数据库连接，高并发下连接池要按最坏情况预留；其二，外层事务未提交的修改对内层不可见（不同连接、不同事务视图），内层若依赖外层刚写的数据就会查不到——这是”REQUIRES_NEW 方法里查不到外层刚 insert 的记录”的根因。

3. @Transactional(readOnly=true)的作用？

  1. 数据库层面：InnoDB不做change buffer，查询性能提升
  2. Spring层面：标记只读，部分事务管理器可以做优化
  3. 读写分离：readOnly=true走从库

补充一个踩坑点：readOnly 只是”建议”而非强制——MySQL 的 InnoDB 对只读事务的约束是”执行写语句时报错”，但 Hibernate/JPA 层面可能有 flush 策略优化，跨实现的行为不完全一致。所以 readOnly=true 应当被视为性能与语义的双重声明，不能当作防止误写的安全机制——防误写要靠数据库账号权限。

总结

Spring事务的本质是AOP + Connection.setAutoCommit(false) + ThreadLocal。2023年深入源码后，我彻底理解了事务传播行为的实现机制，也掌握了事务失效的所有场景。

在实际场景中，线上遇到数据不一致问题，不再盲目排查，而是从代理是否生效、异常是否被吞、传播行为是否正确三个维度系统分析。安全生产场景下事务的正确性至关重要，理解底层实现是保障系统可靠性的基础。

原理深挖：@Transactional 为什么必须依赖代理

@Transactional 能生效，根本前提是方法调用经过 Spring 生成的代理对象，而不是 this 直接调用。原因在于事务逻辑写在 TransactionInterceptor 里，只有代理在调用目标方法前后织入该拦截器，才能实现”开启事务→执行→提交/回滚”。

当在 DeviceService 内部用 this.updateDeviceStatus() 自调用时，绕过了代理，拦截器没机会执行，事务自然失效——这正是前文”同类方法调用”会失效的根因。解决方案有两种：

事务传播行为真实行为矩阵

下表总结了在”调用方是否已有事务”的不同前提下，各传播行为的真实行为，这是面试和排查的双重重点：

传播行为 调用方无事务 调用方有事务 内部异常是否影响外部 外部异常是否影响内部
REQUIRED 新建事务 加入外部事务 是（同一事务） 是（同一事务）
REQUIRES_NEW 新建事务 挂起外部，新建事务 否（已提交） 否（已提交）
NESTED 新建事务 在外部事务内建 Savepoint 仅回滚到 Savepoint 是（外部回滚带它）
SUPPORTS 非事务执行 加入外部事务 视外部而定 视外部而定
NOT_SUPPORTED 非事务执行 挂起外部，非事务 否 否
MANDATORY 抛异常 加入外部事务 是 是
NEVER 非事务执行 抛异常 — —

关键区别 NESTED vs REQUIRES_NEW：NESTED 是”外部事务的子事务”，外部回滚它会跟着回滚，它内部回滚只回到 Savepoint 不影响外部；REQUIRES_NEW 是”完全独立的新事务”，内外互不影响。所以需要”部分失败不影响整体”用 REQUIRES_NEW，需要”整体失败连坐、局部失败可恢复”用 NESTED。

事务与并发：隔离级别注解背后的真实行为

@Transactional(isolation = Isolation.READ_COMMITTED) 是很多人踩过的”看起来配了但不生效”重灾区。源码层面看，DataSourceTransactionManager.doBegin() 会把注解上的隔离级别透传给 Connection.setTransactionIsolation()——前提是底层连接池允许且配置一致。Druid 的 defaultTransactionIsolation 与 HikariCP 的 transactionIsolation 若与注解不一致，行为取决于驱动与连接池版本的组合：有的直接生效、有的在事务结束后才恢复默认值、有的干脆忽略。更隐蔽的是 MySQL 默认 RR 隔离级别下，事务内第一条查询建立的 ReadView 决定了整个事务的可见性快照，”注解配 RC + 数据库默认 RR”的组合会让不同事务方法在同一连接上表现出难以预测的读行为。我们的实践准则是：隔离级别统一在数据源/连接池层配置，注解只用于极少数确实需要不同级别的读场景，并把连接池隔离级别纳入代码评审检查项——这类问题压测环境几乎不暴露，往往到生产高峰期才以”读到半小时前的数据”这种诡异形式出现。

实战：生产环境事务设计准则

结合智慧矿山安全生产场景，我们沉淀了以下事务设计准则：

  1. 只读查询必须 readOnly=true：数据库层 InnoDB 会跳过 change buffer、减少一致性视图开销；读写分离场景下路由到从库；Spring 对只读事务也会做优化（如关闭脏数据检查）。
  2. 告警通知用 REQUIRES_NEW：预警创建成功后，即使后续业务异常回滚，告警通知、操作日志这类”旁路动作”也不能被带走，必须独立提交。
  3. 批量导入用编程式事务：每批一个独立 TransactionTemplate，某批失败只回滚该批，避免一条脏数据导致全量回滚（见前文代码）。
  4. 长事务是大忌：事务越长，持有的数据库连接和行锁越久，越容易引发死锁和连接池耗尽。原则：事务里只做数据库操作，RPC/HTTP/文件 IO 全部挪到事务外。
