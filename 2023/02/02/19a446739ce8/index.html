Spring事件机制——ApplicationEvent的发布与监听

发布于 2023-02-02 分类：技术, 2023, Spring源码 👁

前言

做订单系统时，下单后要发短信、加积分、发推送，最初全写在一个方法里，代码越来越臃肿。后来学会Spring事件机制，下单只发事件，各模块各自监听，代码瞬间清爽。2023年深入源码后，对事件机制有了更深的理解。

在实际场景中，在安全预警模块中，当瓦斯浓度超标时需要同时触发：创建预警记录、推送通知安全主管、联动排风设备、记录操作日志。如果把这些逻辑全写在预警方法中，代码会非常臃肿且难以维护。通过Spring事件机制，预警方法只发布事件，各模块独立监听，实现了业务解耦。

实际项目技术栈：SpringBoot 2.7 + SpringCloud + Nacos + MyBatis-Plus + Redis + MQTT。事件机制被广泛应用于安全预警、设备状态变更、人员位置更新等场景。

面试高频问题

1. Spring事件机制的原理？

基于观察者模式，通过ApplicationEventPublisher发布事件，ApplicationEventMulticaster广播给所有匹配的ApplicationListener。@EventListener是注解驱动的便捷方式。

2. @EventListener和@TransactionalEventListener的区别？

@TransactionalEventListener绑定事务阶段，只在事务特定阶段（如AFTER_COMMIT）执行；@EventListener立即执行。事务回滚时@TransactionalEventListener不会触发。

3. 事件监听是同步还是异步？

默认同步。加@Async注解可异步执行，需要配置线程池。异步事件需要注意异常处理和丢失问题。

核心认知：事件驱动的解耦价值

Spring事件机制是业务解耦的利器。核心认知是：事件驱动让核心逻辑与副作用解耦，@TransactionalEventListener保证数据一致性，@Async保证性能。

在实际场景中，预警系统从”一个方法500行”到”核心逻辑+5个监听器”，代码可维护性有了质的飞跃。瓦斯超标时，预警创建、短信通知、排风联动、操作日志各自独立监听，互不影响，真正实现了业务解耦。

实际项目通过Spring事件机制，将传感器数据处理、告警通知、设备联动等解耦为独立的事件监听器。关键原则：核心业务用同步事件确保一致性，通知类操作用异步事件提升性能，事务相关操作用@TransactionalEventListener保证数据完整性。

事件机制常见陷阱与避坑指南

陷阱1：监听器中抛出异常影响其他监听器

陷阱2：@TransactionalEventListener未触发

陷阱3：循环事件导致栈溢出

陷阱汇总表

序号 陷阱 现象 解决方案 智慧矿山场景
1 监听器异常传播 后续监听器不执行 try-catch或@Async 短信发送失败不影响数据持久化
2 @TransactionalEventListener未触发 监听器不执行 fallbackExecution=true 非事务方法发布事件
3 循环事件 StackOverflowError @Async或重新设计 告警事件循环触发
4 事件对象可变 监听器间数据污染 事件字段用final 多监听器修改同一告警对象
5 异步事件丢失 应用关闭时事件未处理 优雅停机+队列缓冲 停机时告警事件丢失
6 事件监听器顺序错误 数据未持久化就发通知 @Order控制顺序 先持久化再发短信
7 泛型事件擦除 监听器收不到子类事件 指定具体事件类型 MineBaseEvent监听不到子事件

原理深挖：事件广播为什么默认同步

SimpleApplicationEventMulticaster 在广播事件时，如果 taskExecutor == null 就串行同步调用每个监听器。这意味着：发布者线程会一直阻塞，直到所有监听器执行完毕。

同步的好处是强一致：发布者能感知监听器是否成功，异常可向上传播（结合 @TransactionalEventListener(AFTER_COMMIT) 还能和事务绑定）。代价是：任何一个监听器慢，都会拖慢发布者；任何一个监听器抛异常（且未捕获），后续监听器被短路。因此耗时操作（短信、推送、文件导出）务必异步，核心数据操作（写库）保持同步以保证一致。

@Async 事件的坑：异常吞掉与上下文丢失

异步监听器运行在线程池线程上，有两个典型坑：

  1. 异常被静默吞掉：异步任务抛出的异常不会回到发布者线程，若没有全局异常处理器，错误会被”吃掉”。解决：配置 AsyncUncaughtExceptionHandler。
  2. ThreadLocal 上下文丢失：发布者线程里的 SecurityContext、MDC 日志链路（TraceId）不会自动传递到异步线程。解决：自定义 TaskDecorator 透传。

实战：事件 vs 消息队列（MQ）如何抉择

Spring 事件和 MQ（如 RabbitMQ、RocketMQ、项目中的 MQTT）都能解耦，但适用边界不同：

维度 Spring 事件 消息队列 MQ
作用范围 单 JVM 内 跨服务/跨进程
持久化 无（发布即丢） 有（可落盘、可重放）
可靠性 低（进程重启即丢失） 高（ACK、重试、死信）
事务绑定 支持 @TransactionalEventListener 需事务消息
适用场景 同服务内模块解耦 微服务间异步通信

经验法则：同一个微服务内部、需要和数据一致性强绑定的副作用（写预警记录、记日志）用 Spring 事件；跨服务、需要削峰填谷或可靠投递的通知（短信、大屏推送）用 MQ。本项目正是”事件做内部解耦 + MQTT 做设备下行”的组合。

一个混合反例：从”事件里做重活”到”事件里投递任务”

这张对比表还有一个经常被忽略的推论：Spring 事件不可靠，所以监听器里绝不能做”不能丢”的事。我们曾把”推送 MQTT 下行指令”直接写在事件监听器里，一次发布窗口期应用重启，三条设备断电指令丢了——事件已经”发布成功”，监听器却没来得及执行，且无任何痕迹。修复方案是把监听器瘦身为”任务投递者”：事件到达后只做参数校验并写入本地任务表（与业务同事务），由后台调度器消费任务表去执行真正的 MQTT 推送。这样一来事件机制仍然承担”模块解耦”的职责，可靠性则交给了与数据绑定的任务表——相当于在单 JVM 内部用了一个轻量版”本地消息表”。判断一个监听器该不该瘦身，就看一个问题的答案：**这条副作用丢了，业务要不要紧？**要紧就落库投递，不要紧才允许直接写在监听器里。

泛型事件与事件继承的实战价值

前文已给出 TypedEvent<T> 和 MineBaseEvent 的写法。它们的真正价值在于监听基类即可收到所有子类事件，非常适合”按大类统一处理”的场景：

注意泛型的类型擦除陷阱：@EventListener 监听 TypedEvent<T> 在运行时擦除为 TypedEvent，监听器仍能收到具体子类事件；但若监听器声明为监听某个具体子类，而事件确实是其子类实例，才会匹配。排查”监听器收不到事件”时，优先用 ResolvableType 核对事件类型与监听器参数类型是否一致。

监听器的执行顺序与异常隔离：容易被忽略的两个行为

Spring 事件机制有两个默认行为，不理解它们迟早踩坑。第一，监听器默认执行顺序是未定义的：同一个事件的多个 @EventListener 方法，Spring 不保证调用顺序，想让告警监听器先于日志监听器执行，必须显式加 @Order（数值越小越先执行）。我们曾依赖”先校验后入库”的隐式顺序，升级 Spring 版本后顺序颠倒导致脏数据入库——这类 bug 极难定位，因为单元测试里顺序往往”恰好正确”。第二，同步监听器的异常会直接抛回发布方：某个监听器抛 NPE，整个发布调用链中断，前面的业务代码已经执行、后面的监听器全部跳过。如果监听器之间没有”一损俱损”的关系，要么在每个监听器内部 try-catch 兜底，要么把非关键监听器改为 @Async（异步执行天然隔离异常，但要注意异步线程无法读取事务绑定的资源）。理解了这两点再看 @TransactionalEventListener 的设计，就能体会它是把”何时执行”从隐式约定变成了显式声明。

实战：事件驱动下的事务一致性落地

以”瓦斯超限 → 创建预警 + 联动排风”为例，如果两者在同一事务内用同步 @TransactionalEventListener(AFTER_COMMIT) 监听，就能保证：要么预警记录和排风指令的数据库写入都随主事务提交，要么都回滚，不会出现”预警写了但排风没联动”的中间态。

sequenceDiagram
    participant S as SensorDataService
    participant DB as 数据库
    participant L1 as 预警记录监听器
    participant L2 as 排风联动监听器
    S->>DB: begin transaction
    S->>DB: insert 传感器数据
    S->>S: publishEvent(GasOverLimitEvent)
    S->>DB: commit
    DB-->>L1: AFTER_COMMIT 触发
    L1->>DB: insert 预警记录
    DB-->>L2: AFTER_COMMIT 触发
    L2->>DB: insert 排风指令

注意：若在 AFTER_COMMIT 监听里再次抛出异常，主事务已经提交，无法回滚——因此监听器内部务必 try-catch，失败走补偿或告警，而不能依赖事务回滚来兜底。
