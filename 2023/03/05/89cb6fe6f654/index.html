Redis五种数据结构深度解析——选对数据结构事半功倍

发布于 2023-03-05 分类：技术, 2023, Redis 👁

前言

实际项目初期，所有数据都用String+JSON存Redis，导致大量问题：更新设备某个字段需要读取-修改-写回、计数器并发不准、排行榜用MySQL排序太慢、去重逻辑自己实现一遍又一遍。2023年深入理解五种数据结构后，用Hash存设备状态、ZSet做排行榜、Set做标签去重、List做消息队列，代码量减少80%的同时性能提升数倍。本文系统地总结Redis五种数据结构在实际项目中的选型、原理和实战经验。

String——最基础也最强大

底层实现

Redis 的 String 底层并不是 C 语言原生的 char* 字符串，而是自己实现的 SDS（Simple Dynamic String）。sdshdr 头部保存了已用长度 len、剩余空间 free，后面跟着真正的数据 buf[]。

flowchart LR
    A["redisObject.type=String"] --> B["ptr 指向 SDS"]
    B --> C["sdshdr: len=已用长度"]
    B --> D["sdshdr: free=剩余空间"]
    B --> E["buf[]: 实际字节数组"]
    C --> F["O(1) 获取长度"]
    D --> G["预分配避免频繁扩容"]

为什么不用 C 原生字符串？ C 字符串有三大痛点，SDS 逐一解决：

  1. O(1) 取长度：C 字符串要靠 \0 遍历，O(N)；SDS 直接读 len 字段，O(1)。这是 STRLEN 命令飞快的原因。
  2. 二进制安全：C 字符串遇 \0 即认为结束，无法存图片或序列化后的二进制；SDS 以 len 判定结尾，\0 只是兼容 C 函数的”尾巴”，中间出现 \0 也不影响。
  3. 杜绝缓冲区溢出 + 减少重分配：C 字符串拼接若忘记扩容会写穿内存；SDS 拼接前先检查 free，不够才扩容，并采用空间预分配（翻倍或 +1MB）和惰性释放（删了不立即回收，留作 free 复用），把频繁 realloc 降到最低。

典型应用场景

Hash——对象存储的最佳选择

底层实现

Hash 底层有两种编码，Redis 会根据元素数量和大小自动转换（小数据省内存，大数据保性能）：

flowchart TD
    A["Hash 写入"] --> B{元素数 <= hash-max-ziplist-entries 且 所有 value <= hash-max-ziplist-value}
    B -->|是| C["ziplist / listpack 紧凑存储 省内存"]
    B -->|否| D["hashtable 哈希表 O(1) 查找"]
    C --> E["元素变大 → 转成 hashtable"]

原理剖析：当 Hash 字段少、value 小时，用 ziplist（Redis 7.0 起改为 listpack）把 field-value 紧凑地连续存放，没有哈希表的开销，内存占用极低；一旦字段数超过 hash-max-ziplist-entries（默认 128）或任意 value 超过 hash-max-ziplist-value（默认 64 字节），就一次性转成真正的哈希表 dict，后续查询变 O(1)。这正是”设备状态用 Hash”的前提——单设备字段不多、value 不大时它比 String(JSON) 省内存，且 HGET/HSET 是 O(1) 字段级操作。注意：编码只升不降，一旦转成 hashtable 就不会退回。

List——消息队列与最新列表

底层实现

Redis 3.2 之后，List 的底层统一为 quicklist——它是”链表 + 压缩列表”的折中：整体是一个双向链表，每个节点又是一个 ziplist/listpack（一段紧凑存储的小数组）。这样既保留了链表两端 O(1) 插入删除的能力，又用紧凑存储压低了内存开销。

flowchart LR
    A["quicklist 头节点"] --> B["listpack 段1: 多个元素紧凑存储"]
    A --> C["listpack 段2"]
    A --> D["listpack 段N"]
    B --> E["每段元素数受 list-max-listpack-size 控制"]

原理剖析：早期 List 在小数据时用 ziplist、大数据时用 linkedlist；但 ziplist 修改中间元素要整体重分配、linkedlist 每个节点都有前后指针浪费内存。quicklist 取两者之长——每个 listpack 段足够小（默认 8KB 左右），修改只动一段；段与段之间是普通指针，头尾操作 O(1)。这就是为什么 LPUSH/RPUSH/LPOP/RPOP 都是 O(1)、而 LINDEX/LINSERT 是 O(N)。LPUSH + LTRIM 做”最新 N 条”正是利用了头插 O(1) 的特性。

实战：最新告警列表（List）

实战：简单消息队列（List）

Set——去重与集合运算

底层实现

Set 的底层也是双编码：当所有成员都是整数且数量不多时用 intset（整数集合，一片有序的整数数组），否则用 hashtable（value 统一为 NULL 的字典，仅用 key 保证去重）。

flowchart TD
    A["Set 写入"] --> B{所有成员都是整数 且 数量 <= set-max-intset-entries?}
    B -->|是| C["intset 有序整数数组 查找 O(logN) 省内存"]
    B -->|否| D["hashtable value=NULL 去重 O(1)"]
    C --> E["加入非整数或超阈值 → 转 hashtable"]

原理剖析：intset 用二分查找定位成员，内存极省（没有哈希表指针开销），适合”设备标签 ID 集合”这种纯数字场景；一旦出现字符串成员或超过 set-max-intset-entries（默认 512），会整体升级成 hashtable。由于 Set 的 hashtable 只用 key、value 为 NULL，它天然支持 SADD/SISMEMBER O(1) 去重，以及 SINTER/SDIFF/SUNION 集合运算——这正是标签系统、UV 去重选 Set 而不是 List 的原因（List 不去重、查存在是 O(N)）。

ZSet——排行榜与延迟队列

底层实现

ZSet 的底层是**「跳表（skiplist）+ 字典（dict）」双结构并存**，这是 Redis 在”范围查询”和”单点查询”之间做的精妙权衡。

flowchart TD
    A["ZSet 有序集合"] --> B["zset 结构体"]
    B --> C["skiplist 跳表: 按 score 排序"]
    B --> D["dict 字典: member -> score"]
    C --> E["ZRANGE / ZRANGEBYSCORE 范围查询 O(logN+M)"]
    D --> F["ZSCORE 单点查分 O(1)"]
    C --> G["rank 排名由跳表层级算出"]

为什么需要两个结构？ 单独用跳表时，ZSCORE（按成员查分数）要 O(logN) 遍历；单独用字典时有序性丢失，做范围查询要全量排序 O(NlogN)。Redis 让二者共享同一份成员和分值（dict 的 value 指针和 skiplist 的节点指向同一对象，不重复存数据），跳表负责”有序”、字典负责”查分”，各取所长。这种”空间换时间、双索引互补”的思路，和 MySQL 的”聚簇索引 + 二级索引”异曲同工。

跳表为什么比红黑树更适合？ 跳表是多层有序链表：最底层是完整有序链表，每往上一级随机”抽稀”一部分节点作为快捷通道。查找从顶层开始，本层走不到就下沉，平均 O(logN)。Redis 选它而非红黑树，因为：① 范围查询（如取 Top10）只需定位起点后顺序遍历，红黑树要中序遍历且实现复杂；② 插入删除只改相邻指针、不需要旋转平衡；③ 代码量和调试难度远低于红黑树。代价是更占内存（多级指针），但 Redis 用”概率性层级”把平均指针数控制在约 1.33 个/节点。

编码方式与内存优化全景

理解每种结构的底层编码，才能真正做好内存优化。下面是五种结构的编码转换全景：

结构 小数据编码 大数据编码 转换阈值（默认） 时间复杂度要点
String int / embstr raw >44 字节转 raw GET/SET O(1)
Hash ziplist/listpack hashtable 字段>128 或 value>64B HGET O(1)，HGETALL O(N)
List quicklist（listpack 段） 同左 每段约 8KB 头尾 O(1)，中间 O(N)
Set intset hashtable 出现非整数或 >512 个 SADD/SISMEMBER O(1)
ZSet ziplist/listpack skiplist+dict 元素>128 或 value>64B ZADD O(logN)，ZRANGE O(logN+M)

实战调优：把 *-max-ziplist-entries、hash-max-ziplist-value、zset-max-listpack-size 等阈值适当调大，能让更多 key 停留在紧凑编码，显著省内存（代价是少量 CPU）。但别调太大——紧凑编码修改中间元素的代价会随段变长而上升。智慧矿山里设备状态 Hash 字段稳定在 10 个以内、value 都很小，长期停留在 listpack，比 String(JSON) 省了约 40% 内存。反过来，若一个 Hash 字段暴涨到上千个，会自动转成 hashtable，此时”字段级更新省内存”的优势仍在，但紧凑性消失了——所以控制单 key 的元素规模永远是第一原则。

常见踩坑与实战经验

理论要落地，下面是真实项目里反复踩过的坑。

踩坑1：用 String 存对象导致更新字段要”读-改-写”

现象：SET device:CR001 '{"name":"采煤机1号","temp":45.2}'，要改 temp 得先 GET 整个 JSON、反序列化、改字段、再 SET 回去——三步且非原子，并发下会互相覆盖。

解法：多字段且会独立变化的对象用 Hash。只改 temp 用 HINCRBY device:CR001 temp 1 一步原子完成。判断标准：需要”整体读写”→ String(JSON)；需要”字段级操作”→ Hash。

踩坑2：大 Hash / 大 Set / 大 ZSet 引发慢查询

当 Hash 字段数到几万、ZSet 成员到几十万时，一次 HGETALL / ZRANGE 0 -1 会一次性返回海量数据，阻塞 Redis 主线程。务必用 HSCAN / SSCAN / ZSCAN 分批游标遍历（见上文生产环境注意事项）。智慧矿山曾因一个 10 万字段的设备大 Hash 做 HGETALL，导致监控接口 RT 从 5ms 飙升到 800ms。

踩坑3：ZSet 的 score 是 double，精度与排序陷阱

ZSet 的 score 是 double 类型，整数范围虽大但超大整数会有精度损失；而且相同 score 时按 member 字典序排序。做”精确整数排行榜”时如果分值可能超过 2^53，要格外小心。另外 ZINCRBY 浮点累加可能产生 0.30000000000000004 这类尾巴，展示层记得四舍五入。

踩坑4：List 做消息队列丢消息、无 ACK

LPUSH + BRPOP 看似能当队列，但进程崩溃会丢正在处理的消息，且没有消费确认和消费组。重要业务务必上 Kafka/RocketMQ；Redis 只适合”最近告警列表”这类允许丢失的场景。若坚持用 Redis 做可靠队列，至少用 Stream（XADD/XREADGROUP）替代 List。

踩坑5：INCR 计数器溢出与 TTL 丢失

INCR 的值是有符号 64 位长整型，超过 2^63-1 会报错；且 INCR 本身不会设过期时间，若忘了配套 EXPIRE，计数器会一直累加变成”幽灵数据”。正确姿势是首次 SET key 1 EX ttl，或用 Lua 脚本保证 INCR+EXPIRE 原子（见前文限流示例）。

实战：用 TYPE + OBJECT ENCODING 做结构健康检查

选型一句话总结：缓存对象整体读写用 String，字段级更新用 Hash，最新列表/简单队列用 List，去重与集合运算用 Set，排序/排行榜/延迟任务用 ZSet，海量去重计数用 HyperLogLog，位状态用 BitMap，附近的人用 GEO。

数据结构选型的三个原则

结合智慧矿山的实际项目，我总结出三条选型原则。第一，先看访问模式再看数据形态：同样是”设备信息”，如果页面每次都整页读取，String 存 JSON 一次 GET 更划算；如果状态字段频繁单独变更（在线状态、电量），Hash 的 HSET 只改动一个 field，避免读改写的并发覆盖。第二，警惕隐式类型转换：Set 存入的全是整数时会用 intset 编码，一旦混入一个字符串就整体转 hashtable，内存可能翻几倍——曾经一个白名单功能混入了带空格的 ID，导致内存告警，排查半天才发现是编码退化。第三，容量估算要在设计期做完：ZSet 每个成员除了 value 还要维护 score 和 skiplist 指针，单个成员开销约 100 字节起，百万级成员的排行榜光结构就上百 MB，上线前必须用 MEMORY USAGE 实测，而不是拍脑袋。

面试高频问题深度解析

1. String和Hash存储对象怎么选？

整体读写用String(JSON)，字段级操作用Hash。Hash的HGET/HSET是O(1)，但HGETALL是O(N)；String的GET/SET都是O(1)，但解析JSON需要时间。智慧矿山中：传感器数据整体读写用String，设备状态需要字段级更新用Hash。

2. ZSet底层的跳表是什么？

多层有序链表结构，每一层都是下一层的”快捷方式”。查找从顶层开始逐层向下，时间复杂度O(logN)。Redis选择跳表而非红黑树的原因：实现更简单、范围查询更高效、插入删除不需要旋转。

3. List做消息队列有什么问题？

不支持消息确认(ACK)、不支持消费组、没有持久化保障、消息堆积时内存压力大。生产环境建议用RabbitMQ/RocketMQ/Kafka。智慧矿山中List只用于简单的告警列表场景。
