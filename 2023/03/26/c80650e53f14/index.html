Redis持久化——RDB与AOF的选择

发布于 2023-03-26 分类：技术, 2023, Redis 👁

前言

实际项目上线三个月后，某天凌晨Redis服务器因内存故障重启，所有设备实时状态数据丢失，监控大屏一片空白，运维花了两个小时才从数据库重新加载完数据。排查发现Redis持久化配置形同虚设——RDB快照间隔太长（save 900 1）、AOF根本没开。

这次事故给我最大的教训是：持久化策略必须按数据重要性分级设计，而不是一套配置走天下。有些数据丢了可以从数据库重载，有些丢了就是生产事故。本文系统地复盘RDB和AOF两种持久化方案的原理、配置、选型和踩坑经验。

为什么需要持久化

Redis数据在内存里，进程重启、机器断电，数据就没了。但”需要持久化”不等于”所有数据都要最高级别保护”。持久化是有代价的——磁盘IO、fork开销、CPU——正确的做法是先给数据分级，再匹配持久化策略。

智慧矿山Redis数据重要性分级：

数据类型 示例Key 可丢？ 恢复手段 持久化要求
告警阈值配置 config:threshold:TEMP ❌ 不可丢 丢了无法自动重建 AOF(everysec)起步，配置类考虑always
物资库存 stock:material:MAT001 ❌ 不可丢 需与DB对账恢复 AOF(everysec) + 定期对账
设备实时状态 device:status:CR001 ✅ 可丢 从DB重载，秒级 RDB即可
传感器缓存 sensor:data:TEMP001 ✅ 可丢 实时采集自动覆盖 可以不持久化
分布式锁 lock:device:CR001 ✅ 可丢 过期自动清除 反而怕持久化恢复出”僵尸锁”
限流计数 rate:limit:api:query ✅ 可丢 重新计数即可 可以不持久化

这里有个反直觉的点：分布式锁恰恰不希望被持久化恢复。主库宕机后从库提升，如果锁状态被恢复出来，原来持有锁的客户端已经释放过了，就会出现”锁已释放但Redis里还有”的僵尸状态。Redlock和Redisson的watchdog机制都专门处理过这个问题——这也是为什么”持久化越强越好”是一种误解。

RDB快照

工作原理

RDB是把某一时刻的全量内存数据以二进制压缩格式写到磁盘。核心机制是fork + 写时复制（Copy-On-Write）：

  1. 自动触发：配置save规则（如save 60 10000），60秒内至少10000次修改就触发bgsave
  2. 手动触发：bgsave命令，异步执行不阻塞主线程（对比save命令是同步的，会阻塞，生产禁用）
  3. shutdown触发：正常关闭时自动保存——注意只有非NOSAVE方式的正常关闭才触发，kill -9不会
  4. 主从全量复制触发：Master执行bgsave生成RDB发给从库

fork + COW 是理解RDB一切问题的关键：

flowchart TD
    A["主进程执行 bgsave"] --> B["调用系统 fork()"]
    B --> C["fork 瞬间：子进程复制页表
（不是复制内存！）"]
    C --> D["父子进程页表指向同一批物理内存页"]
    D --> E["子进程：遍历内存数据
写 RDB 临时文件"]
    D --> F["主进程：继续处理读写请求"]
    F --> G{"主进程修改某个内存页？"}
    G -- 是 --> H["触发写时复制 COW：
复制该页，主进程改副本
子进程看到的仍是 fork 瞬间的旧数据"]
    G -- 否 --> I["继续共享同一物理页"]
    E --> J["子进程写完，原子替换 dump.rdb，退出"]
    H --> J

三个关键推论，面试和排查都高频：

  1. fork耗时与内存大小成正比，但COW只复制被改的页——10GB实例fork约耗时100~200ms（复制页表的开销），这期间主线程阻塞，所有请求排队
  2. COW导致内存峰值可能翻倍——如果bgsave期间主进程写入热点数据，被改的页都会复制一份。极端情况（全量重写）内存占用接近2倍，OOM就是这么来的
  3. 子进程看到的是fork瞬间的数据快照——所以RDB不是”执行时的数据”，而是”bgsave发起那一刻的数据”

RDB配置详解

stop-writes-on-bgsave-error值得展开说一句：它默认开启是为了防止你”以为在持久化其实一直失败”。但我们真实踩过坑——磁盘满导致bgsave失败，整个Redis拒绝写入，设备状态上报全线报错，最后Redis自己把自己变成了故障中心。有持久化需求的核心实例保持yes，纯缓存实例务必设no，否则持久化故障会升级成服务故障。

RDB文件结构

RDB是紧凑的二进制格式，了解结构对排查”RDB文件损坏”有用：

区块 内容 说明
魔数 REDIS 5字节 标识这是RDB文件，损坏检测的第一道关卡
版本号 4字节，如0011 RDB版本，高版本格式低版本Redis读不了
辅助字段 redis-ver、redis-bits、创建时间等 排查时可以确认快照时间
数据区 按类型逐条写入键值对 LZF压缩，expired key跳过
EOF + 校验和 结束符 + CRC64 rdbchecksum yes时加载会校验

版本兼容是隐藏坑：Redis 5.x生成的RDB（v9格式）不能被Redis 3.x加载。集群升级时如果打算”新版本Master的RDB直接塞给旧版本节点”，一定先做兼容性验证。

RDB优缺点

维度 评价
文件体积 ✅ 紧凑，6GB内存数据压缩后约1.2GB
恢复速度 ✅ 快，直接加载二进制，6GB数据约1~2分钟
数据安全 ❌ 非实时，两次快照之间的数据全丢
实时性代价 save 60 10000最多丢60秒；事故案例的save 900 1最多丢15分钟
fork开销 ❌ 大实例fork阻塞主线程，COW有内存翻倍风险

RDB的丢数据窗口计算：最坏情况 ≈ 最长满足条件的间隔。我们事故的save 900 1意味着流量低峰时（15分钟1次修改才触发），实际丢数据窗口可能远超15分钟——低峰期数据变化少，可能几个小时都没有一次快照，凌晨重启就全丢了。

COW内存翻倍：机理、量级与对策

fork + 写时复制的完整链条值得展开。fork 本身只复制页表，几 GB 实例的 fork 通常在几十毫秒量级（页表 2MB~数百MB，与实例大小线性相关），这几十毫秒就是主进程的第一段阻塞。真正的风险在 fork 之后：子进程遍历内存写 RDB 期间，父进程的每次写操作都可能触发 COW——操作系统按 4KB 页为单位复制被修改的页。触发 COW 的概率与”写入命中率”有关：如果写入恰好分散在整个地址空间（大量 key 均匀更新），内存放大可以接近 100%；如果写入集中在少数热 key（同一页被反复改），放大可以忽略不计。

量级估算用这个经验公式：COW 追加内存 ≈ 快照期间的写入页数 × 4KB。一个 10GB 实例、快照耗时 60 秒、期间每秒写 5 万个不同 key，最坏情况要预留 60 × 5万 × 4KB ≈ 11GB 的内存余量——这就是”实例内存使用率超过 50% 就不敢 bgsave”的由来。三个对策按优先级：其一，maxmemory 控制在物理内存的一半以下，给 COW 留足余量；其二，把 save 安排在低峰期，降低快照期间的写入页数；其三，Redis 7.0 之后的 CoW 优化（大页关闭 THP，echo never > /sys/kernel/mm/transparent_hugepage/enabled）能显著减少放大倍数——透明大页会把 4KB 页放大成 2MB 页，一个字节修改就复制 2MB，这是很多”开了 THP 的机器 bgsave 必然内存翻倍”的根因。

AOF追加日志

工作原理

AOF记录的是每一条写命令，恢复时重放命令。数据从命令到磁盘要经过三段缓冲，理解这三段才能理解”丢1秒数据”到底丢在哪：

flowchart LR
    A["Redis 主进程
执行写命令"] --> B["① aof_buf 缓冲区
（用户态内存）"]
    B --> C["② 内核页缓存 PageCache
write() 系统调用"]
    C --> D["③ 磁盘
fsync() 真正落盘"]
    E["appendfsync 策略
控制 ②→③ 的时机"] -.-> C

关键认知：write()成功不代表数据安全。write只是把数据交给了操作系统页缓存，机器断电时页缓存里的数据照样丢。只有fsync落盘才是真正安全的。appendfsync的三种策略，本质就是在”fsync时机”上做权衡：

三种appendfsync策略对比：

策略 fsync时机 数据安全性 性能（参考TPS） 适用场景 智慧矿山对应
always 每次写事件循环都fsync 基本不丢 ~2000 数据绝不能丢 告警阈值配置
everysec 后台线程每秒fsync一次 最多丢1秒 ~10000 生产环境默认推荐 设备状态/库存
no 由OS决定（通常30秒左右） 不可控 ~20000 纯缓存可接受 传感器缓存

注意always并不绝对安全：Redis只保证”命令写入aof_buf后fsync”，如果fsync进行中宕机，最后一条命令仍可能丢。always的真实语义是”最多丢一个正在执行中的命令”。

另外everysec的”最多丢1秒”有个前提——磁盘不卡。我们踩过的坑：AOF fsync延迟超过2秒时，Redis主线程会阻塞等待fsync完成（aof_delayed_fsync计数增加），表现为所有写入突然卡200ms~2秒。这就是后文”持久化性能优化”里磁盘选型的重要性。

AOF重写

AOF记录原始命令，天然会膨胀——同一个计数器incr一百万次，AOF里就有一百万条命令，但内存里只是一个小整数。重写（rewrite）就是根据当前内存数据生成一份等价的最小命令集：

指标 重写前 重写后
文件大小 8GB 1.5GB
恢复时间 3分钟 40秒
冗余率 99.97% 0%

AOF重写完整流程（面试必考）：

flowchart TD
    A["触发重写
BGREWRITEAOF 或 auto-aof-rewrite"] --> B["主进程 fork 子进程"]
    B --> C["子进程：根据 fork 瞬间的内存数据
生成精简命令，写入临时AOF文件"]
    B --> D["主进程：新写命令同时写入
① aof_buf（正常AOF流）
② AOF重写缓冲区"]
    C --> E["子进程完成后通知主进程"]
    D --> E
    E --> F["主进程将重写缓冲区内容
追加到新AOF（阻塞但量小）"]
    F --> G["原子 rename 替换旧AOF"]

核心问题——重写期间的新写命令怎么不丢？ 双写：主进程继续把新命令写入AOF重写缓冲区，子进程完成后，主进程把这段增量追加到新AOF，再原子替换。所以重写期间不会丢数据，代价是重写末尾主进程要短暂阻塞来做”追加增量 + rename”。

重写本质上也是fork，所以RDB的fork/COW问题在AOF重写时同样存在——大实例AOF重写时的卡顿和内存翻倍风险，和bgsave一模一样。这是很多同学排查”没开RDB为什么还是卡”时想不到的答案。

重写期间的三个生产级陷阱

陷阱一：重写风暴。 auto-aof-rewrite-percentage 100 意味着文件翻倍就触发重写。如果业务存在周期性的大批量写入（比如每晚同步一批设备档案），AOF 会在同一段时间内被反复触发重写——每次重写都是一次 fork，叠加起来主进程反复卡顿。对策：把 auto-aof-rewrite-min-size 抬高到与实例内存同量级（比如 8GB 内存实例设 2GB+），并在低峰期用定时任务主动 BGREWRITEAOF，白天关掉自动触发。

陷阱二：重写缓冲区撑爆内存。 重写持续时间与数据量成正比，期间所有新写命令都堆在 AOF 重写缓冲区（aof_rewrite_buf）。写入密集的实例（比如每秒 10 万条命令的缓存集群）重写 30 秒，缓冲区就能堆出几个 GB——表现为”重写期间内存曲线异常抬升，重写结束瞬间回落”，严重时直接 OOM 被 kill。这类实例要么拆分热 key 热库降低单实例写入速率，要么评估升级到 Redis 7.0（Multi-Part AOF，重写机制重构后缓冲压力小得多）。

陷阱三：rename 瞬间的写放大。 子进程完成后的”追加增量 + rename 替换”在主线程执行，增量越大阻塞越久。如果重写期间恰好赶上写入洪峰，这个尾部的阻塞可能达到数百毫秒，且发生在谁也想不到的时间点。监控上要看的不只是重写是否成功，还有 aof_delayed_fsync 和重写结束时长分布。

这三类问题有一个共同排查入口：info persistence 里的 aof_rewrite_in_progress、aof_last_write_status 配合 info stats 的写入速率曲线。看到”卡顿时间点与重写时间点重合”，就往这三个方向查，基本不会走偏。

AOF配置详解

aof-load-truncated选yes还是no值得单独说：选yes是”自动容错”，服务能起来但没人知道丢了多少数据；选no是”快速失败”，凌晨宕机你会被电话叫起来修文件——但我强烈建议no，静默丢数据比告警可怕得多，尤其是库存和配置类数据。

混合持久化（Redis 4.0+）

混合持久化是RDB和AOF优点的合体，重写时才体现：

方案 数据安全 恢复速度 文件大小 适用
纯RDB 丢分钟级 快 小 纯缓存、可从DB重建
纯AOF(everysec) 最多丢1秒 慢 大（未混合） Redis 4.0以下
混合持久化 最多丢1秒 快（RDB头+AOF尾） 中 生产环境标配
RDB+AOF双开（非混合） 最多丢1秒 用AOF恢复 两份文件 空间充裕且要快速灾备

实际项目结论：4.0以上版本无脑开aof-use-rdb-preamble yes，它同时解决了AOF恢复慢和RDB丢数据多的两个痛点，没有明显代价。

从本质看权衡：日志型与快照型是同一个问题的两个答案

把 RDB 和 AOF 放在一起看，会发现它们其实是数据库领域一个经典问题的两种解法：如何在崩溃后恢复状态。AOF 是”日志先行”（WAL，Write-Ahead Logging）思路——先记下每一步操作，恢复时重放，好处是粒度细、丢失窗口小，代价是日志无限增长、恢复重放慢；RDB 是”全量快照”思路——某个时刻把整个状态拍下来，恢复时直接加载，好处是文件紧凑、恢复快，代价是两次快照之间的变更无处安放。MySQL 的 redo log + binlog、HDFS 的 editlog + fsimage、Kafka 的 segment 快照，都是同一对矛盾的翻版。

理解了这个本质，很多配置就不再是”背参数”而是”推结论”：AOF 重写相当于 WAL 的 checkpoint（把日志压缩成状态），所以重写期间新命令必须继续追加（aof_rewrite_buf 的存在意义）；混合持久化相当于”checkpoint 文件 + 增量日志”，所以它必然是”RDB 头 + AOF 尾”；RDB 的 fork + COW 相当于”一致性快照读”——子进程看到的是 fork 瞬间的数据视图，父进程后续修改走副本，两者互不干扰。跨领域把这套模型建立起来之后，排查持久化问题就不局限于 Redis 本身：凡是”恢复时间变长”，先查日志膨胀（该 checkpoint/重写了）；凡是”快照期间内存暴涨”，先查 COW 写入率。

持久化方案选择

这是原文里缺失的决策框架，补上。按实例角色和数据分级决策：

实例角色 推荐配置 理由
纯缓存（可从DB重建） save "" + AOF关闭 持久化是纯开销，恢复靠DB重载
混合业务（我们主实例） RDB(save 300 10) + AOF(everysec) + 混合持久化 配置/库存安全 + 状态数据可丢
配置中心型（不可丢） AOF(always) 或 everysec + 主从 + 定期RDB备份到对象存储 always的TPS损耗可接受
主从架构Master AOF(everysec) + 混合持久化 从库同时开，宕机切换后数据基本不丢

再叠加运维三件套，才是完整方案：

  1. 异地备份：RDB文件定时（如每天凌晨低峰bgsave后）上传到对象存储/异地机房，防止磁盘整盘损坏
  2. 恢复演练：每季度用备份RDB/AOF真实恢复一次到测试环境——没验证过恢复的备份不叫备份
  3. 监控告警：见下文PersistenceMonitor，bgsave失败、fork超时必须当天感知

关键监控指标

线上问题排查：fork耗时

THP这一项展开说：THP开启时内核用2MB大页，fork后主进程每写一个2MB页就要复制2MB（普通页只需4KB），COW写放大500倍，还容易触发内存告警。Redis官方文档明确建议关闭THP，这是部署检查清单的必查项。

AOF文件损坏修复

修复后必须对账：截断丢掉的命令不可知（只知道时间边界），要用业务数据核对”最后一条成功命令”之后是否有业务差异。我们当时的做法是以AOF最后写入时间为界，从数据库拉取该时间点后的库存变更做比对。

数据丢失窗口的量化思维

谈持久化方案，”丢数据”三个字太粗，工程上必须把它量化成丢失窗口才能做决策。各方案的最坏丢失窗口可以精确计算：RDB 保存点 save 900 1 的语义是”900 秒内至少 1 次修改才触发”，实际丢失窗口 = 距上次成功快照的时间，低峰期可能长达数小时；AOF appendfsync always 理论上 0 丢失，但每条命令一次 fsync，写入吞吐直接掉一个数量级，通常只用于极端关键的小数据集；everysec 丢失窗口标称 1 秒，实际最坏 2 秒——fsync 由后台线程执行，主线程发现上次 fsync 未完成会先返回再补，恰在此时断电就丢两秒；no 模式的丢失窗口等于 Linux 页缓存刷盘周期（默认 30 秒），且不可控。量化之后选型就变成了数学题：我们的遥测数据允许丢最近 1 分钟（设备端有本地缓存可重传），everysec 绰绰有余；设备指令下发记录不允许丢，那就根本不该放 Redis 单点，要么 always、要么写前落库。把业务能容忍的丢失窗口写成数字，再挑满足数字的最便宜方案，比背”RDB 快 AOF 安全”的口诀可靠得多。

主从架构下的持久化分工策略

持久化讨论常常默认单机视角，生产上更现实的架构问题是：主从之间谁做持久化、怎么做。最常见的错误配置是”主从都不开持久化”——Redis 崩了从主从重新同步就是了——这个判断在主从同时故障（机房断电、Redis 版本升级引发的连锁重启、误操作 FLUSHALL 被同步）时会被击穿，全部数据丢失。我们的实践方案是主从分工：主库关闭 RDB 快照（避免 fork 阻塞主库写入，主库对延迟最敏感），保留 appendfsync everysec 的 AOF（崩溃恢复丢 1 秒可接受）；从库开启 RDB 定时快照加 AOF，承担”数据底座”角色，主库故障切换后新主库再从旧从库的 AOF 恢复完整状态。有两个配套细节必须注意：一是主从切换后要重建持久化布局——原从库升主后 AOF/RDB 配置还带着”从库”的角色设定，哨兵不会替你改配置，需要运维脚本联动；二是RDB 文件也是从库全量同步的数据源，从库不开 RDB 会让新从库加入时只能走 AOF 重放或直接触发主库 bgsave，把主库的 fork 风险又引回来了。持久化从来不是”开不开”的单选题，而是整个复制拓扑里的角色分配问题。

面试高频问题

1. RDB和AOF的区别？

RDB是快照，定时保存内存全量数据到磁盘，恢复快但可能丢分钟级数据；AOF是追加日志，记录每条写命令，everysec下最多丢1秒但恢复慢。推荐混合持久化（Redis 4.0+）：重写后文件前半部分是RDB格式快速加载，后半部分AOF增量保证完整。生产标配：AOF(everysec) + 混合持久化。

2. AOF重写的原理？

fork子进程，根据fork瞬间的内存数据生成最少写命令。重写期间的新写命令同时写入aof_buf和AOF重写缓冲区，子进程完成后主进程把重写缓冲区追加到新AOF，原子rename替换旧AOF。关键点：重写期间数据不丢；重写也是fork，大实例同样有fork阻塞和COW内存翻倍风险。

3. Redis宕机数据能恢复多少？

取决于配置：RDB——丢最后一次快照后的所有数据（注意低峰期快照间隔会被拉长）；AOF(everysec)——最多丢1秒；AOF(always)——基本不丢；混合持久化——与AOF(everysec)一致。追问他”everysec为什么是1秒不是2秒”：后台线程每秒fsync一次，宕机时最多有一秒的缓冲未落盘；但磁盘IO过载时fsync延迟，丢的会更多。

4. fork为什么会阻塞Redis？

fork需要复制页表，页表大小与内存成正比——10GB内存约250万个4KB页表项，fork耗时约100~200ms，期间主线程阻塞。三个优化方向：控制实例内存（拆分实例，最有效）、关闭THP（避免COW大页写放大）、使用物理机（避免虚拟化页表开销）。监控指标latest_fork_usec超过100ms就该行动了。

5. 什么情况下可以不持久化？

纯缓存且可从数据库重建的实例（传感器缓存、限流计数、临时会话）。判断标准一句话：“丢了之后的恢复成本”是否低于”持久化的运行成本”。注意主从架构里即使Master不持久化，也要保证至少一个从库持久化，否则主从同时重启就是全灭。
