MyBatis插件机制——Interceptor的原理与实战

发布于 2023-03-08 分类：技术, 2023, MyBatis源码 👁

前言

实际项目上线第一周，运维就反馈：传感器数据查询偶发超时，但日志里看不到具体哪条SQL慢。最初的监控方案是在Service层用AOP记录耗时，但AOP只能拿到方法执行时间，无法获取到实际执行的SQL语句和参数。更头疼的是，某些批量操作涉及数千条传感器数据，逐条insert的性能问题在AOP层面完全看不出根因。

后来深入研究MyBatis的Interceptor机制，发现它能精准拦截SQL执行的全过程——从SQL构建、参数设置到结果映射，每一个环节都可以增强。基于Interceptor，我为实际项目实现了慢SQL监控、分表路由、数据权限过滤、操作审计四个核心插件，彻底解决了SQL层面的可观测性和安全性问题。

为什么用 JDK 动态代理而非 CGLIB

MyBatis 选择 JDK 动态代理来包裹插件，而不是 CGLIB，背后有清晰的取舍：四大可拦截对象（Executor、StatementHandler、ParameterHandler、ResultSetHandler）本身都是接口或实现了接口的类，JDK 动态代理天然要求被代理对象实现接口，正好契合；而 CGLIB 通过继承生成子类，会破坏 MyBatis 内部对象的封装，还可能因为 final 方法、构造函数等问题引入不确定性。

更关键的是，插件的拦截点不是按”类”拦截，而是按 @Signature 标注的”具体方法”拦截。比如你用一个插件拦截 Executor，但只声明了 query 方法，那么 update、commit 等方法仍会直接调用原对象。这种”精确到方法”的能力，只有先建立 signatureMap、在 Plugin.invoke() 中做命中判断才能实现，而 JDK 动态代理的 InvocationHandler 正是承载这一判断的天然载体。

代理链的完整结构

每个插件都能在 proceed() 前后插入自己的逻辑，也可以直接短路返回、不调用真实方法——这就是分页插件能”改写SQL”、监控插件能”统计耗时”的机制基础。注册顺序决定包裹顺序：interceptorChain.pluginAll() 按注册列表依次包裹，后注册的包在最外面、最先被调用；生产上建议把轻量通用插件（监控）放外层、重量改写插件（分表）放内层，减少无效的深层调用。

执行时序（sequenceDiagram）：

sequenceDiagram
    participant C as 调用方
    participant P1 as 插件1(分表)
    participant P2 as 插件2(权限)
    participant P3 as 插件3(监控)
    participant E as 实际Executor
    C->>P1: query()
    P1->>P2: invocation.proceed()
    P2->>P3: invocation.proceed()
    P3->>E: invocation.proceed()
    E-->>P3: 结果
    P3-->>P2: 结果(含耗时统计)
    P2-->>P1: 结果
    P1-->>C: 结果

关键点：每个插件的”前置逻辑”在外层 intercept() 中、调用 proceed() 之前执行；”后置逻辑”则放在 proceed() 之后。所以先注册的插件前置逻辑先跑，但后置逻辑最后跑——这正是洋葱模型的本质。

四大拦截对象如何选型

并不是所有需求都该挂在 StatementHandler 上。选错拦截点，要么拿不到想要的信息，要么引入性能或正确性问题。下面的对比表是我在选型时反复用的速查表：

拦截对象 触发时机 能拿到的关键信息 典型用途 主要风险
Executor SQL 执行入口（query/update 前） MappedStatement、完整参数对象、SQL 类型 操作审计、读写分离、缓存 拿不到最终改写后的 SQL 文本
StatementHandler SQL 编译前（prepare） BoundSql 原始 SQL、可改写 SQL 分表路由、数据权限、多租户、分页 改写 SQL 字符串易出错，需小心子查询
ParameterHandler 参数绑定到 PreparedStatement 时 parameterObject、参数映射 特殊类型处理、参数脱敏 拿不到 SQL 文本，只能在参数层面动手
ResultSetHandler 结果集映射时 Statement、原始 ResultSet 大结果集保护、字段加解密 已执行完 SQL，无法阻断查询本身

选型口诀：想”改 SQL”用 StatementHandler，想”拦操作”用 Executor，想”动参数”用 ParameterHandler，想”管结果”用 ResultSetHandler。多个插件同时改写 SQL 时，务必用注册顺序约定好先后（见后文插件顺序规范）。

面试高频问题

1. MyBatis插件的原理？

基于JDK动态代理，在创建四大对象时通过InterceptorChain依次应用所有插件，生成代理对象。每个插件通过Plugin.wrap()创建代理，在Plugin.invoke()中检查@Intercepts签名决定是否拦截。多个插件形成代理链（洋葱模型）。

2. MyBatis能拦截哪些对象？

Executor（SQL执行、事务管理）、StatementHandler（SQL语句处理）、ParameterHandler（参数映射）、ResultSetHandler（结果集映射）。最常用的是StatementHandler.prepare和Executor.query。

3. PageHelper的原理？

拦截StatementHandler.prepare方法，从ThreadLocal取分页参数，拼接LIMIT实现分页，优化COUNT SQL获取总数。关键：startPage必须紧挨查询，使用后必须清理ThreadLocal。

4. 插件的注册顺序有什么影响？

先注册的插件在最外层，最先执行intercept逻辑，最后执行proceed之后的逻辑（洋葱模型）。修改SQL的插件顺序尤其重要：分表路由先于数据权限，数据权限先于分页，监控在最外层。

插件开发完整清单

把上面所有经验浓缩成一个可落地的检查清单，每次写新插件前过一遍，能避开 90% 的坑：

定义阶段

  • 是否真的需要插件？能用 MyBatis 原生功能（如 @SelectProvider、TypeHandler、拦截器之外的 Setting）解决就不要写插件。
  • 拦截点是否选对？对照上文选型表确认 Executor / StatementHandler / ParameterHandler / ResultSetHandler。
  • @Signature 的方法签名（type/method/args）是否与目标 MyBatis 版本一致？参数类型写错会导致插件”静默失效”。

实现阶段

  • intercept() 内是否一定调用了 invocation.proceed()？漏掉会导致 SQL 永远不执行。
  • 改写 SQL 后用 MetaObject.setValue("delegate.boundSql.sql", newSql) 是否同时保留了参数映射？避免改完表名后参数错位。
  • 是否用 try/finally 包裹了耗时统计与 ThreadLocal 清理？
  • 重逻辑（远程调用、复杂计算）是否移出了插件主路径（改为异步）？

注册与顺序

  • 多插件时是否用 @Configuration 手动注册以固定顺序？顺序约定：分表 → 数据权限 → 分页 → 监控 → 审计。
  • 是否给每个插件加了异常隔离（catch 后降级 proceed()），避免一个插件崩了拖垮全站？

测试与上线

  • 是否覆盖”无 @Intercepts 注解””签名不匹配”等降级路径的单测？
  • 是否在预发环境用 ExplainInterceptor 验证没有引入全表扫描？
  • 生产环境是否确认插件 sampleRate、阈值等配置可按环境动态调整？

一句话总结：MyBatis 插件是”能力越大责任越大”的典型。它让你能在 SQL 执行的毛细血管里做增强，但也意味着任何一行错误代码都会被每一条 SQL 放大。写好插件的核心心法是——轻量、可降级、顺序可控。
