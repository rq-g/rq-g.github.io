设计哲学：MVCC 为什么用「undo log 版本链 + ReadView」这一套

理解了机制后，更重要的是回答”为什么 MySQL 要这么设计”。如果让我们从零实现”读写不冲突”，至少有三种思路，而 InnoDB 的选择是深思熟虑的结果：

思路 A：为每行数据保留多份快照（类似 MVCC 的朴素实现）
直接在数据页里存历史版本。缺点是存储膨胀不可控，且一次 UPDATE 要复制整行，写放大严重。

思路 B：读写都加锁，用锁调度并发
最简单，但读写互斥，吞吐量直接回到”单线程”，完全失去并发意义。

思路 C（InnoDB 实际采用）：undo log 版本链 + ReadView 快照
更新时不改旧版本，只在 undo log 里追加新版本并让旧版本通过 DB_ROLL_PTR 串成链表；读时根据事务启动时的 ReadView 沿链表找到”对当前事务可见”的那一版。它的精妙在于：

  1. 写不阻塞读：读永远访问历史快照，和最新写入的 Buffer Pool 页互不干扰；
  2. 存储按需回收：历史版本存在 undo log 中，当没有任何活跃事务需要它时，purge 线程会异步清理，不会无限膨胀；
  3. 可见性判断与存储解耦：ReadView 只是一个”活跃事务列表 + 边界 ID”的轻量快照，判断可见性只做几次整数比较（O(1)），不必扫描全部历史；
  4. 天然支持”可重复读”与”读已提交”的差异：只需控制 ReadView 的”创建时机”（第一次读 vs 每次读），同一套版本链就能支撑两种隔离级别，几乎零额外成本。

一句话总结：MVCC 把”并发控制”从”锁的调度问题”转变成了”版本可见性的判断问题”，而可见性判断是纯内存的整数比较，这正是它高性能的根本原因。

实战：一次线上”读到了旧数据”的排查全过程

智慧矿山项目曾遇到一个典型问题：对账定时任务在每天凌晨跑批时，偶发性地”少算了”当天的告警数据。排查过程正好串起了本文所有知识点，这里完整复盘，作为隔离级别实战的收尾。

现象与初步怀疑

对账任务逻辑很简单：先查 t_alarm 当天新增告警，再和 Kafka 消费进度比对。但日志显示，任务偶尔比人工统计少几十条。第一反应是”是不是事务没提交就读了”，但代码用的是默认的 RR 隔离级别，理论上快照读不该读到未提交数据。

根因定位：当前读 + 间隙锁的副作用

深入排查发现，对账任务里有一段”标记已对账”的逻辑：

问题出在 UPDATE 是当前读：如果它执行时，业务侧正好有一批新告警通过 INSERT 写入（这些新行 create_time 也落在当天范围内），Next-Key Lock 会阻塞这批 INSERT 直到对账事务提交。更隐蔽的是——由于 UPDATE 是当前读，它会感知到 ReadView 创建之后才插入、但已提交的新行，于是”标记”把这批新告警也置为 reconciled=1，而前面 COUNT(*) 快照读却没把它们算进去，造成”统计少、标记多”的账实不符。

解决与经验

  1. 读写分离时序：把”统计快照”和”标记”拆成两个独立事务，统计用 START TRANSACTION WITH CONSISTENT SNAPSHOT 的纯快照读，标记单独提交，避免当前读污染快照；
  2. 缩小当前读范围：UPDATE 改用主键精确条件（WHERE id IN (...)）而非范围条件，避免 Next-Key Lock 锁住整段区间，减少对 INSERT 的阻塞；
  3. 对账幂等：对账任务设计为可重跑，按”已对账批次号”去重，即使偶尔漏算也能在下一批补齐。

这次事故让我真正理解了：RR 只保证”快照读”的可重复读，一旦涉及 UPDATE/DELETE/SELECT ... FOR UPDATE 这种当前读，你就离开了 MVCC 的保护伞，进入锁的世界。

面试高频问题

1. MVCC的原理？

通过隐藏列（事务ID+回滚指针）+undo log版本链+ReadView实现。每个事务根据ReadView判断能看到哪个版本的数据，实现读写不冲突。

2. RC和RR的MVCC区别？

RC每次SELECT创建新ReadView，RR只在第一次SELECT创建。所以RC允许不可重复读，RR保证可重复读。

3. RR隔离级别能完全解决幻读吗？

快照读通过MVCC解决幻读，当前读通过Next-Key Lock解决幻读。但在某些特殊场景下（先快照读再当前读）仍可能出现幻读。

总结

事务隔离级别和MVCC是MySQL并发控制的基石。核心认知是：MVCC通过版本链实现读写不冲突，ReadView决定可见性，RC每次读创建新ReadView而RR复用。理解了这些，遇到不可重复读、幻读问题就能从底层原理分析根因。

总结

事务隔离级别与MVCC是MySQL并发控制的基石，实际项目的实践总结：

  1. 默认RR够用 — 大多数业务场景用RR即可，无需修改
  2. 理解MVCC原理 — ReadView+undo log版本链是理解隔离级别的关键
  3. 当前读要警惕 — RR下当前读仍可能幻读，需要Next-Key Lock保护
  4. 长事务要拆分 — 大事务拆小事务，减少锁持有时间
  5. 乐观锁优先 — 冲突少的场景用乐观锁CAS，冲突多的用悲观锁
  6. 分布式事务用消息表 — 本地消息表实现最终一致性，简单可靠
