MyBatis动态SQL源码——XmlScriptBuilder解析

发布于 2023-12-10 分类：技术, 2023, MyBatis源码 👁

前言

实际项目的告警查询接口需求极其复杂：需要根据告警类型、级别、设备、区域、时间范围、处理状态等多达10个条件进行组合查询，且每个条件都是可选的。最初用Java代码拼接SQL字符串，代码又长又乱，稍不注意就拼出语法错误的SQL。后来全面改用MyBatis动态SQL，if/choose/foreach/where/set的组合让代码简洁了很多，但一直没搞懂这些标签底层是怎么工作的——为什么where标签能自动去掉开头的AND？为什么foreach生成的参数映射叫做__frch_item？

深入XmlScriptBuilder源码后，理解了动态SQL的解析和执行原理：每个动态标签对应一个SqlNode实现类，执行时递归apply拼接SQL，OGNL表达式做条件判断。理解了SqlNode体系，动态SQL不再是黑盒。

foreach 参数映射内部变量名生成规则：

  • XML:
  • <foreach collection=”ids” item=”id” open=”(“ close=”)”
  • separator=”,”>
  • #{id}
  • 生成的SQL和参数映射：
  • SQL: (?, ?, ?)
  • ParameterMappings:
  • [__frch_id_0, __frch_id_1, __frch_id_2]
  • 命名规则：_frch{item}_{index}
  • _frch → foreach前缀
  • id → item属性名
  • 0/1/2 → 元素索引
  • 这就是为什么DefaultParameterHandler
  • 要优先从boundSql.additionalParameters取值
  • 因为foreach生成的参数名是__frch_xxx格式
  • 不在原始参数对象中

where标签源码

where标签 vs 1=1

where标签 vs WHERE 1=1 对比：

  • ❌ WHERE 1=1 写法：
  • SELECT * FROM alert WHERE 1=1
  • AND alert_type = ?
  • AND level = ?
  • 问题：1=1导致数据库无法优化查询计划
  • 某些数据库优化器会将1=1视为恒真条件
  • 可能导致全表扫描而非走索引
  • ✅ where标签写法：
  • SELECT * FROM alert
  • AND alert_type = ?
  • AND level = ?
  • 生成SQL: SELECT * FROM alert WHERE alert_type = ? AND level = ?
  • 无1=1干扰，索引正常使用

RawSqlSource vs DynamicSqlSource

RawSqlSource vs DynamicSqlSource：

维度 对比：

RawSqlSource SQL中只有#{}，没有${}和动态标签：

  • 解析一次，缓存BoundSql
  • 每次调用直接返回缓存的BoundSql
  • 性能更好

DynamicSqlSource SQL中有${}或动态标签(if/foreach等)：

  • 每次调用都重新解析SqlNode树
  • 根据参数动态生成不同的SQL
  • 性能稍差（但通常可忽略）

判断逻辑 parseDynamicNode()中：

  • 含${} → TextSqlNode → DynamicSqlSource
  • 含动态标签 → DynamicSqlSource
  • 纯文本+#{} → StaticTextSqlNode → Raw

面试高频问题

1. MyBatis动态SQL的原理？

XML解析时将动态标签解析为SqlNode树，执行时通过OGNL表达式判断条件，递归apply拼接SQL。每个标签对应一个SqlNode实现类：IfSqlNode、ForEachSqlNode、WhereSqlNode等。最终由DynamicSqlSource汇总生成BoundSql。

2. #{}和${}在动态SQL中的区别？

#{}在SqlSourceBuilder阶段替换为?，是预编译参数，安全；${}在TextSqlNode阶段直接通过OGNL求值后toString()替换，有SQL注入风险。动态SQL解析时，含${}的文本节点创建TextSqlNode（标记为动态），含#{}的创建StaticTextSqlNode。

3. where标签的作用？

自动添加WHERE关键字，自动去掉开头的AND/OR。本质是TrimSqlNode的语法糖，等价于<trim prefix="WHERE" prefixOverrides="AND |OR ">。比WHERE 1=1写法更优雅且不影响查询优化。

4. foreach的参数映射原理？

foreach遍历集合时，为每个元素创建子DynamicContext，将item和index变量绑定到上下文。参数名生成规则为__frch_{item}_{index}，这些参数作为附加参数存储在BoundSql中，DefaultParameterHandler优先从附加参数取值。

嵌套查询与延迟加载

嵌套查询的N+1问题

嵌套查询的N+1问题：

  • 查询10条Alert记录 → 每条Alert关联一个Device
  • 无延迟加载：
  • 1条主查询: SELECT * FROM alert_record WHERE …
  • 10条子查询: SELECT * FROM device WHERE id = ?
  • ────────────────────────────────
  • 总计: 11条SQL → N+1问题
  • 有延迟加载：
  • 1条主查询: SELECT * FROM alert_record WHERE …
  • 子查询只在访问device属性时执行
  • 如果不访问device → 只执行1条SQL
  • 配置：
  • mybatis.configuration.lazy-loading-enabled=true
  • mybatis.configuration.aggressive-lazy-loading=false
  • 实际项目建议：
  • 优先使用JOIN替代嵌套查询
  • 只有确实需要延迟加载时才使用嵌套查询

总结

MyBatis动态SQL的本质是SqlNode树+OGNL表达式。实际项目的多条件组合查询需求让我深入理解了动态SQL的设计精妙之处：每个动态标签对应一个SqlNode，执行时递归apply拼接SQL，OGNL表达式做条件判断。where标签自动去AND、set标签自动去逗号、foreach自动遍历集合生成参数映射，这些便利的背后是TrimSqlNode的前缀后缀处理机制和DynamicContext的参数绑定机制。理解了SqlNode体系，动态SQL不再是黑盒，遇到问题可以从SqlNode树的apply过程逐步定位。
