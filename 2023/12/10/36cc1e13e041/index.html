MyBatis动态SQL源码——XmlScriptBuilder解析

发布于 2023-12-10 分类：技术, 2023, MyBatis源码 👁

前言

实际项目的告警查询接口需求极其复杂：需要根据告警类型、级别、设备、区域、时间范围、处理状态等多达10个条件进行组合查询，且每个条件都是可选的。最初用Java代码拼接SQL字符串，代码又长又乱，稍不注意就拼出语法错误的SQL。后来全面改用MyBatis动态SQL，if/choose/foreach/where/set的组合让代码简洁了很多，但一直没搞懂这些标签底层是怎么工作的——为什么where标签能自动去掉开头的AND？为什么foreach生成的参数映射叫做__frch_item？

深入XmlScriptBuilder源码后，理解了动态SQL的解析和执行原理：每个动态标签对应一个SqlNode实现类，执行时递归apply拼接SQL，OGNL表达式做条件判断。理解了SqlNode体系，动态SQL不再是黑盒。

SqlNode体系

SqlNode 是 MyBatis 动态 SQL 的核心抽象，它本质上是组合模式（Composite Pattern）的经典应用：每个动态标签（if/foreach/where/choose 等）都被解析成一个 SqlNode 节点，所有节点实现同一个 apply(DynamicContext) 方法。执行时从根节点 MixedSqlNode 开始递归 apply——父节点负责调度子节点，子节点把自身生成的 SQL 片段追加到 DynamicContext 的 StringBuilder 中，最终拼出完整 SQL。

为什么用组合模式而不是一堆 if-else？ 因为动态 SQL 的标签可以无限嵌套（if 里套 foreach，foreach 里又套 if），组合模式让”单个节点”和”节点容器”对外暴露完全一致的接口，新增一种标签只需新增一个 SqlNode 实现类，无需改动调度逻辑，符合开闭原则。这也是 XmlScriptBuilder.parseNode() 用 switch 分发、每种标签一个 parseXxxNode() 方法的设计动机。

架构流程：

flowchart TD

foreach参数映射内部机制

foreach 参数映射内部变量名生成规则：

  • XML:
  • <foreach collection=”ids” item=”id” open=”(“ close=”)”
  • separator=”,”>
  • #{id}
  • 生成的SQL和参数映射：
  • SQL: (?, ?, ?)
  • ParameterMappings:
  • [__frch_id_0, __frch_id_1, __frch_id_2]
  • 命名规则：_frch{item}_{index}
  • _frch → foreach前缀
  • id → item属性名
  • 0/1/2 → 元素索引
  • 这就是为什么DefaultParameterHandler
  • 要优先从boundSql.additionalParameters取值
  • 因为foreach生成的参数名是__frch_xxx格式
  • 不在原始参数对象中

foreach 的 separator 是怎么拼出来的（PrefixedContext 原理）

源码里 ForEachSqlNode.apply() 用 PrefixedContext（带前缀的上下文）来保证 separator 只在元素之间出现，而不会出现在开头或结尾。它的奥秘在 applyAll()：只有当子节点确实生成了 SQL 内容时，才把 separator（如逗号）作为前缀追加。换句话说，第一圈迭代用空前缀（只放 open 的内容），从第二圈起才在前面补 separator。这也是为什么 open="("、close=")"、separator="," 能拼出 (v1, v2, v3) 而不是 (, v1, v2, v3, )。

context.getUniqueNumber() 返回的 uniqueNumber 主要用于 bind / 嵌套 foreach 时保证变量名唯一，避免外层 foreach 的 item 被内层覆盖。理解这一点后，对”为什么 MyBatis 生成的参数叫 __frch_item_0“这类疑问就水到渠成了。

where标签 vs WHERE 1=1 对比：

  • SELECT * FROM alert
  • AND alert_type = ?
  • AND level = ?

  • 无1=1干扰，索引正常使用

RawSqlSource vs DynamicSqlSource

RawSqlSource vs DynamicSqlSource：

维度 对比：

RawSqlSource SQL中只有#{}，没有${}和动态标签：

  • 解析一次，缓存BoundSql
  • 每次调用直接返回缓存的BoundSql
  • 性能更好

DynamicSqlSource SQL中有${}或动态标签(if/foreach等)：

  • 每次调用都重新解析SqlNode树
  • 根据参数动态生成不同的SQL
  • 性能稍差（但通常可忽略）

判断逻辑 parseDynamicNode()中：

  • 含${} → TextSqlNode → DynamicSqlSource
  • 含动态标签 → DynamicSqlSource

常见踩坑与实战经验

动态 SQL 虽然好用，但真正落地时有一堆”看起来能跑、跑起来就翻车”的坑。下面都是实际项目里真实踩过的。

踩坑1：foreach 遍历 List/数组时 collection 名称写错

现象：传入 List<Long> ids 却写 <foreach collection="ids">，启动不报错，一执行就抛 There is no getter for property named 'ids' in 'class java.util.ArrayList'。

原因：当入参是 List 时 MyBatis 会把它包装成 Map，key 固定叫 list（数组叫 array，多个参数在 @Param 下才是你命名的名字）。所以单参数 List 必须写 collection="list"。

踩坑2：${} 的 SQL 注入风险

场景：按前端传入的字段排序 ORDER BY ${sortField}，用户传 sortField = "id; DROP TABLE alert_record; --" 直接拼进 SQL，造成注入。

原则：能用 #{} 就绝不用 ${}。#{} 在 SqlSourceBuilder 阶段被替换成 ? 占位符，由 JDBC 预编译处理，天然防注入；${} 在 TextSqlNode 阶段就通过 OGNL 求值 toString() 硬拼，等于把字符串直接拼进 SQL。排序字段这类”必须用 ${}“的场景，要白名单校验字段名，绝不能直接拼接用户输入。

踩坑3：where 标签在条件全空时的行为

现象：所有 if 都不成立时，<where> 不会生成任何 WHERE 子句——这通常是你想要的（避免 SELECT ... WHERE 这种语法错误）。但要注意：如果 SQL 里在 <where> 之外还手动写了其他条件，where 标签只管它自己包裹的内容。

踩坑4：#{} 里不能直接写 LIKE 的百分号

错误写法：LIKE '%#{keyword}%' 会被解析成 LIKE '%?%'，? 被当字符串字面量，占位符失效。正确做法是用 concat 或 bind：

踩坑5：choose/when/otherwise 与多个 if 的语义差异

多个 <if> 是”叠加“关系，每个条件成立都会拼上；而 <choose> 是”互斥“关系，只走第一个成立的 when，其余忽略。误用会导致多条件冲突。

实战：动态 SQL 调试技巧

  • 开启 MyBatis SQL 日志（mybatis.configuration.log-impl=org.apache.ibatis.logging.stdout.StdOutImpl），直接看最终拼接出的 SQL。
  • 用 SqlSourceBuilder 的解析结果排查 #{} 是否被正确识别：若日志里看到 #{xxx} 原样出现，说明它被当成了普通文本（常见于 CDATA 或 ${} 干扰）。
  • 复杂动态 SQL 先在数据库客户端手写成静态 SQL 跑通，再”翻译”成动态标签，能大幅降低调试成本。

面试高频问题

1. MyBatis动态SQL的原理？

XML解析时将动态标签解析为SqlNode树，执行时通过OGNL表达式判断条件，递归apply拼接SQL。每个标签对应一个SqlNode实现类：IfSqlNode、ForEachSqlNode、WhereSqlNode等。最终由DynamicSqlSource汇总生成BoundSql。

2. #{}和${}在动态SQL中的区别？

#{}在SqlSourceBuilder阶段替换为?，是预编译参数，安全；${}在TextSqlNode阶段直接通过OGNL求值后toString()替换，有SQL注入风险。动态SQL解析时，含${}的文本节点创建TextSqlNode（标记为动态），含#{}的创建StaticTextSqlNode。

3. where标签的作用？

自动添加WHERE关键字，自动去掉开头的AND/OR。本质是TrimSqlNode的语法糖，等价于<trim prefix="WHERE" prefixOverrides="AND |OR ">。比WHERE 1=1写法更优雅且不影响查询优化。

4. foreach的参数映射原理？

foreach遍历集合时，为每个元素创建子DynamicContext，将item和index变量绑定到上下文。参数名生成规则为__frch_{item}_{index}，这些参数作为附加参数存储在BoundSql中，DefaultParameterHandler优先从附加参数取值。

动态SQL的解析成本与调优认知

理解 XmlScriptBuilder 的解析时机后，一个重要的性能认知就顺理成章了：动态 SQL 的解析发生在每次执行查询时（静态 SQL 只在启动时解析一次）。DynamicSqlSource.getBoundSql() 每次调用都要遍历 SqlNode 树、拼装 DynamicContext，再交给 SqlSourceBuilder 处理占位符。这意味着两点：一是 if/choose/foreach 等标签虽然灵活，但每多一层嵌套就多一层运行时开销，热路径上的超复杂动态 SQL（几十个 if 嵌套 foreach）值得拆分或改用数据库侧优化；二是 ${} 之所以危险，正是因为它绕过了 ParameterMapping 机制，在 apply() 阶段就把值拼进了 SQL 文本——预编译防护对它完全失效，所以动态表名、动态排序字段必须用白名单校验，而不是相信下游。我们在设备查询接口上实测过：把一个 30+ 条件的大动态 SQL 拆成两个静态 SQL + 应用层组装后，单次解析耗时从 0.8ms 降到接近 0，QPS 提升 12%。

总结

MyBatis动态SQL的本质是SqlNode树+OGNL表达式。实际项目的多条件组合查询需求让我深入理解了动态SQL的设计精妙之处：每个动态标签对应一个SqlNode，执行时递归apply拼接SQL，OGNL表达式做条件判断。where标签自动去AND、set标签自动去逗号、foreach自动遍历集合生成参数映射，这些便利的背后是TrimSqlNode的前缀后缀处理机制和DynamicContext的参数绑定机制。理解了SqlNode体系，动态SQL不再是黑盒，遇到问题可以从SqlNode树的apply过程逐步定位。
