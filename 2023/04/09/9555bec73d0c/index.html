Redis过期策略与内存淘汰——数据不会永远存在

发布于 2023-04-09 分类：技术, 2023, Redis 👁

前言

实际项目运行半年后，运维发现Redis内存使用率从2GB持续增长到8GB，最终触发了内存淘汰策略，导致大量设备实时状态数据被误删，监控大屏出现大面积空白。排查发现是大量传感器缓存key没有设置过期时间，导致过期数据永远占着内存。更严重的是，内存淘汰策略配置为volatile-lru，但很多没设过期时间的key也参与了淘汰。2023年深入理解Redis过期策略和内存淘汰机制后，终于能合理规划实际项目的Redis内存使用。本文系统地总结过期策略、淘汰机制和内存优化在实际项目中的实战经验。

定期删除源码分析

Redis定期删除源码分析：

核心函数：server.c / activeExpireCycle()：

  • 入口：serverCron() 每隔 1000/hz 毫秒调用一次
  • activeExpireCycle() 核心逻辑：
    1. 遍历所有数据库（CRON_DBS_PER_CALL=16个）
    1. 对每个数据库：
  • a. 随机抽取 ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP=20 个key
  • b. 检查是否过期，过期则删除
  • c. 统计过期比例
  • d. 如果过期比例 > 25%，重复步骤a
  • e. 如果过期比例 <= 25%，处理下一个数据库
    1. 总执行时间不超过 ACTIVE_EXPIRE_CYCLE_SLOW_TIME_PERC=25% 的
  • 服务器周期时间
  • 关键常量：
  • ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP = 20 // 每次抽查20个key
  • ACTIVE_EXPIRE_CYCLE_FAST_DURATION = 1000 // 快速模式1ms限时
  • ACTIVE_EXPIRE_CYCLE_SLOW_TIME_PERC = 25 // 慢速模式25%时间
  • ACTIVE_EXPIRE_CYCLE_SLOW = 0 // 慢速模式标志
  • 为什么是25%？
  • 如果过期key比例超过25%，说明有大量key过期未被清理
  • 需要继续清理，否则内存会持续增长
  • 如果比例低于25%，说明清理效果良好，可以停下了
  • 智慧矿山调优：
  • hz=10：每秒10次，每次最多20个key，每秒最多200个key
  • hz=20：每秒20次，每次最多20个key，每秒最多400个key
  • 传感器数据5分钟过期，每秒新增约1000条
  • hz=10时：每秒只能清理200条 → 清理速度 < 新增速度 → 内存增长
  • hz=20时：每秒清理400条 → 清理速度接近新增速度 → 内存稳定

LRU算法实现

架构流程：

LRU源码分析

Redis LRU实现源码分析：

Redis对象头结构（server.h / redisObject）：：

  • typedef struct redisObject {
  • unsigned type:4; // 数据类型
  • unsigned encoding:4; // 编码方式
  • unsigned lru:LRU_BITS; // LRU时间戳或LFU计数器(24bit)
  • int refcount; // 引用计数
  • void *ptr; // 数据指针
  • } robj;
  • LRU_BITS = 24，所以lru字段是24位
  • 当用作LRU时：存储的是最后一次访问的时间戳（低24位）
  • 最大表示：2^24秒 ≈ 194天
  • 超过194天的访问时间戳会被截断 → 但不影响LRU排序
  • LRU时间更新时机：
  • lookupKey() → 被任何命令访问时更新
  • obj->lru = LRU_CLOCK() 或 mstime() >> 8
  • 淘汰流程（evict.c / performEvictions）：
    1. 循环直到释放了足够的内存
    1. 每次随机采样 maxmemory-samples 个key
    1. 找出其中lru最小的（最久未访问）
    1. 删除该key，释放内存
    1. 如果仍超过maxmemory，继续循环
  • 智慧矿山优化：
  • maxmemory-samples 从5改为10
  • 采样更多key → 淘汰更精准 → 命中率提高
  • CPU开销增加约0.1ms/次淘汰 → 可接受

面试高频问题

1. Redis的过期策略？

惰性删除+定期删除。惰性删除在访问时检查是否过期，过期则删除返回null；定期删除每100ms随机抽查一批设置了过期时间的key，过期则删除，如果过期比例>25%则继续检查。两者结合保证过期key最终被清理，同时不会消耗过多CPU。实际项目中调大hz参数到20，使定期删除更积极。

为什么不用定时删除？定时删除需要为每个key维护一个定时器，当key数量很大时（百万级），CPU开销极高。Redis选择惰性删除+定期删除的折中方案，在CPU和内存之间取得平衡。

2. Redis的内存淘汰策略？

8种策略。纯缓存推荐allkeys-lru，混合存储推荐volatile-lru，有明显热点推荐allkeys-lfu。LRU是近似实现，随机采样N个key淘汰最久未使用的。实际项目中设备状态缓存用allkeys-lru，告警阈值配置用noeviction。

选择建议：

  • 数据能丢吗？不能→noeviction
  • 所有key都设了TTL？否→allkeys-lru，是→看是否有热点
  • 有明显热点？→allkeys-lfu，否→allkeys-lru

3. LRU和LFU的区别？

LRU淘汰最久未访问的，LFU淘汰访问频率最低的。LRU更适合访问模式均匀的场景，LFU更适合有明确热点的场景。LFU需要维护频率计数器并定期衰减，否则早期热点永远不被淘汰。智慧矿山中，采煤机等核心设备访问频率远高于边缘设备，适合LFU。

底层实现差异：LRU用24bit存储时间戳，LFU用8bit存储对数计数器+16bit存储衰减时间。LRU的近似实现采样maxmemory-samples个key，LFU使用概率递增计数器避免溢出。

4. 为什么Redis不用定时删除？

定时删除需要为每个key维护一个定时器，当key数量很大时（百万级），CPU开销极高。Redis选择惰性删除+定期删除的折中方案，在CPU和内存之间取得平衡。定时删除的时间复杂度是O(1)每次删除，但维护大量定时器的总开销是O(N)。

5. 内存碎片率多少算正常？

1.01.5为正常范围。低于1.0说明RSS小于used_memory（不可能，说明统计有误）。1.52.0偏高，需要关注。大于2.0需要处理，开启activedefrag。实际项目碎片率曾达到2.5，开启自动碎片整理后降到1.2。

碎片产生原因：频繁修改value导致分配的内存块不适合新数据大小；大量删除key导致内存出现空洞；不同数据结构对齐方式不同。

6. 大key怎么处理？

查找：redis-cli –bigkeys。拆分：按区域/类型拆分大Hash。删除：使用UNLINK异步删除。预防：控制单个key的元素数量不超过5000。智慧矿山中10MB的设备历史Hash被拆分为按区域的小Hash。

大key危害：过期删除阻塞Redis（同步删除耗时）；淘汰时占用大量CPU；AOF重写时膨胀；fork时COW内存翻倍。Redis 7.0推荐开启lazyfree-lazy-eviction yes。

7. LFU的计数器为什么不直接+1？

8bit最大值255，如果直接+1，热点key很快到达上限，无法区分热度差异。对数计数器使增长概率随计数器增大而降低：counter小时概率高（快速增长），counter大时概率低（缓慢增长），最终收敛到255。这样既节省了空间（8bit），又能区分不同热度的key。

8. 惰性删除和定期删除的25%阈值怎么来的？

Redis作者antirez在设计时权衡了CPU和内存：如果过期比例低于25%，说明清理效果良好，不需要继续消耗CPU；如果高于25%，说明有大量过期key积压，必须继续清理。25%是一个经验值，在大多数场景下表现良好。实际场景中，传感器数据频繁过期，过期比例经常超过25%，需要调大hz参数让定期删除更积极。

9. Slave上的过期key怎么处理？

Slave不会主动删除过期key，而是等待Master发送DEL命令。这意味着Slave可能短暂返回已过期的数据。智慧矿山中从Slave读取传感器数据时遇到过这个问题，解决方式是关键读操作走Master，或者业务层通过TTL检查数据是否过期。这是Redis为保证主从数据一致性的设计选择。
