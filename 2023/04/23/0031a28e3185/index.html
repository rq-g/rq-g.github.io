Sentinel限流熔断——微服务的流量防护盾

发布于 2023-04-23 分类：技术, 2023, 微服务 👁

前言

在实际场景中，微服务上线后遇到两次大事故：一次是大促期间矿车调度流量洪峰把订单服务打挂，另一次是下游瓦斯预警服务超时导致上游矿车调度服务线程池耗尽。两次事故让我认识到：微服务没有流量防护，就像矿井没有瓦斯监测——迟早出事。Sentinel是阿里开源的流量防护组件，是智慧矿山微服务稳定性的最后一道防线。

为什么需要流量防护

微服务面临的流量问题：

1. 流量突增：

  • 大促/矿车集中调度 → 瞬间流量翻倍 → 服务被打挂
    1. 级联故障
  • 瓦斯预警服务超时 → 矿车调度线程池耗尽 → 链路雪崩
    1. 资源耗尽
  • 慢接口占用线程 → 正常接口无法响应 → 服务假死
    1. 恶意攻击
  • 刷接口、爬虫、DDoS → 资源被恶意占用

源码深挖：滑动窗口 LeapArray

Sentinel 统计 QPS/RT/线程数的核心是 LeapArray（”跳跃数组”）。它把时间轴切成多个固定长度的”采样窗口”（Bucket），例如 1 秒 = 2 个 500ms 窗口：

为什么用滑动窗口而非固定窗口？ 固定窗口在边界处会出现”双倍突发”（如 0.99s 来 100 个、1.01s 又来 100 个，单窗口没超却在 1 秒内实际 200 个）。滑动窗口随时间滚动统计，平滑了边界，限流更精准——这也是面试常问”Sentinel 滑动窗口 vs 固定窗口”的考点。

原理剖析：为什么 Sentinel 比 Hystrix 轻量

Hystrix 用线程池隔离，每次远程调用都丢到独立线程池执行，隔离彻底但线程开销大（上下文切换、线程数膨胀）。Sentinel 用信号量 + 责任链（SlotChain）：请求在主线程通过一串 Slot 完成校验（统计→授权→系统保护→流控→熔断→热点），不切换线程；统计基于 ThreadLocal 的 Context 与无锁 LeapArray，开销极小。代价是 Sentinel 不提供线程池那种”物理隔离”，需配合熔断+降级+限流组合使用。这是两者选型的核心差异。

集群限流

为什么需要集群限流

单机限流 vs 集群限流：

单机限流问题：：

  • 假设限流阈值100 QPS，3个实例
  • 每个实例限33 QPS → 总共99 QPS
  • 但实际流量分布不均：
  • 实例1: 50 QPS → 被限17次
  • 实例2: 30 QPS → 未限
  • 实例3: 20 QPS → 未限
  • 总共只过了80 QPS，浪费了20 QPS的配额
  • 集群限流：
  • 所有实例共享100 QPS配额
  • Token Server统一分配令牌
  • 实际通过 = 100 QPS，精确控制
  • 智慧矿山场景：
  • 矿车调度3节点部署 → 集群限流确保总QPS=100

生产实战与踩坑经验

规则必须持久化，否则重启即丢

Sentinel 默认把规则存在内存，Dashboard 推送的规则重启后全部丢失，服务重启瞬间失去防护。生产环境务必通过 datasource 对接 Nacos/ZooKeeper（见上文配置），并让 Dashboard 也走同一数据源，实现”推拉结合”持久化。智慧矿山所有微服务规则都落在 Nacos 的 ${app}-flow-rules / -degrade-rules 上。

blockHandler / fallback 方法签名三要素

@SentinelResource 的 blockHandler / fallback 方法必须满足：① static 方法；② 返回值与原方法一致；③ 参数列表末尾追加 BlockException（blockHandler）或 Throwable（fallback）。新手常因”非 static”或”漏参数”导致兜底方法不生效，限流时直接抛 BlockException 而非走兜底。

web-context-unify=false 才能用链路限流

spring.cloud.sentinel.web-context-unify=true（默认）会把所有 Servlet 入口收敛成同一个 sentinel_web_servlet_context，导致”链路”模式（按入口资源限流）失效——所有入口被当成同一资源。需要对指定入口限流（如只限 Web 入口、不限 MQ 入口）时，必须设 web-context-unify=false。

热点参数只支持基本类型 / String

ParamFlowSlot 通过 CacheMap 按参数值统计 QPS，参数必须是 String、基本类型或其包装类；传对象会直接不生效。例外项 ParamFlowItem 也只能配 String/int 等可比对的值。

熔断时间窗口别太长

设备服务曾因 timeWindow=300s 熔断后长时间 OPEN，恢复迟钝。熔断是为了”快速失败 + 给下游喘息”，窗口一般设 10~30s，配合 minRequestAmount 与 statIntervalMs 避免小流量误熔断。

限流阈值的容量规划方法：从压测数据到规则值

阈值不是拍脑袋填的数字，生产上它应该是一条推导链的终点。第一步压测单实例容量：固定限流接口关闭 Sentinel，用阶梯加压找出该服务的吞吐拐点（QPS 不再上升、RT 开始陡增的点），比如设备状态查询拐点在 1200 QPS。第二步打折留余量：生产规则取拐点的 60%~70%（约 750 QPS），留出流量毛刺和 GC 停顿的缓冲——限流阈值的意义是”保护余量不被常态流量吃掉”，按 100% 容量配置等于没留防线。第三步区分常态与峰值语义：匀速排队（RateLimiter）适合”下游处理能力固定”的接口（如对接 MQ 的消费出口），直接拒绝适合”用户可重试”的接口（查询类）；同一资源两类规则不要叠加使用，否则排队窗口内的请求会被拒绝规则二次拦截。第四步定期回归：每次大版本发布后重跑压测，容量变了规则跟着改——阈值是”容量模型的一个参数”，容量模型变了参数不变，防线就形同虚设。

限流、熔断、降级的分工：一张响应预案表

很多团队三者的规则值互相抄，出问题才发现语义完全不同。分工可以用一句话锚定：限流是”对外的准入控制”（挡掉多余的），熔断是”对下游的止损”（下游病了先别去打扰），降级是”对自己业务的后路”（核心流程保住，非核心让路）。对应到响应预案：限流触发说明流量超出容量，动作是扩容或调高阈值；熔断触发说明下游故障，动作是排查下游而不是调阈值；降级触发说明本服务在自保，动作是评估降级内容对业务的影响时长。把”触发原因 → 责任人 → 标准动作”写进值班手册，比任何告警阈值都更能缩短故障处理时间。

平台化落地：让 Sentinel 从”各写各的”变成”统一基建”

三个以上服务接入后，散装用法的问题就开始显现：每个服务自己定义 blockHandler、返回格式五花八门、规则命名混乱，值班同学看到限流告警还要先猜是哪个接口的什么规则。平台化的切入点有四个，成本都不高。统一兜底响应体：定义全局 BlockExceptionHandler（Web 入口）+ 统一的 BlockException 处理模板，所有服务的限流响应都是 {"code":429,"msg":"请求过于频繁，请稍后重试"}，前端和调用方只需处理一种格式。规则命名与分组规范：规则资源名强制”服务:接口”格式、Nacos 上的 dataId 强制 ${app}-flow-rules 后缀，跨服务比对规则时不用逐个猜。默认熔断模板：新服务注册时自动下发一套保守的慢调用比例熔断模板（RT 阈值取该服务 P99 的两倍），再按需微调——“先有防线再调优”比”裸奔等出事再配”安全得多。接入度度量：统计各服务的规则覆盖率（有多少对外接口配了限流），覆盖率进周报。Sentinel 的能力上限是它自带的，但用出多少价值取决于这些工程化包装。

热点参数限流：普通限流规则照不到的角落

接口级 QPS 限流有一个盲区：单接口总量没超，但流量高度集中在一个参数值上。设备详情接口总量限流 500 QPS 运行平稳，某天一个设备固件 bug 导致 10 万台终端轮询同一台网关设备的详情，单参数值 3000 QPS 直接把该设备的缓存行打穿、数据库单行查询排队——总量限流完全感知不到这种”参数级热点”。Sentinel 的热点参数限流（ParamFlowRule）正是为此设计的：对资源方法上被 @SentinelResource 标注的参数按值维度限流，且支持参数例外项——比如全局单设备 50 QPS，但给内部运维平台调用的设备 ID 单独放宽到 200。实践中两个细节决定成败：一是热点参数只对基本类型和 String 生效，用对象参数时无法按值限流，接口设计期就要把”会被热点访问的维度”（设备 ID、矿区 ID）提为独立参数；二是规则里的 durationInSec 统计窗口要大于客户端重试间隔，否则会出现”限流窗口内反复触发、恢复瞬间又被打满”的振荡。网关层限流挡的是”总量异常”，热点参数限流挡的是”分布异常”，两层都要有。

面试高频问题

1. Sentinel和Hystrix的区别？

Sentinel支持QPS限流、慢调用熔断、系统保护、可视化控制台；Hystrix只支持异常比例熔断，已停止维护。

2. 熔断器的三种状态？

CLOSED（正常）→ OPEN（熔断，拒绝所有请求）→ HALF-OPEN（探测，放一个请求测试）。探测成功回CLOSED，失败回OPEN。

3. Sentinel规则如何持久化？

默认规则存内存，重启丢失。推荐持久化到Nacos/ZooKeeper，通过datasource配置。实际项目全部持久化到Nacos。

4. blockHandler和fallback的区别？

blockHandler处理限流/熔断异常（BlockException），fallback处理业务异常。两者都配置时限流/熔断优先走blockHandler。

5. Sentinel的滑动窗口算法？

将1秒分为2个500ms的窗口，统计QPS时取所有窗口的值之和。窗口随时间滑动，比固定窗口更平滑，避免边界突发。

6. Sentinel如何实现热点参数限流？

通过ParamFlowSlot + CacheMap统计每个参数值的QPS。需要@SentinelResource注解配合ParamFlowRule，可设置例外项（关键设备更高阈值）。

7. 集群限流和单机限流怎么选？

单实例部署用单机限流即可；多实例部署且对限流精度要求高时用集群限流。集群限流需要部署Token Server，增加运维复杂度。

总结

Sentinel是智慧矿山微服务流量防护的核心组件：流量控制防止流量突增打挂服务，熔断降级防止级联故障，系统保护防止资源耗尽。在实际场景中，矿车调度接口用QPS限流，瓦斯预警接口用慢调用比例熔断，全站用系统保护兜底。记住：没有流量防护的微服务，就像没有瓦斯监测的矿井——跑得越快，出事越惨。
