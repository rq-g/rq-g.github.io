Synchronized与Lock锁——到底用哪个

发布于 2023-04-23 分类：技术, 2023, 并发编程 👁

前言

多线程开发中，锁是最基本的同步工具。早期只知道synchronized，后来发现还有ReentrantLock、ReadWriteLock。到底该用哪个？它们的底层实现有什么区别？2023年系统学习后终于搞清楚了。在实际场景中，我们面临着设备数据并发采集、井下人员定位并发更新、传感器数据实时同步等大量并发场景，锁的选择直接影响系统的稳定性和性能。

或StampedLock：读多写少且临界区极短时，可以在 ReadWriteLock 的基础上再进一步考虑 StampedLock 的乐观读模式——它连读锁都不加，读前后各校验一次版本号，冲突了再退化成悲观读。三种读方案（Synchronized、ReadWriteLock、StampedLock）的本质区别在于”读操作之间要不要互斥”：Synchronized 让读读也互斥，ReadWriteLock 解放了读读，StampedLock 连读锁的开销都省掉了，代价是编程模型更复杂、不可重入。

选型时还有一个经常被忽略的维度：锁的持有者是谁。Synchronized 和 ReentrantLock 锁的是”代码+对象”，天然适用于保护内存状态；而在分布式部署下，本地锁只能保护单个 JVM 内的并发，多实例之间必须靠分布式锁（Redis/Redisson/ZooKeeper）或数据库乐观锁兜底。实践中最常见的架构是”本地锁挡热点、分布式锁保互斥、数据库约束做最终防线”的三层结构，而不是三者取其一。

六、锁的内存语义

这套内存语义在实际开发中有两层含义值得展开。第一层是可见性保证的边界：锁只保证”临界区内的写”对”后续持同一把锁的读”可见，如果一部分代码绕过锁去读共享变量（比如加了 volatile 之外的字段却在锁外直接读），那么 happens-before 链条就断了，读到旧值是合法行为。典型的错误是把配置对象放在锁里初始化、却在定时任务里无锁读取——偶发的”配置没生效”就是这么来的。

第二层是与 volatile 的协作关系。锁的获取/释放语义虽然等价于 volatile，但它只覆盖临界区窗口，粒度比字段级 volatile 粗。经典的双重检查锁（DCL）单例就是一个锁与 volatile 必须配合的例子：synchronized 只能保证其他线程”要么看到完整的实例、要么看不到”，但挡不住半初始化对象引用逸出——构造函数的写与字段赋值的写可能被重排序，另一个线程在锁外判断 instance != null 后直接使用，就会用到未构造完的对象。所以 DCL 中的 instance 必须再叠加 volatile 修饰，用它的禁止重排序语义补上锁覆盖不到的那段窗口。

同理，ConcurrentHashMap 里 val 和 next 用 volatile、而 hash 和 key 用 final，也是锁语义与字段语义分工的范例：桶内链表的并发修改由 synchronized 头节点锁保证，而读路径大部分场景完全无锁，靠的就是这些字段自身的内存语义。理解了这一点，就能回答”为什么有了锁还需要 volatile”——两者是互补关系，不是替代关系。

九、面试高频问题

1. Synchronized和ReentrantLock的区别？

Synchronized是JVM内置锁，自动获取释放；ReentrantLock是API层面的锁，需要手动获取释放。ReentrantLock功能更丰富：可中断、超时、公平锁、多条件。

2. 什么是锁升级？

Synchronized在JDK6后引入锁升级：无锁→偏向锁（单线程）→轻量级锁（CAS自旋）→重量级锁（线程阻塞）。升级不可逆，减少重量级锁的开销。

3. AQS是什么？

AbstractQueuedSynchronizer，JUC锁的底层框架。核心是state变量+CLH双向队列。

4. 为什么Synchronized在JDK6后性能提升了？

锁升级、自旋锁优化、锁消除、锁粗化等JVM层面的优化使得性能接近ReentrantLock。

5. StampedLock与ReadWriteLock的区别？

StampedLock支持乐观读，读操作不阻塞写操作，性能更高。但不支持重入。

十、最佳实践

  1. 简单场景用Synchronized：代码简洁，JVM优化好
  2. 高级功能用ReentrantLock：可中断、超时、公平锁
  3. 读多写少用ReadWriteLock：读读共享提升并发
  4. 极高读并发用StampedLock：乐观读不阻塞写
  5. 永远在finally中释放锁：避免死锁
  6. 锁粒度要细：只锁必要的代码块
  7. 分布式场景加分布式锁：本地锁无法跨JVM

13 分布式场景库存不一致 多节点部署后库存数据不一致 本地锁只能保护单节点并发，跨节点无效 引入Redis分布式锁(Redisson)，配合数据库乐观锁
14 告警缓冲区溢出 告警事件缓冲区满导致事件丢失 生产者速度远大于消费者，缓冲区无上限 使用ReentrantLock+Condition实现有界缓冲区，满时阻塞生产者
15 设备状态缓存写饥饿 设备状态更新延迟严重，缓存数据过期 读多写少场景下ReentrantReadWriteLock默认非公平，读请求不断插队 使用公平模式的ReentrantReadWriteLock(true)，或改用StampedLock

十二、锁的常见误区与反模式

误区一：锁粒度越细越好。 细粒度锁降低竞争的同时也引入了死锁风险和复杂度。曾经在设备状态上报模块见过一个反面案例：每台设备一把锁（Map<String, ReentrantLock>），两台设备联动时需要同时持有两把锁，A 线程先锁设备1再锁设备2，B 线程顺序相反，上线第三天就出现了每 40 分钟一次的线上死锁。修复方案不是加锁排序工具类，而是退一步用”每桶一把锁”（按设备 ID hash 到 16 把锁），竞争没上升多少，死锁从根上消失。锁粒度的下限是”正确性能撑住”，不是”零竞争”。

误区二：用了 ConcurrentHashMap 就不需要锁了。 ConcurrentHashMap 的原子性只到”单个操作”级别，map.get(key) 和 map.put(key, value) 分别原子，但”检查再更新”（check-then-act）组合起来不原子。必须用 compute/merge/putIfAbsent 这类原子复合方法，或者在 lambda 外再套锁。这个误区在扣减库存、限流计数等场景里出现的频率极高。

误区三：只锁写、不锁读。 有人认为读操作天然安全就不加同步，但共享的”写后读”如果不在同一个 happens-before 链上，读到的可能是失效值。正确做法是要么读写都走锁，要么写后通过并发容器/volatile 传递结果，而不是靠”读不加锁应该没事”的直觉。

反模式：锁对象被复用或逃逸。 用 String 字面量做锁对象（字符串常量池全局共享，锁被无关代码意外竞争甚至死锁）、用 Integer 缓存对象做锁（-128~127 缓存导致两把”不同的锁”实为一把）、锁对象被重新赋值（线程 A 锁旧引用、线程 B 锁新引用，互斥失效）。锁对象应当是 private final 的专用字段。

十三、生产选型演进：一个真实模块的三次重构

以设备指令下发模块的演进为例，可以完整看到锁选型如何随业务规模变化。第一版用 synchronized 方法保护”设备连接表”，代码最简单，单实例 2000 台设备时毫无压力——这个阶段选 Synchronized 就是正确的，任何”提前优化”都是负担。

第二版设备规模到了 2 万台，心跳线程和工作线程在连接表上竞争加剧，JMH 压测显示锁等待占了 30% 耗时。此时引入 ReadWriteLock，心跳读连接表、只有断线重连才写，读写比约 20:1，吞吐提升 4 倍。这个阶段的关键决策依据是量化的读写比，而不是”ReadWriteLock 更高级”。

第三版演进为微服务多实例部署，本地锁彻底失效——两台实例各自认为某设备”未分配”，重复下发了调度指令。修复方案是把”分配”这一步的互斥上移到 Redisson 分布式锁，而本地的 ReadWriteLock 保留下来继续保护内存缓存。这次重构的教训是：本地锁保护的永远是”本进程的内存”，业务上的互斥语义必须由能跨进程的原语承担，两者不是替换关系而是分层关系。选型不是一次性的决定，而是随流量规模、部署形态变化的持续过程。

锁升级：JVM 替你做的优化，你理解对了吗

JDK6 的锁升级（无锁 → 偏向锁 → 轻量级锁 → 重量级锁）常被当作面试背诵材料，但它在生产中的实际意义需要澄清三点。第一，升级不可逆：一旦有真实竞争，锁就永久升到重量级，直到对象头重置——所以”预热后竞争消失，锁会变回轻量”是想当然，批量重偏向（bulk rebias）机制只处理 epoch 过期的偏向锁，救不了已膨胀的重量级锁。第二，偏向锁在竞争下的代价是负的：偏向撤销需要等到全局安全点（STW），高竞争场景下频繁的偏向撤销反而制造停顿，这也是 JDK15 直接废弃偏向锁（JEP 374）的原因——硬件和软件环境变了，二十年前有收益的优化如今成了负债。第三，锁升级解释了”为什么 synchronized 不一定慢”：大多数锁实际处于无竞争或低竞争状态，轻量级锁的 CAS 加解锁和 volatile 写的开销接近无锁路径，我们压测过保护 100 微秒级临界区的 synchronized，与 ReentrantLock 的吞吐差距在 5% 以内，远小于传说中”慢一个数量级”。给实践的启示是：选锁时不要用十年前的性能结论，用你的临界区长度和竞争度做当前版本的实测——JVM 在持续进化，去年的经验今年可能就不成立。

tryLock 超时语义：最常见的三个误用

tryLock(timeout, unit) 看似简单，误用率却出奇地高。误用一：超时后资源状态未回滚。获取两把锁的顺序加锁场景，第二把锁超时后代码直接 return false，第一把锁虽然会释放（finally 里有 unlock），但第一把锁保护的业务状态已经被修改了一半——超时路径必须当作异常路径处理，先恢复状态再释放锁。误用二：把 tryLock 当限流用。有人用 tryLock(0) 实现”拿不到就拒绝”，逻辑没错，但忽略了锁是进程内的——多实例部署时每个实例各自持有一份锁对象，”全局同时只有一个任务在跑”的假设在第二个节点上就失效，跨进程互斥请回到 Redis/ZK 分布式锁。误用三：超时值拍脑袋。超时时间应该有业务含义：下游 P99 耗时 200ms 的调用，锁等待给 1 秒意味着极端情况下调用方已经超时、锁还在傻等，正确做法是让锁等待时间与调用方整体超时预算联动（锁等待 ≤ 上游超时 − 下游耗时 − 余量）。tryLock 的本质是把”无限等待”变成”有限等待”的逃生舱，舱门什么时候开，应该由业务 SLA 决定，而不是随手写个 3 秒。

十四、总结

Synchronized和ReentrantLock不是替代关系，而是互补关系。2023年最大的收获是：Synchronized足够简单，ReentrantLock足够灵活，ReadWriteLock适合读多写少。在实际项目中的实战经验告诉我们：根据场景选择合适的锁，而不是一味追求”高级”。简单场景用Synchronized，需要高级功能用ReentrantLock，读多写少用ReadWriteLock，极高读并发用StampedLock。锁的选择没有银弹，只有最合适的方案。

读表结论（比数字本身更重要）：

  1. 低竞争下单线程 Synchronized 甚至比 ReentrantLock 快——偏向锁/轻量级锁下它只是一次 CAS，没有 AQS 队列开销

  4. 高并发下”选哪个锁”的收益远小于”能不能不用锁”——这是这张表最该带走的认知

参数 默认值 说明 智慧矿山建议
-XX:+UseBiasedLocking 开启(JDK15前) 偏向锁 开启
-XX:BiasedLockingStartupDelayMillis 4000 偏向锁启动延迟 0(立即启用)
-XX:+UseSpinning 开启 自旋锁 开启
-XX:PreBlockSpin 10 自旋次数(JDK6前) 默认
-XX:-UseBiasedLocking – 禁用偏向锁 竞争激烈时可禁用
