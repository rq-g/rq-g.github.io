Redis实战——排行榜系统的设计与实现

发布于 2023-04-23 分类：技术, 2023, Redis 👁

前言

实际项目需要实现多种排行榜：设备运行时长榜、班组安全积分榜、物资消耗排行、设备故障率排行。最初用MySQL ORDER BY查询，1000条数据排序耗时500ms，数据量增长到10万后查询超过3秒。2023年用Redis ZSet重构后，排行榜查询从500ms降到5ms，同时支持多时间维度和排名变化趋势。本文系统地总结排行榜系统在实际项目中的设计与实现。

跳表（Skiplist）

  • 元素数量 < 128 且所有元素 < 64字节 → ziplist（压缩列表）
  • 元素数量 >= 128 或任意元素 >= 64字节 → skiplist + dict

跳表源码关键数据结构

ZSet 的底层由 zskiplist（跳表）和 dict（哈希表）共同维护：dict 以 member 为键、score 为值，提供 O(1) 的 ZSCORE；zskiplist 保证有序，提供范围查询与排名。下面是 server.h 中两个核心结构（已简化，指针声明里的 * 是 C 语言解引用而非 Markdown 加粗）：

span 字段是跳表能 O(logN) 算排名的关键：ZRANK 不是去数节点个数，而是从头节点沿 forward 指针前进时，把沿途经过的 span 累加，到达目标节点时累加值就是排名。这意味着排名计算不需要遍历整条链，复杂度与查找同阶。

层数由随机函数决定：新节点的层数按 1/2概率1层、1/4概率2层、1/8概率3层…… 的幂次分布生成，最大层数 32（Redis 5.0+ 提升为 64）。平均层数约 1.33，额外指针开销很小。以智慧矿山 10 万设备排行榜为例，跳表高度约 17 层，ZRANK 只需约 17 次指针比较即可定位，远优于 MySQL 用 B+Tree 做 COUNT(*) 全表扫描。

深度剖析：ZSet 为什么用跳表而不是红黑树

面试高频里已经点过，这里展开”为什么”。从工程权衡角度，Redis 作者 antirez 选择跳表而非红黑树，核心原因有四点：

  1. 范围查询天然有序：排行榜 90% 的操作是 ZRANGE/ZREVRANGE 取一段连续排名，跳表沿 forward 指针顺序遍历即可得到有序结果；红黑树要做中序遍历，且缓存局部性更差。
  2. 实现简单、不易出错：跳表插入只需”找到每层前驱 → 改指针”，红黑树插入后需要多种旋转（LL/LR/RL/RR）来修复平衡，代码复杂度与出 bug 概率都更高。
  3. span 带来排名能力：红黑树没有”跨度”概念，要算排名必须额外维护子树大小；而跳表的 span 让 ZRANK 几乎零成本。
  4. 内存换性能可接受：跳表平均多花约 1.33 倍指针内存，但对 Redis 这种内存换性能的系统完全值得。

代价是跳表比红黑树占更多指针内存，但对”读多写少、要排名、要范围”的排行榜场景，利远大于弊。

实战：排行榜缓存击穿与雪崩防护

排行榜 ZSet 虽然快，但在智慧矿山监控大屏这类高并发读场景下，仍有三类典型风险。这里结合真实踩坑给出可落地的方案。

风险 1：缓存击穿（热点 key 失效瞬间大量请求打到 DB）
监控大屏 TOP 10 是绝对热点，一旦 Redis 主节点抖动导致 key 短暂不可用，瞬时请求会回源 MySQL。解决：本地缓存（Caffeine）兜底 + 互斥重建——只允许一个线程去查 DB 并回填，其余线程短暂等待重试。

风险 2：缓存雪崩（大量 key 同时过期）
若所有日榜 key 都用相同的 expire(7天)，会在第 7 天同一时刻集体失效。解决：过期时间加随机抖动 expire(key, 7天 + random(0,3600)秒)，把失效打散。

风险 3：热点成员频繁更新导致单 key 写入瓶颈
设备运行时长榜每秒 ZINCRBY 上千次，单 key 写入成为瓶颈。解决：按设备 ID 哈希做多 key 分片（如 rank:runtime:shard:{hash%16}），读取时 ZUNIONSTORE 聚合，把写压力分摊到多个 key。

这三招（本地兜底+互斥重建、过期抖动、分片）是排行榜上线前必须做好的防护。

面试高频问题

1. Redis实现排行榜用什么数据结构？

ZSet（有序集合）。元素唯一（member），按分数排序（score），支持增减分数（ZINCRBY O(logN)）、范围查询（ZRANGE O(logN+M)）、排名查询（ZRANK O(logN)）。实际项目中所有排行榜都用ZSet实现。底层使用跳表+字典，跳表保证有序性，字典保证O(1)查分数。

2. 如何实现多时间维度的排行榜？

不同时间维度用不同的key（日榜、周榜、月榜、总榜），通过ZUNIONSTORE合并日榜到周榜/月榜。日榜设置过期时间自动清理历史数据。智慧矿山中每天凌晨定时合并榜单。大数据量时用Pipeline批量ZINCRBY代替ZUNIONSTORE避免阻塞Redis。

3. 排行榜数据量很大怎么办？

只缓存TOP N，排名靠后的从数据库查询近似排名。使用时间衰减策略淘汰冷数据。智慧矿山中百万级设备排行只缓存前1万名，其他从MySQL查询。还可以使用多级缓存（Caffeine本地缓存+Redis+MySQL）减轻Redis压力。

4. ZSet底层为什么用跳表而不是红黑树？

跳表范围查询天然有序（沿链表遍历），红黑树需要中序遍历；跳表实现简单，插入只需修改相邻节点指针，红黑树需要旋转操作；跳表并发友好，锁粒度更小；跳表通过span字段可以O(logN)计算排名。Redis作者antirez认为跳表代码更简洁，性能相当。

5. 如何保证排行榜数据与数据库一致？

先更新MySQL再更新Redis（推荐），配合定时校验补偿。关键业务需要实时一致性用同步双写，非关键业务可以异步同步。智慧矿山每天凌晨3点校验排行榜一致性，修正Redis与MySQL的差异。

6. ZUNIONSTORE合并大ZSet阻塞Redis怎么办？

三种方案：1) 低峰期执行合并任务；2) 用Pipeline批量ZINCRBY代替ZUNIONSTORE，逐条更新不阻塞主线程；3) 只合并增量数据而非全量合并。智慧矿山使用Pipeline方式，合并10万元素耗时约50ms且不阻塞Redis。

7. 排行榜分页查询如何保证一致性？

问题：查询期间有ZINCRBY更新 → 分页跨页数据不一致。方案：1) 缓存查询结果，短时间内返回相同数据；2) 使用ZREVRANGEBYSCORE按分数范围分页，而非按排名分页；3) 客户端允许最终一致性。智慧矿山监控大屏使用10秒本地缓存，保证同一屏数据一致。
