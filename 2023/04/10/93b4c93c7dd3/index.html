AQS源码分析——并发工具的基石

发布于 2023-04-10 分类：技术, 2023, 并发编程 👁

前言

在实际场景中，AQS（AbstractQueuedSynchronizer）几乎渗透到了每一个并发场景——矿车调度系统的互斥访问用 ReentrantLock，设备状态变更的限流用 Semaphore，多传感器数据汇聚的等待用 CountDownLatch，井下人员定位的读写分离用 ReentrantReadWriteLock。2023年之前只知道 AQS 是”抽象队列同步器”，完全不清楚内部运作机制。一旦遇到锁超时、队列出错、线程饥饿等线上问题，排查基本靠猜。2023年决定啃透 AQS 源码，系统理解 volatile state + CLH 队列 + CAS + park/unpark 这套统一设计范式，之后在生产中排错和选型才真正有了底气。

AQS 架构总览

AQS 是 JUC（java.util.concurrent）并发包的底层框架，提供了一套通用的同步状态管理机制。ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock 等工具全部基于 AQS 实现，区别仅在于 state 的语义和 tryAcquire/tryRelease 的具体逻辑。

面试高频问题深度解析

1. AQS 的原理是什么？

AQS 通过 volatile int state + CLH 双向等待队列实现同步。state 表示同步状态，由 volatile 保证可见性、CAS 保证原子性。队列存放等待获取同步状态的线程。AQS 定义了 acquire/release 等模板流程，子类只需实现 tryAcquire/tryRelease 即可定义自己的同步语义。

2. AQS 为什么用 volatile state 而不是 AtomicInteger？

3. 公平锁和非公平锁的实现区别？

公平锁在 tryAcquire 中先检查 hasQueuedPredecessors()，队列有等待线程就不插队。非公平锁直接 CAS 竞争 state，允许插队。非公平锁吞吐量更高（减少上下文切换），但可能导致线程饥饿。

4. 独占模式和共享模式的区别？

独占模式同一时刻只有一个线程获取（ReentrantLock），共享模式允许多个线程同时获取（Semaphore、CountDownLatch）。共享模式获取成功后会通过 setHeadAndPropagate 传播唤醒后续共享节点，这是与独占模式最核心的区别。

5. 为什么 unparkSuccessor 从尾部向前遍历？

因为 addWaiter 中入队操作不是原子的：先设置 node.prev，再 CAS 设置 tail，最后设置 pred.next。从 head 向后遍历可能遇到 next 还未设置的情况。而从 tail 向前遍历，prev 是最先设置的，一定能遍历到所有节点。

总结

AQS 是 JUC 并发包的基石。深入源码后，核心认知是：AQS = volatile state + CLH 队列 + CAS + park/unpark。

  • volatile state：同步状态的唯一载体，不同工具赋予不同语义
  • CLH 队列：FIFO 双向等待队列，保证公平性，每个节点通过 waitStatus 协调唤醒
  • CAS：无锁竞争 state，失败后入队等待，避免忙等待浪费 CPU
  • park/unpark：精确的线程阻塞/唤醒机制，比 Object.wait/notify 更灵活
  • 模板方法模式：AQS 定义 acquire/release 流程，子类实现 tryAcquire/tryRelease 语义
  • 共享模式传播唤醒：setHeadAndPropagate 保证剩余资源被充分利用

理解了 AQS，ReentrantLock、Semaphore、CountDownLatch、ReentrantReadWriteLock 的原理就都通了——它们只是 AQS state 语义和 tryAcquire/tryRelease 实现的不同组合。掌握 AQS 不仅能应对面试，更能帮助我们在生产环境中正确使用并发工具，避免死锁、饥饿、超时等问题，并在需要时自定义同步器实现特殊的并发控制逻辑。

在实际场景中，正是基于对 AQS 的深入理解，我们才能针对矿车调度（ReentrantLock 公平锁）、传感器数据汇聚（CountDownLatch 超时等待）、设备状态限流（Semaphore）、告警配置读写分离（ReentrantReadWriteLock）等场景做出正确的选型和排错。
