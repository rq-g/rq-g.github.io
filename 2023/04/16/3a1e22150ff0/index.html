Redis集群方案——主从、哨兵与Cluster

发布于 2023-04-16 分类：技术, 2023, Redis 👁

前言

实际项目初期用单机Redis，一次服务器宕机导致整个监控系统不可用2小时。之后部署了主从复制，但Master故障需要手动切换，又出了一次40分钟的故障。接着上了哨兵模式实现自动故障转移，但数据量增长到15GB后单Master写性能不足。最终迁移到Redis Cluster分片集群，3主3从架构，支撑了2000+台设备的数据读写。本文系统地总结主从复制、哨兵、Cluster三种方案在实际项目中的演进和实战经验。

主从复制的问题

主从复制的三大问题：

1. Master故障需要手动切换：

  • 智慧矿山事故：凌晨3点Master宕机
  • 运维手动切换Slave为Master，耗时40分钟
  • 还需要通知所有客户端修改连接地址
    1. Master单点写入，无法水平扩展
  • 智慧矿山2000台设备同时上报数据
  • 单Master写QPS约5万，接近上限
  • 无法通过增加Master分摊写入压力
    1. 全量复制时Master压力大
  • 15GB数据全量复制 → Master bgsave 1秒
  • 期间所有写操作缓冲在复制缓冲区
  • 缓冲区可能溢出 → 再次全量复制 → 恶性循环
  • 解决：哨兵模式 → 解决问题1
  • Redis Cluster → 解决问题1+2+3

故障转移流程

哨兵故障转移完整流程：

1. 主观下线（SDOWN）：

  • Sentinel1 ping Master → 超时未响应
  • → 标记Master为SDOWN
    1. 客观下线（ODOWN）
  • 超过quorum个Sentinel认为Master下线
  • → 标记ODOWN → 触发故障转移
  • quorum=2 → 至少2个Sentinel同意才转移
    1. 选举Leader Sentinel
  • Sentinel之间通过Raft算法选举Leader
  • Leader负责执行故障转移
    1. 选举新Master
  • 规则（优先级从高到低）：
  • a. 排除下线的Slave
  • b. 排除最近5秒未响应的Slave
  • c. 优先选replication-offset最大的（数据最新）
  • d. runId最小的
    1. 执行故障转移
  • a. Leader对新Master执行 SLAVEOF NO ONE
  • b. 通知其他Slave复制新Master
  • c. 更新Sentinel的Master配置
  • d. 通知客户端新Master地址
  • 智慧矿山实测：
  • 故障检测：30秒（down-after-milliseconds）
  • 选举+转移：5秒
  • 总计不可用时间：约35秒

Sentinel Raft选举源码分析

  • 每次故障转移，configEpoch+1
  • configEpoch大的Sentinel优先成为Leader
  • 保证同一时间只有一个Leader执行故障转移
  • 保证同一时间只有一个Sentinel执行故障转移
  • 避免多个Sentinel同时选举新Master导致脑裂
  • configEpoch机制保证了选举结果的全局一致性

Cluster的MOVED/ASK重定向

MOVED vs ASK重定向：

MOVED：slot已永久迁移到新节点：

  • 客户端请求Master1 → slot不在 → MOVED slot newMaster
  • 客户端缓存新路由 → 后续请求直接路由到新节点
  • ASK：slot正在迁移中，临时路由
  • 客户端请求Master1 → slot正在迁移 → ASK slot newMaster
  • 客户端不缓存路由 → 下次可能回到原节点
  • 智慧矿山迁移经验：
  • 扩容时迁移slot → ASK重定向频繁
  • 迁移完成 → MOVED重定向，客户端更新路由缓存
  • 迁移期间少量请求延迟增加（重定向开销）

选型的真实决策点：什么时候从哨兵升级到 Cluster

这张表容易让人得出”Cluster 全面胜出”的结论，实际上哨兵到 Cluster 的升级是一次伤筋动骨的迁移，不能因为”以后可能数据量大”就提前上 Cluster。升级信号有三个，同时满足才值得动手：其一，写容量——单实例写入持续超过实例规格的 60%（哨兵只解决读扩展和高可用，写永远单点）；其二，内存规模——数据量逼近单实例经济规格上限（约 30~50GB，再大 bgsave 的 fork/COW 开销和恢复时长都难以接受）；其三，key 布局——业务能把关联 key 收拢进 hash tag（{order:1001}:info 与 {order:1001}:items 同槽），多 key 操作和 Lua 才有出路，这个改造往往比部署 Cluster 本身更费劲。

反过来，数据量在 10GB 以内、写 QPS 压得住的场景，哨兵是最优解：架构简单、运维心智负担低、Pipeline/事务/Lua 全功能可用。我们平台的演进路径是”主从 → 哨兵（2年）→ 设备时序数据引入 Cluster（只把时序库迁过去）”，核心配置和库存数据始终留在哨兵集群——混合部署让每类数据用最适合的架构，比一刀切更务实。

故障演练：把”切换能用”变成”切换验证过”

监控解决”知道出事”，故障演练解决”出事后确定能活”。生产集群上线前必须做三类演练，并且把实测时序写进运维手册。演练一：杀 Master。kill -9 主库进程，验证哨兵在 down-after-milliseconds + 选举 + 切换的总时长（我们实测 35 秒），同时观察客户端行为——Jedis/Lettuce 会收到连接错误并重连新 Master，但要确认读写分离的从库路由在切换后不会把写打到旧 Master（旧 Master 降级为从库后是有只读保护的，但客户端缓存的路由表有刷新窗口）。演练二：网络分区。用 iptables 掐断 Master 与哨兵的通信但保留 Master 与应用的通信，验证脑裂防护——旧 Master 在发现”自己不再是 Master”后会降级拒绝写，关键配置是 min-replicas-to-write 1 + min-replicas-max-lag 10，宁可拒绝写入也不接受脑裂数据分叉。演练三：全节点重启。模拟机房断电，验证 Cluster 模式下”多数 Master 同时缺席”时的表现——slot 不完整集群进入 FAIL 状态，此时唯一手段是 cluster-restore 或尽快拉起节点，所以任何一个 Cluster 都必须有快照/RDB 备份的异机副本，这是演练三给出的最重要结论。

演练的产出不是”演练通过”四个字，而是三份带时间线的记录：检测耗时、切换耗时、客户端恢复耗时。这三段时长加起来，才是业务方真正感知到的故障持续时间——把这个数字交给上游服务做超时和重试参数设计，比拍脑袋配 30 秒超时科学得多。

从主从到Cluster：一次真实的演进复盘

我们的设备遥测缓存最初是单机 + 主从，日活设备不到 5000 台时毫无压力。随着接入设备突破 3 万，两个问题先后爆发：一是写 QPS 逼近单机上限（每台设备 2 秒上报一次状态，叠加告警写入），主从架构写无法扩展；二是内存接近 maxmemory，淘汰策略开始清掉热数据。当时的演进决策值得复盘：先上哨兵解决了”主库挂了要半夜人工切换”的可用性问题，但写瓶颈依旧；最终迁 Cluster 的关键是按 device:{deviceId} 设计 hash tag，把同一设备的遥测、状态、告警键落到同一 slot，跨 slot 的事务和 Lua 需求全部消除。这段经历说明：架构选型不必一步到位，但数据键的设计要为下一步演进预留空间——如果一开始键名就带 hash tag，迁移成本会低得多。

面试高频问题

1. Redis集群方案有哪些？

主从复制（数据备份+读写分离）、哨兵（监控+自动故障转移）、Cluster（分片+高可用）。生产环境推荐哨兵或Cluster。智慧矿山从主从演进到哨兵再到Cluster。选择依据：数据量<6GB用哨兵，>6GB用Cluster。

2. 哨兵的故障转移流程？

主观下线(SDOWN)→客观下线(ODOWN)→选举Leader Sentinel(Raft算法)→选举新Master(数据最新的优先)→执行故障转移→通知客户端。智慧矿山实测故障转移约35秒。关键配置：down-after-milliseconds决定检测速度，parallel-syncs控制切换后复制压力。

3. Cluster的slot机制？

16384个slot分配给Master节点，key通过CRC16(key)%16384计算slot，路由到对应Master。支持hash tag让相关key在同一slot。扩缩容通过迁移slot实现。智慧矿山3主架构每Master约5461个slot。

4. 主从复制数据一致性如何保证？

Redis采用异步复制，Master写入后立即返回客户端，后台线程将命令异步发送给Slave。这意味着Master宕机时，未复制到Slave的数据可能丢失。解决方案：配置min-replicas-to-write 1，确保至少1个Slave才能写入；但会降低可用性。智慧矿山对关键数据（告警记录）同时写入MySQL做兜底。

5. Cluster和Sentinel能一起用吗？

不需要也不推荐。Cluster自带故障转移机制，不依赖Sentinel。Cluster中Slave通过Gossip协议检测Master故障并自动选举新Master。Sentinel是主从模式的高可用方案，两者设计理念不同，混合使用会增加复杂度。

6. 为什么Cluster用16384个slot而不是65536？

Redis作者antirez的解释：1) Gossip消息中携带的slot bitmap，16384个slot只需2KB，65536需要8KB，Gossip消息越小心跳开销越小；2) 集群节点数通常不超过1000个，16384个slot足够均匀分配；3) slot数越少，客户端的slot映射表越小，内存开销更低。

7. Cluster扩缩容对服务有什么影响？

扩容：迁移slot期间，部分请求会收到ASK重定向（临时路由），延迟略有增加；迁移完成后，客户端收到MOVED重定向，更新本地路由缓存。缩容：需要先迁移走slot再删除节点。智慧矿山在凌晨低峰期执行扩缩容，每次迁移不超过2000个slot。

8. 什么是PSYNC2？

Redis 4.0引入的增强版复制协议。核心改进是引入replid2和second_replid_offset，使得故障转移后新Master也能接受旧Slave的部分复制请求，而不是强制全量复制。智慧矿山在升级到PSYNC2后，故障转移的同步时间从分钟级降到秒级。
