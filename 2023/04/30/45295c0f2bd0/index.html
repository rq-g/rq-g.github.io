Redis Pipeline与Lua脚本——批量操作与原子性

发布于 2023-04-30 分类：技术, 2023, Redis 👁

前言

实际场景中，井下设备实时数据采集频率极高，每秒产生上千条传感器读数需要批量写入Redis。最初逐条执行SET命令，1000条数据写入耗时超过800ms，严重拖慢了数据采集链路。引入Pipeline后批量写入耗时降至15ms，性能提升50倍以上。但Pipeline不保证原子性——在设备告警判定场景中，需要先读取阈值再比较再写入告警记录，三步操作必须原子执行，Pipeline无法满足。最终用Lua脚本解决了原子性问题。本文系统地总结Pipeline和Lua脚本在实际项目中的实战经验。

Pipeline——批量操作减少网络往返

    end
    subgraph Pipeline["Pipeline：1000条 = 1次RTT"]

    end

逐条模式的时间成本是”1000 × (RTT + 处理时间)”，Pipeline把它压成”1 × RTT + 1000 × 处理时间”——当处理时间是微秒级、RTT是毫秒级时，性能差距就是两个数量级。

Pipeline原理深入

Pipeline 快的本质是把 N 次网络往返压缩成 1 次。逐条模式下每条命令的生命周期是”发请求 → 等回复 → 发下一条”，等待时间 = 网络RTT + Redis处理时间，其中RTT占大头（内网0.5~1ms，跨机房可达几十ms）。Pipeline 模式下客户端把命令写入发送缓冲区一次性刷出，服务端按顺序执行后把所有回复打包返回——1000条命令只承担1次RTT。

两个容易被忽略的底层细节：

  1. Redis服务端不需要任何特殊支持。Pipeline 纯粹是客户端行为：命令流进来照常逐条执行，只是回复被攒着一次性写回 socket。所以任何版本的 Redis 都支持 Pipeline。
  2. 客户端要缓存所有回复。服务端执行完的回复会进入客户端的接收缓冲区，如果一次 Pipeline 塞了10万条命令，回复会把客户端内存撑爆，甚至拖累服务端的输出缓冲区（client-output-buffer-limit）。每批控制在500~1000条，分批执行，是实践中稳妥的上限。

Pipeline注意事项与踩坑

  1. Pipeline不保证原子性：执行期间其他客户端的命令可能穿插进来。上面例子中客户端B的 SET k2 完全可能插在A的两次写之间。需要原子性时必须换Lua。

  2. 批量大小要克制：曾经一次塞10万条命令，客户端回复缓冲区直接OOM。实践值：500~1000条/批，配合 Lists.partition() 分批。

  3. Cluster模式下按slot分组：Pipeline 里的命令如果散布在不同slot，Jedis/Lettuce 会自动按节点拆分多次发送——批量性能会退化为”每节点一次RTT”。生产上先按 CRC16(key) % 16384 分组再分别Pipeline，效果更可控。

  4. 事务包裹与Pipeline的关系：executePipelined 里如果用 MULTI/EXEC 包裹，就同时获得了打包发送和原子性（SessionCallback 的用法），但吞吐不如纯Pipeline，按需取舍。

  5. 异常语义：Pipeline 中某条命令失败（如对String执行LPUSH），回复列表里对应位置是 RedisSystemException，其他命令照常执行。要逐条检查回复，不能假设全部成功。

批量大小的量化方法：从缓冲区原理推导，而不是背经验值

“500~1000条/批”这个经验值背后是可以推导的原理，理解推导过程才能在自己的场景里算出合适的值。客户端命令请求进入 Redis 后有两道缓冲：查询缓冲区（query buffer，存放还没执行的请求内容）和输出缓冲区（output buffer，存放还没发给客户端的回复）。Pipeline 的 N 条命令会同时占用这两道缓冲——命令本身占查询缓冲区，每条命令的回复占输出缓冲区。client-output-buffer-limit normal 默认 0（不限制），client-query-buffer 默认 1GB，所以 10 万条命令塞进来不会立刻报错，而是慢慢把服务端内存吃穿，最后 OOM 的是 Redis 进程——这比客户端 OOM 危险得多。

推导公式：单批命令总字节数 ≤ 预期 Redis 可容忍的瞬时内存增量。比如命令平均 60 字节、回复平均 20 字节，1000 条一批的瞬时占用约 80KB，1000 批并发就是 80MB——对 8GB 实例无压力，对 512MB 小实例就要降到 200 条/批。再叠加 RTT 收益递减：批从 100 加到 1000，QPS 线性提升；从 1000 加到 10000，QPS 基本不动（瓶颈已从 RTT 转移到服务端单线程执行），风险却翻十倍。批量优化的终点是”RTT 开销不再是瓶颈”，而不是”批越大越好”，压测时盯 QPS 曲线的拐点就够了。

Lua脚本——原子操作的利器

为什么需要Lua

回到开头的告警场景：先 GET 阈值、再比较、再写告警记录，三步之间有时间窗。线程A刚读完阈值还没写入，线程B也读到了同一个阈值，两边都判定需要告警、都写入了记录——重复告警。Pipeline 解决不了这个问题，因为它只是”打包发送”，命令之间照样穿插其他客户端的操作。

Lua 脚本的原子性来自 Redis 的执行模型：Redis 是单线程事件循环，Lua 脚本作为一条”命令”整体执行，执行期间事件循环不会切出去处理其他客户端。也就是说脚本执行期间，其他客户端的请求要么排队等待，要么超时——这就是原子性的代价，也是”脚本不能太长”警告的来源。

原子性的边界：Lua 能保证什么、不能保证什么

原子性这个词在 Lua 语境下有两条精确的边界，划不清就会埋雷。边界一：原子 ≠ 事务。脚本执行中途出错时，已经执行的写命令不会回滚——Redis 没有 undo log，脚本原子性的含义是”中间状态不被其他客户端看到”，而不是”要么全做要么不做”。所以脚本内部必须自己保证逻辑顺序：先判断后写入（像限流脚本那样），把可能失败的判断放在写操作之前，而不是写完再补救。

边界二：原子性挡不住”脚本太慢”。一个循环十万次的 Lua 脚本会把 Redis 主线程锁死几秒甚至几十秒，期间所有请求（包括其他库的读写）全部超时——这比不原子严重得多，等于把 Redis 打挂。三个工程约束：脚本复杂度控制在 O(1) 或小 O(n)（n 是 KEYS 数量级，不是数据量级）；禁止在脚本里写无界循环；用 SCRIPT KILL 兜底时要知道它只能杀”还没执行过写命令”的脚本，一旦写过就只能 SHUTDOWN NOSAVE——这个不对称性决定了脚本上线前必须压测。

边界的延伸：脚本与集群的 key 约束。Cluster 模式要求脚本访问的所有 key 落在同一个 slot（或用 hash tag {user1001} 强制同槽），否则直接报错。这个约束的本质还是”单线程执行”——脚本原子性由单点执行保证，跨节点的 key 无法在单线程里原子处理。所以设计 Lua 方案时第一步永远是画 key 布局：哪些 key 要一起原子操作、它们的 hash tag 怎么设计，这比脚本本身的编码重要得多。

Pipeline 批次大小：一个必须实测的参数

“Pipeline 能提速”人人都知道，但单批多少条最合适没有万能答案，只有实测出来的工程参数。批次太小的极端是每批 1 条，退化成逐条请求，优化归零；批次太大有两个天花板：客户端内存（回复对象全部堆积在内存里等业务消费，10 万条的批次可能堆积几百 MB）和服务端输出缓冲区（client-output-buffer-limit 对普通客户端默认无限制但 client-output-buffer-limit normal 0 0 0 配置因版本而异，超限会断连）。我们的经验起点是 500~1000 条/批，配合两层调优：一是按 RTT 与命令大小估算——单命令 100 字节、RTT 2ms 的链路，1000 条批次的传输时间约 0.1s，加上服务端执行时间，批次内耗时可控；二是观察 p99 而不是平均值——大批次拉长的是尾延迟，平均值好看但 p99 飙升意味着其他请求在该批次执行期间排队，对延迟敏感的在线业务应该压小批次（200 条以内），离线批量任务才敢开大批次。最后提醒一个集群模式的隐藏变化：Cluster 会按 slot 把 Pipeline 命令拆分到不同节点，客户端自行分组的实现质量参差不齐，升级客户端库后务必重新压测 Pipeline 行为，我们在 Lettuce 升级后遇到过批次被静默拆散、吞吐下降 40% 的案例。

Lua脚本在生产环境的注意事项

  1. 脚本不能太长：默认超时 lua-time-limit 5000ms。超时后 Redis 进入阻塞状态，其他客户端只能收到 BUSY 错误，此时只有两个选择：SCRIPT KILL（脚本还没执行过写命令时可用）或 SHUTDOWN NOSAVE（已写过数据，只能重启）。所以上线前必须压测脚本耗时。

  2. 不能有死循环：while true do end 会让 Redis 完全不可用。Lua 没有强制中断机制，唯一的防线是代码评审 + 上线前压测。

  3. KEYS 参数必须传入所有操作的 key：Cluster 环境下，Redis 根据 KEYS 参数路由到对应节点，所有 key 必须落在同一个 slot（可用 hash tag {} 保证）。

  1. 善用脚本缓存：EVAL 每次传输完整脚本内容，有网络开销；EVALSHA 只传 SHA1 摘要。Spring Data Redis 内部自动先试 EVALSHA、收到 NOSCRIPT 错误再降级 EVAL，无需手动处理。

  2. 返回值类型匹配：Lua number → Java Long；Lua string → Java String；Lua table → Java List；Lua false → Java null。DefaultRedisScript 必须指定正确的 resultType，否则会出现 ClassCastException。

  3. 脚本版本管理：复杂脚本放 resources/scripts/ 目录并用 Git 管控。修改脚本后 SHA1 变化，Spring 的 ScriptSource 方案会自动重传；直接用 SHA 缓存的方案要注意清理（SCRIPT FLUSH 会清空所有脚本缓存，慎用）。

Lua 脚本的演进治理：从脚本散落到统一仓库

Lua 脚本用得多了，治理问题就浮出水面。第一个坑是脚本缓存失效：Redis 重启（非持久化脚本缓存）或 SCRIPT FLUSH 后，EVALSHA 会报 NOSCRIPT 错误，写死 EVALSHA 的代码直接崩溃——正确姿势是”先 EVALSHA、捕获 NOSCRIPT 降级 EVAL 重发”的重试模式，Spring Data Redis 的 DefaultRedisScript 内部已实现该逻辑，但很多人为了”性能”绕开它手写 EVALSHA，等于埋雷。第二个坑是脚本版本漂移：同一个业务脚本在三个服务里各自复制了一份，某次修 bug 只改了两处，第三处的旧逻辑悄悄错了半年。我们的治理方案是把所有 Lua 脚本收进独立的脚本仓库（Git 管理 + CI 校验语法 + 发版时统一推送），业务代码只引用”脚本名 + 版本号”，运行期通过统一封装加载。第三个坑是幂等与重试的交互：网络超时后客户端重发 EVAL，脚本已执行过一次的话，非幂等脚本（INCR、RPUSH）会重复生效——写脚本时就要设计幂等（用 SETNX 做执行标记、用 Lua 内部的去重键），或者像分布式锁那样接受”释放操作必须幂等”的约束。脚本是把双刃剑：它给了你在数据侧编程的能力，也就要求你用工程化方式管理这些”分布式的存储过程”。

面试高频问题

1. Pipeline和Lua脚本的区别？

Pipeline减少网络往返但不保证原子性，命令之间可能穿插其他客户端的操作。Lua脚本原子执行但脚本不能太长（默认5秒超时）。批量读写用Pipeline，原子操作用Lua。在实际场景中，传感器数据批量写入用Pipeline，告警去重和锁释放用Lua。

2. 为什么Lua脚本是原子的？

Redis是单线程执行命令的，Lua脚本作为一个整体被执行，执行期间不会处理其他客户端的命令。这是由Redis的事件循环机制保证的——执行Lua脚本期间，不会返回事件循环去处理其他请求。

3. Lua脚本有什么限制？

脚本不能太长（默认5秒超时，由lua-time-limit配置）；不能有死循环；KEYS参数必须传入所有操作的key（集群环境下必须，方便节点路由）；脚本中的操作不应该太耗时，否则会阻塞Redis。

4. Pipeline的批量大小怎么确定？

建议每批500-1000条。批量太大会阻塞Redis（单线程执行，其他客户端请求排队）；批量太小网络优化效果不明显。实际需要根据命令复杂度和Redis负载测试确定最佳值。
