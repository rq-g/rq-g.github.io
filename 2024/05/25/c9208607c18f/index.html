SkyWalking全链路监控——分布式系统的可观测性

发布于 2024-05-25 分类：技术, 2024, 高可用 👁

前言

微服务上线后最头疼的问题：用户反馈下单失败，但不知道是哪个服务出了问题。日志散落在十几个服务中，排查一个问题要登录多台服务器grep。在实际场景中，井下设备数据采集涉及设备服务、告警服务、数据服务、网关等十多个微服务，一个设备告警从触发到通知的链路可能跨越6个服务，任何一个节点出问题都可能导致安全告警延迟——这在矿山场景下是不可接受的。引入SkyWalking后，一个请求经过的所有服务、每个节点的耗时、错误信息一目了然，排查时间从小时级降到分钟级。

8.2 采样策略优化

开发/测试环境：：

  • agent.sample_n_per_3_secs = -1 （全量采集，方便调试）
  • 生产环境（推荐）：
  • agent.sample_n_per_3_secs = 3 （每3秒采集3条Trace）
  • → QPS=1000时，采样率约 3/(1000*3) = 0.1%
  • → 依然能发现P99慢请求（慢请求不会被采样遗漏）
  • 生产环境（高危场景强制采样）：
  • → 错误Trace强制采样（SkyWalking默认行为）
  • → 慢Trace强制采样（超4秒默认记录）
  • → 关键接口使用 @Trace 强制创建Span
  • 采样率与ES存储的关系：
  • 12个服务 × 3实例 = 36个Agent
  • 全量采集：36 × ~100 Trace/s = 3600 Trace/s → ES日增 ~50GB
  • 采样率3：36 × 1 Trace/s = 36 Trace/s → ES日增 ~0.5GB

8.3 降低开销的方法

优化手段 配置 效果 风险
调整采样率 sample_n_per_3_secs=3 减少Trace数量，降低ES写入压力 可能遗漏部分Trace
忽略低价值URL trace.ignore_path=/health,/actuator/** 减少无意义的Span 可能遗漏健康检查异常
限制Span数量 trace.span_limit=300 防止单条Trace过大 超出部分被截断
关闭SQL参数追踪 plugin.mysql.trace_sql_parameters=false 减少Span Tag大小 无法看到SQL参数值
关闭Redis参数追踪 plugin.jedis.trace_redis_parameters=false 减少Span Tag大小 无法看到Redis key
使用Kafka中转 Agent → Kafka → OAP 解耦Agent和OAP，削峰 增加Kafka依赖
异步上报 Agent默认异步gRPC 不阻塞业务线程 gRPC队列满时丢弃
ES分片优化 index_shards=3, replicas=1 提高ES写入吞吐 增加ES存储开销

十三、常见项目问题与解决方案

基于实际项目线上运维经验，总结以下15个常见问题：

# 问题 现象 原因 解决方案
1 Agent无法连接OAP 应用启动日志报Channel is inactive，SkyWalking UI看不到服务 网络不通或OAP端口未开放，gRPC 11800端口被防火墙拦截 检查OAP服务状态、防火墙规则、K8s Service配置，确认11800端口可达
2 服务拓扑不显示 SkyWalking UI有服务指标但没有拓扑连线 跨服务调用未传播sw8 Header，如手动使用RestTemplate未加拦截器 确认Agent版本一致、Feign/RestTemplate已自动增强、检查Agent日志有无拦截异常
3 Trace断链 一个请求在Service A有Span，Service B没有关联上 sw8 Header被中间件（如Nginx）剥离，或跨线程未传递Context 配置Nginx不剥离自定义Header（proxy_set_header sw8 $http_sw8），跨线程用TraceRunnable
4 Kafka消费链路断链 Producer的Trace和Consumer的Trace无法关联 Kafka消息Header被清理或Consumer未使用SkyWalking增强的Kafka客户端 确认Consumer也接入Agent、Kafka版本兼容、消息Header未被自定义序列化器清除
5 ES磁盘暴涨 SkyWalking ES索引日增50GB+，7天就用掉350GB 全量采样+大量Span Tag导致单条Trace数据量大，ES索引策略不当 调低采样率(sample_n_per_3_secs=3)、关闭SQL参数追踪、缩短Record TTL、ES ILM策略
6 OAP Server OOM OAP进程频繁Full GC后OOM退出 ES写入积压导致内存堆积、JVM堆配置过小、大量聚合计算 增大JVM堆到4G+、调整ES批量写入参数(bulk_actions/flush_interval)、启用L2聚合
7 Agent导致应用启动慢 应用启动时间从30s增加到2min Agent字节码增强扫描类过多、插件冲突、classpath过大 排除不需要的插件(删除plugin目录下无用jar)、开启插件预加载、优化classpath
8 采样率设置不当 生产环境全量采集导致ES写入瓶颈，或采样率太低导致慢请求未记录 sample_n_per_3_secs=-1（全量）或值过大 生产环境设3~5、慢请求和错误请求自动全量采集、关键接口用@Trace强制采样
9 定时任务无链路 @Scheduled定时任务在SkyWalking中无Trace SkyWalking Agent默认不追踪定时任务（非HTTP入口） 使用@Trace注解标记定时任务、或手动创建Span
10 异步线程链路丢失 CompletableFuture/线程池中的操作没有Trace上下文 线程切换时ContextSnapshot未传递，ThreadLocal丢失 使用TraceRunnable/TraceCallable包装、或手动ContextManager.capture()/continued()
11 Redis链路无key信息 SkyWalking Redis Span只显示命令，不显示key plugin.jedis.trace_redis_parameters=false（默认关闭防止敏感信息泄露） 按需开启（注意可能记录敏感数据），或用@Tag手动记录关键key
12 告警通知延迟 SkyWalking告警触发后5分钟才收到钉钉通知 Webhook接口超时、告警通知服务队列积压 告警通知服务异步化、增加超时配置、Webhook接口增加重试机制
13 多实例同名服务无法区分 同一服务3个实例在UI上显示相同名称，无法定位哪个实例有问题 agent.service_name配置相同但未区分instance 默认会自动附加hostname，如需自定义可设置SW_AGENT_INSTANCE_NAME
14 Gateway链路追踪不生效 Spring Cloud Gateway接入Agent后无链路数据 Gateway基于WebFlux（Netty），默认MVC插件不生效 使用skywalking-agent 8.8+版本，确保reactive-plugin已加载，检查plugin目录
15 大批量数据导入导致Agent OOM 设备数据批量导入时应用OOM SkyWalking为每条数据库操作创建Span，批量操作10000条=10000个Span 限制trace.span_limit=300、批量操作用@Trace包装整个方法而非逐条追踪、增大Agent内存

十五、总结

SkyWalking是分布式系统可观测性的核心工具。在实际场景中，12个微服务全部接入SkyWalking后，从设备告警产生到通知的完整链路可视化，任何节点的异常都能在分钟级定位。核心收益：

  1. 链路可视化：一个请求经过的所有服务、每个节点的耗时、错误信息一目了然，排查时间从小时级降到分钟级
  2. 服务拓扑：新人看拓扑图就能理解微服务架构，依赖关系一目了然
  3. 告警联动：Metrics发现异常 → Tracing定位问题 → Logging查看详情，三支柱协作
  4. 业务关联：Correlation上下文传播让矿区ID、操作人等业务信息贯穿全链路
  5. 零侵入：Java Agent字节码增强，只需加JVM参数，不改动业务代码
  6. Profile剖析：不改代码、不加日志，精确定位方法级性能瓶颈

接入SkyWalking后，排查问题从”登录N台服务器grep日志”变成”在UI上点几下”，效率提升10倍以上。对于微服务架构的系统，全链路监控不是可选项，而是必选项。
