接口幂等性设计——防重复提交的完整方案

发布于 2024-08-25 分类：技术, 2024, 分布式 👁

前言

2022年学过基础的接口幂等方案，2024年在实际项目中遇到了远比教科书复杂的幂等问题。井下矿车调度指令被MQ重复消费导致同一车辆被调度到两条路线、安全告警接口被Feign重试触发两次告警让值班人员疲于奔命、设备巡检提交按钮被工人的防爆终端双击导致两条巡检记录、瓦斯浓度超限告警因重复提交触发了三次紧急停机流程——每一件都是真金白银的生产事故。

幂等性远不是”加个Token”就能解决的。它需要根据业务场景的语义特性选择不同方案：查询类接口天然幂等、状态类操作靠状态机保证、写入类操作靠唯一键去重、并发修改靠乐观锁防护。这篇文章将从幂等性理论出发，系统梳理幂等性设计的完整方案，覆盖幂等性定义与数学语义、幂等场景分类与识别、Token机制防前端重复提交、唯一业务键防MQ重复消费、状态机防业务重复流转、乐观锁防并发修改、去重表通用兜底、分布式幂等（Redis+Lua）、幂等与分布式事务的关系、幂等框架设计、实际项目15个真实问题、方案选型决策树、踩坑记录与最佳实践等核心主题，并结合实际项目的实战经验，给出落地方案和踩坑记录。

幂等性定义与数学语义

什么是幂等性

幂等性（Idempotency）一词来源于数学，原意是”多次运算产生相同结果”。在HTTP协议中，PUT和DELETE被定义为幂等方法，而POST不是。在分布式系统中，幂等性意味着：同一操作执行一次和执行多次所产生的效果相同，系统状态一致。

不需要幂等的场景

Token机制——防前端重复提交

原理

Token机制是防止前端重复提交最常用的方案。核心思想是：请求前先获取一个一次性Token，提交时携带Token，服务端验证并消费Token，重复请求因Token已消费而被拒绝。

状态机——防业务状态重复流转

原理

状态机幂等是最优雅的方案——它不需要引入任何额外组件，而是利用业务自身的状态流转规则来保证幂等。核心思想是：只有特定状态才能执行特定操作，重复请求时状态已变更，操作自然被拒绝。

状态机幂等原理：

  1. 创建操作：PENDING -> DISPATCHED（只有PENDING状态才能调度）
  2. 重复调度：当前状态已经是DISPATCHED，不满足条件，直接跳过
  3. 取消操作：PENDING/DISPATCHED -> CANCELED（只有这两个状态才能取消）
  4. 重复取消：当前状态已经是CANCELED，不满足条件，直接跳过

乐观锁——防并发修改

原理

乐观锁通过版本号（version）机制防止并发修改冲突。每次更新时检查版本号是否匹配，匹配则更新并将版本号+1，不匹配则说明已被其他请求修改。

乐观锁实现

乐观锁 vs 悲观锁

锁机制 | 无锁，冲突时重试 | 数据库行锁

  • 维度 | 乐观锁 | 悲观锁
  • 实现方式 | version字段 + CAS | SELECT … FOR UPDATE
  • 并发性能 | 高（无锁等待） | 低（锁等待）
  • 冲突处理 | 失败重试 / 返回错误 | 串行执行
  • 适用场景 | 读多写少，冲突概率低 | 写多，冲突概率高
  • 死锁风险 | 无 | 有
  • 数据库依赖 | 通用（MySQL/PG/Oracle） | 依赖数据库行锁实现
  • 智慧矿山场景 | 设备里程累加、状态更新 | 库存扣减、资源分配
  • 代码侵入性 | 低（加version字段） | 中（需要手动加锁）
  • 事务持有时间 | 短 | 长（锁持有期间）

去重表——通用兜底方案

原理

当业务自身没有合适的幂等机制时，去重表是最通用的兜底方案。核心思想是：将每个请求的唯一标识记录到去重表中，重复请求因为唯一约束被拦截。

分布式幂等——Redis + Lua

为什么需要分布式幂等

在微服务架构中，多个服务实例同时运行，传统的本地幂等机制可能不够。Redis + Lua方案提供了跨实例的分布式幂等能力。

分布式幂等架构：

  1. 所有实例共享同一个Redis
  2. Lua脚本在Redis中原子执行
  3. 不会出现两个实例同时通过幂等检查的情况
  4. 性能远优于数据库去重表

幂等与分布式事务的关系

幂等是分布式事务的前提

幂等与分布式事务的关系：

  • 分布式事务协议（TCC / Saga / Seata AT）
  • 都依赖幂等性：
  • TCC模式：
  • Try -> Confirm/Cancel
  • -> Confirm/Cancel可能被重试 -> 必须幂等
  • -> 否则：Confirm执行两次 = 资源被扣两次
  • Saga模式：
  • T1 -> T2 -> T3 -> … -> Tn
  • -> 任一Ti失败 -> 执行补偿Ci
  • -> Ci可能被重试 -> 必须幂等
  • -> 否则：补偿执行两次 = 资源被加两次
  • Seata AT模式：
  • -> 全局事务提交/回滚时，各RM可能重复收到指令
  • -> undo_log的分支事务ID唯一 -> 天然幂等
  • -> 但业务层面的补偿操作仍需幂等
  • 结论：
  • -> 幂等性是分布式事务的必要条件
  • -> 不实现幂等 = 分布式事务无法正确运行
  • -> 先实现幂等，再上分布式事务

总结

幂等性设计是分布式系统的基本功。在实际场景中，我们从一次次生产事故中认识到：幂等性不是锦上添花，而是系统可靠性的底线。

核心认知：能用业务自身特性保证幂等（状态机、唯一键）就不要引入额外组件；幂等判断要在业务逻辑之前；幂等操作要保证原子性。Token机制防前端重复提交，唯一业务ID防MQ重复消费，状态机防业务重复流转，乐观锁防并发修改，去重表是通用兜底方案，Redis+Lua是分布式幂等的高性能选择，多层联合是极端高安全场景的最后防线。

实际项目的15个真实问题告诉我们：每一个幂等缺陷背后，都是真实的生产事故。矿车调度重复导致安全风险、瓦斯告警重复触发停机影响生产、物资出库并发扣减导致库存为负——这些问题不是假设，而是教训。关键是根据业务场景选择最合适的方案，在安全与性能之间找到平衡点。
