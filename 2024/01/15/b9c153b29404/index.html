本地消息表实战——分布式事务的最终一致性方案

发布于 2024-01-15 分类：技术, 2024, 分布式 👁

前言

实际项目在2024年初完成了核心业务模块的微服务拆分后，分布式事务问题立刻成为横亘在团队面前的一道硬坎。矿井安全监控服务（safety-service）检测到瓦斯超限时，需要同步联动设备调度服务（device-service）执行紧急停机、同时通知生产调度服务（order-service）中止当前工单——三个服务、三个数据库、三种业务状态，必须保持一致性。Seata AT模式在上线初期确实解决了大部分问题，但全局锁在矿井设备高频数据采集场景下成了性能瓶颈，一次全局事务的锁定时间动辄超过500ms，严重时甚至引发锁超时回滚。

实际项目中，大部分业务对实时一致性要求并没有想象中那么苛刻——工单状态晚几百毫秒更新完全可以接受，库存扣减延迟一两秒也不影响矿井安全运行。本地消息表方案正是为这类场景量身定制的：简单、可靠、没有全局锁的性能开销，成为实际项目生产环境使用频率最高的分布式事务方案。

本文将系统性地梳理本地消息表在实际项目中的完整实战经验，从核心原理到表结构设计、从事务消息投递到幂等消费、从定时任务调度到监控告警、从方案对比到生产踩坑，力求给出一份可直接落地的工程实践指南。

一、为什么需要本地消息表

1.1 分布式事务的困境

微服务拆分后，实际项目面临的核心挑战之一就是跨服务数据一致性。单体架构下一条SQL就能搞定的业务操作，微服务架构下变成了跨网络、跨数据库的分布式调用：

单体架构（一条事务搞定）:

  • BEGIN;
  • INSERT INTO orders (…); – 创建工单
  • UPDATE inventory SET stock=stock-1; – 扣减库存
  • INSERT INTO alert_log (…); – 记录告警
  • COMMIT;
  • 所有操作在同一个数据库事务中，天然保证一致性
  • 微服务架构（三个独立事务）:
  • +——————+ +——————+ +——————+
  • order-service | | device-service | | safety-service
  • BEGIN; | | BEGIN; | | BEGIN;
  • INSERT INTO | | UPDATE device | | INSERT INTO
  • orders (…); | | SET status= | | alert_log (…);
  • COMMIT; – 成功 | | ‘STOPPED’; | | COMMIT; – 成功
  • +——————+ | COMMIT; – 失败!| +——————+
  • 设备停机失败，但工单已创建、告警已记录
  • 三个服务状态不一致！

项目的业务特征决定了分布式事务方案的选型方向：

业务场景 一致性要求 并发量 延迟容忍 推荐方案
瓦斯超限→紧急停机 强一致 高 零容忍 Seata TCC

可以看到，实际项目中超过80%的跨服务调用场景对一致性要求是”最终一致”而非”强一致”，本地消息表方案天然契合这些业务场景。

二、本地消息表核心原理

2.1 方案整体架构

本地消息表方案的核心思想是：将分布式事务拆解为”本地事务+消息通知”，通过消息的可靠投递和消费来保证最终一致性。

本地消息表方案整体架构:

  • 实际项目 - 本地消息表方案

  • | 上游服务 | | 下游服务 |
  • | (order-service) | | (device-service) |
  • | | | |
  • | +————-+ | RocketMQ | +————-+ |
  • | | 业务操作 | | ==========> | | 消费消息 | |
  • | | (本地事务) | | | | (幂等处理) | |

2.2 核心流程详解

本地消息表的完整执行流程包含六个步骤：

本地消息表执行流程:

  • 步骤1: 业务操作 + 写入消息表（同一个本地事务）
  • BEGIN;
  • INSERT INTO orders (order_no, product_id, count, status)
  • VALUES (‘ORD-20240115-001’, ‘P-D003’, 5, ‘CREATED’);
  • INSERT INTO local_message (message_id, topic, content, status)
  • VALUES (‘MSG-UUID-001’, ‘inventory_decrease’,
  • ‘{“orderId”:1001,”productId”:”P-D003”,”count”:5}’,
  • 0); – 0=待发送
  • COMMIT;
  • 事务成功: 订单已创建 + 消息已记录（原子性保证）
  • 事务失败: 订单未创建 + 消息未记录（一起回滚）
  • 步骤2: 定时任务扫描待发送消息
  • SELECT * FROM local_message
  • WHERE status = 0
  • AND next_retry_time <= NOW()
  • AND retry_count < max_retry
  • ORDER BY create_time ASC
  • LIMIT 100;
  • 步骤3: 发送消息到MQ
  • RocketMQTemplate.syncSend(“inventory_decrease”, message);
  • 发送成功 → status = 1 (已发送)
  • 发送失败 → retry_count++ , status = 0 (待重试)
  • 步骤4: 下游服务消费消息
  • @RocketMQMessageListener(topic = “inventory_decrease”)
  • public void onMessage(String message) {
  • // 幂等校验 → 执行业务 → 确认消费
  • }
  • 步骤5: 下游服务执行业务操作（本地事务）
  • BEGIN;
  • UPDATE inventory SET stock = stock - 5 WHERE product_id = ‘P-D003’;
  • INSERT INTO inventory_log (order_id, op) VALUES (1001, ‘扣减’);
  • COMMIT;
  • 步骤6: 确认消息已处理（MQ自动ACK）
  • 消费成功 → RocketMQ ACK → 消息不再投递
  • 消费失败 → RocketMQ NACK → 消息重试投递

2.3 关键设计保证

本地消息表方案之所以可靠，关键在于以下三个设计保证：

三大可靠性保证:

  • 保证1: 本地事务原子性
  • 业务操作和消息写入在同一个数据库事务中
  • 要么同时成功，要么同时失败
  • 不存在”业务成功了但消息没写”的情况
  • 保证2: 消息必达性
  • 定时任务持续扫描 + 指数退避重试 + 最大重试次数兜底
  • 即使MQ短暂不可用，消息也不会丢失
  • 重试失败的消息进入人工告警流程
  • 保证3: 消费幂等性
  • 下游服务通过唯一业务ID去重
  • 同一条消息无论消费多少次，业务结果一致
  • 保证消息重复消费不会导致数据错误

2.4 异常场景分析

本地消息表方案需要覆盖所有可能的异常场景，确保在各种故障情况下数据最终一致：

异常场景 影响 处理机制 结果
业务事务回滚 消息未写入 无消息需要发送 一致
业务事务成功，MQ发送失败 消息待发送 定时任务重试发送 最终一致
MQ发送成功，消费者未收到 消息已发送 MQ重试投递 最终一致
消费者收到消息，业务处理失败 消息待消费 MQ重试投递 最终一致
消费者处理成功，ACK失败 消息重复消费 幂等校验去重 最终一致
定时任务执行期间宕机 消息未发送 另一个实例接管发送 最终一致
同一条消息被发送两次 重复消费 幂等校验去重 最终一致
消费者长时间不可用 消息堆积 MQ重试+死信队列 告警人工介入

3.2 字段设计说明

字段 设计考量 说明
message_id 唯一标识，防止重复写入 UUID生成，全局唯一，UK约束兜底
trace_id 链路追踪，问题排查 SkyWalking TraceId，便于跨服务追踪
topic / tag MQ路由，精确投递 对应RocketMQ的Topic和Tag，支持精细路由

source_service / target_service 服务追踪，问题定位 明确消息的生产者和消费者，便于排查
status 状态机，流程控制 0待发送→1已发送→2已消费，异常时3失败→4死信
retry_count / max_retry 重试控制，避免无限重试 指数退避重试，超限后进入死信
next_retry_time 重试调度，避免密集重试 配合定时任务，实现延迟重试
error_msg 错误记录，问题排查 记录最后一次失败原因，便于定位

3.3 索引设计分析

索引设计决策:

  • 索引1: uk_message_id (message_id)
  • 用途: 防止消息重复写入
  • 场景: 并发创建同一业务消息时，UK约束保证只写入一条
  • 代价: INSERT时额外维护唯一索引
  • 索引2: idx_status_next_retry (status, next_retry_time)
  • 用途: 定时任务高效扫描待发送消息
  • 场景: WHERE status=0 AND next_retry_time<=NOW() ORDER BY create_time
  • 代价: 状态变更时需更新索引
  • 优化: 联合索引避免回表，覆盖查询条件
  • 索引3: idx_biz_type_biz_id (biz_type, biz_id)
  • 用途: 按业务维度查询消息状态
  • 场景: 查询某个订单/设备的消息发送情况
  • 代价: INSERT时额外维护索引
  • 索引4: idx_create_time (create_time)
  • 用途: 历史消息归档时按时间范围批量删除
  • 场景: DELETE FROM local_message WHERE create_time < ‘2024-01-01’
  • 代价: 额外索引空间

3.4 消息状态机

消息状态流转遵循严格的状态机模型，确保状态变更的合法性和可追溯性：

消息状态流转图:

  • | 0-待发送 | <— 初始状态
  • |
  • 定时任务发送
  • / \
  • 发送成功 发送失败
  • / \
  • +——+——+ +——+——+
  • 1-已发送 | | 3-发送失败
  • +——+——+ +——+——+
  • MQ投递到消费者 retry_count < max_retry ?
  • | / \
  • +——+——+ 是: 回到0 否: 进入死信
  • | 2-已消费 | (指数退避) +——-+——+
  • +————-+ | 4-已死信 |
  • |
  • 人工介入处理
  • 状态变更规则:
  • 0→1: 定时任务发送MQ成功
  • 0→3: 定时任务发送MQ失败
  • 3→0: 重试次数未超限，重置为待发送（附带退避延迟）
  • 3→4: 重试次数超限，进入死信队列
  • 1→2: 下游服务消费确认（通过回调接口或主动查询）

3.5 分库场景下的消息表归属

在实际项目的微服务架构中，每个服务拥有独立数据库，消息表应归属哪个库是一个关键设计决策：

消息表归属规则: 消息表必须与业务表在同一个数据库实例中

  • 正确的归属:
  • order-service 数据库 (order_db)
  • +– orders 表
  • +– order_item 表
  • +– local_message 表 <— 与业务表同库，保证本地事务原子性
  • 下单事务:
  • BEGIN;
  • INSERT INTO orders (…); – 业务操作
  • INSERT INTO local_message (…); – 消息记录
  • COMMIT; – 两个操作在同一个事务中，原子性有保证
  • 错误的归属:
  • order-service 数据库 (order_db)
  • +– orders 表
  • +– order_item 表
  • 消息数据库 (message_db) <— 独立的消息库
  • +– local_message 表
  • 下单事务:
  • BEGIN;
  • INSERT INTO orders (…); – order_db 事务
  • COMMIT;
  • BEGIN;
  • INSERT INTO local_message (…); – message_db 事务
  • COMMIT; – 两个独立事务！如果第二步失败，订单已创建但消息未记录！

实际项目的消息表分布情况：

服务 数据库 消息表 消息类型
order-service order_db local_message 工单创建→设备调度、工单完成→库存回补
device-service device_db local_message 设备状态变更→安全告警、设备停机→工单中止
safety-service safety_db local_message 安全告警→设备联动、告警解除→工单恢复
inventory-service inventory_db local_message 库存扣减→采购通知、库存预警→补货提醒

6.1 集群部署下的并发问题

定时任务在集群部署时，如果每个实例都独立执行消息扫描，会导致同一条消息被多个实例同时发送：

集群部署下的重复发送问题:

  • 实例A: SELECT … WHERE status=0 LIMIT 100 → 获取消息列表 [M1, M2, M3]
  • 实例B: SELECT … WHERE status=0 LIMIT 100 → 获取消息列表 [M1, M2, M3]
  • 实例C: SELECT … WHERE status=0 LIMIT 100 → 获取消息列表 [M1, M2, M3]
  • 三个实例同时发送M1 → MQ收到3条相同的消息 → 下游重复消费！
  • 解决方案:
  • 方案1: 分布式锁（推荐）
  • 定时任务执行前获取Redis分布式锁，只有一个实例执行
  • 优点：实现简单，性能好
  • 缺点：依赖Redis，锁过期需注意
  • 方案2: 数据库行锁
  • SELECT … FOR UPDATE 获取消息时加行锁
  • 优点：不依赖外部组件
  • 缺点：性能差，锁粒度粗
  • 方案3: 乐观锁
  • UPDATE status=1 WHERE messageId=? AND status=0
  • 更新成功才发送，更新失败则跳过
  • 优点：无锁竞争，性能好
  • 缺点：需要额外的UPDATE操作

十、生产环境踩坑实录

在实际项目的实际生产环境中，本地消息表方案经历了大量真实场景的考验。以下记录15个最具代表性的生产问题及其解决方案：

序号 问题类别 问题描述 根因分析 解决方案 效果
1 消息丢失 工单创建成功但库存未扣减 业务方法加了@Transactional，消息创建在同事务中，但业务异常回滚导致消息一起回滚 消息创建必须在业务事务内部，不能在事务外创建 消息零丢失
2 重复消费 库存被扣减两次 MQ重试投递，消费端幂等校验使用了Redis SETNX但Key过期时间仅设了5分钟，第二次消费时Key已过期 幂等Key过期时间设为72小时，并增加数据库UK约束兜底 重复消费率降为0
3 消息堆积 待发送消息从几十条暴增到8000+ device-service定时任务因Full GC暂停，5分钟未执行扫描 优化JVM参数（G1GC+堆4G），增加定时任务超时告警 堆积量恢复正常
4 死信告警 死信消息突然产生5条 inventory-service在做版本升级，服务不可用长达30分钟 调大max_retry至8，增加退避上限至120分钟 版本升级期间零死信
5 并发发送 同一消息被两个实例同时发送 新增实例后定时任务未加分布式锁 引入Redisson分布式锁+乐观锁CAS双重保障 并发发送问题消除
6 消息表膨胀 order-service消息表超过300万行 已消费消息未归档，查询性能严重退化 建立归档任务，已消费消息7天后迁移历史表 主表数据量降低92%
7 事务超时 下单接口偶发超时 一次事务中创建3条消息（库存+设备+通知），消息内容过大（含大量冗余字段） 精简消息内容仅保留必要字段，消息体从2KB压缩至0.5KB 事务耗时降低60%
8 消费顺序 工单取消消息先于工单创建消息被消费 两个消息分属不同Topic，消费进度不一致 同一业务流程的消息使用相同Topic+不同Tag，保证顺序 消费顺序正确
9 状态不一致 消息状态为”已发送”但下游从未收到 RocketMQ Broker磁盘故障，消息写入后未刷盘 RocketMQ主从同步复制+同步刷盘，消息发送改为syncSend 消息零丢失
10 幂等失效 设备停机指令重复执行 幂等表与业务表不在同一个库，幂等校验与业务操作非原子 幂等日志写入业务库（UK约束），保证校验与操作原子性 幂等100%可靠
11 死信误判 消息重试5次后进入死信，实际MQ只是短暂抖动 max_retry=5过小，退避时间不够等到MQ恢复 max_retry调整为8，最大退避调整为120分钟，加入随机抖动 死信产生率降低80%
12 消费阻塞 safety-service消费线程被一条大消息阻塞 告警消息体包含完整设备快照（10MB），反序列化耗时过长 限制消息体大小不超过1MB，大消息改为引用ID+按需查询 消费延迟降低95%
13 回调失败 下游消费成功但回调上游更新状态失败 回调接口超时时间过短（1秒），网络抖动时频繁失败 回调超时调整为5秒+重试3次，上游增加定时主动查询兜底 状态一致率99.99%
14 索引失效 定时任务扫描待发送消息耗时从10ms暴涨到5s status字段选择性差（90%以上是已消费状态），索引效率低 定时任务查询条件增加create_time范围限制（近1小时），索引生效 扫描耗时恢复至10ms
15 分库遗漏 拆分新服务时忘记在新库创建local_message表 新服务独立部署后直接使用本地消息表注解，但库中无此表 建立服务创建检查清单，包含local_message表创建步骤 新服务上线零遗漏

十二、总结

本地消息表是实际项目中最实用、使用频率最高的分布式事务方案，全年承载了超过2000万条跨服务消息的可靠投递。相比Seata的全局锁机制，本地消息表在性能、可靠性和运维成本上具有明显优势，尤其适合大部分对一致性要求为”最终一致”的业务场景。

核心要点回顾：

  1. 本地事务原子性：业务操作与消息记录在同一个数据库事务中，不存在”业务成功但消息丢失”的情况。这是整个方案可靠性的基石。

  2. 消息必达性：定时任务持续扫描+指数退避重试+死信告警+人工介入，形成完整的消息投递保障链条。在实际项目全年运行中，消息投递成功率达到99.97%。

  3. 消费幂等性：通过唯一业务ID去重+数据库UK约束兜底，确保消息重复消费不会导致数据错误。这是本地消息表方案的业务方责任，必须在设计阶段就考虑清楚。

  4. 集群高可用：分布式锁+乐观锁双重保障，确保定时任务在集群部署下不会重复发送消息。

  5. 可观测性：消息表直接存储在数据库中，查询和排查非常直观，配合Grafana监控大盘和分级告警，问题发现和定位效率极高。

  6. 运维简便：不依赖Seata TC Server等额外组件，运维成本极低。消息表归档、死信处理等运维操作都有成熟的自动化方案。

本地消息表并非银弹。对于需要强一致性的核心安全链路（如瓦斯超限紧急停机），仍需使用Seata TCC方案。但在实际项目80%以上的跨服务调用场景中，本地消息表方案是最佳选择——简单、可靠、高性能，这三点在工程实践中比理论上的完美一致性更重要。
