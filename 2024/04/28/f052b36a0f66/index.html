DDD聚合与限界上下文——复杂业务的拆分边界

发布于 2024-04-28 分类：技术, 2024, 架构 👁

前言

在实际场景中，我们面对的业务远不止简单的增删改查——采购域涵盖采购申请、供应商管理、合同审批、物资验收；设备域涵盖设备台账、维修工单、巡检计划、备件领用；安全域涵盖安全巡检、隐患排查、报警联动、应急预案。系统上线不到半年，领域模型就从最初的 20 个类膨胀到 300+ 个类，一个 Service 动辄数千行代码，跨模块的事务耦合让任何改动都如履薄冰。

根本原因在于：没有划清聚合边界和限界上下文。聚合（Aggregate）决定了数据的强一致性边界，限界上下文（Bounded Context）决定了模型的语义边界。这两者共同构成了 DDD 拆分复杂业务的核心方法论。

本文以实际项目为贯穿案例，从聚合设计原则到限界上下文划分，从领域事件通信到上下文映射模式，系统性剖析 DDD 中最关键的两个概念——聚合与限界上下文，并结合 15 个真实项目问题，给出可落地的解决方案。

一、聚合：数据一致性的守护者

1.1 什么是聚合

聚合是一组相关对象的集合，作为数据修改的原子单元。每个聚合有一个聚合根（Aggregate Root），外部只能通过聚合根访问聚合内的对象。

1.3 聚合设计原则详解

原则 描述 违反后果 实际项目教训
一致性边界 聚合内的数据必须保证强一致性 数据不一致，业务规则被违反 采购订单金额与明细小计不一致
小聚合优先 聚合应尽量小，理想情况下只包含聚合根 高并发冲突，锁等待严重 设备聚合包含维修记录，导致维修和巡检互相阻塞
通过 ID 引用 聚合间通过 ID 引用而非直接持有对象引用 聚合边界模糊，加载代价大 采购订单直接持有供应商对象，加载订单必须级联查供应商
单事务单聚合 一个事务只修改一个聚合实例 分布式事务，性能瓶颈 一个事务同时修改订单和库存，事务超时频发
最终一致性 跨聚合的一致性通过领域事件实现 系统耦合，无法独立部署 订单支付后同步调用库存扣减，支付服务宕机导致下单失败
聚合根唯一入口 外部只能通过聚合根修改聚合内对象 不变量被绕过，业务规则失效 直接修改工单日志绕过工单状态校验

  • 只有 APPROVED 状态可发货
  • items 不能为空
  • 发货数量 <= 订单数量

五、上下文映射

5.1 上下文映射模式详解

映射模式 含义 典型场景 集成方式 实际项目示例
开放主机服务（OHS） 一个上下文提供标准API供其他上下文调用 上游提供稳定的接口 REST/gRPC 标准接口 供应商域提供 Supplier API
发布语言（PL） 上下文间通过标准事件格式通信 事件驱动的跨上下文通信 事件/DTO PurchaseOrderApprovedEvent
防腐层（ACL） 在自己的上下文中建立翻译层，隔离外部模型 下游隔离上游模型 适配器 + 翻译器 工单域通过 ACL 对接设备域
客户-供应商（C/S） 下游依赖上游，上游需考虑下游需求 有协作关系的上下文 事件驱动 + 接口契约 采购域（供应商）→ 库存域（客户）
遵奉者（Conformist） 下游完全遵循上游模型 下游无法影响上游 直接使用上游模型 工单域遵奉第三方 ERP 接口
共享内核（Shared Kernel） 两个上下文共享部分模型 共用基础类型 共享 JAR 包 Money、EquipmentLevel 等值对象
分道扬镳（Separate Ways） 两个上下文完全不通信 无关的上下文 无 安全域与财务域无直接关联
合作关系（Partnership） 两个团队协同开发，接口变更需协商 紧密耦合的上下文 同步调用 + 版本协商 采购域与供应商域

十一、15个真实项目问题与解决方案

以下是结合实际项目实战中遇到的典型问题汇总：

序号 问题 现象 原因 解决方案
1 贫血模型泛滥 Entity 只有 getter/setter，业务逻辑全在 Service 层，PurchaseOrderService 膨胀到 3000+ 行 未理解 DDD 的充血模型理念，按事务脚本模式开发 将业务逻辑迁移到聚合根和实体中，Service 只做编排；采用测试驱动保证重构安全
2 聚合边界过大 PurchaseOrder 聚合包含入库记录、审批记录、付款记录等所有关联数据，加载一次耗时 2 秒 把弱一致性数据放进聚合，混淆了”关联”与”一致性” 聚合只包含强一致数据；入库记录、审批记录独立为聚合，通过 orderId 引用关联
3 跨聚合强一致性 使用 @Transactional 同时修改 PurchaseOrder 和 Stock，分布式环境下事务经常超时 一个事务跨多个聚合，锁竞争严重 一个事务只修改一个聚合，跨聚合通过领域事件 + 最终一致性
4 值对象使用原始类型 金额用 BigDecimal，地址用 String，没有封装业务规则，金额为负数、地址不完整等问题到处出现 原始类型偏执（Primitive Obsession），用基本类型替代领域概念 定义 Money、ShippingAddress、SafetyLevel 等值对象，在构造器中封装校验规则
5 聚合间直接引用对象 PurchaseOrder 直接持有 Supplier 对象引用，加载订单时必须级联查询供应商信息 违反”通过 ID 引用”原则，导致聚合边界模糊 PurchaseOrder 只持有 supplierId: Long，需要供应商信息时通过 SupplierRepository 单独加载
6 领域事件丢失 采购订单入库后库存未增加，或事件重复消费导致库存多次入库 事件发布与业务事务不在同一个事务中，或消费端未做幂等 采用事务性发件箱模式（Transactional Outbox）；消费端做幂等校验
7 N+1 查询问题 采购订单列表页查询 50 条订单，产生 51 条 SQL（1 查订单 + 50 查明细） JPA 懒加载 PurchaseOrderItem，遍历时逐条查询 使用 JOIN FETCH 或 EntityGraph 一次性加载；列表查询走 CQRS 读模型
8 状态机实现混乱 if-else 链判断订单状态，漏掉某些转换路径，出现已取消订单被审批的 Bug 状态转换规则散落在多个方法中，没有统一的状态机 使用状态枚举（如本文 OrderStatus），显式定义合法转换
9 领域模型与数据库模型耦合 领域对象直接加 @Entity 注解，加新字段要改数据库，改数据库影响领域逻辑 共享模型策略，领域层直接依赖持久化框架 采用双模型转换，领域模型和数据模型分离，通过 Converter 互转
10 采购入库与库存扣减不一致 采购订单确认入库但库存未增加，或超时取消后库存已增加 入库事件未被库存上下文消费，或消费顺序错误 确保事件订阅的完整性；添加入库超时自动补偿机制；定时校验一致性
11 并发修改冲突 两个采购员同时修改同一采购订单，后提交的覆盖前提交 乐观锁未配置，或聚合更新未检查版本号 使用 @Version 乐观锁；聚合根增加 version 字段，更新时检查
12 仓储接口泄露查询需求 PurchaseOrderRepository 中出现 findBySupplierNameLike、findByStatusAndCreateTimeBetween 等大量查询方法 混淆了仓储（命令）和查询的职责 仓储只保留按 ID 查询和保存；复杂查询走 CQRS 查询端
13 应用服务包含业务逻辑 采购折扣校验、安全等级评估写在了 ApplicationService 中，导致无法复用 没有区分领域服务和应用服务的职责边界 业务逻辑下沉到领域服务或聚合根中，应用服务只做编排
14 值对象不可变性被破坏 Money 类提供了 setAmount 方法，外部直接修改金额绕过校验 值对象设计为可变，违反值对象不可变原则 移除 setter，所有修改方法返回新实例；字段加 final 修饰
15 读模型与写模型不分 采购订单列表查询需要关联供应商表、物资表，直接加载 PurchaseOrder 聚合做关联查询，SQL 极慢 用领域模型（写模型）做查询，聚合加载了不必要的关联数据 引入 CQRS，读模型使用视图或 ES，按展示需求反范式化数据

13.3 聚合大小权衡

维度 小聚合 大聚合
一致性保证 聚合内强一致，跨聚合最终一致 聚合内全部强一致
并发性能 锁范围小，并发度高 锁范围大，并发冲突多
加载性能 加载数据少，速度快 加载数据多，速度慢
代码复杂度 需要领域事件协调 不需要事件，直接事务
适用场景 高并发、分布式 低并发、单体
实际项目 采购订单 + 库存（高并发） 安全等级评估（低并发）

总结

聚合和限界上下文是 DDD 中应对复杂业务拆分的两大利器。聚合决定了数据一致性的边界——一个事务只修改一个聚合，跨聚合通过领域事件保证最终一致性；限界上下文决定了模型的语义边界——同一个概念在不同上下文中有不同的含义，防腐层隔离外部模型，防止领域被污染。

实际项目的实践告诉我们：

  1. 聚合要小：只包含必须强一致的属性和实体，宁可多一个小聚合，不要一个大聚合。大聚合是并发冲突和性能瓶颈的根源。
  2. 限界上下文要明确：每个上下文有自己的领域模型、数据库和团队，上下文间通过 OHS/PL 通信，通过 ACL 隔离外部模型。
  3. 领域事件是解耦的关键：跨聚合、跨上下文的同步通过领域事件实现，配合事务性 Outbox 模式保证事件不丢失。
  4. 防腐层必不可少：不要让外部模型的细节污染自己的领域模型，工单域的 EquipmentInfo 不是设备域的 Equipment。
  5. 充血模型是基础：业务逻辑集中在聚合根中，Service 只做编排，贫血模型是 DDD 落地的最大障碍。
  6. 按需引入 DDD：核心域完整建模，支撑域简化 DDD，通用域事务脚本即可，不要一刀切。

DDD 不是银弹，但对复杂业务系统而言，它是目前最有效的应对复杂度的方法论。关键是从业务出发，而非从数据库表出发。
