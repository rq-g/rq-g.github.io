高可用架构设计——从单点到容灾的演进之路

发布于 2024-06-05 分类：技术, 2024, 高可用 👁

前言

在实际场景中，核心业务系统（矿卡调度、安全监控、人员定位）7x24 小时运行，任何停机都可能威胁矿山安全生产。一次 Redis 主节点宕机导致整个矿卡调度系统不可用 40 分钟，让我深刻认识到：高可用不是”加个集群”就完事的，而是一个从流量入口到数据层的系统工程。从应用层到数据层，从流量入口到服务调用，每一环都要考虑故障场景和恢复方案。这篇文章从实际项目实战出发，系统梳理高可用架构设计的五个核心层次，以及每一层在真实故障中的应对策略。

一、高可用核心指标与计算模型

1.1 可用性定义与等级

1.2 可用性影响因素分析

可用性 = f(故障频率, 故障时长, 故障范围, 恢复速度)：

故障频率 ──── 消除单点 → 降低故障发生概率：

  • 故障时长 ──── 自动恢复 → 缩短故障持续时间
  • 故障范围 ──── 爆炸半径 → 限制故障影响面
  • 恢复速度 ──── 降级兜底 → 快速恢复部分服务能力

1.3 提升可用性的核心思路

6 灰度发布 降低变更风险 Nacos 元数据路由灰度

三、第二层：服务层高可用

3.3 服务降级策略

3.3.1 多级降级架构

Level 0：正常服务：

  • → 所有服务正常，完整功能可用

Level 1：远程服务降级：

  • → 下游服务超时/异常，走本地缓存
  • → 数据可能略旧，但功能可用

Level 2：本地缓存降级：

  • → 本地缓存也无数据，返回兜底/默认数据
  • → 功能受限，但不报错

Level 3：限流降级：

  • → 流量超过阈值，直接返回”系统繁忙”
  • → 保护系统不被压垮

3.4 超时与重试

3.4.1 超时设置原则

超时层级：：

  • Gateway → Service A → Service B → DB/Redis/MQ
  • 10s 5s 3s 1s/200ms/5s
  • 原则：外层超时 > 内层超时之和
  • 公式：外层超时 = 内层超时之和 x 1.5 + 重试次数 x 单次超时
  • 示例：
  • Service B 数据库查询超时 = 1s
  • Service B 自身超时 = 1s x 1.5 + 2次重试 x 1s = 3.5s ≈ 3s
  • Service A 调用 Service B 超时 = 3s x 1.5 + 1次重试 x 3s = 7.5s ≈ 5s
  • Gateway 超时 = 5s x 1.5 + 0次重试 = 7.5s ≈ 10s

金丝雀发布 先发布1个实例，观察没问题再逐步扩大
滚动发布 逐个替换实例，确保任何时候都有足够可用实例
蓝绿部署 两套环境，切换流量即可回滚
A/B测试 按用户特征分流，对比两个版本的效果
特性开关 通过配置控制功能开关，无需发布即可启用/关闭

十、常见项目问题与解决方案

在实际项目的高可用架构实践中，我们遇到了大量问题。以下是 15 个最具代表性的问题及其解决方案：

# 问题 现象 原因分析 解决方案
1 Redis 主节点宕机导致全站不可用 Redis 主节点宕机后，大量请求超时，服务线程池耗尽，级联故障导致整个系统不可用 40 分钟 应用没有设置 Redis 降级策略，Redis 不可用时所有操作阻塞；连接池没有超时配置，线程一直等待 1. Redis 操作设置合理超时（3秒）2. 实现 Redis 降级策略（本地缓存兜底）3. Redis Cluster 替代主从 + Sentinel 4. 熔断器保护，Redis 不可用时快速失败
2 MySQL 主从切换后应用报错”只读” MHA 完成主从切换，新主库已就绪，但应用仍然写入失败，报 “The MySQL server is running with the read-only option” 应用使用直连 IP 而非 VIP，主从切换后应用仍连接旧主库（已降级为从库，read_only=1）；DNS 缓存未刷新 1. 应用必须使用 VIP 连接数据库 2. 连接池配置自动重连 3. 主从切换后主动刷新连接池 4. 验证写入前检查 read_only 状态
3 K8s 滚动更新导致服务短暂不可用 发布新版本时，部分请求返回 503/502，持续约 30 秒后恢复 1. 没有配置就绪探针，新 Pod 未就绪就接收流量 2. 没有优雅停机，正在处理的请求被强制中断 3. maxUnavailable=1 导致更新期间少一个可用 Pod 1. 配置就绪探针（readinessProbe）2. 启用优雅停机（server.shutdown=graceful）3. 设置 maxUnavailable=0 4. 配置 PDB 保证最低可用副本数 5. 服务预热后再标记就绪
4 Sentinel 熔断器不生效 下游服务超时率 > 50%，但 Sentinel 熔断器没有触发，请求持续超时 1. 熔断规则只配置了异常比例模式，没配置慢调用比例模式 2. 统计时间窗口过长（60秒），未能及时感知故障 3. 降级方法中再次调用了失败的服务 1. 同时配置异常比例和慢调用比例两种模式 2. 缩短统计时间窗口为 10 秒 3. 降级方法禁止远程调用，只能用本地缓存或默认值 4. 增加熔断器状态监控指标
5 网络抖动导致大量重试雪崩 Gateway 到服务之间网络偶发抖动（200ms延迟），触发大量重试，反而把服务打挂 1. 重试没有退避策略，瞬间大量重试涌入 2. 所有请求都在同一时刻重试，形成”重试风暴” 3. 重试次数过多（5次），放大了请求量 1. 重试使用指数退避 + 随机抖动 2. 重试次数控制在 23 次 3. 只对读操作重试，写操作不重试 4. 重试前增加随机延迟（0200ms），打散重试时刻 5. 全局限流保护，重试请求也计入限流计数
6 Gateway 限流不均匀 基于 IP 限流时，大量请求来自同一个代理 IP（矿山内网出口），导致正常用户被限流 矿山内网统一出口 IP，所有矿卡设备上报的请求来源 IP 相同，基于 IP 的限流策略不适用 1. 限流维度改为 truckId 而非 IP 2. 多维度限流：IP + truckId + 接口 3. 使用 Redis + Lua 脚本实现滑动窗口限流 4. 不同接口设置不同限流阈值
7 Nacos 注册中心不可用导致服务调用失败 Nacos 集群故障时，服务无法发现其他服务实例，调用全部失败 应用只依赖 Nacos 做服务发现，没有本地缓存；Nacos 不可用时本地服务列表为空 1. Nacos 客户端开启本地缓存（nacos.cache.dir）2. 服务实例本地缓存 TTL 设置为 30 秒 3. Nacos 集群至少 3 节点部署 4. 极端场景使用硬编码的 IP 直连兜底
8 灰度发布流量比例不准 配置 10% 灰度比例，实际灰度流量达到 30%，大量用户受影响 1. 灰度路由基于 Gateway 随机策略，流量分布不均匀 2. 少量长连接保持灰度版本，比例逐渐偏移 3. 灰度实例和非灰度实例规格不同（2核 vs 4核） 1. 灰度路由基于用户 ID 取模，保证流量均匀分布 2. 灰度比例动态调整，实时监控流量分布 3. 灰度实例和非灰度实例保持相同规格 4. 灰度验证时间足够长（至少 5 分钟）
9 数据库连接池耗尽导致服务假死 高峰期数据库连接池耗尽，所有请求排队等待连接，服务响应超时但进程存活 1. 连接池大小设置过小（50），无法满足峰值需求 2. 慢查询占用连接不释放 3. 事务超时未设置，长事务持有连接 4. 连接泄露（未关闭的连接） 1. 连接池大小按公式调整：(core_count * 2) + effective_spindle_count 2. 设置连接超时（checkoutTimeout=3000ms）3. 设置事务超时（timeout=5s）4. 开启连接泄露检测（leakDetectionThreshold=60000）5. 增加慢查询告警和自动 Kill
10 RocketMQ 消费延迟导致告警不及时 安全告警消息从产生到消费延迟超过 5 分钟，矿山安全事件未及时通知 1. 消费者线程池过小，消费速度跟不上生产速度 2. 消费逻辑中包含慢操作（调用第三方接口）3. 消费失败重试占用线程 4. Topic 共享消费者组，其他消息积压影响告警消费 1. 告警消息使用独立 Topic + 独立消费者组 2. 增加消费者线程数 3. 消费逻辑中禁止远程调用，先落库再异步处理 4. 设置消费超时，超时后进入重试队列不阻塞线程 5. 告警消息消费优先级高于普通消息
11 限流后降级数据结构不完整 限流触发后返回的降级数据缺少部分字段，前端页面显示异常 降级方法返回的 DTO 是手动构造的，新增字段时忘记在降级方法中补充；降级数据没有统一的模型规范 1. 降级 DTO 复用正常返回的 DTO，缺失字段用默认值填充 2. 单元测试覆盖降级场景，校验返回数据结构 3. 降级数据模型纳入接口文档管理 4. 定期执行降级演练，验证降级数据完整性
12 MHA 切换后数据不一致 MHA 切换后业务出现主键冲突和数据丢失 1. 半同步复制超时降级为异步，切换窗口内有未同步数据 2. 自增 ID 冲突（新主库和旧主库生成相同 ID）3. 切换过程中应用仍在写入旧主库 1. 使用雪花算法替代自增 ID 2. 严格监控半同步复制状态，降级时立即告警 3. 切换前先摘除旧主库流量 4. 切换后执行数据一致性校验 5. 设置 auto_increment_offset 和 auto_increment_increment
13 Nginx 健康检查误判导致流量全丢 Nginx 将所有上游 Gateway 标记为不可用，所有请求返回 502 1. 健康检查接口响应慢（3秒），超过 Nginx 检测超时 2. 网络抖动导致健康检查超时，所有节点被剔除 3. max_fails 设置过低（1），单次失败就剔除节点 1. 健康检查接口必须轻量（直接返回 200，不做深度检查）2. max_fails 设置为 3，fail_timeout 设置为 30s 3. 配置 backup 节点，主节点全挂时启用 4. 增加本地兜底页面，502 时返回静态降级提示
14 JVM GC 停顿导致健康检查失败 服务进行 Full GC 时停顿 5~10 秒，K8s 存活探针连续失败，Pod 被 Kill 后重启 1. JVM 堆内存设置不合理，频繁 Full GC 2. 存活探针超时设置过短（1秒）3. 探针失败次数阈值过低（2次） 1. 优化 JVM 参数（-Xms=-Xmx，使用 G1/ZGC）2. 存活探针超时设置合理值（5秒）3. 失败阈值调整为 3 次 4. 增加启动探针，给足启动/预热时间 5. 监控 GC 停顿时间，超过 1 秒告警
15 故障演练和生产故障混淆 故障演练期间出现真实故障，值班人员以为是演练，未及时响应 1. 演练和生产的告警没有区分标识 2. 演练期间值班人员只看演练群，忽略真实告警 3. 演练流程没有”暂停”机制，真实故障时无法中断 1. 演练告警统一添加 [DRILL] 前缀 2. 演练通知和真实告警使用不同渠道 3. 建立”演练暂停”机制：发现真实故障立即停止演练 4. 演练指定专门的观察员，不占用 On-Call 人员 5. 演练时间选在低峰期，降低与真实故障叠加风险

十一、总结

高可用不是某个技术，而是一种系统思维。从流量入口到数据层，每一环都要考虑”如果挂了怎么办”。回顾实际项目的高可用架构演进历程，核心经验总结如下：

高可用的最高境界不是不出故障，而是出了故障用户无感知。从消除单点到自动故障转移，从降级兜底到灰度发布，从故障演练到监控告警，这五层防护缺一不可。实际项目通过这套高可用体系，核心业务可用性从最初的 99.5% 提升到了 99.97%，年度累计故障时长从 43 小时缩短至 2.6 小时。高可用建设没有终点，随着业务增长和技术演进，需要持续优化和完善。
